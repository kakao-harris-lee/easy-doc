# tools/

`easydict` 빌드 파이프라인(`src/easydict/`)에 넣을 원천 CSV를 만들기 전 단계의
**데이터 확보 도구**를 모아 둔다. `src/easydict/`는 "네트워크 없음, 외부
의존성 없음"이 설계 원칙(`DESIGN.md` §5.3)이라 로컬 CSV만 읽는다 — 여기 있는
스크립트들은 그 CSV를 네트워크로 미리 만들어 두는 별도 단계이며, 빌드
파이프라인 자체는 이 디렉터리에 있는 어떤 것에도 의존하지 않는다. 단,
`fetch_krdict.py`는 한자 판정처럼 이미 검증된 순수 함수(`easydict.normalize`의
`is_pure_hanja`/`normalize_key`)는 새로 만들지 않고 가져다 쓴다 — 이건 네트워크나
빌드 실행에 의존하는 게 아니라 코드 재사용이라 경계 위반이 아니라고 판단했다.
`extract_gaps.py`도 같은 원칙으로 `easydict.normalize`(JOSA/어미 목록/중점
문자 집합)와 `easydict.lookup.EasyDict`(매칭 로직 자체)를 가져다 쓴다 —
네트워크는 아예 안 쓰고 로컬 코퍼스와 `dist/easy_dict.sqlite3`만 읽는다.

## `extract_gaps.py`

`easy-doc` 골든 코퍼스(`data/golden/documents/*.json`, 읽기 전용)에서 현재
사전(`dist/easy_dict.sqlite3`)에 없는 용어 후보를 뽑아 `fetch_krdict.py`의
입력이 될 갭 리스트 CSV(`term,doc_freq,total_freq,sample_context,suggested_tag`)
를 만든다. 표준 라이브러리만 쓴다.

### 사용법 — 산출물은 파생물이다, 커밋하지 않는다

```bash
python3 tools/extract_gaps.py --output <원하는 경로>/gap_list.csv
```

`--golden-dir`/`--db`로 코퍼스·사전 경로를 바꿀 수 있다(기본값은 이 저장소의
실제 경로). `--output`을 생략하면 stdout에 CSV를 쓰고, 요약 통계는 항상
stderr로 나간다(파이프에 CSV만 남게).

**갭 리스트는 원천 데이터가 아니라 파생 산출물이다.** `data/raw/`(사람이
확보한 실데이터: krdict 조회 결과, 수동 선별 CSV 등)와는 성격이 다르고,
`dist/`(빌드 산출물)와도 다르다. 코퍼스나 사전이 바뀌면 다시 뽑아야 하는
값이라 **저장소에 커밋하지 않는다** — 실행이 0.25초밖에 안 걸려서
(57개 문서, 1,899건 사전 기준 실측) 파일로 보관하는 것보다 필요할 때마다
`python3 tools/extract_gaps.py --output <경로>`로 다시 뽑는 쪽이 낫다.
스크래치패드나 로컬 임시 경로에 뽑아서 그 라운드에만 쓰고 버려라. 다음
사람이 이 CSV를 커밋된 원천 데이터로 착각하면 안 된다.

**사전이 자랄수록 결과가 자동으로 좋아진다 — 이게 이 도구의 운영상 핵심
성질이다.** 후보 판정이 매 실행마다 `--db`가 가리키는 사전을 새로
읽어(`EasyDict.from_sqlite`) 이미 등재된 표제어·변형형을 통째로 소비하기
때문이다. **실측**: 사전이 92건일 때 만든 1차 갭 리스트(3,657행)에는
`차상위`,`보장법`,`중등교육법`,`국민기초생활` 같은 조각이 섞여 있었는데,
`국민기초생활 보장법`/`초·중등교육법`/`차상위계층`이 들어간 1,899건 사전으로
**같은 스크립트를 다시 돌리기만 했는데도** 그 조각들이 저절로 사라졌다 —
추출 로직을 안 고쳐도 사전이 자라면서 잡음이 준 것이다. 그래서 오래된
사전 스냅샷으로 이 스크립트를 실행하면 이미 해결된 표기(공백/중점 포함
복합어 등)가 다시 조각나 보일 수 있다 — **항상 최신 `dist/easy_dict.sqlite3`로
돌려라**, 그리고 결과를 해석할 때 "이 갭 리스트는 실행 시점의 사전 크기를
전제한다"는 걸 감안해라.

### 2차 개선(2026-08-28) — 무엇을, 왜 고쳤나

1차 산출물(3,657행)을 `fetch_krdict.py`로 947건 조회했더니 "검색결과없음"
324건 중 178건(55%)이 신조어가 아니라 **추출 결함**이었다(활용형·조사
잔재 143 / 잘린 조각 21 / 생산적 접미사 파생형 12 / 숫자+단위 2). 나머지
146건(복합어 110 + 고유명사 36)은 krdict에 원래 없는 원천 부재라 개선
대상이 아니다.

| 개선 | 방법 | 재사용한 것 |
|---|---|---|
| 활용형·조사 잔재 | `_HADA_SUFFIXES`/`_DOEDA_SUFFIXES`의 리터럴 문자열 + 선행 '하'/'되'를 뗀 파생형을 합쳐 "일반 동사 활용 꼬리표"로 씀. 1글자 꼬리표는 어간 2음절 이상일 때만, 2글자 이상 꼬리표는 어간 0음절도 허용(§코드 주석 참고) | `easydict.normalize._HADA_SUFFIXES`/`_DOEDA_SUFFIXES`, `JOSA` |
| 잘린 조각 | (a) 사전 커버리지 완전포함 판정을 최신 사전으로 다시 돌림 — 예: `국민기초생활 보장법`이 사전에 들어간 뒤로 `국민기초생활`/`보장법` 조각이 저절로 사라짐. (b) 중점(가운뎃점류)으로 이어진 인접 한글 구간을 묶어 후보로 추가 시도(법령·규정류 접미사로 끝날 때만 채택 — 열거형 중점 오탐 방지) | `easydict.lookup.EasyDict.find_all`, `easydict.normalize._MIDDLE_DOT_CHARS` |
| 생산적 접미사 | `-별/-당/-상/-내/-전/-후/-중`을 어근에서 떼어 어근을 후보로 삼음. `-상`/`-내`는 '대상'/'안내'처럼 그 자체가 완결 명사인 경우가 많아 알려진 완결 명사로 끝나면 자르지 않는 차단 목록을 따로 둠 | (신규 — 재사용할 기존 목록 없음, 코퍼스 실측으로 직접 작성) |
| 숫자+단위 | 후보 시작 바로 앞 글자가 숫자면 제외(`34만원`→제외) | (신규, 단순 정규식) |

**실측(회귀 테스트)**: `data/raw/krdict_advanced.csv`(사람이 선별한 114개
표제어)를 사전 커버리지 없이 필터 로직만 통과시켜 봤을 때 **114/114(100%)
통과** — 새 필터가 진짜 후보를 잘라내는 회귀는 없다. `krdict_fetched.csv`의
"검색결과없음" 324건 중 112건(34.6%)이 2차 산출물에서 사라졌다(178건이
이론적 상한이며, 나머지는 개별 조사 없이 이 갭 리스트만으로는 "krdict가
모르는 진짜 신조어"와 "team 분류상 fixable이었지만 이번 개선이 못 잡은 것"을
구분할 수 없어 상한 대비 비율은 보고서에만 별도로 밝혔다).

### 한계 (정직하게)

- **1글자 활용 어미 + 고유어 1음절 어간** 조합(`받고`,`남은`,`없는`)은
  의도적으로 안 거른다. 1글자 꼬리표(`고`,`은`,`는`...)를 공격적으로 걸러도
  되는 조건까지 완화하면 `참고`,`복지`,`고지`,`기한` 같은 진짜 후보(2음절
  한자어 명사의 마지막 음절이 우연히 같은 경우)까지 잘라먹는 게 더 큰
  손해라고 판단했다. 형태소 분석기 없이는 이 둘을 구분할 수 없다.
- **공백으로 이어진 새 복합어**(아직 사전에 없는 `OO OO법` 같은 이름)는
  중점과 달리 결합 시도를 하지 않는다 — 문장 대부분이 공백으로 이어진
  일반 어절 나열이라 공백 결합을 시도하면 문장 전체가 하나의 "후보"가
  되어 잡음이 폭증한다. 대신 사전이 커질수록 기존 표제어의 공백 조각
  문제는 자연히 줄어든다(위 "잘린 조각" 항목 참고). 아직 사전에 없는
  새 공백 복합어의 최초 발견은 여전히 조각난 채로 나온다.
- **생산적 접미사 차단 목록이 코퍼스 실측 기반이라 완전하지 않다.**
  `_SUFFIX_BLOCK_ENDINGS`에 없는 `-상`/`-내` 결합 완결 명사가 코퍼스에
  더 있다면 여전히 잘못 잘릴 수 있다.
- **suggested_tag는 단순 키워드 매칭이라 신뢰도가 낮다** — 최종 판단
  근거로 쓰면 안 된다(1차 산출물과 동일한 한계).

## `fetch_krdict.py`

국립국어원 [한국어기초사전](https://krdict.korean.go.kr) Open API에서 표제어
뜻풀이·한자·급수를 모아 `easydict.build`가 바로 읽는 CSV를 만든다. 표준
라이브러리만 쓴다(`urllib`, `xml.etree`, `csv`, `argparse`).

한국어기초사전은 CC BY-SA다. 사용자가 "공개 가능, 공개 의무 이행 가능"으로
결정해 이 도구를 만들었다 — 2차 저작물(이 사전)도 동일 라이선스로 공개해야
하고 저작자 표시 의무가 있다. 출력 CSV의 `출처` 컬럼에 사전명과
`target_code`를 남기는 것이 그 표시다.

### 인증키

`https://krdict.korean.go.kr/openApi/openApiRegister` 에서 이메일로 신청하면
발급된다(자동승인, 무료, 일 5만 건). **코드에 키를 넣지 마라.** `--api-key`
인자나 `KRDICT_API_KEY` 환경변수로 넘긴다.

### 사용법

**1) 먼저 dry-run으로 무엇을 몇 건 조회할지 확인한다** (키 없이도 된다):

```bash
python3 tools/fetch_krdict.py \
  --input /path/to/gap_list.csv \
  --min-doc-freq 2 --dry-run --limit 200
```

**2) 키가 오면 실제로 돌린다:**

```bash
export KRDICT_API_KEY="발급받은키"
python3 tools/fetch_krdict.py \
  --input /path/to/welfare_term_gaps.csv \
  --output data/raw/krdict_fetched.csv \
  --min-doc-freq 2 --limit 200 --delay 0.2
```

- `--limit`은 이번 실행에서 허용할 최대 API 호출 수다(기본 200 — 일일 한도
  5만 건 대비 보수적인 시험용 기본값). 큰 배치를 돌리려면 명시적으로 올려라.
- `--min-doc-freq N`으로 갭 리스트의 `doc_freq`가 N 미만인 표제어를 아예
  조회 대상에서 뺀다. 실측(`welfare_term_gaps.csv`, 3,657건): `--min-doc-freq 2`
  → 947건, `--min-doc-freq 3` → 432건.
- `--top-n`으로 입력 목록 앞쪽 N개만 자를 수 있다(갭 리스트가 이미 `doc_freq`
  내림차순이라 앞쪽이 우선순위 높은 용어다). `--min-doc-freq`와 `--top-n`을
  같이 주면 필터링 후 자른다.
- `--level level1,level2`로 초급/중급 급수만 필터링할 수 있다(level1=초급/
  level2=중급/level3=고급).
- `--gloss-length-cap N`(기본 40자)으로 gloss 자동 채움 길이 상한을 조정한다.
  "출력" 절 참고.
- `--fetch-examples`를 주면 깔끔한 단일 매치마다 view API로 예문도 시도한다
  (**미검증 기능** — "view API(예문)" 절 참고. 실패해도 나머지 결과에는
  영향 없다).
- `--dump-raw-xml DIR`로 응답 원본을 저장해 두면 파싱이 맞는지 눈으로 확인할
  수 있다.
- 입력은 `--input` 대신 stdin으로도 줄 수 있다(같은 CSV 형식).

전체 옵션은 `python3 tools/fetch_krdict.py --help`.

### 출력

컬럼: `원어,순화어,분야,뜻,예문,주의,출처,replace_strategy,risk_level,status,한자,word_grade`.
앞 10개는 `data/raw/welfare_seed_1.csv`와 같은 순서(팀 지시), 뒤 2개는
krdict 전용 정보 컬럼이다.

- **`한자`**: krdict의 `origin` 필드가 **순수 한자일 때만** 채운다
  (`easydict.normalize.is_pure_hanja()` 재사용). `주민센터`의 `origin`은
  `洞住民center`(한자+로마자 혼합)라 비운다. `easydict.build.COLUMN_ALIASES`가
  `한자`/`한자표기` 헤더를 인식하므로 **이 컬럼은 실제로 `term_hanja`에
  반영된다** — `/tmp` 격리 빌드로 직접 확인했다(검증 절 참고).
- **`word_grade`**: krdict 급수(초급/중급/고급)를 원문 그대로 남긴다.
  **주의**: `easydict.build.classify()`는 지금 `readability`를
  `replace_strategy`에서만 파생시키고(`substitute→1, gloss→2, keep→3`),
  CSV에서 `readability`를 읽는 컬럼 별칭이 `COLUMN_ALIASES`에 아예 없다.
  그래서 이 컬럼은 **아직 파이프라인에 반영되지 않는 정보 전용 컬럼**이다.
  `주의` 컬럼에도 매 행마다 이 사실을 적어 뒀다. `readability`를 실제로
  krdict 급수에서 가져오려면 `build.py`에 `readability` 컬럼 별칭을 추가하고
  `classify()`가 CSV 명시값을 존중하도록 고쳐야 한다 — `build.py`는 이번
  작업 범위 밖이라 건드리지 않았다.
- **`순화어`**: "깔끔한 단일 매치"면 정의문을 그대로 채우고
  `replace_strategy=gloss`, `risk_level=low`로 내보낸다(아래 "gloss 자동
  채움 기준" 참고). 그 외(동음이의어/다의어/검색결과없음/API실패/너무
  길거나 순환 참조인 정의)에는 비운다 — `easydict.build`가 `순화어`가
  빈 행을 조용히 건너뛰므로, 사람이 검토해서 채우기 전까지는 안전하게
  파이프라인에 들어가지 않는다.

모든 행은 `status=review`로 나온다. `주의` 컬럼에 상태가 적힌다:
- `[자동 수집, 검토 필요] ... gloss 초안으로 순화어=뜻으로 채움` — 깔끔한
  단일 매치. 사람이 검토해서 필요하면 `substitute`로 승격하면 된다.
- `[자동 수집, 검토 필요] ... 순화어는 채우지 않음(정의문 N자 > 상한 M자 /
  순환 참조 의심)` — 뜻은 채웠지만 gloss로 자동 승격하지 않았다. 사람이
  직접 짧게 다듬어 `순화어`를 채우면 된다.
- `[검토 필요] 검색 결과 없음` / `동음이의어 N건` / `의미(sense) N건` /
  `API 호출 실패: ...` — 뜻/순화어 둘 다 비어 있다.
- 표제어와 다른 표기로 매칭됐으면(`주민센터` 질의에 `동 주민 센터`가 옴)
  그 사실도 같이 적힌다.

#### gloss 자동 채움 기준

정의문이 **①길이 상한(기본 40자, `--gloss-length-cap`) 이하이고 ②순환
참조가 아닐 때만** `순화어`를 자동으로 채운다.

- **길이 상한 40자의 근거**: DESIGN.md §2.1/§4.2의 gloss 예시("정해진 법을
  안 지켜서 내는 돈" 15자, "기초생활수급자 바로 위의 저소득층" 17자)와 실제
  krdict 응답 3건(11/20/24자)이 전부 10~25자 구간이었다. 그 상한의 넉넉한
  2배를 잡아 정상 범위는 통과시키고 문장 하나를 통째로 괄호에 넣는 수준만
  거른다. "정답"은 없고, 실제 gloss 산출물을 보고 나중에 조정하면 된다.
- **순환 참조 판정**(`is_circular_definition()`): 공백을 지운 정의문 안에
  표제어 전체가 그대로 부분 문자열로 들어있으면 순환으로 본다. 예:
  `수급자`의 정의가 `수급 자격이 있는 자`이면, 공백을 지운 `수급자격이있는자`
  안에 `수급자`가 그대로 있어 순환으로 판정한다. 완벽한 판별은 아니다
  (형태소 분석이 아니라 문자열 포함 검사) — 애매하면 순환 쪽으로 판정해
  "어려운 말을 더 어려운 말로 정의"하는 사고를 막는 쪽을 택했다.
- 두 기준을 통과 못 해도 **`뜻`은 채운다** — gloss로 자동 승격은 안 하지만
  사람이 참고해서 직접 짧게 다듬을 수 있다.

#### 잘린 조각(truncation) 자동 차단

krdict 응답의 `origin`(한자 병기)이 표제어(질의어)보다 **길면**, 표제어가
갭리스트 추출 과정에서 잘린 조각이라고 보고 `순화어`/`뜻`을 채우지 않는다
(`is_truncated_fragment()`). 이유: 한자 병기는 그 표제어가 가리키는 실제
단어의 한자 표기이므로, 한자가 표제어보다 길면 표제어 쪽이 원래 단어의
일부만 남은 것이다(`하실` 질의에 한자가 `地下室`로 오면 `지하실`에서
`지`가 잘린 것).

**실측 근거(오탐 0)**: 두 차례 수집분(947+2,400건)에서 한자 병기가 있는
746행을 전수 확인했다.

| 비교 결과 | 건수 | 판정 |
|---|---|---|
| 한자 > 표제어 | 19건 | 전부 실제로 잘린 조각. **오탐 0** |
| 한자 = 표제어 | 725건 | 정상(영향 없음) |
| 한자 < 표제어 | 2건 | `외에`/`외의`[外] — 조사가 붙어 표제어가 더 긴 정상 케이스. 표본이 2건뿐이라 별도 규칙 없이 그대로 통과시킨다 |

19건 중 위험도가 특히 높았던 예: `경남 → 咸鏡南道`(경상남도가 아니라
함경남도로 잘못 매칭될 뻔함), `등록번호 → 住民登錄番號`(법인등록번호
문맥인데 주민등록번호로 응답), `두지`/`명이`/`회당` 등은 "실·국을 **두지**
아니 하는", "한 **명이**라도", "**회당** 300만 원"처럼 문장 중간의 조각이
그대로 질의어가 된 경우다.

**적용 조건과 판단**:
- `origin`이 **순수 한자일 때만**(`is_pure_hanja(origin)`) 적용한다.
  `주민센터`의 `origin`인 `洞住民center`처럼 한자+로마자가 섞이면 길이
  비교 자체가 무의미해서 애초에 검사하지 않는다.
- 길이는 **내부 공백을 지우고** 비교한다(`_compact()`). 표제어에 공백이
  있으면(`가스 마스크`) 그 공백은 음절이 아니므로 그대로 두면 비교 기준이
  흔들린다 — 공백을 포함해서 세면 공백이 있는 쪽이 부당하게 길어져
  실제로는 한자가 표제어보다 긴 잘린 조각인데도 안 걸릴 수 있다. 실데이터로는
  한자 병기가 있는 표제어 중 공백 포함 사례가 없어서(외래어처럼 공백이
  들어가는 표제어는 애초에 순수 한자 origin이 아니다) 이 케이스가 실제
  결과를 바꾸진 않았지만, 원칙은 명확히 해 뒀다.
- 판정 순서상 동음이의어/다의어 체크보다 **먼저** 검사한다 — 표제어 자체가
  잘린 조각이면 그 뒤 의미가 몇 개인지는 따질 이유가 없다.

**이 신호가 막지 못하는 것**: 길이가 같은데 뜻이 다른 동음이의 오매칭은
이 신호로 못 잡는다. `명시[名詩]`(유명한 시) vs 문서에 흔한 "~을 명시"(明示,
명확히 밝힘), `절상[切上]`(화폐 가치를 올림) vs 문맥에 따라 다른 뜻,
`각목[角木]`(모난 나무토막) 같은 경우는 한자·표제어 길이가 같아서(또는
애초에 정확히 일치하는 후보가 하나뿐이라) 이 필터를 그냥 통과한다. 이런
건 코퍼스 문맥과 대조하는 사람 검수로만 걸러진다 — `대해 → 넓고 큰 바다`
사례([588건 분석] 보고 참고)와 같은 종류의 한계로, "정확히 일치 + 단일
후보"라는 조건 자체가 입력이 노이즈면 뚫릴 수 있다는 걸 보여준다.

## `detect_consumer_overlap.py`

소비자(`easy-doc`)의 자체 치환 목록과 이 사전의 표제어·표면형이 겹치는지
찾는다. `easy-doc`의 프롬프트에는 자체 치환 목록
`DIFFICULT_WORD_REPLACEMENTS`(248건, `backend-kotlin/.../DifficultWords.kt`)가
내장돼 있고 "왼쪽 낱말은 한 글자도 남기지 마라"는 지시가 같이 실린다. 같은
낱말이 이 사전에도 있으면 — 특히 이 사전의 전략이 `gloss`("원래 말을
남겨라")나 `keep`("절대 바꾸지 마라")이면 — 한 프롬프트에 정반대 지시가
공존한다. 실측 A/B(팀 보고)에서 이 구성이 스타일 붕괴(83.9%→51.8%)와 judge
실패 증가(2건→4건)의 유력 원인 축으로 지목돼, 통합 전에 중복을 기계적으로
찾는 도구가 필요했다.

**읽기만 한다.** 소비자 목록도 `dist/`도 고치지 않는다.

### 사용법

```bash
python3 tools/detect_consumer_overlap.py \
  --consumer /path/to/DifficultWords.kt \
  --index dist/easy_dict.index.json
```

- `--consumer`: 소비자 치환 목록. 세 형식을 확장자/내용으로 자동 감지한다
  (`--format kotlin|json|text`로 강제 지정 가능):
  1. **Kotlin 소스**(`.kt`): `"금일" to "오늘",` 패턴을 정규식으로 추출한다.
     `--kt-var-name`(기본 `DIFFICULT_WORD_REPLACEMENTS`)이 가리키는 `val`
     선언부터 다음 `val` 선언 전까지만 스캔해 다른 맵·집합과 안 섞인다.
  2. **JSON 오브젝트**: `{"금일": "오늘", ...}`.
  3. **플레인 텍스트**: 한 줄에 표제어 하나, 탭이나 ` -> `로 구분된 대치어는
     있어도 없어도 된다.
- `--index`: 사전 색인 경로(기본 `dist/easy_dict.index.json`). `entries`의
  표제어(`t`)뿐 아니라 `surface_index`의 표면형(활용형·변형형)과의 충돌도
  검출한다 — 소비자 낱말이 어떤 표제어의 변형형과 우연히 같은 문자열이면
  런타임에 실제로 같은 낱말을 두 지시가 다루게 되기 때문이다.
- `--json`: 사람이 읽는 표 대신 기계 판독용 JSON 배열을 stdout에 출력한다
  (CI에서 파싱하고 싶을 때).

### 충돌 판정

- 사전 전략이 `gloss`/`keep` → **CONFLICT**(치환 지시와 보존 지시가 모순)
- 사전 전략이 `substitute`이고 대치어가 같음 → **DUPLICATE**(무해 중복)
- 사전 전략이 `substitute`이고 대치어가 다름 → **DIVERGENT**(같은 낱말을
  서로 다른 말로 바꾸라는 지시가 공존)

종료 코드: CONFLICT 또는 DIVERGENT가 1건이라도 있으면 1, 아니면 0(CI 게이트용).

### 한계

문자열 동일 여부만 본다 — 형태소 분석이나 실제 문서 문맥에서 어느 지시가
이기는지는 보지 않는다. 소비자 목록의 오타·공백 변형은 정규화 없이 그대로
실패한 매칭이 된다.

### 실측 (2026-08-30)

`easy-doc`의 실제 `DifficultWords.kt`(248건)를 이 사전 색인(2,182건)과 대조한
결과는 실행 시점 사전 상태에 따라 달라지므로, 최신 수치는 직접 위 명령으로
다시 뽑아라.

## `export_reference_contexts.py`

Kotlin 이식본을 참조 구현과 **바이트 단위로 대조**하기 위한 기대 출력 픽스처를
뽑는다. easy-doc의 Kotlin `core`가 `src/easydict/lookup.py`를 이식하는 중인데,
경계 규칙 하나만 빠져도 문서가 조용히 훼손된다(`DESIGN.md` §6.7 실측 결함:
`CCTV`에서 `CT`가 매칭돼 `C전류 변성기V`가 되는 종류). 사람 눈으로 잡히는
결함이 아니라서, 참조 구현의 실제 출력과 대조하는 것이 유일한 기계적
안전장치다.

골든 코퍼스(`../data/golden/documents/*.json`, 읽기 전용) 56건의
`source_text`마다 `EasyDict.build_prompt_context()`를 호출해 `<id>.txt`
한 건씩 쓰고, 무엇으로 뽑았는지를 `manifest.json`에 남긴다. **읽기만 한다** —
`dist/`도 코퍼스도 고치지 않고 사전을 재빌드하지도 않는다.

### 재생성

```bash
python3 tools/export_reference_contexts.py
```

기본 출력 경로는
`../backend-kotlin/infrastructure/src/test/resources/dictionary/reference/`
(`--output-dir`로 변경 가능). 색인·코퍼스 경로는 `--index`/`--golden-dir`.

### 파라미터 — 기본값은 제품이 실제로 쓸 값

`build_prompt_context`의 출력은 예산 파라미터에 따라 통째로 달라지므로, 기본값을
`docs/easy-doc-integration.md` §4·§5 권장값(`max_terms=40`, `max_chars=4000`,
`max_chars_ratio=1.0`, `min_substitute=5`, `max_examples=3`,
`gloss_style=sentence`)으로 두고 전부 CLI로 바꿀 수 있게 했다. **바꾼 값은 그대로
`manifest.json`의 `parameters`에 기록된다** — 기록하지 않으면 픽스처가
"참조 구현의 출력"이 아니라 "알 수 없는 설정에서의 출력"이 되어, 나중에 제품이
다른 값을 쓰기 시작하면 조용히 거짓말을 하게 된다.

### 매니페스트에 생성 일시를 넣지 않는 이유

`manifest.json`이 담는 것은 파라미터, 색인 `schema_version`과 sha256, 문서별
입력(`source_text`)·출력(컨텍스트) sha256과 길이, 매칭 건수뿐이다. 생성
일시처럼 매번 바뀌는 값을 넣으면 재생성할 때마다 diff가 통째로 뒤집혀, 정작
봐야 할 "참조 출력이 달라졌다"는 신호가 잡음에 묻힌다. **같은 입력이면 몇 번을
돌려도 바이트가 같다**(실측: 연속 2회 실행 `diff -r` 차이 없음).

### 픽스처 형식 (Kotlin 쪽이 읽는 계약)

- `<id>.txt` = `build_prompt_context()` 반환 문자열 **그대로**, UTF-8. 끝에
  개행을 덧붙이지 않는다 — 덧붙이면 Kotlin이 매번 걷어내야 하는 가짜 차이가
  된다. 파일을 그대로 읽어 문자열 비교하면 된다.
- 매칭이 0건인 문서도 파일을 남긴다. **주의**: 참조 구현은 매칭이 0건이어도
  빈 문자열이 아니라 3개 섹션 제목만 있는 **골격**을 돌려준다 — 그 케이스의
  정답은 `""`가 아니라 그 골격이다. (골든 코퍼스 56건에는 매칭 0건 문서가
  없다. 최소 8건, 중앙값 21건이다.)
- 골든 문서가 빠지면 대응하는 낡은 `.txt`를 지운다. 안 지우면 존재하지 않는
  문서의 기대 출력이 계속 통과한다.

### 실측 (2026-08-30, 사전 2,179건)

56건 / 총 143.7 KiB(매니페스트 24.4 KiB 포함). 매칭 건수 최소 8 · 중앙 21 ·
최대 108, 고유 엔트리 최소 5 · 중앙 14 · 최대 53. 56건 중 35건에 잘림
안내줄이 붙는다 — 예산 규칙(`max_terms`/`max_chars`/`max_chars_ratio`/
`min_substitute`)이 실제로 과반의 픽스처에서 작동하므로, 이식본이 그 규칙을
빠뜨리면 바로 걸린다.

## API 명세 — 확인 방법과 확인/추정 구분

**사용자가 실제 인증키로 검색 API 3건을 조회한 원본 응답**을
`tools/tests/fixtures/krdict_{geojuji,seonjeong,jumincenter}.xml`로 커밋해
뒀다(거주지=단일 의미/고급, 선정=동음이의어 2건+관련어 5건, 주민센터=단일
의미/중급/표기 불일치). 검색 API 구조는 이 덤프로 **확인**했다:
`channel > item(반복) > target_code/word/sup_no/origin/pronunciation/
word_grade/pos/link/sense(sense_order/definition/example)`.
`_parse_search_response()`가 이 실제 구조로 짜여 있다(이전 버전은 공식 문서
설명만으로 짠 추정이었는데, 실제 구조와 거의 같았다 — 다른 점은 `origin`/
`word_grade` 필드가 문서 요약에는 없었는데 실제로는 있었다는 것 정도).

**미확인**: `example` 태그는 이번 3건 덤프에 하나도 없었다(검색 API 자체가
예문을 안 주는 것으로 보인다 — 아래 "view API" 참고). 파싱 코드는 `example`
태그가 있으면 잡도록 남겨 뒀지만 실제로 검증은 못 했다.

**일일 호출 한도** 50,000건, 초과 시 에러코드 010은 공식 문서 기준(문서만
확인, 실제로 한도를 넘겨보진 않았다). 오류 응답 구조(`<error><error_code>`/
`<message>`)도 정부 오픈 API 관례로 추정한 것이고, 이번 3건 덤프에는 에러
사례가 없어 실제로 확인 못 했다.

### view API(예문) — 미검증, `--fetch-examples`로만 시도

검색 API 응답에 `<example>`이 없어서 예문을 얻으려면 상세보기(view) API가
필요해 보인다. 공식 문서 페이지(`openApiView`류)는 못 찾았지만, 실제로
배포 중인 파이썬 래퍼 [`omarkmu/krdict.py`](https://github.com/omarkmu/krdict.py)
의 소스코드(`src/krdict/request.py`)에서 다음을 **코드로 확인**했다:

```
_VIEW_URL = 'https://krdict.korean.go.kr/api/view'
# target_code로 조회할 때:
params['method'] = 'target_code'
params['q'] = <target_code 값>   # ('target_code' 입력 파라미터가 'q'로 매핑됨)
```

`fetch_krdict.py`도 이 조합(`method=target_code&q=<target_code>&key=...`)을
그대로 쓴다. **그런데 사용자가 정확히 이 파라미터로 수동 호출했을 때
`400 Request Blocked`가 났다** — WAF(방화벽) 레벨 차단으로 보이는 메시지다.
`omarkmu/krdict.py`는 `requests` 기본 헤더로 호출하는데, 이 스크립트는 검색
API에 이미 커스텀 `User-Agent`를 쓰고 있고(그쪽은 실제로 성공 확인됨) 같은
헤더를 view에도 쓰도록 만들어 뒀다 — 그걸로 될지는 **실제로 키로 돌려봐야
안다.** 추측으로 더 파고들지 않았다.

그래서 view 호출은 기본적으로 안 하고, `--fetch-examples`를 명시해야만
시도한다. 실패해도 예외를 던지지 않고 `예문` 컬럼만 비운 채로 계속 진행한다
(나머지 뜻/한자/급수/gloss 판정에는 전혀 영향 없음).

### 키가 오면 할 일 (검증 절차)

1. **검색 API**는 이미 실제 응답 구조로 검증됐다(위 fixtures) — 추가 검증
   없이 바로 정식 실행해도 된다.
2. **view API**(`--fetch-examples`)는 `--limit 5` 정도로 작게, `--fetch-examples`
   와 함께 먼저 돌려서 여전히 400이 나는지 확인한다. 성공하면 그대로 큰
   배치에 써도 된다. 계속 400이면 이 README와 스크립트 상단 docstring의
   "view API" 절에 실패 사실을 적어 두고, 예문 없이(view API 없이) 진행하면
   된다 — 뜻/한자/급수/gloss는 view API와 무관하게 이미 동작한다.
3. 검색 응답 구조가 fixtures와 다른 새 필드/형태가 보이면
   `_parse_search_response()`만 고치면 된다 — 나머지(재시도/속도조절/
   gloss 판정/CSV 출력)는 `Item`/`Sense` 데이터클래스에만 의존한다.
