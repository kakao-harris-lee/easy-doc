# 쉬운 말 사전 (easy-dictionary) 설계 문서

> 지적·발달장애인을 위한 공공/복지 문서 쉬운 글 변환 서비스(easy-doc)의 RAG 사전 계층.
> 버전 `1.0.0` / 작성일 2026-08-27

---

## 1. 배경과 범위

### 1.1 이 저장소가 하는 일
공공데이터포털·국립국어원·법제처가 개방한 **순화어 대조표(CSV/XLSX)** 를 받아, 검증·정규화·증강하여 **런타임에 즉시 조회 가능한 로컬 사전**으로 만든다. 산출물은 SQLite 1개와 JSON 3종이며, 이 저장소는 산출물까지만 책임진다.

### 1.2 비목표 (Non-goals)
- **easy-doc 저장소를 수정하지 않는다.** easy-doc의 `CLAUDE.md`는 "RAG 사전은 MVP 밖"으로 명시하고 있다. 이 저장소는 easy-doc이 *나중에 준비되었을 때* 그대로 집어갈 수 있는 형태의 산출물만 만든다.
- LLM 호출, 문서 파싱, 프롬프트 실행은 하지 않는다. 사전은 **프롬프트에 주입할 컨텍스트를 만들어 줄 뿐** 변환 자체를 수행하지 않는다.
- 벡터 임베딩 생성은 1.0 범위 밖이다. 스키마에 자리(`embeddings` 테이블)만 예약한다.

### 1.3 왜 로컬 DB인가
외부 API를 문장마다 호출하면 지연이 누적되어 Agent 응답이 답답해진다. 순화어 데이터는 **하루에 한 번도 안 바뀌는 정적 데이터**다. 빌드 타임에 말아넣고 런타임에는 메모리/SQLite 조회만 한다. 목표 지연은 문서 1건(A4 3매) 사전 매칭 **50ms 이하**.

## 2. 핵심 설계 원칙

### 2.1 단순 `{term: easy_term}` 딕셔너리는 B2G에서 위험하다 — 가장 중요한 결정

기획서 예시의 `{"명기하다": "기록하다"}` 형태는 즉시 쓸 수 있지만, 공문서에 그대로 적용하면 사고가 난다.

| 원어 | 순진한 치환 | 무엇이 깨지는가 |
|---|---|---|
| 과태료 | 벌금 | **법적으로 다른 개념.** 과태료는 행정질서벌, 벌금은 형벌. 전과 여부가 갈린다. |
| 이의신청 | 다시 말하기 | 법정 기한이 걸린 **권리 행사 절차명**이 사라져 수급자가 권리를 잃는다. |
| 차상위계층 | 기초생활수급자 바로 위의 저소득층 | 뜻은 맞지만 **제도 명칭**이라 신청서·상담 창구에서 그 말을 다시 써야 한다. |
| 수급권자 | 지원금 받을 사람 | "수급자"(현재 받는 사람)와 "수급권자"(받을 권리가 있는 사람)의 구분이 소멸한다. |

따라서 모든 표제어는 **치환 전략(`replace_strategy`)** 을 필수로 가진다.

| 전략 | 의미 | 출력 예 |
|---|---|---|
| `substitute` | 원어를 지우고 쉬운 말로 교체해도 안전 | 내방 → **방문** |
| `gloss` | 원어를 **남기고** 쉬운 말을 덧붙여 설명 | 과태료 → **과태료(늦게 내서 더 내는 돈)** |
| `keep` | 바꾸지 않는다. 표시만 하고 별도 용어 설명 박스로 뺀다 | 「국민기초생활 보장법」, 금액·기한 |

여기에 `risk_level`(none/low/high)을 곱해서, high 위험 용어는 자동 치환 파이프라인에서 **사람 검수 큐로 보낸다.**

> easy-doc의 `data/golden/*.json`은 `required_facts.canonical`로 사실보존을 검증한다. `keep` 전략은 이 검증과 직접 맞물린다 — 금액·날짜·법령명·제도명은 치환 대상에서 원천 배제되어야 검증을 통과한다.

#### 외부 근거: 국립장애인도서관 『발달장애인용 쉬운 책 개발 지침』

이 설계는 우리 추론만이 아니라 국가 지침과 일치한다. B2G 납품 시 근거로 인용할 수 있다.

- **1.4.2** — "일반적으로 사용되는 어휘도 행정적인 용어나 법률용어로는 **다른 의미를 가질 수 있음에 유의**해야 한다"
  → `과태료`(행정질서벌) ≠ `벌금`(형벌) 문제가 지침에 명문화되어 있다. `risk_level=high` + `review` 격리의 근거다.
- **1.4.1** — 행정·법률 용어를 써야 한다면 **쉬운 어휘로 부연 설명**해야 한다
  → 치환이 아니라 "설명 추가"가 원칙이다. `gloss` 전략이 여기에 대응한다.
- **1.1.4 / 1.1.5** — 어려운 어휘는 치환하지 말고 **괄호 설명·각주·문맥 단서**를 덧붙이기를 권장
  → `substitute`를 기본값으로 남발하지 않고 `gloss`를 우선하는 방향이 지침에 부합한다.
- **1.4.3** — 법 조문 인용은 문단 끝이나 각주로 처리
  → `keep` 항목을 본문에서 건드리지 않고 별도 용어 설명으로 빼는 처리와 일치한다.

즉 **"쉬운 말로 바꿔치기"가 아니라 "원문을 지키면서 설명을 덧붙이기"가 이 분야의 표준 접근**이며, 이 사전의 3전략 구조는 그 표준을 데이터 모델로 옮긴 것이다.

### 2.1.1 쉬운 말을 지을 때 가장 흔한 실패: 축약이 범위를 좁힌다

실데이터 검수에서 **7건 중 5건이 같은 유형**이었다. 짧게 만들려다 제도가 포괄하는 범위를 잘라냈다.

| 원어 | 잘못된 순화어 | 무엇이 사라졌나 |
|---|---|---|
| 생계급여 | 밥값 | 의복·연료비 (음식만 남음) |
| 주거급여 | 집세 | 집수리비(수선유지비) |
| 교육급여 | 학비 | 학용품값 |
| 소득인정액 | 소득 계산값 | **재산** (소득만 남음) |
| 실제소득 | 실제로 버는 돈 | 재산소득·이전소득 (근로소득만 남음) |

읽는 사람에게 미치는 영향이 크다. `생계급여(밥값)`을 본 수급자는 "밥값만 주는 건가"라고 이해한다. 제도가 실제로 주는 것보다 적게 받는다고 오해하게 만든다.

**반대 방향(범위를 넓힘)도 같은 무게로 위험하다.** 대상이 아닌 사람이 자격이 있다고 오해하면 신청했다 거절당한다.

#### 규칙
1. **`뜻`(definition)과 `순화어`(easy_term)가 서로 모순되지 않는지 확인한다.** 이 다섯 건 모두 `뜻` 필드에는 정확히 적혀 있었고 `순화어`만 좁았다. 두 필드가 어긋나면 프롬프트가 자기모순이 된다.
2. **`gloss`는 원어를 보존하므로 짧게 만들 이유가 약하다.** `생계급여(먹고 입고 사는 데 필요한 돈)`이 `생계급여(밥값)`보다 낫다. **정확성이 간결함보다 우선한다.**
3. 열거형 제도는 **대표 항목을 최소 둘 이상** 담는다. `의료기관(병원·의원처럼 치료해 주는 곳)` — 하나만 들면 그것만 해당하는 것처럼 읽힌다.

> 반례도 있다. `소득평가액 → 소득인정액을 구할 때 쓰는 소득 부분 계산값`은 좁아 보이지만, 이 용어 자체가 정의상 소득 쪽만 가리키는 것이 맞다(재산 쪽은 소득환산액이 따로 더해진다). **좁히기와 정확히 좁은 것을 구별해야 한다** — 판단 기준은 언제나 `뜻` 필드다.

### 2.2 한국어는 표제어만으로 매칭되지 않는다

문서에는 `명기하다`가 아니라 `명기하여`, `명기한`, `명기해야 합니다`로 나온다. 표제어만 색인하면 매칭률이 절반 이하로 떨어진다. 두 가지로 해결한다.

1. **변형형 테이블(`variants`)**: 용언 활용형·띄어쓰기 변형·한자 병기형·약어를 빌드 타임에 규칙으로 생성해 저장한다.
2. **조사 경계 매칭**: 체언 뒤 조사(`은/는/이/가/을/를/에서/으로/에게/까지/부터`…)는 변형형으로 저장하지 않고 **매칭 시 경계 패턴**으로 처리한다. 조합 폭발을 막는다.

### 2.3 출처와 라이선스는 엔트리 단위로 따라다닌다
B2G 납품 시 "이 순화어의 근거가 무엇이냐"는 반드시 나온다. 공공누리 유형에 따라 재배포 가능 여부도 갈린다. `sources` 테이블을 FK로 물리고 원본 파일 SHA-256까지 남긴다.

### 2.4 카테고리는 단일 컬럼이 아니라 태그
`수급권자`는 행정용어이면서 복지용어이고 법률용어다. 단일 `category` 컬럼은 반드시 정보를 잃는다. `tags` + `entry_tags` N:M으로 두고, 대표 태그만 `is_primary=1`로 표시해 기존 `{"category": "행정용어"}` 형태와의 호환을 유지한다.

## 3. 데이터 모델 (SQLite 정본)

SQLite를 **정본(source of truth)** 으로 두고 JSON은 파생 산출물로 본다. 이유: 제약조건·트리거·FTS5를 공짜로 얻고, 증분 갱신과 검수 이력 관리가 가능하다.

### 3.1 테이블 개요

| 테이블 | 역할 |
|---|---|
| `meta` | 빌드 버전, 생성 시각, 카운트 |
| `sources` | 원천 데이터(기관·라이선스·URL·원본 해시) |
| `entries` | **표제어 본체** |
| `tags` / `entry_tags` | 카테고리 태그 (N:M) |
| `variants` | 활용형·띄어쓰기·한자·약어 변형 |
| `examples` | before/after 예문 (RAG few-shot 재료) |
| `relations` | 동의어·상하위어·충돌어 |
| `embeddings` | 벡터 검색용 예약 자리 |
| `entries_fts` | FTS5 전문검색 (external content) |
| `v_entry_full` | JSON 익스포트/백엔드 단일 조회 뷰 |

### 3.2 `entries` 컬럼 사전

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | INTEGER PK | ● | |
| `term` | TEXT | ● | 원어(어려운 말). 예 `차상위계층` |
| `term_norm` | TEXT | ● | 정규화 키. NFC + 공백/`·`/`-`/괄호 제거 + 소문자 |
| `term_hanja` | TEXT | | 한자 병기 `次上位階層`. `내방(來訪)` 입력에서 분리 |
| `pos` | TEXT | | `noun\|verb\|adjective\|adverb\|determiner\|phrase` |
| `easy_term` | TEXT | ● | 문장에 그대로 끼울 짧은 대치어 |
| `definition` | TEXT | | 한 문장 풀이(초등 3~4학년 수준) |
| `replace_strategy` | TEXT | ● | `substitute\|gloss\|keep` (§2.1) |
| `risk_level` | TEXT | ● | `none\|low\|high` |
| `caution` | TEXT | | 치환 시 주의사항(사람이 읽는 메모) |
| `readability` | INTEGER | ● | 1(가장 쉬움)~3(여전히 조금 어려움) |
| `confidence` | REAL | ● | 0~1. 자동 치환 신뢰도 |
| `priority` | INTEGER | ● | 겹칠 때 큰 값 우선. 기본 `100 + len(term)*10` |
| `frequency` | INTEGER | | 코퍼스 출현 빈도(선택) |
| `status` | TEXT | ● | `active\|review\|deprecated` |
| `source_id` | INTEGER FK | | → `sources.id` |
| `source_ref` | TEXT | | 원본 행 번호/조문 등 역추적 키 |
| `checksum` | TEXT | ● | 중복 판정용 해시 |
| `created_at` / `updated_at` | TEXT | ● | |

제약: `UNIQUE(term_norm, easy_term)` — 같은 원어에 서로 다른 순화어가 여러 개 오는 것은 **허용한다**(문맥별 대안). 완전 중복만 막는다.

### 3.3 태그 표준값

| `name` | `label` | `kind` |
|---|---|---|
| `admin` | 행정 | domain |
| `law` | 법률 | domain |
| `welfare` | 복지 | domain |
| `medical` | 보건·의료 | domain |
| `finance` | 금융·세무 | domain |
| `form` | 서식·신청 | topic |
| `hanja` | 한자어 | register |
| `loanword` | 외래어 | register |
| `jargon` | 전문용어 | register |
| `needs_review` | 검수필요 | ops |

**키 설계**: `tags`는 대리키를 두지 않고 `name`을 그대로 기본키로 쓰고, `entry_tags`는 `tag_name`으로 참조한다.

```sql
tags       (name TEXT PRIMARY KEY, label TEXT NOT NULL, kind TEXT NOT NULL)
entry_tags (entry_id INTEGER REFERENCES entries(id) ON DELETE CASCADE,
            tag_name TEXT REFERENCES tags(name)  ON DELETE CASCADE,
            is_primary INTEGER NOT NULL DEFAULT 0,
            PRIMARY KEY (entry_id, tag_name))
```

태그 이름은 안정적인 소규모 통제 어휘(§3.3의 10개)라 대리키가 주는 이점이 없다. 자연키를 쓰면 태그 이름을 얻는 데 조인이 필요 없어 익스포트 쿼리가 단순해진다. 새 태그 추가는 `INSERT OR IGNORE` 한 줄이다.

> Kotlin 포팅 시 주의: 태그는 `Int` id가 아니라 `String` 이름으로 참조한다.

### 3.4 변형형 생성 규칙 (`variants.kind`)

| kind | 규칙 |
|---|---|
| `conjugation` | `~하다` → 어간 + `하여/해/한/하는/할/하고/하면/하며/해야/합니다/했습니다/하시기/하십시오/함/하지`. `~되다` → 어간 + `되어/된/되는/될/되고/되면/됩니다/되었습니다/됨/되지`. 어근 명사형(`명기`)도 추가 |
| `spacing` | 공백 포함 표제어의 공백 제거형(`차상위 계층` → `차상위계층`), 중점/하이픈 제거형 |
| `hanja` | 한자 병기 분리형 |
| `abbrev` | 원본 CSV에 약어 컬럼이 있을 때만 |
| `synonym` | 원본 CSV의 복수 순화어/이형태 |
| `typo` | 수동 등록 전용(자동 생성 안 함) |

조사 목록(매칭 시 경계 패턴으로만 사용, 변형형 저장 안 함):
`은 는 이 가 을 를 에 에서 에게 에겐 께 한테 으로 로 로서 으로서 로써 으로써 와 과 의 도 만 부터 까지 이나 나 보다 처럼 라도 이라도 조차 마저 밖에 이란 란 이라는 라는 입니다 이다 이며 이고 인 임`

### 3.4.1 표기 변이 — 실데이터에서만 드러나는 축

한국어 공공문서는 **같은 말을 여러 표기로 씁니다.** 표제어 하나만 색인하면 나머지를 전부 놓칩니다. 아래는 실데이터 1,785건에서 실제로 확인된 축입니다.

| 축 | 예 | 대응 |
|---|---|---|
| 띄어쓰기(제거) | `가스 마스크` / `가스마스크` | `spacing` 변형형 |
| 띄어쓰기(삽입) | `국민기초생활보장법` / `국민기초생활 보장법` | 5음절 이상만 위치별 삽입형 |
| 중점 문자 | `초·중등교육법`(U+00B7) / `초ㆍ`(U+318D) / `초･`(U+FF65) | 제거형 + 상호 치환형 |
| 호환 한자 | `領`(U+F9B4) / `領`(U+9818) | NFC 정규화로 폴딩 |
| 오표기 | `라이선스` / `라이센스*` | `typo` 변형형 (원본 CSV의 `*` 표시) |

공백 **삽입**형에 5음절 하한을 두는 이유: `내방`(來訪)에 공백을 넣으면 `내 방`("나의 방")이 되어 무관한 구에 대량 오탐이 납니다. 짧은 표제어일수록 위험합니다.

중점류는 **NFC로 접히지 않습니다.** 호환 한자와 달리 유니코드 정준 동치가 아닌 독립 문자이기 때문입니다.

### 3.4.2 정규화 키와 표면형을 혼동하지 말 것 — 반복해서 터진 실수

`normalize_key()`는 공백·중점·하이픈·괄호를 제거한다(§6.2). 이것은 **"같은 표제어인가"를 판정하는 도구**다. 매칭에 쓰는 표면형과는 목적이 다르다.

이 둘을 혼동해 같은 결함이 **두 곳에서** 발생했다.

1. `build.py`의 변형형 중복 제거가 `normalize_key(surface) == term_norm`을 버림 조건으로 썼다. 공백 변형형은 정의상 언제나 이 조건을 만족하므로 **100% 폐기**됐다.
2. `variants`의 제약이 `UNIQUE(surface_norm, entry_id)`였다. 공백 삽입형은 설계상 같은 `surface_norm`을 공유하므로 **첫 하나만 남고 나머지가 조용히 사라졌다.** 어느 것이 살아남을지는 생성 순서에 달려 재현성도 없었다.

두 번째가 특히 나빴다 — `해외 이주법`처럼 **실제 문서에서 자연스러운 표기가 오히려 매칭에 실패**하고, 우연히 먼저 생성된 `해 외이주법`만 살아남았다.

> **표면형의 유일성은 표면형으로 판정한다.** `export_index()`가 색인 키로 쓰는 것은 `surface`이지 `surface_norm`이 아니다.

따라서 제약은 `UNIQUE(surface, entry_id)`다. `surface_norm` 컬럼과 인덱스는 정규화 조회용으로 유지한다.

`entries`의 `UNIQUE(term_norm, easy_term)`은 **그대로 정규화 기준이 맞다.** `차상위 계층`과 `차상위계층`은 같은 표제어이므로 중복이다. 변형형은 정확히 그 차이를 담으려고 존재하므로 정규화하면 존재 이유가 사라진다. **두 테이블의 기준이 다른 것이 옳다.**

### 3.5 결정: 활용형을 빌드 타임에 전개한다 (색인 크기 vs 조회 복잡도)

어미 목록을 넓히면 색인이 커진다. 실측(엔트리 93개 기준):

| | 변형형 | index.json | 엔트리당 |
|---|---|---|---|
| 기본 규칙만 | 400 | 35.3 KB | 388 B |
| + 명사 하다-파생 | 1,017 | — | — |
| + 존대 어미 계열 | 2,133 | 58.8 KB | 647 B |

1만 엔트리 선형 외삽 시 약 **6.2MB**(상한 추정 — 다음절 제도명·구 표제어는 활용형이 거의 늘지 않으므로 실제로는 더 작을 가능성이 높다).

**결정: 지금 구조(빌드 타임 전개 + 트라이 색인)를 유지한다.** 근거는 셋이다.

1. **지연 예산이 색인 크기보다 깨지기 쉽다.** 6MB는 백엔드 상주 리소스로 부담이 아니지만, 문서 1건 50ms(§1.3)는 빠듯하다. 조회 시점에 후보마다 어미 정규식을 돌리는 방식은 트라이 dict 조회보다 명백히 느리다.
2. **언어 간 이식 표면적이 줄어든다.** easy-doc은 Kotlin이고 `lookup.py`는 참조 구현이다(§7.1). 활용형을 평문 문자열 목록으로 넘기면 Kotlin은 트라이만 만들면 되지만, 조회 시점 정규식으로 가면 **한국어 활용 규칙을 Kotlin에도 통째로 이식**해야 한다. 두 언어가 따로 버그를 낼 표면이 생긴다.
3. 현재 증가폭은 고정 목록이 감당 못 할 신호가 아니다.

**재검토 트리거**: 실 데이터 적재 후 `index.json`이 20MB를 넘거나, 로딩·트라이 구성이 콜드스타트 지연으로 체감될 때. 그때도 전면 정규식 전환보다는 **서술성 명사 하다-파생만 조회 시점 처리로 분리**(엔트리에 `predicate_noun` 플래그를 두고 그 소수만 어미 매칭)하는 절충이 먼저다.

### 4.4 `easy_dict.simple.jsonl` — 기획서 호환 형태
기획서에 적힌 최소 형태를 그대로 유지해 초기 프로토타입/수작업 검토에 쓴다.
```json
{"term": "내방", "easy_term": "방문", "category": "행정"}
```

**안전 계약: 이 파일은 순진한 `str.replace`로 써도 사고가 나지 않아야 한다.**

이 포맷에는 `replace_strategy` 필드가 없다. 소비자가 기획서대로 `{term → easy_term}` 딕셔너리로 쓰면 전략 정보가 사라지므로, **파일 자체가 안전해야 한다.** 초판은 이 조건을 어겨서 법령명이 `법 이름이니 그대로 씀`으로 치환되고 `과태료`가 문장에서 사라졌다 — §2.1이 경고한 사고가 바로 이 파일에서 재현됐다.

| 전략 | 처리 | 순진한 치환 결과 |
|---|---|---|
| `substitute` | `easy_term` 그대로 | 정상 치환 |
| `gloss` | `easy_term`을 **`원어(설명)`** 로 합성 | 원어가 결과에 남음 |
| `keep` | **행을 출력하지 않음** | 아무 일도 일어나지 않음 |
| `status='review'` | **행을 출력하지 않음** | 미검수 데이터가 새지 않음 |

`gloss` 합성이 핵심이다. `과태료` 행은 `"과태료(정해진 법을 안 지켜서 내는 돈)"`로 나가므로 순진하게 치환해도 원어가 보존되어 easy-doc의 `required_facts` 검증을 통과한다. 기획서 예시였던 `차상위계층`도 같은 방식으로 살아남는다.

**형식적 안전 조건**: 모든 행에 대해 `term ⊆ easy_term` 이거나 해당 term이 파일에 없다.

**한계 — 이 파일은 문법을 보장하지 않는다.** 정적 딕셔너리라 §6.7의 조사 이형태 교정을 실을 자리가 없다. 순진하게 치환하면 `급여는` → `지원금는` 같은 비문이 나온다.

이 파일의 계약은 **"안전"이지 "정확"이 아니다.** 뜻이 뒤집히거나 법적 사실이 사라지는 사고는 막지만, 문장이 매끄럽다는 보장은 하지 않는다. 따라서 용도는 **초기 프로토타입·수작업 검토·데이터 훑어보기**에 한정한다.

실제 변환 경로는 `easy_dict.index.json` + `lookup.py`(또는 그 Kotlin 포팅본)이며, 그쪽만이 조사 교정·굴절형 폴백·경계 판정을 수행한다. **운영에서 `simple.jsonl`을 변환에 쓰지 마라.**

> `easy_dict.json`과 `easy_dict.index.json`에는 이 축약을 적용하지 않는다. 그 둘은 `replace_strategy`를 온전히 실어 나르므로 `keep`/`review`를 포함해야 한다. index에서 `keep`이 빠지면 `annotate`가 법령명을 보호하지 못한다 — 그게 더 큰 사고다.

### 4.5 `[확인 필요]` 자동 비활용과 산출물별 `deprecated` 취급

**규칙**: `caution`에 `[확인 필요]` 표시가 있으면 빌드가 `status='deprecated'`를 강제한다. CSV가 `status`를 명시했더라도 이쪽이 우선한다.

근거: 법조문 대조 같은 추가 확인이 필요한 항목은 **확인 전에는 쓰지 않는다**는 방침이다. 작성자가 불확실성을 표시하기만 하면 자동으로 런타임 산출물에서 빠지므로, 검수되지 않은 내용이 사고로 흘러갈 경로가 닫힌다.

`replace_strategy`와 `risk_level`은 덮어쓰지 않는다 — 정본(SQLite)에 "원래 어떻게 분류됐었는지"가 감사용으로 남아야 한다.

비활용 건수와 표제어 목록은 **빌드 리포트에 반드시 출력한다.** 조용히 빠지면 안 된다(§5.5).

#### 산출물별 취급이 다르다

| 산출물 | `deprecated` | 이유 |
|---|---|---|
| `easy_dict.sqlite3` | 포함 | 정본. 모든 상태를 보존한다 |
| `easy_dict.json` | **포함** | 전체 덤프 = **감사 추적**. "무엇이 왜 빠졌는지"가 보여야 값어치가 있다. `status`와 `caution`을 그대로 노출하고 `counts.deprecated`를 별도 표시한다 |
| `easy_dict.index.json` | **제외** | LLM 프롬프트에 직접 들어간다. 미검수 내용이 도달하면 안 된다 |
| `easy_dict.simple.jsonl` | **제외** | §4.4 안전 계약 |

B2G 납품에서 "이 용어는 왜 사전에 없나"라는 질문에 답하려면 제외된 항목과 사유가 남아 있어야 한다. 동시에 그 내용이 LLM에 도달해서는 안 된다. 두 요구가 충돌하므로 산출물을 나눈다.

> 구현은 쿼리 상수를 `_ALL_ENTRIES_SQL` / `_ACTIVE_ENTRIES_SQL`로 분리해, 필터가 실수로 다시 섞이는 것을 막는다. **`index.json` 쪽 누출이 훨씬 위험하다** — 회귀 테스트의 우선순위도 그쪽이다.

#### 알려진 부작용: 끊어진 참조

비활용된 용어를 **다른 엔트리의 `caution`이 참조**할 수 있다. 실제로 `수급자`의 주의 문구가 비활용된 `수급권자`를 언급한다.

문서에 둘 다 나오면 구분은 전달되므로 무해하지만, **비활용된 쪽만 나오면 사전이 완전히 침묵**한다. 그러면 LLM이 자기 판단으로 그 용어를 바꿀 수 있어 오히려 위험이 커진다.

> 대안: 뜻풀이 없이 `keep`으로만 남긴다. `keep`은 "이 말을 그대로 두라"는 지시일 뿐 어떤 정의도 주장하지 않으므로, 추가 확인 없이도 안전하면서 용어 훼손은 막는다. 어느 쪽을 택할지는 용어별 판단이다.

## 5. 빌드 파이프라인

```
data/raw/*.csv
   │  ① 인코딩 자동 판별 (utf-8-sig → utf-8 → cp949 → euc-kr)
   │  ② 컬럼 별칭 해석 (기관마다 헤더가 다름)
   ▼
파싱 → Entry 후보
   │  ③ 정규화: NFC, 한자 병기 분리, 공백/기호 정리, 빈 값·자기참조 제거
   │  ④ 분류: pos 추정 → 태그 부여 → 위험도/치환전략 판정
   │  ⑤ 증강: 변형형 규칙 생성
   │  ⑥ 중복/충돌 해소: (term_norm, easy_term) 유일화, 충돌은 경고 로그
   ▼
SQLite 적재 (트랜잭션 1회, FTS 자동 동기화)
   ▼
JSON 3종 익스포트 + 빌드 리포트
```

### 5.1 ② 컬럼 별칭 — 실무에서 가장 많이 깨지는 지점
기관마다 헤더가 다르다. 하드코딩하면 다음 CSV에서 바로 터진다. 별칭 표로 해석한다.

| 논리 필드 | 허용 헤더 |
|---|---|
| `term` | 순화대상어, 순화 대상어, 원어, 대상어, 어려운말, 어려운 말, 용어, 행정용어, 기존용어, term |
| `easy_term` | 순화어, 다듬은말, 다듬은 말, 쉬운말, 쉬운 말, 대체어, 순화표현, 권장어, easy_term |
| `definition` | 뜻, 의미, 설명, 뜻풀이, 정의, definition |
| `category` | 분야, 구분, категория→분류, 영역, category |
| `example` | 예문, 용례, 사용례, example |
| `hanja` | 한자, 한자표기 |
| `note` | 비고, 참고, 메모 |

해석 실패 시 **빌드를 중단하고** 발견된 헤더 목록을 출력한다. 조용히 빈 사전을 만드는 것이 최악이다.

### 5.2 ④ 위험도·치환전략 자동 판정 (휴리스틱 + 화이트리스트)

```
IF term ∈ KEEP_LIST                       → keep,       risk=high
   (법령명 「」 포함, 제도 고유명칭, 금액/기한 단위)
ELIF term ∈ LEGAL_RISK_LIST               → gloss,      risk=high
   (과태료 벌금 소명 이의신청 처분 기각 각하 반려 압류 체납 고지 최고
    시효 권리 의무 상속 채권 채무 근저당 위임 대리 추징 환수 …)
ELIF 'law' ∈ tags AND len(easy_term) > 12 → gloss,      risk=low
ELIF easy_term이 설명문(공백 2개 이상)      → gloss,      risk=low
ELSE                                       → substitute, risk=none
```
`risk=high`는 `status='review'`로 넣어 **사람 검수 전에는 자동 치환에 쓰이지 않게** 한다. 이게 이 사전의 안전 기본값이다.

#### 불변식: `substitute` + `review`는 존재해서는 안 된다

`status='review'`인 항목도 `index.json`에는 실린다. 빼면 `keep` 항목이 사라져 법령명을 보호하지 못하기 때문이다(§4.4 마지막 문단). 즉 **미검수 초안이 LLM 프롬프트에 도달한다.**

이것이 안전한 이유는 우연이 아니다. `risk=high` → `review`이고, `high`는 항상 `gloss` 아니면 `keep`이다. **둘 다 원어를 보존한다.** 따라서 검수 전 초안은 설명을 덧붙일 뿐 원어를 지우지 못한다.

> **미검수 항목은 원문을 지울 수 없다.**

`substitute` + `review`가 생기면 이 보장이 깨진다 — 사람이 확인하지 않은 쉬운 말이 원어를 대체하게 된다. 휴리스틱만 쓰던 동안에는 구조적으로 발생할 수 없었지만, **CSV가 전략을 명시할 수 있게 되면서 발생 가능해졌다.** 빌드는 이 조합을 발견하면 중단해야 한다.

검증: 실데이터 1,717건 · 샘플 92건 모두에서 `substitute`+`review` 0건 확인.

**의존성 없음.** 표준 라이브러리(`csv`, `sqlite3`, `json`, `re`, `unicodedata`, `hashlib`, `argparse`, `dataclasses`)만 사용한다. 납품 환경에서 pip 설치가 막히는 경우가 잦다.

### 5.4 재현성 계약 — 의미적 동등이며, 바이트 동일은 아니다

같은 입력이면 `--input` 순서와 무관하게 **같은 사전**이 나와야 한다. 그렇지 않으면 "데이터는 안 바뀌었는데 빌드마다 태그가 다르다"가 되어 추적이 불가능해진다. B2G 납품물에서 양보할 수 없는 성질이다.

**보장하는 것 (순서 독립)**
- 엔트리 집합 `(term_norm, easy_term)`
- 대표 태그, 그리고 태그 집합 전체
- `replace_strategy` / `risk_level` / `status` — 안전장치가 적재 순서에 좌우되면 가장 심각하다
- 빌드 리포트의 집계 수치

**대표 태그 결정 규칙**: 엔트리에 최종적으로 붙은 태그 **집합**에 고정 서열을 적용해 고른다.
```
TAG_PRIORITY = (law, welfare, medical, finance, admin, form,
                jargon, loanword, hanja, needs_review)
```
도메인 태그가 register/ops보다 항상 우선한다 — `needs_review`는 "무엇인가"가 아니라 "어떻게 처리할까"라 대표가 될 수 없다. `admin`을 도메인 중 최하위에 둔 것은 그것이 사실상 캐치올이고 `welfare`/`medical`/`finance`가 더 구체적인 분류이기 때문이다.

여러 원천에 걸친 태그는 **합집합으로 누적**한다. 원천별로 갈아끼우면 먼저 적재된 원천의 태그가 소실된다 (실제로 이 버그가 있었다).

**보장하지 않는 것 (바이트 동일)**
`entries.id`가 AUTOINCREMENT라 적재 순서에 따라 다른 정수를 받는다. 따라서 `index.json`은 바이트 단위로 같지 않다.
```
정순 '내방' surface_index=[1, 54]   역순=[33, 34]     내용은 동일
```
회귀 테스트는 id를 내용값으로 정규화한 뒤 비교한다. 원본 바이트 비교를 단언으로 넣으면 **올바른 구현에서도 영원히 실패하는 테스트**가 된다.

> 바이트 동일성이 필요해지면(산출물 체크섬 서명, 릴리스 간 diff) `term_norm` 정렬 후 id를 부여하도록 바꾸면 된다. 전체 재빌드에 한해 성립하며, 증분 upsert에서는 여전히 id가 이동한다. 현재 스펙은 이를 요구하지 않는다.

### 5.5 반복해서 터진 결함 유형 — 새 코드를 쓸 때 먼저 확인할 것

실데이터를 넣기 시작한 뒤 같은 계열의 결함이 여러 번 나왔다. 유형별로 정리한다.

#### (1) 적재 순서에 결과가 좌우된다
| 사례 | 증상 |
|---|---|
| `upsert()`가 태그를 통째로 지우고 재삽입 | 먼저 적재된 원천의 태그가 소실. 대표 태그가 `--input` 순서로 결정 |
| `upsert()`가 예문을 무조건 `DELETE` | 예문 없는 원천이 있는 원천의 예문을 삭제 |
| 리포트의 태그 매핑 카운트 | DB 내용은 같은데 리포트 숫자만 순서에 따라 달라짐 |
| `id(entry)`를 명시값 추적에 사용 | 객체가 GC되면 id가 재사용되어 **조용히 틀린 값**이 들어감 |

> **같은 입력이면 `--input` 순서와 무관하게 같은 산출물이 나와야 한다**(§5.4). 새 상태를 도입할 때마다 순서 독립성을 확인하라. 특히 `id()`·삽입 순서·전역 집합처럼 **객체 생명주기나 처리 순서에 묶인 것**을 판정 근거로 쓰지 마라.

#### (2) 정규화 키와 표면형을 혼동한다
§3.4.2 참조. `build.py`의 dedup, `variants`의 UNIQUE 제약, `seen_surface` 집합 **세 곳**에서 같은 실수가 났고, 하나를 고쳐도 나머지가 막고 있어 증상이 안 바뀌었다.

#### (3) 경계 검사가 한쪽만 되어 있다
매칭 경계는 네 번에 걸쳐 서로 다른 방향에서 터졌다.

| 차수 | 증상 | 원인 |
|---|---|---|
| 1 | `내방`이 `내방객`에 매칭 | 오른쪽 경계 없음 |
| 2 | `급여`가 `급여과장`에 매칭 | 조사 뒤에 한글이 이어지는지 미검사 |
| 3 | `급여에서는` 미매칭 | 연쇄 조사 미허용 |
| 4 | `자`가 `신청자`에 매칭 | **왼쪽 경계 없음** |

4차가 특히 오래 남았다. 왼쪽에는 조사가 올 수 없어 규칙이 훨씬 단순한데, **단순해서 검토 대상에 오르지 않았다.** 경계 관련 테스트는 한 클래스에 모아 어느 방향이 깨져도 잡히게 한다.

#### (4) 조용히 버린다
`row_to_entries()`의 자기참조 필터가 법령명 45행을 **아무 흔적 없이** 삭제했다. 리포트에는 입력 행수만 찍혀서, DB를 직접 조회하기 전에는 알 수 없었다.

> **조용히 버리는 것이 잘못 넣는 것보다 나쁘다.** 잘못 들어간 것은 나중에 보이지만 안 들어간 것은 안 보인다. 행을 버리는 모든 경로는 사유별 집계를 리포트에 남긴다.

#### (5) 가상 샘플에서는 절대 안 보이는 것들
| 사례 | 왜 안 보였나 |
|---|---|
| `jargon` 폴백이 최빈값(957/1717) | 샘플은 분야 컬럼이 항상 채워져 있었음 |
| CJK 호환 한자(`領` U+F9B4) | 사람이 만든 샘플에는 안 섞임 |
| 중점 3종(`·`/`ㆍ`/`･`) | 같은 이유 |
| 원어 표기 미분리 705행(63%) | 샘플에 어원 병기가 없었음 |
| `spacing` 변형형 0건 | 샘플에 공백 든 표제어가 거의 없었음 |

> 새 원천을 넣을 때는 **적재 후 반드시 실제 문서를 통과시켜 본다.** 빌드 성공과 테스트 통과는 데이터가 쓸모 있다는 뜻이 아니다.

이 항목은 실제로 세 번 더 적중했다. 예문을 실데이터에서 뽑자마자 **활용형 비문**(`받음하실`), **1음절 동음이의어**(`한 번` → `까지 번`), **로마자 경계 없음**(`CCTV` → `C전류 변성기V`)이 한꺼번에 드러났다. 셋 다 그때까지 테스트 127개를 전부 통과하던 상태였다.

#### (8) 서술성 명사 판정이 문자 종류를 안 본다 (미수정)

`_is_predicate_noun()`이 **음절 수만 보고 한글인지 로마자인지 구분하지 않는다.** 그래서 `AI`·`CT`·`DR`·`IT`·`QR` 같은 **2글자 로마자 약어 21개**가 서술성 명사로 오판정되어 `AI하다`·`AI되며` 같은 정크 변형형을 갖는다(2026-08-29 실측 754건).

실사용 위험은 낮다 — §6.7 (4)의 로마자 경계 검사가 `PERFECT됨`류 안쪽 매칭을 막고, `AI되다` 자체가 자연스러운 한국어가 아니라 문서에 안 나온다. 골든 57건 전수 스캔에서도 이 21개 표제어의 매칭은 0건이었다.

**그래도 결함이다.** 색인만 늘리고 값을 못 낸다. 수정 방향은 `_is_predicate_noun()`에 한글 전용 조건을 더하는 것이다.

> 이 결함은 되다-파생 확장(2026-08-29) **이전부터 있었다.** 확장이 규모를 두 배로 넓혔을 뿐이라, 어미 목록을 되돌린다고 해결되지 않는다.

#### (7) 원천이 자기가 안 만든 엔트리의 귀속을 가져간다

예문 원천(318행)을 6번째 `--input`으로 얹었더니 **엔트리 318개의 `source_id`가 그 원천으로 바뀌었다.**

```
nikl:admin2018                     1693
easydict:corpus-examples-golden57   318   <- 예문만 얹으려던 원천
krdict:advanced                       8   <- 114에서 줄었다
```

`upsert()`의 `ON CONFLICT DO UPDATE`가 `source_id`도 다른 필드처럼 최신 원천 것으로 갈아치우기 때문이다. 태그·변형형·예문은 이미 "먼저 온 것 유지/병합"으로 고쳐졌는데(§5.5(1)) **`entries.source_id`에는 그 보호가 없었다.**

피해는 귀속 표시로 끝나지 않는다. **§6.8 키②가 원천 신뢰도를 읽는다.** 예문 원천은 신뢰도 표에 없어 tier 0이므로, 318건이 조용히 최하위로 강등되고 승자가 뒤집혔다.

```
적재 전:  모니터링 -> 정보 수집  source=nikl(tier 1)   <- 승자
적재 후:  모니터링 -> 정보 수집  source=예문(tier 0)   -> '점검'이 이김
```

그리고 **재현성 검사가 이걸 못 잡았다.** fwd/rev 빌드 비교가 `(term_norm, easy_term, strategy, risk, status, readability)`만 대조하고 `source_id`를 안 봤다 — §5.5의 "검사 도구의 겨냥이 틀린 경우"가 또 나온 것이다.

#### 결정: 원천에 역할을 준다

> **예문만 기여하는 원천은 엔트리를 만들지도 고치지도 않는다.**

`--source-role examples`로 선언한 원천은:
- 기존 엔트리에 **예문만** 붙인다
- 표제어가 사전에 없으면 그 행을 **버리고 사유를 리포트에 남긴다**(조용히 버리지 않는다)
- `source_id`를 포함해 엔트리의 어떤 필드도 안 건드린다

이 결정이 (6)도 같이 해소한다. 엔트리 필드를 안 쓰므로 **예문 CSV가 전략·위험도 스냅샷을 담을 이유가 사라진다.** 상태가 두 곳에 사는 문제가 원인에서 없어진다.

#### (6) 같은 상태가 두 곳에 산다

예문 원천(`data/raw/corpus_examples_golden57.csv`)은 `upsert`의 덮어쓰기를 피하려고 **엔트리의 모든 필드를 복사해** 담는다. 그래야 이 원천이 마지막에 적재돼도 기존 분류를 우연히 뒤집지 않는다.

부작용이 있다. **적재 시점의 전략·위험도가 그 CSV에 얼어붙는다.** `거치`를 `substitute`에서 `gloss`로 내렸더니, 그 CSV에 박힌 `substitute`가 명시값으로 취급돼 재분류를 도로 덮었다(사람이 정한 값이 휴리스틱보다 우선하는 것이 §5.2 원칙이므로 파이프라인은 정상 동작한 것이다).

> **엔트리를 재분류하면 예문 원천 CSV도 같이 고쳐야 한다.**

이번엔 스크래치 검증의 컬럼 단위 diff가 잡았다. 다음엔 못 잡을 수 있다. 근본 해법은 예문 원천이 표제어와 예문만 담고 엔트리 필드를 안 갖는 것인데, 그러려면 `upsert`가 원천별로 어떤 컬럼을 쓸지 구분해야 한다 — 아직 안 했다.

### 5.5.1 짧은 한자어 표제어의 동음이의어 — 어종이 아니라 형태 충돌이 갈림길

골든 코퍼스 57건으로 1음절 표제어 15건을 전수 측정한 결과다.

```
자(者)  53건 중 92% 의도한 뜻      "졸업한 자는" -> "졸업한 사람은"
한(限)  11건 중  0% 의도한 뜻      전부 관형사 '한(하나의)' 또는 어미 '-한'
소(訴)   5건 전부 PDF 추출 잔재     판정 불가
갭·붐·존·팁·폼(외래어)  0건        코퍼스에 안 나옴 — 안전성 검증 불가
```

**"1음절 한자어가 위험하고 외래어는 덜하다"는 가설은 틀렸다.** 같은 한자어인데 `자`는 92%, `한`은 0%다. 실제 갈림길은 이것이다.

> **그 표면형이 초고빈도 고유어 문법 요소(관형사·활용어미)와 형태가 겹치는가.**

`한`이 위험한 건 한자어라서가 아니라 한국어에서 가장 흔한 관형사 `한(하나의)`과 똑같이 생겨서다. 형태소 정보 없이는 못 가른다 — `josa_pattern()`이 이미 스스로 경고해 둔 모호성과 같은 종류다.

그리고 이건 **1음절만의 문제가 아니다.**

```
수리(受理) -> 받음        "신청서 수리"
수리(修理)               "주택 수리 비용"   <- 사전에 없지만 문서엔 흔하다
```

엔트리는 한자 기준으로 옳다. 표면형이 두 뜻을 다 삼키는 게 문제다. §5.7에서 다듬은말 원천을 탈락시킨 이유가 우리 사전 안에도 이미 들어와 있었다.

#### 판정 (실측 근거)

| 표제어 | 처분 | 근거 |
|---|---|---|
| `한(限) → 까지` | **비활용** | 11건 전부 다른 뜻. 의도한 용법이 코퍼스에 한 번도 없다 |
| `소(訴) → 소송` | `gloss` + 검수 | 실사용 0건. 소/小/訴/牛 충돌 가능 |
| `수리(受理) → 받음` | `gloss` + 검수 | 修理가 복지 문서에 더 흔하다 |
| `자(者) → 사람` | `substitute` 유지 | 92% 정확. `졸업한 자는 → 졸업한 사람은`은 우리가 원하는 변환 그 자체 |
| 갭·붐·존·팁·폼 | `substitute` 유지 | 고유어 문법 요소와 충돌 없음 |

#### 규칙

**1음절 표제어는 휴리스틱만으로 `substitute`를 받지 못한다.** 기본값은 `gloss` + 검수 큐이고, 사람이 확인한 것만 승격한다. 정보량이 너무 적어 원문을 지울 근거가 못 된다.

#### 같은 위험이 변형형에도 있다 — `~하다` 동사의 맨 어간

위 규칙은 **표제어**만 본다. 그런데 `~하다` 동사 표제어가 **맨 어간 변형형**을 자동 생성하면서 같은 위험이 뒷문으로 들어온다.

```
부상을 당한 경우   ->  부상(떠오르다)     浮上하다의 어간이 負傷을 삼킴
인력 배치 계획     ->  배치(어긋나다)     背馳하다의 어간이 配置를 삼킴
가. 신청 방법      ->  가(더하다)         加하다의 어간이 열거 기호를 삼킴
```

동형어 검수에서 `가하다` 빈도 40으로 잡혔는데, **40건 전부 `加`도 `可`도 아니라 열거 기호 `가.`**였다. 엔트리는 멀쩡하다 — `부담을 가하다`는 지금도 올바르게 매칭된다. **틀린 것은 어간 변형형이다.**

> **`~하다` 동사 표제어는 맨 어간 변형형을 생성하지 않는다.**

반대 방향(§3.5의 서술성 명사 하다-파생 — `지참` → `지참하시기`)은 그대로 둔다. 그쪽은 명사 표제어가 자기 활용형을 갖는 정상 동작이다. 금지하는 것은 **동사 표제어가 명사 자리를 차지하는 것**이다 — §6.8의 "표면형 소유권"과 같은 원칙이고, 여기서는 소유자가 아예 없어서 소유권 규칙이 못 걸리는 경우다.

`날인하다(捺印)`처럼 어간이 정당한 경우를 잃는 손실이 있다. 그래도 이쪽을 택한다 — **원문을 잘못 바꾸는 것이 못 잡는 것보다 나쁘다.** 어간이 실제로 필요하면 별도 표제어로 넣으면 된다.

2음절 이상은 이 규칙으로 못 막는다(`수리`가 그렇다). §5.6의 갭 리스트가 "사전에 없는 말"을 찾는다면, 이쪽은 **"사전에 있는데 다른 뜻으로 쓰이는 말"**을 찾아야 한다.

#### 안 되는 방법 — 전문용어 사전끼리의 교차검증

먼저 시도했다가 버린 방법을 기록한다. 다시 시도하지 말 것.

> 다듬은말 풀(§5.7)에 표제어별 한자가 있으니, **우리 표제어와 같은 한글인데 풀에서 다른 한자를 달고 있으면** 동음이의어로 보자.

**재현율 0%였다.** 이미 아는 5건(`수리`·`가설`·`거치`·`한`·`소`) 중 하나도 못 잡았다. 우연이 아니라 구조다.

> 두 원천 모두 "국립국어원이 다듬을 만한 전문·행정 용어"만 수록한다. `受理`처럼 행정 용어인 뜻은 양쪽이 똑같이 갖고, **`修理`처럼 이미 쉬운 일상어인 뜻은 애초에 둘 다 안 갖는다.** 다듬을 필요가 없는 말이니까.

**전문용어 사전 두 개를 교차검증하면 정의상 "전문용어가 아닌 흔한 뜻"과의 충돌을 못 본다.** 이번에 실제로 문제였던 5건이 100% 이 사각지대에 있었다.

부수 교훈도 하나 있다. 이 방법이 만들어낸 신호 37건을 NFKC로 정규화하니 **2건으로 줄었다** — 나머지 35건은 CJK 호환 한자 이체자(`率` U+7387 vs U+F9DB)와 한자 오탈자였다. 정규화 없이 검수 목록으로 냈다면 검수자가 잡음을 읽었을 것이다. §3.4.1의 정규화 축을 탐지 도구에도 적용해야 한다.

#### 되는 방법 — 일반 국어사전의 동형어 번호

필요한 건 전문용어 목록이 아니라 **일반 국어사전의 다의어 정보**였다. 한국어기초사전(krdict) 검색 API가 `sup_no`(동형어 번호)를 준다.

```
수리  동형어 4개   修理 고장 난 것을 손보아 고침 / 數理 / 水利 / 受理 안건·서류를 공식 처리함
한    동형어 3개   (고유어) 하나의 / 恨 / 限 시간·수량의 끝
소    동형어 4개   (고유어) 소(牛) / (고유어) 만두 속 / 小 / 訴
자    동형어 5개   (고유어) 길이 재는 도구 / 字 / 者 ...
```

알려진 5건 중 **4건이 잡힌다.** `한`이 `(고유어) 하나의`를 달고 나오는 것이 결정적이다 — 코퍼스에서 11/11로 확인된 그 충돌이다. **일반 사전이라 고유어와 일상어 뜻을 갖고 있다**는 점이 전문용어 사전과의 차이다. 그래서 한자가 없는 `substitute` 엔트리(789건, 53%)에도 적용된다.

운용 규칙:
- **동형어 수는 신호이지 판정이 아니다.** `자(者)`는 동형어 5개지만 코퍼스 92% 정확이다. 플래그와 코퍼스 빈도를 나란히 놓고 **사람이 판정한다**
- 빈도가 우선순위다 — `한` 567회, `소` 512회, `수리` 18회, `가설` 0회
- 못 잡는 것: `거치(据置) → 예치`처럼 **동형어가 아니라 대치어가 원래 뜻과 미묘하게 다른** 경우. 이건 별개 문제로 남는다

### 5.6 사전과 갭 리스트는 서로를 개선한다

공개 데이터에 복지 순화어가 없다는 것이 조사 결론이었다(§9). 그래서 **변환 대상 문서에서 직접 용어를 뽑는다** — easy-doc의 복지 안내문 57건에서 "문서에는 나오는데 사전에는 없는 말"을 추출한 것이 갭 리스트다(`tools/extract_gaps.py`).

여기서 실측으로 확인된 성질이 있다.

> **갭 리스트 품질은 실행 시점의 사전 크기에 의존한다.**

사전이 92건일 때 만든 리스트에는 `차상위`·`보장법`·`중등교육법` 같은 **잘린 조각**이 섞여 있었다. 그런데 1,899건 사전으로 **같은 스크립트를 다시 돌리기만 했는데** 조각들이 사라졌다 — `차상위계층`·`국민기초생활 보장법`·`초·중등교육법`이 표제어로 들어가면서 매칭 단계에서 통째로 소비됐기 때문이다.

즉 **추출 로직을 고치지 않아도 사전이 자라면 잡음이 준다.** 반대로 사전이 자라려면 갭 리스트가 필요하다. 둘은 순환 관계다.

운영 규칙:
- 갭 리스트는 **항상 최신 `dist/easy_dict.sqlite3`로** 뽑는다
- **커밋하지 않는다.** 재생성이 0.25초이고, 파일로 두면 사전이 자랄 때마다 낡는다. 낡은 갭 리스트가 정확히 위 문제의 원인이었다
- 결과를 해석할 때 "이 리스트는 실행 시점의 사전 크기를 전제한다"를 감안한다

#### 남은 한계: 재현율보다 정밀도

1글자 활용 어미(`고`·`은`·`는`·`지`)를 공격적으로 걸러내면 `받고`·`남은` 같은 잔재는 사라지지만, `참고`·`복지`·`고지`·`거주지`처럼 **끝음절이 우연히 같은 진짜 한자어 명사**까지 잘려나간다. 실제로 `거주지`·`주소지`가 이 방식으로 걸리는 회귀가 발생했다.

형태소 분석기 없이는 "고유어 동사 어간"과 "한자어 명사 끝음절"을 구별할 수 없다. **잡음 몇 건이 남는 것보다 진짜 용어를 잃는 손실이 크므로 정밀도를 택한다.**

### 5.7 원천 평가 기준: 순화 목록은 쉬운 말 목록이 아니다

**국립국어원 다듬은말 18,340건을 수집해 적재 직전까지 갔다가 적재하지 않기로 한 사례에서 도출한 기준이다.** 같은 판단을 다시 하지 않도록 근거를 남긴다.

이 데이터는 컬럼 구조가 완벽했다 — 표제어·순화어·어원·뜻풀이·비고가 모두 채워져 있고, 결번 없이 18,340건, 상세 페이지까지 전수 확보. **형식만 보면 지금까지 확보한 어떤 원천보다 좋았다.** 그래서 위험했다.

코퍼스 실측(골든 문서 57건)에서 드러난 것:

```
급여      → 봉급           문서 8건 등장.  생계급여·주거급여의 그 급여를 '월급'으로
제공하다  → 바치다         문서 26건 등장. 더 어려워짐
서류      → 감자류(薯類)   書類가 아니다
경우      → 목털(頸羽)     境遇가 아니다.  "~하는 경우에는" 마다 매칭
전화      → 전쟁 피해(戰禍) 電話가 아니다
크레인    → 기중기         순화는 맞지만 쉬워지지 않는다
```

원인은 데이터 오류가 아니다. **이 목록은 1978~2002 문교부 국어순화자료집 계열이고, 그 사업의 목표가 우리 목표와 다르다.**

| | 국어 순화의 목표 | 이 사전의 목표 |
|---|---|---|
| 기준 | 한자어·외래어를 고유어로 | 어려운 말을 이해되는 말로 |
| `제공하다→바치다` | 성공 | 실패 |
| `크레인→기중기` | 성공 | 실패 |

두 목표는 겹치는 구간이 있어서(`동절기→겨울철`, `앰뷸런스→구급차`) 원천을 훑어보면 맞는 데이터처럼 보인다. **겹치는 구간만 보고 판단하면 안 된다.**

규모도 확인했다. 1~2음절 표제어가 8,207건(34%)이고 **그중 7,762건이 `substitute` 전략**이었다. 코퍼스 상위 매칭어가 `하`·`한`·`이`·`자`·`인`·`등`·`본` 같은 1음절이라 한국어 문서 어디에나 걸린다.

#### 규칙

새 원천을 적재하기 전에 **형식이 아니라 목표를 먼저 확인한다.**

1. **그 데이터가 만들어진 목적이 "쉽게 하기"인지 확인한다.** 순화(醇化)·정비·표준화·통일은 전부 다른 목표다. 사업명과 발간 연도를 본다.
2. **대치어가 표제어보다 쉬운지 표본으로 검증한다.** 20건이면 충분히 드러난다. `바치다`·`기중기`·`감자류`가 나오면 그 원천은 이 사전의 원천이 아니다.
3. **1~2음절 표제어 비율을 센다.** 높으면 동형이의어 오염을 의심한다. 한자를 병기한 원천이라도 §3.4.1의 한자 길이 신호로는 **같은 길이 동형이의어를 못 잡는다**(`명시[名詩]`, `절상[切上]`).
4. **코퍼스 고빈도 매칭이 곧 가치는 아니다.** 이 원천은 매칭 상위 60건 중 대부분이 다른 뜻이었다. 흔한 단어에 매칭될수록 오염 규모가 크다.

#### 탈락한 원천의 처분: 버리지 않고 후보 풀로 둔다

적재는 0건이지만 데이터는 보관한다(`~/korean-refined-words/`, 저장소 밖). 용도는 **후보 발굴**이다 — 갭 리스트(§5.6)에 걸린 말을 이 목록에서 찾아 대치어 후보를 얻고, **사람이 검수한 것만** `welfare_seed` 방식으로 적재한다.

원천으로 쓰는 것과 후보 풀로 쓰는 것의 차이는 **검수가 앞에 있느냐 뒤에 있느냐**다. 이 구분이 §4.4 안전 계약(미검수 초안은 원문을 삭제할 수 없다)의 적재 단계 대응물이다.

도구는 `tools/review_candidates.py`다. 갭 리스트(§5.6)와 후보 풀을 교차해 **사람이 O/X를 칠 검토표**를 만들 뿐, 사전에는 아무것도 넣지 않는다. `분야`·`replace_strategy`·`risk_level`·`status`는 **일부러 비워서** 출력한다 — 미리 채우면 "이미 정해진 걸 승인만 하면 되는" 착시가 생겨 검수가 형식이 된다. 출력 CSV는 §5.6과 같은 이유로 커밋하지 않는다.

실행 결과가 이 절의 판단을 사후 검증했다. **갭 용어 2,831건 중 후보가 있는 것은 129건(4.6%)뿐**이고, 그 매칭된 것들이 하필 `이유→젖떼기`(理由/離乳), `전화→전쟁 피해`(電話/戰禍)였다. 전량 적재했다면 메워지는 구멍은 4.6%인데 오염은 전면적이었을 것이다.

컬럼 별칭(`source_term`·`refined_term` 등)과 `origin_language` 처리는 저장소에 남겨둔다 — 선별 적재할 때 다시 쓴다.

| 대치어 | 있다 (완비) | **없다 (컬럼 자체가 없다)** |
| 탈락 사유 | 그 대치어를 고른 사업의 목표가 우리와 다르다 | 엔트리를 만들 재료가 없다 |
| 한 줄 | 적재하면 오염된다 | 적재할 수 있는 형태가 아니다 |
| 처분 | 후보 풀 — 검수 뒤 적재한다 | 판정용 화이트리스트 — 적재하지 않는다 |

컬럼은 `법령용어`·`비고내용`·`등록일시` 셋뿐이다. `비고내용`은 1,273행(1.1%)만 채워져 있고, 채워진 것도 대치어가 아니라 **동음이의 구분용 뜻풀이**다.

```
외환   → 외국과의 거래를 결제할 때 쓰는 환어음(外換)
교각   → 두 직선이 만나서 이루는 각 / 두 곡선이나 두 원의 접선이 만나서 이루는 각(橋脚)
```

기준 1(목적)의 답은 여기서 이미 나온다. 이 목록은 **순화어 대조표가 아니라 법령 검색·참조용 용어 색인**이다. 등록 연도 분포(2022년 60,119건 · 2023년 49,899건 · 2024년 6,527건)도 순화 사업의 발간 이력이 아니라 색인 축적의 흔적이다.

#### 기준 2 앞에 0번이 있다: "대치어 컬럼이 존재하는가"

이 원천에는 **기준 2(대치어가 표제어보다 쉬운지 표본 검증)를 적용할 수 없다.** 판정이 어려운 것이 아니라 판정할 대상이 없다. `entries.easy_term`은 필수 컬럼이고(§3.2), 이 CSV만으로는 그 값을 채울 방법이 없다 — **이 원천 단독의 적재 가능 엔트리는 0건이다.**

무작위 20건 표본(seed 20240912)을 뽑아 확인했다.

```
임용자격 · 문화통상협력과장 · 지정변경신고서 · 기부문화 · 시설권
시제품생산계약 · 대위자 · 폐쇄통보 · 발전가능성 · 평정기준일
인터넷전용회선서비스 · 용구 · 국방과학연구소 · 해안가 · 임용무효
강습교육 · 감경대상 · 악취배출시설 · 정수시설 · 원목
```

행정 복합명사와 기관명이다. "이것보다 쉬운 말이 무엇인가"를 이 파일은 말하지 않는다.

> **위 규칙 1번 앞에 0번이 있다 — 대치어(순화어) 컬럼이 있는가.**
> 없으면 기준 1~4를 적용할 것도 없이 원천이 아니다. 용어 목록과 용어 대조표는 다른 물건이고, 파일 크기·행 수·기관 신뢰도는 이 구분에 아무 도움이 안 된다.

기준 0을 건너뛰면 어떻게 되는지도 적어 둔다. 이 파일은 11.6만 행에 법제처 발행이라 **훑어보면 어떤 원천보다 권위 있어 보인다.** 다듬은말이 "형식이 완벽해서 위험했다"면 이건 "규모와 출처가 그럴듯해서 위험하다" — 둘 다 내용이 아니라 겉모습이 판단을 끌고 간 경우다.

#### 기준을 하나 통과한 것은 통과가 아니다

기준 3(1~2음절 비율)만 놓고 보면 이 원천은 다듬은말보다 **낫다.** 1글자 157건 + 2글자 7,213건 = 7,370건으로 6.4%뿐이고(다듬은말은 34%), 길이 최빈값은 4글자 38,106건이다. 네 기준 중 유일하게 통과권이다.

그런데 기준 4(코퍼스 고빈도 매칭)를 실측하면 그 6.4%가 매칭을 지배한다. 참조 구현(`easydict.lookup.EasyDict`, 최장일치 + §6.7 경계 규칙)으로 골든 문서 56건을 실제로 통과시킨 결과다.

| | 값 |
|---|---|
| 매칭된 표제어 | 2,188종 |
| 매칭 횟수 | 연 10,201회 (문서당 182회) |
| 그중 1~2글자 표제어가 차지하는 비중 | **66.3%** |
| 기존 사전·easy-doc 내장 목록이 이미 덮는 것 | 447종 |
| 이 원천만의 신규 기여 | 1,741종 |

신규 기여 1,741종을 문서 빈도(df) 순으로 세우면 이렇다.

```
지원 44 · 경우 43 · 대상 42 · 신청 42 · 방법 41 · 수 36 · 시 36 · 내용 35
기준 34 · 이상 34 · 서비스 32 · 서류 31 · 근거 27 · 안내 27 · 법령 25
조사 25 · 제공 24 · 관리 23 · 신청서 23
```

**전부 어렵지 않은 말이다.** 법령 색인으로서는 정당한 등재다 — `지원`도 `경우`도 법령 조문에 쓰이는 용어이므로 색인에 있어야 한다. 그러나 우리 사전에 들어오면 문서마다 40회씩 걸리면서 아무것도 쉽게 만들지 못한다. 여기에 행정구역 1글자(`군` 24 · `동` 22 · `읍` 20 · `면` 19)가 신규 상위에 섞여 있어 **주소를 건드린다.** 문서당 182회는 커버리지가 아니라 잡음의 규모다.

중복도 재 봤다. 현재 사전 표제어 1,533건 중 **595건(38.8%)** 이 이 목록에 있고, easy-doc 내장 목록 167건 중 137건도 있다. 겹침이 크다는 사실은 이 목록이 어려운 말을 골라 담았다는 뜻이 **아니다** — 행정 문서에 나오는 말을 가리지 않고 담았으니 우리 표제어도 그 안에 들어 있을 뿐이다. §5.7 앞부분의 "겹치는 구간만 보고 판단하면 안 된다"가 여기서도 그대로 적용된다.

> **기준은 통과 개수로 세지 않는다.** 이 원천은 4개 중 1개(기준 3)를 통과했고, 통과한 그 하나가 나머지의 탈락을 상쇄하지 못한다. 기준 0에서 이미 끝난 판정을 기준 3의 숫자가 되살리지 않는다.

#### 이 파일의 처분: 후보 풀이 아니라 판정용 화이트리스트

**저장소에 유지한다. 다만 원천이 아니라 참조 데이터다.** 용도를 하나로 못 박는다 — 갭 리스트(§5.6)의 **"잘린 조각"** 판정이다.

`tools/README.md`가 갭 발굴 실패 유형으로 적어 둔 그 문제다. `국민기초생활 보장법`이 아직 사전에 없으면 갭 리스트에 `국민기초생활`과 `보장법`으로 쪼개져 나온다. 지금 대응은 "사전이 자라면 저절로 사라진다"인데, 그건 **이미 등재된 표제어에만** 듣는다. 아직 없는 새 복합어의 최초 발견은 여전히 조각난 채로 나온다. 이때 "이 문자열이 실제로 존재하는 법령용어인가"를 115,732건으로 조회할 수 있다.

대치어가 없다는 성질이 여기서는 결격이 아니다. **판정에 필요한 것은 표제어 목록의 존재 여부뿐**이고, 이 파일은 정확히 그것만 가지고 있다. 적재 원천으로 쓸모없게 만든 성질과 판정용으로 쓸모 있게 만드는 성질이 같은 성질이다.

**도구는 아직 없다.** 이 절은 용도를 고정해 둘 뿐이고 판정기는 구현되지 않았다. 구현하기 전까지 이 파일은 아무 데서도 읽히지 않는다.

다듬은말의 처분과는 다르다는 점을 분명히 해 둔다.

| | 다듬은말 | 법령용어 |
|---|---|---|
| 위치 | `~/korean-refined-words/` (저장소 밖) | `data/` (저장소 안, `data/raw/` 아님) |
| 역할 | **후보 풀** — 갭 용어의 대치어 후보를 얻고, 사람이 검수한 것만 적재한다 | **화이트리스트** — 문자열이 법령용어인지 판정만 하고 적재하지 않는다 |
| 검수 | 적재 앞에 있다 | 적재가 없으므로 해당 없다 |
| 사전 엔트리 기여 | 선별 적재 시 있다 | **영구히 0건** |

위치가 `data/raw/`가 아니라 `data/` 바로 아래인 것도 이 결정의 일부다. **`data/raw/`는 빌드가 적재하는 원천의 자리다** — §5 파이프라인 도식의 입구가 `data/raw/*.csv`다. 적재하지 않기로 한 파일을 거기 두면 다음 사람이 `--input`에 걸 이유가 생긴다 — 그러면 위에 적은 판정이 사고로 뒤집힌다. 다듬은말을 저장소 밖으로 내보낸 것과 목적은 같고 강도만 다르다: 다듬은말은 언젠가 검수를 거쳐 적재될 물건이라 빌드 입력과 아예 섞이지 않게 두었고, 이 목록은 적재될 일이 없으니 **파이프라인 입력 경로 밖이기만 하면 된다.**

### 6.5 `src/easydict/lookup.py` — easy-doc이 실제로 쓰는 표면
```python
@dataclass(slots=True)
class Match:
    start: int; end: int; surface: str
    entry_id: int; term: str; easy_term: str
    strategy: str; risk: str; definition: str | None; priority: int
    is_inflected: bool = False   # surface != term (활용형으로 매칭됨)

class EasyDict:
    @classmethod
    def from_index_json(cls, path: str | Path) -> "EasyDict"
    @classmethod
    def from_sqlite(cls, path: str | Path) -> "EasyDict"

    def find_all(self, text: str) -> list[Match]
        # 최장일치(longest-match) + 조사 경계 인식. 겹치면 priority 큰 쪽.
    def annotate(self, text: str, strategies=("substitute","gloss")) -> str
        # substitute: 원어 교체 / gloss: '원어(쉬운 말)' / keep: 원문 유지
        # 단, is_inflected=True 인 substitute 매칭은 교체하지 않고 gloss와 동일하게
        # '활용형(쉬운 말)' 로 폴백한다. (§6.6 참조)
    def build_prompt_context(self, text: str, max_terms: int = 30) -> str
        # LLM 프롬프트에 주입할 마크다운 블록 생성 (§7.2). 이 사전의 최종 목적.
    def search(self, query: str, limit: int = 10) -> list[dict]
        # FTS5 (sqlite 모드) / 부분일치 (json 모드)
```
**매칭 알고리즘**: 표면형 트라이(dict 중첩)로 각 위치에서 최장일치. 외부 의존성 금지. 오른쪽 경계는 `josa_pattern()` 또는 비한글 문자여야 한다 — `내방`이 `내방객`에 잘못 걸리는 것을 막는다.

### 6.6 활용형 치환 금지 규칙 — 실제 결함에서 도출된 계약

초판 설계는 "활용형으로 매칭한다"와 "easy_term으로 치환한다"를 각각만 명시하고 **둘이 만나는 지점을 정의하지 않았다.** 그 결과 다음 비문이 생성됐다.

```
입력   : 신청서에 이름과 주소를 명기하여 주십시오.
매칭   : '명기하여' → term='명기하다', easy_term='쓰다', strategy=substitute
잘못된 출력: 신청서에 이름과 주소를 쓰다 주십시오.      ← 어미가 통째로 소실
```

**규칙**: 굴절형 매칭(`surface != term`)에서 **자동 활용(어미 재결합)을 시도하지 않는다.**
한국어 용언 활용은 불규칙이 많아(`쓰다`+`-여` → `써서`) 규칙 기반 생성이 신뢰할 수 없고, **잘못 활용된 말은 원문을 그대로 둔 것보다 나쁘다.** 읽는 사람이 지적·발달장애인이기 때문에 비문은 품질 저하가 아니라 이해 차단이다.

대신 원문 어미를 보존하고 쉬운 말을 덧붙인다.
```
올바른 출력: 신청서에 이름과 주소를 명기하여(쓰다) 주십시오.
```

`build_prompt_context()`는 이 폴백의 영향을 받지 않는다. LLM이 활용을 처리하므로 **표제어 원형으로 표기**하고(`명기하여`가 아니라 `명기하다 → 쓰다`) `entry_id` 기준으로 중복을 제거한다.

### 6.7 조사 교정과 경계 판정 — Kotlin 포팅 시 반드시 이식할 규칙

`lookup.py`는 참조 구현이고 easy-doc(Kotlin)이 이를 다시 구현한다(§7.1). 아래 세 규칙은 **문서를 훼손하느냐 마느냐를 가르므로** 이식에서 빠지면 안 된다. 셋 다 실제 결함에서 도출됐다.

#### (1) 치환 후 조사 이형태 교정
`substitute`로 단어가 바뀌면 받침이 달라지므로 뒤따르는 조사도 바꿔야 한다.
```
급여(받침 없음) + 는  →  지원금(받침 ㅁ) + 은
잘못된 출력: 지원금는 월 30만 원입니다.
```
- 교정 쌍: `은/는` `이/가` `을/를` `과/와` `으로/로` `이나/나` `이란/란` `이라는/라는` `이며/며` `이랑/랑` `아/야` `이여/여`
- 받침 판정: `(code - 0xAC00) % 28 != 0`
- **ㄹ 받침 예외**: `으로/로`는 종성이 ㄹ(종성 인덱스 8)이면 `로` (`서울로`, `지하철로`)
- 새 단어가 한글로 끝나지 않으면(숫자·영문·기호) 교정하지 않는다
- **적용 범위는 `substitute` + 원형 매칭뿐.** `gloss`/`keep`/굴절형 폴백은 원어가 문장에 남으므로 조사가 이미 맞다

#### (2) 연쇄 조사는 첫 조사만 교정한다
```
급여로는 충당이 안 됩니다.  →  지원금으로는 충당이 안 됩니다.
급여에서는 제외됩니다.      →  지원금에서는 제외됩니다.   (는은 그대로)
```
체언에 직접 붙는 **첫 조사만** 원래 명사의 받침에 좌우된다. 그 뒤 보조사는 직전 조사에 붙는데, 조사는 형태가 고정이라(`에서`는 언제나 `서`로 끝나 받침이 없다) 명사가 무엇이든 형태가 변하지 않는다. 따라서 첫 토큰 하나만 교정하면 충분하고, 나머지 체인은 경계 확인만 하면 된다.

#### (0) 표면형 소유권이 `priority`보다 먼저다

§6.8의 승자 정렬은 export 시점에 구워 나가므로 포팅할 것이 없지만, **이 규칙은 조회 시점이라 포팅해야 한다.** `_longest_match_at()`이 원래도 `max(ids, key=priority)`를 조회 시점에 하므로(§6.5) Kotlin이 이미 재구현하는 구간이고, 그 앞에 필터가 하나 붙는 것이다.

```
surface      = text[i:end]
exact_ids    = [eid for eid in ids if entries[eid].term == surface]
candidate    = exact_ids or ids
winner       = max(candidate, key=priority)
```

`entries[].term`은 `index.json`에 이미 있는 필드다 — **추가 데이터도, 색인 크기 증가도 없다.** 이 세 줄을 빼먹으면 `내방을`이 동사 `내방하다`로 잡혀 명사 자리에 동사 원형 설명이 붙는다.

#### (4) 로마자·숫자 경계도 확인해야 한다

조사 경계 검사(§6.5)는 "다음이 한글 음절이 아니면 통과"라, **로마자·숫자끼리 이어 붙는 경우를 전혀 못 걸렀다.** 실측:

```
CCTV를 설치합니다      ->  'CT'가 매칭  ->  C전류 변성기V를 설치합니다   (원문 파괴)
TFT 구성 후 운영합니다  ->  'TF'가 매칭  ->  TF(특별 전담 조직)T 구성 후
```

**규칙**: 매칭된 표면형의 첫 글자가 로마자·숫자면 바로 앞 글자도 로마자·숫자여서는 안 된다. 끝 글자가 로마자·숫자면 바로 뒤도 마찬가지다. **한글 표제어에는 적용하지 않는다** — `3개월`의 `개월`은 숫자 뒤에서 정상 매칭돼야 한다.

```
CCTV   'CT'가 'C' 뒤 -> 거부       MOU를  'MOU' 뒤가 '를'(한글) -> 허용
TFT    'TF' 뒤가 'T' -> 거부       TF팀   뒤가 '팀'(한글) -> 허용
```

한글 경계는 네 차례에 걸쳐 고쳤는데(§5.5(3)) 로마자 경계는 **처음부터 없었다.** 표제어별 패치가 아니라 구조 규칙이므로, 사전에 있는 **로마자·숫자로 시작·끝나는 표면형 817개(그중 4글자 이하 404개)가 한 번에 보호된다.**

`_left_boundary_ok`/`_boundary_ok`가 조회 시점에 적용한다 — (0)과 같은 이유로 Kotlin도 이식해야 한다.

#### (3) 조사 경계는 조사 뒤까지 확인해야 한다
조사 하나가 걸린다고 경계로 인정하면 복합어가 훼손된다.
```
급여과장에게  →  '과'를 조사로 오인  →  지원금과장에게   (직책명 파괴)
```
판정은 `표제어 + (조사)* + 어절경계` 여야 한다. 조사를 0개 이상 소비한 뒤 **다음이 한글 음절이면 매칭 실패**다. 정규식으로는 `(?:조사대안)*(?!한글음절)` — 그리디 소비 후 백트래킹으로 각 지점을 검사한다.

`급여과장`: `과` 소비 → 다음 `장`이 한글이라 실패 → 0개로 백트랙 → `과` 자체가 한글이라 실패 → 전체 거부.
`급여에서는`: `에서`+`는` 소비 → 다음이 공백 → 통과.

> **남는 모호성**: `급여과 협력`은 `급여과`(부서명)인지 `급여`+조사 `과`인지 문맥 없이 판별할 수 없다. 현재 구현은 매칭을 허용한다. 실데이터에서 이 패턴의 빈도가 높게 나오면 형태소 분석기 도입을 검토해야 한다.

#### (5) 길이 1 한글 표제어 전용 경계 규칙

위 (0)~(4)는 앞뒤 어절 경계가 "정상"인 경우만 다룬다. 그런데 길이 1 한글
표제어(`갭`/`붐`/`소`/`자`/`존`/`팁`/`폼`/`한` 등)는 앞뒤가 공백·문장부호로
정상적인 어절 경계인데도 표제어와 무관한 다른 것을 가리키는 경우가
실측에서 확인됐다 — easy-doc A/B 56건 실측(문서 051 등).

```
200자 이내로 작성하세요.        ->  '자'가 표제어 '자'(사람)에 매칭   (수량 단위 '글자 수'의 '자'를 오인)
자. 「학교 밖 청소년…」          ->  '자'가 표제어 '자'(사람)에 매칭   (가나다 목록 기호 '자.'를 오인)
```

**규칙**: 매칭된 표면형 길이가 1이고 한글 음절일 때, 다음 둘 중 하나에
해당하면 거부한다.

1. **수량 단위**: 바로 앞 글자가 ASCII 숫자(`0`-`9`)면 거부한다(전각 숫자는
   실측 코퍼스에 사례가 없어 다루지 않는다). `3개월`의 `개월`(길이 2)처럼
   길이 2 이상인 한글 표제어에는 걸지 않는다 — 숫자 뒤 한글 표제어는
   정상적으로 매칭돼야 한다.
2. **가나다 목록 기호**: 문서 시작 또는 개행 직후(공백·탭만 허용)에
   단독으로 나오고 바로 뒤가 `.` 또는 `)`이면 거부한다.

```
부정한 방법으로 교부받은 자는 처벌됩니다.   ->  허용 (법률문투 '자', 앞이 공백이고 줄머리도 아님)
```

이 정당한 매칭(법률문투 `자`)은 두 조건 다 해당하지 않으므로 계속
허용된다 — 규칙이 "길이 1 + 두 조건 중 하나"로 좁게 정의된 것은 이 매칭을
깨뜨리지 않기 위해서다. `_longest_match_at()`의 후보 검사 루프(길이를 아는
지점)에서 적용한다 — (0)·(4)와 같은 이유로 Kotlin도 이식해야 한다.

### 6.8 동일 표면형에 후보가 여럿일 때의 승자 결정

한 표제어에 엔트리가 여러 개 달리는 것은 예외가 아니라 **정상**이다. 원천 CSV가 한 표제어에 순화어를 여러 개 나열하고(`시스템 → 체제, 조직, 방식, 체계` / `선수 배치`), `row_to_entries()`가 이를 별개 엔트리로 쪼개기 때문이다. 현행 2,142건 사전에서 **467개 표제어가 이미 복수 엔트리를 갖는다.**

문제는 그중 **전략이나 위험도가 서로 다른 50건**이다. 실측으로 확인된 현행 동작:

```
priority = 100 + len(term) * 10          # build.py — 표제어 길이만 반영
winner   = max(ids, key=priority)        # lookup.py
ids      = ... ORDER BY id               # export.py — AUTOINCREMENT = 적재 순서
```

같은 표제어면 길이가 같아 **priority가 동률**이고, Python `max()`는 동률에서 첫 원소를 반환한다. 그 순서는 `id` 오름차순, 즉 **CSV에서 더 먼저 나온 행**이다. 승자를 정하는 기준이 "그 파일에서 먼저 쓰였다" 외에 아무것도 없다.

그리고 진 쪽은 상충 지침으로 남지 않는다. `find_all()`이 겹치는 위치를 승자 하나로 정리하므로 **패자는 그 문서에서 완전히 사라진다.** 위험 모드는 "LLM이 상충 지침을 받는다"가 아니라 **"보호 엔트리의 무음 실종"**이다.

실제 피해 사례:

```
독거노인  '홀로 노인'(substitute) 승   vs  '홀로 사는 노인'(gloss) 패
카시트    '안전 의자'(substitute) 승   vs  '아이 안전 의자'(gloss) 패
```

§2.1.1(축약이 범위를 좁힌다)이 금지하는 형태가 우연히 이기고 있다.

#### 정렬 키 (내림차순 우선, 위에서부터 적용)

1. **`risk_level`** — `high` > `low` > `none`
2. **원천 신뢰도** — 수작업 검수 > 사전 API > 대량 자동 판정
3. **전략 보수성** — `keep` > `gloss` > `substitute`
4. **원천이 제시한 순서** — 한 셀에 순화어가 여럿일 때 앞에 쓰인 것 우선
5. **`easy_term` 사전순 오름차순** — 결정적 최종 키

`risk_level`이 1번인 이유: 위험도는 **엔트리의 품질 주장이 아니라 세상에 대한 사실 주장**이다. 어느 원천이든 "이 말은 법적으로 위험하다"고 하면 위험한 것으로 다룬다. 반면 전략은 권고이므로 원천의 검수 수준(2번)이 먼저 온다 — 우리가 손으로 검수해 넣은 `substitute`가 대량 원천의 `gloss`에게 지면 품질 퇴행이다.

3번이 2번보다 뒤인 것은 의도적이다. 같은 원천 안에서 전략이 갈리면 그 불일치 자체가 불확실성의 신호이므로 **보수적인 쪽을 택한다.**

4번은 **버리고 있던 신호를 되찾는 키**다. 원천 CSV가 한 셀에 순화어를 여러 개 적을 때, **앞에 쓴 것이 권장어**다. 실제 데이터로 확인된다.

```
"아이시티, ICT(...)","정보 통신 기술, 정보 문화 기술"
                       ↑ 첫 번째가 맞는 답
```

이 신호 없이 5번(사전순)으로 가면 `정보 문화 기술`이 이긴다 — **ICT는 정보 통신 기술인데 틀린 답을 고르게 된다.** 현행 사전에서 **417개 표제어가 위 1~3번이 전부 동률**이라 이 구간에서 승부가 갈리므로, 여기서 신호 하나를 더 쓰는 것과 안 쓰는 것의 차이가 크다.

셀 **안**의 순서는 `--input` 순서나 파일 내 행 순서와 무관한 **내용**이다. 그래서 이 키를 써도 재현성 계약(§5.4)은 깨지지 않는다. 적재 순서와 저작 의도를 혼동하지 말 것 — 전자는 우연이고 후자는 신호다.

5번은 순서 독립성을 보장하는 장치다. `easy_term`은 내용이지 적재 순서가 아니다. `UNIQUE(term_norm, easy_term)` 때문에 여기서 반드시 전순서가 완성된다. **사전순 자체에 의미는 없다** — 신호가 다 떨어졌을 때 결정적이기만 하면 되므로 쓴다.

**4번이 고치는 것은 이독성이 아니라 정확성이다.** 실측(승자가 바뀐 211건 표본):

```
가주소(假住所)  "임시 주소, 거짓 주소"    사전순 -> '거짓 주소'   ← 틀렸다
감호(監護)      "보호, 감독, 보호 감독"   사전순 -> '감독'
가벌(家閥)      "집안, 지체"              사전순 -> '지체'
```

`가주소`는 임시 주소다. 시민의 주소를 "거짓 주소"라 부르는 지침이 LLM에 나가고 있었다.

반대 방향도 있다. `개수(改修)`는 `"수리, 고치기"`라 4번이 **더 어려운 `수리`**를 고르고, `가이드북`도 `길잡이` 대신 `안내서`가 된다. **원천의 셀 순서는 국립국어원의 순화 권고 순위이지 발달장애인 기준 이독성 순위가 아니다** — §5.7에서 다듬은말 원천이 탈락한 것과 같은 종류의 목표 불일치다.

그래도 4번을 쓴다. **틀린 대치어가 어려운 대치어보다 나쁘기 때문이다.** 이독성 역행은 검수 큐에서 사람이 되돌릴 수 있지만, `거짓 주소`는 아무도 안 보면 그대로 나간다. 승자가 바뀐 211건은 그대로 사람이 볼 목록이 된다.

#### 표면형이 어떤 표제어와 정확히 같으면 그 표제어가 임자다

위 정렬 키는 **같은 표제어에 순화어가 여럿일 때**를 다룬다. 그런데 실측에서 **다른 표제어끼리 같은 표면형을 두고 다투는** 별개 문제가 나왔다.

`~하다` 동사 표제어는 변형형 목록에 **맨 어간**을 포함한다. 그래서 명사 `가설`과 동사 `가설하다`가 둘 다 표면형 `가설`을 등록한다. `priority = 100 + len(term)*10`이므로 **더 긴 `가설하다`(140)가 명사 `가설`(120)을 항상 이긴다.**

```
"가설을 세워 검증하였다"   ->  LLM 지침: 가설하다 → 놓다       (架設: 전선을 놓다)
"거치 기간이 끝나면"       ->  LLM 지침: 거치하다 → 설치하다
```

`가설`(假設, 전선 가설)과 `가설`(假說, 가정)은 완전히 다른 말이다. `거치 기간`(원금 상환 유예)도 `거치하다`(설치하다)와 무관하다. 그리고 부수 피해가 더 크다 — **명사 엔트리는 자기 표면형에서 영원히 못 이기므로 조회로는 절대 안 나온다.** 사전에 있는데 도달 불가능한 죽은 데이터다(§5.5의 "조용히 버려짐"과 같은 종류).

규칙은 이렇다.

> **어떤 표면형이 한 엔트리의 표제어와 정확히 일치하면, 그 엔트리가 변형형으로만 걸린 엔트리를 이긴다.**

`내방` → 명사 엔트리, `내방하여` → 동사 엔트리(정확 일치가 없으므로). 길이가 아니라 **소유권**으로 가른다.

이 규칙은 최장일치(§2.2)와 충돌하지 않는다. 최장일치는 **표면형 길이**로 결정되고 트라이가 이미 처리한 뒤이므로, 여기서 다투는 후보들은 전부 같은 표면형이다. 표제어 길이는 그 시점에 의미가 없다.

실측 규모: 고유 표제어 조합 59쌍 중 명사/`~하다` 쌍이 4건(`가설`·`거치`·`내방`·`거주`). `가설`·`거치`가 실제 사고, `내방`은 오표시, `거주`는 두 뜻이 같아 무해. 나머지 55건은 로마자·약어 표기쌍(`VAN`/`브이에이엔`)이라 품사가 갈리지 않아 해당 없음.

#### `priority` 값을 바꾸는 방식으로 고치면 안 된다

가장 먼저 떠오르는 수정은 "`priority` 계산식에 risk를 섞는다"이다. **그러면 안 된다.** `priority`는 `lookup.py`에서 다섯 곳에 쓰인다.

| 위치 | 하는 일 |
|---|---|
| `_longest_match_at()` | 같은 표면형 후보 중 승자 선택 — **고쳐야 할 곳은 여기 하나뿐** |
| `find_all()` | 겹치는 매칭 간 우선순위 |
| `_collect_examples()` | 어떤 예문이 프롬프트에 먼저 실릴지 |
| `build_prompt_context()` | 예산 초과 시 **어떤 용어를 통째로 뺄지** |
| `search()` | 자유검색 순위 (FTS5 실패 시 폴백) |

특히 `find_all()`의 정렬 키는 `(-priority, -(end-start), start)`로 **`priority`가 매칭 길이보다 먼저** 온다. 지금은 `priority = 100 + len(term)*10`이라 사실상 길이 순서와 일치하지만, **risk를 섞는 순간 더 짧지만 위험도 높은 매칭이 더 긴 매칭을 밀어낸다.** §2.2가 전제하는 최장일치가 깨진다.

그래서 계약은 이렇다.

> **`priority` 필드의 값도 계산식도 건드리지 않는다. 승자 규칙은 후보 리스트의 순서로만 표현한다.**

#### 결정: 승자는 export 시점에 구워 넣는다

`export.py`가 `ORDER BY id` 대신 위 정렬 키로 후보를 정렬해 산출물에 쓴다. 조회 시점에 비교자를 두지 않는다.

이유는 §6.7과 같은 종류다. **easy-doc(Kotlin)이 이 규칙을 다시 구현하지 않아도 되기 때문이다.** 산출물의 후보 배열 순서 자체가 계약이 되면 소비자는 첫 원소를 쓰면 된다. 조회 시점 비교자로 두면 Python과 Kotlin 두 곳에 같은 규칙이 살고, 둘이 갈라지는 날 조용히 다른 답을 낸다.

부수 효과로 `index.json`이 `--input` 순서와 무관해진다 — §5.4 재현성 계약이 산출물 수준에서 구조적으로 보장된다.

#### 이 결함을 잡는 회귀 테스트는 파일 순서를 바꿔서는 만들 수 없다

**50건이 전부 한 원천 내부의 문제라, `--input` 파일 순서를 아무리 바꿔도 건드려지지 않는다.** 기존 `test_index_json_semantically_identical_ignoring_ids`는 두 겹으로 이 결함을 놓친다.

1. 후보 집합을 `frozenset`으로 비교해 **순서 정보를 의도적으로 지운다** — "후보군이 같다"만 보고 "누가 이기는가"는 안 본다
2. 파일 **간** 재정렬만 하므로 파일 **내부** 행 순서에 묶인 결함은 원리상 검출 범위 밖이다

그래서 테스트는 이렇게 만든다.

- 한 표제어에 전략·위험도가 다른 순화어가 여럿인 픽스처 CSV를 두고, **행 순서를 뒤섞어도 같은 승자**가 나오는지 본다
- 승자가 위 정렬 키대로인지 **값으로** 단언한다(집합 비교가 아니라)
- §5.5에 이 유형을 추가한다: **"검사 도구의 겨냥이 틀린 경우 — 순서를 바꿔 비교하는 검사는 그 순서가 파일 내부에 있으면 무력하다."**

## 7. easy-doc 연동

### 7.1 배포 경계
이 저장소는 `dist/` 산출물만 만든다. easy-doc은 그 파일을 리소스로 복사해 간다. 저장소 간 코드 의존은 만들지 않는다.

```
dictionary/dist/easy_dict.index.json
        └→ (빌드 시 복사) → backend-kotlin/.../resources/dictionary/
```
Kotlin 측은 `kotlinx.serialization`으로 `index.json`을 읽어 동일한 트라이를 구성하면 된다. 스키마가 언어중립이므로 파이썬 구현을 참조 구현으로 삼는다.

### 7.2 프롬프트 주입 형태 (`build_prompt_context` 출력)
사전이 LLM에게 전달하는 최종 형태. 전체 사전을 넣지 않고 **해당 문서에 실제로 등장한 용어만** 넣는 것이 핵심이다.

```markdown
## 이 문서에 나온 어려운 말 (반드시 아래 지침대로 처리하세요)

### 바꿔 쓰세요
- 내방 → 방문
- 지참 → 가져오기

### 원래 말은 남기고, 바로 다음 문장에서 쉽게 풀어 설명하세요 (원래 말을 지우거나 괄호로 붙이지 마세요)
- 과태료 — 뜻: 정해진 날짜보다 늦어서 더 내는 돈
- 차상위계층 — 뜻: 기초생활수급자 바로 위의 저소득층

### 절대 바꾸지 마세요
- 「국민기초생활 보장법」
- 2026년 1월 15일
```

#### `gloss_style`: `sentence`(기본값) vs `paren` — easy-doc A/B 56건 실측

초판은 `gloss` 항목을 `과태료 → 과태료(정해진 날짜보다 늦어서 더 내는 돈)`처럼
괄호 병기 head로 렌더링했다(`gloss_style="paren"`). 이 컨텍스트를 실제
easy-doc 변환 프롬프트에 주입해 A/B 측정한 결과, 사실 보존은 개선됐지만
**스타일 통과율이 83.9% → 51.8%로 무너지고 보정 패스 56/56이 발동했다.**
원인은 head 자체가 `원문(설명)` 괄호 템플릿을 few-shot처럼 LLM에게
보여줬는데, easy-doc의 별도 스타일 규칙("괄호는 풀어 쓰라")과 정면으로
충돌했기 때문이다 — LLM이 프롬프트가 보여준 형식을 그대로 모방했다.

그래서 `gloss_style="sentence"`(신규 기본값)를 추가했다. 괄호 템플릿
자체를 노출하지 않고 "원어는 남기고 바로 다음 문장에서 풀어 쓰라"는
지시로 바꿔 이 충돌을 없앤다. `paren`은 괄호 병기를 실제로 원하는
호출부를 위해 그대로 남아 있다(기존 동작 100% 보존). "이유:"/"주의:" 줄
로직(상세도 tier 처리)은 두 스타일이 완전히 동일하다 — 바뀌는 것은 gloss
섹션 제목과 head 한 줄뿐이다.

| `gloss_style` | 섹션 제목 | head |
|---|---|---|
| `"sentence"`(기본값) | 원래 말은 남기고, 바로 다음 문장에서 쉽게 풀어 설명하세요 (원래 말을 지우거나 괄호로 붙이지 마세요) | `{term} — 뜻: {easy_term}` |
| `"paren"` | 원래 말을 남기고 괄호로 설명하세요 (지우면 안 됩니다) | `{term} → {term}({easy_term})` |

### 7.2.1 예산 초과 시: 상세도가 아니라 항목 수를 줄인다

`max_chars`를 넘으면 ① 예문을 먼저 줄이고 ② 그래도 넘치면 `risk` 낮은 항목부터 **통째로 제거**한다. **각 항목의 상세도는 절대 낮추지 않는다.**

상세도를 낮추면 고위험 항목의 `caution`이 가장 먼저 사라진다. 예산이 빠듯할 때 정확히 이 기능이 막으려던 사고(§2.1)가 재발한다는 뜻이다. 불변식은 이렇다.

> **프롬프트에 표시된 항목은 언제나 자기 위험도에 맞는 완전한 설명을 갖는다.**

항목이 잘리면 마지막 줄에 반드시 명시한다(`용어 9개 중 4개만 표시`). 조용히 자르면 LLM이 사전을 완전한 것으로 오인한다.

> 물리적 하한이 있다. 헤더 + 3개 섹션 제목 + 잘림 안내만으로 약 163자가 나가므로, 그보다 작은 `max_chars`는 항목을 0개로 줄여도 충족할 수 없다.

#### `max_chars_ratio`: 원문 길이에 비례한 상한 (실측: easy-doc A/B 56건)

A/B 측정에서 문서 38/56이 **컨텍스트가 원문보다 긴 상황**이었다(최대
4.61배). 짧은 문서일수록 이 역전이 심해지는데, 고정된 `max_chars` 하나로는
문서 길이별로 이 비율을 맞출 수 없다. `max_chars_ratio: float | None = None`을
지정하면 `int(len(text) * max_chars_ratio)`도 문자 상한 후보로 계산해
`max_chars`와 함께 지정됐으면 **둘 중 작은 값**을 실제 상한으로 쓴다.
이후 처리는 위 `max_chars` 파이프라인을 그대로 재사용한다(예문 감축 →
항목 제거 → 물리적 하한 시 최선 반환). 기본값 `None`은 기존 호출에
영향을 주지 않는다.

#### `min_substitute`: substitute 최소 보장 쿼터 (실측: easy-doc A/B 56건)

`max_terms`/`max_chars` 잘림 모두 `risk` → `priority` 내림차순으로 낮은
쪽부터 제거하는데, `substitute`는 정의상 "지워도 안전"으로 검수된
항목이라 대부분 `risk='none'`이다 — 그래서 예산이 빠듯하면 **항상
`substitute`가 가장 먼저, 통째로 잘려나간다.** 실측(문서 051)에서 매칭된
`substitute` 4건이 전부 잘려 "바꿔 쓰세요" 구역이 빈 채로 나간 사고가
확인됐다.

`min_substitute: int = 5`는 문서에서 매칭된 `substitute` 중 `priority` 상위
`min(min_substitute, 개수)`건을 "예약석"으로 지정해, `max_terms` 잘림과
`max_chars` 항목 제거 **둘 다**에서 예약석이 아닌 항목이 모두 제거된
뒤에야 예약석을 건드리도록 보호한다. `max_terms` 상한 자체는 여전히
지킨다 — 예약석을 먼저 채우고 남는 슬롯을 기존 risk → priority 순으로
채우는 방식이라, 예약석 수가 `max_terms`보다 많으면 예약석 안에서도
priority가 높은 것부터 남는다. `0`을 주면 기존 동작(예약 없음).

### 7.2.2 예문은 few-shot이므로 전략을 지켜야 한다

`examples`의 before/after 쌍은 LLM에게 **지시문보다 강한 신호**다. 따라서 예문 자체가 전략을 위반하면 안 된다.

초판은 `keep` 엔트리에도 치환된 예문을 합성했다.
```
전: 「국민기초생활 보장법」에 따라 지원받을 수 있습니다.
후: 법 이름이니 그대로 씀에 따라 지원받을 수 있습니다.   ← 바꾸지 말라면서 바꾸는 시범
```
프롬프트가 "절대 바꾸지 마세요"라고 지시하는 바로 아래에서 그것을 바꾸는 예를 보여주는 셈이다. **LLM은 예문을 따라간다.**

| 전략 | `after_text` |
|---|---|
| `substitute` | `easy_term`으로 치환 |
| `gloss` | `원어(easy_term)` — 원어 보존 |
| `keep` | 예문을 만들지 않는다 |

`gloss` 예문의 형식적 안전 조건은 §4.4와 같다: **`term ⊆ after_text`**.

**`gloss_style="sentence"`에서는 gloss 예문을 아예 예문 풀에서 뺀다.** 위 표의
`gloss` after_text(`원어(easy_term)` 괄호 병기)가 sentence 스타일의 "괄호로
붙이지 마세요" 지시와 정반대인 few-shot이 되기 때문이다 — 지시문보다 강한
예문이 지시문과 모순되면 실측(§7.2)처럼 예문이 이긴다. `substitute` 예문은
형식이 문제되지 않으므로(위 표) sentence 스타일에서도 그대로 유지된다.
`paren` 스타일은 예문과 형식이 일치하므로 영향 없다.

### 7.3 `required_facts`와의 관계
easy-doc의 골든셋은 `required_facts.canonical`이 변환 결과에 남아 있는지 검사한다. `keep`/`gloss` 전략은 원어를 보존하므로 이 검사를 통과시킨다. **사전이 사실보존 검증의 사전 방어선 역할을 한다.**

## 8. 검증

| 항목 | 방법 |
|---|---|
| 스키마 | `sqlite3 :memory: < schema/schema.sql` 무오류, FTS5 트리거 동작 |
| 파이프라인 | 샘플 CSV 3종(UTF-8/CP949/헤더변형) → 엔트리 수·태그·전략 기대값 일치 |
| 변형형 | `명기하다` → `명기하여/명기한/명기해야` 포함 |
| 매칭 경계 | `내방`이 `내방객`에 매칭되지 않음. `지참하여`가 `지참` 엔트리에 매칭됨 |
| 최장일치 | `차상위계층`이 있을 때 `차상위`로 쪼개지지 않음 |
| 안전장치 | `과태료`가 `substitute`로 분류되지 않음 (회귀 방지 핵심 테스트) |
| 라운드트립 | SQLite → JSON → `EasyDict.from_index_json` 로드 후 매칭 동일 |
| **굴절형 치환** | `명기하여 주십시오` → 어미 보존(`명기하여(쓰다)`). `쓰다 주십시오` 같은 어미 소실이 없을 것 (§6.6) |
| **`keep` 경로** | 「법령명」·금액·기한이 `keep`+`risk=high`+`status=review`. `annotate`가 한 글자도 바꾸지 않을 것. `### 절대 바꾸지 마세요` 섹션이 실제로 채워질 것 |
| **명사 하다-파생** | `지참하시기`/`내방하시면`이 `지참`/`내방` 엔트리에 매칭됨. `구비서류하여`는 생성되지 않을 것 |

> §8 반성: 위 굵은 3항목은 초판 검증표에 없었고, 그 때문에 테스트 53개가 전부 통과한 상태에서 §6.6의 비문 결함이 살아남았다.
> **계약에서 파생된 테스트는 계약의 구멍을 그대로 물려받는다.** 실제 문장을 손으로 넣어보는 탐색적 검증을 자동화 테스트가 대체하지 못한다.

### 8.1 검사로도 못 잡는 것

층위 1(구조 불변식, `tools/check_invariants.py`)·층위 2(코퍼스 통과, `tools/audit_corpus.py`)·층위 3(의미 검증 초안, `tools/detect_homonym_risk.py`)을 다 갖춰도 남는 구멍이다. "검사를 통과했다"가 "이 항목이 맞다"를 뜻하지 않는 지점을 명시한다 — 위 §8 반성의 연장이다.

| 구멍 | 근거 |
|---|---|
| 전문 행정용어의 의미 오류 | `substitute`의 62%(573건)가 krdict에 표제어 자체가 없어 일반 사전 대조가 불가능하다 |
| 대치어가 원어보다 어려운 경우 | `개수 → 수리`, `크레인 → 기중기`. 고유어인지 한자어의 한글 표기인지 문자열만으로 구분할 수 없다 — 외부 어원 DB가 있어야 풀린다 |
| 동형어가 아닌 미묘한 의미 차이 | `거치(据置) → 예치`. 뜻이 하나뿐이라 §5.5.1의 동형어 검사에 안 걸리는데, `거치 기간`(상환 유예)과 `예치 기간`(맡겨 둠)은 다른 말이다 |
| 골든 코퍼스 57건의 대표성 | 층위 2(`tools/audit_corpus.py`)는 이 57건에만 답한다. 여기 안 나오는 표현은 검사되지 않는다 |
| 형태소 경계 | `제13조제3항`의 `조제`. 일반 규칙을 만들면 `복지`·`급여`·`수급` 199건을 잃는다. 형태소 분석기 없이는 못 푼다 |

### 8.2 검사가 실패하는 네 가지 방식

위 8.1이 "검사가 아직 안 닿는 영역"이라면, 이건 **검사 코드 자체가 결함을 놓치는 경우**다. 넷 다 "테스트는 초록인데 결함이 산다"는 같은 결과를 낸다.

| # | 방식 | 실측 사례 |
|---|---|---|
| 1 | 비교에서 순서를 지운다 | 후보를 `frozenset`으로 비교하면 후보 **집합**은 같아도 그중 어느 것이 **승자**인지는 못 본다 — §6.8의 핵심은 집합이 아니라 순서다 |
| 2 | 겨냥이 파일 간에만 있다 | `--input` **파일** 순서만 바꿔 비교하는 검사는 **파일 내부** 행 순서 문제를 원리상 못 본다 |
| 3 | 대조 항목에서 빠진다 | fwd/rev 비교가 `(term_norm, easy_term, strategy, risk, status, readability)`만 보고 `source_id`를 목록에 안 넣어, 예문 원천의 귀속 탈취 318건(§5.5(7))을 놓쳤다 |
| 4 | 검사가 검사 대상을 재호출한다 | `find_all()`은 이미 경계 판정을 통과시킨 매칭만 돌려주는데, 검사가 같은 경계 함수를 다시 불러 재검사하면 **절대 실패할 수 없다** — `tools/audit_corpus.py`의 `check_boundaries`가 초안에서 이 사고를 실제로 냈다가 도입 검증 중 잡고 되돌렸다 |

1·2·3은 이번 세션에 실제로 결함을 놓쳤다(대응: `tests/test_reproducibility.py`가 후보 집합이 아니라 승자와 `source_code`를 비교하고, 파일 내부 행 순서까지 별도로 검사한다). 4는 층위 2 검사를 만드는 과정에서 저질렀다가, 도입 시점에 스스로 잡았다.

> **모든 검사는 도입할 때 일부러 깨서 실패하는지 확인한다. 확인되지 않은 검사는 장식이다.**
