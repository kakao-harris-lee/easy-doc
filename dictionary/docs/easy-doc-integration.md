# easy-doc 연동 — RAG 프롬프트 만들기

> 이 사전은 **치환 엔진이 아니라 LLM에 주는 지식**이다. easy-doc이 문서를 변환할 때, 그 문서에 실제로 나온 어려운 말에 대한 지침만 골라 프롬프트에 얹는 용도다.

---

## 1. 무엇을 읽나

```
dist/easy_dict.index.json      <- 이것만 읽으면 된다
```

나머지 산출물은 용도가 다르다. `easy_dict.sqlite3`는 정본(검수·감사용), `easy_dict.json`은 전체 덤프(벡터화·재배포용), `easy_dict.simple.jsonl`은 기획서 호환 형태다. **런타임 조회는 `index.json` 하나로 끝난다.**

현재 크기 약 1.5MB. 프로세스 시작 시 한 번 메모리에 올려 두고 재사용한다.

## 2. 어떻게 부르나

```python
from easydict.lookup import EasyDict

ed = EasyDict.from_index_json("dist/easy_dict.index.json")   # 시작 시 1회
context = ed.build_prompt_context(document_text)             # 문서마다 1회
```

`build_prompt_context()`가 하는 일은 이렇다.

1. 문서 텍스트에서 사전에 있는 표제어를 찾는다(경계·최장일치·활용형 처리 포함)
2. 찾은 것만 골라 전략별로 묶어 지침 문단을 만든다
3. 예산을 넘으면 위험도가 낮은 항목부터 통째로 뺀다

**문서에 안 나온 말은 안 실린다.** 사전이 2,186건이어도 프롬프트에 들어가는 건 그 문서에 실제로 나온 것뿐이다(위 예시 문서에서는 13건, 1,706자).

### Kotlin에서 쓸 때

`index.json` 형식은 언어 중립이지만 **조회 로직은 포팅이 필요하다.** `DESIGN.md §6.7`에 반드시 이식해야 할 규칙이 정리돼 있다 — 조사 경계, 로마자·숫자 경계, 표면형 소유권. 이 셋을 빼먹으면 `CCTV` 안에서 `CT`가 걸리는 식의 오매칭이 난다.

## 3. 출력 구조

세 구역과 예문으로 나온다. **구역 이름 자체가 LLM에 주는 지시다.**

```
### 바꿔 쓰세요                                                strategy=substitute
    원문을 대치어로 교체해도 안전하다고 검수된 것

### 원래 말은 남기고, 바로 다음 문장에서 쉽게 풀어 설명하세요      strategy=gloss
    원문을 지우면 정보가 줄거나 위험한 것. 대부분이 여기 온다

### 절대 바꾸지 마세요                                          strategy=keep
    법령명·금액·기한처럼 한 글자도 바뀌면 안 되는 것

### 참고 예문                                                  few-shot
    실제 복지 문서에서 뽑은 전/후 문장 쌍
```

각 항목에는 `이유`(그 말이 무슨 뜻인지)와 `주의`(LLM이 어떻게 틀리는지)가 붙는다. **`주의`가 이 사전의 핵심이다.**

```
- 급여 — 뜻: 나라에서 주는 돈이나 도움
  이유: 복지 제도에서 '급여'는 나라가 형편에 따라 주는 돈이나 서비스입니다.
  주의: 일하고 받는 월급이 아닙니다. 일반 국어사전은 '일한 대가로 받는 돈'으로
       풀지만, 복지 문서의 '급여'는 정반대로 나라가 지급하는 쪽입니다.
```

### `gloss` 형식이 위와 다르게 나온다면 (`gloss_style`)

위 예시는 기본값 `gloss_style="sentence"` 출력이다. easy-doc 변환 프롬프트에
A/B로 주입해 실측한 결과 이 기본값을 쓰는 게 맞다 — 원래 있던
`gloss_style="paren"`(`급여 → 급여(나라에서 주는 돈이나 도움)`처럼 괄호
병기 head)은 easy-doc의 "괄호는 풀어 쓰라"는 스타일 규칙과 충돌해 스타일
통과율이 83.9% → 51.8%로 무너지고 보정 패스가 56/56 발동했다. `paren`을
그대로 써야 하는 사정이 있는 게 아니라면 기본값(`sentence`)을 그대로 두는
것을 권한다. 두 형식 모두 `이유`/`주의` 줄은 동일하고, `gloss_style`에
따라 바뀌는 것은 섹션 제목과 head 한 줄뿐이다(`DESIGN.md §7.2`).

## 4. 프롬프트에 어디에 넣나

**문서 바로 앞, 같은 메시지에** 넣는다. 문서마다 내용이 달라지므로 시스템 프롬프트에 고정하면 안 된다.

```
[시스템]
당신은 공공·복지 문서를 지적·발달장애인이 읽을 수 있는 쉬운 글로 바꾸는 일을 합니다.

원칙:
- 짧은 문장으로 씁니다. 한 문장에 한 가지만 말합니다.
- 어려운 말은 쉬운 말로 바꾸되, 아래 「어려운 말 지침」이 있으면 그것을 먼저 따릅니다.
- 금액·날짜·기한·법령 이름·기관 이름은 절대 바꾸지 않습니다.
- 원문에 없는 내용을 지어내지 않습니다. 확실하지 않으면 원문 표현을 남깁니다.

[사용자]
{build_prompt_context(document_text) 출력을 그대로 여기에}

## 바꿀 문서
{document_text}
```

지침을 문서보다 **앞에** 두는 이유는, 뒤에 두면 모델이 문서를 먼저 읽고 나름의 판단을 굳힌 뒤에 지침을 보기 때문이다.

## 5. 예산 관리

권장 호출:

```python
ed.build_prompt_context(text, max_terms=40, max_chars=4000, max_chars_ratio=1.0)
```

예산을 넘으면 **항목을 통째로 빼지, 설명을 줄이지 않는다.** 잘린 설명은 오해를 만들기 때문이다. 빼는 순서는 위험도가 낮은 쪽부터다 — `risk=high`인 항목이 마지막까지 남는다.

문서가 길면 `max_chars`를 올리기보다 **문서를 나눠 변환하는 쪽**을 권한다. 지침이 길어지면 모델이 문서보다 지침에 끌린다.

### `max_chars_ratio` — 짧은 문서에서 컨텍스트가 원문보다 길어지는 문제

A/B 실측(56건)에서 문서 38/56이 **컨텍스트가 원문보다 긴 상황**이었다(최대
4.61배). 고정된 `max_chars` 하나로는 문서마다 다른 이 비율을 못 잡으므로,
원문 길이에 비례한 상한도 함께 준다. `max_chars_ratio=1.0`은 "컨텍스트가
원문보다 길어지지 않게"라는 뜻이고, `max_chars`도 함께 지정했으면 **둘 중
작은 값**이 실제 상한이 된다. 기본값은 `None`(비활성)이라 기존 호출은
영향받지 않는다.

### `min_substitute` — `substitute` 항목이 잘림에서 먼저 사라지는 것 방지

`substitute`는 "지워도 안전"하다고 검수된 것이라 대부분 `risk='none'`이다.
그런데 잘림 순서가 `risk` → `priority`라서, 예산이 빠듯하면 `substitute`가
**항상 가장 먼저, 통째로** 잘려나간다(실측: 문서 051에서 매칭된 4건
전부). `min_substitute`(기본 `5`)는 문서에서 매칭된 `substitute` 중
`priority` 상위 그만큼을 "예약석"으로 지정해 다른 항목이 다 빠진 뒤에야
제거되게 한다. `0`을 주면 이 보호를 끈다.

## 6. 지금 상태와 한계

```
엔트리 2,186건 (검수 큐 480 · 비활용 4)
그중 복지 핵심어 직접 집필분 113건
예문 340건
```

**대부분이 `status=review`다.** 사람이 최종 확인하지 않았다는 뜻이지, 틀렸다는 뜻은 아니다. 다만 이 상태의 항목은 `substitute`를 받지 못한다(§4.4) — 그래서 위 출력에서 `### 바꿔 쓰세요` 구역이 비어 있는 문서가 많다.

알려진 한계는 `DESIGN.md §8.1`에 있다. 특히:

- **합성어는 잡히지 않는다.** `중증질환자`에서 `중증`이 걸리지 않는다. 경계를 풀면 `대상자`에서 `자`가 걸리는 결함이 되살아나므로 일부러 막아 둔 것이고, 필요한 합성어는 개별 표제어로 넣어야 한다.
- **검사 범위가 골든 57건이다.** 그 밖의 문서에서 무슨 일이 나는지는 아직 모른다.

## 7. 이 연동으로 확인하고 싶은 것

지금 사전은 "LLM이 이걸 틀릴 것이다"라는 **추정**으로 쓰였다. 실제로 돌려 보면 세 가지를 알 수 있다.

1. **어떤 지침이 실제로 변환을 바꾸는가** — 없어도 LLM이 알아서 하는 항목은 빼야 한다
2. **어떤 지침이 무시되는가** — 표현이 약하거나 위치가 나쁜 것
3. **지침이 없어서 틀리는 곳이 어디인가** — 다음에 쓸 항목

`중증`을 장애 분류로 단정해 넣었다가 코퍼스 실제 용법이 `중증질환`(의료)이라 되돌린 일이 있었다. **추정으로 쓴 것은 돌려 봐야 안다.**

## 8. 중복 표제어 — easy-doc 자체 치환 목록과의 관계

easy-doc은 내장 치환 목록 `DIFFICULT_WORD_REPLACEMENTS`를 이 사전과 별도로 갖고 있다. 두 곳이 같은 낱말을 다루면서 서로 다른(때로는 정반대인) 지시를 내리는 문제와 그 처분 정책은 `docs/consumer-overlap-policy.md`에 정리했다. 통합 릴리스 체크리스트에 반영할 것: **① `DifficultWords.kt`에서 흡수 완료 낱말 제거는 사전 컨텍스트 주입이 켜지는 릴리스와 같은 변경으로 나간다**(먼저 지우면 그 낱말이 무지침 상태가 된다), **② `tools/detect_consumer_overlap.py`를 CI 게이트로 추가한다**(CONFLICT/DIVERGENT 존재 시 종료 코드 1) — 두 항목을 빠뜨리면 이 문서 §7에서 확인하려는 스타일 격차 회수 여부를 검증할 수 없다.
