# python-kotlin-parity

## 전제가 바뀌었다

이 하네스는 "Kotlin이 Python과 **같은 값**을 내는가"를 증명하는 도구였다. 그 전제는 폐기됐다.

> "파이썬이 회귀 문제가 많아서 코틀린으로 이전하고 있는 것이 핵심이야. 파이썬이 완벽한 코드가 아니야. 출력의 결과를 파이썬과 동일하게 맞출 필요는 없어. 프로젝트의 요구사항을 반영/구현하고, 이후에 개선해 나가면 돼." (사용자, 2026-08-12)

근거는 코드 이력에 있다. `app/easyread/style_rules.py`의 최근 커밋은 `fix: 치환 비문 검출 오탐 제거`, `fix: 마스킹 보안 구멍 수정(외국인등록번호·무구분자 표기)`, `fix: 골든셋 팩트 허용 변형 보정`이다 — 정규식·휴리스틱을 고칠 때마다 오탐과 누락이 번갈아 생겼다. 그 동작을 값으로 굳혀 옮기면 **회귀를 옮기는 것**이고, 하네스가 그것을 "증명"이라 부르게 된다.

그래서 판정 근거를 바꾼다. 정본은 `docs/master-plan.md`다(프로젝트 CLAUDE.md가 그렇게 정한다). 관련 절: §3.2 데이터 처리 정책, §3.3 품질 신뢰 체계, §4.0 Lean MVP, §6.2 회귀 방지 4원칙.

| | 옛 전제 | 지금 |
|---|---|---|
| `expected`의 정체 | Python이 낸 값 | 요구사항이 요구하는 **성질** |
| 마스킹 판정 | 자리표시자 번호가 Python과 같은가 | 주민등록번호·카드번호가 **빠짐없이 가려졌는가**, 나머지 본문이 **남아 있는가** |
| 스타일 판정 | 위반 목록이 Python과 같은가 | 50자·쉼표 2개 규칙을 넘는 문장이 **빠짐없이 잡히고** 넘지 않는 문장이 **잡히지 않는가** |
| Python 출력 | 정답 | **참고값** — 갈리는 자리는 정보이지 결함이 아니다 |
| Python이 틀렸을 때 | 그대로 옮긴다 | 성질을 기준으로 판정하고 갈림을 기록한다 |

**Python 출력을 버리지는 않는다.** 값이 갈린다는 것은 둘 중 하나가 틀렸다는 신호라 정보 가치가 크다. 그래서 판정에서 빼되 `reference`로 함께 싣고, 갈린 자리를 **참고 갈림 원장**에 기록한다.

## 판정 방식은 하나다 — `mode: "spec"`

fixture 헤더의 `mode`가 그것을 선언하고, **정본 생성기가 정한다**(파일에서 고쳐 적으면 정본 대조가 잡는다).

도메인 8개 — `masking`, `text`, `style`, `style-tables`, `prompts`, `postprocess`, `repair-adoption`, `export`.

케이스마다 `assert` 목록이 있고, 비교기가 그 검사를 **Kotlin 산출물에 실행**한다. Python 구현을 부르지 않는다 — 부르는 순간 기준이 다시 Python 동작이 된다.

### 없어진 것 — `compat` 모드와 `crypto`·`jwt`·`argon2` (2026-08-12)

여기에는 "값이 같은 것이 곧 요구사항"인 두 번째 모드가 있었고 그 아래 세 도메인이 있었다. **지웠다.** 다시 넣기 전에 이 절을 읽어라.

**왜 없어졌나.** 세 도메인의 근거는 하나뿐이었다 — "절체 후 롤백 창에서 Python이 Kotlin이 만든 암호문·토큰·해시를 읽어야 한다." 사용자 결정(2026-08-12)으로 Python 런타임을 폐기하고 **롤백을 포기**하면서 읽을 쪽이 사라졌다. 저장 암호화는 표준 AEAD를 처음부터 쓴다. 근거 문서: 계획 `docs/plans/2026-08-11-kotlin-react-migration.md`의 2026-08-12 2차 변경 이력과 §4.3, `docs/migration/_workspace/00_progress.md`의 재개발 전환 절.

**왜 도메인만 빼지 않고 모드까지 지웠나.** `compat`의 기대값은 **다른 런타임이 낸 값**에서 권위를 얻는 방식이다. 그 다른 런타임이 폐기됐으므로 어떤 도메인도 compat에 권위를 공급할 수 없다. 반면 "요구사항이 못박은 값과 정확히 같아야 한다"는 이미 spec 모드의 `equals_field`가 표현한다 — 잃은 표현력이 없다. 남겨 두면 `mode: compat` 한 줄로 `assert` 의무와 방향 가드를 건너뛰는 우회로만 남는데, 이 스킬이 "값 비교로 때우는 경로는 두지 않았다"고 적은 바로 그 문이다. 쓰는 곳 없는 문은 닫는다. 되살릴 일이 생기면 그때 필요한 것은 옛 코드가 아니라 **새 권위의 출처**이고, 그것을 정하는 일이 재도입 비용의 대부분이다.

**암호 검증이 없어진 것이 아니다.** 없어진 것은 "Python과 같은 바이트"뿐이다. 아래는 **여전히 요구사항**이며, 받는 곳이 옮겨졌다.

| 요구 | 어디로 갔나 |
|---|---|
| AEAD 암호화→복호화 round-trip, 변조(tamper) 거부, 다른 키 거부, 복호화 oracle 금지(단일 예외) | Kotlin 자체 테스트 + `migration-safety-gate` **I-7** |
| Argon2id 해시·검증, 낮은 파라미터 해시 검증, 로그인 **성공 시에만** 재해시, 재해시 판정의 **전체 파라미터 동등성**(Phase 0 필수조치 A) | Kotlin 자체 테스트 + `migration-safety-gate` **I-8** |
| JWT HS256 `sub`/`exp`/`typ`, 서명 위조·알고리즘 혼동 거부, **clock skew 0** 경계(필수조치 B), 시크릿 32바이트 하한 | Kotlin 자체 테스트 + `migration-safety-gate` **I-9** |
| `encryption_scheme`·`key_version` — 이제 **키 회전용**이다(롤백 호환용 아님) | `migration-safety-gate` **I-7** |

**왜 spec 모드로 옮기지 않았나.** 이 하네스로는 암호를 판정할 수 없기 때문이다. spec 판정은 비교기가 산출물을 **열어 보고** 성질을 재는 방식인데(마스킹의 `masked_text`처럼), 암호문은 불투명해서 비교기가 열 수 없고 `{"tamper_rejected": true}` 같은 필드는 Kotlin 하네스의 **자기 신고**이지 증거가 아니다. 성질처럼 생긴 fixture를 만들어 두면 "검증한 것처럼 보이는데 아무것도 재지 않는" 상태가 되는데, 그것이 이 하네스가 X-05·X-09·X-12에서 반복해 고친 실패 유형이다.

정말로 독립 검증이 필요하면 방법은 하나다 — Phase 4에서 AEAD 방식을 고정한 뒤 **표준 AEAD를 독립 구현으로 복호화하는** 검증기를 새로 짜는 것. 표준 알고리즘이라 두 번째 구현이 존재한다는 점이 옛 Fernet 상황과 다르다. 지금 짓지 않는 이유는 AEAD 선택이 아직 안 됐기 때문이고, 짓기로 하면 그때 이 문단이 설계 근거의 출발점이다.

### `spec_status: "pending"` — 아직 성질을 적지 못했다

성질을 적지 못한 spec 도메인은 `pending`으로 선언한다. 그 도메인의 케이스는 **미검증**으로 집계되고 종료 코드 2가 나온다. 값 비교로 때우는 경로는 두지 않았다 — 그것이 폐기된 전제로 되돌아가는 유일한 문이다.

현재 상태(2026-08-14): `masking`·`text`·`repair-adoption`·`style`·`style-tables`·`prompts`·`postprocess` 가 ready, `export` 하나가 pending(Kotlin 구현 없음). pending 도메인의 fixture에도 `requirement` 한 줄이 들어 있고, 그 문장이 곧 성질을 적을 때의 명세다.

## 성질을 fixture로 어떻게 적는가

```json
{
  "domain": "masking",
  "mode": "spec",
  "requirement": "master-plan §3.2 마스킹 선행 + 사용자 결정(2026-08-12) 범위 축소 — …",
  "source": "app/privacy/masking.py::mask_text",
  "generator": "dump_parity_fixtures.py",
  "normalization": ["nfc", "lf"],
  "spec_status": "ready",
  "cases": [
    {
      "id": "masking-rrn-hyphen",
      "description": "하이픈 표기 주민등록번호를 가려야 한다 — 남으면 개인정보가 그대로 외부 LLM으로 나간다",
      "input": { "text": "주민등록번호 900101-1234567 를 확인합니다." },
      "assert": [
        { "check": "restores_input" },
        { "check": "placeholder_scheme", "args": { "categories": ["주민등록번호", "카드번호"] } },
        { "check": "absent", "args": { "path": "masked_text", "needles": ["900101-1234567"] } },
        { "check": "present", "args": { "path": "masked_text", "needles": ["주민등록번호", "를 확인합니다."] } }
      ],
      "reference": { "masked_text": "주민등록번호 [[주민등록번호1]] 를 확인합니다.", "items": [...] }
    }
  ]
}
```

| 필드 | 역할 |
|---|---|
| `requirement` | 이 도메인이 무엇을 지켜야 하는지를 **문서 근거와 함께** 적는다. 여기에 근거를 못 적으면 그 도메인은 아직 성질로 판정할 준비가 안 된 것이다 |
| `assert` | 판정의 전부. 비어 있으면 그 케이스는 아무것도 검증하지 않으므로 구조 결함으로 막힌다 |
| `reference` | Python 실행 결과. **판정에 쓰지 않는다.** 갈리는 자리는 원장에 기록된다 |
| `reference_divergence: "expected"` | 요구사항이 바뀌어 **갈리는 것이 정상**인 케이스. **면제가 아니라 검사 추가다** — 원장 기록 요구는 그대로이고, 갈림이 **사라지면** 선언이 낡은 것이므로 막는다. 예전에는 이 한 단어가 원장 기록과 대조를 통째로 건너뛰어 갈림의 내용이 바뀌어도 아무도 몰랐다(X-10/S-2, 재현으로 확인) |
| `verdict_pending` | 어느 방향도 단언하지 않는 자리. **객체이고 `reason`·`owner`·`deadline`·`referred_by` 가 필수다** — 하나라도 비면 종료 코드 1. 옛 `known_gap`(자유 문자열)은 **어느 게이트도 읽지 않아** 미룸이 영구가 됐다(R-4). 이 마커가 뜻하는 것은 "아무도 안 봤다"가 아니라 **열린 결정의 소유권**이다. 보류 케이스는 `성질 판정 N건` 에서 **분리돼** 별도 구획에 소유자·기한과 함께 찍힌다. 케이스 하한의 ` !deferred` 꼬리표가 마커 제거까지 막는다 |

**fixture는 손으로 고치지 않는다.** 비교기가 매번 생성기를 다시 돌려 헤더 전량·케이스 id·순서·`assert`·`reference`까지 대조한다. 단언 하나를 지워 게이트를 무르게 만드는 경로가 여기서 막힌다(실측: `$.assert: 길이 4 != 3`, 종료 코드 1).

**입력은 전부 합성(synthetic)이다.** fixture는 커밋되어 영구히 남는다. 실제 사용자 문서·실제 개인정보·실제 운영 키를 넣지 않는다.

## 검사 목록 (`CHECKS`)

정본은 `compare_parity.py`의 `CHECKS` 딕셔너리다. 전부 **산출물과 fixture 입력만** 보고 판정한다.

| 검사 | 방향 | 무엇을 보는가 |
|---|---|---|
| `absent` | under | 가려야 할 문자열이 지정 경로에 남지 않았다 |
| `present` | over | 남겨야 할 문자열이 지워지지 않았다 |
| `restores_input` | 구조 | 자리표시자를 원문으로 되돌리면 입력과 **정확히** 같아진다 |
| `placeholder_scheme` | 구조 | `[[{범주}{번호}]]` 형식, 범주 집합, 범주별 1부터 등장 순서, `items` 짝 맞음 |
| `equals_field` | 양방향 | 지정 경로가 요구사항이 못박은 값과 같다 |
| `at_most` | over | 지정 경로의 수가 상한을 넘지 않는다 (변환 호출 2회 계약) |
| `contains_all` | under | 요구 항목을 전부 포함한다 — **추가는 허용하고 누락만 막는다** |
| `equals_derived` | 양방향 | 입력에서 **규칙으로 유도한 값**과 같다 (`control_strip`, `repair_policy`) |

`equals_derived`가 이 설계의 핵심이다. 요구사항이 규칙으로 완전히 적히는 자리(XML 비허용 제어문자 제거, 보정 채택 정책)에서는 비교기가 **자기 힘으로 기대값을 계산**한다. Python 구현이 틀려도 기대값이 따라 틀리지 않는다.

`contains_all`이 "개선을 막지 않는다"의 표현형이다. 치환 사전 246개를 값으로 비교하면 Kotlin이 항목을 추가하는 순간 빨개진다. 포함 관계로 보면 **누락은 막고 추가는 허용**된다.

### 같은 입력을 두 번 재지 않는다 (M-08)

케이스 둘의 `input`이 같으면 산출물도 같으므로 **같은 것을 두 번 잰다.** 성질은 늘지 않는데 케이스 수는 늘고, 그 수가 리포트에서 커버리지의 대리 지표로 쓰인다(`성질 판정 83건`). 즉 **커버리지가 늘어난 것처럼 보이게 만드는 가장 값싼 방법**이 중복 붙여넣기다. 도메인 안에서 입력이 겹치면 구조 결함으로 종료 코드 1이다.

손편집으로 들어오는 중복은 정본 대조가 이미 막는다. 이 검사가 받는 것은 **생성기에 중복이 들어오는 경로**다 — 그때 fixture는 자기 정본과 일치하므로 정본 대조는 조용하다.

### 방향 가드를 스크립트가 강제한다

성질 검증의 고전적 실패는 한쪽으로만 재는 것이다. "가려졌는가"만 재면 **본문을 통째로 가린 구현이 만점**을 받고, "남았는가"만 재면 아무것도 안 하는 구현이 만점을 받는다.

그래서 spec 도메인은 `under`와 `over` 검사를 **둘 다** 갖춰야 하고, 한쪽뿐이면 구조 결함으로 종료 코드 1이다. 케이스 단위로도 자동으로 짝을 맞춘다 — `absent`가 붙은 케이스에는 생성기가 **남은 본문 조각에 대한 `present`를 자동으로 덧붙인다**(실측 근거: 전문 마스킹 스탠드인이 자동 가드 도입 전에는 RRN 케이스들을 통과했고, 도입 후 23건 중 22건에서 걸렸다).

## 참고 갈림 원장 — Python 출력을 두는 자리

경로: `parity/reference-ledger/{도메인}.json`. **저장소에 커밋되어 리뷰에 올라가는 것이 존재 이유다.**

원장에는 본문을 넣지 않는다 — 케이스 id, `agree`/`diverge`, 첫 차이 경로, 양쪽 값의 SHA-256만 남긴다.

판정 규칙:

- 갈렸는데 원장에 없다 → **종료 코드 1**. 닫는 방법은 구현을 되돌리는 것이 아니라 `--record-reference`로 원장을 갱신해 커밋하는 것이다.
- 원장은 `diverge`인데 관측이 `agree`(또는 그 반대) → **원장이 낡았다**. 같은 명령으로 갱신한다.
- 갈림의 **내용**이 바뀌었다(해시 불일치) → 같은 취급.
- fixture가 `reference_divergence: "expected"`로 **선언했더라도 위 세 규칙은 그대로 적용된다.** 선언은 면제가 아니라 "갈림이 사라지면 막는다"는 검사를 하나 더하는 것이다. 선언이 붙거나 빠지면 원장 항목의 `declared` 값이 바뀌므로 그 변경도 diff로 리뷰에 올라간다.
- 원장에는 있는데 이번 관측 범위에 **없는 항목**(케이스가 지워졌거나 `reference`가 사라짐) → **낡은 원장 항목**으로 보고한다. 남겨 두면 "검토된 갈림"처럼 보이면서 아무것도 가리키지 않는다. 범위를 좁힌 실행(`--only`)이나 결과 파일이 없어 대조하지 못한 도메인에서는 보지 않는다.
- 케이스의 성질이 **불충족**이면 원장을 건드리지 않는다. 이미 설명된 차이이고, 고장난 산출물을 원장에 굳히면 그것이 다음 기준이 된다.

왜 막지 않고 기록만 하는가: 차이를 차단 사유로 쓰면 "Python이 정답"으로 되돌아간다. 왜 그냥 통과시키지 않는가: 조용한 갈림은 6개월 뒤 아무도 설명하지 못한다. 그래서 **막지 않되 조용할 수는 없게** 한다 — `.github/parity-canonical-floor.txt`가 게이트 축소에 쓰는 것과 같은 방식이다.

### `--record-reference`는 판정이 아니다 (종료 코드 4)

원장을 **바꾼** 기록 실행은 종료 코드 4로 끝나고 그 실행으로는 어떤 게이트도 닫지 못한다. 예전에는 갈림 23건을 방금 침묵시킨 실행과 애초에 0건이던 실행이 **둘 다 3**(부분 검증 통과)을 냈다 — 자동화는 종료 코드만 읽으므로 두 실행이 구분되지 않았다(X-09). 바뀐 것이 없으면 0/2/3의 정상 경로로 떨어지는데, 그때는 관측이 커밋된 원장과 정확히 같다는 뜻이라 플래그 없이 돌린 실행과 판정이 정의상 같고, 원장 파일도 다시 쓰지 않는다.

**"바꿨다"는 쓴 내용과 이전 내용의 차이다 — 지적 건수가 아니다(X-12).** 위 문단은 한동안 특정 경우에 **거짓**이었다. 판정 기준이 `reference_problems()`의 **지적 건수**였는데, 그것은 "원장이 낡았다"의 척도이지 "원장이 바뀐다"의 척도가 아니다. 원장이 아직 **없는** 상태(이 저장소의 현재 상태다 — `parity/reference-ledger/`가 없다)에서 관측이 전부 `agree`이면 지적은 0건이다. 그래서 `--only-domain masking --record-reference`가 31건을 담은 원장을 **새로 만들고서** 종료 코드 3으로 끝났고, CI는 3을 통과로 읽으므로(`.github/workflows/ci.yml`) 스킬 지시를 그대로 따른 에이전트가 **원장을 쓰고서 "게이트 통과"를 보고**하게 되어 있었다.

두 함정이 양쪽에 있다. 하나는 **없음 → 있음을 변경으로 세지 않는 것** — 지금 이 구멍이 그대로 남는다. 다른 하나는 **`recorded_at`을 비교에 넣는 것** — 그 값은 매 실행 달라지므로 기록 실행이 **항상** 4가 되어 정반대 방향으로 고장나고, 어떤 기록 실행도 영원히 게이트를 닫지 못한다. 그래서 비교에서 빼는 것은 `recorded_at` 하나뿐이고(`LEDGER_VOLATILE_FIELDS`), 그 목록을 늘리는 것은 원장 변경을 조용하게 만드는 것과 같다.

절차: `--record-reference`로 원장을 갱신(4) → **왜 갈렸는지 한 줄과 함께** 원장 diff를 커밋 → 플래그 **없이** 다시 돌린 결과로 판정한다.

## 회귀를 무엇으로 정의하는가

기준이 바뀌어도 "어제 되던 것이 오늘 안 되는" 것은 막아야 한다. 새 구조에서 회귀는 세 층이다.

| 층 | 회귀의 정의 | 무엇이 잡는가 | 등급 |
|---|---|---|---|
| ① 성질 | 어제 충족하던 케이스가 오늘 불충족 | 같은 게이트. 케이스가 사라지는 경로는 정본 대조가 막는다 | **차단**(1) |
| ② 참고 갈림 | 어제 Python과 같던 자리가 오늘 갈림 (성질은 여전히 충족) | 참고 갈림 원장 | **기록 요구**(1, 기록으로 닫힌다) |
| ③ 품질 | 통과율·judge 점수·충실성 하락 | `tests/golden` — `PASS_RATE_THRESHOLD=0.9`, `JUDGE_SCORE_THRESHOLD=4.0`, `DEFAULT_FIDELITY_FLOOR=2` 이하 0건 | 골든셋 게이트 |

①이 성립하려면 **케이스가 계속 존재해야 한다.** 그것을 정본 대조가 지킨다. ③은 이 하네스의 범위 밖이지만 회귀 방지의 세 번째 다리이므로 여기에 적어 둔다 — 성질은 "가려졌는가"를 말할 수 있어도 "읽기 쉬운가"를 말하지 못한다. master-plan §6.2가 골든셋 평가를 2단(스키마·규칙은 매 CI, LLM 평가는 nightly)으로 강제한 이유가 이것이다.

**Python 쪽이 바뀌면 fixture부터 재생성한다.** 재생성 diff가 곧 "Python 동작이 이렇게 바뀌었다"는 기록이다. 재생성을 건너뛰면 정본 대조가 종료 코드 1과 함께 재생성 명령을 찍는다.

## 마스킹 범위 축소 (2026-08-12)

사용자 결정: **주민등록번호·카드번호 2종만 유지.** 전화번호·이메일·계좌번호는 뺀다. 근거는 "공용 문서 번역이 주 용도라 개인정보 위험이 낮고, 포팅 비용을 줄여 개발 속도를 얻는다"이다. 정책 문구의 정본은 `docs/master-plan.md` §3.2와 프로젝트 CLAUDE.md이며 이 스킬은 그것을 따른다.

**계약이 값을 못박았다** (`contracts/easy-doc-v1.yaml`): `MaskedItemResponse.category`는 `enum: ["주민등록번호", "카드번호"]`이고 자리표시자는 `^\[\[(주민등록번호|카드번호)[0-9]+\]\]$`다. **값이 한국어 문자열**이며 자리표시자에 그대로 박히므로 표기가 아니라 복원 키다 — Kotlin enum 이름이나 영문 코드를 직렬화하면 계약 위반이다. 계약에는 "전화번호·이메일이 든 문서라도 `masked_items`가 비어 있는 것이 정상"도 명시돼 있다.

**범주 문자열의 정본은 계약이고, 생성기도 비교기도 그것을 읽는다.** 생성기는 `mask_contract()`로 `MaskedItemResponse.category` enum을 읽어 fixture를 만들고, 비교기는 `placeholder_scheme` 검사에서 **같은 계약을 독립적으로 읽어** fixture 선언과 대조한 뒤 계약 쪽 값으로 판정한다. 계약을 읽지 못하면 통과가 아니라 불충족이다(fail closed). 이 배선 전에는 fixture가 스스로 넘긴 `categories` 인자와만 대조해, 생성기가 `["RRN","CARD"]`로 흘러가면 게이트는 통과하고 API는 계약을 위반했다(X-12/S-1 — 재현에서 종료 코드 3 = 통과를 확인했고, 배선 후 같은 재현이 종료 코드 1로 막힌다).

fixture는 31 케이스·단언 114개다.

- **가려야 하는 것**(`absent`): 하이픈·무구분자·공백·탭 표기 주민등록번호, 성별코드 5~8(외국인등록번호), 하이픈·공백·무구분자 카드번호, 그리고 **숫자 사이에 보이지 않는 문자가 낀 표기**(아래).
- **남아야 하는 것**(`present`): 날짜(`2026-01-01`), 12·14자리 숫자열, 이름·주소 줄, **개행으로 갈린 두 숫자열**, 그리고 **범위에서 뺀 전화번호·이메일·계좌번호**.
- **참고 갈림 없음**(2026-08-12 갱신): 범위에서 뺀 3종은 한때 `reference_divergence: "expected"`로 선언돼 있었다. Python이 아직 5범주여서 참고값이 요구사항과 갈리는 것이 정상이었기 때문이다. Python 구현이 2종으로 축소되면서 참고값이 요구사항과 일치하게 되어 선언이 낡았고(비교기가 "의도한 갈림이 사라졌다"로 막는다) 생성기에서 지웠다. 판정이 느슨해지지는 않는다 — `present` 단언이 그대로 남아 패턴을 다시 넓히면 걸린다.
- **알려진 공백**(`known_gap`): **전각 표기 주민등록번호 1건만 남았다.** 전각 숫자로만 적은 주민등록번호는 현재 Python이 못 잡고(성별코드 `[1-8]`이 ASCII 리터럴), 지금 단언하면 Kotlin에 Python보다 넓은 구현을 요구하게 되므로 어느 방향도 단언하지 않는다. `privacy-gate` 판정서가 이 건을 **범위 밖**으로 명시했다.

### 보이지 않는 문자 회피 — `known_gap`에서 단언으로 전환 (2026-08-12)

`02_privacy-gate_control-char-verdict.md`가 이 자리를 **(가) 실제 위험**으로 닫았다. 그전까지 `masking-known-gap-rrn-control-char`는 어느 방향도 단언하지 않았고, 그래서 **제어문자가 낀 주민등록번호를 한 글자도 가리지 않은 산출물이 게이트를 통과했다**(X-05, codex #3 — 재현에서 종료 코드 3 확인). 판정이 내려진 뒤에도 fixture가 그대로였다는 것이 지적의 요지였다.

판정서가 교정한 문제 틀 두 가지를 그대로 따른다.

- **위협 모델은 악의적 회피가 아니라 사고성 유입이다.** 업로더(기관 담당자)와 개인정보 주체(문서에 등장하는 시민)가 다르므로 "자기 주민번호를 숨기는 공격자"는 성립하지 않는다. 그런데도 위험은 남는다 — 피해자가 동의한 적 없고 조용한 누락이라 담당자도 모른다.
- **막을 대상은 "제어문자"가 아니라 "숫자 사이에서 보이지 않는 문자 전체"다.** C0 제어문자는 docx·hwpx에서 XML 1.0 위반으로 파일째 거부되지만 U+00AD·U+200B·U+FEFF는 XML에 합법이고, PDF와 JSON 붙여넣기 경로는 아예 무방비다. 실문서 16건(1,971,740자)에서 제어문자 1,000건 이상·"숫자 사이 끼임" 4건이 실측됐고 그중 U+00AD가 하이픈 자리를 대신하고 있었다.

전환한 케이스: `rrn-soft-hyphen`(U+00AD — 유일하게 실문서 근거가 있어 우선순위 최상), `rrn-zwsp`(U+200B), `rrn-bom`(U+FEFF), `rrn-nul`, `rrn-fs`(U+001C), `rrn-us`(U+001F), `rrn-zwsp-inside-tail`(뒤 7자리 **안쪽**), `card-zwsp`(카드번호도 같은 벡터다).

반대 방향 가드도 함께 넣었다 — `keeps-newline-split-digits`. 이것이 없으면 "보이지 않는 문자를 접는다"를 "공백을 전부 접는다"로 구현해도 통과하고, 그 구현은 서로 다른 줄의 숫자를 붙여 진짜 과잉 마스킹을 만든다. 스탠드인 `whitespace-fold`로 실증했다(종료 코드 1, `keeps-newline-split-digits`·`newline` 2건 지목).

**단언이 구현보다 앞선다.** 이 전환은 Kotlin 구현을 기다리지 않고 먼저 넣는 것이 옳은 의존 방향이다 — 성질을 못박아야 구현이 그것을 향해 간다.

### 유니코드 숫자는 여전히 축이다

주민번호·카드번호가 숫자이므로 `\d` 차이가 그대로 걸린다. **실측**(`docs/migration/_workspace/02_parity-verifier_masking-spec.md`):

- Python `re`의 `\d`는 유니코드 십진 숫자를 포함하고, Java 기본 `\d`는 `[0-9]`다. 앞 6자리가 아랍-인도 숫자인 주민번호와 전각/아랍-인도 카드번호는 Python이 **가린다** — Java 기본으로 옮기면 조용한 마스킹 누락이다.
- `[1-8]`(성별코드)은 ASCII 리터럴이라 전부 전각인 주민번호는 Python이 **못 잡는다**. 이것이 위의 `known_gap`이다.
- 범위 축소로 **`\s` 축은 통째로 사라졌다.** 29종/23종/4종 분석은 PHONE 패턴의 `[-.\s]` 때문이었고, RRN의 구분자는 `[ \t]`, CARD는 `[- ]` 리터럴이다.
- `UNICODE_CHARACTER_CLASS`를 켜도 **보이지 않는 문자 회피는 해결되지 않는다.** 낀 문자는 숫자가 아니라 숫자 **사이**에 있다. 두 수정이 모두 필요하고, 뷰↔원문 대응은 **UTF-16 인덱스 기준**으로 만들어야 이모지 인접 입력에서 스팬이 어긋나지 않는다.

스탠드인 실증(2026-08-12 갱신, 31 케이스·단언 114개 기준). 명령은 전부 `--fixture parity/fixtures --actual <스탠드인> --only-domain masking`:

| 스탠드인 | 흉내 낸 것 | 결과 |
|---|---|---|
| `conformant` — 2범주 + 유니코드 `\d` + 뷰/좌표 대응 | **요구사항대로 포팅** | **종료 코드 3**(부분 검증 통과), 성질 31건·단언 114개 충족, 참고 갈림 0건 |
| `scope2` — 위와 같되 보이지 않는 문자 미처리 | 판정 전의 "충분해 보이는" 포팅 | 종료 코드 1, **8건 지목**(회피 6종 + 안쪽 삽입 + 카드) |
| `java-default` — `\d`=`[0-9]` | 플래그를 안 켠 JVM 포팅 | 종료 코드 1, 3건 지목 |
| `whitespace-fold` — 회피 차단을 공백 접기로 구현 | 과잉 방향으로 넘어간 방어 | 종료 코드 1, 2건 지목(`keeps-newline-split-digits`·`newline`) |
| `over` — 전문을 하나로 가림 | 과잉 마스킹 | 종료 코드 1, 30건 지목 |
| `nomask` — 아무것도 안 함 | 마스킹 누락 | 종료 코드 1, 22건 지목 |
| `python-verbatim` — Python 참고값 그대로 | 값 동일성 시대의 "정답" | 종료 코드 3 — **현재 Python이 요구 성질을 충족한다**(2종 축소 + 회피 차단이 모두 반영된 상태) |

마지막 줄은 시점에 따라 뒤집힌다. 이 표를 인용할 때는 **언제 측정했는지**를 함께 적는다 — `python-verbatim`이 통과한다는 것은 "Python이 정답"이라는 뜻이 아니라 "이 시점의 Python이 이 성질 집합을 우연히 전부 만족한다"는 뜻이고, 판정 근거는 여전히 성질이다.

## 정규화 규칙

동등으로 볼 것 — 표기 차이일 뿐 제품 동작이 같은 경우만: `nfc`, `nfkc`, `lf`, `trim`, `trim_line_ends`, `mask_document_id`(프롬프트의 난수 문서 id), `float_tol`(기본 1e-9, 상한 1e-3). JSON 객체 키 순서는 항상 무시한다.

절대 정규화로 눈감아 주면 안 되는 것 — 스크립트가 규칙 이름으로 거부한다(`FORBIDDEN`): `ignore_placeholders`(복원이 깨진다), `ignore_body`, `ignore_status`(계약이다), `casefold`, `collapse_all_space`, `sort_lists`.

정규화는 **줄이는 방향으로** 관리한다. 하나 추가할 때마다 "그 차이가 왜 제품 동작에 무해한가"를 남긴다. 근거를 못 대면 그것은 정규화가 아니라 은폐다.

## 자격증명·암호는 이 스킬이 판정하지 않는다

`crypto`·`jwt`·`argon2` 도메인과 역방향 외부 검증(`verify-crypto`/`verify-jwt`, `*.verified.json`)이 여기 있었다. 2026-08-12에 없어졌다 — 근거와 요구가 어디로 갔는지는 위 「없어진 것」 절에 있다. 요약: 값 동일성 요구는 사라졌고 **암호가 올바른가**는 여전히 요구사항이며, 그 판정은 Kotlin 자체 테스트와 `migration-safety-gate` I-7·I-8·I-9가 맡는다.

이 스킬을 부른 요청이 "암호 fixture 검증", "Fernet 양방향", "JWT 교차 검증"처럼 들리면 **먼저 그 요청이 낡은 전제 위에 있다는 것을 알린 뒤** `migration-safety-gate`로 넘긴다. fixture를 새로 만들어 요청을 들어주지 않는다.

## 아직 성질을 적지 않은 도메인 (pending)

pending 도메인은 미검증으로 집계된다. 성질을 적을 때의 출발점은 각 fixture의 `requirement`다.

- **style** — 50자·쉼표 2개 규칙의 **건전성과 완전성**: 위반으로 보고된 문장은 실제로 규칙을 넘어야 하고, 넘는 문장은 빠짐없이 보고돼야 한다. 문장 분리 경계 자체는 휴리스틱이라 규칙으로 적히지 않는다 — 그 자리는 판정하지 않고 참고 갈림으로 남긴다.
- **style-tables** — 정책 상수(`MAX_SENTENCE_CHARS`·`MAX_COMMAS_PER_SENTENCE`·`STYLE_PRINCIPLES`)는 `equals_field`, 치환 사전은 `contains_all`(누락 금지·추가 허용).
- **prompts** — 스타일 원칙 전량 포함, 검출된 어려운 말이 각각 실림, 자리표시자 보존, 문서 id 경계 유지. 문면이 한 글자까지 같을 필요는 없다.
- **postprocess** — 껍데기만 벗기고 본문 손실 0. 과잉 제거가 과소 제거보다 위험하다.
- **export** — 파일명에 경로 구분자·제어문자 없음, 길이 상한, RFC 5987 해석 가능, 자리표시자 **전량** 복원.
- **ingest·golden** — 생성기 자체가 없다. 도메인명을 임의로 만들어 쓰지 말고 "미구현"으로 보고한다.

`ingest`(문서 추출)는 여전히 가장 위험한 자리다. 현재 Python docx 추출기는 공개 API 대신 OOXML 트리를 직접 순회하며, 그 이유들이 그대로 요구사항이다 — 표가 본문 안 제자리에 남고, 텍스트박스·중첩 표·SDT가 딸려 오고, `w:ins`는 포함하고 `w:delText`는 제외하며, `mc:Fallback`에서 하강을 멈춘다(멈추지 않으면 텍스트박스가 두 번 나와 크레딧이 두 배로 청구된다). **포팅 불가능한 요소를 조용히 누락하지 않는다** — 지원 한계로 문서화하거나 명시적으로 실패한다. 한계값(`MAX_UPLOAD_BYTES` 10MB, `MAX_EXTRACTED_CHARS` 500,000, 압축 해제 예산, DTD 차단, 스캔 PDF 거절, OLE2 진단)도 함께 옮긴다.


Kotlin 결과 파일 형식: `{"runtime": "kotlin", "cases": [{"id": "...", "actual": {...}}]}` — fixture와 **같은 상대 경로·같은 파일명**에 둔다. `runtime`은 반드시 `kotlin`이어야 한다(문자열 선언이라 단독 방어선은 아니고, 실수로 Python 하네스 출력을 넣은 경우를 잡는 값어치다).

종료 코드:

| 코드 | 뜻 | 게이트 |
|---|---|---|
| 0 | 요구 성질 전건 충족 + 미검증 0건 + 기대 도메인 전부 존재 | 닫아도 된다 (마지막 줄이 `요구 성질 충족:`일 때만) |
| 1 | 성질 불충족·미실행·도메인 누락·빈 fixture·**단언 없는 spec 케이스**·**방향 가드 결손**·**입력이 같은 케이스 둘**·**기록되지 않은 참고 갈림**·**낡은 원장 항목**·**fixture 범주가 계약과 다름/계약을 못 읽음**·fixture가 정본과 다름·`runtime` 문제·사용법 오류 | 차단 |
| 2 | 불충족은 없으나 **미검증**이 남음 (spec_status=pending) | 닫지 않는다 |
| 3 | **부분 검증**(`--only` / `--only-domain` / 단일 fixture / 도메인 디렉터리)이 그 범위 안에서 통과 | 닫지 않는다 |
| 4 | `--record-reference`가 **원장 파일 내용을 바꿨다**(없던 원장을 새로 만든 것 포함) — 판정이 아니라 기록이다 | 닫지 않는다 |

**Phase 종료 조건은 전체 게이트 실행(종료 코드 0)으로만 닫는다.** 부분 검증은 정상적인 개발 중 작업이지만 진행 상황이지 게이트가 아니다. 부분 검증이라도 불충족이 있으면 1, 미검증이 남으면 2가 그대로 나가고 3은 그 둘을 통과한 뒤에만 도달한다. 4는 `--record-reference`를 준 실행에서만 나오며 CI는 그 플래그를 주지 않는다(`.github/workflows/ci.yml`은 0과 3만 통과로 읽는다).

### 이 게이트가 막지 못하는 것

완벽히 막을 수 없는 것은 적어 둔다. 조용히 뚫리는 것보다 낫다.

- **단언이 요구사항을 다 덮는지는 보장되지 않는다.** 값 동일성 시절에는 "전부"를 재는 대신 무엇을 재는지 몰랐고, 지금은 무엇을 재는지 알되 그것이 전부가 아니다. 덮이지 않은 자리는 참고 갈림 원장과 골든셋 게이트가 받고, 커버리지는 사람이 리뷰한다.
- **"그 산출물을 정말 Kotlin이 만들었는가"는 증명되지 않는다.** fixture의 입력이 전부 공개돼 있으므로 같은 값을 Python으로도 만들 수 있다. Kotlin 하네스가 산출물 파일을 쓰도록 CI에 배선하는 것이 유일한 방어다(`.github/workflows/ci.yml`의 `parityHarness` 단계).
- **정본 생성기 자체의 위조는 막지 못한다.** 생성기를 고치면 성질도 따라 바뀐다. 생성기·비교기 변경은 리뷰 게이트를 거친다. 게이트 범위 축소는 `.github/parity-canonical-floor.txt`가 조용할 수 없게 만든다. 마스킹 **범주 문자열**만은 예외로 저장소 밖(계약 파일)에 기준을 두었으나, 그 계약을 읽는 함수(`mask_contract()`)를 통째로 바꿔치우는 것은 여전히 막지 못한다 — 리뷰가 받는다.
- **계약 파일 자체가 틀린 경우는 판정하지 않는다.** 이 게이트는 "fixture·산출물이 계약과 같은가"만 본다. 계약이 요구사항에 맞는지는 `contract-keeper`와 `api-contract-freeze`의 몫이다.
- **품질은 판정하지 않는다.** "가려졌는가"는 말할 수 있어도 "읽기 쉬운가"는 골든셋의 몫이다.

**이 게이트 자신이 같은 실패를 두 번 냈다.** ① 자리표시자 범주를 계약이 아니라 **fixture 자신이 넘긴 인자**와 대조해, 생성기가 선언한 집합을 그 생성기가 만든 fixture로 검사하는 구조였다(지금은 `mask_contract()`가 계약 파일을 읽는다). ② `mypy .`가 점 디렉터리를 크롤링에서 건너뛰어 이 스킬의 스크립트 2파일을 **한 번도 보지 않았다** — 저장소의 다른 모든 판정을 그 코드가 내리는데 정작 가장 덜 검사받았다(지금은 `CLAUDE.md` 명령 절이 경로를 명시한다). 그래서 스크립트를 고칠 때마다 **검사의 기준이 검사 대상 자신에게서 나오지 않는지**와 **이 스크립트가 타입 검사·CI 범위 안에 있는지**를 함께 확인한다. 규칙 전문과 근거가 된 실패 7건은 `kotlin-migration` 스킬의 "선언한 범위와 실제 도달을 대조한다" 절에 있다.

## 재호출 지침

`docs/migration/_workspace/`의 이전 parity 산출물을 먼저 읽는다(특히 `02_parity-rebase.md`).

- Python 쪽 코드가 바뀌었으면 **fixture부터 재생성**하고 diff를 본다. 재생성을 건너뛰면 종료 코드 1과 함께 "정본과 다르다"가 찍힌다 — 그 출력이 곧 재생성 지시다.
- **요구사항이 바뀌었으면 성질부터 고친다.** 순서를 뒤집어 Kotlin을 먼저 고치면 하네스가 구현을 따라가는 도구가 된다.
- 참고 갈림이 새로 생겼으면 **왜 갈렸는지 한 줄을 리포트에 남기고** 원장을 갱신한다. 원장 갱신만 하고 이유를 안 적으면 다음 사람이 판단할 근거가 없다. 갱신 실행은 종료 코드 4로 끝나므로 그 자체로는 아무것도 닫지 못한다 — 판정은 플래그 없이 다시 돌린다. **원장을 처음 만드는 실행도 4다**(갈림 0건이어도 파일이 없다가 생기는 것은 변경이다). 한동안은 그 경우가 3으로 끝나 기록 실행이 통과로 보고됐다(X-12).
- **`known_gap`·`pending`·`reference_divergence` 같은 자기 면제 선언이 붙은 자리는 "지적 없음"으로 닫지 않는다.** 리뷰 회차에서 실제로 그 실패가 났다 — 같은 3건을 실행으로 관측하고도 "기지 공백이므로 설계상 불가피"로 기각했고, 그 사이 게이트는 개인정보 평문 누출을 계속 통과시켰다(X-05). 선언이 붙은 케이스는 별도 목록으로 올린다.
- 계약(`contracts/easy-doc-v1.yaml`)이 바뀌었으면 **fixture를 재생성**한다. 범주 enum이 바뀌면 생성기가 새 값으로 fixture를 만들고 비교기가 같은 계약으로 판정하므로 자동으로 맞춰지지만, 재생성하지 않으면 정본 대조가 종료 코드 1로 막는다.
- pending 도메인을 ready로 올릴 때는 방향 가드(under/over)가 둘 다 있는지 확인한다 — 스크립트가 막지만, 막히기 전에 설계에서 챙기는 편이 싸다.
- 이전 불일치가 해결되었다는 보고를 받으면 **말이 아니라 스크립트 출력(명령 전문 + 종료 코드 + 마지막 줄)으로** 확인한다.
