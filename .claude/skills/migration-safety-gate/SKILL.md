# migration-safety-gate

> 글로벌 `rule-checker`와의 차이: 저 스킬은 범용 코딩 규칙 준수를 훑고, 이 스킬은 **이 마이그레이션에서 깨지면 사용자 데이터가 유출·유실되는 불변식**만 다룬다. 둘은 대체 관계가 아니라 별개 게이트다.

## 감사의 전제

포팅은 로직을 옮기지만 **보호 장치는 옮기지 않는다.** Python 쪽 방어는 코드가 아니라 주석·순서·타입에 걸려 있는 것이 많다 — `MaskedItem.original`이 `SecretStr`이라 `repr`에 안 찍히는 것, `raise ... from None`으로 예외 체인을 끊어 트레이스백에 값이 안 실리는 것, `_logger.warning("...: %s", type(exc).__name__)`처럼 타입만 남기는 것. Kotlin으로 옮기면서 이것들은 기본값으로 되돌아간다. Kotlin의 `data class`는 `toString()`에 모든 필드를 찍고, `logger.error("실패", exc)`는 스택트레이스 전체를 남긴다.

그래서 감사는 "새 코드에 나쁜 게 들어갔나"가 아니라 **"Python이 하던 보호를 Kotlin이 계속 하고 있나"**를 묻는다.

## 불변식 목록

각 항목: ① 무엇을 보장하는가 ② 어떻게 검증하는가 ③ 위반 시 영향.

### I-1. 원문은 마스킹을 거친 뒤에만 LLM에 도달한다 — **차단**

**보장**: 사용자 문서 텍스트는 `mask_text()`(Kotlin 대응 구현)를 통과한 결과만 LLM provider로 전달된다. 원문·마스킹 대응표는 벤더로 나가지 않는다. 근거: CLAUDE.md 보안 규칙, `app/privacy/masking.py` 모듈 docstring, `app/services/conversion.py` "처리 순서(변경 금지)", 계획 §2.3.

**검증**:
1. Kotlin에서 provider 인터페이스를 호출하는 **모든** 지점을 찾는다. Python 현황은 2곳뿐이다 — `app/services/conversion.py:133`, `app/easyread/judge.py:163`. 이 개수가 늘었다면 왜 늘었는지 설명이 있어야 한다.
2. 각 호출 지점에서 인자로 들어가는 값의 출처를 역추적한다. 마스킹 결과 타입을 거치지 않은 경로가 하나라도 있으면 위반이다.
3. 타입으로 강제되었는지 확인한다. 가장 튼튼한 형태는 provider가 `String`이 아니라 `MaskedText` 같은 전용 타입만 받고, 그 타입의 생성자가 마스킹 함수 안에서만 호출되는 구조다. 검증이 grep에 의존하는 상태면 그 자체를 개선 권고로 남긴다.
4. **judge(LLM-as-judge) 경로를 빠뜨리지 않는다.** `judge_conversion`도 원문을 `mask_text`에 통과시킨 뒤 보낸다. 평가 도구라서 예외라고 넘기면 골든셋 원문이 그대로 나간다.
5. 기계 스캔: `scan_privacy_invariants.py --rule LLM-RAW-INPUT --rule LLM-VENDOR-SDK`.
6. 벤더 SDK import가 provider 어댑터 밖에 없는지 본다. 어댑터 밖에서 SDK를 직접 부르면 마스킹뿐 아니라 호출 수 상한·no-training 계약도 함께 우회된다.

**영향**: §5 Phase 7 즉시 중단 기준("마스킹 전 본문이 LLM이나 로그로 전송됨"). 이미 전송된 데이터는 회수할 수 없다 — 되돌릴 방법이 아예 없는 유일한 종류의 사고다(재개발 이후에는 롤백 자체가 없으므로 다른 항목도 fix-forward뿐이다).

### I-2. LLM 호출은 변환 1회 + 조건부 보정 1회, 최대 2회 — **차단**

**보장**: 문서 한 건당 provider 호출이 2회를 넘지 않는다. `MAX_LLM_CALLS_PER_CONVERSION = 2`. 보정은 "다시 검사해 또 부르는 루프"가 아니다.

**검증**:
1. 규칙 검사 통과 시 1회로 끝나는지, 위반 시에만 보정 1회가 붙는지 fixture로 확인한다(parity 스킬의 고정 응답 계층).
2. **재시도 책임이 한 계층에만 있는지** 본다. 계획 §4.6: LLM SDK 자체 자동 retry(`DEFAULT_MAX_RETRIES = 2`)와 worker retry가 겹치면 호출 수가 조용히 늘어난다. 어느 계층이 재시도를 소유하는지 코드와 설정에서 확인하고, 다른 쪽은 껐는지 본다.
3. 워커 crash/재기동 시 이미 완료된 변환을 다시 부르지 않는지 확인한다(idempotency 검사 유지 — 현재 Python은 "이미 완료된 변환입니다" 분기가 있다).
4. **메트릭에 드러나는지** 본다. §4.6이 "제품 계약은 네트워크 재전송과 별도로 메트릭에 드러나야 한다"고 요구한다. 도메인 호출 수와 HTTP 요청 수를 분리해 세는 지표가 없으면 위반을 관찰할 방법이 없다.
5. 보정 호출이 실패해도 변환 전체가 실패하지 않는지(원본 채택) 확인한다.

**영향**: §5 Phase 7 즉시 중단("중복 LLM 호출", "최대 2회 호출 계약 위반"). 비용이 문서 수에 비례하지 않고 폭주하며, 지연이 늘어 pending 체류로 이어진다.

### I-3. 로그에 문서 본문·개인정보가 없다 — **차단**

**보장**: 로그에는 문서 ID·길이·처리 상태·failure code·소요 시간만 남는다. 본문·마스킹 원문·이메일·비밀번호·토큰·예외 메시지에 실린 값은 남지 않는다.

**검증**:
1. `scan_privacy_invariants.py --rule LOG-BODY --rule LOG-FSTRING --rule EXC-BODY`. 후보를 하나씩 열어 판정한다.
2. Kotlin `data class`의 `toString()`을 점검한다. 문서·변환·마스킹 항목을 담는 클래스는 `toString()`을 **재정의**해 값 대신 id·길이만 내보내야 한다. Python은 `SecretStr`로 같은 일을 하고 있다. 이것은 grep으로 안 나오므로 클래스 목록을 직접 훑는다.
3. 예외 처리를 본다. `logger.error("실패", exc)`는 스택트레이스에 인자 값이 실릴 수 있다. Python은 `raise ... from None`으로 체인을 끊고 타입 이름만 남긴다(`app/privacy/crypto.py`의 주석이 그 이유를 적어 뒀다: 예외 체인이 붙으면 트레이스백에 생성자 인자가 노출되는 지점이 늘어난다).
4. 구조화 로그의 MDC/컨텍스트에 본문이 실리지 않는지 본다.
5. **실제로 돌려서 본다.** 코드 검사만으로는 부족하다 — 업로드→변환→내보내기를 합성 개인정보가 든 문서로 한 번 돌리고, 나온 로그 전문에서 그 개인정보 리터럴을 grep한다. 0건이어야 한다. 이것이 §5 Phase 4 종료 조건("평문이 DB·로그에 없음")의 증거다.
6. 프레임워크 기본 로그를 확인한다. Spring의 request/response 로깅, `DEBUG` 레벨 SQL 바인딩 파라미터 로깅(`spring.jpa.show-sql`, `logging.level.org.springframework.jdbc=DEBUG`)이 켜지면 암호문이 아니라 바인딩 값이 찍힌다.

**영향**: §5 Phase 7 즉시 중단. 로그는 평문으로 수집·장기 보관되므로 암호화 저장 정책 전체가 무의미해진다.

### I-4. 원문·결과·마스킹 대응표를 평문으로 DB에 저장하지 않는다 — **차단**

**보장**: `documents.encrypted_*`, `conversions`의 결과·검수본, 마스킹 항목은 AEAD 암호문으로만 저장된다(I-7). 파일명은 아예 저장하지 않는다(파일명 자체가 개인정보일 수 있다 — `app/models/document.py`).

**검증**:
1. 저장 경로마다 암호화 호출이 앞서는지 확인한다. `scan_privacy_invariants.py --rule PLAINTEXT-PERSIST`는 후보만 준다.
2. Testcontainers PostgreSQL에서 실제로 저장한 뒤 **DB에서 직접 읽어** 합성 개인정보 리터럴을 검색한다. 0건이어야 한다. 이것이 코드 리뷰보다 강한 증거다.
3. 신규 컬럼이 추가되었으면(예: 검색용 요약, 미리보기 캐시) 그것이 평문인지 본다. **additive 마이그레이션이 평문 컬럼을 들여오는 것이 가장 흔한 회귀 경로다.**
4. `key_version`이 함께 기록되는지 확인한다(현재 `CURRENT_KEY_VERSION = 1`).
5. 임시 파일·로컬 디스크·에러 덤프에 원문이 남지 않는지 본다.

**영향**: DB 덤프 한 번으로 전량 노출. 암호화 저장은 30일 보존 정책과 함께 이 서비스의 데이터 보호 근거 전부다.

### I-5. 다른 사용자 자원은 403이 아니라 404로 은닉한다 — **차단**

**보장**: 소유자가 아닌 자원에 접근하면 존재 여부를 알리지 않고 404를 반환한다. 목록도 빈 결과가 아니라 404다(잘못된 작업 공간 id의 경우).

**검증**:
1. `scan_privacy_invariants.py --rule OWNERSHIP-403`. CORS·인증 미들웨어·프런트 문구의 403은 오탐이므로 소유권 분기인지만 본다.
2. repository 쿼리에 소유자 조건이 `WHERE`에 있는지 본다. 조회 후 애플리케이션에서 비교하는 방식이면 타이밍·오류 메시지로 존재가 새기 쉽다.
3. **교차 사용자 테스트를 명시적으로 작성한다.** 사용자 A가 만든 문서·변환·작업 공간·내보내기 각각에 사용자 B가 접근해 전부 404인지 확인한다. §6 검증 매트릭스의 Security 게이트 기준이 "교차 사용자 접근 0"이다.
4. 404와 401을 구분한다. 인증 실패는 401, 소유권 불일치는 404다.

**영향**: §5 Phase 7 즉시 중단("다른 사용자 데이터 노출 또는 404 소유권 규칙 위반"). 403은 "있지만 네 것이 아니다"를 알리므로 자원 존재 자체가 유출이다.

### I-6. 개인정보 응답에 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` — **차단**

**보장**: 문서 본문·마스킹 원문·변환 결과가 담긴 응답에 두 헤더가 붙는다. 현재 정의는 `app/api/documents.py:50`의 `PRIVATE_RESPONSE_HEADERS`.

**검증**: 헤더가 **붙은** 곳이 아니라 **안 붙은** 개인정보 엔드포인트를 찾는 것이 목적이다. 개인정보를 반환하는 엔드포인트 목록을 먼저 만들고, 각각에 대해 contract test가 헤더를 확인하는지 본다. `scan_privacy_invariants.py --rule CACHE-HEADER`는 지정 지점 분포만 보여 준다. 파일 다운로드 응답도 포함한다 — 가장 자주 빠지는 자리다.

**영향**: 브라우저·중간 프록시 캐시에 문서 본문이 남는다. 공용 PC에서 뒤로 가기로 남의 문서가 보이는 형태로 드러난다. 계약 위반이기도 하다(§2.2).

### I-7. 저장 암호화(AEAD)의 정확성과 `encryption_scheme`·`key_version` 관리 — **차단**

> **2026-08-12 개정 — 무엇이 바뀌었나.** 이 항목은 "Python `cryptography`가 만든 기존 Fernet 토큰을 Kotlin이 읽는다"였다. 그 요구는 **롤백 창이 존재할 때만** 성립했고, 사용자 결정(2026-08-12)으로 Python 런타임을 폐기하고 롤백을 포기하면서 근거가 사라졌다(계획 §4.3 2차 개정). 보존할 운영 DB도 없다(§9 결정 2). 그래서 **Fernet·양방향·호환은 빠지고 저장 암호화는 표준 AEAD 신규 구현**이 된다. 함께 사라진 것: parity `crypto` 도메인, Fernet 직접 구현 승인(옛 §9 결정 3), `fernet-v1` 읽기/쓰기 유지 요구.
>
> **없어지지 않은 것이 이 항목의 본체다.** "Python과 같은 바이트"가 사라졌을 뿐 **암호가 올바른가**는 그대로 차단 사유다. 아래 검증은 그 요구만 남긴 것이다.

**보장**: 문서 본문·변환 결과·마스킹 대응표가 표준 AEAD(AES-GCM 또는 검토를 거친 동등 AEAD)로만 저장된다. 암호화→복호화 round-trip이 성립한다. 변조·다른 키는 **실패한다**. 키 세대가 행마다 기록돼 키 회전이 가능하다.

**검증**:
1. **round-trip** — 한글·ASCII·빈 값·긴 값·개행/탭이 든 값을 암호화 후 복호화해 원문과 같은지 본다. Kotlin **자체 테스트**로 확인한다(parity 하네스로는 못 본다 — 암호문이 불투명해 비교기가 열 수 없고, 산출물의 `"tamper_rejected": true` 같은 필드는 하네스의 자기 신고라 증거가 아니다).
2. **음성 케이스** — 변조(1바이트 flip), 다른 키, 암호문 형식이 아닌 바이트가 **전건 실패**해야 한다. **음성 케이스가 통과해 버리면 그것은 인증 암호화가 아니다.** AEAD를 쓴다면서 태그 검증 결과를 무시하거나, GCM 대신 CTR/CBC로 조립하고 무결성 검사를 빠뜨린 구현이 실제로 있다.
3. **복호화 oracle 금지** — 실패 원인(태그 불일치 / 키 불일치 / 형식 오류)을 구분하지 않는 **단일 예외**로 처리하는지 본다. 원인이 응답·로그·지연으로 구분돼 나가면 그것이 oracle이다. 예외 체인도 끊는다(트레이스백에 생성자 인자가 실린다).
4. **nonce/IV 재사용 금지** — AES-GCM은 같은 키로 nonce가 겹치면 평문이 복원 가능해진다. nonce가 매 암호화마다 새로 생성되는지, 고정값·카운터 하드코딩이 없는지 본다. AEAD를 새로 쓰기 때문에 생긴 **신규 검사 항목**이다(Fernet은 라이브러리가 IV를 다뤘다).
5. **`encryption_scheme`·`key_version`** — 두 컬럼이 읽기/쓰기 경로에서 실제로 쓰이는지 본다. 의미가 "롤백 호환"에서 **"키 회전용"**으로 바뀌었다. 처음부터 새 scheme 값(예: `aes-gcm-v1`)으로 쓰고 `fernet-v1`을 쓰지 않는다. 옛 키 복호화 지원은 확장 지점만 열어 둔다.
6. **즉흥 암호 금지** — JDK/검증된 라이브러리의 표준 AEAD를 쓴다. 직접 프리미티브를 조립한 코드가 있으면 위반이다. 이 조항은 Fernet 시절부터 유지되며 근거가 더 강해졌다(호환 제약이 사라져 표준을 고를 자유가 생겼다).

**영향**: §5 Phase 7 즉시 중단 기준("AEAD 복호화 round-trip 실패, 또는 변조가 예외 없이 통과됨"). 사용자가 올린 문서를 영구히 읽지 못하게 되거나, 인증 없는 암호화라 변조가 그대로 복호화된다. **롤백으로 되돌릴 수 없다** — 돌아갈 런타임이 없으므로 대응은 신규 업로드 중단 + fix-forward다.

### I-8. Argon2 PHC 검증과 로그인 성공 시에만 재해시 — **차단**

> **2026-08-12 개정.** "Python이 만든 PHC를 Kotlin이 그대로 검증한다"는 **호환** 프레이밍이 빠졌다 — 보존할 사용자 DB가 없고 롤백도 없다. 남은 것은 **순수 기능·보안 요구**이고 아래가 그 전부다. 특히 4번(재해시 판정의 전체 파라미터 동등성)은 Phase 0 spike의 **필수조치 A**인데, 호환이 아니라 **정확성** 문제라 재개발에도 그대로 유효하다.

**보장**: Argon2id로 안전하게 해시·검증한다. 파라미터는 명시 고정한다(현재 값 `time_cost=3, memory_cost=65536, parallelism=4` — 재개발에서 재검토 가능하되 라이브러리 기본값에 기대지 않는다). 재해시는 로그인 **성공 시에만** 한다.

**검증**:
1. 해시·검증 round-trip과 틀린 비밀번호 거부를 확인한다. 변종(argon2i/argon2d/argon2id)과 파라미터를 **PHC 문자열에서 읽어** 쓰는지 본다 — 하드코딩된 파라미터로 검증하면 파라미터를 올리는 날 기존 해시가 전부 실패한다.
2. 재해시 시점을 확인한다. 실패한 로그인에서 재해시하면 오프라인 공격자에게 계산 자원을 태워 준다.
3. 재해시 실패가 로그인을 실패시키지 않는지 본다(best-effort — 경고 로그만 남기고 진행).
4. **재해시 판정이 전체 파라미터 동등성인지 본다 (필수조치 A).** Spring Security `Argon2PasswordEncoder.upgradeEncoding`은 memory·iterations의 **"미만"만** 본다. 그래서 parallelism만 다르거나 hash_len·salt_len이 다른 해시를 "최신"으로 오판한다(탐침 7건 중 5건 불일치, `00_privacy-gate_crypto-spike.md`). 지금은 무해해도 파라미터를 바꾸는 날 **이관이 조용히 멈춘다.** 전체 파라미터 동등성 판정 함수로 교체하고 탐침 7건을 회귀로 고정했는지 확인한다.
5. 해싱이 요청 스레드를 잠그지 않는지 본다. `memory_cost=65536`은 1건당 64MiB를 계산 끝까지 붙들고 있어 동시 실행 수 제한이 없으면 컨테이너가 OOM으로 죽는다.

**영향**: 파라미터 상향 시 재해시가 조용히 멈추거나(4), 로그인 경로가 서비스 거부 벡터가 된다(5). 검증 자체가 깨지면 전 사용자가 로그인하지 못한다.

### I-9. JWT 발급·검증의 정확성 — **차단**

> **2026-08-12 개정.** "양방향 호환"(Python 발급 토큰을 Kotlin이 읽고 그 반대도 성립)은 **롤백 창에서 세션이 끊기지 않게** 하려던 요구였다. 롤백이 없어져 근거가 사라졌다. 남은 것은 발급·검증 자체의 정확성과 위조 방어이며, Phase 0 spike의 **필수조치 B**(clock skew 0)는 호환이 아니라 정확성 문제라 그대로 유효하다.

**보장**: HS256으로 발급·검증한다. 클레임은 `sub`·`exp`·`typ`만(개인정보 금지). 만료 경계는 **clock skew 0**으로 판정한다.

**검증**:
1. 음성 케이스 — 만료 토큰, 서명 위조, 다른 키, **알고리즘 혼동**(`alg: none`, HS256을 RS256 헤더로 위조), `sub`/`exp`/`typ` 누락, `typ` 불일치, 비UUID `sub`가 전건 거부되는지 본다. 알고리즘 혼동은 JVM JWT 라이브러리에서 반복적으로 나온 취약점 유형이다.
2. **clock skew를 0으로 명시했는지 본다 (필수조치 B).** `DefaultJWTClaimsVerifier`의 기본 `maxClockSkew`는 **60초**이고 Spring Security `JwtTimestampValidator`도 기본 60초라, 기본값으로 두면 만료된 토큰이 `+59s`까지 받아들여진다. 경계 fixture 2건이 회귀로 고정돼 있는지 확인한다.
3. 서명 키 최소 길이 32바이트(`MIN_JWT_SECRET_BYTES`)를 기동 경로에서 강제하는지 본다 — 미만이면 경고가 아니라 설정 오류로 끊는다.
4. 클레임에 이메일 등 개인정보가 추가되지 않았는지 본다.

**영향**: 위조·만료 토큰으로 남의 계정에 접근된다. skew 기본값을 방치하면 로그아웃·세션 만료가 최대 60초 늦게 걸린다.

### I-10. 문서 파서 방어: DTD·외부 엔터티 차단, zip bomb 제한, 10MB, 스캔 PDF 거절 — **차단**

**보장**: 아래 표의 제한이 Kotlin에서도 동일하게 강제된다.

| 방어 | 현재 값 / 방법 |
|---|---|
| 업로드 상한 | `MAX_UPLOAD_BYTES = 10 * 1024 * 1024` |
| 추출 길이 상한 | `MAX_EXTRACTED_CHARS = 500_000` |
| 압축 해제 예산 | `_MAX_UNCOMPRESSED_BYTES = 5 * MAX_UPLOAD_BYTES`, **실제 읽은 바이트로** 계산 |
| DTD·외부 엔터티 | expat `StartDoctypeDeclHandler`로 파서 수준 거부 |
| 스캔 PDF | 텍스트 레이어 없으면 명시적 거절(페이지 0건과 구분) |
| 지원 형식 | `.docx`, `.pdf`, `.hwpx` (확장자 판별, 대소문자 무시) |

**검증**:
1. `scan_privacy_invariants.py --rule XML-DTD --rule ZIP-NO-BUDGET`로 위치를 찾고, 각 지점에서 방어가 실제로 켜졌는지 코드를 읽는다. JVM은 `XMLInputFactory.SUPPORT_DTD=false` + `IS_SUPPORTING_EXTERNAL_ENTITIES=false`, `DocumentBuilderFactory`는 `disallow-doctype-decl` feature.
2. **`<!DOCTYPE` 바이트 검색으로 막는 구현을 승인하지 않는다.** UTF-16으로 인코딩하면 그대로 뚫린다는 실측이 `app/ingest/extractors.py`의 `_hwpx_blocks` docstring에 있다. 파서 수준에서 막아야 한다.
3. **헤더 선언 크기를 상한으로 쓰는 구현을 승인하지 않는다.** 선언값을 위조한 94KB 파일이 힙 141MB를 먹는다는 실측이 `_ensure_zip_within_budget` docstring에 있다. `ZipEntry.getSize()`를 믿는 JVM 구현이 정확히 이 함정이다.
4. 악성 입력 fixture로 실제 거부를 확인한다: zip bomb, DTD 폭탄(UTF-16 인코딩 포함), 10MB 초과, 마크업 대비 본문 비율이 극단적인 문서, 암호 걸린 OOXML, 확장자만 바꾼 `.doc`.
5. 파서 예외가 사용자에게 스택트레이스로 새지 않는지 본다.

**영향**: XXE는 서버 파일 읽기·SSRF로, zip bomb·과대 추출은 OOM으로 이어진다. 제한 우회는 §6 Document 게이트("제한 우회 없음") 실패다.

### I-11. 보존 만료 파기: 04:00 KST, 500건 단위, 다중 worker 중복 실행 방지 — **차단(동작) / 기록(시각 미세 차이)**

**보장**: 매일 04:00 KST에 만료 문서를 파기한다. `RETENTION_BATCH_SIZE = 500`씩 커밋하고, `RETENTION_MAX_BATCHES = 1_000`으로 무한 루프를 막는다. 여러 worker가 동시에 돌아도 중복 실행되지 않는다.

**검증**:
1. `scan_privacy_invariants.py --rule RETENTION-PURGE`로 지점을 찾고, 배치 크기·advisory lock·시간대가 모두 있는지 본다.
2. **시간대를 명시했는지** 확인한다. 컨테이너 TZ는 보통 UTC라 명시하지 않으면 04:00이 13:00 KST가 된다. Python은 `RETENTION_CRON_HOUR`와 명시적 KST를 쓴다.
3. 다중 인스턴스 방어: PostgreSQL advisory lock(§4.4). 스케줄러가 인스턴스마다 도는 구성에서 잠금이 없으면 같은 행을 여러 트랜잭션이 잡는다.
4. 배치 단위 커밋인지 본다. 한 트랜잭션으로 전량 삭제하면 그만큼의 행을 오래 잠근다(`app/repositories/documents.py:149` 주석).
5. 삭제 범위: 문서와 변환을 함께 파기하되 **작업 공간은 지우지 않는다**(§2.3).
6. **파기가 실제로 일어났는지 관찰 가능한지** 본다. 만료 문서 잔존 수 지표가 없으면 파기 중단이 조용히 지나간다.

**영향**: 30일 자동 삭제 정책 위반은 곧 개인정보 보유 기간 위반이다. 실패해도 알림이 없어 가장 늦게 발견된다. 반대로 잘못된 조건으로 지우면 유효 문서가 사라진다.

### I-12. 비밀키는 환경변수만, 코드·커밋에 포함 금지 — **차단**

**보장**: 저장 암호화 키, `jwt_secret`, provider API 키가 `.env`·환경변수로만 들어온다. 로그·오류 응답·설정 덤프에 값이 찍히지 않는다.

**검증**: `scan_privacy_invariants.py --rule SECRET-LITERAL`. Spring은 `/actuator/env`·`/actuator/configprops`가 설정을 노출하므로 비활성화 또는 마스킹을 확인한다. Kotlin 설정 클래스가 `data class`면 `toString()`에 키가 찍히므로 재정의를 확인한다(Python은 `SecretStr`로 처리 중). 커밋 히스토리에 키가 들어간 적 있는지도 본다 — 들어갔다면 파일을 지우는 것으로 끝나지 않고 키 교체가 필요하다.

**영향**: 키 노출은 암호화 전체를 무력화한다. 히스토리에 들어간 키는 지워지지 않는다.

### I-13. AI 초안과 검수 수정본을 별도 보존한다 — **기록**

**보장**: 워커가 저장한 AI 초안과 담당자 검수 수정본을 각각 보관해 수정률 KPI 원천을 유지한다(§2.3). 초안을 수정본으로 덮어쓰지 않는다.

**검증**: 컬럼이 둘 다 살아 있고 저장 경로가 분리되어 있는지, 초안이 저장 시점에 정규화되지 않는지 확인한다(`app/text.py` 모듈 docstring: 초안·마스킹 원문을 저장 전에 손대면 원문 대조와 KPI 기준값이 우리가 고친 판본으로 바뀐다).

**영향**: 데이터 유출은 아니지만 되돌릴 수 없다. 덮어쓴 초안은 복구할 방법이 없고 KPI 시계열이 끊긴다. 발견 즉시 기록하고 다음 Phase 전에 고친다.

### 전수 검사와 변경분 검사

**변경분 검사**는 빠른 회전용이다. `--changed`로 git 변경 파일만 훑고, 변경이 닿은 불변식의 검증 절차만 돈다. Phase 진행 중에는 이것으로 충분하다.

**전수 검사**는 Phase 종료와 첫 배포 전에 한다. 변경분 검사가 놓치는 것이 있기 때문이다 — **불변식은 파일 하나가 아니라 파일 사이의 관계로 지켜진다.** A 파일에서 마스킹을 부르고 B 파일에서 provider를 부르는 구조에서, B만 바꾸면 변경분 검사는 A를 안 본다. 설정 파일(로그 레벨, actuator 노출, TZ) 변경도 코드 변경 없이 불변식을 깨뜨린다.

### 증거 없는 통과는 없다

각 불변식마다 **실행 결과**를 남긴다. "코드를 읽어 보니 맞습니다"는 통과 근거가 아니다. 남길 것:

- 스캔 리포트: `docs/migration/_workspace/{phase}_privacy-gate_scan.md`
- 실행 증거: 합성 개인정보 문서로 돌린 로그 grep 결과 0건, DB 직접 조회 결과 0건, 교차 사용자 404 테스트 결과
- 판정: 항목별 통과/차단/기록과 근거

## 차단 기준

### 즉시 중단 (계획 §5 Phase 7)

아래는 **작업을 멈추고 리더에게 즉시 보고**한다. 배포 후면 **신규 업로드를 멈춘다** — 되돌아갈 Python 런타임이 없으므로 롤백이 아니라 원인 수정 후 재배포(fix-forward)다(계획 §5 Phase 7 2차 개정). "고치면서 진행"이 없는 이유는, 이 항목들이 이미 발생한 피해를 되돌릴 수 없는 종류이거나(유출), 진행할수록 피해가 누적되기 때문이다(중복 호출, 데이터 유실).

| 즉시 중단 기준 | 대응 불변식 |
|---|---|
| AEAD 복호화 round-trip 실패, 또는 변조가 예외 없이 통과됨(복호화 oracle) | I-7 |
| 다른 사용자 데이터 노출 또는 404 소유권 규칙 위반 | I-5 |
| 마스킹 전 본문이 LLM이나 로그로 전송됨 | I-1, I-3 |
| 중복 LLM 호출, 작업 영구 유실, pending 무한 체류 | I-2 |
| 문서 추출·내보내기 주요 fixture 불일치 | I-10 (+ parity 스킬) |
| 골든 품질 바닥 또는 최대 2회 호출 계약 위반 | I-2 (+ parity 스킬) |

배포 후 중단 시: **Kotlin API와 worker를 함께** 다룬다 — 신규 접수를 막을 때 API만 세우면 worker가 큐에 남은 작업을 계속 처리한다. 롤백 대상은 없다(2026-08-12 재개발 전환).

### 차단 (진행 불가, 중단은 아님)

I-1 ~ I-12의 위반이 **아직 운영 데이터에 닿지 않은 상태**에서 발견되면 차단이다. 해당 Phase를 종료시키지 않고 수정 후 재감사한다. 예: Testcontainers 테스트에서 평문 저장이 잡힘, 교차 사용자 테스트에서 403이 나옴, 스캔에서 어댑터 밖 SDK import 발견.

### 기록 후 진행 가능

- **I-13**(초안·수정본 분리) 같이 유출이 아니고 되돌릴 수 있는 구조 문제. 단, 다음 Phase 전 해결을 조건으로 건다.
- **관찰 가능성 부족** — 불변식은 지켜지는데 지표가 없어 확인할 방법이 없는 경우. 첫 배포 전까지는 반드시 해결한다(관찰 기간에 지표 없이 들어가면 관찰이 성립하지 않는다).
- **스캔 오탐**으로 판정된 항목. 왜 오탐인지 근거를 남긴다. 근거 없이 "오탐"으로 처리하면 다음 감사가 같은 판단을 반복할 수 없다.
- **개선 권고** — 현재도 안전하지만 더 튼튼하게 만들 수 있는 것(예: 마스킹 선행을 grep이 아니라 타입으로 강제). 별도 목록으로 모아 둔다.

판정이 애매하면 차단 쪽으로 기운다. 잘못 차단하면 시간을 잃지만, 잘못 통과시키면 사용자 데이터를 잃는다.

## 번들 스크립트

### `scripts/scan_privacy_invariants.py`

Python과 Kotlin 소스를 함께 훑어 불변식 위반 **후보**를 모은다. 판정하지 않는다.

```bash
uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py
uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py --changed
uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py \
    --changed --base origin/main
uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py --list-rules
uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py \
    --rule LOG-BODY --report-md docs/migration/_workspace/07_privacy-gate_scan.md
```

규칙 12개: `LOG-BODY`, `LOG-FSTRING`, `EXC-BODY`, `LLM-VENDOR-SDK`, `LLM-RAW-INPUT`, `OWNERSHIP-403`, `PLAINTEXT-PERSIST`, `SECRET-LITERAL`, `XML-DTD`, `ZIP-NO-BUDGET`, `CACHE-HEADER`, `RETENTION-PURGE`. 대상: `app/`, `backend-kotlin/`, `scripts/`, `frontend/src/`의 `.py .kt .kts .ts .tsx .java`.

종료 코드 0 = BLOCK 후보 없음, 1 = BLOCK 후보 있음, 2 = 입력 오류, 3 = `--changed` 범위가 비어 아무것도 검사하지 못함. 리포트 수집만 할 때는 `--no-fail`.

**`--changed`의 범위**는 `<base>...HEAD` + 작업 트리 + 미추적이고 base 기본값은 `main`이다. base 없이 작업 트리만 보면 **브랜치에 커밋된 변경이 통째로 빠져**, 에이전트가 구현을 커밋한 뒤 스캔하면 보안 코드를 한 줄도 안 읽고 통과한다. 같은 이유로 검사 파일이 0개면 종료 코드 3으로 실패시킨다 — "검사하지 않음"과 "위반 없음"은 다르다. 정말 빈 것이 맞을 때만 `--allow-empty`. base를 해석할 수 없으면 전수로 넓혀 폴백하고, 리포트의 `검사 범위:` 줄에 실제 적용된 범위를 적는다.

**2차 판정**: 규칙은 정규식 적중 뒤에 두 가지를 더 볼 수 있다. `refine`은 적중한 **값의 모양**으로 거르고(`SECRET-LITERAL`은 엔트로피·문자 클래스로 난수 키와 `wrongpassword` 같은 픽스처를 가른다 — 경로가 아니라 값이 기준이므로 테스트 파일 안의 진짜 키는 그대로 잡힌다), `hardened`는 같은 창 안에 완화 조치가 있으면 뺀다(`XML-DTD`는 `disallow-doctype-decl`·`SUPPORT_DTD=false`·`StartDoctypeDeclHandler`를 인정한다). 제외 건수는 리포트 상단에 함께 찍는다 — 규칙이 눈감은 양이 보이지 않으면 규칙이 죽은 것을 알아채지 못한다.

**출력은 후보 목록이지 판정이 아니다.** 정규식은 문맥을 읽지 못하므로 오탐이 반드시 섞이고, 스크립트도 그렇게 출력한다. 자동 차단에 쓰면 곧 "어차피 오탐"이라며 전체를 무시하게 되고, 그때 진짜 유출이 지나간다. 각 항목의 `오탐 가능` 줄을 읽고 파일을 열어 판정하라.

설계상 허용된 경로는 규칙의 `sanctioned` 필드로 제외되어 있다(예: `LLM-VENDOR-SDK`는 `app/llm/`·`backend-kotlin/infrastructure/` 안의 어댑터를 제외). **이 목록 자체가 감사 대상이다** — 새 경로를 추가할 때는 그 파일이 정말 어댑터 경계인지 확인하고 근거를 주석에 남긴다.

**규칙이 구조적으로 못 보는 것**(실증 목록은 `docs/migration/_workspace/00_privacy-gate_scan-baseline.md`): 매칭이 **줄 단위**라 인자를 개행으로 나누면 전 규칙이 뚫린다(`provider.complete(\n  sourceText)`). 변수를 한 번 경유해도 놓치고, 동적 import(`__import__("openai")`)·산술 상태코드(`400 + 3`)도 못 본다. 그래서 스캔 0건은 "위반 없음"이 아니라 "이 표현형에서 안 걸림"이다. **Kotlin 본코드가 들어오는 Phase 3 시작 전에 최소한 `LLM-RAW-INPUT`·`LOG-BODY`·`PLAINTEXT-PERSIST`를 다중 줄 대응으로 올려야 한다** — 이 셋이 §5 Phase 7 즉시 중단 기준에 직접 걸리고, Kotlin의 여러 줄 호출 스타일에서 가장 먼저 무력화되기 때문이다. `CACHE-HEADER`는 성질이 달라 개선이 아니라 **교체**가 필요하다: 헤더가 붙은 줄을 세는 방식이라 엔드포인트가 몇 개든 적중이 상수이고, 찾아야 할 것은 헤더가 **없는** 응답이므로 라우트 목록과의 대조로만 판정된다(계약 테스트가 맡는 편이 맞다).

**스캔이 못 보는 것**을 기억하라. `toString()` 노출, 프레임워크 기본 로그, actuator 엔드포인트, 설정 파일의 로그 레벨, 파일 사이의 호출 관계 — 전부 정규식 밖이다. 스캔은 감사의 시작이지 전부가 아니다.

## 재호출 지침

`docs/migration/_workspace/`의 이전 감사 산출물을 먼저 전부 읽는다.

- **이전에 차단으로 판정한 항목이 해결되었다는 보고를 받으면 말이 아니라 실행 증거로 확인한다.** 수정 커밋을 읽는 것으로 끝내지 말고 검증 절차를 다시 돌린다.
- 이전에 "오탐"으로 넘긴 항목은 근거가 여전히 유효한지 본다. 코드가 바뀌면 오탐이 진짜 위반이 된다.
- 통과 기록은 그 시점 코드에 대한 것이다. 관련 파일이 바뀌었으면 다시 돈다.
- 새 불변식이 필요해졌으면(새 기능·새 저장 경로) 이 목록에 추가하고 왜 필요한지를 함께 적는다. 근거 없는 항목은 다음 사람이 지운다.
- 감사 결과는 이전 파일을 덮어쓰지 말고 Phase 표기를 붙여 누적한다. 언제부터 지켜졌는지가 배포 판단의 근거다.
