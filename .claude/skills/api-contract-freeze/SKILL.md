# API 계약 절차 (easy-doc v1)

## 0. 계약이 무엇인가 — 2026-08-12 개정

**요구사항이 요구하는 인터페이스**다. 현재 Python 구현의 스냅샷이 아니다.
초판은 "현재 Python 동작을 v1으로 동결한다"는 전제로 썼다. 그 전제가 사용자 결정으로
걷혔다 — **Python은 회귀가 잦아 Kotlin으로 옮기는 구현이지 기준이 아니고, 출력을
Python과 맞출 필요가 없다.** 명백히 잘못된 계약(상태 코드 오용, 실재하지 않는 값 예시,
요구사항 미충족)은 고치고 React도 그에 맞춰 고친다.

**그렇다고 아무나 아무 때나 바꿔도 되는 문서는 아니다.** 바꿀 수 있는 근거와 못 바꾸는
것의 기준은 §7과 `contracts/easy-doc-v1.yaml`의 `x-change-policy`에 있다. 계약이 여전히
계약인 이유는 하나다 — React가 의존하는 인터페이스이고, Kotlin 구현과 프런트 타입 생성이
같은 한 곳을 읽어야 두 쪽이 갈리지 않는다.

**여전히 유효한 원칙**: 계획 문서를 맹신하지 않고 **코드를 조사의 출발점으로 삼는다.**
계획 문서 §2.2는 의도를 적은 것이고 현재 실제 동작은 `app/api/*.py`·`app/main.py`에 있다.
달라진 것은 그다음이다 — 예전에는 코드가 이겼지만, 이제 코드는 **가장 신뢰도 높은 사실
진술**일 뿐이고 "그렇게 동작한다"가 "그래야 한다"는 아니다.

**이름에 'freeze'가 남아 있는 이유**: 정확하지 않은 이름이지만 두는 쪽이 싸다. 저장소
안에 이 이름을 가리키는 참조가 **38곳(17개 파일)** 있고, 다른 에이전트가 동시에 쓰는
문서·이미 작성된 리뷰·Kotlin 테스트 주석의 `api-contract-freeze §5` 같은 **고정 인용**이
섞여 있다. 일부만 고치면 "§2.7 해결 3"이라는 지시가 어디도 가리키지 않게 되고, 스킬은
이름으로 호출되므로 개명은 진행 중인 참조를 한꺼번에 끊는다. 대신 선택 신호인
frontmatter `description`과 이 §0을 개정했다. **이름은 역사이고 §0이 현재 규칙이다.**

## 1. 실제 엔드포인트 표 (2026-08-11 코드 확인)

FastAPI가 노출하는 경로는 **정확히 14개**다. 다만 그중 하나는 `/health`이므로
**제품 엔드포인트는 13개 + 헬스 체크 1개**다. 계획 §2.2의 "14개 HTTP 엔드포인트"는
`/health`를 포함해야만 맞는 수다. 계약 파일에도 `/health`를 포함시켜 14개를 유지한다.
확인 명령(§3)의 출력과 이 표가 다르면 코드가 바뀐 것이므로 표를 갱신하고 보고한다.

비고의 **`[no-store → §2.5]`는 표시(포인터)일 뿐 정의가 아니다.** 대상·사유는
**§2.5 한 곳에만** 적는다 — 이 표에 사유까지 옮겨 적었다가 두 곳이 갈린 전례가 있다
(#9·#12 누락). **두 곳이 갈리면 §2.5가 이긴다.**
표시가 붙은 **10개는 하한선이지 부착 범위가 아니다** — 2026-08-12 리더 판정으로 두 헤더는
**모든 응답**에 붙는다(§2.8 판정 9). 표시가 없는 행이라고 헤더가 없는 것이 아니다.
표시를 늘리거나 줄이지 않는다 — 이 열 자리는 필터가 무너졌을 때 먼저 깨져야 하는
고위험 경로의 목록이다.

## 2. 계약 항목 체크리스트

각 항목은 **테스트로 확인 가능한 형태**로 적었다. 계약 테스트가 없는 항목은 계약이 아니라
희망 사항이다. 그리고 §7의 근거 없이 이 목록을 고치는 것은 개선이 아니라 표류다.

### 2.1 상태 코드

- [ ] 가입 성공 = **201** (200 아님)
- [ ] 업로드 접수 = **202** (201 아님 — 변환은 아직 시작 전)
- [ ] 작업 공간 생성 = **201**
- [ ] 문서 삭제·작업 공간 삭제 = **204**, 본문 길이 0
- [ ] 입력 검증 실패 = **422** (Spring 기본값 400 아님)
- [ ] 지원하지 않는 파일 형식·추출 실패 = **422** (415 아님 — Content-Type이 아니라 본문 자체를 처리 못 하는 상황)
- [ ] 업로드 크기 초과 = **413** — *계획 §2.2 목록에 없는 코드다. 반드시 계약 파일에 넣는다*
- [ ] 이메일 중복·이름 중복·상태 충돌(완료 전 검수 저장, 비어 있지 않은/마지막 작업 공간 삭제) = **409**
- [ ] 인증 실패(헤더 누락·위조·만료·삭제된 계정 전부) = **401** + `WWW-Authenticate: Bearer`
- [ ] 남의 자원 접근 = **404** (403 아님 — 존재 사실 자체를 숨긴다)
- [ ] LLM·큐 장애 = **502**, 설정 미비·큐 미준비 = **503**, 저장소·미처리 예외 = **500**
  - 큐 관련 코드가 둘로 갈리므로 주의한다. **큐에 등록을 시도했다가 실패**하면 `QueueUnavailableError` → **502**(`app/services/documents.py`의 enqueue 실패 경로). **큐 의존성 자체가 배선되지 않았으면**(lifespan이 Redis에 붙지 못한 상태) `ConfigurationError` → **503**(`app/api/deps.py`의 큐 provider). 둘을 하나로 합치면 "일시적 장애라 재시도할 값어치가 있는가"라는 클라이언트 판단이 무너진다

### 2.2 오류 본문

- [ ] 본문 최상위 키는 항상 `detail` 하나
- [ ] 도메인 예외 → `detail`은 **문자열**(한국어 사용자 문구)
- [ ] 검증 실패(422) → `detail`은 **객체 배열** `[{loc: string[], msg: string, type: string}]`
- [ ] 검증 실패 응답에 **입력값이 없다**(`input`, `ctx` 키 금지). 비밀번호가 응답 본문과 액세스 로그에 남는 경로다
- [ ] 미매핑 도메인 예외 = 500 + `{"detail": "요청을 처리하지 못했습니다"}`
- [ ] 도메인 밖 예외 = 500 + `{"detail": "서버 오류가 발생했습니다"}`
- [ ] `Content-Type: application/json` (`application/problem+json` 아님)
- [ ] **"모든 오류 응답"은 경로를 가리지 않는다** (2026-08-12 명시, 정본은 계약 파일
      `x-error-body-universality`). 전역 예외 매퍼를 거친 응답만이 아니라 `sendError` →
      `/error` ERROR 디스패치 응답, 필터·보안 계층이 만든 응답, 컨테이너 생성 응답까지다.
      **실측으로 확인된 사각지대**: `sendError` 경로가 `{"timestamp","status","error","path"}`
      (Spring `BasicErrorController` 기본 본문)를 낸다 — `ProblemDetail`이 새는 것과 같은
      등급의 위반이다. 지금 안 드러나는 이유는 운영 코드가 `sendError`를 부르지 않아서일
      뿐이고, **Phase 3에서 인증 필터가 401을 `sendError`로 내는 순간 드러난다**

`detail`이 문자열과 배열의 union이라는 점이 계약의 핵심이다.
`frontend/src/api/client.ts`의 **`readErrorMessage`**가 두 분기를 나란히 두므로, 한쪽만
구현하면 화면에 폴백 문구만 나오고 진짜 사유가 사라진다.
(코드 위치는 함수 이름으로 찾는다 — 행 번호는 코드가 움직이면 곧 틀린 값이 된다.)

### 2.3 필드 이름·형식

- [ ] 모든 JSON 필드는 **snake_case** (`access_token`, `document_id`, `char_count`, `has_more`, `retention_expires_at`, `missing_placeholders`, `provider_name`, `input_tokens`, `failure_code`, `document_count`, `edited_text`, `reviewed_at`, `masked_items`, `source_format`, `workspace_id`, `expires_in`, `token_type`, `conversion_id`)
- [ ] 식별자는 UUID 문자열
- [ ] 시각은 ISO 8601 문자열
- [ ] 변환 상태는 `pending | processing | done | failed` 소문자 4개뿐 (DB CHECK 제약과 동일 집합)
- [ ] 내보내기 형식은 `docx | txt | hwpx` (`pdf`·구버전 `hwp` 없음)
- [ ] `source_format`은 `text | docx | pdf | hwpx` **enum**. 자유 문자열이 아니다 —
      붙여넣기는 상수 `"text"`, 파일은 `extract_text`가 지원 형식만 통과시킨 **뒤**
      확장자를 소문자화한 값이라 그 밖이 나올 경로가 없다
- [ ] **마스킹 범주는 `주민등록번호 | 카드번호` 2종뿐**이고 **값이 한국어**다.
      `"rrn"`·`"phone"` 같은 영문 코드가 아니다 — React `ReviewEditor`가 이 값을
      표에 그대로 렌더링하므로 값 자체가 화면 문구다.
      자리표시자는 `[[<범주><n>]]`이고 `n`은 **범주별** 1부터의 일련번호다.
      전화번호·이메일·계좌번호는 **가리지 않는다**(2026-08-12 사용자 결정): 공공기관
      안내문에는 담당 부서 연락처처럼 가려서는 안 되는 값이 본문에 들어가고, 그것을
      자리표시자로 바꾸면 안내문의 쓸모가 사라진다. 남기는 것은 고유식별정보와
      금융 식별자뿐이다

### 2.4 인증

- [ ] `Authorization: Bearer <token>`
- [ ] JWT 알고리즘 **HS256**
- [ ] 페이로드 클레임은 `sub`(사용자 UUID 문자열), `exp`, `typ` **세 개뿐**. 이메일 등 개인정보를 넣지 않는다
- [ ] `typ` 값은 `"access"` — 값이 다르면 거부
- [ ] `sub`/`exp`/`typ`가 **모두 있어야** 유효. `exp` 없는 토큰은 영구 자격증명이 되므로 필수
- [ ] 서명 키 최소 길이 32바이트(HS256 해시 출력 크기) 검사 유지
- [ ] 로그인 성공 시에만 Argon2 재해시. 기존 PHC 문자열은 그대로 검증 가능해야 한다
- [ ] Python 발급 토큰을 Kotlin이 읽고, Kotlin 발급 토큰을 Python이 읽는 **양방향** fixture

### 2.5 헤더

**계약 정본은 `contracts/easy-doc-v1.yaml`의 `x-global-response-headers`다.**
§1 표의 `[no-store → §2.5]` 표시는 이곳을 가리키는 포인터다.

- [ ] `Cache-Control: no-store` + `X-Content-Type-Options: nosniff` — **Kotlin 런타임의
      모든 응답**에 붙는다(2026-08-12 리더 판정, 근거 G4 — §2.8 판정 9).
      상태 코드·경로·핸들러 유무를 가리지 않는다. 성공·오류·204·`/health`·프리플라이트·
      컨테이너가 직접 만든 응답까지 전부다. 부착 수단은 **서블릿 필터 + Tomcat Engine
      밸브 2층**이며(2026-08-12 실측으로 필터 1층이 부족함이 확인됐다 — §5.2)
      엔드포인트별로 기억해야 하는 목록이 아니다. **밸브는 Tomcat 결합**이라 서블릿 표준
      필터만으로는 이 조항이 만족되지 않는다 — 계약 파일 `x-container-coupling`이 정본이다
- [ ] **아래 10곳은 하한선이지 범위가 아니다** — 필터가 무너져도 고위험 경로에서 먼저
      깨지게 하는 장치이므로 개별 단언을 **유지한다**:
      `GET /documents`, `GET /conversions/{id}`, `PUT /conversions/{id}`,
      `GET /conversions/{id}/export`, `GET /workspaces`, `POST /workspaces`,
      `PATCH /workspaces/{id}`, `POST /auth/signup`, `POST /auth/login`, `GET /auth/me`
      — 고른 규칙은 "개인정보·자격증명이 실리는 응답"이다. `POST /auth/login`은 Bearer
      토큰 자체를, 나머지 `/auth` 둘은 이메일을, 문서·작업 공간 응답은 사용자 콘텐츠를 싣는다
- [ ] **Python은 이 전역 요구를 만족하지 않는다 — 인정된 이탈이며 고치지 않는다**
      (리더 판정 부수 결정 2). Python은 위 10곳에만 붙인다. 기준선 확인:

      ```bash
      grep -rn "headers.update(PRIVATE_RESPONSE_HEADERS)\|\*\*PRIVATE_RESPONSE_HEADERS" app/api/ | wc -l
      # 10 (documents.py 4 · workspaces.py 3 · auth.py 3)
      ```

      관찰 기간에 두 런타임의 헤더가 다른 것은 **결함이 아니라 기록된 차이**다.
      parity 대조에서 불일치로 올리지 않는다
- [ ] **오류 응답에 헤더가 "없음"을 단언하던 종전 항목은 Kotlin에서 폐기됐다** — 부호가
      뒤집혀 **"있음"** 단언이 된다. Python `tests/api/test_errors.py`의 부정 단언은
      Python 기준선의 기술로서 **그대로 옳다**. 검증 체계 전체는 §5.1·§5.2에 있고,
      **컨테이너 레벨 응답 도달 여부는 2026-08-12 실측으로 확인됐다** — 필터 1층으로는
      7종이 비어 Tomcat Engine 밸브를 더했다(§5.2)
- [ ] `POST /documents` 202 응답에 **`Location: /conversions/{conversion_id}`**
- [ ] 내보내기 미디어 타입:
      docx → `application/vnd.openxmlformats-officedocument.wordprocessingml.document`,
      txt → `text/plain; charset=utf-8`(charset 필수 — 없으면 한글이 깨진다),
      hwpx → `application/hwp+zip`
- [ ] `Content-Disposition: attachment; filename="easy-read.<ext>"; filename*=UTF-8''<percent-encoded>`
      — ASCII 대체 이름과 RFC 5987 확장을 **둘 다** 보낸다. 헤더 값은 latin-1만 담을 수
      있어 한글 이름은 `filename*`에만 실린다. React `parseFilename`이
      `filename\*=UTF-8''` 부분만 읽는다
- [ ] CORS: `allow_origins` 설정값(기본 `http://localhost:5173`),
      `allow_credentials=false`, 메서드 `GET, POST, PUT, PATCH, DELETE`,
      요청 헤더 `Authorization, Content-Type`,
      **노출 헤더 `Content-Disposition, Location`**
- [ ] 노출 헤더가 빠지면 브라우저 JS가 파일명과 접수 주소를 읽지 못한다. 서버가 보내는
      것과 브라우저가 읽을 수 있는 것은 다른 문제이므로 **브라우저 컨텍스트에서** 확인한다

### 2.6 입력 상한

- [ ] 변환 대상 본문 **4,000자** 초과 → 422 (`MAX_CONVERTIBLE_CHARS`)
- [ ] 검수 수정본도 같은 4,000자 상한
- [ ] 업로드 파일 **10MB**(`10 * 1024 * 1024`) 초과 → **413**
- [ ] zip 컨테이너(docx·hwpx) 압축 해제 예산 = 업로드 상한의 5배. 초과 → 422
- [ ] 지원 확장자 `docx | pdf | hwpx`(대소문자 무시). 구버전 `doc`은 전용 안내 문구와 함께 422
- [ ] 텍스트 레이어 없는 PDF·암호화 PDF 거절
- [ ] 목록 `limit` 1~100, `offset` ≥ 0 — 범위 밖은 422

## 3. `contracts/easy-doc-v1.yaml` 작성 절차

FastAPI가 만드는 OpenAPI를 **초안**으로 쓰되 그대로 계약으로 삼지 않는다.
자동 생성물은 라우터 시그니처에서 유도할 수 있는 것만 담기 때문에,
§2 항목의 절반 이상이 빠져 있고(§3.2) **요구사항이 요구하지만 아직 구현되지 않은 것**
(예: `/health` 진단)은 원리상 담길 수 없다.

### 3.1 초안 추출

```bash
mkdir -p contracts docs/migration/_workspace
uv run python -c "
import yaml
from app.main import app
spec = app.openapi()
with open('docs/migration/_workspace/00_contract-keeper_openapi-fastapi.yaml','w',encoding='utf-8') as f:
    yaml.safe_dump(spec, f, allow_unicode=True, sort_keys=False)
rows = sorted((p, m.upper(), sorted(op['responses'])) for p, ops in spec['paths'].items() for m, op in ops.items())
print('count', len(rows))
for p, m, r in rows: print(f'{m:6} {p:40} {r}')
"
```

출력이 §1 표와 일치하는지 먼저 확인한다. **개수가 14가 아니면 표부터 갱신한다.**

### 3.2 자동 생성물에서 빠지는 것 — 수기로 채운다

실행해 확인한 결과, FastAPI OpenAPI에는 **200/201/202/204/422만** 선언되어 있다.
다음은 전부 손으로 채워야 한다.

- 401, 404, 409, 413, 502, 503 응답과 각 오류 본문 스키마
- 오류 `detail`의 문자열 / 배열 union
- 모든 응답 헤더: `Location`, `Cache-Control`, `X-Content-Type-Options`,
  `Content-Disposition`, `WWW-Authenticate`
- CORS 정책(OpenAPI가 표현하지 못하므로 `description` 또는 별도 섹션에 산문으로 기록)
- `POST /documents`의 multipart 스키마 — 라우터가 `Request`를 직접 읽어 파싱하므로
  (JSON과 multipart를 한 엔드포인트가 받기 때문) 자동 생성물에 요청 본문 스키마가 없다.
  `file`, `title`, `workspace_id` 파트를 손으로 적는다
- `status`·`source_format`·`category`의 enum 값 — 백엔드 Pydantic이 `str`로 선언해
  스키마에 `string`으로만 나온다. **계약 파일에서 enum으로 고정**한다
- 입력 상한(4,000자, 10MB)을 `description`과 제약으로 명시

### 3.3 작성 순서

1. 초안을 `docs/migration/_workspace/`에 뽑는다(계약 파일에 바로 덮어쓰지 않는다).
2. §1 표와 대조해 경로·메서드·성공 코드를 확정한다.
3. §2 체크리스트를 위에서부터 훑으며 빠진 항목을 채운다.
4. §2.7·§2.8의 판정을 반영하고, 근거를 해당 스키마의 `description`에 남긴다.
   **자동 생성물과 다른 조항은 근거 ID(G1~G4)를 함께 적는다** — 적지 않으면 다음 사람이
   그것을 오기로 보고 되돌린다.
5. `contracts/easy-doc-v1.yaml`로 저장한다. 이 파일이 이후 Kotlin API와 React 타입 생성의
   **단일 기준**이다.
6. 3자 대조(§4)를 돌려 보고서를 낸다.

## 4. 3자 대조 절차

목적은 "문서를 만드는 것"이 아니라 **세 곳의 진술이 어디서 갈리는지 찾는 것**이다.
갈리는 자리가 곧 잠재 버그이거나 개선 후보다.

| 축 | 무엇 | 성격 |
|---|---|---|
| ① | FastAPI OpenAPI 산출물 | 현재 Python 구현이 하는 일 (기계 생성) |
| ② | `contracts/easy-doc-v1.yaml` | **우리가 정한 약속** (수기, 정본) |
| ③ | `frontend/src/api/types.ts` + `client.ts` | 클라이언트가 믿고 있는 것 (수기) |

①은 **참고 자료이지 정답이 아니다.** 셋이 갈리면 ②가 이긴다 — 단, ②가 이기는 이유는
정본이어서이지 옳아서가 아니므로, 갈린 이유를 §7의 판정으로 남긴다.

절차:

1. ①에서 (경로, 메서드, 상태 코드, 응답 스키마 필드명·타입)을 뽑는다.
2. ②에서 같은 항목을, ③에서 인터페이스 필드와 `client.ts`의 실제 호출 경로·메서드·
   쿼리 파라미터를 뽑는다.
3. 아래 표 형식으로 **불일치만** 보고한다. 일치 항목을 나열하면 진짜 문제가 묻힌다.

```markdown
| 항목 | ① FastAPI | ② 계약 파일 | ③ React | 판정 | 조치 |
|---|---|---|---|---|---|
| ConversionResponse.status | string | enum 4값 | 리터럴 union 4값 | ①이 느슨함 | ②를 기준으로 Kotlin은 enum, ①은 절체 후 소멸 |
```

판정은 넷 중 하나다: **계약 파일이 틀렸다(고친다)** / **구현이 계약을 어겼다(차단)** /
**의도된 차이(사유 기록)** / **계약을 개선한다(§7의 근거 ID를 지목한다)**.
넷째가 §0 개정으로 새로 생겼다 — 예전에는 "v2 후보로 미룬다"였다.
"나중에 본다"는 여전히 판정이 아니다.

보고서는 `docs/migration/_workspace/00_contract-keeper_three-way-diff.md`에 남긴다.
**이미 알려진 3자 차이 21건은 그 파일에 있고**(D-1~D-21 + 계획-코드 P-1~P-3),
개정 이후의 재분류는 `docs/migration/_workspace/02_contract-rebase.md`에 있다.
대조를 돌리기 전에 둘 다 읽는다 — 거기 적힌 차이가 보고서에 다시 나오면 정상이다.
그중 **판정이 바뀌지 않는 대표 3건**만 여기 적어 둔다:
`DELETE /workspaces/{id}`와 `GET /health`는 React에 호출부가 없고(의도적 — 타입 생성
후에도 호출 래퍼를 만들지 않는다), `POST /documents`의 multipart 요청 본문은 자동
생성물에 없어 계약 파일이 유일한 기록이다.

## 5. contract test 작성 기준

계약 테스트는 **HTTP 경계에서** 돈다. 서비스 계층 단위 테스트로 대신할 수 없다 —
상태 코드 매핑, 헤더 부착, 직렬화 이름은 전부 경계에서 결정되기 때문이다.

계층별 역할:

| 계층 | 도구 | 검증 범위 |
|---|---|---|
| 계약(경계) | Python: FastAPI `TestClient` / Kotlin: `@SpringBootTest` + MockMvc | 상태 코드, **응답 헤더**, 오류 본문 모양, 필드 이름, enum 값 |
| 통합(DB) | Testcontainers PostgreSQL | 소유권 404, 409 충돌, 트랜잭션 원자성 |
| 브라우저 | compose + 실제 브라우저 | CORS 노출 헤더, 파일 다운로드 파일명, 401 세션 만료 |

**본문만 검증하면 안 되는 이유**: 이 API에서 깨지기 쉬운 것은 대부분 본문이 아니다.
`Location`이 빠지면 202 본문은 멀쩡한데 폴링 주소를 못 만들고, `Cache-Control: no-store`가
빠지면 **프록시가 개인정보를 캐시한다**(200 OK로 나타나는 보안 사고라 본문 검증으로는
절대 안 잡힌다). `filename*`이 빠지면 다운로드는 되고 파일명만 깨지며, CORS
`expose_headers`가 빠지면 서버 응답은 완전한데 브라우저 JS만 헤더를 못 읽는다.

따라서 **엔드포인트 하나당 최소한** ① 성공 경로(상태 코드 + 헤더 + 필드 이름),
② 인증 없음 401, ③ 남의 자원 404, ④ 대표 입력 오류 422를 둔다.
409·413이 있는 엔드포인트는 그것도 추가한다.

추가로 반드시 넣을 테스트:

- 검증 실패 응답 본문에 **제출한 비밀번호 문자열이 없음**을 단언한다. 회귀하면 즉시 잡힌다.
- 401 응답에 `WWW-Authenticate: Bearer`가 있음.
- 남의 자원 접근이 403이 **아님**을 단언한다(404여야 한다).
- Python 발급 JWT를 Kotlin이 수용하고 그 반대도 되는 양방향 fixture 테스트.
- **`GET /health`의 `status`가 `checks`와 일치**함을 단언한다 — 의존 서비스 하나를
  죽여 `degraded`가 나오고 **상태 코드는 200**임을 함께 본다(§2.8 판정 5).
- **`masked_items[].category`가 2종 밖의 값을 내지 않음**을 단언한다. 영문 코드(`rrn`)나
  사라진 범주(`전화번호`)가 나오면 즉시 실패한다(§2.3).
- **`source_format`이 `text|docx|pdf|hwpx` 밖의 값을 내지 않음**을 단언한다.

### 5.1 사적 응답 헤더 — 전역 부착의 검증 (2026-08-12 리더 판정)

**계약 정본은 `contracts/easy-doc-v1.yaml`의 `x-global-response-headers`다.** 여기에는
검증 방법만 적는다.

#### 내려간 것 — 옛 "규칙 1 + 단언 A·B" 기계장치

직전 판까지 이 절은 Phase 3 종료 조건으로 **규칙 1**(사적 헤더는 `ResponseEntity`로만
싣는다. 필터·인터셉터·`HttpServletResponse` 금지)과 그 **감시 단언 B**(같은 컨트롤러의
오류 경로에 헤더가 **없음**)를 요구했다. 리더 판정이 헤더를 전역으로 만들면서 규칙 1은
계약과 **정면으로 충돌**한다 — 이제 헤더를 붙이는 수단이 바로 그 금지 대상인 필터다.
단언 B는 부호가 뒤집혀 폐기된다(Kotlin 한정. Python 쪽은 아래 참조).

**그냥 지우지 않는 이유가 있다.** 옛 기계장치의 실질 문제는 설계가 틀렸다는 것이 아니라
**근거가 이 저장소에서 실측된 적이 없다**는 것이었다("Spring MVC는 `ResponseEntity`
헤더를 컨트롤러 정상 반환 이후에 기록한다" — API 문서 수준 확인). 전역 필터도 한동안
똑같은 상태였다. **검증되지 않은 기계장치를 검증되지 않은 필터로 바꾸는 것은 개선이 아니다.**
그래서 그 자리를 비워 두지 않고 **§5.2의 실측**이 대신했다.

**2026-08-12 그 실측이 끝났고, 이 경계심이 옳았음이 확인됐다** — "서블릿 필터 하나면
전역 요구가 만족된다"는 서술은 **틀렸다.** 파싱 단계에서 거절되는 응답 7종에 필터는
닿지 못했고, 목록 대조로는 그것이 보이지 않았으며, MockMvc는 오히려 **통과했다는 잘못된
근거**를 냈다. 강제 수단은 필터 + Tomcat Engine 밸브 **2층**으로 갱신됐다.

#### 무엇이 뒤집혔고 무엇이 그대로인가

| 대상 | 종전 | 지금 |
|---|---|---|
| 열거 10곳 성공 응답 | 두 헤더 **있음** | **그대로** — 삭제하지 않는다. 전역 규칙의 하한선 |
| 오류 응답(401·404·409·413·422·500·502·503) | 두 헤더 **없음** | **있음** — 부호가 뒤집혔다 |
| DELETE 204 · `GET /health` | 없음 | **있음** |
| 컨테이너가 직접 만든 응답 | 논의 대상 아니었음 | **있음 — 2026-08-12 실측 확인.** 필터로는 7종에 못 닿아 Tomcat Engine 밸브를 더했다 (§5.2) |
| Python `tests/api/test_errors.py`의 부정 단언 | 옳음 | **여전히 옳다** — Python은 고치지 않기로 판정됐다. 두 런타임의 헤더 차이는 결함이 아니라 **기록된 차이**이며 parity 불일치로 올리지 않는다 |

#### 체크 항목 — Kotlin

- [ ] **G-A 하한선(유지)**: §2.5의 성공 응답 **10곳 각각**에 두 헤더가 있음을 MockMvc로
      단언한다. 전역 필터가 있어도 **지우지 않는다** — 필터가 제거되거나 체인 순서가
      어긋났을 때 고위험 경로에서 **먼저** 깨지게 하는 장치다(리더 판정 부수 결정 1)
- [ ] **G-B 오류 응답(부호 반전)**: 실제 엔드포인트가 내는 401·404·409·413·422·500에
      두 헤더가 **있음**을 단언한다. 종전의 "없음" 단언을 **지우는 것으로 끝내지 말고**
      반대 단언으로 바꾼다 — 지우기만 하면 그 자리에 아무 검사도 남지 않는다
- [ ] **G-C 본문 없는 응답**: `DELETE /documents/{id}` 204, `DELETE /workspaces/{id}` 204,
      `GET /health` 200
- [ ] **G-D 값 정확성과 중복 부착 부재**: 값이 정확히 `no-store` / `nosniff`이고
      **헤더가 하나씩만** 있음을 단언한다. 필터와 컨트롤러 `ResponseEntity`가 같은 헤더를
      **둘 다** 실으면 `Cache-Control: no-store, no-store`가 나가 `const` 제약에 위반된다.

      뒤 이 단언이 더 중요해졌다** — 필터·밸브·`ResponseEntity` 셋이 겹치는 구간이 생겼다
- [ ] **G-E 컨테이너 레벨 응답**: §5.2 — **2026-08-12 실측 완료.** 필터 1층으로는 파싱 단계
      거절 7종에 못 닿고, Tomcat Engine 밸브가 그 자리를 덮는다. 회귀 테스트는 원시 소켓으로
      유지한다 — **MockMvc로 다시 쓰면 근거가 사라진다**
- [ ] **G-G 밸브 음성 대조**: 밸브를 제거하면 malformed 계열 3건이 **정확히** 깨지는지
      확인한다. 음성 대조가 없으면 "밸브가 없어도 통과하는 테스트"를 근거로 삼게 된다
- [ ] **G-F CORS 프리플라이트**: `OPTIONS` 응답에도 두 헤더가 붙는지 확인한다.
      스펙에 오퍼레이션이 없어 계약 파일로는 표현되지 않는 자리다(계약 파일
      `x-openapi-expressibility` ④)

### 5.2 강제 수단이 어디까지 닿는가 — 2026-08-12 실측 완료

**종전 이 절은 "Phase 3 미실측 항목"이었다. 실측이 끝났으므로 결과 표로 바꾼다.**
계약 정본은 `x-global-response-headers.x-phase3-measurement`이며 여기에는 방법과
회귀 유지 조건만 적는다.

판정의 핵심 귀결은 실패 양상이 바뀐다는 것이었다 — 위험이 "누가 한 자리를 빠뜨렸는가"에서
**"강제 수단이 그 응답까지 닿는가"**로 옮겨간다. 전자는 목록 대조로 잡히고 후자는
**실행해야만** 잡힌다. **재 보니 실제로 비어 있었다** — 그것이 이 절의 값어치다.

#### 측정 방법 (회귀 테스트도 같은 방법을 유지한다)

`@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제 포트를 열고 **원시 소켓**으로
요청을 보내 응답 바이트를 그대로 읽었다(Tomcat 11.0.22 / Boot 4.1.0).

- **MockMvc로는 이 항목을 측정할 수 없다.** 서블릿 컨테이너를 띄우지 않아 컨테이너가
  필터 앞·바깥에서 만드는 응답을 재현하지 못하는데, 그런데도 **측정한 것처럼 보이는
  통과**가 나온다. 통과했다는 사실이 근거가 되지 않는 종류의 측정이다 —
  이 테스트를 MockMvc로 옮기는 것은 검증이 아니라 검증의 외양이다.
- malformed 요청은 HTTP 클라이언트 라이브러리가 교정해 버리므로 원시 소켓이 필요하다.

#### 결과 — 필터 1층으로는 부족했다

| 도달 여부 | 응답 | 비고 |
|---|---|---|
| **필터에 닿음** | 핸들러 없는 404 · 415 · 413 · CORS 프리플라이트 OPTIONS 200 · `sendError` → `/error` ERROR 디스패치 503 | 서블릿에 매핑되므로 체인이 돈다 |
| **필터에 못 닿음** | 요청 대상 금지 문자 400 · 콜론 없는 헤더 줄 400 · 요청 줄 파손 400 · 헤더 상한 초과 400 · `Host` 없음 400 · 알 수 없는 HTTP 버전 505 · 알 수 없는 메서드 405 | 요청 줄·헤더 블록 **파싱 단계**에서 거절돼 서블릿에 매핑되지 않는다. **필터 체인이 시작조차 하지 않으므로 배치를 어떻게 고쳐도 닿지 않는다** |

**해결 — 계약을 좁히지 않고 강제 수단을 넓혔다.** Tomcat Engine 밸브
(`PrivateResponseHeadersValve`)가 위 7종 **전부**를 덮는 것을 계측으로 확인하고 구현했다.
순서 ①(닿게 만든다)에서 끝나 리더 재심(순서 ②)은 필요하지 않았다.
**음성 대조도 돌렸다** — 밸브를 빼면 malformed 계열 3건만 정확히 깨진다.

**밸브는 Tomcat 결합이다.** 계획 §3.1이 내장 Tomcat을 고정했으므로 감수 범위지만,
"서블릿 표준 필터면 이 조항이 만족된다"고 읽으면 오독이다. 컨테이너를 바꾸면 **기동
시점에 깨진다(조용히 사라지지 않는다)** — 계약 파일 `x-container-coupling`이 정본이다.

#### 기각된 가설 — 후보를 사실로 적지 않았던 것이 값어치를 했다

종전 이 절은 미도달의 **후보 원인** 셋을 "이 저장소에서 확인된 바 없다"고 단서를 달아
적었다. 그중 ⓐ `OncePerRequestFilter.shouldNotFilterErrorDispatch()`는 **기각됐다** —
그 오버라이드와 `DispatcherType.ERROR` 등록을 **둘 다 기본값으로 되돌려도** 헤더가 남는다.
필터가 `chain.doFilter` **앞에서** 헤더를 쓰고 Tomcat이 포워딩에서 버퍼만 비우기 때문이다.

후보를 사실로 적었다면 기각을 기록할 자리가 없었고, 틀린 원인 설명이 계약에 굳었을 것이다.
**앞으로도 미확인 가설에는 단서를 단다.**

#### 남은 것

이 실측이 다룬 것은 **두 헤더의 유무**뿐이다. 같은 7종 응답의 **본문 모양**은 아직
측정되지 않았다 — §5.3의 E-4가 그 자리다.

### 5.3 오류 본문이 경로를 가리지 않는지 — 신규 (2026-08-12)

계약 정본은 `x-error-body-universality`다. 여기에는 검증 항목만 적는다.
**H-1 실측의 범위 밖 부수 발견**에서 나왔다 — `sendError` → `/error` 응답이
`{"timestamp","status","error","path"}`(Spring `BasicErrorController` 기본 본문)를 낸다.

- [ ] **E-1 `sendError` 경로**: 그렇게 만들어진 응답의 본문이 `{"detail": …}`이고 최상위
      키 집합이 **정확히 `{detail}` 하나**다. `timestamp`·`status`·`error`·`path`·`trace`·
      `message`·`errors`가 **없음**을 명시적으로 단언한다 — `detail`이 있는지만 보면
      나머지 넷이 함께 실려도 통과한다.
      측정은 `RANDOM_PORT`로 한다. **MockMvc가 `/error` ERROR 디스패치를 재현하는지는 이
      저장소에서 확인된 바 없으므로**, 확인 없이 MockMvc로 쓰면 §5.2에서 겪은 "측정한 것처럼
      보이는 통과"를 반복한다
- [ ] **E-2 인증 실패 401**: **어떤 구현 수단으로 나가든** 본문이 `{"detail": …}`이고
      `WWW-Authenticate: Bearer`가 붙는다. **Phase 3에서 인증 필터가 401을 `sendError`로
      내는 것이 가장 흔한 구현**이므로, 이 단언은 인증 필터를 도입하는 커밋과 **같은
      변경 단위**에 넣는다. 나중에 넣으면 그사이에 계약이 깨진 채로 지나간다
- [ ] **E-3 `Content-Type`**: 오류 응답이 `application/json`이다 (`text/html`도
      `application/problem+json`도 아니다). 기존 X-C4를 `/error`·컨테이너 경로로 확장한다
- [ ] **E-4 컨테이너 생성 응답의 본문 — 미측정**: §5.2의 7종이 어떤 본문을 내는지 보지
      않았다. **"충족"으로도 "위반"으로도 적지 않는다.** 측정 결과 만족시킬 수 없는 자리가
      남으면 계약을 좁히지 말고 목록·실측 근거와 함께 리더에게 올린다
      (`x-change-policy.escalate_to_leader` 1번) — 헤더 쪽에서 밟은 순서와 같다

**계약이 정하는 것은 나간 바이트뿐이다.** `sendError`를 안 쓸지, `/error` 응답을 계약
모양으로 바꿀지, 오류 속성을 다시 쓸지는 `kotlin-implementer`의 구현 판단이다.

---

계약 테스트는 **Kotlin 쪽이 정본**이다. Python suite는 계약을 코드로 적어 둔 참고 자료이고
비교 기준이 아니다 — 계약이 Python과 의도적으로 다른 조항(미처리 500의 CORS 헤더,
`/health` 진단, 마스킹 2종, **사적 헤더 전역 부착**)에서는 **Python이 테스트를 통과하지
못하는 것이 정상**이다.
그런 조항은 §2.7·§2.8에 판정으로 적혀 있어야 하고, 적혀 있지 않은 차이는 여전히 결함이다.

## 6. React 타입 교체 절차 (Phase 6)

1. `contracts/easy-doc-v1.yaml`에서 TypeScript 타입을 생성해 `frontend/src/api/types.ts`를
   **대체**한다. 수기 타입을 유지하면 계약이 바뀔 때마다 손으로 따라가야 한다.
2. 생성 전 `status`·`format`·`source_format`·`category`가 계약 파일에서 enum으로
   고정돼 있는지 확인한다. `string`으로 두면 생성 타입이 넓어져 **현재 React보다 타입
   안전성이 떨어진다** — 교체가 퇴보가 되면 안 된다.
3. **`client.ts`는 유지한다.** 계약에서 생성할 수 없는 클라이언트 정책이 들어 있다 —
   토큰 부착·폐기, **인증된 호출에서만** 401을 세션 만료로 보는 분기(로그인 실패 401은
   아니다), 네트워크 오류를 `status = 0`으로 정규화, `detail` union을 한국어로 바꾸는
   `readErrorMessage`, FormData일 때 `Content-Type`을 **손대지 않는 것**(boundary가 빠지면
   서버가 못 읽는다), `downloadExport`의 blob 처리와 `filename*=UTF-8''` 파싱.
   생성기는 이 중 어느 것도 만들어 주지 않는다. 타입만 갈아끼우고 정책은 그대로 둔다.
4. 교체 후 `ExportFormat`처럼 `client.ts`가 import하던 타입 이름이 생성 타입에서 다르면,
   **`client.ts`를 고치기보다 얇은 재수출 모듈을 두는 쪽**을 먼저 검토한다.
5. **계약 개선이 만든 React 부채를 함께 갚는다.** 계약이 Python 스냅샷이 아니게 되면서
   프런트 픽스처가 계약과 어긋나는 자리가 생겼다 — 확인된 것은
   `frontend/src/test/factories.ts`의 `category: 'phone'`(어떤 구현에서도 나오지 않는
   허구 값)과 사라진 마스킹 범주를 쓰는 `ReviewEditor.test.tsx` 픽스처다. 런타임 코드는
   깨지지 않지만 **틀린 예시가 테스트에 굳어 있는 것**이므로 교체와 같은 단위에서 고친다.
6. Kotlin 오류 문구가 현재 한국어 사용자 메시지와 같은지 확인한다(계획 §4.1). 문구가
   바뀌면 화면 텍스트가 바뀌고, React 테스트가 문구를 단언하고 있으면 함께 깨진다.
7. `npm run` 기준의 타입 검사·린트·테스트·프로덕션 빌드가 모두 통과해야 교체 완료다.
   기존 React 테스트(60개 기준선)가 줄면 안 된다.

## 7. 계약 개선 판정 절차

계약은 개선 대상이지 동결물이 아니다(§0). 그래도 **아무나 아무 때나 바꾸면 계약이
아니게 되므로**, 바꿀 수 있는 근거와 못 바꾸는 것을 아래로 고정한다.
정본은 `contracts/easy-doc-v1.yaml`의 `x-change-policy`이고, 이 절은 그 요약이다.

### 7.1 바꿀 수 있는 근거 — 넷 중 하나를 지목해야 변경이 성립한다

| ID | 근거 | 판별 질문 |
|---|---|---|
| **G1** | 계약이 사실과 다르다 | 스펙에 적힌 값이 **어떤 구현에서도** 나오지 않는가? (허구 예시, 잘못 옮긴 상태 코드) |
| **G2** | 요구사항이 그것을 요구한다 | 어느 요구사항인지 지목할 수 있는가? |
| **G3** | 정책 결정이 바뀌었다 | 사용자·리더가 정한 것인가? (계약 소유자가 정책을 만들지는 않는다) |
| **G4** | 조항이 지킬 수 없거나 지켜지지 않는 형태다 | 물리적으로 불가능하거나, **이미 두 번 이상 누락된 이력**이 있는가? |

**근거가 아닌 것**: "Kotlin에서 이렇게 하는 게 자연스러워서", "이게 더 낫다", "정책 일관성"
(규칙을 지목하지 못하면 인상이다). G4는 결과만 바꾸지 말고 **강제 수단**을 함께 바꾼다.

### 7.2 못 바꾸는 것

계약 소유자가 단독으로 좁힐 수 없는 불변식 — 깨지면 사용자 데이터가 샌다.
소유권 은닉 404(403 금지) · 오류 본문 최상위 `detail` 하나 · 422 입력값 에코 금지 ·
snake_case · JWT 페이로드에 개인정보 금지 · **모든 응답의 `no-store` + `nosniff`**
(2026-08-12 전역 확대, §2.8 판정 9 — 고위험 10곳은 좁힐 수 없는 하한선) · 인증 실패 응답의
균일성. 넓히는 방향은 금지가 아니라 리더 승인 사항이다.

**리더에게 올릴 것**: ① 리더가 이미 명시적으로 판정한 조항을 뒤집는 변경 — **전제가
바뀌었더라도** 단독으로 뒤집지 않고 재심을 요청한다(OQ-1이 이 경로를 밟았고
2026-08-12 리더 판정으로 종결됐다 — §2.8 판정 9가 그 선례다),
② React **런타임 코드**가 이미 의존하는 동작의 변경(테스트·타입만 닿으면 제외),
③ 불변식 축소, ④ 배포·운영 동작이 달라지는 변경(헬스 체크 상태 코드 등).

### 7.3 절차

1. 근거를 G1~G4로 지목한다. 못 하면 바꾸지 않는다.
2. **React 영향을 먼저 확인한다** — `types.ts`·`client.ts`·컴포넌트를 읽고 무엇이 깨지는지
   적는다. "아마 괜찮다"는 확인이 아니다. 런타임 코드가 깨지면 계약·백엔드·프런트를 같은
   변경 단위로 묶는다.
3. 파괴성을 판정한다. 필드·헤더·상태 코드 **추가**는 대개 비파괴, 제거·이름 변경·타입
   축소·enum 값 제거는 파괴다. **응답** 필드의 enum 축소는 소비자 쪽에서는 비파괴다(더
   좁은 값만 받는다) — 다만 그 값을 쓰던 화면이 있으면 파괴다.
4. 계약과 contract test를 **같은 변경 단위**에서 고친다. 스펙만 바뀌면 두 기준이 충돌한다.
5. `x-changelog` + `00_contract-keeper_changelog.md`에 조항·근거 ID·영향 테스트·통보
   대상을 남기고, `kotlin-implementer`·`parity-verifier`에 통보한다.

### 7.4 parity와의 관계 — 달라진 부분

**parity 불일치는 더 이상 자동으로 차단 사유가 아니다.** 계약이 Python과 의도적으로 다른
조항에서는 **Kotlin이 계약을 따르는 것이 옳고**, parity 하네스는 그 차이를 "의도된 차이"로
기록한다. 계약이 아무 말도 하지 않는 자리에서 값이 갈리면 종전대로 차단이며, 어느 쪽인지
판정하는 권한은 계약 소유자에게 있다.

### 7.5 기록 위치

계약 변경은 `contracts/easy-doc-v1.yaml`에 반영하고 해당 스키마 `description`에 근거를 한
문장 남긴다. 판정 근거와 대안 비교는
`docs/migration/_workspace/{phase}_contract-keeper_{주제}.md`에, 계획 문서와 어긋나는
결정은 계획 문서 갱신 **제안**으로 남긴다(프로젝트 Definition of Done).
**파괴적 변경**이면 `easy-doc-v2.yaml`을 새로 만들고 v1을 남긴다 — 같은 파일을 덮어쓰면
"무엇이 v1이었는지"를 잃어 롤백 판단이 불가능해진다. 비파괴 변경은 `info.version` minor를 올린다.
