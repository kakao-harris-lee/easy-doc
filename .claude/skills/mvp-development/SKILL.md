# MVP Development

현재 코드에서 사용자가 요청한 MVP 기능을 가장 작은 완결 단위로 구현한다.

## 기준 문서

- 제품 범위와 정책: `docs/master-plan.md`
- 미구현 기능과 우선순위: `docs/kotlin-redevelopment-backlog.md`
- 외부 API: `contracts/easy-doc-v1.yaml`
- 실제 상태: 현재 코드와 테스트

관련 부분만 읽는다. 모든 계획과 과거 기록을 선행 조건으로 만들지 않는다.

## 작업 흐름

1. 요청이 MVP 범위인지 확인하고 관련 코드와 테스트를 찾는다.
2. 기존 구현에서 재사용할 경계와 이번 작업의 완료 조건을 정한다.
3. 의존성 선택, 보안 API, 버전별 프레임워크 동작이 불확실할 때만 공식 문서를 조사한다.
4. 요청 범위의 코드와 테스트를 함께 구현한다.
5. 변경한 모듈의 검증을 실행하고, 필요할 때 backend·frontend 전체 검증으로 넓힌다.
6. 구현한 범위와 아직 남은 backlog를 분리해 보고한다.

작은 기능에 별도 계획 문서를 강제하지 않는다. 여러 모듈의 계약·데이터·배포 구조를 함께 바꾸거나 사용자가 계획을 요청한 경우에만 `docs/plans/YYYY-MM-DD-*.md`를 작성한다.

## 범위 경계

- 사용자 요청 없이 인접 backlog를 함께 구현하지 않는다.
- 현재 미완성 상태를 숨기기 위한 stub, 가짜 성공 응답, 테스트 완화는 만들지 않는다.
- API 계약을 바꿀 때만 `api-contract` 스킬을 함께 사용한다.
- Kotlin/Spring Boot 코드를 바꿀 때만 `kotlin-spring-conventions` 스킬을 함께 사용한다.
- 외부 서비스 호출, 실제 LLM 비용, 배포, push는 별도 승인 범위다.

## 완료 조건

- 요청한 사용자 흐름 또는 기술 단위가 실제 코드로 동작한다.
- 성공·실패·권한 경계 중 변경과 관련된 경로가 테스트된다.
- 관련 검증 결과가 보고된다.
- 범위 밖 미구현 기능은 그대로 남고 명확히 구분된다.
