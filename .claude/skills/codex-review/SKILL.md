# codex-review

## 1. 이 스킬이 있는 이유

Claude가 작성한 Kotlin 코드를 Claude가 리뷰하면 **같은 맹점을 공유한다.** Python 원본을 Kotlin으로 옮길 때 오해한 지점이 있으면, 옮긴 쪽과 리뷰하는 쪽이 같은 오해를 그대로 반복해 "일관되게 틀린" 결과를 통과시킨다. 마이그레이션에서 가장 위험한 결함은 컴파일 오류가 아니라 *양쪽 다 그럴듯해 보이는 동작 차이*이므로, 이 맹점 공유가 곧 parity 사고다.

codex는 다른 모델 계열이고 이 저장소의 대화 맥락을 공유하지 않는다. 그래서 우리가 당연하게 여긴 전제를 당연하게 여기지 않고, 우리가 이미 "확인했다"고 믿는 코드를 처음 보는 눈으로 읽는다. **이 독립성이 이 스킬의 가치 전부다.**

따라서 다음을 지킨다.

- **codex 출력을 요약해서 대체하지 않는다.** 원문 지적을 그대로 인용해 산출물에 남기고, 요약은 별도 줄에 덧붙인다. 요약하는 순간 Claude의 판단이 codex의 관점을 덮어써서 독립성이 사라진다.
- **codex 지적을 "우리가 이미 알아서 처리했다"로 조용히 기각하지 않는다.** 기각하려면 반박 근거(파일·라인·테스트)를 산출물에 적는다. 근거 없는 기각은 리뷰를 받지 않은 것과 같다.
- **codex가 틀렸다고 판단해도 지적 자체는 삭제하지 않는다.** "codex 지적 / Claude 반박 / 근거"를 병기하고 판단은 사용자에게 넘긴다. codex가 맥락을 몰라 틀린 경우와, 우리가 맥락에 취해 틀린 경우는 겉보기에 똑같이 생겼다.

## 2. 운용 정책

### 2.1 필수 게이트

**Kotlin 변경 단위가 끝날 때마다 codex 독립 리뷰를 돌린다.** "변경 단위"는 커밋 직전, 또는 계획 문서 §5의 Phase 종료 조건을 판정하기 직전이다. 게이트를 통과하지 못한 변경은 Phase 종료로 보고하지 않는다.

게이트는 **3단계**로 돈다. 병렬 호출 한 번으로는 닫히지 않는다.

1. **병렬·독립 실행** — `migration-reviewer`(Claude, 저장소 맥락과 계획 문서를 아는 리뷰)와 `codex-reviewer`(이 스킬로 codex를 호출하는 맥락 없는 독립 리뷰)를 같은 메시지에서 동시에 띄운다. 서로의 결론을 보지 못하게 한다.
2. **완료 확인** — 두 산출물이 실제 파일로 존재하는지 확인한다.
3. **교차 대조 종합 (§5)** — `migration-reviewer`를 **재호출**해 두 산출물을 한 표로 합치고 `..._cross.md`로 제출한다.

`migration-reviewer`가 한 게이트에서 **2회 호출**된다는 뜻이다 — 1회차는 자기 독립 리뷰, 2회차는 종합 전용. 1회차와 3단계를 한 호출로 합치면 시작 시점에 codex 산출물이 아직 없어 매번 "codex 리뷰 없음"으로 종결되고, 필수 게이트가 형식만 남는다. **2차 호출에서는 새 지적을 만들지 않고 대조만 한다** — 그때 새로 나온 지적은 교차 검증을 받지 않은 채 정본에 실리기 때문이다. 새로 발견한 것은 별건으로 다음 게이트에 올린다.

두 리뷰가 **상충하면 어느 쪽도 지우지 않는다.** 양쪽 근거를 병기하고 `상충` 표시를 단 뒤 사용자 판단을 요청한다. 마이그레이션에서 상충은 대개 "무엇이 원래 동작인지"에 대한 불일치이고, 그건 코드가 아니라 Python 원본을 실행해 봐야 결론이 나기 때문이다.

### 2.2 리뷰를 건너뛸 수 있는 예외

게이트가 형식화되면 아무도 결과를 읽지 않으므로, 다음만 명시적으로 면제한다.

| 면제 | 조건 |
|---|---|
| 문서만 수정 | `docs/**`, `*.md`, `README` 등 실행 코드가 하나도 바뀌지 않은 변경 |
| 주석·오타 | 코드 파일이라도 주석·문자열 오타 수정이고 동작에 영향이 없음이 diff로 자명한 경우 |
| 포매팅 전용 | ktlint/detekt/prettier 자동 포매팅 결과만 담긴 커밋 |
| 산출물 파일 | `docs/migration/_workspace/**` 리뷰·분석 산출물 추가 |

**면제되지 않는 것** (예외처럼 보여도 반드시 리뷰한다):

- 테스트 코드만 바꾼 변경 — 테스트가 보장 범위를 좁히는 방향으로 바뀌는 사고가 여기서 난다
- 의존성 버전·Gradle 설정 변경 — 계획 문서 §3.1이 버전 조합 고정을 요구한다
- 로그 문구 변경 — 평문 유출은 로그 한 줄에서 시작한다
- 설정값·프로퍼티 기본값 변경 — 상한(4,000자, 10MB)과 보존 정책이 여기 산다

## 3. 실행 절차

### 3.1 스크립트로 실행한다

```bash
.claude/skills/codex-review/scripts/codex-review.sh <review|adversarial> [--base <ref>] [--scope <auto|working-tree|branch>] [--json] [--dry-run] [focus text...]
```

헬퍼 경로를 **직접 쓰지 마라.** codex 플러그인 헬퍼는 `~/.claude/plugins/cache/openai-codex/codex/<버전>/scripts/codex-companion.mjs`에 있고 경로에 버전이 박혀 있다. 하드코딩하면 플러그인이 올라가는 순간 리뷰 게이트가 조용히 깨지고, 게이트가 깨진 줄 모른 채 Phase가 통과된다. 스크립트는 매 실행마다 다음 순서로 탐색한다.

1. `$CODEX_COMPANION` 환경변수 (비표준 위치 수동 지정용)
2. `~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs` 중 **버전 내림차순으로 실제 파일이 있는 최신 버전**
3. `~/.claude/plugins/marketplaces/openai-codex/plugins/codex/scripts/codex-companion.mjs` (마켓플레이스 원본)
4. 헬퍼가 전혀 없으면 `codex` CLI 직접 호출 (`codex review [PROMPT] --uncommitted | --base <ref>`)
5. 넷 다 실패하면 확인 절차를 출력하고 exit 3

`CLAUDE_CONFIG_DIR`이 설정돼 있으면 그것을 `~/.claude` 대신 쓴다.

먼저 `--dry-run`으로 어떤 헬퍼가 잡히고 어떤 명령이 나가는지 확인하는 습관을 들여라. 리뷰 한 번은 수 분과 토큰 비용이 들고, scope를 잘못 잡으면 엉뚱한 diff를 리뷰하고 그 결과를 통과 근거로 삼게 된다.

### 3.2 `review`와 `adversarial` 선택

| 모드 | 언제 | focus text |
|---|---|---|
| `review` | 일반 변경. 리팩터링, 배선, 설정, 테스트 보강 | **불가** — 헬퍼가 거부한다 |
| `adversarial` | parity·보안·계약 위험이 있는 변경 | 필수. focus 없는 adversarial은 review의 열화판이다 |

`review`는 codex 내장 리뷰어에 그대로 매핑되므로 커스텀 지시를 받지 않는다. 스크립트가 focus text와 함께 온 `review`를 먼저 막는 이유다 (헬퍼까지 갔다가 실패하면 job만 남고 시간을 버린다).

**`adversarial`을 반드시 쓰는 변경 영역:**

- 암호화·복호화 (`fernet`, `encryption_scheme`, `key_version`) — 계획 §4.3, 실패 시 기존 문서를 못 읽는다
- 마스킹 파이프라인 — 계획 §2.3, CLAUDE.md의 보안 불변식
- 인증·인가 (Argon2, JWT, 소유권 404) — 계획 §2.2, §5 Phase 7 즉시 중단 기준
- 문서 파서·내보내기 (docx/pdf/hwpx, ZIP/XML) — 계획 §4.5, zip bomb·DTD 차단이 걸려 있다
- 작업 큐·worker (lease, retry, 보존 파기) — 계획 §4.4, 유실·이중 완료가 여기서 난다
- LLM provider 어댑터 — 계획 §4.6, 최대 2회 호출 계약

이 영역은 "동작하는지"가 아니라 "**틀렸을 때 무엇이 새는지**"를 물어야 하고, 그런 질문은 적대적 리뷰 프롬프트가 훨씬 잘 만든다.

### 3.3 `--scope`와 `--base`

- `--base <ref>`를 주면 **scope는 무시되고** `<ref>` 대비 branch diff를 리뷰한다.
- `--scope working-tree` — 아직 커밋하지 않은 변경. 커밋 직전 게이트의 기본값.
- `--scope branch` — 기본 브랜치 대비 누적 diff. base를 안 주면 헬퍼가 기본 브랜치를 탐지한다.
- `--scope auto`(기본) — 작업 트리가 더러우면 working-tree, 깨끗하면 기본 브랜치 대비 branch.

선택 기준:

| 상황 | 선택 | 이유 |
|---|---|---|
| 커밋 전 마지막 점검 | `--scope working-tree` | 지금 커밋될 것만 본다 |
| Phase 종료 판정 | `--base main` | Phase 전체 누적 변경을 한 번에 본다. 커밋별로 쪼개 보면 커밋 사이에 생긴 모순을 못 잡는다 |
| 여러 Phase가 브랜치에 쌓임 | `--base <Phase 시작 커밋>` | 기본 브랜치 대비는 너무 커져 리뷰 품질이 떨어진다 |
| 잘 모르겠다 | `--dry-run`으로 확인 | auto가 무엇을 고를지 추측하지 마라 |

### 3.4 실행 시간과 결과 회수

**리뷰는 동기 실행이다.** 헬퍼 usage에 `--wait|--background`가 보이지만, `review`/`adversarial-review`에서는 파싱만 되고 실제로 쓰이지 않는다(`--background`는 `task`, `--wait`는 `status`에서만 동작). 그러니 스크립트에 그 플래그를 넘기지 말고, Claude Code 쪽에서 실행을 제어하라.

- Bash 도구 `timeout`을 넉넉히 준다 (기본 120000ms로는 잘린다. `600000` 권장).
- 리뷰 중 다른 작업을 진행하려면 Bash 도구의 `run_in_background`로 띄우고 나중에 회수한다.

리뷰 실행은 job으로 기록되므로 사후 재조회가 된다. 결과를 잃어버렸거나 백그라운드 출력이 잘렸으면 **다시 돌리지 말고** 회수하라 (재실행은 비용이 두 배다).

```bash
node <헬퍼경로> status --all          # job 목록과 id
node <헬퍼경로> result <job-id>       # 해당 job의 전체 결과
node <헬퍼경로> cancel <job-id>       # 잘못 띄운 job 정리
```

헬퍼 경로는 `codex-review.sh ... --dry-run`이 출력하는 경로를 그대로 쓴다.

### 3.5 focus text 작성법

codex는 이 프로젝트의 계약도, 계획 문서도, Python 원본의 의도도 모른다. 그 공백을 focus text로 메우지 않으면 codex는 일반적인 Kotlin 코드 리뷰(널 안전성, 예외 처리)만 하고 돌아온다. **focus text는 "우리 계약을 codex에 주입하는 통로"다.**

작성 규칙:

1. **불변식을 단정문으로 준다.** "확인해 달라"가 아니라 "이것이 지켜져야 한다"로 쓴다. 판정 기준이 명확해야 위반을 찾는다.
2. **Python 원본 파일 경로를 같이 준다.** codex는 저장소를 읽을 수 있으므로 비교 대상을 지목하면 실제로 대조한다.
3. **위반 시 결과를 적는다.** "실패하면 기존 문서를 복호화할 수 없다" 같은 문장이 심각도 판단을 바꾼다.
4. **한 번에 3~5개 축까지만.** 열 개를 넣으면 전부 얕게 본다.

바로 쓸 수 있는 예시:

```
"이 변경은 Python Fernet 암호문과 호환되어야 한다. app/privacy/crypto.py의 토큰 형식(버전 바이트, timestamp, IV, HMAC 검증 순서)과 Kotlin 구현을 대조하고, 변조 토큰을 거부하지 않거나 HMAC 검증을 복호화 뒤로 미룬 지점을 찾아라. 호환이 깨지면 기존 사용자 문서를 영구히 읽을 수 없다."
```

```
"이 저장소의 불변식: 사용자 문서 텍스트는 마스킹 파이프라인을 통과한 뒤에만 LLM provider로 전달될 수 있다. 원문이 마스킹을 우회해 provider 호출, 로그, 예외 메시지, 메트릭 태그로 흘러가는 경로가 있는지 데이터 흐름을 따라가며 찾아라. 로그에는 문서 id·길이·상태만 남아야 한다."
```

```
"접근 통제 계약: 다른 사용자의 자원에 접근하면 403이 아니라 404를 반환해야 한다(자원 존재 자체를 숨긴다). 소유권 검사가 조회 이후에 오거나, 예외 매퍼가 403/401을 흘리거나, 오류 본문·타이밍·헤더로 자원 존재가 드러나는 지점을 찾아라."
```

```
"API 응답 계약: JSON 필드는 snake_case, 오류 본문은 {\"detail\": ...} 형태여야 하고 Spring 기본 ProblemDetail을 노출하면 안 된다. Jackson 네이밍 전략, @JsonProperty 누락, 전역 예외 매퍼가 처리하지 않아 기본 응답이 나가는 경로를 찾아라. React가 이 형태에 이미 의존한다."
```

```
"제품 계약: 문서 한 건당 LLM 호출은 변환 1회 + 조건부 보정 1회로 최대 2회다. SDK 자체 재시도와 worker 재시도가 겹쳐 이 상한을 넘기는 경로, 그리고 lease 만료 후 재처리 시 이미 완료된 변환을 다시 호출하는 경로를 찾아라."
```

축별 focus 문장 모음은 [references/focus-library.md](references/focus-library.md)에 있다.

## 4. 마이그레이션 특화 리뷰 축

글로벌 `multi-review` 스킬이 보안·성능·유지보수성·테스트라는 **범용 축**을 담당한다. 이 스킬은 그것과 겹치지 않는, 이 전환에서만 의미 있는 축을 본다. 범용 축을 여기서 또 돌리면 결과가 두 배로 길어지고 정작 parity 지적이 묻힌다.

### 4.1 계약 준수

계획 §2.2가 동결한 외부 계약을 실제로 지키는가. **codex에 물을 것:**

- "상태 코드가 가입 201 / 업로드 202 / 삭제 204 / 입력 오류 422 / 충돌 409 / 인증 401 / 소유권 404와 다르게 나가는 경로가 있는가?"
- "`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`가 빠지는 응답 경로가 있는가?"
- "업로드 `Location` 헤더, 다운로드 RFC 5987 `Content-Disposition`이 비ASCII 파일명에서 깨지는가?"
- "CORS 노출 헤더에서 `Content-Disposition`/`Location`이 빠지면 브라우저가 못 읽는데, 설정이 그대로인가?"

### 4.2 parity 위험

Python 원본과 동작이 갈라지는 지점. **codex에 물을 것:**

- "이 Kotlin 함수와 <Python 파일 경로>의 대응 함수가 경계값(빈 문자열, null, 공백만, 매우 긴 입력, 유니코드 결합 문자)에서 다른 결과를 내는가?"
- "정규식·문자열 분할·정규화가 Python과 Kotlin에서 다르게 동작하는 지점이 있는가?" (`\s`, `\b`, 유니코드 클래스, `strip()` 대 `trim()`)
- "정렬 순서, 반올림, 소수 표현, 타임존 처리가 원본과 다른가?"
- "Python이 조용히 넘기던 예외를 Kotlin이 던지거나, 그 반대인 곳이 있는가?"

### 4.3 보안 불변식

계획 §2.3과 §5 Phase 7 즉시 중단 기준. **codex에 물을 것:**

- "마스킹 전 원문이 LLM·로그·예외 메시지·메트릭으로 나가는 경로가 있는가?"
- "원문·결과·마스킹 대응표가 평문으로 DB에 저장되거나 로그에 남는가?"
- "소유권 검사가 없거나 순서가 잘못된 조회·삭제·다운로드 경로가 있는가?"
- "암호문 형식·키 버전 처리가 기존 데이터를 읽지 못하게 바뀌었는가?"
- "삭제가 문서와 변환을 함께 파기하는가? 마지막 작업 공간을 지울 수 있는가?"

### 4.4 Kotlin/Spring 관용성

계획 §3.1이 고른 선택을 유지하는가. **codex에 물을 것:**

- "JPA/Hibernate가 아니라 `JdbcClient`/Spring Data JDBC를 쓰기로 한 결정이 유지되는가? 무의식적으로 JPA 애너테이션이 들어왔는가?"
- "플랫폼 타입(`!`)이나 `!!`로 널 안전성이 무너진 지점이 있는가? DB 컬럼 nullable과 Kotlin 타입이 일치하는가?"
- "`@Transactional`이 private/internal 메서드나 자기 호출에 붙어 프록시가 적용되지 않는 곳이 있는가?"
- "문서 저장과 작업 큐 등록이 같은 트랜잭션 안에 있는가? (계획 §4.4가 요구하는 원자성)"
- "`FOR UPDATE SKIP LOCKED` lease 획득과 lease 만료 재처리에 경합 조건이 있는가?"
- "core 모듈이 Spring·DB 의존성 없이 유지되는가? (계획 §3.2)"

### 4.5 테스트 적정성

계획 §6 검증 매트릭스의 계층에 맞게 배치됐는가. **codex에 물을 것:**

- "이 변경이 깨뜨릴 수 있는 동작 중 어떤 테스트로도 덮이지 않은 것은 무엇인가?"
- "계약 조항(상태·헤더·오류 본문)이 contract test로 고정됐는가, 아니면 단위 테스트가 우회 검증만 하는가?"
- "DB 제약·트랜잭션·잠금·cascade가 Testcontainers 테스트로 확인되는가, mock으로 대체됐는가?"
- "Python↔Kotlin 교차 fixture가 있어야 할 자리(암호화, JWT, Argon2, 문서 추출)에 한쪽 구현만 쓰는 테스트가 들어갔는가?"
- "테스트가 구현을 그대로 복사해 항상 통과하는 구조인가?"

## 5. 교차 대조 종합 형식

**누가 언제 쓰는가**: §2.1의 3단계에서 **`migration-reviewer`가 2차 호출로** 작성한다. 1단계 병렬 리뷰 중에는 쓰지 않는다 — 그 시점엔 상대 산출물이 없다. 입력은 `..._codex-reviewer.md`와 `..._migration-reviewer.md` 두 파일이고, 출력은 `..._cross.md` 하나다. 이 호출은 **대조만** 하며 새 지적을 만들지 않는다.

codex 리뷰와 Claude 리뷰를 합칠 때 아래 표를 쓴다. 표 위에는 두 리뷰의 실행 조건(모드, scope, base, focus, 실행 시각)과 입력 파일 두 경로를 적어 재현 가능하게 남긴다.

| # | 지적 사항 | 출처 | 심각도 | 근거 파일·라인 | 상충 | 권고 |
|---|---|---|---|---|---|---|
| 1 | Jackson이 응답 필드를 camelCase로 직렬화 | 양쪽 | Critical | `api/.../DocumentResponse.kt:24` | - | 수정 후 재리뷰 |
| 2 | lease 만료 재처리 시 중복 LLM 호출 가능 | codex | Critical | `worker/.../ConversionWorker.kt:88` | - | 근거 확인 필요 |
| 3 | 소유권 검사 순서 문제 | Claude | Major | `application/.../DocumentService.kt:41` | 상충 | 사용자 판단 |

컬럼 규칙:

- **출처**: `codex` / `claude` / `양쪽` 중 하나. 반드시 채운다. 출처가 사라지면 독립성 정보가 사라져 교차 대조 자체가 무의미해진다. (§6 파일명 규약의 `{reviewer}`와는 별개 축이다 — 여기는 *어느 모델이* 그 지적을 냈는지를 표시한다.)
- **심각도**: `Critical` / `Major` / `Minor` / `제안`. 계획 §5 Phase 7의 즉시 중단 기준(Fernet 복호화 실패, 타 사용자 데이터 노출, 마스킹 전 전송, 중복 LLM 호출·작업 유실, 문서 fixture 불일치, 최대 2회 호출 위반)에 해당하면 **무조건 Critical**이다.
- **근거 파일·라인**: codex가 준 경로·라인은 **그대로 옮긴다.** 다시 세거나 바꾸지 않는다.
- **상충**: 두 리뷰가 반대 결론이면 `상충`. 표 아래에 양쪽 주장과 각 근거를 인용해 붙인다.
- **권고**: `수정 필요` / `근거 확인 필요` / `사용자 판단` / `기각(근거 첨부)` 중 하나.

판단 규칙:

1. **양쪽이 같은 지적 → 신뢰도 높음.** 서로 다른 맥락에서 같은 결론에 도달했으므로 근거 재확인 없이 수정 대상으로 올린다.
2. **codex만 지적 → 근거를 먼저 확인한다.** 맥락을 몰라 생긴 오탐일 수도, 우리가 맥락에 취해 못 본 진짜 결함일 수도 있다. 확인 없이 기각하는 것이 이 게이트에서 가장 흔한 실패다.
3. **Claude만 지적 → codex가 못 본 이유를 적는다.** diff 범위 밖이라 안 보였는지, focus에서 빠졌는지. 후자면 focus를 고쳐 재리뷰한다.
4. **상충 → 양쪽 병기 후 사용자에게.** 특히 "원래 Python 동작이 무엇이었나"에 대한 상충은 Python 원본을 실행해 증거를 만들기 전에는 결론 내지 않는다.
5. **Critical이 하나라도 남으면 Phase 종료를 보고하지 않는다.**

## 6. 산출물 경로

```
docs/migration/_workspace/reviews/{phase}_{scope}_{reviewer}.md
```

- `{phase}`: `00`~`09` (계획 §5의 Phase 번호). Phase 밖 임시 리뷰는 `xx`.
- `{scope}`: 리뷰 대상 축약. `crypto`, `auth`, `documents`, `worker`, `contract`, `frontend` 등.
- `{reviewer}`: `codex-reviewer` / `migration-reviewer` / `privacy-gate` / `cross` 중 하나. 앞의 셋은 **작성한 에이전트 이름 그대로**이고, `cross`만 예외적으로 교차 종합본을 뜻한다. 파일명만 보고 누가 쓴 것인지 알 수 있어야 출처를 되짚을 수 있다.

예: `docs/migration/_workspace/reviews/04_crypto_codex-reviewer.md`, `.../04_crypto_migration-reviewer.md`, `.../04_crypto_cross.md`

`cross` 파일이 사용자에게 제출하는 정본이지만, `codex-reviewer` 원본 파일을 **반드시 남긴다.** 원본이 없으면 종합 과정에서 무엇이 잘려 나갔는지 아무도 확인할 수 없고, 독립 리뷰를 받았다는 사실 자체를 검증할 수 없다.

`codex-reviewer` 파일에는 최소한 이것을 적는다: 실행 명령 전문(스크립트 인자 그대로), 사용한 헬퍼 경로와 버전, 모드·scope·base, focus text 전문, codex 출력 원문, job id.

## 7. 실패 처리

**공통 원칙: 1회 재시도 → 재실패하면 codex 결과 없이 진행하되, 산출물 맨 위에 "⚠ codex 리뷰 누락(사유: ...)"을 명시한다.** 조용히 통과시키면 필수 게이트가 형식만 남고, 나중에 "리뷰를 통과했다"는 기록만 남아 더 나쁘다.

| 증상 | 판별 | 대응 |
|---|---|---|
| 헬퍼 미발견 (exit 3) | 스크립트가 확인 절차를 출력 | 플러그인 설치/갱신 확인 → `CODEX_COMPANION`으로 직접 지정 → 그래도 없으면 codex CLI 폴백 확인. 전부 실패 시 누락 명시 |
| codex CLI 미설치·미인증 | `node <헬퍼> setup --json`의 `ready`/`auth.loggedIn`이 false | `npm install -g @openai/codex`, `codex login` 안내. 스킬이 임의 인증 흐름을 만들지 않는다 |
| Bash 도구 타임아웃 | 도구가 잘림 | job은 살아 있다. **재실행하지 말고** `status --all`로 job id를 찾아 `result <job-id>`로 회수 |
| 리뷰 자체 실패 | 헬퍼 stderr | 가장 실행 가능한 stderr 줄을 산출물에 그대로 인용하고 1회 재시도. 추측으로 메우지 않는다 |
| scope 오류 | 스크립트가 exit 2 | 대상이 없거나(diff 없음) git 상태가 예상과 다르다. `git status`로 확인 후 scope 재선택 |
| 출력이 비어 있음 | 지적 0건 | "지적 없음"을 그대로 기록한다. Claude가 대신 지적을 만들어 채우지 않는다 — 그건 독립 리뷰가 아니다 |

절대 하지 않는 것:

- codex가 실패했을 때 Claude가 codex 역할을 대신 수행해 "codex 리뷰"라고 적는 것
- codex 출력이 짧다는 이유로 Claude 리뷰를 codex 리뷰 칸에 채우는 것
- 리뷰 결과를 받자마자 지적 사항을 자동으로 고치는 것 — **먼저 표로 제시하고 무엇을 고칠지 확인받는다** (codex 플러그인의 결과 처리 계약과 동일)
