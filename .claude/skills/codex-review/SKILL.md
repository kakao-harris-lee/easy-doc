# codex-review

## 1. 이 스킬이 있는 이유

Claude가 작성한 Kotlin 코드를 Claude가 리뷰하면 **같은 맹점을 공유한다.** Python 원본을 Kotlin으로 옮길 때 오해한 지점이 있으면, 옮긴 쪽과 리뷰하는 쪽이 같은 오해를 그대로 반복해 "일관되게 틀린" 결과를 통과시킨다. 마이그레이션에서 가장 위험한 결함은 컴파일 오류가 아니라 *양쪽 다 그럴듯해 보이는 동작 차이*이므로, 이 맹점 공유가 곧 parity 사고다.

codex는 다른 모델 계열이고 이 저장소의 대화 맥락을 공유하지 않는다. 그래서 우리가 당연하게 여긴 전제를 당연하게 여기지 않고, 우리가 이미 "확인했다"고 믿는 코드를 처음 보는 눈으로 읽는다. **이 독립성이 이 스킬의 가치 전부다.**

따라서 다음을 지킨다.

- **codex 출력을 요약해서 대체하지 않는다.** 원문 지적을 그대로 인용해 산출물에 남기고, 요약은 별도 줄에 덧붙인다. 요약하는 순간 Claude의 판단이 codex의 관점을 덮어써서 독립성이 사라진다.
- **codex 지적을 "우리가 이미 알아서 처리했다"로 조용히 기각하지 않는다.** 기각하려면 반박 근거(파일·라인·테스트)를 산출물에 적는다. 근거 없는 기각은 리뷰를 받지 않은 것과 같다.
- **codex가 틀렸다고 판단해도 지적 자체는 삭제하지 않는다.** "codex 지적 / Claude 반박 / 근거"를 병기하고 판단은 사용자에게 넘긴다. codex가 맥락을 몰라 틀린 경우와, 우리가 맥락에 취해 틀린 경우는 겉보기에 똑같이 생겼다.

## 2. 운용 정책

### 2.0 실행 방식

**Stop-time review gate 는 켜 둔다.** `codex@openai-codex` 플러그인의 stop 훅(`scripts/stop-review-gate-hook.mjs`)은 **세 번째 리뷰 레인**이고, 아래 3단계 명시 게이트를 **대체하지 않으며 대체되지도 않는다.** 둘 다 돈다.

**[2026-08-21 되살림 — 사용자 결정]** 직전 판(같은 날)이 *"이 저장소와 모든 worktree에서 Stop-time review gate 는 비활성화한다. `/codex:setup --enable-review-gate` 를 실행하지 않는다"* 고 적었다. 근거는 *"명시적 리뷰와 중복되어 종료 지연과 토큰 소비를 만든다"* 였다. **원장이 그 근거를 반증한다.**

- `stop-time` 은 원장에 **30회** 나온다(`00_progress-archive.md` 28 · `00_progress.md` 2).
- `00_progress-archive.md:647` — "두 리뷰 레인이 **회전 경합 자리를 모두 놓쳤다** … 세 번째 레인(stop-time codex 게이트)이 찾았고 리더가 코드로 확인해 `d19175b` 로 닫았다."
- `00_progress-archive.md:956` — "**stop-time 게이트가 다섯 번을 잡았고** 열거가 한 번을 잡았다."
- `00_progress-archive.md:1577`·`:1588` — "**네 회차 연속**", "**다섯 번 연속 세션 종료를 막아**".
- `00_progress-archive.md:493` — "**stop-time 게이트가 세 번 다 잡았다는 것이 리뷰 대체가 되지는 않는다** — 그것은 같은 세션 안의 검사이고, 독립 리뷰가 겨누는 것은 바로 그 자기 승인이다."

마지막 줄이 방향을 못 박는다: **stop-time → 명시 리뷰 대체 불가**는 근거와 함께 기록돼 있는데, 비활성화 판은 **반대 방향**(명시 리뷰 → stop-time 대체 가능)을 근거 없이 주장했다. 실측은 그 반대다 — 명시 리뷰 두 레인이 놓친 것을 stop-time 이 여러 회차 잡았다.

**결정적 근거는 그 판을 들여온 회차 자신이다.** 하네스 비용 구조 개조(`xx_harness`) 회차에서 실제로 돈 게이트는 stop-time **하나**였고(3단계 명시 게이트는 도달 0 — 계획 §6 자기 기록), 그 하나가 결함 **2건**을 잡았다(원장 분리의 아카이브 소실 미탐지, 라쳇만 남기고 정확 일치를 지운 6개 삭제 창). **도달이 증명된 장치를 끄고 같은 회차에 도달 0이던 장치를 대체물로 지목한 것**이 그 판이었다.

**선언과 실제가 갈려 있었다(기록해 둔다).** 비활성화를 선언한 문면에 **강제자가 없었다** — 플러그인 훅은 그 문장과 무관하게 계속 돌았고, 실제로 위 2건을 잡았다. 즉 그 선언은 도달 0이었고, 이번엔 갈림이 **안전한 방향**이었을 뿐이다. 문서가 "껐다"고 말하는 동안 게이트가 돌고 있었다는 사실 자체가 이 하네스가 반복해 겪은 「선언 ≠ 도달」의 또 한 사례다.

**따라서 세 레인이 모두 필요하다:** ① codex 독립(명시) ② Claude 독립(명시) ③ stop-time(같은 세션 자기 검사). ③은 ①·②의 **자기 승인을 겨누지 못한다** — 같은 세션 안이므로. 반대로 ①·②는 세션 종료 직전의 마지막 편집을 못 본다. 겹치는 것이 아니라 **서로 다른 시점의 다른 결함**을 잡는다.

### 2.1 필수 게이트

**변경 단위가 끝날 때마다 codex 독립 리뷰를 돌린다.** 게이트를 통과하지 못한 변경은 Phase 종료로 보고하지 않는다.

**"변경 단위"는 무엇을 건드렸는지로 정한다 — 커밋 수가 아니다** (2026-08-21 개정, 사용자 승인). 종전 정의는 "커밋 직전, 또는 Phase 종료 조건 판정 직전"이었고, 그 앞쪽 절반이 **커밋 기반 축**이라 게이트 39회차·리뷰 산출물 43,157줄을 만들었다(실측 2026-08-21). 정본은 `kotlin-migration` 스킬의 리뷰 게이트 절이고 **두 곳은 항상 같은 내용이어야 한다.**

**아래 일곱 중 하나에 닿으면 그 변경 단위마다 반드시 돌린다. 면제 없다.**

1. **보안·개인정보 불변식** — 마스킹 선행 · 저장 암호화 · 소유권 은닉 404 · 평문 로그/저장 · 인증(JWT·Argon2)
2. **외부 HTTP 계약** — 상태 코드 · 헤더 · 오류 본문 · 필드명
3. **게이트·탐지기 자신** — `.claude/**` · `tests/test_*_reach.py` · `tests/test_*_gate*.py` · `.github/workflows/ci.yml` · `pyproject.toml`
4. **Phase 종료·착수 판정**
5. **작업 큐·LLM 호출 규약** — 중복 호출 · 작업 영구 유실 · pending 무한 체류 · 문서당 최대 2회 호출
6. **문서 추출·내보내기 무결성** — 필수 정보 누락 · 산출 파일이 열리지 않음
7. **골든 품질 합격선** — 절대 팩트축 누락 · 기록된 하한선 대비 하락

**일곱 중 어디에도 닿지 않는 변경**(모듈 내부 리팩터 · 성능 · 이름 바꾸기)은 **Phase 단위 또는 게이트 회차 단위로 묶어 한 번에** 리뷰한다.

축 5·6·7 은 codex 독립 리뷰 지적으로 신설했다(high, 2026-08-21) — 초판 4축이 계획 §5 즉시 중단 기준 7개 중 4개를 담지 못했다. 경위와 매핑 강제자는 `kotlin-migration` 스킬 리뷰 게이트 절이 정본이다.

**§2.2 의 면제 목록은 이 개정으로 한 줄도 늘지 않는다.** 모든 변경은 여전히 정확히 한 번 리뷰를 받고, 바뀐 것은 **여부가 아니라 시점**이다 — 「면제를 넓힌다」로 구현하면 그것은 `kotlin-migration` 규칙 4 ⑵ 가 거부권을 갖는 **은폐형** 확대가 된다. 이 구분을 흐리지 마라.

### 2.1-a 묶음 리뷰는 `--base <묶음 시작 커밋>` 을 **반드시** 준다 (C-2, 2026-08-21)

**기본값이 맞는 경계에서 기본값이 틀린 경계로 리뷰를 옮겼으므로 호출도 함께 바뀐다.**

| 경계 | 대상 | `--scope auto` 가 고르는 것 | 맞나 |
|---|---|---|---|
| **종전(커밋 직전)** | 아직 커밋 안 된 그 변경 | 작업 트리가 더러움 → working-tree | **맞다** |
| **개정(Phase·회차 묶음)** | **이미 커밋된** 여러 변경 | 작업 트리가 더러우면 **여전히 working-tree** | **틀리다 — 커밋된 묶음을 건너뛴다** |

건너뛴 결과가 조용하다는 것이 핵심이다: 대상이 0건이 **아니므로** `EXIT_EMPTY_TARGET`(7)에 걸리지 않고, **exit 0 + 비지 않은 출력**이 남아 그 회차의 통과 근거로 기록된다. 스크립트 자신이 이 실패를 실측으로 적어 두었다(`scripts/codex-review.sh:23-25`): *"커밋한 뒤 `--scope working-tree` 로 돌리거나 … 리뷰 대상 0줄인 채 게이트 통과가 기록된다."*

**규약:**

- **묶음 리뷰는 `--base <묶음 시작 커밋>` 을 명시한다.** `--base` 는 scope 를 무시하고 `merge-base(HEAD, <ref>)..HEAD` 를 대상으로 잡으므로 커밋된 묶음이 정확히 들어온다.
- **`--base HEAD` 를 주지 마라.** `merge-base(HEAD, HEAD)` = `HEAD` 이므로 **항상 빈 diff** 이고 exit 7 로 끝난다. 스크립트 도움말이 이 함정을 이름까지 대서 경고하는데 **`xx_harness` 회차에서 실제로 밟았다**(1차 시도 exit 7, 그리고 실패 원인을 "변경이 모두 커밋된 상태"로 **잘못** 기록했다 — 실제로는 미커밋 56파일이었다).
- **단일 변경 단위 리뷰(4축에 닿아 즉시 도는 경우)는 `--scope working-tree` 로 충분하다** — 그 변경이 아직 커밋되지 않았을 때에 한한다.
- **호출한 명령과 대상 크기를 산출물 「호출 상태」에 적는다.** 종료 코드만으로는 「무엇을 봤는가」가 남지 않는다.

**공유 작업 트리 주의.** 다른 레인이 같은 트리에서 작업 중이면 `--scope working-tree` 는 **그 레인의 변경까지 끌어온다.** `xx_harness` 회차 실측: 대상 56파일 중 이 회차 것은 8개뿐이었고 48개가 다른 레인의 미커밋 작업이었다. 리뷰가 느려지는 것보다 **리뷰 대상이 오염되는 것**이 문제다. 스크립트에 경로 필터 옵션이 **없으므로**(옵션은 `--base`·`--scope`·`--focus`·`--json`·`--dry-run` 뿐), 이럴 때는 자기 변경을 브랜치에 커밋하고 `--base` 로 돌린다.

게이트는 **3단계**로 돈다. 병렬 호출 한 번으로는 닫히지 않는다.

1. **병렬·독립 실행** — `migration-reviewer`(Claude, 저장소 맥락과 계획 문서를 아는 리뷰)와 `codex-reviewer`(이 스킬로 codex를 호출하는 맥락 없는 독립 리뷰)를 같은 메시지에서 동시에 띄운다. 서로의 결론을 보지 못하게 한다.
2. **완료 확인** — 두 산출물이 실제 파일로 존재하는지 확인한다.
3. **교차 대조 종합 (§5)** — `migration-reviewer`를 **재호출**해 두 산출물을 한 표로 합치고 `..._cross.md`로 제출한다.

`migration-reviewer`가 한 게이트에서 **2회 호출**된다는 뜻이다 — 1회차는 자기 독립 리뷰, 2회차는 종합 전용. 1회차와 3단계를 한 호출로 합치면 시작 시점에 codex 산출물이 아직 없어 매번 "codex 리뷰 없음"으로 종결되고, 필수 게이트가 형식만 남는다. **2차 호출에서는 새 지적을 만들지 않고 대조만 한다** — 그때 새로 나온 지적은 교차 검증을 받지 않은 채 정본에 실리기 때문이다. 새로 발견한 것은 별건으로 다음 게이트에 올린다.

두 리뷰가 **상충하면 어느 쪽도 지우지 않는다.** 양쪽 근거를 병기하고 `상충` 표시를 단 뒤 사용자 판단을 요청한다. 마이그레이션에서 상충은 대개 "무엇이 원래 동작인지"에 대한 불일치이고, 그건 코드가 아니라 Python 원본을 실행해 봐야 결론이 나기 때문이다.

### 2.2 리뷰를 건너뛸 수 있는 예외

게이트가 형식화되면 아무도 결과를 읽지 않으므로, 다음만 명시적으로 면제한다. 기준은 **산출물의 동작에 영향이 없는 변경**이며 그 밖으로 넓히지 않는다. 같은 목록이 `kotlin-migration` 스킬의 리뷰 게이트 절에도 있고, 두 곳은 항상 같은 내용이어야 한다.

| 면제 | 조건 |
|---|---|
| 산문 문서만 수정 | `docs/**`(단 `docs/migration/_workspace/**`는 아래 행), `README` 등 실행 코드도 하네스 정의도 바뀌지 않은 변경 |
| 주석·오타 | 코드 파일이라도 주석·문자열 오타 수정이고 동작에 영향이 없음이 diff로 자명한 경우 |
| 포매팅 전용 | ktlint/detekt/prettier 자동 포매팅 결과만 담긴 커밋 |
| 산출물 파일 | `docs/migration/_workspace/**` 리뷰·분석 산출물 추가 |

**면제되지 않는 것** (예외처럼 보여도 반드시 리뷰한다):

- **스킬·에이전트 정의와 하네스 스크립트(`.claude/**`)** — 확장자가 `.md`여도 "문서 수정"이 아니다. 하네스 자체가 게이트이므로 하네스 수정을 면제하면 **게이트가 검증 없이 통과하는 경로가 그대로 남는다.** 실제로 pre-phase0 회차의 지적은 전부 하네스였다
- 테스트 코드만 바꾼 변경 — 테스트가 보장 범위를 좁히는 방향으로 바뀌는 사고가 여기서 난다
- 의존성 버전·Gradle 설정 변경 — 계획 문서 §3.1이 버전 조합 고정을 요구한다
- 로그 문구 변경 — 평문 유출은 로그 한 줄에서 시작한다
- 설정값·프로퍼티 기본값 변경 — 상한(4,000자, 10MB)과 보존 정책이 여기 산다

## 3. 실행 절차

### 3.1 스크립트로 실행한다

```bash
.claude/skills/codex-review/scripts/codex-review.sh <review|adversarial> [--base <ref>] [--scope <auto|working-tree|branch>] [--json] [--dry-run] [focus text...]
```

헬퍼 경로를 **직접 쓰지 마라.** codex 플러그인 헬퍼는 `~/.claude/plugins/cache/openai-codex/codex/<버전>/scripts/codex-companion.mjs`에 있고 경로에 버전이 박혀 있다. 하드코딩하면 플러그인이 올라가는 순간 리뷰 게이트가 조용히 깨지고, 게이트가 깨진 줄 모른 채 Phase가 통과된다. 스크립트는 매 실행마다 다음 순서로 탐색한다.

1. `$CODEX_COMPANION` 환경변수 (비표준 위치 수동 지정용)
2. `~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs` 중 **버전 내림차순으로 실제 파일이 있는 최신 버전**
3. `~/.claude/plugins/marketplaces/openai-codex/plugins/codex/scripts/codex-companion.mjs` (마켓플레이스 원본)
4. 헬퍼가 전혀 없으면 `codex` CLI 직접 호출 (`codex review [PROMPT] --uncommitted | --base <ref>`)
5. 넷 다 실패하면 확인 절차를 출력하고 exit 3

`CLAUDE_CONFIG_DIR`이 설정돼 있으면 그것을 `~/.claude` 대신 쓴다.

먼저 `--dry-run`으로 어떤 헬퍼가 잡히고 어떤 명령이 나가는지 확인하는 습관을 들여라. 리뷰 한 번은 수 분과 토큰 비용이 들고, scope를 잘못 잡으면 엉뚱한 diff를 리뷰하고 그 결과를 통과 근거로 삼게 된다.

**리뷰 대상이 비어 있으면 스크립트가 헬퍼를 부르기 전에 거부한다(exit 7).** codex는 빈 diff를 받아도 실패하지 않는다 — "빈 diff로 확인되어 검토할 변경 사항이 없다"를 1KB 넘게 써서 `Verdict: approve`로 끝낸다(실측: `adversarial --base HEAD` → exit 0, 1,164바이트). 그래서 "종료 코드 0이고 출력이 비어 있지 않다"는 조건만으로는 **아무것도 리뷰하지 않은 실행**을 걸러내지 못한다. `--base`를 잘못 주거나(예: `--base HEAD`), 이미 커밋한 뒤 `--scope working-tree`로 돌리거나, 브랜치를 착각하면 리뷰 대상 0줄인 채로 "게이트 통과"가 기록된다.

대상 판정은 헬퍼(`lib/git.mjs`의 `resolveReviewTarget`·`getWorkingTreeState`·`buildBranchComparison`)와 같은 규칙을 쓴다.

| 인자 | 리뷰 대상 | "비어 있다"의 뜻 |
|---|---|---|
| `--base <ref>` | `merge-base(HEAD,<ref>)..HEAD` (scope 무시) | 그 범위의 **커밋된** 변경 파일이 0개 |
| `--scope working-tree` | staged + unstaged + untracked | 셋 다 0개 |
| `--scope branch` | 기본 브랜치를 탐지한 뒤 위 branch 규칙 | 위와 같음 |
| `--scope auto`(기본) | 작업 트리가 더러우면 working-tree, 깨끗하면 branch | 선택된 쪽이 0개 |

두 가지를 기억하라.

- **branch 모드는 커밋된 변경만 본다.** 커밋하지 않은 변경만 있는데 `--base main`을 주면 대상은 진짜로 비어 있고 exit 7이 맞다. 그 상황에서는 `--scope working-tree`를 써라.
- **untracked 파일은 대상으로 센다.** 헬퍼가 working-tree 리뷰에서 untracked 파일 *본문*을 컨텍스트에 싣기 때문이다. 다만 헬퍼는 디렉터리·바이너리·24KB 초과 파일을 `(skipped: ...)`로 대체하므로, untracked가 그런 파일뿐이면 실질 대상은 비었는데 스크립트는 통과시킨다 — **이 검사가 놓치는 구멍이다.**

판정이 모호하면(merge-base를 구할 수 없다, 기본 브랜치를 탐지할 수 없다, git 명령이 실패한다) **거부하지 않고 통과시킨다.** 잘못된 거부로 정상 리뷰를 막는 것도 게이트를 망가뜨리기 때문이다. 이 검사는 "명백히 0건"만 잡는다.

보조로, 리뷰가 끝난 뒤 결과에 "리뷰 대상이 없었다"는 신호가 있으면 역시 exit 7로 끝낸다. 신호는 ① `--json`일 때 헬퍼가 만드는 `Reviewing 0 staged, 0 unstaged, and 0 untracked file(s).`(모델이 아니라 헬퍼가 쓰는 문장이라 언어·모델이 바뀌어도 유지된다)와 ② **지적이 0건일 때만** 적용하는 빈 diff 서술 문구 매칭이다. ②는 codex 응답 문구에 의존하므로 모델·언어가 바뀌면 조용히 무력해진다. **이 사후 검사는 보조일 뿐 단독 방어선이 아니다 — 근본 대책은 위의 사전 거부다.** (구조적 신호가 ①뿐인 이유: 헬퍼 payload에는 `fileCount`·`diffBytes`가 실리지 않아 branch 모드에는 대응하는 구조적 필드가 없다.)

종료 코드:

| 코드 | 뜻 | 리뷰 근거가 되는가 |
|---|---|---|
| `0` | 리뷰가 돌았고 출력이 비어 있지 않다 | **예 — 이 값일 때만** |
| `2` | 사용법 오류 | 아니오 |
| `3` | 리뷰 수단 부재 (헬퍼·codex CLI 모두 없음) | 아니오 |
| `4` | handshake 실패 — 파일은 있으나 동작하는 리뷰 도구가 아니다 | 아니오 |
| `5` | 도구가 0으로 끝났는데 출력이 비었다 (= 리뷰 미실행) | 아니오 |
| `6` | `--dry-run` (실행하지 않음) | 아니오 |
| `7` | **리뷰 대상이 비어 있다** (변경 0건). 사전 거부 또는 결과 신호 | 아니오 |
| 그 외 | 리뷰 도구의 종료 코드 전파 | 아니오 |

`7`이 `0`이 아닌 이유: 리뷰어가 **아무것도 보지 않았으므로** "검토했다"는 근거가 되지 않는다. 0으로 돌려주면 잘못된 scope로 돌린 빈 리뷰가 통과 기록으로 남고, 그것이 이 하네스가 막으려는 실패(검증하지 않고 통과) 그 자체다. `5`와 나누는 이유는 조치가 다르기 때문이다 — `5`는 "도구가 고장 났다"(헬퍼·인증 점검), `7`은 "도구는 멀쩡한데 잘못된 대상을 줬다"(`--base`/`--scope` 재선택).

대상 검사는 헬퍼 탐색과 `--dry-run`보다 **먼저** 돈다. 따라서 대상이 비어 있으면 `--dry-run`이어도 `6`이 아니라 `7`이 나온다 — scope를 확인하려고 `--dry-run`을 돌린 것이라면 그게 바로 알아야 할 답이다.

### 3.2 `review`와 `adversarial` 선택

| 모드 | 언제 | focus text |
|---|---|---|
| `review` | 일반 변경. 리팩터링, 배선, 설정, 테스트 보강 | **불가** — 헬퍼가 거부한다 |
| `adversarial` | parity·보안·계약 위험이 있는 변경 | 필수. focus 없는 adversarial은 review의 열화판이다 |

`review`는 codex 내장 리뷰어에 그대로 매핑되므로 커스텀 지시를 받지 않는다. 스크립트가 focus text와 함께 온 `review`를 먼저 막는 이유다 (헬퍼까지 갔다가 실패하면 job만 남고 시간을 버린다).

**`adversarial`을 반드시 쓰는 변경 영역:**

- 저장 암호화·복호화 (AEAD, `encryption_scheme`, `key_version`) — 계획 §4.3(2026-08-12 2차 개정 — Fernet 호환이 아니라 표준 AEAD 신규), 실패 시 사용자 문서를 못 읽거나 변조가 통과한다
- 마스킹 파이프라인 — 계획 §2.3, CLAUDE.md의 보안 불변식
- 인증·인가 (Argon2 재해시 판정, JWT clock skew, 소유권 404) — 계획 §2.2, §5 Phase 7 즉시 중단 기준
- 문서 파서·내보내기 (docx/pdf/hwpx, ZIP/XML) — 계획 §4.5, zip bomb·DTD 차단이 걸려 있다
- 작업 큐·worker (lease, retry, 보존 파기) — 계획 §4.4, 유실·이중 완료가 여기서 난다
- LLM provider 어댑터 — 계획 §4.6, 최대 2회 호출 계약

이 영역은 "동작하는지"가 아니라 "**틀렸을 때 무엇이 새는지**"를 물어야 하고, 그런 질문은 적대적 리뷰 프롬프트가 훨씬 잘 만든다.

### 3.3 `--scope`와 `--base`

- `--base <ref>`를 주면 **scope는 무시되고** `<ref>` 대비 branch diff를 리뷰한다.
- `--scope working-tree` — 아직 커밋하지 않은 변경. 커밋 직전 게이트의 기본값.
- `--scope branch` — 기본 브랜치 대비 누적 diff. base를 안 주면 헬퍼가 기본 브랜치를 탐지한다.
- `--scope auto`(기본) — 작업 트리가 더러우면 working-tree, 깨끗하면 기본 브랜치 대비 branch.

선택 기준:

| 상황 | 선택 | 이유 |
|---|---|---|
| 커밋 전 마지막 점검 | `--scope working-tree` | 지금 커밋될 것만 본다 |
| Phase 종료 판정 | `--base main` | Phase 전체 누적 변경을 한 번에 본다. 커밋별로 쪼개 보면 커밋 사이에 생긴 모순을 못 잡는다 |
| 여러 Phase가 브랜치에 쌓임 | `--base <Phase 시작 커밋>` | 기본 브랜치 대비는 너무 커져 리뷰 품질이 떨어진다 |
| 잘 모르겠다 | `--dry-run`으로 확인 | auto가 무엇을 고를지 추측하지 마라 |

### 3.4 실행 시간과 결과 회수

**리뷰는 동기 실행이다.** 헬퍼 usage에 `--wait|--background`가 보이지만, `review`/`adversarial-review`에서는 파싱만 되고 실제로 쓰이지 않는다(`--background`는 `task`, `--wait`는 `status`에서만 동작). 그러니 스크립트에 그 플래그를 넘기지 말고, Claude Code 쪽에서 실행을 제어하라.

- Bash 도구 `timeout`을 넉넉히 준다 (기본 120000ms로는 잘린다. `600000` 권장).
- 리뷰 중 다른 작업을 진행하려면 Bash 도구의 `run_in_background`로 띄우고 나중에 회수한다.

리뷰 실행은 job으로 기록되므로 사후 재조회가 된다. 결과를 잃어버렸거나 백그라운드 출력이 잘렸으면 **다시 돌리지 말고** 회수하라 (재실행은 비용이 두 배다).

```bash
node <헬퍼경로> status --all          # job 목록과 id
node <헬퍼경로> result <job-id>       # 해당 job의 전체 결과
node <헬퍼경로> cancel <job-id>       # 잘못 띄운 job 정리
```

헬퍼 경로는 `codex-review.sh ... --dry-run`이 출력하는 경로를 그대로 쓴다.

### 3.5 focus text 작성법

codex는 이 프로젝트의 계약도, 계획 문서도, Python 원본의 의도도 모른다. 그 공백을 focus text로 메우지 않으면 codex는 일반적인 Kotlin 코드 리뷰(널 안전성, 예외 처리)만 하고 돌아온다. **focus text는 "우리 계약을 codex에 주입하는 통로"다.**

작성 규칙:

1. **불변식을 단정문으로 준다.** "확인해 달라"가 아니라 "이것이 지켜져야 한다"로 쓴다. 판정 기준이 명확해야 위반을 찾는다.
2. **Python 원본 파일 경로를 같이 준다.** codex는 저장소를 읽을 수 있으므로 비교 대상을 지목하면 실제로 대조한다. 단 Python은 **참고 구현이지 정답이 아니다**(2026-08-12 재개발 전환) — "같은지"가 아니라 "요구사항을 만족하는지"를 묻는다. 암호·인증에서는 Python 대조 자체를 요구하지 않는다(호환 요구 소멸).
3. **위반 시 결과를 적는다.** "실패하면 기존 문서를 복호화할 수 없다" 같은 문장이 심각도 판단을 바꾼다.
4. **한 번에 3~5개 축까지만.** 열 개를 넣으면 전부 얕게 본다.

바로 쓸 수 있는 예시:

```
"이 저장 암호화는 표준 AEAD여야 한다. 다음을 찾아라 — (1) 암호화→복호화 round-trip이 깨지는 경로, (2) 변조된 암호문·다른 키·형식 오류가 예외 없이 통과하는 경로(인증되지 않은 암호화), (3) 실패 원인이 예외 타입·메시지·지연으로 구분돼 복호화 oracle이 되는 자리, (4) nonce/IV가 고정이거나 재사용되는 자리 — AES-GCM에서 nonce가 겹치면 평문이 복원된다, (5) 표준 라이브러리 대신 프리미티브를 직접 조립한 코드. Python Fernet과의 호환은 요구하지 않는다(롤백 포기, 계획 §4.3 2026-08-12 2차 개정). 깨지면 사용자 문서를 영구히 읽지 못하거나 변조가 그대로 복호화된다."
```

```
"이 저장소의 불변식: 사용자 문서 텍스트는 마스킹 파이프라인을 통과한 뒤에만 LLM provider로 전달될 수 있다. 원문이 마스킹을 우회해 provider 호출, 로그, 예외 메시지, 메트릭 태그로 흘러가는 경로가 있는지 데이터 흐름을 따라가며 찾아라. 로그에는 문서 id·길이·상태만 남아야 한다."
```

```
"접근 통제 계약: 다른 사용자의 자원에 접근하면 403이 아니라 404를 반환해야 한다(자원 존재 자체를 숨긴다). 소유권 검사가 조회 이후에 오거나, 예외 매퍼가 403/401을 흘리거나, 오류 본문·타이밍·헤더로 자원 존재가 드러나는 지점을 찾아라."

"API 응답 계약: JSON 필드는 snake_case, 오류 본문은 {\"detail\": ...} 형태여야 하고 Spring 기본 ProblemDetail을 노출하면 안 된다. Jackson 네이밍 전략, @JsonProperty 누락, 전역 예외 매퍼가 처리하지 않아 기본 응답이 나가는 경로를 찾아라. React가 이 형태에 이미 의존한다."
```

```
"제품 계약: 문서 한 건당 LLM 호출은 변환 1회 + 조건부 보정 1회로 최대 2회다. SDK 자체 재시도와 worker 재시도가 겹쳐 이 상한을 넘기는 경로, 그리고 lease 만료 후 재처리 시 이미 완료된 변환을 다시 호출하는 경로를 찾아라."
```

축별 focus 문장 모음은 [references/focus-library.md](references/focus-library.md)에 있다.

## 4. 마이그레이션 특화 리뷰 축

글로벌 `multi-review` 스킬이 보안·성능·유지보수성·테스트라는 **범용 축**을 담당한다. 이 스킬은 그것과 겹치지 않는, 이 전환에서만 의미 있는 축을 본다. 범용 축을 여기서 또 돌리면 결과가 두 배로 길어지고 정작 parity 지적이 묻힌다.

### 4.1 계약 준수

계획 §2.2가 동결한 외부 계약을 실제로 지키는가. **codex에 물을 것:**

- "상태 코드가 가입 201 / 업로드 202 / 삭제 204 / 입력 오류 422 / 충돌 409 / 인증 401 / 소유권 404와 다르게 나가는 경로가 있는가?"
- "`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`가 빠지는 응답 경로가 있는가?"
- "업로드 `Location` 헤더, 다운로드 RFC 5987 `Content-Disposition`이 비ASCII 파일명에서 깨지는가?"
- "CORS 노출 헤더에서 `Content-Disposition`/`Location`이 빠지면 브라우저가 못 읽는데, 설정이 그대로인가?"

### 4.2 parity 위험

Python 원본과 동작이 갈라지는 지점. **codex에 물을 것:**

- "이 Kotlin 함수와 <Python 파일 경로>의 대응 함수가 경계값(빈 문자열, null, 공백만, 매우 긴 입력, 유니코드 결합 문자)에서 다른 결과를 내는가?"
- "정규식·문자열 분할·정규화가 Python과 Kotlin에서 다르게 동작하는 지점이 있는가?" (`\s`, `\b`, 유니코드 클래스, `strip()` 대 `trim()`)
- "정렬 순서, 반올림, 소수 표현, 타임존 처리가 원본과 다른가?"
- "Python이 조용히 넘기던 예외를 Kotlin이 던지거나, 그 반대인 곳이 있는가?"

### 4.3 보안 불변식

계획 §2.3과 §5 Phase 7 즉시 중단 기준. **codex에 물을 것:**

- "마스킹 전 원문이 LLM·로그·예외 메시지·메트릭으로 나가는 경로가 있는가?"
- "원문·결과·마스킹 대응표가 평문으로 DB에 저장되거나 로그에 남는가?"
- "소유권 검사가 없거나 순서가 잘못된 조회·삭제·다운로드 경로가 있는가?"
- "암호문 형식·키 버전 처리가 기존 데이터를 읽지 못하게 바뀌었는가?"
- "삭제가 문서와 변환을 함께 파기하는가? 마지막 작업 공간을 지울 수 있는가?"

### 4.4 Kotlin/Spring 관용성

계획 §3.1이 고른 선택을 유지하는가. **codex에 물을 것:**

- "JPA/Hibernate가 아니라 `JdbcClient`/Spring Data JDBC를 쓰기로 한 결정이 유지되는가? 무의식적으로 JPA 애너테이션이 들어왔는가?"
- "플랫폼 타입(`!`)이나 `!!`로 널 안전성이 무너진 지점이 있는가? DB 컬럼 nullable과 Kotlin 타입이 일치하는가?"
- "`@Transactional`이 private/internal 메서드나 자기 호출에 붙어 프록시가 적용되지 않는 곳이 있는가?"
- "문서 저장과 작업 큐 등록이 같은 트랜잭션 안에 있는가? (계획 §4.4가 요구하는 원자성)"
- "`FOR UPDATE SKIP LOCKED` lease 획득과 lease 만료 재처리에 경합 조건이 있는가?"
- "core 모듈이 Spring·DB 의존성 없이 유지되는가? (계획 §3.2)"

### 4.5 테스트 적정성

계획 §6 검증 매트릭스의 계층에 맞게 배치됐는가. **codex에 물을 것:**

- "이 변경이 깨뜨릴 수 있는 동작 중 어떤 테스트로도 덮이지 않은 것은 무엇인가?"
- "계약 조항(상태·헤더·오류 본문)이 contract test로 고정됐는가, 아니면 단위 테스트가 우회 검증만 하는가?"
- "DB 제약·트랜잭션·잠금·cascade가 Testcontainers 테스트로 확인되는가, mock으로 대체됐는가?"
- "암호화·JWT·Argon2가 **Kotlin 자체 테스트로** round-trip·음성 케이스(변조·다른 키·서명 위조·알고리즘 혼동)까지 덮였는가, 아니면 성공 경로만 있는가?" (Python↔Kotlin 교차 fixture는 2026-08-12에 없어졌다 — 롤백 포기로 근거가 소멸했고 parity의 crypto·jwt·argon2 도메인도 함께 제거됐다.)
- "테스트가 구현을 그대로 복사해 항상 통과하는 구조인가?"

### 4.6 선언 범위 대 실제 도달 (앞의 다섯 축을 가로지른다)

**판정 기준의 전문은 `kotlin-migration` 스킬 "선언한 범위와 실제 도달을 대조한다" 절이다** — 규칙 6개와 근거가 된 실패 7건이 거기 있고, 여기에는 리뷰에서 무엇을 묻는지만 적는다. 값을 복제하지 않는 이유는 §6 `{scope}`와 같다.

이 축은 4.1~4.5와 나란한 여섯 번째 주제가 아니라 **다섯 축 각각에 매번 던지는 질문**이다. 실제 사고는 계약(§4.1)·parity(§4.2)·보안 불변식(§4.3)·테스트(§4.5) 어디서든 같은 형태로 났다 — 선언한 범위와 실제 도달 범위가 다른데 아무도 재지 않았다. 그래서 "이번엔 이 축까지 못 봤다"가 성립하지 않도록, **게이트·불변식·규칙을 새로 세우거나 기존 것의 범위를 넓히는 변경이면 이 축을 focus text에 반드시 넣는다.** 그런 변경이 아니면 아래 질문 중 걸리는 것만 골라 쓴다 — §3.5의 "한 번에 3~5개 축까지" 상한이 여기에도 적용되고, 여섯 개를 다 넣으면 전부 얕게 본다. codex가 이 축에서 아무것도 지적하지 않았으면 **그 사실을 그대로 기록한다** — Claude가 대신 지적을 만들어 채우지 않는다(§7).

**codex에 물을 것** (전부가 아니라 해당하는 것만):

- "이 코드·설정이 '전역'·'모든 응답'·'항상' 적용된다고 선언하는데, 그 강제 수단이 **닿지 않는 경로**가 있는가? 필터·인터셉터·애너테이션이 시작조차 하지 않는 요청, 크롤링에서 빠지는 디렉터리, 마커로 제외되는 테스트를 찾아라."
- "이 게이트는 **어디서 도는가**? 로컬에서만 도는가, CI 잡에 배선돼 있는가, 아니면 아무 데서도 안 도는가? CI 설정 파일에서 실제 실행 경로를 짚어라."
- "이 검사가 대조하는 **기준이 검사 대상 자신에게서 나오지 않는가**? 생성기가 만든 fixture를 그 생성기의 선언과 대조하는 구조, 구현을 복사한 기대값, 자기가 쓴 파일을 자기가 읽는 검증을 찾아라."
- "성공/실패 판정이 **대리 지표**로 이뤄지는가? 지적 건수를 변경 여부로, 종료 코드 0을 '검토했다'로, 테스트 통과를 '그 경로가 돌았다'로 바꿔 읽는 자리를 찾아라."
- "이 규칙·패턴의 **범위가 근거보다 넓은가**? 한 건의 사고를 막으려고 전역 무시·전역 예외·광범위한 억제를 넣어, 앞으로 같은 사고가 **보이지 않게** 되는 자리를 찾아라."
- "이 장치를 제거하면 **정확히 무엇이 깨지는가**? 떼어도 아무 테스트가 깨지지 않는 장치를 지목하라."

**`adversarial`을 쓴다.** 이 축의 결함은 "동작하지 않는다"가 아니라 "**동작하는 것처럼 보이면서 아무것도 재지 않는다**"이고, 일반 리뷰 프롬프트는 초록불을 결함으로 의심하지 않는다.

## 5. 교차 대조 종합 형식

**누가 언제 쓰는가**: §2.1의 3단계에서 **`migration-reviewer`가 2차 호출로** 작성한다. 1단계 병렬 리뷰 중에는 쓰지 않는다 — 그 시점엔 상대 산출물이 없다. 입력은 `..._codex-reviewer.md`와 `..._migration-reviewer.md` 두 파일이고, 출력은 `..._cross.md` 하나다. 이 호출은 **대조만** 하며 새 지적을 만들지 않는다.

codex 리뷰와 Claude 리뷰를 합칠 때 아래 표를 쓴다. 표 위에는 두 리뷰의 실행 조건(모드, scope, base, focus, 실행 시각)과 입력 파일 두 경로를 적어 재현 가능하게 남긴다.

| # | 지적 사항 | 출처 | 심각도 | 마감 | 근거 파일·라인 | 상충 | 권고 |
|---|---|---|---|---|---|---|---|
| 1 | Jackson이 응답 필드를 camelCase로 직렬화 | 양쪽 | Critical ① | 즉시 | `api/.../DocumentResponse.kt:24` | - | 수정 후 재리뷰 |
| 2 | lease 만료 재처리 시 중복 LLM 호출 가능 | codex | Critical ① | 즉시 | `worker/.../ConversionWorker.kt:88` | - | 근거 확인 필요 |
| 3 | parity 비교기가 위조된 증거 파일을 통과시킴 | 양쪽 | Critical ② | Phase 2 착수 전 | `compare_parity.py:204` | - | 수정 필요 |
| 4 | 소유권 검사 순서 문제 | Claude | Major | Phase 3 종료 전 | `application/.../DocumentService.kt:41` | 상충 | 사용자 판단 |

컬럼 규칙:

- **출처**: `codex` / `claude` / `양쪽` 중 하나. 반드시 채운다. 출처가 사라지면 독립성 정보가 사라져 교차 대조 자체가 무의미해진다. (§6 파일명 규약의 `{reviewer}`와는 별개 축이다 — 여기는 *어느 모델이* 그 지적을 냈는지를 표시한다.)
- **심각도**: `Critical` / `Major` / `Minor` / `제안`. Critical은 **두 갈래**이며 둘 다 같은 무게다.
  - **① 사건** — 계획 §5 Phase 7(2차 개정)의 즉시 중단 기준(AEAD round-trip 실패 또는 변조가 예외 없이 통과, 타 사용자 데이터 노출, 마스킹 전 전송, 중복 LLM 호출·작업 유실, 문서 추출·내보내기의 필수 정보 누락, 최대 2회 호출 위반)에 해당하는 일이 실제로 일어나는 경로.
  - **② 장치** — 그 사건을 탐지·차단하는 게이트가 무력화된 상태(검증 없이 통과하는 경로, 위조 가능한 증거 파일, 검사 대상 0건인데 성공으로 끝나는 스크립트 등). 게이트의 목적이 ①을 막는 것인데 장치가 무력하면 사건이 나도 알지 못하므로, Kotlin 코드가 아직 0줄이어도 Critical로 센다.
  - 심각도와 **"착수를 차단하는가"는 별개 축이다.** 그 판정은 오케스트레이터가 "해당 게이트가 처음 실제로 쓰이는 시점"을 기준으로 따로 내린다 — 아직 쓰이지 않는 게이트의 ② Critical은 다음 단계 착수를 막지 않고 그 시점 전까지 닫으면 된다. 리뷰는 심각도와 **언제까지 닫아야 하는지**(첫 실사용 Phase)를 함께 적고, 차단 여부는 판정하지 않는다.
- **마감**: `Critical`·`Major` 행에 필수. 그 게이트·코드가 **처음 실제로 쓰이는 시점**을 적는다(`즉시` / `Phase N 착수 전` / `Phase N 종료 전`). 차단 여부의 판정은 오케스트레이터 몫이며, 이 칸은 그 판정의 입력이다.
- **근거 파일·라인**: codex가 준 경로·라인은 **그대로 옮긴다.** 다시 세거나 바꾸지 않는다.
- **상충**: 두 리뷰가 반대 결론이면 `상충`. 표 아래에 양쪽 주장과 각 근거를 인용해 붙인다.
- **권고**: `수정 필요` / `근거 확인 필요` / `사용자 판단` / `기각(근거 첨부)` 중 하나.

판단 규칙:

1. **양쪽이 같은 지적 → 신뢰도 높음.** 서로 다른 맥락에서 같은 결론에 도달했으므로 근거 재확인 없이 수정 대상으로 올린다.
2. **codex만 지적 → 근거를 먼저 확인한다.** 맥락을 몰라 생긴 오탐일 수도, 우리가 맥락에 취해 못 본 진짜 결함일 수도 있다. 확인 없이 기각하는 것이 이 게이트에서 가장 흔한 실패다.
3. **Claude만 지적 → codex가 못 본 이유를 적는다.** diff 범위 밖이라 안 보였는지, focus에서 빠졌는지. 후자면 focus를 고쳐 재리뷰한다.
4. **상충 → 양쪽 병기 후 사용자에게.** 특히 "원래 Python 동작이 무엇이었나"에 대한 상충은 Python 원본을 실행해 증거를 만들기 전에는 결론 내지 않는다.
5. **Critical이 하나라도 남으면 Phase 종료를 보고하지 않는다.** ② 장치 Critical도 여기 포함된다 — 다만 각 항목에 **마감(첫 실사용 Phase)**을 적어 올리고, 마감이 이후 Phase인 항목을 그 단계의 착수 차단으로 볼지는 오케스트레이터가 판정한다. 리뷰가 임의로 "아직 안 쓰이니 Critical 아님"으로 낮추지 않는다.

## 6. 산출물 경로

```
docs/migration/_workspace/reviews/{phase}_{scope}_{reviewer}.md
```

- `{phase}`: `00`~`09` (계획 §5의 Phase 번호). Phase 밖 임시 리뷰는 `xx`.
- `{scope}`: **정본은 `kotlin-migration` 스킬 "리뷰 게이트 → `{scope}` 정본" 표 하나뿐이다.** 여기에 값을 다시 적지 않는다 — 값을 여러 문서에 복제한 것이 슬러그가 세 갈래로 갈린 원인이었다. 리더가 1단계 호출에서 지정한 어간을 그대로 쓰고, 표에 없는 값이 필요하면 표에 먼저 추가한다.
- `{reviewer}`: `codex-reviewer` / `migration-reviewer` / `privacy-gate` / `cross` 중 하나. 앞의 셋은 **작성한 에이전트 이름 그대로**이고, `cross`만 예외적으로 교차 종합본을 뜻한다. 파일명만 보고 누가 쓴 것인지 알 수 있어야 출처를 되짚을 수 있다.

예: `docs/migration/_workspace/reviews/04_crypto_codex-reviewer.md`, `.../04_crypto_migration-reviewer.md`, `.../04_crypto_cross.md`

한 게이트의 세 파일은 **같은 `{phase}_{scope}` 어간**을 공유해야 한다. 어간이 갈리면 3단계 교차 종합이 자기 입력 파일을 찾지 못해 `..._cross.md`가 아예 만들어지지 않는다 — 1·2단계가 정상으로 보여도 게이트는 닫히지 않는다.

`cross` 파일이 사용자에게 제출하는 정본이지만, `codex-reviewer` 원본 파일을 **반드시 남긴다.** 원본이 없으면 종합 과정에서 무엇이 잘려 나갔는지 아무도 확인할 수 없고, 독립 리뷰를 받았다는 사실 자체를 검증할 수 없다.

`codex-reviewer` 파일에는 최소한 이것을 적는다: 실행 명령 전문(스크립트 인자 그대로), **스크립트 종료 코드**, 사용한 헬퍼 경로와 버전, 모드·scope·base, focus text 전문, codex 출력 원문, job id, 그리고 스크립트가 stderr에 찍는 **대상 판정 두 줄**(`codex-review: 리뷰 대상 = ...` / `codex-review: 대상 판정 = ...`). 대상 판정 줄이 없으면 "무엇을 리뷰했는가"를 나중에 확인할 방법이 없고, 그것이 빈 리뷰가 통과 기록으로 남는 경로였다.

## 7. 실패 처리

**공통 원칙: 1회 재시도 → 재실패하면 codex 결과 없이 진행하되, 산출물 맨 위에 "⚠ codex 리뷰 누락(사유: ...)"을 명시한다.** 조용히 통과시키면 필수 게이트가 형식만 남고, 나중에 "리뷰를 통과했다"는 기록만 남아 더 나쁘다.

| 증상 | 판별 | 대응 |
|---|---|---|
| 헬퍼 미발견 (exit 3) | 스크립트가 확인 절차를 출력 | 플러그인 설치/갱신 확인 → `CODEX_COMPANION`으로 직접 지정 → 그래도 없으면 codex CLI 폴백 확인. 전부 실패 시 누락 명시 |
| codex CLI 미설치·미인증 | `node <헬퍼> setup --json`의 `ready`/`auth.loggedIn`이 false | `npm install -g @openai/codex`, `codex login` 안내. 스킬이 임의 인증 흐름을 만들지 않는다 |
| Bash 도구 타임아웃 | 도구가 잘림 | job은 살아 있다. **재실행하지 말고** `status --all`로 job id를 찾아 `result <job-id>`로 회수 |
| 리뷰 자체 실패 | 헬퍼 stderr | 가장 실행 가능한 stderr 줄을 산출물에 그대로 인용하고 1회 재시도. 추측으로 메우지 않는다 |
| 사용법 오류 | exit 2 | 모드·옵션·`--scope` 값을 고친다 (`--help` 참고) |
| **리뷰 대상 없음** | exit 7 | 리뷰가 돌지 않았거나 아무것도 보지 않았다. `git status` / `git log --oneline -5`로 실제 상태를 확인하고 `--base`·`--scope`를 **바로잡아** 재실행한다. 같은 인자로 재시도해 통과시키려 하지 마라 — 결과는 같고, 통과해도 근거가 아니다. 이 코드는 §7 공통 원칙의 "1회 재시도" 대상이 아니다(도구 실패가 아니라 요청 오류다) |
| 리뷰 도구 출력이 비었음 | exit 5 | 헬퍼 경로·codex 인증(`codex login`)을 점검하고 1회 재시도. 빈 출력은 "지적 없음"이 아니다 |
| 지적 0건 | exit 0 + "No material findings" | "지적 없음"을 그대로 기록한다. Claude가 대신 지적을 만들어 채우지 않는다 — 그건 독립 리뷰가 아니다. **단 exit 0일 때만 그렇게 기록한다** (5·7은 지적 0건이 아니라 리뷰 근거 없음이다) |

절대 하지 않는 것:

- codex가 실패했을 때 Claude가 codex 역할을 대신 수행해 "codex 리뷰"라고 적는 것
- codex 출력이 짧다는 이유로 Claude 리뷰를 codex 리뷰 칸에 채우는 것
- 리뷰 결과를 받자마자 지적 사항을 자동으로 고치는 것 — **먼저 표로 제시하고 무엇을 고칠지 확인받는다** (codex 플러그인의 결과 처리 계약과 동일)

## 8. 실행 체크리스트

- [ ] 면제 대상(§2.2)이 아님을 확인 — `.claude/**` 하네스 수정은 면제가 아니다
- [ ] `{phase}_{scope}` 어간을 리더 지정값(정본 표 기준)으로 확정 — 세 산출물이 같은 어간을 쓴다
- [ ] 위험 영역(§3.2)이면 `adversarial` + focus text 준비
- [ ] **§4.6(선언 범위 대 실제 도달)을 focus에 포함** — 게이트·불변식·규칙을 세우거나 넓히는 변경이면 필수. codex가 이 축에서 지적을 내지 않았으면 그 사실을 그대로 기록한다(§7) — 대신 채우지 않는다
- [ ] `--dry-run`으로 헬퍼 경로·scope·명령 확인 — 이때 찍히는 `대상 판정` 줄이 `non-empty`인지 본다
- [ ] Bash 도구 timeout 600000 또는 `run_in_background`로 실행
- [ ] **스크립트 종료 코드가 `0`인지 확인** — `0`이 아니면 리뷰 근거가 아니다. 특히 `7`(리뷰 대상 0건)은 "지적 없음"이 아니라 "아무것도 리뷰하지 않았음"이다
