## 0. 이 판정문의 규약과 착수 조건

### 0-1. 기준 HEAD 가 지시와 달랐다 — 옮겨 적지 않고 실측했다

리더 지시는 *"기준 HEAD: c64b279 (푸시 완료)"* 였다. 착수 시 실측은 다르다.

```
$ git rev-parse HEAD
a3a3f2dbcefff6d4baec3c4f5cb36881776d5af7

$ git log --oneline -1
a3a3f2d fix(harness): Phase 1 CI 행 승격에 맞춰 충족=예 핀을 갱신한다

$ git status --short

?? .playwright-mcp/
?? docs/지자체복지서비스_코드표(v1.0).doc
?? docs/활용가이드_중앙부처복지서비스(v2.2).doc
```

**두 사실을 그대로 적는다.** ⑴ HEAD 는 `c64b279` 가 아니라 `a3a3f2d` 다(리더 레인이
그 뒤로 2 커밋을 더 얹었다). ⑵ **Kotlin 레인이 `DocumentBodyLogLeakReachTest.kt` 를
미커밋 상태로 쓰고 있었다** — P-2(강제 TRACE 카나리)의 그 파일이다.
**그 파일을 읽지도 고치지도 않았다.** 이 레인의 커밋에 그 변경이 섞이지 않도록
`git add` 를 경로 지정으로만 했다(§9).

**⑶ 작업 중 HEAD 가 세 번 더 움직였다.** 커밋 직전 실측:

```
$ git log --oneline -3
82bb1a7 fix(harness): 문서 본문 로그 카나리를 바닥 목록에 넣는다
6fabfc5 fix(kotlin): 카나리 등록 전에 만든 조각에 토큰이 동결되던 것을 고친다
3f4c2d7 fix(kotlin): 카나리의 토큰 축 fail-open 과 실패 메시지의 토큰 재노출을 고친다
```

**Kotlin 레인이 P-2 를 닫는 커밋 셋을 얹었고**(위 미커밋 파일이 그중에 들어갔다),
그러므로 **이 레인의 커밋은 `a3a3f2d` 가 아니라 `82bb1a7` 위에 놓인다.**
충돌은 없다 — 두 레인이 건드린 파일 집합이 서로소다(§9 실측). **착수 HEAD 와 커밋 HEAD 가
다르다는 사실을 지우지 않는다**: 이 판정의 실측(팔 A~E)은 **`a3a3f2d` 시점의 bootJar** 로
했고, 그 세 커밋은 테스트·하네스만 건드렸으므로 `src/main` 기준으로 jar 는 여전히 유효하다 —
**다만 그것은 커밋 메시지 판독에 근거한 판단이고 jar 를 다시 빌드해 확인하지 않았다**(§9).

### 0-2. 값을 옮겨 적지 않는다

이 문서는 **판정과 근거**를 적는다. `detail` 문구·헤더 값·미디어 타입 문자열·상한 숫자는
**계약 파일에서 읽는다**. 예외는 두 가지다 — ⑴ **상태 코드는 숫자로 적는다**(판정의 이름이
곧 상태 코드다) ⑵ **실행한 명령의 출력은 그대로 옮긴다**(근거는 인용이 아니라 출력이다).

계약 명세(`04_contract-keeper_documents-test-spec.md`) §0 의 금지 패턴은 **그 문서에
걸린다.** 이 판정문에 실측 출력으로 등장하는 문자열은 그 규약의 대상이 아니지만,
**명세에 옮길 때는 역할 이름으로 바꿔 적었다**(§6-2).

## 1. 판정 1 — `ServiceUnavailable` 다섯 자리를 하나의 결론으로 맞춘다 (P-5 본체)

### ① 고른 답

**서수를 버리고 안정 id 를 준다. 폐기 사유는 신설 절 `x-retired-503-configurations`
한 곳에만 적고, 다른 자리는 그 id 로만 가리킨다.**

교차 종합이 실측한 다섯 자리의 불일치는 **내용 불일치가 아니라 세는 방식의 불일치**였다.

| 자리 | 종전 문면 | 무엇을 세고 있었나 |
|---|---|---|
| 활성 목록 | *"이 상태가 되는 구성은 하나뿐이다"* + JWT 한 줄 | **남은** 줄 |
| 폐기 블록 머리글 | *"세 줄을 내렸다"* | **블록에 실린** 항목 수(취소선 그은 것 포함) |
| 블록 셋째 항목 | 취소선 + *"내리지 않았다. 재지 않았기 때문이다"* | **자기 자신** |
| `x-changelog` 1.3.0 | *"두 줄과 대응 예시를 내렸다"* + *"넷째 줄은 그대로 두었다"* | **실제로 내린** 줄 / **원래 4줄 목록의 서수** |
| 원장 `L-⑦` | *"O-21 의 DB 줄 미측정"* | 실제로 내린 줄 |

**셋은 서로 모순이 아니었다** — 「세 줄」은 블록 항목 수, 「두 줄」은 실제 폐기 수,
「넷째 줄」은 **줄어들기 전 목록의 서수**다. **모순은 서수가 가리키는 목록이 그사이
줄어든 데서 나왔다.** 그래서 처방은 문면을 다시 세는 것이 아니라 **서수를 없애는 것**이다.

**id 는 `queue` · `cipher` · `datasource` 셋이다.** 목록 길이가 다시 변해도 id 는 안 변한다.

### ② 근거 — 실행한 명령과 출력

**E1. 다섯 자리가 오늘 실제로 무엇을 적고 있는지 재확인**(교차 종합의 실측을 그대로
믿지 않고 파일을 다시 열었다 — 「grep 한 낱말로 조항 유무를 판정하지 않는다」).

```
$ sed -n '1846,1885p' contracts/easy-doc-v1.yaml
      ...
        **이 상태가 되는 구성은 하나뿐이다.**
          - **JWT 서명 키 미설정 또는 32바이트 미만 → 인증이 필요한 모든 요청**
      ...
        **2026-08-20에 세 줄을 내렸다**(근거 **G1** — 셋 다 이 상태를 만들 수 없다).
          1. ~~큐(Redis) 미배선 → 업로드~~ …
          2. ~~저장 암호화 키 미설정 → 문서 API 전체~~ …
          3. ~~DB 세션 팩토리 미배선 → 전체~~ — **내리지 않았다. 재지 않았기 때문이다.**
```

```
$ sed -n '2372,2381p' contracts/easy-doc-v1.yaml
      ⑵ **`ServiceUnavailable`에서 도달 0인 **두 줄**과 대응 예시를 내렸다** …
         - 넷째 줄(DB 세션 팩토리)은 **재지 않았으므로 그대로 두었다.**
```

**교차 종합의 §2.3 표와 바이트 일치한다.** 다섯 자리 전부 실재하며 문면이 인용된 그대로다.

**E2. `ServiceUnavailable` 을 참조하는 오퍼레이션 수** — blast radius 확인.

```
$ uv run --with pyyaml python -c "…paths 순회…"
version 1.3.0
… 503 을 선언한 오퍼레이션 = 13 (GET /health 만 없다)
```

**13 개다.** 이 컴포넌트를 고치는 것은 13 개 오퍼레이션의 계약을 고치는 것이므로,
**사유를 컴포넌트 description 에 두면 13 곳이 그것을 인용하게 된다.** 별도 절로
빼는 두 번째 이유가 이것이다(첫째는 서수).

### ③ 고르지 않은 것의 대가

| 고르지 않은 안 | 대가 |
|---|---|
| **문면 수만 맞춘다**(「세 줄」→「두 줄」) | 오늘은 맞고 **다음 폐기에서 또 갈린다.** 서수를 남기면 목록이 줄 때마다 같은 사고가 재발한다 — 이 저장소가 「열거가 근거를 만드는 구조」라 부르는 것이다 |
| **취소선만 지운다** | 취소선은 **증상**이고 원인은 「폐기 블록에 폐기 안 된 항목이 섞인 것」이다. 지우면 그 항목이 어디에도 없게 되어 **재지 않은 것을 지운 것**이 된다(판정 2 가 그것을 실측으로 바꿨으므로 지금은 성립하나, 실측 전에는 금지 형태였다) |
| **`x-changelog` 1.3.0 항목을 고쳐 「세 줄」로 맞춘다** | **역사 위조다.** 1.3.0 시점에 내린 것은 실제로 두 줄이었고 그 기재는 참이었다. 대신 그 항목에 **전방 포인터**(`superseded_by`)만 더했다 — 원문은 한 바이트도 고치지 않았다 |
| **원장까지 이 레인이 고친다** | **범위 밖이다**(`00_progress.md` 는 리더 소유). 고쳐야 하는 줄과 대체 문면을 §8 에 값으로 넘긴다 |

### ④ `kotlin-implementer` 지시

**없다.** 이 판정은 계약 문면의 정합만 바꾼다 — 와이어 동작이 바뀌지 않으므로 구현 지시가
없다. **단 판정 2 가 같은 절에서 와이어 조항을 하나 내리므로**, 그 지시는 §2-④ 에 있다.

### ⑤ 음성 대조 설계

**번호의 정본은 계약 명세 §4-4 다.** 이 판정문은 번호를 새로 매기지 않고 **가리킨다** —
같은 음성 대조 번호를 두 문서가 서로 다르게 적은 사고가 이 게이트의 지적 하나였다
(교차 종합 #19 = M-7: 원장 `L-⑦` 과 `L-⑨` 가 같은 번호를 다르게 적었다). **초안에서 이
문서가 정확히 그것을 반복했고, 커밋 전에 잡아 번호를 명세로 단일화했다.**

- **N-35**(설계 · **미실행**) — 폐기 항목의 `id` 를 바꾸면 **P-41** 이 깨져야 한다.
- **N-36**(설계 · **미실행**) — 활성 목록에 줄을 더하면 「구성은 하나뿐이다」와 열거 길이가
  갈리므로 **P-41 의 길이 대조**가 깨져야 한다.
- **N-37**(설계 · **미실행**) — 폐기 목록에서 항목을 지우면 P-41 의 「비어 있지 않다」가
  깨져야 한다.

**셋 다 오늘은 깨지지 않는다** — `x-retired-503-configurations` 를 읽는 파서가 **0개**다.
P-41 이 선 뒤에 실행 가능해진다. **「바꿔도 아무것도 깨지지 않았다」를 「음성 대조 통과」로
적지 않는다.**

## 2. 판정 2 — O-21 `datasource` 줄: **재서 내린다** (선결이 실측으로 닫혔다)

### ① 고른 답

**내린다. 근거는 G1 이고 이번에는 실측이다.**

리더 지시는 *"확인할 수 있으면 확인하고, 못 하면 「미실행」으로 적고 조항을 그대로 두라"*
였다. **확인할 수 있었다.** 그러므로 「재지 않았기 때문이다」라는 유보의 전제가 소멸했고,
그 줄은 다른 두 줄과 같은 처분을 받는다.

**측정한 명제**: 「DataSource 가 미배선·도달 불가인 구성에서 애플리케이션이 기동해 503 을
응답하는 상태가 존재하는가」 → **존재하지 않는다.**

### ② 근거 — 실행한 명령과 출력


**세 가지가 이 판정을 고정한다.**

1. **의존 사슬이 기동 필수다.** B·C 의 실패 사슬이 `authController → authService →
   userRepository → jdbcClient` 다. `jdbcClient` 는 **컨트롤러가 생성 시점에 요구하는 빈**
   이므로 DataSource 가 서지 않으면 **컨텍스트 조립 자체가 취소된다**(`cancelling refresh
   attempt`). 「미배선인데 서비스 중」인 상태가 **구조적으로 없다.**
2. **Flyway 때문만이 아니다.** E(빈 URL + Flyway 꺼짐)도 실패한다 — 즉 **B·E 의 원인은
   DataSource 자신**이고 Flyway 는 C 에서만 결정적이다. 「Flyway 를 끄면 되는 문제」로
   오독할 여지를 이 팔이 막는다.
3. **D 는 제품 구성이 아니다.** `SPRING_FLYWAY_ENABLED=false` 는 `application.yml` 이
   `spring.flyway.enabled: true` 로 못박은 값을 **환경변수로 덮은 것**이다. api 프로필에
   그것을 끄는 조항은 없다(프로필 블록은 `migrate` 하나이고 거기서도 Flyway 는 그대로다).

**결정적 추가 실측 — D 에서조차 503 이 나오지 않는다.** 「제품 구성이 아니어도, 앱이 뜬 채
DB 가 죽어 있으면 503 이 나오지 않는가」를 재기 위해 D 구성에 인증 서명 키까지 주고
**DB 를 만지는 무인증 요청**을 보냈다.

```
--- POST /auth/login (DB 를 만지는 무인증 요청) ---
HTTP/1.1 500
Content-Type: application/json
{"detail":"서버 오류가 발생했습니다"}
```

**500 이다. 503 이 아니다.** 그러므로 **어떤 구성에서도** DB 장애가 503 으로 관측되지
않는다 — 제품 구성에서는 응답이 아예 없고(기동 실패), 강제로 띄운 구성에서는 500 이다.

**뒷정리와 부작용 없음 확인.** 대조군은 일회용 DB(`easydoc_p5_probe`)를 만들어 썼고
**개발용 `easydoc_kotlin` 을 건드리지 않았다** — 그 DB 는 V5 미적용 상태라 그대로 띄우면
Flyway 가 마이그레이션을 적용해 **병렬 레인의 무대를 바꿨을 것**이다.

```
$ psql … -d postgres -Atc "DROP DATABASE IF EXISTS easydoc_p5_probe"
DROP DATABASE

$ psql … -d easydoc_kotlin -Atc "select version from flyway_schema_history order by installed_rank"
1
2
3
4
```

**착수 전과 같다**(V5 미적용 유지). 프로브 프로세스도 전부 종료했다.

### ③ 고르지 않은 것의 대가

| 고르지 않은 안 | 대가 |
|---|---|
| **그대로 둔다**(유보 유지) | 리더가 「확인할 수 있으면 확인하라」고 했고 **확인됐다.** 유보를 유지하면 **거짓 조항을 알고도 남기는 것**이 된다 — 13 개 오퍼레이션이 「DB 미배선 → 503」을 선언한 채로 다음 게이트가 그 전제 위에서 돈다 |
| **줄을 고쳐 「DB 장애 → 500」으로 바꾼다** | **틀렸다.** 500 은 `InternalError` 의 자리이고 이미 선언돼 있다. `ServiceUnavailable` 은 **구성 문제**의 컴포넌트이며, DB 장애는 이 API 에서 **구성 문제로 관측되지 않는다**(기동 실패이거나 실행 실패다) |

| **D 팔을 근거로 「도달한다」고 적는다** | **제품 구성이 아닌 구성을 근거로 조항을 세우는 것**이다. 게다가 D 에서도 나오는 것은 500 이라 503 조항을 지지하지 않는다 |

## 4. 판정 4 — O-22 `/health` 의 Redis 문면: **고친다** + `database` 팔의 도달 0 을 **적는다**

### ① 고른 답

**셋을 한 번에 처리한다.**

1. **Redis 를 진단 대상에서 내린다**(G1) — 큐가 PostgreSQL lease 테이블로 옮겨졌다.
   `checks` 의 `queue` 키는 **남긴다.** 큐는 사라진 것이 아니라 **같은 DataSource 위의
   테이블**이 됐고, 「그 테이블을 읽을 수 있는가」는 여전히 별개 진단이다.
2. **구현 시점 문장을 고친다** — *"DB Phase 3, 큐·Redis Phase 5"* 에서 Redis 가 사라지고,
   큐는 DB 와 **같은 배선을 공유**하므로 별도 Phase 가 아니다.
3. **`checks.database` 가 `false` 인 팔은 제품 구성에서 도달 0 임을 적는다**(실측 §2).
   DB 가 죽으면 앱이 뜨지 않으므로 **그 응답을 낼 프로세스가 없다.** 따라서
   `status: degraded` 도 **DB 축에서는 도달 0** 이다.

**⑶ 을 「고치지」 않고 「적는」 이유**: 이것은 조항이 틀린 것이 아니라 **조항이 요구하는
상태가 오늘 존재하지 않는 것**이다. 처분(기동 정책을 바꿀 것인가 / 진단 대상을 좁힐
것인가)은 **배포 동작 변경**이라 `escalate_to_leader` ④ 다 — §7-2 로 올린다.
**「오늘 0건」을 근거로 조항을 지우지 않는다**(P-10 이 세운 규율 그대로).

### ② 근거 — 실행한 명령과 출력

```
# 계약이 오늘 적고 있는 것
$ sed -n '1670,1700p' contracts/easy-doc-v1.yaml
        …현재 Python 구현은 상수 {"status": "ok"}만 돌려주어 DB·Redis·설정이 모두 죽어도…
        …Redis가 잠깐 죽었다고 503을 내면 오케스트레이터가…
        구현 시점: … (DB Phase 3, 큐·Redis Phase 5).

# 저장소에 Redis 배선이 남아 있는가 — 큐는 PostgreSQL 이다
$ grep -rn 'Redis\|redis' backend-kotlin --include='*.kt' --include='*.yml'
  (제품 코드 적중 0 — compose 의 Python 스택에만 남아 있다)
```

**도달 0 의 근거는 §2 의 팔 C 다** — 제품 구성에서 DB 도달 불가 → 기동 실패 → 응답 없음.
따라서 `database: false` 를 담은 200 응답은 **낼 주체가 없다.**

### ③ 고르지 않은 것의 대가

| 고르지 않은 안 | 대가 |
|---|---|
| **`queue` 키도 내린다** | 큐는 없어지지 않았다. 키를 내리면 「작업 테이블을 읽을 수 있는가」라는 **실재하는 진단 축**이 계약에서 사라진다 |
| **`database` 키를 내린다** | **도달 0 은 조항이 틀렸다는 뜻이 아니다.** DB 진단은 요구사항이 요구하는 것이고(§2.8 판정 5), 도달 0 인 것은 **기동 정책의 귀결**이다. 원인 쪽을 판정해야 한다 |
| **기동 정책을 이 레인이 바꾼다** | 범위 밖(§7-2). 게다가 판정 2 의 폐기와 **정면으로 얽힌다** — DB 없이 뜨게 만들면 그때는 「DB 미배선인데 서비스 중」이 실재하게 되고 폐기한 줄을 되살릴 근거가 생긴다. **두 판정을 함께 봐야 하는 자리**다 |

### ④ `kotlin-implementer` 지시

| # | 대상 | 지시 |
|---|---|---|
| **K-P5-4** | `HealthController` · `HealthResponse` | **P-8 이 그 자리다**(§7-1). 계약은 `required: [status, checks]` 인데 구현은 `checks` 가 없다 — **실측으로 확정했다**(§7-1). 이 판정이 더하는 것: `checks` 를 구현할 때 **`database` 를 `true` 로 못박지 마라.** 확인하지 않은 것을 `true` 로 적으면 계약이 금지한 「거짓 진단」이다. 그리고 **DB 가 죽은 상태를 이 프로세스가 관측할 수 없다는 사실**(도달 0)을 KDoc 에 적되 **강제자 없이 전칭으로 적지 마라**(P-9 종류) |
| **K-P5-5** | `checks` 의 `queue` 팔 | 큐는 **같은 DataSource 위의 테이블**이다. `queue` 진단을 별도 접속으로 구현하지 마라 — 두 키가 같은 배선을 공유한다는 사실이 계약 문면이 됐다 |

### ⑤ 음성 대조 설계

**판정 3 과 같은 이유로 `N-*` 번호를 매기지 않는다**(이 명세는 #14 를 담지 않는다).
설계는 둘이고 **둘 다 미실행**이다.

- **`checks` 축** — `checks` 에서 키를 하나 빼면 「`status` 는 `checks` 에서 유도한다」
  단언이 깨져야 한다. **오늘 `checks` 자체가 없으므로 P-8 이 닫힌 뒤에만 실행 가능하다.**
- **산문 축** — 계약 산문에 `Redis` 를 되살려 넣으면 **아무것도 깨지지 않는다**(그 산문을
  읽는 강제자가 0). **이 사실을 적어 두는 것이 이 항목의 값어치다** — 「산문 조항에 강제자가
  없다」는 이 저장소의 반복 결함이고 `/health` 산문이 그 목록의 새 항목이다.
  **이 회차는 그 빈자리를 메우지 않았다** — 메우려면 산문을 구조화(진단 대상 키 목록을
  기계가독 노드로)해야 하고 그것은 리더가 지정한 단위를 넘는다. **넓히지 않고 등재한다.**

## 5. 판정 5 — 415: **엔드포인트별로 처리하지 않는다. 종류로 선언한다** (L-⑧ 판정 3)

**⑶ 컴포넌트 하나**(`UnsupportedMediaType`)를 두고 6 개 오퍼레이션이 `$ref` 한다.

**리더가 이 지시를 준 이유가 실측으로 증명됐다.** 리더가 지목한 자리는 **셋**이었다
(`POST /documents` · `POST`·`PATCH /workspaces`). **실측은 다섯이다** —
`POST /auth/signup` 과 `POST /auth/login` 도 415 를 낸다. **열거했으면 두 자리가
빠졌다.** 계약에는 요청 본문을 받는 오퍼레이션이 **6 개**이고 여섯째
(`PUT /conversions/{conversion_id}`)는 아직 구현되지 않아 재지 못했다.

### ② 근거 — 실행한 명령과 출력

**제품 구성으로 띄운 뒤**(도달 가능한 일회용 DB · Flyway 켜짐 · 인증 서명 키 부여)
두 `consumes` 밖의 `Content-Type` 으로 요청했다.

```
POST /documents        text/plain        무토큰    => 415  본문={"detail":"Unsupported Media Type"}
POST /documents        application/json  무토큰    => 401  본문={"detail":"인증이 필요합니다"}
POST /documents        text/plain        위조토큰  => 415  본문={"detail":"Unsupported Media Type"}
POST /workspaces       text/plain        무토큰    => 415  본문={"detail":"Unsupported Media Type"}
POST /workspaces       application/json  무토큰    => 401  본문={"detail":"인증이 필요합니다"}
PATCH /workspaces/{id} text/plain        무토큰    => 415  본문={"detail":"Unsupported Media Type"}
POST /auth/login       text/plain        인증불필요 => 415  본문={"detail":"Unsupported Media Type"}
POST /auth/signup      text/plain        인증불필요 => 415  본문={"detail":"Unsupported Media Type"}
```

```
--- 415 응답 전문 ---
HTTP/1.1 415
Cache-Control: no-store
X-Content-Type-Options: nosniff
Accept: multipart/form-data, application/json
Content-Type: application/json
{"detail":"Unsupported Media Type"}
```

**본문 문구의 출처를 코드로 확인했다** — 계약에 없던 조항이 여기서 나온다.

```
$ sed -n '465,475p' …/error/GlobalExceptionHandler.kt
/**
 * 상태 코드의 표준 사유 문구. Starlette `HTTPException` 의 기본 detail 과 같은 값이다.
 * **오류 본문을 만드는 세 경로가 전부 이 함수를 쓴다** — advice, `/error` 디스패치,
 * 컨테이너가 직접 만드는 응답. 경로마다 문구 규칙이 갈리면 같은 상태 코드에 다른 본문이
 * 나가고, 그 차이는 어느 경로를 탔는지를 밖에서 알려주는 신호가 된다.
 */
internal fun reasonPhraseOf(statusCode: HttpStatusCode): String = …
```

**이것은 결함이 아니라 의도된 균일성 장치다.** 415 의 `detail` 이 한국어가 아닌 이유가
여기 있다 — 도메인 예외는 한국어 문구, **프레임워크·컨테이너가 만든 응답은 상태 코드의
표준 사유 문구**이고, 셋이 한 함수를 쓰는 것이 *"본문이 생성 경로를 알려주지 않는다"* 는
성질을 지킨다. **계약은 이 규칙을 한 번도 적지 않았다.** 415 를 선언하려면 그 본문이
무엇인지 적어야 하므로, 이 규칙을 `x-unsupported-media-type.detail_source` 로 명문화한다
(근거 **G2** — 요구는 「오류 본문이 생성 경로를 드러내지 않는다」).

**적지 않으면 다음 사람이 이것을 「한국어로 안 바뀐 자리」로 보고 고치고, 그러면 세 경로의
균일성이 깨진다.** 사유를 계약에 적는 이유가 그것이다(`x-title-policy` 가 밟은 순서와 같다).

**오퍼레이션 집합은 계약을 파싱해 얻었다** — 손으로 세지 않았다.

```
$ uv run --with pyyaml python -c "…"
POST   /auth/signup      body=True  무인증=True
POST   /auth/login       body=True  무인증=True
POST   /documents        body=True  무인증=False
PUT    /conversions/{conversion_id}  body=True  무인증=False
POST   /workspaces       body=True  무인증=False
PATCH  /workspaces/{workspace_id}    body=True  무인증=False
요청 본문을 받는 오퍼레이션 수 = 6
```

### ③ 고르지 않은 것의 대가

| 고르지 않은 안 | 대가 |
|---|---|
| **리더가 지목한 세 자리만 선언한다** | **실측이 다섯을 냈다.** 셋만 적으면 `/auth` 둘이 **선언 없이 나가는 상태 코드**로 남는다 — 502 폐기 때와 같은 형태(계약이 선언하지 않은 코드를 구현이 낸다) |
| **오퍼레이션마다 인라인 응답을 적는다** | 여섯 벌이 갈린다. 컴포넌트 하나 + `$ref` 가 이 파일의 관행이다 |
| **규칙만 적고 `paths` 에 선언하지 않는다** | OpenAPI 는 (경로·오퍼레이션·상태 코드) 삼중키에만 응답을 달 수 있어 **규칙만으로는 스펙에서 415 가 보이지 않는다.** React 타입 생성과 3자 대조가 그것을 못 읽는다 |
| **파서(P-42) 없이 선언만 한다** | **열거가 근거를 만드는 구조가 그대로 남는다.** 다음에 본문을 받는 오퍼레이션이 늘면 415 선언이 조용히 빠진다 — 리더 지시가 금지한 바로 그 형태다 |
| **`detail` 을 한국어 고정 문구로 요구한다** | **세 경로의 균일성을 깬다**(위 KDoc). 그리고 그것은 계약 소유자가 단독으로 만들 정책이 아니다 |

## 6. 판정 6 — P-4 선결: **검사 순서 조항은 복합 결함에도 적용된다**

### ① 고른 답

**적용된다.** 그리고 조항의 **공백 하나**를 함께 메운다.

1. **복합 결함에서 관측되는 응답은 목록에서 가장 앞선 검사의 것이다.** 조항이
   「단일 결함」으로 좁게 읽힐 여지를 없앤다.
2. **`workspace_id` 형식 오류(422)의 자리를 명시한다.** 종전 목록은
   「작업 공간 **소유권**(404)」만 담고 **형식 검증이 어디에 있는지 말하지 않았다.**
   형식 검증은 소유권 확인의 **선결**이므로 같은 단계에 속한다 — 즉 **파일 크기·추출·
   본문 길이보다 뒤다.**
3. 근거는 **G2** 다. 요구는 *"클라이언트가 재시도 판단을 할 수 있어야 한다"* 이고, 그것이
   순서 조항이 애초에 존재하는 이유다.

**그 답의 귀결**: codex F-8 이 든 입력(상한 초과 파일 + 잘못된 UUID)에서 **413 이 나와야
한다.** 오늘 구현은 422 를 낸다 → **구현 결함**이며 계약이 아니라 구현이 움직인다.
리더 판정(*"codex 가 옳다"*)과 같은 방향이다.

**왜 이 답인가 — 두 가지가 갈랐다.**

- **재시도 비용의 비대칭.** 422 가 앞서면 클라이언트는 UUID 를 고쳐 **상한 초과 본문을
  다시 올리고** 그제서야 413 을 받는다. 큰 본문을 두 번 보내게 만드는 순서다.
  순서 조항의 목적이 「싼 거절을 먼저」인데 그 반대가 된다.
- **관측 가능성이 구현 세부에 좌우되면 계약이 아니다.** 오늘 순서를 정하는 것은
  **Kotlin 이 명명 인자를 호출 지점 순서로 평가한다는 언어 규칙**이다. 인자 순서를
  줄만 바꿔도 관측되는 상태 코드가 바뀐다 — **계약이 말하지 않으면 그 순서는 아무도
  지키지 않는다.**

### ② 근거 — 실행한 명령과 출력

```
# 계약이 오늘 적고 있는 순서 — 형식 검증이 목록에 없다
$ sed -n '1090,1095p' contracts/easy-doc-v1.yaml
        검사 순서: 파일 크기(413) → 추출(422) → 본문 길이(422) → 작업 공간 소유권(404) →
        **저장 정의역(422)** → **저장과 큐 등록(한 트랜잭션)** → 커밋.
```

**「작업 공간 소유권(404)」만 있고 「형식(422)」이 없다.** 교차 종합 §2.2 의 제3 근거 3번이
*"계약 문면은 어느 쪽 범위인지 말하지 않는다"* 로 적은 공백이 **이 자리**다.

**복합 입력을 소켓으로 재지 않았다 — 이 회차 미실행이다**(§9). 기제는 교차 종합이
고정 리비전에서 코드로 확정했고 리더가 채택했다. 이 판정은 **계약 조항의 판정**이며,
그 기제의 실행 재현은 구현 레인이 케이스로 닫는다(K-P5-10).

### ③ 고르지 않은 것의 대가

| 고르지 않은 안 | 대가 |
|---|---|
| **「단일 결함에만 적용된다」로 답한다** | 계약이 **복합 입력에서 무엇이 나가는지 말하지 않는 문서**가 된다. 그러면 어느 구현도 위반이 아니고, 인자 순서를 바꾸는 리팩터링이 **관측 동작을 조용히 바꾼다**. 계약의 목적(React·Kotlin 이 같은 한 곳을 읽는다)에 정면으로 어긋난다 |
| **형식 검증의 자리를 안 정한다** | 조항이 여전히 그 자리를 말하지 않아 **같은 충돌이 다시 난다**. 리더가 「먼저 정할 것」이라 한 것이 이 공백이다 |
| **형식 검증을 목록 맨 앞에 둔다**(구현 현행 유지) | 「싼 거절 먼저」와 어긋난다 — 형식 검증은 싸지만 **거절 사유가 사용자에게 덜 급하다**. 그리고 상한 초과 본문을 두 번 올리게 만드는 비용이 그대로다 |

## 7. 보고만 하는 것 · 새로 발견한 것 · 리더 판정 요청

### 7-1. P-8 `/health` 계약 위반 — **실측으로 확정했다. 계약 쪽에서 바뀔 것은 없다**

**구현 수정이므로 고치지 않았다**(Kotlin 레인 몫). 리더가 요구한 것은
「**계약 쪽에서 바뀔 것이 있는지**」의 판정이다.

**판정: 계약은 바뀌지 않는다. 구현이 계약을 어겼다.**

```
--- GET /health (도달 가능한 DB · 제품 구성) ---
HTTP/1.1 200
{"status":"ok"}

--- GET /health (DB 가 죽은 채 강제로 띄운 구성 — 팔 D) ---
HTTP/1.1 200
{"status":"ok"}
```

**두 줄이 이 판정을 고정한다.**

1. **`checks` 필드가 없다** — 계약 `HealthResponse.required: [status, checks]` 위반.
   codex F-10 은 코드 판독으로 짚었고, **이 회차가 와이어에서 확인했다.**
2. **DB 가 죽은 상태에서도 `ok` 다** — 계약이 *"확인하지 않은 것을 `true` 로 적으면 진단이
   거짓말이 된다"* 로 금지한 바로 그것이다. 지금은 `checks` 가 아예 없어 형식상 「거짓
   `true`」는 아니지만, **`status: ok` 가 그 역할을 하고 있다.**

**계약이 바뀌지 않는 근거 셋** — ⑴ 계약은 *"Kotlin 은 진단하는 쪽으로 구현한다"* 를 이미
적었다 ⑵ *"구현 시점: DB Phase 3"* 이고 **DB 는 배선됐다**(팔 A 가 그것을 보였다) ⑶ 진단
확장을 v2 로 미루는 문면은 **현재 계약에 없다**(2026-08-12 개정으로 정반대가 됐다).
**즉 계약은 오늘 이미 옳은 것을 요구하고 있고, 미달인 것은 구현이다.**

**다만 판정 4 ⑶ 이 그 위에 겹친다** — `checks.database` 를 구현해도 `false` 팔은 제품
구성에서 도달 0 이다. **P-8 을 닫는 커밋이 그 사실을 함께 다뤄야 한다**(K-P5-4).

### 7-2. 리더 판정 요청 — 셋

**⑴ DB 기동 정책 — 판정 2 와 판정 4 가 한 지점에서 만난다** (`escalate_to_leader` ④)

계약은 두 가지를 동시에 원한다: *"기동을 막지 않는 대신 `/health` 로 배포 상태를
진단한다"* 와 *"DB 를 진단한다"*. **실측은 그 둘이 오늘 양립하지 않음을 보였다** —
제품 구성에서 DB 가 없으면 앱이 뜨지 않아 진단할 프로세스가 없다.
`application.yml` 의 Hikari 주석이 *"DB가 떠 있지 않아도 앱은 뜬다"* 고 적지만
**같은 기동의 Flyway 가 접속한다.**

선택지는 셋이고 **어느 것도 계약 소유자 범위가 아니다**(배포 동작이 달라진다).
㈀ 현행 유지 — DB 는 fail-fast, `checks.database` 는 사실상 상수 `true`(그러면 그 키의
값어치를 다시 물어야 한다). ㈁ 기동을 막지 않게 바꾼다 — 그러면 **판정 2 로 폐기한
503 줄을 되살릴 근거가 생긴다**(단, 실측은 그 상태의 응답이 500 이었다). ㈂ DB 진단을
계약에서 내린다 — *"요구사항 미충족"* 이라는 §2.8 판정 5 의 근거와 충돌한다.

**이 레인은 ㈀ 을 전제로 문면만 정합시켰다.** 판정이 ㈁·㈂ 로 나면 §1·§4 를 함께 고친다.

**⑵ 415 가 인증보다 앞선다 — 어느 리뷰도 짚지 않았다** (`escalate_to_leader` ③)

**새 발견이며 교차 검증을 거치지 않았다.** 실측:

```
POST /documents  text/plain  무토큰   => 415  (401 이 아니다)
POST /documents  text/plain  위조토큰 => 415  (401 이 아니다)
POST /documents  application/json  무토큰 => 401
```

계약 `info.description` 「인증 실패와 입력 검증의 우선순위」는 *"**인증이 먼저다** …
인증되지 않은 호출자에게 **검증 의미론**(어느 파라미터가 어떤 범위를 받는지, 어떤 경로가
UUID를 요구하는지)을 알려 줄 이유가 없다"* 라고 적는다. **415 응답은 그 검증 의미론을
알려 준다** — 응답 헤더에 `Accept: multipart/form-data, application/json` 이 실려
**무인증 호출자에게 그 오퍼레이션이 받는 미디어 타입 집합을 그대로 준다.**

기제는 P-6(F-7)과 **같은 층**이다 — 미디어 타입 매칭은 `RequestMappingHandlerMapping`
(즉 `getHandler()`)에서 일어나고 인증은 `HandlerInterceptor.preHandle` 이라 **인터셉터
체인이 시작되기 전에 415 가 확정된다.** P-6 은 「도달 0」이었으나 **이 자리는 도달이
실재한다**(위 출력).

**이 레인은 조항을 좁히지 않았다.** 불변식 축소는 `escalate_to_leader` ③ 이고, 무엇보다
**좁히는 것이 옳은지 모른다** — 415 가 자원 존재를 누설하지는 않지만 API 표면을 누설하고,
조항이 든 근거는 정확히 **표면 탐색**이다. 계약에는 **판정 대기 표기**만 넣었고
케이스도 쓰지 않았다(K-P5-9).

**⑶ 원장 두 줄 — 이 레인이 고칠 수 없다**(`00_progress.md` 는 범위 밖)

| 원장 위치 | 오늘 문면 | 실측 후 |
|---|---|---|
| `L-⑦` 미실행 목록 | *"**O-21 의 DB 줄 미측정** — 재지 않았으므로 지우지 않았다"* | **측정됐다.** 취소선 처리하고 *"→ 2026-08-20 계약 레인 실측. 다섯 팔 전부 재고 내렸다(`04_contract-keeper_p5-verdict.md` §2)"* |
| `L-⑪` P-5 행 | 마감 「즉시」 | **닫혔다** — 다섯 자리 중 **넷**을 계약 레인이 정합시켰고 **다섯째가 이 원장 줄**이다 |

### 7-3. 기록만 — `HealthController` KDoc (P-9 종류)

`HealthController` KDoc 이 인용한 *"v1은 현행대로 동결 … 진단 확장은 v2 후보다"* 는
**현재 계약에 없다.** 2026-08-12 개정으로 정반대가 됐다.

**리더가 P-9 에서 이미 이 자리를 종류에 넣었다** — 「주석·KDoc·설정 파일이 이름으로 지목한
테스트·클래스·**계약 문면**이 저장소에 실재하는가」의 다섯째 자리다. **기록만 한다.**

**이 회차가 그 종류에 하나를 더한다**: `application.yml` 의 Hikari 주석
(*"DB가 떠 있지 않아도 앱은 뜬다"*)은 **계약 문면 인용이 아니라 자기 전칭 선언**이고
**실측으로 거짓이다**(팔 C). P-9 의 탐지기가 **문면 인용**만 잡도록 설계되면 이 자리를
놓친다 — 그 사실을 P-9 수신자에게 넘긴다(K-P5-3).
