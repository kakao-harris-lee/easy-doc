### 2.2 무엇을 바꿨나

`OWNERSHIP-403` 을 `multiline=True` 로 옮기고 `opener` 를 줬다. 호출 이름 목록은
`_403_CALL` 로 뽑아 **자리 패턴과 opener 가 같은 조각을 쓰게** 했다 — 목록을 두 벌 적으면
사본이 갈리고, 갈린 사본은 늘 조용한 쪽이었다(게이트 23 ⓐ 가 겪은 형태).

**대가가 없다는 근거:** 논리 줄은 `_advance` 가 **주석을 뺀 코드만** 잇고, 한 줄로 끝나는

즉 이 전환은 저장소의 실제 트리에서 후보를 하나도 새로 만들지 않았고 하나도 잃지 않았다.

### 2.4 `xfail(strict)` 2종 — **은폐형 판정을 받아들여 전환했다**

D1(계산값)·D2(응답 자리 밖 인자)를 `xfail(strict=True)` 에서 **형태 목록의
`blocks=False` 항목**으로 옮겼다.

| 축 | `xfail(strict)` 판 | **전환 후** |
|---|---|---|
| 알려진 실패를 성공 종료로 바꾸는가 | **그렇다** (codex B-3 의 규정) | **아니다** — 통과하는 단언일 뿐이다 |
| 해소되면 시끄러운가 | 그렇다(XPASS) | **그렇다** — S2 로 실측 |
| 선언을 떼면 무엇이 깨지는가 | **아무것도** | **아무것도** — 바뀌지 않았다(S3 로 실측) |

- **S2**(자리 목록에 `add` 를 더해 D2 가 잡히게 만듦) → **red**. 「해소되면 시끄럽다」가
  전환 후에도 성립한다.
- **S3**(D1·D2 항목을 표에서 삭제) → **exit 0, 아무것도 안 깨진다.** 이 잔여는 xfail 판과
  같으며 이번 변경이 없앤 것은 「실패를 성공으로 바꾸는」 성질 하나다. **더 낫다고 적지
  않는다 — 정확히 그만큼만 나아졌다.**
- **D1 에는 보상 통제가 실재하고 그것은 결속돼 있다.** 계산의 출처가 `= 403` 리터럴이면
  그 선언 줄이 BLOCK 으로 남고 N14~N16 이 `blocks=True` 로 고정한다. D1 은 「전면 미탐」이
  아니라 「선언 줄 경유 탐지」다.
- **S1**(`multiline=True` 되돌리기) → **5 failed** — 형태 4건 + 기제 테스트 1건.

### 2.5 판단이 갈릴 수 있는 자리 — `return` 뒤 줄바꿈을 닫지 않았다

privacy-gate S-1 표의 두 형태 중 **하나는 닫고 하나는 닫지 않았다.** 근거를 적는다.

- `.status(` 계열은 **괄호가 열려 있어** 논리 줄 결합기가 올바로 잇는다 → 닫혔다.
- `return` 뒤 줄바꿈은 괄호가 열려 있지 않아 **두 개의 논리 줄**이 된다. 이것을 닫으려면
  결합기가 값 산출 키워드 뒤에서도 이어 붙여야 하는데, 그 변경은 `LOG-BODY`·
  `LLM-RAW-INPUT`·`PLAINTEXT-PERSIST` 를 포함한 **모든 multiline 규칙의 판정 범위**를
  바꾼다. 이번 게이트에서 그 위험을 지지 않았다.
- **그리고 그 형태는 이 저장소가 쓰는 어느 언어에서도 403 자리가 아니다.** Kotlin·Python 은
  `return` 에서 문장이 끝나 Unit/None 을 돌려주고 다음 줄은 죽은 식이며, TypeScript 는
  ASI 로 같다. 실제 자리가 되는 언어는 **Java 하나**이고 저장소의 `.java` 는 **0개**다
  (`git ls-files '*.java'` — 실측).
- **그 전제를 산문이 아니라 트리거로 지킨다.** `test_java_소스가_들어오면_return_
  줄바꿈_판정을_다시_한다` 가 `.java` 유입 시 빨개진다 — **S4 로 실측**(더미 `.java` 를
  `git add` → red, 제거 후 green).

**리더가 다르게 판단할 수 있는 자리다.** 옛 판이 이 형태를 BLOCK 한 것은 사실이고,
「옛 판 대비 손실 0」을 엄격히 요구하면 결합기를 고쳐야 한다. 이 레인은 **언어 의미론상
자리가 아니라는 근거 + 유입 트리거**로 대신했다.

### 2.6 그대로 남긴 것

게이트 25 가 남긴 리더 확인 요청(`@ApiResponse(responseCode = "403")` 을 통과로 바꿀
것인가)은 **이 배치에서 손대지 않았다.** 판정이 오지 않았고, 지금은 탐지를 잃지 않는
쪽(BLOCK 유지)이다.

## 3. 조치 3 — 원시 제어문자 전수 탐지 (`a1d6005`)

### 3.1 설계 (지시 그대로 + 교차 §10-① 폐쇄)

| 요구 | 구현 |
|---|---|
| 자리 = `quality` 잡의 「경로 명시」 계열 | `tests/test_raw_control_chars.py` + `ci.yml` quality 잡 스텝. 개인정보 스캐너에 넣지 않았다 — 축이 다르다 |
| 루트 목록이 아니라 전수 | `git ls-files -z` (실측 727 추적) |
| 바이너리 제외를 git 에 위임 | `git ls-files --eol -z` 의 `i/-text` |
| 면제 목록·억제 표기 없음 | **0개** |
| 훑은 수 0 이면 실패 | `test_훑은_텍스트_파일이_0건이_아니다` |
| 판정 기준 = 원시 제어문자 보유 | C0 전부(TAB·LF·CR 제외) + DEL(0x7F) |
| git 바이너리 상태 별도 표시 | 실패 메시지에 「git 이 이미 바이너리로 잡아 diff 가 보이지 않는다」 + 첫 8000바이트 안 NUL 여부 |
| `.gitattributes` 강제 | **채택하지 않음**(표현형 — 바이트가 남아 다른 도구는 계속 속는다) |

**교차 §10-① 이 지적한 함정을 성질로 닫았다.** 「git 이 바이너리라 부름」을 **제외 사유로**
쓰면 `AesGcmContentCipherTest.kt` 처럼 **NUL 이 앞 8000바이트에 있는 텍스트 파일**이 통째로
빠진다 — 정확히 이번 사고의 본체다. 그래서 두 단으로 판정한다.

```
진짜 바이너리 = (git 이 -text 라 부름) AND (바이트 전체가 UTF-8 로 디코드되지 않음)
```

**실측이 저장소를 정확히 가른다** — 진짜 바이너리 8건(jar·zip 2·docx 4·hwpx)은 UTF-8 디코드에
**전건 실패**하고, 제어문자를 실수로 품은 텍스트는 **전건 성공**한다. 즉 git 이 바이너리라
부르는 것은 **제외 사유가 아니라 가중 사유**이고, 그 상태를 실패 메시지가 따로 표시한다.

## 7. 추가 조치 — 같은 종류의 **잠복 자리**를 닫는다 (리더 지시, 2026-08-20)

parity 레인이 자기 몫을 닫으면서(`f282ff3` — `dump_json()` 신설) 같은 형태의 두 번째
자리를 보고했고, 리더가 규칙 4 로 판정해 **그 종류만큼 닫으라**고 지시했다.

**기제는 하나다.** 파이썬 인코더는 C0(0x00~0x1F)만 이스케이프하고 **DEL(0x7F)은
`ensure_ascii=True` 여도 원시 바이트로 흘려보낸다** — DEL 은 ASCII 라 비-ASCII 경로에
걸리지 않고, JSON 규격상 문자열 안에서 합법이라 필수 이스케이프 대상도 아니다.
그래서 **생성기가 정상 동작해도** 데이터에 제어문자가 한 글자만 들어오면 그 자리는
반드시 원시 바이트가 된다. `parity/fixtures/export/export.json` 의 DEL 21개가 그 실측
사례이고, 나머지 자리는 **오늘 데이터에 제어문자가 없어서 초록일 뿐**이다.

나왔다 — `tests/golden/baseline.json` 은 추적되고(`git ls-files` 확인), `write_baseline`
은 `GOLDEN_RECORD_BASELINE=1` 로 지금도 도는 **살아 있는 생산자**이며, `note` ·
`observed_models` 같은 문자열 필드를 담는다.

### 7.2 무엇을 바꿨나 — parity 의 `dump_json()` 과 **같은 조작**

세 자리 모두 같은 형태다: 인코더 출력 **전체**에 `str.translate` 로 치환을 걸고,
**끝에서 결과를 되짚어** 원시 제어문자가 남으면 `RuntimeError` 로 죽는다.

치환을 출력 전체에 걸어도 안전한 이유: JSON 구조 문자(`{`·`,`·`"`·들여쓰기)는 전부 이
집합 밖이고, 문자열 안의 제어문자는 그 시점에 이미 인코더가 이스케이프했거나(C0)
원시로 남아 있다(DEL). 즉 바뀌는 것은 **문자열 리터럴 안의 원시 제어문자**뿐이다.

**되짚기가 핵심이다.** 치환표가 좁아지면 다음 `--write` 가 원시 바이트를 정본에 심는데,
그 상태는 `--check` 류의 **재생성 대조로는 드러나지 않는다** — 재생성이 같은 바이트를
다시 만들어 diff 가 0 이기 때문이다. 되짚기가 그 통로를 닫는다.

**값은 바뀌지 않는다.** JSON 파서에게 `\u007f` 와 원시 0x7F 는 같은 문자다. 실측:

- `dump_python_snapshots.py --check` → **[일치] 2건**, 두 스냅샷 파일 sha256 무변경
  (`5d9d4ac9…` · `09853246…`).
- `tests/golden/baseline.json` 을 읽어 새 `dump_json` 으로 다시 뽑아 **바이트 동일**
  (1896 → 1896). `tests/golden` 전건 **157 passed**.
- **지문 계산 경로는 건드리지 않았다** — `baseline.py` 의 `_canonical`(`sort_keys=True`)이
  지문의 입력이고 그것을 바꾸면 커밋된 지문이 통째로 갈린다. 새 함수는 **파일에 쓰는
  자리 전용**이다.

### 7.3 복사본이냐 공용 유틸이냐 — **복사본 + 결속 테스트를 골랐다**

리더가 판단을 맡긴 자리다. 이 저장소는 정본을 복제했다가 갈린 전례가 여럿이라
복사본이 기본 선택지가 아니다. 그런데도 이쪽을 고른 근거 셋:

1. **런타임 결합이 수명을 거꾸로 잇는다.** 세 생성기는 `python-kotlin-parity` 스킬
   (**폐기 예정 하네스**) · `migration-safety-gate` 스킬(**차단 게이트**) · `tests/golden`
   에 산다. 하나를 정본으로 삼아 나머지가 import 하면 차단 게이트가 폐기 예정 하네스에
   의존하거나, 독립 실행 스크립트가 테스트 트리에 의존하게 된다.
2. **위험한 방향의 드리프트가 조용하지 않다.** 치환표가 좁아지면 ⑴ 결속 테스트가
   **좁아진 순간** 잡고 ⑵ 결과물을 전수 탐지가 잡는다. `_403_TOKEN` 을 열거에서
   파생으로 바꿀 때 이 저장소가 쓴 것과 같은 처방이다.
3. **공용 모듈은 「새 생성기가 그것을 쓰는가」를 보장하지 못한다.** 보장하는 것은
   결과를 보는 전수 탐지뿐이고, 그것은 이미 있다.

**결속 테스트 4종**(`tests/test_raw_control_chars.py`, 3 → 11 tests):

| 테스트 | 무엇을 잰다 |
|---|---|
| `test_직렬화_선언이_비어_있지_않다` | 빈 선언 통과 금지(규칙 4 ⑶) |
| `test_생성기가_원시_제어문자를_남기지_않는다` | 선언한 생성기마다 **제어문자를 데이터로 넣어 실제로 호출**한다. 상수만 대조하면 「이름은 같은데 안 쓰이는」 상태를 통과시킨다 |
| `test_생성기들의_치환_결과가_서로_같다` | 이름이 아니라 **결과**로 묶는다. 들여쓰기·키 순서까지 같아야 하므로 직렬화 옵션이 한쪽만 바뀌어도 드러난다 |
| `test_치환표가_좁아지면_생성기가_죽는다` | `_CONTROL_ESCAPES` 를 비워 되짚기가 **장식이 아님**을 매 실행 확인한다 |

**닫지 않는 것(적어 둔다):** 선언 목록에 없는 **새 생성기**는 이 결속이 보지 못한다.
그 자리를 지키는 것은 전수 탐지 하나뿐이고, 따라서 새 생성기의 결함은 **발생 시점이
아니라 결과 시점**에 드러난다. 정적 스캐너로 「JSON 을 파일에 쓰는 자리」를 열거하는
갈래도 검토했으나 기각했다 — `tmp_path` 쓰기와 추적 경로 쓰기를 정적으로 가를 수 없어
오탐이 나고, **잘못된 근거를 만드는 도구는 없느니만 못하다**(규칙 2).

### 7.4 5번을 닫지 않은 이유 (판정이 갈릴 수 있는 자리)

`make_doc_spike_fixtures.py` 는 추적 파일(`spike-oracle.json`)에 JSON 을 쓰므로 종류
안에 있다. 그런데도 손대지 않았다.

- **결속이 불가능하다.** 이 파일은 최상위에서 곧바로 실행되는 스크립트다 — import 하는
  순간 `app.ingest.extractors` 를 불러 fixture 를 다시 쓴다. 결속 테스트에 넣을 수 없고,
  넣으려면 `if __name__ == "__main__":` 로 재구조화해야 하는데 README 가 *"생성기 소스는
  spike 문서 본문에 실려 있지 않다. 이 파일이 유일본이다"* 라고 적은 대체 불가 산출물이다.
- **살아 있는 생산자가 아니다.** 같은 README: *"생성기가 `app.ingest.extractors` 를
  import 한다 → **Python 삭제 후에는 실행 불가**."* 3·4번과 갈리는 지점이 이것이다 —
  3·4번은 지금도 도는 생산자이고, 그 재생성 대조(`--check`)가 **원시 바이트를 조용히
  재생산**한다. 5번에는 그 통로가 없다.
- **산출물은 전수 탐지가 덮는다.** 오늘 `spike-oracle.json` 의 원시 제어문자는 0개다.

**리더가 뒤집을 수 있는 자리다.** 「종류 안이면 예외 없이 닫는다」를 엄격히 적용하면
재구조화가 필요하다. 이 레인은 **대체 불가 파일의 재구조화 위험 > 동결된 생산자의
잠복 위험**으로 봤고, 근거를 여기 남겨 판단을 올린다.

### 7.5 경계 밖 — **가장 위험한 자리가 `app/**` 에 있다**

`app/easyread/collection.py:1070` (`write_draft`) 는 골든 문서 **초안 본문**을 JSON 으로
쓴다. 목적지 `docs/golden-drafts/` 는 `.gitignore` 가 **일부러 무시하지 않는** 디렉터리이고,
그 파일의 주석이 *"`app/easyread/collection.py` 가 초안을 **커밋 대상으로 전제**"* 라고
적었다(오늘은 아직 커밋되지 않아 전제가 성립하지 않는다).

**이 자리가 잠복 위험이 가장 크다** — 담는 것이 **공공기관 문서에서 추출한 실제 본문**이고,
`parity/fixtures/export/export.json` 의 DEL 이 온 곳도 정확히 그 종류의 데이터다.
다른 다섯 자리는 상수·측정치를 담지만 이 자리만 문서 본문을 담는다.

**고치지 않았다** — `app/**` 는 이 레인의 경계 밖이고 `CLAUDE.md` 상 폐기 대상이다.
리더 판정이 필요하다: ⓐ 폐기 예정이므로 두고 초안이 커밋될 때 다시 본다 /
ⓑ 초안 커밋 전에 닫는다.

### 7.6 `parity/actual/**` 는 전수 장치의 **분모 밖**이다 (parity 레인 관측, 재실측)

`.gitignore:36` 이 `parity/actual/` 를 무시하므로 `git ls-files` 에 나오지 않는다.

```
git ls-files parity/actual | wc -l   → 0
디스크 실측                            → 파일 8개 · 원시 제어문자 보유 0개
```

실행할 때마다 생기는 산출물이라 무시 자체는 옳은 판단이다. 다만 **추적으로 바뀌면 이
검사의 분모가 달라진다** — 그때 다시 봐야 한다. 이 사실을 장부에서 지우지 않는다.

### 7.7 음성 대조 (일회용 워크트리 `wt-h26b`, 본 저장소 무변조)

오늘 데이터에 제어문자가 없으므로 **주입 실험**으로 쟀다. 주입은 `app/easyread/prompts.py`
의 `CONVERTED_TAG_NAME` 에 `chr(0x7F)` 를 **식으로** 더했다 — 주입원 파일 자신은 원시
바이트를 갖지 않게 해서(실측: prompts.py 원시 제어문자 0개) 탐지가 **스냅샷 때문에**
빨개진 것임을 분리했다. *(첫 시도는 소스에 원시 바이트를 직접 넣어 측정이 오염됐다 —
탐지가 스냅샷이 아니라 주입원을 잡았다. 다시 쟀다.)*

| 대조 | 변조 | 결과 |
|---|---|---|
| 0 | — | 11 passed · exit 0 |
| **N3-a** | 주입 + **옛 판**(HEAD 커밋본) 으로 `--write` | 스냅샷에 **원시 `0x7f`** 기록(`\u007f` 표기 0회) · 전수 탐지 **exit 1** ← 잠복 자리가 실현된 상태 |
| **N3-b** | 같은 주입 + **새 판** 으로 `--write` | 원시 제어문자 **0개** · `\u007f` 표기 **11회** · 11 passed **exit 0** |
| N1 | 스냅샷 생성기의 치환만 되돌린다 | **exit 1** (2 failed — 생성기별 대조 + 서로 같은가). 게다가 되짚기가 살아 있어 `--write` 자체가 `RuntimeError` 로 죽는다 |
| N2 | 기준선 기록기의 치환만 되돌린다 | **exit 1** (2 failed, 같은 두 축) |
| N4 | `_CONTROL_ESCAPES` 를 비운다 | 세 생성기 전부 `RuntimeError` — **상시 회귀로 고정**(`test_치환표가_좁아지면_생성기가_죽는다`) |
| 복원 | — | sha256 대조 일치, 스냅샷 `5d9d4ac9…` 무변경 |

**절차 자기 정정.** N3 도중 워크트리에서 `git stash push` 를 한 번 썼다. `git stash` 는
**저장소 공용 ref** 라 다른 레인에 닿을 수 있고, SKILL 규칙 5 가 금지한 도구다.
곧바로 알아채고 `git stash drop` 으로 지웠으며(`stash list` 비었음 확인), 그 stash 에는
이 워크트리의 변경만 들어 있었고 손실 0 이다. 그 실행이 만든 측정값은 **오염된 것으로
보고 폐기**한 뒤 다시 쟀다 — 위 표는 재측정값이다.

### 7.10 자기 정정 — **이 절을 쓰면서 또 저질렀다 (다섯 번째 · 통산 열한 번째)**

§3.5 가 「네 번째 사례」를 적었고, **이 절의 초판이 다섯 번째**다. 원시 `0x7f` 세 개
(13,901바이트 중 오프셋 3775 · 10896 · 11073). 자리는 전부 *"JSON 파서에게 (이스케이프
표기) 와 원시 0x7F 는 같은 문자다"* · *"(표기) 0회"* · *"(표기) 11회"* — **이스케이프
표기를 쓰려던 자리에 그 글자를 넣었다.** §3.5 와 글자 하나까지 같은 형태다.

| 항목 | 값 |
|---|---|
| 발견 | 이 회차가 만든 장치로 자기 검사(작성 직후 전 바이트 훑기) |
| 정정 | 원시 바이트 → 이스케이프 표기. 13,901 → 13,916바이트 |
| git 이 바이너리로 잡았나 | 아니다 — `0x7f` 로는 판정하지 않는다. §10-① 이 경고한 그 자리 |

**이것이 §7 의 존재 근거를 한 번 더 확인한다.** 다섯 번 다 「제어문자에 관해 쓰는
도중」이었고, 사람의 주의로는 줄지 않았다. 줄어든 것은 **자동 검사가 붙은 뒤 발견까지의
시간**이다 — 앞의 셋은 커밋·게이트를 통과한 뒤에야 잡혔고, 뒤의 둘은 작성 직후 잡혔다.
