# Phase 1 후속 — parity 게이트의 정본 하한(canonical floor)

**작성:** 2026-08-12
**대상 결함:** codex stop-time 게이트 지적 — "정본 0개만 막아 **부분 삭제**가 여전히 초록으로 통과한다"
**수정 파일:** `.github/workflows/ci.yml`(kotlin 잡의 `parity 비교` step), `.github/parity-canonical-floor.txt`(신규)

---

## 1. 고치기 전에 뚫려 있던 것

parity 게이트의 판정 범위는 **정본**(`dump_parity_fixtures.py` 의 `BUILDERS` 키)에서 나온다.
직전 조치로 "정본이 0개면 실패"는 막혔지만, 0이 아닌 축소는 그대로 통과했다.

| 정본 | 선언 | 그때의 동작 | 로그 |
|---|---|---|---|
| 11 → 3 | 0개 | exit 0 | `정본 3개 / 검증하지 않음 3개` |
| 11 → 3 | 3개(그 3개) | exit 0 | **`parity 전체 게이트 통과 — 도메인 3개 전부 값으로 대조했다`** |

두 번째가 특히 나쁘다. 선언이 정본을 다 덮으면 전체 게이트로 들어가므로, **축소가 "완전 검증"으로
위장된다.** 8개가 사라진 사실은 어디에도 남지 않는다.

계열은 codex 가 Phase 1 리뷰에서 지적한 것과 같다 — *"provenance and external verification trust the
same mutable source they validate."* 정본이 곧 기준인데 기준 자체가 저장소 안의 변경 가능한 코드이고,
축소를 감지할 기준점이 없었다.

## 2. 택한 설계 — 비대칭 검사 (현재 정본 ⊇ 스냅샷)

정본 도메인 목록의 **스냅샷**을 버전 관리 파일로 두고, CI 는 `현재 정본 ⊇ 스냅샷` 만 검사한다.

- **추가는 통과시킨다.** 정본에 새 도메인이 생겼는데 스냅샷에 없어도 막지 않는다. 그 도메인은
  선언되지 않았으므로 게이트 배너에 `검증하지 않음`으로 이름이 찍히고, 추가로 `하한 미등재`
  줄에도 이름이 찍힌다. 놓쳐도 드러나므로 무해하다.
- **삭제는 막는다.** 스냅샷에 있는데 정본에 없으면 exit 1 이고, 사라진 도메인 이름을 전부 찍는다.

### 왜 비대칭인가

원래 설계 원칙은 "도메인 목록을 CI 에 복제하지 않는다 — 복제가 곧 드리프트"였고 지금도 타당하다.
다만 복제를 완전히 피하면 축소를 감지할 기준점이 없다. 그래서 드리프트를 **방향별로** 나눴다.

- 드리프트 위험이 실재하는 방향은 **추가**다(새 도메인을 만들고 스냅샷 갱신을 잊는다). 그런데 그
  방향은 무해하다 — 게이트가 좁아지지 않고, 로그가 이름을 찍는다.
- 게이트를 무르게 만드는 방향은 **삭제**다. 그 방향만 막으면 복제의 대가는 치르지 않으면서 위험만
  덮는다.

### 왜 별도 step 이 아니라 같은 step 안인가

`parity 하네스 배선 확인`처럼 별도 step 으로 뺄 수도 있었지만, 그러려면 그 step 이 생성기를 한 번 더
돌려 **자기만의 정본 목록**을 만들어야 한다. 그러면 하한이 검사한 정본과 게이트가 실제로 판정에 쓰는
정본이 다른 실행에서 나온 두 개가 되고, 둘이 갈라지는 순간(경로·working-directory·의존성 차이) 하한은
게이트가 쓰지도 않는 목록을 지키게 된다. 지금은 하한 검사와 모든 분기가 **같은 `$work/canonical`
파일 하나**를 본다. 검사 위치는 모든 분기보다 앞이고 무조건 실행된다.

## 3. 스냅샷 파일의 위치와 이름

`.github/parity-canonical-floor.txt`

혼동하면 안 되는 파일이 하나 있다. 이름과 위치를 둘 다 다르게 잡은 이유다.

| | `backend-kotlin/parity-domains.txt` | `.github/parity-canonical-floor.txt` |
|---|---|---|
| 뜻 | Kotlin 이 **포팅했다고 선언하는** 도메인 = 검증 범위 | 정본 생성기에 **최소한 있어야 하는** 도메인 = 게이트가 아는 세계의 크기 |
| 정상적인 변경 | Phase 마다 **늘어난다**. 고치는 게 일이다 | 거의 안 고친다. **줄이면 게이트가 줄어든다** |
| 있는 곳 | Kotlin 쪽 | CI 게이트 쪽 |

`.github/` 를 고른 이유가 하나 더 있다. 스냅샷을 `parity/` 에 두면 그 디렉터리는 생성되는
fixture 가 사는 곳이라 diff 가 "fixture 다시 뽑았구나"로 읽힌다 — 축소를 감추기 좋은 위장이다.
`.github/` 의 diff 는 누가 봐도 "CI 게이트를 건드렸다"로 읽힌다. 우리가 원하는 신호가 그것이다.

파일 안에는 (a) 두 파일의 구분, (b) 비대칭의 근거, (c) **줄이는 변경은 리뷰에서 반드시 근거를
요구한다**는 취지와 요구할 항목, (d) 원리적 한계를 주석으로 남겼다. 초기값은 현재 정본 11개
(`--list` 로 실제 확인: argon2 crypto export jwt masking postprocess prompts repair-adoption style
style-tables text).

## 4. 실증

`ci.yml` 의 `run:` 문자열을 **파일에서 그대로 추출해**(`scratchpad/floor/extract_step.py`) bash 로
실행했다. 옮겨 적지 않았다. 정본 크기가 다른 "세계"를 스크래치패드에 만들어 돌렸다 — `w3` 는
생성기 사본에서 `BUILDERS` 항목 8줄을 실제로 지운 것이고, `w12` 는 한 줄 더한 것, `w0` 는 목록을
못 뽑는 생성기다. 저장소에는 `parity/fixtures` 를 만들지 않았다.

| # | 상황 | 명령 (cwd) | 종료 코드 | 확인한 것 |
|---|---|---|---|---|
| 1 | 정본 11 / 선언 0 (현재 상태) | `bash step.sh` (저장소 루트) | **0** | `정본 11개 (하한 11개 충족)` + 기존 "게이트 미가동" 경고 그대로. 회귀 없음 |
| 2 | 정본 11→3 / 선언 0 | `bash step.sh` (`w3`) | **1** | `::error::정본에서 도메인이 사라졌다: argon2 crypto export jwt postprocess prompts repair-adoption style-tables` |
| 3 | 정본 11→3 / 선언 3(그 3개) | `bash step.sh` (`w3`) | **1** | 같은 오류. "전체 게이트 통과"로 위장되던 경로가 닫혔다 |
| 4 | 정본 11→12 (도메인 추가) / 선언 0 | `bash step.sh` (`w12`) | **0** | 막지 않는다. 배너에 `하한 미등재 : brand-new` 로 이름만 남는다 |
| 5a | **가드 제거 A** + 시나리오 2 | `bash step-noguardA.sh` (`w3`) | **0** | 구멍이 다시 열린다 |
| 5b | **가드 제거 A** + 시나리오 3 | `bash step-noguardA.sh` (`w3`) | **0** | `parity 전체 게이트 통과 — 도메인 3개 전부 값으로 대조했다` — 위장이 그대로 재현된다 |
| 5c | **가드 제거 B** + 시나리오 2 | `bash step-noguardB.sh` (`w3`) | **0** | 〃 |
| 5d | **가드 제거 B** + 시나리오 3 | `bash step-noguardB.sh` (`w3`) | **0** | 〃 |
| 6a | 회귀: 정본 0개(생성기 고장) | `bash step.sh` (`w0`) | **1** | 직전 가드의 진단 문구가 그대로 나온다 |
| 6b | 회귀: 선언에 정본에 없는 이름 | `bash step.sh` (`w11`) | **1** | `정본에 없는 도메인이 있다: not-a-domain` |
| 6c | 회귀: 부분 게이트 선언 1개 | `bash step.sh` (`w11`) | **0** | `부분 게이트 통과 — 선언한 1개 도메인(masking)만 값으로 대조` (값 비교 14건) |

가드 제거 변형은 두 가지를 만들었다. **A** 는 `vanished` 비교 분기 9줄만 지운 것(하한 파싱은 그대로),
**B** 는 하한 관련 코드를 전부 걷어내 가드 도입 이전 동작으로 되돌린 것이다. 둘 다 시나리오 2·3 에서
exit 0 이 나온다 — 구멍을 막고 있는 것이 정확히 이 비교라는 뜻이다.

하한 파일 자체를 건드리는 경우도 함께 쟀다.

| 상황 | 종료 코드 | 확인한 것 |
|---|---|---|
| 하한 파일 삭제 (정본은 11개 그대로) | **1** | `기준점이 사라졌다` — 파일을 지워도 통과하지 않는다 |
| 하한 파일을 주석만 남기고 비움 | **1** | `하한이 비면 무엇을 지우든 통과한다` — 지우는 것과 비우는 것을 같게 취급한다 |
| 하한만 3개로 줄임 (정본 11개) | **0** | 막지 않는다. **이것이 아래 §5 의 한계다** — 배너에 `하한 미등재` 8개가 찍히지만 CI 는 통과한다 |

저장소 상태: 실험 전후 `git status --porcelain` 동일. 이번 작업으로 늘어난 항목은
`?? .github/parity-canonical-floor.txt` 하나뿐이다. Python(`quality`)·React(`frontend`) 잡은
건드리지 않았다.

## 5. 이 조치가 막지 못하는 것

1. **같은 커밋에서 스냅샷과 정본을 함께 줄이는 것.** 스냅샷은 저장소 안의 파일이고, 저장소 안의 어떤
   파일도 저장소 자신에 대한 절대 기준이 될 수 없다. 이 한계는 원리적이므로 없애려 하지 않고
   명시한다. 이 검사가 하는 일은 축소를 **불가능하게** 만드는 것이 아니라 **조용할 수 없게** 만드는
   것이다 — 줄이려면 `.github/` 안의 파일을 고쳐야 하고 그 diff 가 리뷰에 올라간다. 최종 방어선은
   자동화가 아니라 리뷰 게이트이고, `codex-review` 스킬이 `.claude/**` 를 리뷰 면제에서 뺀 것이 그
   장치다. 같은 이유로 `.github/**` 도 면제 대상이 아니어야 한다.
2. **CI 설정 자체를 무르게 만드는 변경.** 이 step 을 통째로 지우거나 `continue-on-error` 를 붙이면
   하한도 같이 사라진다. ci.yml diff 를 사람이 읽는 것 말고 막을 장치는 없다.
3. **도메인 안의 케이스를 줄이는 것.** 하한은 도메인 **이름**의 집합만 본다. `masking` 이 남아 있는데
   그 안의 케이스가 40건에서 3건으로 줄어드는 축소는 이 검사에 걸리지 않는다. (그 방향은
   `compare_parity.py` 가 fixture 를 정본 생성기와 매번 대조하는 것으로 일부 덮이지만, 생성기의
   케이스 자체가 줄면 역시 조용하다. 별도 결함으로 남긴다.)
4. **선언 범위 자체가 좁은 것.** 하한은 "정본이 줄지 않았다"만 보증한다. Kotlin 선언이 0개면 여전히
   값은 한 건도 검증되지 않으며, 그것은 배너와 경고가 담당한다.

## 6. 스냅샷을 고쳐야 하는 정당한 경우와 절차

| 경우 | 해야 할 일 |
|---|---|
| 정본에 도메인을 **추가**했다 | 같은 커밋에서 스냅샷에도 한 줄 추가한다. 필수는 아니지만(추가는 막지 않는다) 적어 두어야 그 도메인이 나중에 삭제될 때도 걸린다 |
| 정본에서 도메인을 **삭제**해야 한다 | 스냅샷에서도 지운다. 그리고 PR 설명에 아래 세 가지를 적는다. 없으면 리뷰어는 승인하지 않는다 |
| 이름만 바꿨다 | 삭제 + 추가로 취급한다. 삭제 절차를 따른다 |

삭제 PR 이 반드시 답해야 하는 것:

1. 그 도메인이 왜 더 이상 존재하지 않는가 — 기능 제거인가, 다른 도메인으로 흡수인가.
2. 흡수라면 흡수한 도메인의 fixture 가 그 케이스를 실제로 덮는가 — **케이스 id 로 제시**한다.
3. Kotlin 쪽 대응(`backend-kotlin/parity-domains.txt` 의 선언과 해당 parity 테스트)을 같이 지웠는가.

리뷰어에게: 이 파일의 diff 에서 **줄이 사라진 것**을 보면 그것은 "정리"가 아니라 게이트 범위 축소다.
근거 세 가지가 PR 에 없으면 그 자리에서 반려한다.

## 7. 후속 (2026-08-14) — 두 번째 하한: 선언 하한 (C-02)

작성: `parity-verifier` · 근거: 게이트 08 차단 ②장치 **C-02**(codex A-4) · 파일: `.github/parity-declared-floor.txt`

### 7.1 첫 하한이 막지 못한 자리

§2의 정본 하한은 **"생성기가 아는 세계"**가 줄어드는 것을 막는다. 그런데 그 세계가 그대로여도 **실제로 판정되는 범위**는 따로 줄어들 수 있다 — `backend-kotlin/parity-domains.txt`의 선언이 줄면 된다.

| 편집 | 정본 하한 | 그때 CI |
|---|---|---|
| 선언 2개 → 1개 | 통과(정본 8개 그대로) | 남은 1개가 통과 → **초록** |
| 선언 2개 → 0개 | 통과 | `::warning::parity 게이트 미가동` → **exit 0** |

둘 다 게이트를 끄는 편집인데 결과가 초록이다. **정본 하한과 선언 하한은 다른 축이다** — 하나는 "무엇을 알고 있어야 하는가", 다른 하나는 "무엇을 실제로 보고 있는가"다.

### 7.2 "선언 0개 = 경고"는 한때 사실이었다

이 자리를 바로 실패로 만들지 않았던 것은 옳았다. Phase 1 종료 시점에는 포팅한 도메인이 **정말로 0개**였고, "값을 한 건도 검증하지 않았다"가 정직한 보고였다. 그때 실패로 두었다면 CI는 몇 주 동안 빨간 채였을 것이고, 그런 빨강은 읽히지 않는다.

**그 시기가 끝난 것이 이 조치의 계기다.** `masking`·`repair-adoption` 두 도메인이 실제로 값을 판정한다(94건·330단언). 지금부터 선언이 0개가 되는 경로는 하나뿐이다 — **누군가 지웠다.** 같은 로그가 이제는 거짓말이다.

### 7.3 설계 — 정본 하한과 같은 모양, 다른 대상

- 파일: `.github/parity-declared-floor.txt`. `.github/`에 두는 이유는 §3과 같다 — 줄이려면 CI 디렉터리를 건드려야 하고 그 diff가 리뷰 신호가 된다.
- 검사: **비대칭**(현재 선언 ⊇ 스냅샷). 추가는 통과, 삭제만 차단.
- 부수 가드 셋: 파일 부재 → 실패 / 파일 비움 → 실패 / **선언 0개 → 실패**(경고에서 승격).

### 7.4 순서가 판정을 삼켰다 — 도달 0을 실측으로 잡았다

처음에는 `declared_count -eq 0` 검사를 선언 하한 검사 **뒤에** 두었다. 음성 대조에서 선언을 비운 변형이 **하한 검사 메시지로 걸렸다** — 하한이 비어 있지 않으면 전부 누락으로 걸려 0개 분기까지 오지 못하고, 하한이 비면 그쪽 검사가 먼저 막는다. 즉 그 분기는 **어떤 경로로도 도달하지 않았다.**

동작은 옳았지만(둘 다 exit 1) **진단이 사라졌다** — "방금 껐다"와 "하한과 어긋난다"는 조치가 다르다. 0개 검사를 하한 검사 **앞으로** 옮겨 각 검사가 도달 가능한 고유 진단을 갖게 했다. 이 저장소가 반복해 겪은 「선언한 범위와 실제 도달을 대조한다」가 게이트를 **만드는 중에** 다시 걸린 사례라 기록해 둔다.

### 7.5 실증 — CI 셸을 합성 트리에서 돌렸다

`ci.yml`의 해당 step `run:` 블록을 그대로 추출해(212줄) 저장소 사본에서 실행했다. 저장소 자체는 건드리지 않았다.

| 변형 | 종료 코드 | 첫 오류 |
|---|---|---|
| 현재 상태 | **0** | — (통과) |
| 선언 0개(파일 비움) | **1** | `parity 게이트 미가동 — 포팅을 끝냈다고 선언한 도메인이 0개다` |
| 선언 1개로 축소 | **1** | `구현 완료로 선언돼 있던 도메인이 선언에서 사라졌다: repair-adoption` |
| **선언 + 생산자 동시 제거** | **1** | 위와 같음 |
| 선언 하한 파일 삭제 | **1** | `…-declared-floor.txt 가 없다 — 기준점이 사라졌다` |
| 선언 하한 비움 | **1** | `…에 도메인이 한 줄도 없다 — 하한이 비면 무엇을 지우든 통과한다` |
| 하한까지 함께 축소(정당한 삭제) | **0** | — (설계된 탈출구) |

네 번째 줄이 C-02가 요구한 음성 테스트다 — **생산자와 선언을 함께 지워도 빨갛다.** 이전에는 Gradle `parityManifestCheck`가 "선언 O/산출 X"·"선언 X/산출 O"의 **불일치**만 봤기 때문에 둘을 **같이** 지우면 아무 데서도 걸리지 않았다.

마지막 줄은 결함이 아니라 **설계된 탈출구**다. 정당한 삭제는 가능해야 하고, 다만 `.github/` 안의 파일을 고쳐야 하므로 조용할 수 없다. §5의 한계 선언이 여기에도 그대로 적용된다 — 이 파일도 같은 커밋에서 함께 바꿀 수 있고, **최종 방어선은 리뷰다.**

### 7.6 이 하한이 막지 못하는 것

- **도메인 이름까지만 본다.** 도메인 안의 케이스가 줄어드는 것은 잡지 못한다 — 그 자리는 fixture 정본 대조(생성기 재실행)가 받는다.
- **선언과 구현의 진위는 보지 않는다.** "선언했고 산출물도 있다"까지만 본다. 산출물을 정말 Kotlin이 만들었는지는 여전히 `parityHarness` 배선이 유일한 근거다.
