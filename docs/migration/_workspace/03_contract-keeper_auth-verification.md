### 1-1. 미달 1건 (경미) — 422·`/auth/me` 401의 계약 선언 대조가 없다

명세 §4-1 P-1은 성공 상태뿐 아니라 **「§2 표의 오류 상태가 계약에 선언돼 있는지」**도 읽으라고 했다.
실제로 대조되는 것은 409(S-2) · 401(L-2, login) · 503(AuthUnavailable) 셋이고,
**422와 `/auth/me`의 401은 상수만 쓰고 계약 대조가 없다.**

- 결과: 계약에서 `paths./auth/signup.post.responses.'422'` 또는 `paths./auth/me.get.responses.'401'`가
  **삭제돼도 어떤 테스트도 깨지지 않는다.**
- 심각도 **낮음** — 응답 자체는 여전히 단언되므로 구현 회귀는 잡힌다. 새는 것은 **계약 조항의 소실**뿐이다.
- 처분: 기록. 같은 형태가 다음 단위에서 반복되면 그때 P-1을 강제 형태로 올린다.

## 5. ⚠ 신규 결함 — 계약을 바꿔도 계약 테스트가 돌지 않는다

**요청 범위 밖에서 드러났다.** 음성 대조를 하려고 캐시 동작을 확인하다 나왔다.

**측정.** worktree에서 계약 파일 **하나만** 바꾸고 같은 Gradle 명령을 다시 돌렸다.

| 조건 | 결과 |
|---|---|
| 같은 명령 1차 | `:api:test` **실행됨** · exit 0 |
| 같은 명령 2차 (변경 없음) | `:api:test` **UP-TO-DATE** · exit 0 |
| **계약 파일만 바꾸고 같은 명령** | `:api:test` **UP-TO-DATE** · **exit 0** — 테스트가 아예 돌지 않았다 |
| **`cleanTest` 후 계약이 바뀐 상태로 재실행** | `:api:test` **FROM-CACHE** · **exit 0** |

**기제.** 계약 파일이 테스트 태스크의 **선언된 입력이 아니다.** `ContractSpec`은 실행 시점에
시스템 속성으로 경로를 만들어 읽으므로 Gradle의 입력 지문에 잡히지 않는다. 그래서
계약만 바뀐 변경은 태스크를 무효화하지 못하고, 저장소가 `org.gradle.caching=true`이며
CI가 `gradle/actions/setup-gradle`로 캐시를 유지하므로 **`clean` 뒤에도 캐시가 초록을 돌려준다.**

**왜 중요한가.** X-J2가 요구한 「계약 값을 바꾸면 테스트가 깨진다」는 **테스트가 돌 때만** 참이다.
지금은 **계약을 고치는 변경이 계약 테스트를 한 번도 돌리지 않고 초록으로 통과할 수 있다.**
이 하네스가 반복해 겪은 형태 그대로다 — 조항은 있고 **강제 수단이 그 자리까지 닿지 않는다.**

**범위를 넘겨 적지 않는다.** 내가 실제로 잰 것은 **로컬 증분 실행과 로컬 빌드 캐시**다.
CI에서 캐시가 실제로 그 지문을 재사용하는지는 **관측하지 않았다** — 캐시 설정과 액션 기본값에서
따라 나오는 추론이다. 신선한 체크아웃에 캐시가 없으면 테스트는 돈다.

**처분.** 기록만 한다(Kotlin·Gradle 코드 수정 금지). 고치는 방향은 구현 판단이며,
계약이 정하는 것은 「계약이 바뀌면 계약 테스트가 실행돼 판정한다」까지다.
**Phase 3 종료 전 마감을 권고한다** — 이것이 열린 채로는 이번에 붙인 파서·음성 대조의
값어치가 「돌았을 때만」으로 한정된다.

## 6. ⑸ 판정 — 이메일을 ASCII로 좁힌 것

**판정: 허용한다. 계약 준수 위반이 아니다.**

**근거.**
1. **계약이 그 자리를 규정하지 않는다.** `SignupRequest.email`은 `type: string`이고
   `format`·`pattern`이 없다. 계약이 정한 것은 **정규화 축**(`measured_on`)·**상한**·
   **위반 시의 상태 코드와 `detail` 문구**이며, 허용 문자 집합은 어디에도 없다.
2. **불변식 축소가 아니다.** `x-change-policy`의 불변식 목록 어느 것도 건드리지 않는다.
3. **오히려 계약이 규정한 것을 지키는 선택이다.** `users`의 `ck_users_email_lowercase`와
   호스트 로캘 의존 `lower()`가 갈리면 **정상 입력이 500**이 된다. 계약은 500을 서버 결함 경로로
   두었지 유효 입력의 귀결로 두지 않았다. 갈림을 없애는 쪽이 계약을 더 잘 만족시킨다.
4. **React 런타임 의존 없음** — `types.ts`는 `email: string`이고 IDN에 의존하는 코드가 없다.
   §7.2의 리더 상신 사유(①~④) 어디에도 해당하지 않는다.

**확인한 경계 — 거절의 **모양**이 계약과 같은가.** ASCII 밖 입력은 형식 위반으로 떨어져
`InvalidInputException` → **422 + 문자열 `detail`**이며, 문구가 다른 형식 오류와 **같다**.
길이 전용·문자셋 전용 문구를 새로 만들지 않았다 — 만들었다면 그 자체가 계약 위반이었다.

**붙이는 조건 셋.**
1. **넓힐 때는 혼자 넓히지 않는다.** 정규화 방식(`lowercase()`)과 DB 제약을 **같은 변경 단위**로
   바꾼다. 한쪽만 넓히면 유효 입력이 500이 되는 경로가 되살아난다.
2. **계약은 고치지 않는다.** 문자 집합을 계약에 적을 근거가 G1~G4 어디에도 없다
   (사실과 다르지 않고, 요구사항이 요구하지 않으며, 정책 결정이 아니고, 지킬 수 없는 형태도 아니다).
   **바꾸지 않기로 하는 것도 판정이므로** 여기 남긴다 — 같은 제안이 다시 올라오지 않게.
3. **미검증 자리 하나를 등재한다.** 비ASCII 이메일이 실제로 422 + 같은 문구로 나가는지를
   **직접 단언하는 테스트가 없다**(S-3은 `not-an-email`을 쓴다). 구현상 같은 경로이므로 위험은
   낮지만, 좁히기를 정당화한 근거가 「거절의 모양이 계약과 같다」인 이상 그 자리는 재는 편이 낫다.

## 9. 이 검증이 재지 않은 것

**「충족」으로도 「위반」으로도 적지 않는다.**

- **전체 빌드**를 다시 돌리지 않았다. 내가 실행한 것은 auth 대상 3클래스 32건(기준선)과
  변이별 재실행 11회다. 구현 레인이 보고한 613건·`ktlintCheck`·`detekt`·Python 게이트는
  **재현하지 않았고**, 그 축은 병렬 리뷰 게이트 소관이다.
- **CI에서의 캐시 재사용**을 관측하지 않았다(§5).
- **Argon2·JWT의 암호 성질**(I-8·I-9)은 계약 소유자 범위 밖이다 — `privacy-gate` 소관이며,
  내가 확인한 것은 그 규칙이 계약의 `x-auth` 노드에서 기대값을 읽는가까지다.
- **부하·타이밍**(로그인 응답 시간 균일성)은 재지 않았다. 계약은 응답의 **동일성**만 요구하고
  구현 레인이 타이밍 축을 개선 후보로만 남긴 것은 그 조항 밖이다.
