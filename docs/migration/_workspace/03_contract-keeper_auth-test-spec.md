## 0. 이 문서의 규약 — 값을 전사하지 않는다

**상한·하한의 숫자, `detail` 문구, 헤더 값 문자열, 클레임 값, `expires_in` 값, enum 원소를 이 문서에
적지 않는다.** 경계는 「하한」·「상한」이라는 **역할 이름**으로 부르고, 실제 값은 **계약 파일에서
읽는다**(§4 파서 요건). 근거는 게이트 15 별건 1(손으로 옮긴 계약 요약이 원본과 갈렸다)과 게이트 16 N
(그 규약이 자기 세 행에서 빈 채로 통과했다)이다.

**이 규약의 도달 범위 — 이 문서 전체다.** 표·산문·각주를 가리지 않는다. 아래 검사로 확인할 수 있다:

```bash
grep -nE '"[^"]*(입력해|올바르지|이상이어야|이하여야|가입된|필요합니다)[^"]*"|no-store|nosniff|\b(255|4000|3600|8자)\b' \
  docs/migration/_workspace/03_contract-keeper_auth-test-spec.md
# 기대: 이 코드 블록 자신의 패턴 문자열 외 0건
```

**적는 것과 적지 않는 것의 경계.**

| 적는다 | 적지 않는다 |
|---|---|
| 키 경로(+ 2026-08-19 실측 행 번호) | 그 키의 **값** |
| 「하한」·「상한」·「정규화 후」 같은 역할·축 이름 | 그 역할이 가리키는 숫자 |
| `detail`의 **타입**(문자열 / 배열) | `detail`의 **문구** |
| 헤더·클레임·컴포넌트의 **이름**과 그 값이 사는 키 경로 | 헤더 값 문자열 · 클레임 값 · `token_type`·`expires_in` 값 |
| 상태 코드 — **케이스를 지목하는 이름**으로만 | — |

**이름과 값을 가른다.** 헤더 이름(`WWW-Authenticate`), 클레임 이름(`sub`·`exp`·`typ`), 컴포넌트 이름
(`WWWAuthenticateBearer`)은 **자리를 지목하는 식별자**라 적는다 — 이것을 지우면 케이스를 부를 말이
없어진다. 지우는 것은 그 자리에 들어가는 **값**이다. 테스트 쪽에서도 같은 경계가 선다: M-4는 클레임
**목록 자체를 계약에서 읽어** 케이스를 유도하므로, 이 문서가 이름을 적어도 테스트에는 복제본이
생기지 않는다.

**상태 코드만은 숫자로 적는다.** 케이스의 이름이 곧 상태 코드이고, 이름을 지우면 표가 읽히지 않기
때문이다. 대신 **기대값의 근거는 이 문서가 아니라 계약 파일**이다 — 테스트는 상태 코드도 계약에서
읽어 대조한다(§4 P-1·P-2). 이 문서의 숫자가 계약과 갈리면 **틀린 것은 이 문서이고 테스트는 계약을
따른다.** 테스트가 이 문서를 읽지 않으므로 그 드리프트가 테스트를 오염시키지 않는다 — 이것이
상태 코드를 예외로 두면서도 규약이 무너지지 않는 이유다.

**행 번호는 2026-08-19 실측이며 키 경로와 함께 적는다.** 파일이 움직이면 행은 틀리고 키는 남는다.

### 4-2. 파서가 지켜야 하는 성질

1. **없으면 실패한다 — 건너뛰지 않는다.** 계약 파일을 못 찾거나 노드가 없으면 테스트가 **빨갛게**
   끝난다. `@Disabled`·조건부 스킵·`null` 반환·기본값 대입은 전부 금지다. 기본값을 두면 **계약에서
   조항이 삭제돼도 테스트가 통과한다** — 파서를 붙인 목적이 정확히 그 반대다.
2. **경로 해석이 작업 디렉터리에 의존하지 않는다.** Gradle 테스트의 작업 디렉터리는 모듈 디렉터리이고
   계약 파일은 저장소 루트에 있다. 상대 경로 조립이 조용히 어긋나면 1번의 「실패한다」가 **개발자
   기계에서만** 참이 된다.
3. **`fields[]`는 인덱스가 아니라 `field` 값으로 찾는다.** test-plan이 `fields[1]`이라 적은 것은
   **위치의 표기**이고, 조회는 이름으로 한다 — 항목이 추가·재배열되면 인덱스는 **조용히 다른 필드를
   읽는다**. 못 찾으면 실패다.
4. **읽은 값을 단언에 실제로 쓴다.** 읽어 두고 단언에는 상수를 쓰는 배선이 과거에 한 번 통과했다
   (X-1이 그 형태다). §4-4의 음성 대조가 이것을 잡는 유일한 장치다.
5. **파서는 auth 밖 노드까지 읽어도 되지만, 이 배치가 요구하는 것은 위 12개다.** 넓히는 것은 자유지만
   **넓힌 만큼 음성 대조도 넓힌다** — 읽기만 하고 안 쓰는 노드는 다음 사람에게 「이미 덮였다」로 읽힌다.

### 4-3. P-7의 자리 — 계약 내부 이중 선언 대조

**같은 상한이 계약 안에 두 벌 있다**(2026-08-19 실측): `x-input-limits.max_email_length` ↔
`fields[?email].limit`, `x-input-limits.min_password_length` ↔ `fields[?password].limit`.
다섯 필드 전부 같은 구조이며 **현재 두 벌의 값은 일치한다.**

파서는 **auth가 만지는 두 필드에 한해** 두 값을 읽어 **서로 같은지 단언한다.** 한쪽만 읽으면 다른
쪽이 갈려도 아무 데서도 안 걸린다 — 상한을 고치는 사람이 한 곳만 고치는 것이 이 저장소에서 가장 흔한
드리프트 형태다.

**계약은 고치지 않는다.** 이중 선언을 하나로 합치는 것은 구조 변경인데 근거가 없다(G1~G4 어디에도
해당하지 않는다 — 두 값이 실제로 같고, 절이 나뉜 데는 이유가 있다: 값과 적용 방식을 가른다).
**탐지로 충분한 자리를 구조 변경으로 풀지 않는다.** 나머지 세 필드는 해당 작업 단위에서 같은 대조를
붙인다 — 여기서 다섯을 한꺼번에 거는 것은 근거를 넘는다.

성질 5 위반은 아니지만, 밟지 않은 갈래이므로 등재해 둔다.

**과잉 결합도 함께 본다.** 각 변경에서 깨지는 것이 **위 열의 케이스뿐**인지 확인한다. 무관한 테스트가
함께 깨지면 파서가 값을 엉뚱한 곳으로 흘리고 있는 것이고, 그때는 「깨졌으니 통과」로 읽으면 안 된다.

**복원 절차(규칙 5).**

```bash
# worktree에서 값 하나 변경 → 해당 테스트만 실행 → 실패 확인
git -C <worktree> diff --stat          # 변경이 계약 파일 1개뿐인지 확인
git -C <worktree> checkout -- contracts/easy-doc-v1.yaml
shasum -a 256 <worktree>/contracts/easy-doc-v1.yaml contracts/easy-doc-v1.yaml   # 두 해시 일치 확인
# 대조가 끝나면 worktree 자체를 제거한다
```

`cp`로 되돌리지 않는다 — 사본의 최신성도 복원 내용도 증명하지 못한다. **git 경유 + sha256 대조가 그
증명을 제공한다.** 게이트 실행·음성 대조처럼 종료 코드가 판정 근거인 명령은 **파이프 없이 직접**
돌린다(SKILL 규칙 3 — `pytest | tail`이 빨간 채 0으로 끝난 실측이 있다).

**기록할 것**: 변경한 노드 · 실패한 테스트 이름 · 함께 깨진 것의 유무 · 복원 후 해시 일치.
§7의 2단계가 이 표를 채운다.

| **C-M** | `@WebMvcTest` + MockMvc | 디스패처를 **통과해** 만들어지는 응답 — 성공 응답, 어드바이스가 만든 오류, 본문·필드 이름·`detail` 타입·성공 응답 헤더 | `FrameworkErrorContractTest` · `ErrorContractTest` · `PrivateResponseHeadersContractTest`(G-D) |
| **C-R** | `@SpringBootTest(RANDOM_PORT)` + 실제 소켓 | **필터·컨테이너가 만드는 응답** — 인증 실패 401 전부(M-2~M-7) | `ContractErrorBodyReachTest` · `PrivateResponseHeadersReachTest` |
| **C-P** | 구성이 다른 컨텍스트(속성 주입) + 위 둘 중 하나 | S-13·L-6·M-8(서명 키 미비 503) | `ApiStartupOnEmptyDatabaseTest`의 `@DynamicPropertySource` 방식 |
| **U** | 순수 단위 테스트 | X-I2(Argon2 재해시 판정) | — |

**MockMvc는 대리 측정이다**(SKILL 규칙 2). 이 저장소에서 그 대리가 **잘못된 근거를 만든 실측**이 이미
있다 — 필터 1층으로 7종이 비었는데 MockMvc는 통과를 냈다(`x-phase3-measurement.method` `:635-642`).
**가르는 기준은 「누가 그 응답을 만드는가」다.**

**M-2~M-7을 C-R로 두는 것은 이 배치에서 양보할 수 없는 자리다.**

- 계약이 명시한다: E-1의 `how`(`:481-485`)가 *"MockMvc가 `/error` ERROR 디스패치를 재현하는지는 이
  저장소에서 확인된 바 없다 — 확인 없이 MockMvc로 쓰면 헤더 쪽에서 이미 겪은 '측정한 것처럼 보이는
  통과'를 반복한다"*고 적는다.
- E-2(`:486-491`)의 요점이 **「어떤 구현 수단으로 나가든」**이다. 인증 401을 `sendError`로 내는 구현이
  가장 흔하고(`x-measured-blind-spot` `:463-465`), 그 경로는 컨테이너 재디스패치를 지난다.
  **MockMvc로 재면 구현 수단을 바꿨을 때 단언이 따라오지 못한다** — 그러면 이 단언이 지키려던 성질
  자체가 사라진다.
- MockMvc는 필터를 **손으로 체인에 끼워** 부른다(기존 테스트들이 `@Import`로 필터 구성을 들여오는
  이유다). 실제 체인 순서·컨테이너 재디스패치를 재현하지 않으므로, 인증 필터의 배치 오류가 통과한다.

**C-M으로 충분한 자리를 C-R로 올리지 않는다.** 성공 응답과 어드바이스 오류는 디스패처를 통과하므로
대리로 충분하고, 전건을 RANDOM_PORT로 올리면 실행 시간만 늘고 잡는 것은 같다.
