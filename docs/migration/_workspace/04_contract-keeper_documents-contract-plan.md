## 2. 리서치 — 라이브러리와 기구현

### 2-1. `$ref` 해석을 라이브러리에 맡길 것인가 (H5)

**후보**: `io.swagger.parser.v3:swagger-parser` (Context7 `/swagger-api/swagger-parser`, 공식 README).

확인한 사실 두 가지와 결론:

1. **기본이 관용(lenient)이다.** `OpenAPIParser().readLocation(...)` 은 `SwaggerParseResult` 를
   돌려주고, 오류·경고는 **던지지 않고** `getMessages()` 리스트에 담기며 `getOpenAPI()` 는
   **부분 모델**을 돌려줄 수 있다. 이 저장소가 요구하는 **fail-closed** 와 정면으로 다르다 —
   도입한다면 `getMessages()` 가 비었음을 단언하는 층을 **추가로** 써야 하고, 그 단언을 빠뜨리는
   순간 지금보다 **더 조용한** 파서가 된다.
2. **`setResolveFully(true)` 는 이 파서의 목적을 파괴한다.** 전량 역참조는 `$ref` 를 내용으로
   치환하므로, 해석 후에는 **인라인 선언과 컴포넌트 선언을 구별할 수 없다.**
   그런데 `inlineHeaderNames()`·`headerComponentsByName()`·"컴포넌트 갈래는 전부 `const`" 라는
   `ContractHeaderDeclarationTest` 의 세 단언이 **정확히 그 구별 위에 서 있다.**

**결론: 라이브러리로 갈아타지 않는다.** 바퀴 재발명이 아니라 **요구 성질이 다르다** —

### 5-1. 무엇이 결함인가

`grep` 0건은 미착수라 정상이지만, **엔드포인트가 들어오는 커밋에서 케이스가 빠져도 아무도 모른다.**
게다가 이 결함은 **종류로 재발한다** — 배치마다 새 케이스 표가 생기고 매번 사람이 기억해야 한다.
따라서 넓힐 근거가 서고(구조적 재발), **탐지형**이어야 한다(면제 목록·무시 패턴 금지).

### 5-2. 설계 — 도달에 열쇠를 건다

**`SpecCaseCoverageContractTest`** (`@WebMvcTest` — `AuthenticationCoverageContractTest` 와 같은 슬라이스·같은 발견 수단)

1. **발견**: `RequestMappingHandlerMapping` 에서 **서비스 중인 (경로, 메서드)** 를 뽑는다.
   수기 목록 없음 — 그 테스트가 이미 증명한 방식이다.
2. **명세**: 세 test-spec 의 `### 2-N. \`METHOD /path\` (…)` 헤더를 파싱해
   (경로, 메서드) → 그 절의 케이스 ID 집합을 만든다.
3. **테스트 소스**: `api`·`application` 테스트의 `@DisplayName("<ID> …")` **머리**에서 ID 를 뽑는다.
   (본문 아무 데나가 아니라 머리다 — 주석에 ID 를 적어 두는 것만으로 통과하면 안 된다.)
4. **단언 세 방향**:
   - **A. 도달한 것은 덮인다** — 서비스 중인 (경로, 메서드) 가 명세에 있으면, **그 절의 케이스 ID
     전건**이 `@DisplayName` 머리에 있어야 한다. *→ 엔드포인트를 만들면서 케이스를 빠뜨린 커밋이 빨강.*
   - **B. 없는 ID 를 쓰지 않는다** — 테스트에 나오는 케이스 ID 는 전부 명세에 있어야 한다.
     *→ 오타·이름 변경 드리프트가 빨강.*
   - **C. 위임은 위임처가 실재해야 한다** — 아래 §5-3.
5. **아직 서비스되지 않는 (경로, 메서드) 는 의무가 없다.** 그래서 오늘 documents 77건은
   **초록**이고, 첫 컨트롤러가 붙는 순간 그 절만 의무가 생긴다. 면제 목록이 아니라 **도달 기반**이다.

### 5-3. 위임 갈래 — 은폐형이 되지 않게

WR-2 는 명세 스스로 "PUT 은 계약에 없다 … **개별 케이스를 두지 않는다**"로 P-15 단언에 위임했다.
산문 매칭은 취약하므로 **기계가독 표식**을 쓴다.

- 명세 ID 칸에 표식을 붙인다: `| **WR-2** ⟨위임: P-15⟩ | …`
- 단언 C: 위임 표식이 있는 행은 **본인 ID 대신 위임처 ID** 가 테스트에 실재해야 한다.
  위임처가 없으면 빨강.
- **위임 행의 총수를 정확 일치로 고정**한다(오늘 1). 새 위임이 생기면 diff 로 올라간다.

> 위임처가 사라지면 빨강이 되고, 위임 개수가 늘면 리뷰에 보인다. **CLAUDE.md 규칙 4 의
> 「은폐형은 넓히지 않고 탐지형으로 갈아탄다」에 어긋나지 않는다** — 다만 이것이 이 설계의

>
> WR-2 행에 표식을 다는 것은 **이미 그 행 산문에 적혀 있는 결정을 기계가독으로 옮기는 것**이지
> 판정을 바꾸는 사후 편집이 아니다. O-12 선례에 어긋나지 않는다.

## 6. K1 — `x-filename-charset` 소비자 배선

### 6-1. 처방의 뼈대

**계약을 오라클로 쓰되 구현 상수를 열지 않는다.** `FORBIDDEN_IN_FILENAME` 을 `internal` 로 여는 것은
**틀린 처방**이다 — 그러면 테스트가 계약 문자열과 구현 문자열을 **문자열 비교**하게 되고, 그것은
성질이 아니라 표기를 재는 것이며, 계약이 명시한 "어느 층에서 걷어내는지는 구현 판단"과도 어긋난다.
읽는 것은 **계약**이고, 재는 것은 **나간 값**이다.

| 항목 | 내용 |
|---|---|
| **P-37**(구 P-22, §3) | 인라인 헤더 `schema.examples[0]` — CE-3·CE-4 가 헤더 **구조**를 계약에서 읽는다 |
| **P-23** | `x-filename-charset.forbidden` · `.measured_on` 접근자를 `ContractSpec` 에 신설 |
| **CE-5** | **C-R**. 금지 집합의 **각 블록에서 표본**(C0 시작·중간·끝 / DEL / C1 시작·끝 / `"` `\` `/` `:` `*` `?` `<` `>` `|` 전건)을 제목에 넣어 내려받고, `filename*` 을 **퍼센트 디코딩한 값**에 금지 문자가 0개임을 단언. **케이스는 계약 집합에서 유도**한다 |
| **CE-6** | 제목이 금지 문자만으로 이뤄져 통째로 지워져도 이름이 비지 않고 헤더가 구조를 만족 |
| **CE-5t**(신규 제안) | **core 계층 전수 sweep**: 계약 `forbidden` 을 코드포인트 집합(74개)으로 전개해 **74개 각각**을 제목에 넣고 `exportFilename` 출력에 남지 않음을 단언. C-R 74회는 비싸고 이쪽은 싸다 — **표본(CE-5)과 전수(CE-5t)를 함께 둔다** |
| **N-20** | 계약의 `forbidden` 에서 **C1 구간만** 제거 → **CE-5·CE-5t 의 C1 케이스만** 깨지고 다른 블록은 안 깨진다 |

**CE-5t 의 배치**: `exportFilename` 은 `core` 에 있고 `ContractSpec` 은 `api` 테스트에 있다.
`application` 이 `api(project(":core"))` 로 core 를 노출하고 `api` 가 `implementation(project(":application"))`
이므로 **api 테스트에서 `exportFilename` 을 직접 부를 수 있다**(실측). 모듈 구조를 바꾸지 않는다.
`core` 쪽에 두려면 계약 리더를 `core` testFixtures 로 옮겨야 하는데, 그것은 이 항목이
요구하지 않는 구조 변경이다.

### 6-2. parity fixture 의 공허한 단언 (§1-4 신규 실측)

`parity/fixtures/export/export.json` 은 `:` `\` `|` DEL 의 **부재**를 단언하면서 그 문자를 넣는
입력이 없다. 그리고 C1 블록은 입력에도 needles 에도 없다.

- **이 파일은 `parity-verifier` 소관이다**(documents 명세 §7-3 O-19 가 F-3·F-4 의 parity 몫을
  그쪽으로 남겼다). 계약 레인은 **고치지 않고 통보한다** — §11.
- 통보 내용: ⑴ 4건이 공허하다는 실측 ⑵ 입력을 계약 `forbidden` 에서 유도하라는 요청
  ⑶ `export-filename-all-forbidden` 의 입력이 `'///'` 라서 이름과 다르다는 것.

### 6-3. 도달 증명

- **오늘의 손열거를 지우지 않는다.** `ExportTest.kt` 의 기존 케이스는 남기되, **CE-5t 가 전수를
  덮으므로** 그 손열거가 계약과 갈리면 CE-5t 가 먼저 빨개진다.
- **N-20 이 결속을 잰다**(명세 §4-4 에 이미 등재됨). C1 구간만 지웠을 때 **C1 케이스만** 깨져야 하고,
  다른 블록 케이스가 함께 깨지면 두 축이 한 값으로 뭉개져 있는 것이다.
- **추가 음성 대조 N-20b(신설 제안)**: 계약 `forbidden` 에서 `\\`(U+005C) 하나만 뺀다 →
  **CE-5t 의 `\` 케이스만** 깨진다. 오늘 `\` 는 Kotlin 테스트에도 parity fixture 입력에도
  **커버리지 0** 이므로, 이 대조가 통과해야 그 구멍이 실제로 메워진 것이다.
- **마감**: 내보내기 엔드포인트를 구현하는 그 커밋(§6 표 그대로).

하나가 바로 이번에 틀린 것으로 판정됐다.** 조항 문면만 고치고 규칙을 안 세우면, 다음 항목은
사유를 안 적는 아홉 쪽으로 돌아간다 — 그러면 정정 자체가 흔적 없이 사라진다.

**제안**: `x-change-policy` 에 `versioning` 절을 신설한다.

```
versioning:
  rule: |
    info.version 은 <소비자 관측 형태>가 바뀔 때 올린다 — 상태 코드·본문 스키마·필드 이름·

  entry_requirement: |
    version 을 올리지 않는 x-changelog 항목은 no_bump_reasons 중 하나를 version_note.reason
    으로 지목한다. 산문은 그 지목에 붙는 설명이지 사유 자체가 아니다.
```

- **근거 ID: G4** — 사람이 매번 기억해야 지켜지는 조항이고 **이미 여섯 번 반복**됐다.

### 7-3. 강제자 (범위 선언형은 빈 선언에서 통과하면 안 된다)

**`ContractVersioningTest`** (api 테스트, `ContractSpec` 확장)

2. 모든 항목의 `version` 이 **단조 비증가**(위가 최신)다.
3. **앞 항목과 `version` 이 같은 항목은 `version_note.reason` 이 있고, 그 값이
   `no_bump_reasons` 의 원소다.** ← *지어낸 산문 사유를 닫는 자리*
4. `no_bump_reasons` 어휘의 **원소 수를 정확 일치로 고정**한다(어휘가 느는 것은 diff 로 올라온다).

## 8. H5 — `$ref` 연쇄와 헤더 집합 하한선

### 8-1. 두 자리를 함께 고친다

한쪽만 고치면 다른 쪽이 여전히 가린다.

**⑴ `ContractSpec.resolveResponse` 재귀화** (`:247-255`)

- 로컬 `$ref` 를 **반복 해석**한다. 종료 조건 셋 — 매핑이 아님 / 순환 / 깊이 상한(예: 8) → **전부 `error`**.
- **섹션을 검증한다.** 지금은 `substringAfterLast('/')` 로 섹션을 버린다 →
  `#/components/schemas/X` 가 `components/responses/X` 로 조회된다. 응답 `$ref` 는
  `#/components/responses/` 로 시작해야 하고, 아니면 `error`.
- **외부 참조**(`other.yaml#/…`)는 `error` — 이 계약은 단일 파일이고, 조용히 무시하면 그 응답이 사라진다.

**⑵ 해석 결과에 `$ref` 가 남아 있으면 `error`** (`collectHeaders:263` 진입 전)

`response["headers"] ?: return` 자체는 옳다(대부분의 응답은 헤더가 없다). 막을 것은
**"`$ref` 노드를 헤더 없는 응답으로 오독"** 하는 것이므로, 판정을 `collectHeaders` 가 아니라
`resolveResponse` 의 사후 조건에 둔다.

**⑶ `operations()` 의 Path Item `$ref` fail-closed** (`:129-135`)

`paths.<path>` 값에 `$ref` 가 있으면 메서드 키가 하나도 없어 **그 경로가 통째로 사라진다.**
지원하지 않는 형태이므로 `error` 로 끊는다(오늘 0건 — 실측).

**⑷ `EXPECTED_HEADER_NAMES` 를 하한선에서 정확 일치로**

`containsAll(5개)` → `containsExactlyInAnyOrder`. 이것이 **H5 의 본체**다 — 연쇄 뒤에서 사라진
여섯 번째 헤더를 잡는 것은 재귀 수정이 아니라 이 단언이다. 새 헤더가 계약에 들어오면 이 목록에
한 줄을 더하는 diff 가 리뷰에 올라간다(`INLINE_HEADERS` 와 같은 관용구, `MIN_SOURCE_DECLARATIONS`
정확 일치 전환과 같은 처방).

### 8-2. 도달 증명 — 음성 대조가 이 항목의 본체다

**codex 가 「Claude 미실행 자리」에 떨어뜨린 지적이다. 이번에는 실행이 처방의 절반이다.**

| # | worktree 에서 계약에 할 것 | 깨져야 하는 것 | 안 깨지면 |
|---|---|---|---|
| **N-H1** | `components/responses/Unauthorized` 를 `{$ref: '#/components/responses/Unauthorized2'}` 로 바꾸고 내용을 `Unauthorized2` 로 옮긴다 (**연쇄 1단**) | 재귀 해석이 성공해 **아무것도 안 깨져야 정상**. `WWW-Authenticate` 가 여전히 세어진다 | ⑴이 배선되지 않았다 |
| **N-H2** | 두 응답이 서로를 가리키게 한다 (**순환**) | 명시적 순환 오류 | 깊이 상한만 있고 순환 탐지가 없다 |
| **N-H3** | 어떤 응답의 `$ref` 를 `#/components/schemas/ErrorResponse` 로 (**섹션 오류**) | 섹션 오류 메시지로 실패 | ⑴의 섹션 검증이 없다 |
| **N-H4** | 새 응답 헤더 `X-Request-Id` 를 인라인으로 하나 더한다 | `inlineHeaderNames()` 정확 일치 **및** ⑷ | ⑷가 여전히 하한선이다 |
| **N-H5** | `Location` 선언을 통째로 지운다 | ⑷ | 하한선이라 초록이었을 자리 |
| **N-H6** | `paths./health` 를 Path Item `$ref` 로 바꾼다 | ⑶ **그리고** `AuthenticationCoverageContractTest`(계약 쪽에서 경로가 사라져 매핑이 「계약 밖」이 된다) | ⑶이 배선되지 않았다 |

**N-H1 이 가장 중요하다** — 나머지는 "끊는가"를 재고, N-H1 만 **"제대로 따라가는가"** 를 잰다.
끊기만 하는 수정은 계약이 합법적으로 쓸 수 있는 형태(OpenAPI 3.1 에서 연쇄는 합법 — §1-6)를
금지하는 것이라 계약을 좁히는 셈이다. **계약을 좁히지 않고 강제 수단을 넓힌다**(§5.2 선례).

### 8-3. 라이브러리를 쓰지 않는 사유 (§2-1 요약 재게)

swagger-parser 는 ⑴ 기본이 관용이라 `getMessages()` 를 따로 단언하지 않으면 **지금보다 조용하고**,
⑵ `resolveFully` 는 인라인↔컴포넌트 구별을 없애 `ContractHeaderDeclarationTest` 의 세 단언을
성립 불가능하게 만든다. **요구 성질이 라이브러리가 제공하는 것과 다르다** — CLAUDE.md 의
직접 구현 허용 ①번이다.

## 12. 이 계획 자신의 미측정 자리

**후보를 사실로 적지 않는다**(§5.2 선례).

1. **§5-2 의 명세 헤더 파싱이 세 명세 전건에서 성립하는지**는 헤더 형식
   (`### 2-N. \`METHOD /path\` (…)`)이 셋 다 같다는 것까지만 확인했다. **파서를 돌려 보지는 않았다**
   (Gradle 금지). C5 착수 시 첫 단계로 확인한다.
2. **§8-1 ⑷(정확 일치 전환)이 오늘 트리에서 초록인지** 확인하지 못했다 — `headerDeclarations()` 가
   오늘 정확히 다섯 이름만 돌려주는지는 실행해야 안다. 계약 실측상 헤더 선언은
   `Cache-Control`·`X-Content-Type-Options`·`WWW-Authenticate`·`Location`·`Content-Disposition`
   다섯으로 보이나 **`$ref` 21건을 손으로 센 것이지 파서를 돌린 값이 아니다.**
   C8 첫 단계에서 확인하고, 여섯째가 나오면 그 자체가 H5 의 증거다.
3. **§7-2 의 `no_bump_reasons` 어휘 3종이 1.1.0 유지 아홉 항목을 다 덮는지** 분류해 보지 않았다.
   C6 에서 덮이지 않는 항목이 나오면 **어휘를 늘리지 말고 리더에 올린다** —
   어휘를 늘려 맞추는 것이 §7 이 막으려는 「사유를 지어낸다」의 재발이다.
4. **`x-filename-charset.forbidden` 이 Kotlin `Regex` 문법에서도 74 코드포인트인지**는
   **Python `re` 로 전개해 확인한 값**이다. `[` 안의 `\\` 와 `-` 해석은 두 엔진이 같지만,
   C9 착수 시 **Kotlin 쪽에서 한 번 더 전개해 74 를 확인**한다 — CE-5t 가 계약을 전개하므로
   그 확인이 테스트 안에 들어간다.
