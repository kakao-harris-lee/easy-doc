## 1. 판정 ① — 세마포어 초과 응답 코드

### 1-1. ⑴ 구현 레인 판독이 맞는가 — **맞다**

세 지점을 열어 확인했다.

| 확인한 것 | 자리 | 결과 |
|---|---|---|
| `/auth/login` 이 선언한 상태 코드 | `contracts/easy-doc-v1.yaml:815-829` | 200·401·422·500·503 — 구현 레인이 적은 것과 같다 |
| `ServiceUnavailable` 이 원인을 좁히는가 | `:1562-1583` | **좁힌다.** 첫 줄이 원인을 `ConfigurationError` 로 **명시**하고 본문 4개 항목·`examples` 4건이 전부 설정 미배선이다 |
| 그러므로 503 투입이 개정인가 | — | **개정이다.** 서술을 고치지 않고 배압을 넣으면 조항과 실동작이 갈린다 |

`x-error-body-universality`(`:439-511`)는 이 판정에 관여하지 않는다 — 그 절은 **본문 모양**의
보편성을 정할 뿐 어느 원인이 어느 상태 코드로 가는지를 정하지 않는다. 500·503 어느 쪽을 골라도
본문은 `ErrorResponse` 여야 한다는 요구는 동일하게 걸리고, 현행 500 은 그것을 만족한다.

### 1-2. ⑵ 500이 계약 위반인가 — **아니다**

세 조건이 모두 선다.

1. **선언돼 있다** — `:828` 이 `/auth/login` 의 `'500'` 을 `InternalError` 로 건다.
2. **본문이 계약이 든 문구다** — `PasswordHashingOverloadedException` 은
   `Argon2PasswordHasher.kt:186` 에서 `IllegalStateException` 을 상속한다. `EasyDocException`
   (`core/.../exceptions` `:19`)의 하위가 **아니므로** `GlobalExceptionHandler.handleUnexpected`
   가 잡고, 그 자리는 `UNEXPECTED_MESSAGE` 고정 문자열을 낸다. 계약 `InternalError` 의
   `examples.unexpected`(`:1544`)와 같은 값이다.
3. **헤더·Content-Type 도 그대로다** — 전역 부착(필터+밸브)과 `jsonError` 의
   `application/json` 을 지난다. §3의 27건 델타에 `ErrorContractTest` 가 포함돼 있어
   오류 응답의 전역 헤더가 계약에서 읽히고 있음이 실행으로 확인된다.

**그러므로 이번 배치를 계약 사유로 막지 않는다.**

### 1-3. 그래도 남는 것 — 위반은 아니지만 정확하지 않다

계약이 500 에 붙인 뜻은 「도메인 밖 예외(라이브러리 오류 등)」(`:1534`)와
「예상하지 못한 예외」다. **배압은 예상하지 못한 것이 아니라 설계된 동작**이다 — ②가 대기 줄에
상한을 건 목적 자체가 「매달리지 말고 떨궈라」였다. 그 결과가 「서버 오류가 발생했습니다」로
나가고 `handleUnexpected` 가 **건마다 ERROR 로 로그를 찍는다**(`GlobalExceptionHandler.kt:120`).
부하 급증 구간에서 이것은 ⑴ 사용자에게 서버 결함으로 보이고 ⑵ 로그·경보에서 용량 압력이
**장애로 읽힌다**. 계약 조항 위반은 아니고, **개정 근거의 실질**이 여기 있다.

### 1-4. ⑶ 503으로 넓히려면 — 근거와 문면

**근거: G2**(요구사항이 그것을 요구한다). 지목할 요구는 **계약 자신이 적어 놓았다** —
`BadGateway` 서술 `:1553-1555`: 5xx 를 가르는 축은 「일시적 장애라 **재시도할 값어치가 있는가**」이며
그 판단이 무너지면 안 된다. 자기 배압은 밀리초 뒤 풀리는 전형적 재시도 대상인데 500 은
클라이언트에게 「재시도해도 같다」를 말한다. **계약이 세운 축을 계약의 다른 조항이 못 지키는 형태**다.

**G1은 성립하지 않는다.** 현행 서술은 사실과 어긋나지 않는다(지금 배압은 503으로 나가지 않는다).
G1은 「즉시 고친다」 근거라 잘못 집으면 절차를 건너뛰게 되므로 여기 못박는다.

**필요한 문면 — 네 곳이다. 한 줄 추가로 끝나지 않는다.**

| # | 자리 | 무엇을 고쳐야 하나 |
|---|---|---|
| ⓐ | `components/responses/ServiceUnavailable.description` `:1563-1575` | 원인을 `ConfigurationError` **하나로 한정하는 첫 줄**을 두 갈래로 재서술한다 — ⓐ-1 운영 설정 미배선(현행 4종, 사람이 고쳐야 함) / ⓐ-2 **일시적 배압**(곧 풀리며 재시도 가치가 있음). 두 갈래의 **재시도 가치가 서로 반대**라는 것을 명시하지 않으면 503 하나가 상반된 두 뜻을 갖는다 |
| ⓑ | 같은 절 `examples` `:1579-1583` | 배압 전용 `detail` 문구 1건 추가. 기존 4건은 전부 「…이 설정되지 않았습니다」 형이라 배압을 그 어휘로 쓸 수 없다 |
| ⓒ | `components/responses/BadGateway.description` `:1553-1555` | 「503과 반드시 구분한다 — 503은 큐·설정이 아예 배선되지 않은 상태다」가 ⓐ 이후 **거짓이 된다.** 구분 기준을 「하위 시스템 장애(502) ↔ 자기 용량(503)」으로 다시 적는다. 이 줄을 안 고치면 두 절이 갈린다 |
| ⓓ | `x-changelog` + `00_contract-keeper_changelog.md` | 조항·근거 ID·영향 테스트·통보 대상 (`x-change-policy.procedure` 5) |

**`Retry-After` 는 이번 개정에 넣지 않기를 권고한다.** 헤더 컴포넌트 신설 + 전역 헤더 절과의
관계 재정리가 딸려 오고, 그것을 요구하는 근거가 G1~G4 어디에도 없다.

### 1-5. **판정 — 개정을 권고하되 계약 소유자 단독으로 시행하지 않는다**

리더 재심으로 올린다. 단독 판정하지 않는 이유는 blast radius 다.

- `ServiceUnavailable` 은 **12개 오퍼레이션이 `$ref`** 한다(`:794`·`829`·`853`·`945`·`994`·`1034`·
  `1077`·`1132`·`1220`·`1248`·`1288`·`1343`·`1382`). auth 한 자리의 문제를 푸는 개정이
  **문서·작업공간 API 전부의 503 의미를 바꾼다.**
- 그 중 문서 API 의 503 은 지금 「운영자가 키를 넣어야 한다」는 **배포 신호**로 읽힌다.
  거기에 「곧 풀리니 재시도하라」가 섞이면 운영 판독이 흐려진다 — 실질이
  `x-change-policy.escalate_to_leader` **4번(배포·운영 동작이 달라지는 변경)** 이다.

**React 영향: 없다**(`x-change-policy.procedure` 2 이행). `frontend/src/api/client.ts` 는 상태
코드로 **401 하나만** 분기하고(`:128`) 나머지는 전부 `ApiError(status, message)` 로 감싼다(`:132`).
500↔503 어느 쪽이든 화면은 `detail` 문자열을 그대로 보여 준다. 파괴적 변경이 아니다.

**대안도 함께 올린다 — 「개정하지 않는다」.** 현행 500 이 계약을 만족하므로 무개정이
blast radius 0 이다. 비용은 §1-3(사용자에게 서버 결함으로 보임 · ERROR 로그 홍수)이다.
**바꾸지 않기로 하는 것도 판정이므로**, 리더가 무개정을 고르면 그 근거를 이 문서에 적어
같은 제안이 다시 올라오지 않게 한다.

**리더가 개정을 고르면** 이 자리는 구현에서 도메인 예외 한 줄 + `mappingFor` 한 줄로 바뀌고
(`GlobalExceptionHandler.kt:368` 옆), 계약·contract test·구현이 **같은 변경 단위**여야 한다
(`x-change-policy.procedure` 4).

## 2. 판정 ② — C4 타입 불일치 422 본문의 계약 모양

### 2-1. 실측 방법

worktree 에 **측정 전용** `@SpringBootTest(RANDOM_PORT)` 케이스를 넣어 `/auth/signup`·`/auth/login`
에 13개 요청을 태우고 **나간 바이트를 그대로 찍었다**(단언 없음). 측정 후 파일을 지우고
`git status` 로 잔여 0 을 확인했다. 구현 레인의 표를 재확인하는 것이 아니라 **독립 측정**이다.

### 2-2. 실측 결과 — 타입 불일치는 **계약 준수**

| 요청 | 상태 | 본문 |
|---|---|---|
| `password` 자리에 정수 | 422 | `{"detail":[{"loc":["body","password"],"msg":"Input should be a valid string","type":"string_type"}]}` |
| `email` 자리에 불리언 | 422 | `{"detail":[{"loc":["body","email"],…,"type":"string_type"}]}` |
| `email` 자리에 정수 | 422 | 같은 모양 (`loc` = email) |
| `password` 자리에 불리언 | 422 | 같은 모양 (`loc` = password) |
| `password` 자리에 **배열** | 422 | 같은 모양 — 스칼라 밖 타입도 같은 갈래로 떨어진다 |
| `password` 자리에 **객체** | 422 | 같은 모양 |
| `/auth/login` 정수 `password` · 불리언 `email` | 422 | 같은 모양 — signup 전용 처방이 아니다 |

`ValidationFailed`(`:1497-1528`) 대조 — **네 조건 전부 선다.**

1. **상태 422** — 계약이 `/auth/signup` `:791` · `/auth/login` `:826` 에 선언한 값이다.
2. **배열 갈래가 맞다** — `:1510` 이 「타입 불일치」를 **명시적으로 배열 쪽**에 배정한다.
   문자열 갈래(`:1512`, 길이·형식·빈 값)와 섞이지 않았다: 형식 위반 요청은 같은 실측에서
   `{"detail":"이메일 형식이 올바르지 않습니다"}` 로 **문자열**이 나왔다. 두 갈래의 경계가 산다.
3. **키 3개 정확히** — `loc`·`msg`·`type` 뿐. `input`·`ctx` 없음
   (`ValidationErrorItem` `:1615-1618`, `x-change-policy.invariants` 3번).
4. **입력값 미반향** — 거절된 값(`12345678`·`31337`·`true`·배열/객체 원소)이 응답 바이트
   어디에도 없다. 불변식이 지켜진다.

`loc` 이 문제 필드를 가리키는 것까지 확인했다(계약 `loc.examples` `:1629` 와 같은 모양).

### 2-3. ⚠ 범위 인접 결함 — 계약의 `field_missing` 예시가 **실재하지 않는다**

리더가 기준형으로 지목한 그 예시를 재려고 필수 필드 누락을 태웠더니 이것이 나왔다.

| 요청 | 실측 본문 |
|---|---|
| `password` **키 자체를 뺀다** | `{"detail":[{"loc":["body"],"msg":"JSON decode error","type":"json_invalid"}]}` |
| `password` 를 **명시적 `null`** | 위와 **완전히 동일** |
| **깨진 JSON** (본문 절단) | 위와 **완전히 동일** |

계약 `ValidationFailed.examples.field_missing`(`:1524`)이 든 모양은
`loc:["body","password"]` · `msg:"Field required"` · `type:"missing"` 이다. **그 모양은 어떤
요청에서도 나오지 않는다.** 기제: Kotlin data class 의 필수 생성자 파라미터 누락이
`bodyReadItem`(`GlobalExceptionHandler.kt:305`)의 `MismatchedInputException` 탐색에 걸리지 않아
`?: return` 의 파싱 실패 갈래로 떨어진다. 핸들러의 `FIELD_REQUIRED_MESSAGE`(`:278`)는 쿼리
파라미터·multipart 누락에만 쓰이고 **본문 필드 누락에는 도달하지 않는다.**

**판정: 계약 위반은 아니다.** `loc`·`msg`·`type` 의 값은 스키마에서 `examples` 로만 적혀 있고
(`:1629-1631`) `const`·`enum` 이 아니다 — 규범이 아니라 예시다. 규범인 것(422 · 배열 갈래 ·
키 3개 · 미반향)은 전부 선다.

**그래도 등재한다. 두 가지가 실질이다.**

- **진단 가능성 상실** — 「비밀번호를 안 보냈다」와 「JSON 이 깨졌다」가 **바이트 단위로
  구분되지 않는다.** React `client.ts` 의 `readErrorMessage` 는 `msg` 를 그대로 화면에 올리므로,
  필드 하나를 빠뜨린 사용자가 **"JSON decode error"** 를 보게 된다.
- **강제자가 없다** — S-9(누락)·S-9b(타입 불일치) 어느 쪽도 `loc`·`msg`·`type` 의 **값**을
  단언하지 않는다(키 집합과 미반향만 본다). 구현 레인 산출물 §6이 「`loc` 이 어느 필드인지
  가리킨다」고 적었는데, **타입 불일치에서는 참이고 누락에서는 거짓**이며 어느 쪽도 테스트가
  붙들고 있지 않다.

**처분: 계약을 고치지 않는다.** 예시를 실측 모양(`json_invalid`)으로 바꾸는 것이 G1 처럼
보이지만, 그것은 **계약을 Kotlin 스냅샷으로 만드는 것**이다 — 계약은 요구사항이 요구하는
인터페이스이고(`x-change-policy.premise`), `field_missing` 예시는 **요구하는 쪽**을 정확히
표현하고 있다. 고쳐야 할 것은 예시가 아니라 구현이다. `kotlin-implementer` 에 넘긴다(§5).

### 2-4. 반대 방향 — **대상 없음이 맞다**

같은 실측에서 요청 DTO 의 선언 필드를 리플렉션으로 찍었다:
`SignupRequest` = `email: String, password: String` / `LoginRequest` = 동일.
**비문자열 필드가 하나도 없다.** `/auth/me` 는 요청 본문이 없다. auth 표면에 문자열→숫자 방향의
대상이 존재하지 않는 것이 확인된다 — 구현 레인의 「Phase 4 첫 비문자열 필드 커밋에서 판정」이
맞는 처분이다. **추론이 아니라 실측으로 확인했다.**

## 3. 판정 ③ — 계약 대조 확대(`8b5ede6`)

### 3-1. 세 델타 독립 재현 — **전부 일치**

각 변이는 계약 파일 **한 행만** 바꾸고 `:api:test` 전량을 돌린 뒤 결과 XML 에서 실패를 셌다.

과잉 결합 없음 — 세 변이 모두 해당 열의 케이스만 깨졌다(명세 §4-4 말미 요건).

### 3-2. P-3b / P-4b 가 성질 5를 만족하는가 — **만족한다**

명세 §4-2 성질 5는 「넓히는 것은 자유지만 **넓힌 만큼 음성 대조도 넓힌다** — 읽기만 하고 안 쓰는
노드는 다음 사람에게 『이미 덮였다』로 읽힌다」이다. 세 갈래로 갈라 본다.

| 새 읽기 | 단언에 쓰이는가 | 음성 대조가 있는가 |
|---|---|---|
| **P-3b** `headerComponentsByName` — 응답 `$ref` 에서 헤더 이름→컴포넌트 유도 | **쓴다** — `globalHeaderValues` 12곳 + `assertPrivateHeaders` | **있다.** N-3 델타 3→27 을 **독립 재현**했다. 손 목록 두 벌이 사라지면서 검사 범위가 5개 클래스로 늘어난 것이 숫자로 드러난다 |
| **P-4b** `globalHeaderValues` — 전역 절 × 컴포넌트 `const` 합성 | **쓴다** — 같은 12곳 | **있다.** 같은 N-3. 더해 「계약 안 두 절의 값이 서로 같다」 전용 케이스가 27건 안에 있다 |
| **`security` / `operations`** (③ 커밋에서 함께 늘어난 읽기) | 쓴다 — `AuthenticationCoverageContractTest` | §3-3 참조 |

성질 4(읽은 값을 실제 단언에 쓴다)도 함께 선다 — 값 리터럴을 쓰던 다섯 테스트가 전환됐고,
전환되지 않았다면 `const` 변이에서 깨질 수 없다. **27 이라는 수 자체가 그 증거다.**

**미실행 가드 1건(경미).** `headerComponentsByName` 의 「같은 헤더 이름이 서로 다른 컴포넌트를
가리키면 실패」(`ContractSpec.kt:199`)는 어떤 음성 대조도 밟지 않는다. 읽고 안 쓰는 **노드**가
아니라 방어 `require` 라 성질 5 위반은 아니다. N-10 으로 명세에 등재만 한다.

### 3-3. `security`/`operations` 의 **계약 측** 음성 대조 — 없던 것을 실행해 채웠다

구현 레인 §3의 변이 두 건은 **구현 측**(경로를 서비스하거나 목록에서 빼는)이다. 계약 노드를
새로 읽기 시작했으면 **계약을 바꿔서** 깨지는지도 봐야 성질 5가 닫힌다. 실행했다:

```
변이: /auth/me 의 security 선언을 빈 목록으로 (공개라고 계약이 말하게 한다, :840)
→ 빨강 1 — AuthenticationCoverageContractTest
   「보호로 분류된 매핑이 전부 인증 목록에 있고, 목록에 계약 밖·공개 경로가 없다」
복원 sha256 일치: True · 잔여 diff 0
```

**결속돼 있다.** `operations()` 는 이 케이스가 계약의 (경로, 메서드) 전량을 훑어 공개/보호를
가르는 구조라 같은 케이스가 전이적으로 붙든다 — 전용 대조를 따로 만들 필요는 없다고 판정한다.

### 3-4. ⚠ 범위 인접 결함 — 계약이 **7종**이라 적은 자리를 강제자가 **5종**만 돈다

§3-1 의 5 vs 7 을 따라갔더니 내 조항 쪽 문제였다.

`x-global-response-headers.x-phase3-measurement.unreachable_by_filter.cases`(`:654-661`)가
파싱 단계 거절을 **7종으로 열거**하고, `resolution`(`:662-666`)이 「밸브가 위 7종 **전부**를
덮는 것을 계측으로 확인했다」고 적는다. 그런데 상시 회귀인 `ContainerRejectedRequest`
(`api/src/test/.../support/RawHttp.kt:237-283`)의 열거자는 **5개**다. 계약의 7종 중 둘에
대응하는 케이스가 없다:

- **「콜론 없는 헤더 줄 → 400」**
- **「알 수 없는 메서드 → 405」**

열거자 자신의 주석(`:230-232`)도 축으로 「메서드 토큰」을 들지만 그 열거자는 없다 —
**선언이 두 겹으로 실제보다 넓다.**

**판정: 이번 배치의 결함이 아니고 계약 위반도 아니다.** 밸브가 그 둘을 못 덮는다는 뜻이 아니라
「7종 전부」라는 주장을 **일회성 계측이 붙들고 있고 상시 회귀는 5종만 붙든다」는 뜻이다.
이 하네스가 반복해 겪은 「선언한 범위 ≠ 실제 도달」 형태이고, 구조적 재발형이므로 등재한다.

**두 갈래 중 하나로 마감해야 한다. 어느 쪽인지 측정 없이 못 정한다.**

- 열거자 2개를 더해 도달을 선언에 맞춘다(계약 무수정), **또는**
- 측정 결과 「알 수 없는 메서드」가 실은 서블릿까지 도달해 Spring 이 405 를 만드는 것이라면
  그 항목은 `unreachable_by_filter` 가 아니라 `reachable_by_filter`(`:643-648`) 소속이고,
  그때는 **계약이 사실과 다르다(G1)** — 내가 고친다.

지금 어느 쪽으로도 적지 않는다(`x-error-body-universality.x-unmeasured` 와 같은 처분).
`00_progress.md` 는 이 배치에서 손대지 않으므로 리더가 열린 항목으로 받는다.

## 4. 판정 ④ — Gradle 선언 입력(`2660252`) 재확인

`03_contract-keeper_auth-verification.md` §5에서 내가 등재한 결함
(「계약을 바꿔도 계약 테스트가 돌지 않는다」)의 **4조건을 직접 재현했다.**

| 조건 | §5 실측(처방 전) | **이번 재현(처방 후)** | 판정 |
|---|---|---|---|
| 같은 명령 2차 · 변경 없음 | UP-TO-DATE | `:api:test` **UP-TO-DATE** (16 up-to-date) | 증분이 살아 있다 — 선언 입력이 캐시를 무력화하지 않았다 |
| **계약 파일만 변경** | **UP-TO-DATE (실행 0)** | `:api:test` **실행** (1 executed) | **결함이 닫혔다** |
| `cleanTest` 후 **처음 보는** 계약 내용 | **FROM-CACHE (실행 0)** | `:api:test` **실행** — FROM-CACHE 아님 | **결함이 닫혔다** |
| 양성 대조: `/auth/login` `'401'`→`'403'` (`:824`) | — | `:api:test` **FAILED** · 빨강 **1** (`AuthContractTest` L-2) | 실행이 **판정까지** 간다 |

**추가 대조 하나 — 캐시가 죽은 것이 아님을 보였다.** 계약을 원상 복구하고 `cleanTest` 후
재실행하니 `:api:test` **FROM-CACHE**(1 from cache)였다. 즉 빌드 캐시는 살아 있고, 달라진 것은
**계약 파일이 지문에 들어갔다**는 것뿐이다. 이 대조가 없으면 위 세 행이 「캐시를 꺼서 늘 도는
것」과 구분되지 않는다.

경로 민감도를 `NONE` 으로 둔 것도 확인했다(`backend-kotlin/build.gradle.kts:147` 부근) —
절대 경로가 지문에 들어가면 다른 기계가 캐시를 재사용하지 못한다.

**§5 결함: 닫혔다.** 「Phase 3 종료 전 마감 권고」를 해제한다.

**도달 범위를 넓혀 적지 않는다 — CI 캐시 축은 이번에도 미관측이다.** 내가 잰 것은
**로컬 증분 실행과 로컬 빌드 캐시**뿐이다. 원격/CI 캐시가 이 지문을 실제로 재사용·무효화하는지는
관측하지 않았다. 구현 레인도 같은 한계를 적었고 **양쪽이 같은 자리에서 멈춰 있다** —
합쳐서 「확인됐다」로 읽히면 안 되므로 여기 못박는다. 충족으로도 위반으로도 적지 않는다.

## 6. 이 판정이 재지 않은 것

**충족으로도 위반으로도 적지 않는다.**

- **CI 에서의 캐시 재사용**(§4 말미). 두 레인이 같은 자리에서 멈춰 있다.
- **세마포어 초과의 HTTP 실측.** 500 판정은 예외 계층(`IllegalStateException` ← 백스톱)과
  고정 문구에서 **연역**했고 부하를 걸어 응답 바이트를 보지는 않았다. 개정하기로 하면
  그 커밋에서 HTTP 경계 회귀와 함께 재는 것이 맞다.
- **계약 7종 중 나머지 2종의 실제 거절 단계**(§3-4). 측정이 선행돼야 갈래가 정해진다.
- **전체 빌드**(`ktlintCheck`·`detekt`·Python 게이트). 내가 돌린 것은 `:api:test` 기준선 1회와
  변이별 재실행 6회다. 그 축은 병렬 리뷰 게이트 소관이다.
