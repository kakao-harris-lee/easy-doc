## 2. SECRET-LITERAL — 코드 측 해소

### 왜 걸렸나

`const val SIGNUP_PASSWORD = "SignupRequest.password"`. 규칙의 이름 관문은 `password\s*[:=]`로 **왼쪽 경계가 없어** 식별자 접미사에도 걸린다(의도된 설계 — `user_password = …`를 잡기 위함). 값 판정 `looks_like_real_secret`은 문자 클래스 3종(소문자·대문자·`.`) · 길이 22 · 엔트로피 3.97 bits/char로 임계(3종·12자·3.2)를 모두 넘겨 통과했다.

### 처방과 근거

**상수를 `SIGNUP_PASSWORD_FIELD`로 개명**(대칭으로 `SIGNUP_EMAIL` → `SIGNUP_EMAIL_FIELD`). 로직 변경 0, 파일 내부 전용 `private companion object` 상수, 사용처 3+3 전건 치환. `:api:compileTestKotlin` exit 0.

개명이 회피가 아닌 이유: 담긴 것은 **계약 필드 경로**이지 비밀번호가 아니다. 이름이 내용과 어긋나 있었고 개명이 그것을 바로잡는다 — 규칙이 조용해지는 것은 원인이 아니라 결과다. 같은 처방을 저장소가 이미 규정하고 있다: `LLM-RAW-INPUT`(역시 unmarkable)의 오탐 안내가 *"이름을 masked\*로 바꿔 의도를 드러낼 것"*이다. **값-이름 불일치의 정본 처방이 개명**이라는 전례.

되돌림 방지로 선언 자리에 KDoc을 남겼다(왜 접미사가 붙었는지 + 되돌리면 CI가 다시 빨개진다).

### 기각한 갈래

- **탐지 정밀화(값이 점 구분 식별자 경로면 비밀 아님)** — 기각. JWT가 점 구분이고, 숫자 없는 base64 키가 존재할 수 있다(43자 기준 ≈0.05%). **비밀키 BLOCK 규칙을 좁히는 데 쓰기엔 근거가 얇다.** 이번 배치에서 탐지 좁힘은 OWNERSHIP-403 한 건으로 제한했다.
- **임시 마커** — 지시대로 달지 않았고, 위 §1로 애초에 불가.

## 3. OWNERSHIP-403 — 규칙 정밀화 (탐지형)

### 왜 걸렸나 — 구조적 결함

옛 패턴은 `\b(?:403|FORBIDDEN|Forbidden)\b` 하나. **토큰이 보이면 무조건 BLOCK**이라 다음이 전부 걸렸다:

| 줄 | 내용 | 성격 |
|---|---|---|
| 181 · 296 | `@DisplayName("… 403 이 아니다")` | 테스트 이름 |
| 182 | `fun \`타인 자원은 404 이고 403 이 아니다\`()` | 테스트 이름 |
| 189 · 304 | `assertThat(…).isNotEqualTo(FORBIDDEN)` | **불변식 집행** |
| 533 | `private const val FORBIDDEN = 403` | 위 단언이 쓰는 상수 (토큰 2개) |

**404 소유권 은닉 불변식을 지키는 코드가 그 불변식의 게이트에 막혔다.** 규칙의 `false_positive` 주석이 *"테스트의 403 기대값이면 오탐"*이라고 이미 적고 있었는데 심각도는 BLOCK이고 마커도 못 쓴다 — **정당한 오탐에 출구가 없는 게이트**였고, 그 상태의 CI 빨강은 무시·면제로만 풀린다.

전수 census 결과 **저장소의 어떤 생산 코드도 403을 만들어 내지 않는다** — 8건 전부 주석·테스트 이름·집행 단언·상수다.

### 처방

**불활성 형태를 먼저 소비하는 대안**을 패턴 앞에 두고, 그 그룹이 참여했으면 `refine`이 후보에서 뺀다. 세 형태를 뺀 근거는 셋 다 같은 문장이다:

> 그 자리는 403 응답을 보낼 수 없고, **보낼 수 있는 자리는 여전히 전부 잡힌다.**

| 형태 | 뺀 범위 | 무손실 근거 |
|---|---|---|
| ① 부호 반전 단언 | `isNotEqualTo`/`assertNotEquals`/`assertNotSame`/`isNotIn`의 **첫 인자**가 403 토큰일 때 | 부호가 반대다. `isEqualTo(FORBIDDEN)`(403을 **기대**하는 단언 — 진짜 위반 신호)은 그대로 잡힌다 |
| ② 테스트 이름 | `@DisplayName("…403…")` · 백틱 식별자 — **토큰을 품은 것만** | 라벨·식별자는 값이 아니다 |
| ③ 상수 선언 | `val`/`var`/`const`/`let` 키워드가 있거나, Python은 **대문자 상수**만 | 선언은 묶기만 한다. `status(FORBIDDEN)` 같은 사용처는 `FORBIDDEN` 토큰으로 여전히 매치 |

③이 특히 강하다 — **무손실을 실행으로 증명**했다(대조 C).

`refine` 판별식(§4-octies.7) 통과: 이 훅은 **자기 패턴이 직접 소비한 캡처 그룹**이 참여했는지만 본다. 바깥 텍스트도, `_advance`·`_argument_span`의 산출물도 읽지 않는다 — 어휘·구문 층의 정확성에 의존하지 않으므로 `LOG-BODY`가 다섯 갈래를 냈던 형태가 아니다.

### 기각한 더 넓은 갈래 (근거를 넘지 않는다)

- **문자열 리터럴 전체 제외** — *"상태 코드는 세 스택 모두 정수·열거값이지 문자열이 아니다"*는 참이나, `@ApiResponse(responseCode = "403")` · `responses={"403": …}` 같은 **403 응답 선언**을 조용히 삼킨다. 그것은 이 불변식이 봐야 할 신호다. (대조 N10이 이 기각을 회귀로 고정)
- **경로 면제(`tests/` 통째로)** · **심각도 강등(BLOCK→WARN)** — 둘 다 은폐형.
- **`hardened` 창** — 창 안의 다른 403까지 통째로 눌러 **줄 단위 부수 피해**가 난다. 소비형은 그 자리만 뺀다(대조 N12·N13이 이 차이를 잰다).

첫 구현은 백틱 대안을 `` `[^`\n]*` ``로 두었다가 KDoc 인라인 코드를 전부 삼켜 제외 집계가 **1446건**으로 폭증했다. 뺀 것이 없는데도 "규칙이 눈감은 양"이 거짓이 되는 상태 — 리포트가 다음 감사의 입력이므로 토큰을 품은 것만 매치하도록 조였다(최종 6건).

### 부수 수정

`Rule.refine_reason` 신설(필드는 **끝에** 추가 — 위치 인자 밀림 방지 주석 준수). 옛 코드는 모든 `refine` 제외를 `"값의 모양이 불변식 대상이 아님"` 한 문장으로 적었는데, OWNERSHIP-403은 값의 모양을 보지 않는다. 리포트가 무엇을 눈감았는지 잘못 적는 것을 막는다.

## 5. 남는 것 (닫지 않았다고 적는다)

1. **`HTTP_403_FORBIDDEN` · `SC_FORBIDDEN` 미도달 — 선언된 0으로 전환.**
   `\b` 경계 때문에 밑줄에 둘러싸인 토큰은 잡히지 않는다. **정밀화 이전부터 그랬고**(옛 패턴 실측: 무적중) 이번 변경과 무관한 **기존 결함**이다. 경계를 풀지 않은 이유: `FORBIDDEN_IN_FILENAME`(파일명 정화) · `FORBIDDEN_ANNOTATIONS`(계약 검사) 등 **HTTP와 무관한 이름**이 전부 BLOCK이 되어, 출구 없는 규칙에 새 오탐 무리를 들인다. 조용한 0 대신 `xfail(strict=True)` 2건으로 **선언**했다 — 누가 탐지에 넣으면 `xpass`로 뒤집혀 시끄러워진다. **넓힐지는 별건 판정 대상.**
2. **개명의 잔여 위험.** 규칙의 이름 관문이 이름 기반이므로, 장래에 `SIGNUP_PASSWORD_FIELD`에 진짜 키를 넣으면 걸리지 않는다. 이름 기반 관문의 내재적 성질이고 개명이 새로 만든 것이 아니다. KDoc이 그 자리를 지킨다.
3. **`tests/test_privacy_scanner.py:73 _log_body_verdict` 가 썩어 있다.** 존재하지 않는 `scanner._is_candidate`를 부르는데 **호출자가 0**이라 조용하다(부르면 `AttributeError`). 이번 변경과 무관하고 게이트도 아니라 손대지 않았다 — 정리는 별건으로 남긴다.
4. **마커 예산 7/7 그대로.** 올리지 않았고 새로 쓰지도 않았다.

## 7. 정정 (2026-08-19, 게이트 23 교차 종합 ⓐ 이후)

**위 §3·§4·§6 은 지우지 않는다.** 옛 판정이 무엇을 근거로 통과라고 적었는지가 남아 있어야
같은 형태의 공백을 다음에 알아볼 수 있다. 아래가 그 판정의 정정이다.

### 7-1. 무엇이 틀렸나 — 판정이 아니라 **대조 입력**이 좁았다

`OWNERSHIP-403` 정밀화의 ③(상수 선언 제외)을 정당화한 문장은 이것이었다:

> ③ 이 특히 무손실이다 — 선언을 빼도 `status(FORBIDDEN)` 같은 사용처는 `FORBIDDEN` 토큰으로
> 여전히 매치된다.

이 문장은 **무조건형**으로 적혔지만 실제로는 **상수의 이름이 그 자체로 403 토큰일 때만** 참이다.
불활성 패턴 ③ 의 식별자 자리가 `\w+` 였고 — **이름에 아무 제약이 없었다.** 이름이 토큰을 품지
않으면 선언은 제외되고 **사용처에도 토큰이 없어**, 진짜 403 반환이 어디서도 잡히지 않는다.

§4-1 의 종단 음성 대조 C 는 `const val FORBIDDEN = 403` + 사용처였고, §4-2 의 회귀 N11 도 같은
형태였다. **둘 다 상수 이름이 `FORBIDDEN`** — 즉 위 KDoc 이 든 예시를 그대로 재현한 것이다.
그래서 통과가 나오는 것이 당연했고, 통과는 **그 이름 하나에 대해서만** 유효했다.

**따라서 옛 판정("게이트 자신의 탐지력 — 준수")은 거짓이 아니라 근거가 부족했다.** 대조 집합에
「토큰 없는 이름」 갈래가 아예 없었고, 그 공백을 codex C-1 과 Claude B-1 이 각각 독립으로 짚었다.

### 7-3. 처방 — 제외의 전제를 **패턴이 강제하게** 바꿨다

논증으로 남겨 두면 다음 편집에서 조용히 거짓이 되므로, 조건을 규칙 안으로 옮겼다.

| 갈래 | 정정 |
|---|---|
| ③ 상수 선언 | **선언된 이름 자신이 규칙의 토큰(`_403_TOKEN`)일 때만** 제외. 토큰 없는 이름의 `= 403` 리터럴 선언은 **BLOCK 유지** — 사용처가 잡히지 않기 때문이다 |
| ② 백틱 | **`fun` 바로 뒤**(함수 이름 자리)만 소비. 자리를 묻지 않으면 호출 인자의 백틱 식별자까지 삼킨다 |
| 공유 | 탐지 토큰과 ③ 의 이름 관문이 **한 조각(`_403_TOKEN`)**에서 나온다. 두 벌이면 갈리고, 갈린 쪽은 늘 조용하다 |

`HTTP_FORBIDDEN`·`FORBIDDEN_STATUS` 처럼 밑줄로 이어 붙인 이름은 사용처가 `\b` 경계 때문에
안 잡히므로 **제외 대상이 아니다 — 선언이 BLOCK 으로 남는다**(회귀 N18·N19).

**넓힘의 방향에 유의한다.** 붙은 조건은 전부 후보를 **늘리는** 쪽이고, 은폐 장치는 이번에도 0이다
(마커 0 · 경로 면제 0 · 예산 인상 0 · 심각도 강등 0). Kotlin 파일은 한 줄도 건드리지 않았다.

## 8. 재판정 (2026-08-19, 게이트 24 교차 종합 ⓐ · 리더 재판정)

**§5-1 과 §7-4 의 옛 판정을 지우지 않는다.** 그 판정이 무엇에 대해 내려진 것이었는지가 남아
있어야 이번 재판정이 **번복**이 아니라 **범위 분리**임을 다음 사람이 알아본다. 아래가 그
좁힘이고, 게이트 23 충돌 Ⅲ(「privacy-gate 재감사」)에 대한 답이다.

### 8-1. 옛 판정을 **좁혀** 다시 적는다 — 무엇이 기각됐던 것인가

§7-4 는 이렇게 적었다:

> **§5-1 의 `HTTP_403_FORBIDDEN`·`SC_FORBIDDEN` 미도달은 그대로 둔다** … codex 의
> 「정상 통과로 전환」안은 기각한다. 사유: 경계를 풀면 `FORBIDDEN_IN_FILENAME`·
> `FORBIDDEN_ANNOTATIONS` 처럼 **HTTP 와 무관한 이름**이 전부 BLOCK 이 되어 …

**이 기각은 「`\b` 경계를 푸는 갈래」에 대해 내려졌다.** 사유 문장 자체가 그것을 말하고 있다 —
근거가 전부 경계 완화의 부수 피해다. 그런데 처방에는 **두 번째 갈래**가 있었고 그 갈래는
판정의 대상이 아니었다:

| 갈래 | 얻는 것 | 대가 | 판정 |
|---|---|---|---|
| ㉮ 경계 완화(`\b` 제거) | 밑줄 결합 전부 | `FORBIDDEN_*` 계열이 전부 BLOCK — **출구 없는 규칙**(`UNMARKABLE_RULES`)에 오탐 무리 | **기각 유지** (§7-4 그대로) |
| ㉯ 명시 토큰 추가 | **실측된 두 이름만** | 없음 — 둘 다 HTTP 상태 상수 전용 이름 | **채택** (신규) |

따라서 §5-1·§7-4 의 「미도달을 그대로 둔다」는 **㉮ 에 대한 기각으로 좁혀 읽는다.** ㉯ 는
`CLAUDE.md` 규칙 4 분류로 **탐지형 넓힘**이고, 기각 근거였던 오탐 무리가 이 갈래에서는
발생하지 않는다(`FORBIDDEN_IN_FILENAME` 은 토큰 목록에 없다).

**판정을 바꾼 근거는 3관점 실측이다.** codex 게이트 23 C-1 후단 · 게이트 24 X24-1(`scan()`
직접 호출) · Claude S-2(실제 Kotlin 프로덕션 파일 주입 + CI 동일 명령 **exit 0**)가 **같은
자리**를 가리켰음이 게이트 24 교차 종합 ⓐ 에서 확정됐다. 옛 판정이 든 「기존 결함이라 이
배치의 회귀가 아니다」도 여전히 참이지만, 그것은 **누구의 책임인가**에 대한 답이지
**닫아야 하는가**에 대한 답이 아니었다.

### 8-2. 무엇을 바꿨나

`_403_TOKEN` **한 조각**에 두 이름을 더했다. 탐지 패턴과 불활성 ③ 의 이름 관문이 같은 조각을
쓰므로 **선언 제외도 함께 따라온다** — `const val SC_FORBIDDEN = 403` 은 빠지고 사용처
`sendError(SC_FORBIDDEN)` 는 잡힌다. ③ 의 전제("이름이 토큰일 때만 뺀다")가 확장 뒤에도
그대로 성립한다.

```
- _403_TOKEN = r"(?:403|FORBIDDEN|Forbidden)"
+ _403_TOKEN = r"(?:403|HTTP_403_FORBIDDEN|SC_FORBIDDEN|FORBIDDEN|Forbidden)"
```

**`sendError` 자체는 토큰으로 올리지 않았다 — 범위는 근거를 넘지 않는다.** 리더가 든 두 관용구
`sendError(…403…)`·`sendError(SC_FORBIDDEN)` 는 `403`·`SC_FORBIDDEN` 토큰으로 **전건 잡힌다**
(회귀 N5·N20·N22·N23 이 그것을 잰다). 맨 `sendError` 를 올리면 `sendError(404)`·`sendError(500)`
처럼 403 과 무관한 호출까지 출구 없는 규칙의 후보가 되는데, 그 확장에는 실측 근거가 없다 —
교차 종합 §143-148 이 이 대가를 미확정으로 남겼고 여기서 **좁은 쪽으로 확정**한다.

Kotlin 은 **한 줄도 건드리지 않았고**, `00_progress.md` 도 무접촉이다. 은폐 장치 0(마커 0 ·
경로 면제 0 · 예산 인상 0 · 심각도 강등 0) — 이번 변경은 후보를 **늘리는** 방향뿐이다.

### 8-3. 음성 대조 — CI 스텝과 동일 명령 (`--rule` 없이 전수)

주입 파일은 신규 생성 후 삭제(기존 파일 무수정). 잔여 0 · 복원 후 리포트 **바이트 동일** 확인.

| 대조 | 주입 | 옛 스캐너 | **새 스캐너** |
|---|---|---|---|
| 0 기준선 | — | exit 0 | **exit 0** |
| M | `response.sendError(HttpServletResponse.SC_FORBIDDEN)` (.kt) | exit 0 · **미검출** | **exit 1 · 검출** |
| N | `raise HTTPException(status.HTTP_403_FORBIDDEN)` (.py) | exit 0 · **미검출** | **exit 1 · 검출** |
| O | `response.sendError(SC_FORBIDDEN, "denied")` (.kt) | exit 0 · **미검출** | **exit 1 · 검출** |
| 복원 후 | — | exit 0 | **exit 0** |

세 형태를 함께 넣은 한 번의 전수 스캔에서 `[BLOCK] OWNERSHIP-403 3건`. 옛 스캐너는 같은 세
파일이 디스크에 있는 상태에서 **적중 0**이었다.

### 8-4. 오탐이 늘지 않았다는 증거 — 리포트 **바이트 동일**

전수 리포트를 변경 전후로 받아 `diff` 했다: **완전 동일**. 즉 이 확장은 저장소의 실제 트리에서
새 후보를 하나도 만들지 않았다.

| 지표 | 변경 전 | 변경 후 |
|---|---|---|
| 전수 스캔 | exit 0 · 검사 파일 241개 | **exit 0 · 241개** |
| 호출 지점 표기(마커) | 7건 / 상한 7 | **7건 / 상한 7 (인상 0)** |
| `OWNERSHIP-403` 2차 제외 | 6건 | **6건** |
| `SECRET-LITERAL` / `XML-DTD` 2차 제외 | 1건 / 2건 | **1건 / 2건** |

### 8-5. 회귀 — `xfail(strict)` 2건이 **정상 통과**로 전환됐다

`OWNERSHIP_403_KNOWN_MISSES` 와 그 `xfail(strict=True)` 테스트를 **제거**했다(strict 라
`xpass` 는 실패다 — 표식을 남긴 채 탐지에 넣을 수 없다). 두 형태는 형태 목록으로 옮겨
`blocks=True` 로 고정했다.

| 회귀 | 무엇을 잰다 |
|---|---|
| **N20·N21** | 옛 xfail 2건. `False` 로 되돌리면 진짜 403 을 내는 두 줄이 다시 조용해진다 |
| **N22·N23·N24** | `sendError` 관용구 3형태 — 맨 `sendError` 를 토큰으로 올리지 **않고도** 전건 잡힌다는 증거 |
| **N25** | 확장 뒤에도 ③ 의 전제가 성립하는가 — 선언은 빠지고 사용처가 잡힌다 |
| **P8·P9** | **㉮ 기각의 회귀.** `FORBIDDEN_IN_FILENAME`·`FORBIDDEN_ANNOTATIONS` 는 여전히 BLOCK 이 아니다 — 두 갈래가 뒤섞이면 여기서 빨개진다 |

### 8-7. 남는 것 (닫지 않았다고 적는다)

1. **㉮ 경계 완화는 여전히 기각이다.** `FORBIDDEN_IN_FILENAME` 류 이름은 잡히지 않는다 —
   의도된 미도달이고 P8·P9 가 그것을 회귀로 고정한다.
2. **상태 코드가 계산값인 자리** — `sendError(computed)` 처럼 문면에 403 표지가 없는 형태는
   토큰으로 닿지 않는다. 다만 계산의 출처인 `= 403` 리터럴 선언이 ③ 의 이름 관문에 걸려
   **BLOCK 으로 남는다**(N14~N16). 완전한 해소는 정의-사용 추적(파서)이 필요하고 근거가 아직 없다.
3. **Django 류 `HttpResponseForbidden`** — 이 스택에 없어 토큰에 넣지 않았다. 들어오면 그때 잰다.
4. `tests/test_privacy_scanner.py` `_log_body_verdict` 의 썩은 헬퍼(§5-3)는 이번에도 손대지
   않았다 — 별건으로 남는다.
