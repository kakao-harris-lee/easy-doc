## 3. 리더가 지정한 여섯 대조 — 결과

### ⓐ 1(스캐너) 의 3관점 2:1 — **왜 privacy-gate 는 통과였는가 (기제)**

**결론: 판정이 갈린 것이 아니라 대조 입력이 갈렸다.**

privacy-gate 음성 대조 8종의 **상수 관련 갈래는 C 하나**이고, 그 형태는
**`const val FORBIDDEN = 403` + 사용처**다(③ §2-2 표). **상수의 이름이 `FORBIDDEN` 이다.**
Claude B-1·codex C-1 이 잡은 것은 **상수의 이름이 `403`·`FORBIDDEN` 어느 토큰도 품지 않는 경우**
(`OWNER_MISMATCH`, `ACCESS_DENIED`, `q7x9k2`)이며, **그 형태가 8종 안에 없다.**

| privacy-gate 8종 | 상수 이름 | 결과 |
|---|---|---|
| A `status(403)` · B `status(HttpStatus.FORBIDDEN)` | — | 잡힘 |
| **C `const val FORBIDDEN = 403` + 사용처** | **`FORBIDDEN`** | 잡힘 — **사용처의 `FORBIDDEN` 토큰으로** |
| F `isEqualTo(FORBIDDEN)` · G `@ApiResponse("403")` | — | 잡힘 |
| H 집행형(자체 줄 상수 + 부호 반전) | — | 제외(의도) |
| D `jwtSecret` 리터럴 · E `SIGNUP_PASSWORD` 되돌림 | — | `SECRET-LITERAL` — 다른 규칙 |
| **「토큰 없는 이름의 403 상수」** | — | **8종에 없음** |

**제3의 근거(코드 대조).** `OWNERSHIP_403_INERT` ③ 갈래의 정규식을 직접 읽었다:

```
r"|^\s*(?:(?:private|internal|public|protected|open|companion)\s+)*"
r"(?:const\s+)?(?:va[lr]|let)\s+\w+\s*(?::\s*[\w<>?.\[\]]+\s*)?=\s*403\b"
```

식별자 자리가 **`\w+`** 다 — **이름에 아무 제약이 없다.** 즉 codex C-1 의 문장
*"상수 선언 대안은 이름과 무관하게 모든 `val/var/const ... = 403` 을 불활성으로 소비한다"* 는
**정규식 문면 그대로 참**이다. 그리고 그 제외를 정당화한 KDoc 문장

> ③ 이 특히 무손실이다 — 선언을 빼도 `status(FORBIDDEN)` 같은 사용처는 `FORBIDDEN` 토큰으로 여전히 매치된다.

은 **상수 이름이 `FORBIDDEN` 일 때만 성립하는 성질**을 무조건형으로 적은 것이다. privacy-gate 의 대조 C 는
**정확히 그 KDoc 이 든 예시를 그대로 재현**했으므로 통과가 나오는 것이 당연하다.

**같은 기제가 `HTTP_403_FORBIDDEN`·`SC_FORBIDDEN` 미도달도 설명한다.** 패턴이 `\b403\b`·`\bFORBIDDEN\b`
인데 `HTTP_403_FORBIDDEN` 안의 `403`·`FORBIDDEN` 은 양옆이 `_`(단어 문자)라 **단어 경계가 서지 않는다.**
codex 가 이 둘을 「같은 실제 미탐」으로 묶은 것은 **기제가 실제로 같기 때문**이다(§4-Ⅱ 는 성격 판정의 충돌).

**처방 — 1차 것을 병기한다(2차가 새로 만들지 않는다).**

| 출처 | 처방 |
|---|---|
| **Claude B-1** | ③ 을 **선언된 식별자 자신이 `403`/`FORBIDDEN` 토큰을 품을 때만**으로 조인다(②가 라벨에 이미 요구하는 조건과 같다). ② 는 애너테이션 라벨과 `fun` 위치 백틱으로 한정한다. **그리고 네 형태를 `tests/test_privacy_scanner.py` 형태 목록에 `blocks=True` 로 넣는다** — 지금 표는 `P4 백틱 함수명 → blocks=False` 로 미검출을 회귀로 고정하고 있다 |

**어느 쪽을 고를지는 리더 판단이며, 둘 다 「네 형태가 회귀에 `blocks=True` 로 들어간다」를 요구한다.**

**⚠ privacy-gate 판정 우선권에 대한 이 문서의 처리.** 보안 축 판정이 갈리면 privacy-gate 를 따르는 것이
규약이다. 그러나 여기서 확인된 것은 **판정의 대립이 아니라 근거 집합의 공백**이다. 이 문서는 privacy-gate 의
「통과」를 뒤집지 않고, **그 통과가 커버하지 않는 형태가 실행으로 두 번 재현됐다는 사실**(Claude 2층 재현 ·
codex `scan()` 프로브)을 병기해 **리더에게 재감사 여부의 판단을 올린다.**

### ⓑ 2(401 타이밍) — 2관점 합의, 심각도 갈림

**현상은 3관점이 같은 것을 본다.** 갈리는 것은 심각도와 「누가 만들었는가」다.

| 관점 | 무엇을 말했나 |
|---|---|
| **codex C-2 (high)** | 위조 토큰은 `verify` 에서 즉시 실패해 DB 를 타지 않고, 서명이 유효한 삭제 계정 토큰은 `exists` 의 `SELECT 1` 왕복을 반드시 친다. **반복 측정으로 토큰이 한때 유효했는지 구분하는 타이밍 채널.** `DeletedAccountTokenReachTest` 는 헤더 값·시간을 재지 않는다. 처방: 서명·클레임 실패에도 **더미 DB 조회**로 비용을 맞추고, 교차 측정 타이밍 회귀 + 변동 헤더 제외 전체 헤더 **값** 비교를 추가 |

**privacy-gate 가 제시한 「문제 아님」 쪽 사실 — 그대로 병기한다.**
- 계약 `x-auth.failure_uniformity` 의 시간 문장은 **로그인 경로의 더미 해시**를 가리키며, 인증 경계에 그 요구가 붙은 적은 없다.
- 격차의 정체는 「서명·클레임이 유효해 DB 왕복 1회를 더 돈다」이고, 없애려면 **서명 실패에도 더미 DB 왕복**이 필요하다 — 인증 실패 트래픽에 DB 부하를 얹는 절충(= codex 처방과 **같은 조치**를 비용 쪽에서 본 것).
- 악용에는 **대상 계정의 유효 서명 토큰 보유**가 선행되고, 얻는 정보는 「이 계정이 그 사이 지워졌는가」뿐.
- **X-1 이 만든 채널이 아니다.** 고치기 전에도 삭제 계정 요청은 200(목록 질의)·500(FK 위반)으로 DB 왕복을 돌았고 그 위에 **상태 코드 채널까지** 있었다. **X-1 은 엄격한 개선이다.**

**종합이 더하는 사실 하나(대조 결과).** Claude F-3 의 처방 ⑴(「세 경로를 실제로 재고 결과를 적는다」)은
**privacy-gate 기록 ① 이 이미 수행했다** — 이 회차 이후로는 「재지 않았다」가 아니라 **「재었고 2.18배다」**가
사실이다. 남는 F-3 은 **구현 산출물 §1-3 의 제목·근거 불일치**(다른 게이트의 수치를 「시간 동형 유지」로
표기)이며, 그 문면 결함은 실측이 나왔다고 사라지지 않는다(표 2a).

**리더 판단 요청:** 문턱 **1.5 선례**(로그인 B-1 · 소유권 X-3ⓑ)와 실측 **2.177** 의 정합을 어떻게 볼 것인가.
codex 는 high, privacy-gate 는 기록으로 두고 이 자리를 명시적으로 리더에게 넘겼다.

### ⓒ 3(CountingDataSource) — 코드 대조로 판정

**셋 다 사실이고, 서로 다른 대상을 가리킨다.**

**⑴ codex C-3 의 계수 주장 — 참(코드 확인).** `CountingDataSource.kt:54-56` 은
`STATEMENT_FACTORIES = setOf("prepareStatement","createStatement","prepareCall")` 에 든 메서드 호출만
증가시키고, **반환된 `Statement` 를 다시 감싸지 않는다.** `execute*` 는 계측 대상이 아니다.
KDoc 자신이 그것을 명시한다 — *"실행 횟수가 아니라 **문장 생성 횟수**를 세는 이유는, JDBC 드라이버의
배치·재사용 최적화가 실행 쪽 계측을 흔들기 때문이다."* **codex 의 사실 진술은 정확하고, 이유까지 코드에 적혀 있다.**

**⑵ 그런데 왜 변이는 잡혔는가 — 문장 수가 왕복 수와 갈리지 않는 경로만 쓰이기 때문.**
`JdbcWorkspaceRepository` 는 전 질의를 `JdbcClient.sql(...)` 로 낸다(코드 확인). `JdbcClient` 는
**SQL 문자열 하나당 `PreparedStatement` 하나**를 만든다 — 한 `PreparedStatement` 에 다른 SQL 을 태울 수 없다.
따라서 privacy-gate 가 만든 변이(「`SELECT user_id` 로 읽고 같으면 `UPDATE … WHERE id`」)는
**필연적으로 `prepareStatement` 2회**가 되고, 구조 축이 `없음=1 타인=1 내것=2` 로 잡는다(③ §4-1 FAILED).
**privacy-gate 의 「통과」 판정은 그 변이 형태에 대해 옳다.**

**⑶ codex 가 말한 우회는 어디에 있나 — `JdbcClient` 를 벗어나야 성립한다.**
codex 의 *"Statement 하나로 소유자를 SELECT 하고 Kotlin 에서 비교한 뒤 같은 Statement 로 UPDATE"* 는
JDBC 에서 **가능하다** — 평범한 `createStatement()` 로 얻은 `Statement` 는 `executeQuery(sql1)` 뒤
`executeUpdate(sql2)` 를 받을 수 있고, 생성은 1회로 남는다. 다만 그러려면 **`JdbcClient` 를 버리고 raw JDBC 로
내려가야** 하며, **그 형태를 실제로 만들어 돌린 관점은 없다**(codex 도 §4.4-3 대로 실측 서술이 없다).
**미실증으로 남긴다 — 추측을 사실로 승격하지 않는다.**

**⑷ 실증된 우회는 Claude F-4 다 — 층이 다르다.** Claude 는 소유 판정을 `WorkspaceService.rename` 으로 올려
(`listOwned()` 선행 조회가 **내 자원일 때만** SELECT 를 하나 더 내도록) 일회용 worktree 에서 실제로 돌렸다:
**`JdbcWorkspaceRepositoryTest` 11/11 초록 · `WorkspaceEndpointReachTest` 22/22 초록 — 두 게이트 모두 통과.**
codex 가 「가능한가」로 물은 것과 **같은 종류의 우회가 실행으로 성립**했고, 다만 우회 지점이
「같은 Statement」가 아니라 **「repository 밖 상위 층」**이다.

**⑸ 배선에 관한 표면 충돌 — 지시 대상이 다르다(코드 확인).**
`JdbcWorkspaceRepositoryTest.kt:343-344` 가 `DriverManagerDataSource(database.jdbcUrl, …)` 를 만들고
`:71` 이 `CountingDataSource(dataSource())` 로 감싼다. 그 위에 얹히는 것은 **프로덕션 클래스**
`JdbcWorkspaceRepository` 다.
→ Claude 「대리 구현이 아니다(계측 대상이 프로덕션 클래스)」 **참**.
→ codex 「테스트용 `DriverManagerDataSource` 에 직접 만든 저장소만 감싸므로 프로덕션 Hikari·트랜잭션 경로의
부가 실행을 증명하지 않는다」 **참**.
**둘은 서로를 부정하지 않는다** — 하나는 *계측 대상 클래스*, 다른 하나는 *DataSource·트랜잭션 배선*을 말한다.

**⑹ privacy-gate 4a 가 세 번째 도달 축을 더한다.** 단언은 `RENAME_STATEMENTS = 1` 하나이고
`delete`·`lockForDeletion`·`listOwned` 는 덮지 않는다(오늘 위반은 없음 — 셋 다 소유 조건이 SQL 안에 있음을
코드로 확인). **구조 축의 도달 공백은 두 방향이다 — 계층(F-4)과 오퍼레이션(4a).**

## 4. 충돌 항목 — 양쪽 근거 전문 병기 (리더 판단 요청)

> 어느 쪽도 삭제하지 않았다. 코드 대조는 **제3의 근거로 추가**했을 뿐 판정을 대신하지 않는다.

### Ⅰ. 3 — `CountingDataSource` 의 검출력 (codex high ↔ privacy-gate 통과 ↔ Claude 부분)

**codex C-3 (원문 요지).** *"프록시는 `prepareStatement/createStatement/prepareCall` 호출만 증가시키고
반환한 Statement 의 `execute*` 는 감싸지 않는다. 따라서 Statement 하나로 소유자를 SELECT 하고 Kotlin 에서
비교한 뒤 같은 Statement 로 UPDATE 해도 없음/타인/내것이 모두 1 로 남는다. 현재 기능 테스트와 1.5 타이밍
테스트도 이 형태를 통과할 수 있어, 소유 판정이 SQL 조건에서 애플리케이션으로 빠져도 구조 게이트가 초록이다.
별도 테스트용 DriverManagerDataSource 에 직접 만든 저장소만 감싸므로 프로덕션 Hikari·트랜잭션 경로의 부가
실행도 증명하지 않는다."*

**privacy-gate §4-1 (원문 요지).** 일회용 worktree 에서 `JdbcWorkspaceRepository.rename` 을
「`SELECT user_id` 로 읽고 같으면 `UPDATE … WHERE id`」로 변이 → **구조 축 FAILED**
(`소유 결과에 따라 SQL 문 수가 갈린다 — 없음=1 타인=1 내것=2`), 시간 축 전건 통과.
*"**왕복 1 단언이 소유 조건의 SQL 내장을 강제한다**는 주장이 실행으로 확인됐다. 같은 변이에서 API 계층
테스트가 전부 초록이라는 사실이 이 장치의 필요성을 동시에 증명한다."*

**Claude F-4 (원문 요지).** 소유 판정을 `WorkspaceService.rename` 으로 올린 변이에서
**구조 축 11/11 초록 · 시간 축 22/22 초록 — 두 게이트를 모두 빠져나간다.**
*"「소유 조건이 SQL 을 떠났는가」라는 선언된 주제 자체가 한 층 위에서는 검사되지 않는다."*
차단으로 올리지 않은 근거를 명시: *"이 변이에서도 소유권 응답의 관측 채널(상태·본문·헤더 바이트 동일)은
독립적으로 살아 있고 실제로 초록이었다 … 빠져나간 것은 부수 채널 축 하나 … **형태를 결정적으로 보면
차단이 되므로, 그 판단은 리더에게 명시적으로 올린다.**"*

**이 문서의 제3 근거(§3-ⓒ).** ① 계수 대상이 문장 **생성**임은 코드로 참. ② `JdbcClient` 경유 변이는 구조상
반드시 2문장이 되므로 privacy-gate 의 통과 판정은 그 형태에 대해 옳다. ③ codex 가 든 「같은 Statement 재사용」
우회는 raw JDBC 로 내려가야 성립하며 **아무도 실행하지 않았다(미실증)**. ④ **실행으로 성립한 우회는 Claude 의
서비스 층 변이**다. ⑤ 배선 진술은 양쪽 다 참이며 지시 대상이 다르다.

**리더 판단 요청 두 갈래.**
1. **F-4 를 차단(②장치)으로 올릴 것인가.** Claude 스스로 「형태로 보면 차단」이라 적고 판단을 넘겼다.
2. **codex 처방(생산 DataSource 빈을 감싼 통합 테스트 + `execute*`·SQL 문면 기록)을 채택할 것인가**,
   아니면 Claude 의 얇은 처방(계측을 `service.rename(...)` 으로 올리거나 서비스 층 케이스 한 벌 추가)만
   채택할 것인가. 후자는 오늘 값이 1 이라 **추가해도 초록**이고 Phase 4 에서 값이 갈리는 순간 걸린다.

### Ⅱ. 1a — `HTTP_403_FORBIDDEN`·`SC_FORBIDDEN` xfail 의 **성격** (Claude 「정직」 ↔ codex 「미탐」)

**Claude A-2.** *"`HTTP_403_FORBIDDEN`·`SC_FORBIDDEN` 미도달을 조용한 0 이 아니라 `xfail(strict=True)` 로
**선언**한 것은 이 하네스의 규약대로다 — **정직성 확인.**"* (전건 strict, xpass 0 실측)
다만 `pyproject.toml` 에 `xfail_strict` 가 없어 **다음에 붙는 xfail 은 조용해진다**(→ 표 1b).

**codex C-1 후단.** *"별도 xfail 로 남긴 `HTTP_403_FORBIDDEN` 과 `SC_FORBIDDEN` 도 **같은 실제 미탐**이다 …
현재 strict xfail 을 **정상 통과 테스트로 전환**하라."*

**충돌의 정체.** 두 진술은 **다른 질문에 답하고 있다** — Claude 는 *"미도달을 숨겼는가"*(→ 아니다, 선언했다),
codex 는 *"미도달 자체를 남겨도 되는가"*(→ 안 된다, 잡게 고쳐라). **둘 다 성립할 수 있다.**
**제3 근거:** `\b403\b`·`\bFORBIDDEN\b` 의 단어 경계가 `_` 앞뒤에서 서지 않는다 — 미탐의 기제는 codex 말대로
**1 과 동일 계열**이다. 즉 **1 의 처방을 어떻게 고르든 이 두 상수가 함께 걸리는지를 같은 커밋에서 확인해야 한다.**
**리더 판단 요청:** xfail 유지(정직 선언) / 정상 통과 테스트로 전환(미탐 해소) 중 어느 쪽인가.

### Ⅲ. 1 — privacy-gate 「통과」 ↔ Claude·codex 「차단·high」

§3-ⓐ 에 기제를 전부 적었다. **요지: 판정 대립이 아니라 근거 집합의 공백이며, 이 문서는 privacy-gate 의
판정을 뒤집지 않고 사실만 병기한다.** 보안 축 우선권 규약에 따라 **최종 판정은 privacy-gate 재감사 또는
리더 결정**에 달려 있다.
**리더 판단 요청:** privacy-gate 에 **「토큰을 품지 않은 이름의 403 상수 + 사용처」 한 갈래를 추가한 재감사**를
지시할 것인가. 그 한 줄이 2:1 을 사실로 정리한다.

### Ⅳ. 5 — `errorDetailUnionTypes` 백스톱 (Claude 「있음·권고」 ↔ codex 「fail-open·medium」)

§3-ⓔ 에 코드 대조 결과를 적었다. **요지: 손상 방향에 따라 갈리며, codex 가 명시한 「갈래 추가」 방향은
두 소비자 단언 모두 통과한다.** 심각도 갈림만 남는다 — **리더 판단 요청.**

### ① 표 1(B-1/C-1)이 「소유권 404」 행을 막는가 — **판정에 필요한 사실만**

**사실 1.** 그 행의 불변식(I-5 · §5 Phase 7 즉시 중단 기준 「타 사용자 노출 · 404 위반」)을 **상시로 탐지하는
게이트는 `OWNERSHIP-403` 하나**이고, CI `quality` 잡에서 실제로 돈다(Claude §7 · privacy-gate §2-3 · 둘 다 exit 0 관측).

**사실 2.** 그 게이트가 **이 배치에서 네 형태의 탐지를 잃었다.** Claude 가 술어 층과 **CI 와 동일한 명령**의
두 층에서 재현했고(옛 `exit 1` → 새 `exit 0`), codex 가 별도 `scan()` 프로브로 같은 결론에 닿았다.

**사실 3.** **오늘 저장소에 403 을 내는 프로덕션 코드는 없다**(privacy-gate·Claude 공통 census).
즉 **오늘 유출은 없다.** 잃은 것은 **「없던 것이 생기는 순간」을 잡는 능력**이다.

**사실 4.** **Phase 4 가 소유 자원(문서·변환)을 대량으로 추가한다** — 이 게이트가 실제로 쓰이는 첫 자리다.

**사실 5.** privacy-gate 는 이 항목을 **통과**로 판정했고, 그 근거 집합에 해당 형태가 **없다**(§3-ⓐ).
보안 축의 최종 판정 권한은 privacy-gate 에 있다.

**따라서 리더가 정할 것은 둘이다.**
⒜ **행 4 를 「예」로 움직이기 전에 표 1 을 닫을 것을 요구할 것인가** (Claude 1차 권고: *"B-1 을 닫기 전에는
「소유권 404」 행을 움직이지 않는 것이 맞다"*).

## 7. 대조하지 못한 범위 · 「종합 중 발견 — 미교차」

### 7-1. codex 가 답하지 않아 대조가 성립하지 않은 항목

codex 원문 §4.3 이 열거한 미응답 축은 **그대로 유효**하다. **답이 없는 것은 「문제 없음」이 아니다.**
그중 **다른 관점이 메운 것**과 **여전히 1관점뿐인 것**을 가른다.

| codex 미응답 | 다른 관점이 메웠는가 |
|---|---|
| `exists` 가 이메일을 힙에 안 올리는가 | **메워짐** — privacy-gate §1-2 가 **나간 SQL 문면**으로 확인(`SELECT 1 FROM users WHERE id = ?`), Claude 도 코드로 확인 |
| 캐시 0 / 인증 경계 미도달 엔드포인트 유무 | **메워짐** — Claude §3(4단언) · privacy-gate §1-3(호출 구조) |
| 401 두 갈래 중 맞는 문구인가 | **메워짐** — Claude §2(계약 `invalid_token` 대조) · privacy-gate §1-1 |
| `MAX_TIMING_RATIO` 1.5 로 걸러지는 공격 시나리오 | **미대조** — 어느 관점도 답하지 않았다 |

### 7-2. 어느 관점도 확인하지 않은 것 (미대조)

- `MAX_TIMING_RATIO` **1.5 로 걸러지는 실제 공격 시나리오**의 유무
- 부호 반전 단언의 **둘째 이후 인자·역배치**(`assertThat(FORBIDDEN).isNotEqualTo(x)`) 형태에서의 실측
- codex 가 든 **「같은 Statement 재사용」 우회**의 실제 실행(§3-ⓒ-⑶ — 미실증)
- `max_connections` **중간값(4~6)**
- **A-11 의 「13 vs 14」 실제 케이스** 확정(X-1 이전 상태 복원 필요)
- **240 동시 배압 재현**(R-2 표 값은 인용)
- **프런트엔드 대조** — `frontend/src/api/` 는 이 범위에서 무변경(diff 0)이나 대조하지 않았다
- **parity 도메인·골든셋** — **미검토가 아니라 대상 없음**(도메인 로직·프롬프트·LLM 설정 무접촉)

### 7-3. **종합 중 발견 — 미교차** (다음 회차 범위 제안)

> 아래는 대조 과정에서 눈에 띈 것으로 **교차 검증을 거치지 않았다.** 정본 표에 넣지 않고 여기 분리한다.
> **이번 게이트의 판정 근거로 쓰지 말 것.**

1. **`errorDetailUnionTypes` 의 「갈래 추가」 방향이 두 소비자 단언을 모두 통과한다**는 코드 판정(§3-ⓔ)은
   codex C-5 의 주장을 **확증**한 것이지만, 그 확증 자체(소비자 두 곳의 단언 형태 대조)는
   어느 1차 산출물에도 없다. **다음 회차에서 실행 음성 대조로 확정할 것을 제안한다.**
2. `User.kt` 안에서 **`StoredUser` 는 `toString()` 을 재정의하는데 바로 위 `User` 는 하지 않는다**는
   **같은 파일 안의 비대칭**은 privacy-gate 3a 의 「비대칭이 이동했을 뿐」 진술을 강화하지만,
   **한 파일 안에서 갈린다는 사실**은 어느 산출물도 적지 않았다.
3. codex 지적 5건 중 **단독이 0** 이라는 분포 자체(§2 관점 수 표). 두 회차 연속으로 같은 분포가 나오면
   focus text 가 Claude 관점을 지나치게 좁게 지정하고 있는지 점검할 자리다 — **관측 1회이므로 제안까지만.**

## 8. 이 회차가 하지 않은 것

- **새 지적을 만들지 않았다.** §7-3 은 정본 표 밖에 분리했다.
- **1차 산출물의 심각도를 올리거나 내리지 않았다.** 갈리는 자리는 양쪽 값을 병기했다.
- **어느 쪽 지적도 삭제하지 않았다.** 코드 대조는 제3 근거로만 더했다.
- **코드 수정 0 · 커밋 0 · `00_progress.md` 무접촉**(읽기만) · 다른 리뷰어 산출물 무접촉(읽기만).
- **규칙 5 해당 없음** — 이 회차는 변조·복원을 하지 않았다. 실행한 것은 읽기 전용
  (`sed`·`grep`·`git log`·`git diff --stat`)뿐이며 `cp` 미사용.
- 1차 산출물(`03_workspaces-fixes_migration-reviewer.md`)을 **덮어쓰지 않았다** — 이 문서는 별도 파일이다.
