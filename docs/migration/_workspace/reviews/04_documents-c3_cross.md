두 지적의 기제가 한 문장으로 같다 — `pin` 이 `"$file | $verb [테이블]"` 이라(`OwnershipPredicateGuardTest.kt:336`) **문장 수준의 신원을 담지 않으므로, 같은 파일 안에서 서로 다른 두 문장이 하나의 핀으로 접힌다.** 접히면 한쪽의 방어를 떼고 다른 쪽에 붙이는 편집이 두 목록의 값을 글자 그대로 보존한다.

- **실측(고정 리비전 `16df925`)**: `EXPECTED_STATEMENTS` 의 `:483`·`:484` 두 줄이 `…/auth/JdbcWorkspaceRepository.kt | SELECT [documents]` 로 **완전히 동일**하고, `EXPECTED_UNGUARDED:509` 에 같은 문자열이 한 줄 있다. **핀 충돌은 오늘 실재한다.** 리더 지시 ⑶ 과 codex 확인과 본 회차 실측이 일치한다.
- **두 레인이 서로 다른 경로로 같은 곳에 닿았다.** codex 는 상수 목록에서 중복을 먼저 보고 기제를 역산했고(F-4), Claude 는 핀 문자열의 해상도에서 기제를 먼저 보고 「맞바꿈」 갈래를 구성했다(M-4 전단). **독립 도달이므로 합의의 무게가 크다.**
- **다만 갈래 하나는 서로 다르다.** codex 의 「**형제 Envelope 가드의 분모가 `src/main` 이 아니다**」와 Claude 의 「**`TABLE_REFERENCE` 가 `DELETE…USING`·콤마 조인을 못 본다**」는 같은 뿌리가 아니다 — 각각 #6·#4 로 따로 세웠다.
- **덧붙여 확인한 문면 과대 선언 하나**: 같은 클래스 KDoc 이 *"목록은 순서 있는 **리스트**라 같은 파일에 같은 모양을 하나 더 넣는 편집도 드러난다"* 고 적는데, **추가에는 참이고 맞바꿈에는 거짓**이다. 그리고 이 갈래가 같은 KDoc 의 「막지 못하는 것」 목록에 없다. Claude 1차가 지적한 그대로이며, codex 의 중복 핀 실물이 그 문장의 반례다.

## 2. 충돌 항목 — 어느 쪽도 지우지 않는다

### 2.1 (충돌 아님 — 다른 층임을 밝힌다) codex F-7 ↔ Claude 「지목 1: 검토함 — 지적 없음」

리더가 *"정면으로 갈릴 수 있다"* 로 지목한 자리다. **코드로 가른 결과 충돌이 아니라 서로 다른 층이다.** 그래도 두 문서를 나란히 읽는 사람에게는 같은 축(「검사 순서」)에서 정반대 결론으로 보이므로, 여기 적어 둔다.

- **Claude 가 잰 것**: 계약 `POST /documents` description 이 열거한 **애플리케이션 층 검사 순서**(크기 413 → 추출 422 → 본문 길이 422 → 소유권 404 → 저장 정의역 422 → 트랜잭션). 이 순서는 코드와 **일치한다**(재확인함).
- **codex 가 잰 것**: 그 순서에 들어가기 **전**의 **컨테이너 층 자원 소비 순서** — `resolve-lazily: false` 로 `DispatcherServlet.checkMultipart()` 가 인터셉터보다 앞서 돌아 **비인증 요청도 파일을 스풀한다**.
- **두 진술은 동시에 참이다.** 겹치는 대상이 없다.
- **제3 근거(본 회차 실측)**: 계약 `info.description:89-97` 의 「인증이 먼저다」를 재는 케이스는 **DC-20·DC-21 둘뿐이고 둘 다 JSON 팔**이다. **multipart 팔에서 인증 선후를 재는 케이스는 0건이다.** 즉 codex 가 지적한 자리는 「틀렸다」가 아니라 **「아무도 재지 않는다」**이다 — 이 저장소 척도로는 도달 0 이다.
- **반대 방향 근거도 병기한다**: `application.yml:57-60` 의 주석은 `resolve-lazily` 를 켜지 않은 이유를 **적어 두었다** — 켜면 상한 초과 예외가 핸들러 안에서 나 *"어느 갈래가 먼저인지가 구현에 좌우된다"*. 즉 이것은 **의도된 트레이드오프**이고, codex 는 그 선택의 반대편 비용을 든 것이다. **어느 쪽이 옳은지 이 문서는 정하지 않는다.**

### 2.2 **충돌** — codex F-8 ↔ Claude §5.1 「검사 순서: 검토함 — 지적 없음」

**같은 대상(계약이 명시한 검사 순서)에 대해 두 레인이 반대 결론을 냈다.** 어느 쪽도 지우지 않는다.

**Claude 1차 원문 (§5.1 첫 항목):**

> **검사 순서 (리더 지목 1)** — **검토함, 지적 없음.** 계약 `POST /documents` description 은 *"파일 크기(413) → 추출(422) → 본문 길이(422) → 작업 공간 소유권(404) → **저장 정의역(422)** → **저장과 큐 등록(한 트랜잭션)** → 커밋"*. 코드는 `DocumentController.readBounded` → `DocumentService.createFromFile`(…) → `store`(…). **문면과 같다.** 저장 정의역이 트랜잭션 **안**이고 소유권 **뒤**라는 계약의 명시 조항까지 일치한다.

**codex F-8 원문 (`high`):**

> **잘못된 workspace_id가 선행해야 할 파일 오류를 422로 덮는다** (`DocumentController.kt:115-121`)
> Kotlin 인수 평가 순서상 `readBounded(file)` 다음 `parseWorkspaceId(...)`가 실행된 뒤에야 `DocumentService.createFromFile`로 진입한다. 그러므로 10 MiB+1 파일과 잘못된 UUID를 함께 보내면 서비스의 크기 검사에 도달하지 못하고 413 대신 422가 반환된다. 손상된 파일이나 추출 본문 초과도 같은 방식으로 workspace 형식 오류에 가려져, 계약의 크기→추출→본문 길이→소유권 순서를 위반하고 오류 detail·타이밍을 잘못된 분기로 노출한다.

**제3 근거 (고정 리비전 `16df925` 에서 확인 — 승자를 정하지 않는다):**

1. **호출 지점 인자 순서는 codex 가 인용한 그대로다.** `DocumentController.kt:115-121` 이 `bytes = readBounded(file)` · `title = request.getParameter(TITLE_PART)` · `workspaceId = parseWorkspaceId(request.getParameter(WORKSPACE_ID_PART))` 순으로 적혀 있고, Kotlin 은 명명 인자를 **호출 지점에 적힌 순서**로 평가한다. `parseWorkspaceId` 는 형식 오류에 `InvalidInputException` 을 **그 자리에서 던진다**(`:145-149`).
2. **크기 판정은 서비스 안이다.** `readBounded` 는 상한+1 바이트를 읽을 뿐 던지지 않는다 — 그 KDoc 이 *"경계 판정 자체는 여기서 하지 않는다 … `DocumentService` 가 진다"* 로 적는다. 그러므로 **두 결함이 함께 오면 422 가 413 을 앞선다.**
3. **두 진술이 갈리는 이유는 「단일 결함이냐 복합 결함이냐」다.** Claude 는 **결함 하나짜리 경로**의 순서를 확인했고 그 범위에서 참이다. codex 는 **결함 둘이 겹친 입력**을 구성했고 그 범위에서 참이다. **계약 문면은 어느 쪽 범위인지 말하지 않는다** — *"검사 순서: 파일 크기(413) → …"* 만 있고 「복합 결함의 우선순위」 조항이 없다.
4. **JSON 팔에서는 관측되는 상태 코드가 갈리지 않는다.** 그쪽은 `workspace_id` 형식 오류도 본문 길이 초과도 둘 다 422 라 순서가 바깥에서 보이지 않는다. **갈리는 것은 multipart 팔의 413 대 422 하나다.**
5. **이 우선순위를 고정한 테스트는 0건이다**(복합 입력 케이스를 찾지 못했다).

**리더 판단 요청** — ⑴ 계약의 검사 순서 조항이 **복합 결함에도 적용되는가**(적용된다면 구현 결함, 적용되지 않는다면 계약이 그 자리를 말하지 않는다는 것 자체가 계약 공백이다), ⑵ 그 판정 결과를 **계약 문면에 적을 것인가 구현을 옮길 것인가**.

### 2.3 **부분 충돌** — codex F-9 ↔ Claude 「지목 7: O-21·O-22 로 이월돼 있다」

**같은 대상(=`ServiceUnavailable` 의 DB 조항)에 두 레인이 다른 결론을 냈다.** 겹치지 않는 부분이 있어 「부분」이다.

**Claude 1차의 답 (지목 7 · §8 미실행 항목):** 원장 `L-⑦` 의 *"O-21 의 DB 줄 미측정 — 재지 않았으므로 지우지 않았다"* 를 읽고, **미측정 항목이 정직하게 이월됐다**고 판정했다. Claude 는 **원장만 보았고 계약 파일의 해당 블록 문면을 대조하지 않았다.**

**codex F-9 원문 (`high`):** *"활성 설명에는 JWT 설정 실패만 남아 있고, 폐기 목록의 DB 세션 팩토리 문장은 취소선으로 제거된 동시에 「내리지 않았다」라고 적혀 있다. … 따라서 DB 장애가 503인지, 기동 실패인지, 기본 500인지 **정본 자체로 결정할 수 없으며** 후속 구현·게이트가 서로 다른 전제로 통과할 수 있다."*

**제3 근거 (본 회차 실측 — 계약 파일을 직접 읽었다):**

| 자리 | 문면 | 함의 |

**정리**: Claude 의 답은 **원장 축에서 참**이다(원장은 미측정을 정직하게 적었다). codex 의 지적은 **계약 파일 축에서 참**이다(같은 문서가 한 조항에 대해 세 가지 결론을 동시에 담는다). **두 진술 모두 참이고, 두 레인이 서로 다른 파일을 보았다.** 종합하면 **「이월은 정직했으나, 이월한 사실을 계약 정본에 적는 과정에서 문면이 갈렸다」**가 된다 — 그러나 이 종합조차 **판정이 아니라 해석**이므로 리더에게 넘긴다.

**리더 판단 요청** — DB 조항의 처분(측정 후 복구 / 명시적 폐기 / 현상 유지)과, 그와 무관하게 **머리글 수(「세 줄」)·취소선·활성 목록·`x-changelog`·원장 다섯 자리를 하나의 결론으로 맞추는 일**의 마감.
