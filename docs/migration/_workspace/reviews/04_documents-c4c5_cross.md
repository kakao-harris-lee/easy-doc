## 4. 충돌 — 양쪽 근거 전문 병기 · **리더·사용자 판단 필요**

어느 쪽도 삭제하지 않았다. 표의 한 칸에 요약해 넣으면 근거가 잘려 판단이 불가능해지므로 여기 전문을 둔다.

### X1 — `GET /documents` 의 소유권 은닉이 몇 축으로 증명됐는가

**codex (C1-2, high)** — 원문:
> GET 목록의 소유권 은닉은 헤더·시간 축을 전혀 측정하지 않는다 (`DocumentListReachTest.kt:190-200`)

> C3의 네 축 중 둘이 비어 있고, 문자열 비교도 원시 바이트 동일성 증명이 아니다. (…) 악용 비용은 하네스 편집 0이다.

**`GET`(DL-9)** 이다. 즉 두 진술이 서로 다른 엔드포인트를 말하고 있을 가능성이 있다 — 그렇다면 이것은

판정 결과로는 정면으로 갈린다. **어느 해석이 맞는지 판정하지 않는다.** 리더가 갈라야 할 물음:
「C3(소유권 은닉)의 축 요구가 `GET` 목록에도 같은 수로 적용되는가, 아니면 목록 응답은 다른 축 집합인가」 —
이것은 계약·`migration-safety-gate` 쪽 규정 물음이므로 `contract-keeper`·`privacy-gate` 판정 대상이다.

> 그러면 기준이 판별력을 잃는다. **처방: 기준 문장을 「악용 비용 × 자동 탐지 여부」로 다시 적어라.**

그리고 Claude §11 은 codex 가 차단으로 올리라는 항목들을 개별로 이렇게 처분했다:
> **L-㉖ ②** 소유 술어 4갈래 → **옳다.** 두 인자 기준(비용 × 탐지)에서 「탐지: diff 가시」가 성립한다.
> **L-㉖ ③** `LiveSql` 조립 SQL → **옳다.** **L-㉖ ④** 축 A 멤버 참조 → **옳다**(오탐 22% 근거).
> **B-19** pitest → **옳다.** **B-22** → **옳다.** **B-21** → **재검토 요청**(Cβ-10 이 값싼 처방을 제시).

**쟁점의 정확한 형태**: codex 는 **한 인자**(한 줄이면 차단)로 잔여 다수를 차단으로 올리고, Claude 는
**바로 그 한 인자 읽기가 판별력을 잃는다**고 지적하며 두 번째 인자(자동 탐지 / diff 가시성)로 다수를
백로그에 유지했다. 즉 Claude 는 codex 의 논법을 **예측하고 반박한 형태**이고, codex 는 Claude 를 읽지
않은 상태에서 그 논법을 실제로 실행했다. **양쪽 다 삭제하지 않는다.** 리더가 결정해야 하는 것은
**잔여 처분 기준의 문면 자체**다 — 한 인자인가 두 인자인가(그리고 Claude 가 지목한 암묵의 세 번째 인자
「닫는 비용」을 적을 것인가). 이 결정이 β-08·β-19·β-20·β-23 의 심각도를 한꺼번에 정한다.

### X7 — 장치 분류의 전수 판정

### 5.2 심판 대상이 도중에 움직였다 (리더 책임)

리더가 선언한 범위는 `81ba9fa..19062cc` 였으나, `94440d8`(`fix(harness): ruff format 을 통과시킨다`)이
**codex 호출 2 가 도는 중**(2026-08-21 16:11:57, 호출 2 구간 16:07:47~16:23:14)에 브랜치에 올라왔다.
확인: `git show --stat 94440d8` → `tests/test_kotlin_gate_reach.py` **한 파일 +9/−3**.

| 산출물 | 실제로 본 범위 | 그 회차의 지적 |
|---|---|---|
| Claude 1차 | `81ba9fa..19062cc` — **선언과 일치** | Cβ-1 ~ Cβ-16 전부 |
| codex 호출 1 | `81ba9fa..19062cc` — **선언과 일치** | C1-1 ~ C1-8 (β-07·β-19·β-03·β-20·β-02·β-21·X1·X4) |
| codex 호출 2 | `81ba9fa..94440d8` — **선언보다 1커밋 넓다** | C2-1 ~ C2-8 (X6·β-04·β-19·X3·β-22·β-05·β-06·β-01·β-23·β-25·β-26·β-27) |

**「그 범위를 정확히 심판했다」는 주장은 이번에 성립하지 않는다.** 구체적 귀결 셋:

1. **C2-7 은 `94440d8` 의 존재를 근거로 인용한다** — 원문: 「실제로 제공된 19062cc 뒤 HEAD 94440d8이
   `ruff format` 실패 수정으로 추가됐다」. 즉 그 지적의 증거 하나가 **선언 범위 밖의 사건**이다.
   같은 결함을 Claude 는 **범위 안**에서(19062cc 의 CI 런 실측) 잡았다 — 그래서 β-01 은 두 범위에서
   독립적으로 확인된 것이 되고, **이 이동은 β-01 의 근거를 약화시키지 않는다.**
2. **줄 번호가 서로 다른 파일 버전을 가리킨다.** `94440d8` 이 바꾼 파일이 정확히
   `tests/test_kotlin_gate_reach.py` 이고, 호출 1 은 그 파일을 `446-475`·`125-127`·`1123-1130`(19062cc),
   호출 2 는 `1129-1177`·`721-742`·`906-907`·`922-923`·`540-548`·`816-917`·`995-998`(94440d8)로 인용한다.
   **그 파일의 지적을 실제로 확인·수정할 레인은 어느 HEAD 의 줄 번호인지 먼저 갈라야 한다.**
   같은 자리를 두 회차가 다른 번호로 부른 경우(β-19: `1123-1130` 대 `1129-1177`)가 실제로 있다.
3. **이 이동을 좁혀 다시 돌리지 않았다.** codex 레인이 그 사유를 적었다 — 「`--base 81ba9fa` 는 항상
   현재 HEAD 를 보므로 지정 범위로 되돌리려면 `19062cc` 를 detach 해 돌려야 하고, 그것은 이 에이전트가
   작업 트리를 움직이는 일이다(내 역할 밖)」. 그 판단에 동의·반대를 표하지 않고 사실로 남긴다.
   **처방의 소유자는 리더다** — 심판 중 브랜치에 커밋하지 않는 것, 또는 심판 대상을 detached SHA 로
   고정해 주는 것.

## 6. 이미 닫힌 것 하나 — 중복 조치를 만들지 않는다

**β-01 의 인스턴스 = Cβ-1(CI `quality` 잡 사망 → 게이트 체인 skip)은 리더가 `94440d8` 로 닫았다.**

- 리더가 커밋 메시지에 적은 사실 하나를 여기 옮긴다 — **리더 검증 집합이 CI `quality` 잡의 부분집합이었다.**
  빠진 것: `ruff format --check` · `dump_python_snapshots.py --check` · 개별 경로 pytest 8종.
  그 뒤 CI 와 같은 13종을 돌려 전건 초록.
- **codex 쪽 같은 자리 지적(C2-7)도 합쳐 「인스턴스 닫힘」으로 처리한다.**

**단, 그 결함이 재발하지 않게 하는 장치는 열려 있다.** 이것은 codex C2-7 과 Claude §7⑷ 이 **각각
독립적으로** 지목한 것이고 양쪽 처방이 상보다:

| 레인 | 처방 (원문) |
|---|---|
| Claude | 「처방은 사람의 주의가 아니라 **라벨**이다 — 「ruff 0」을 「`ruff check` 0 · `ruff format --check` 0」으로 쪼개 적으면 빠진 절반이 문면에 보인다」 + 「전건 초록 템플릿에 `ruff format --check` 를 **명령 단위**로 넣는다」 |
| codex | 「출하 근거를 **정확한 HEAD SHA 의 필수 CI check suite** 로 제한하고, 로컬 러너는 시작·종료 SHA 가 같고 프로젝트 설정을 사용했음을 기록하도록 한다」 + 「정확한 HEAD SHA 에서 전체 CI 가 완료되기 전에는 '전건 초록'을 수락하지 않는다」 |

두 처방은 **다른 층**을 막는다(보고 라벨 / 증거의 SHA 결속). 어느 하나만으로는 다른 쪽이 열린다.
**둘 다 β-01 의 「장치」 항목으로 남긴다.** 또한 codex 가 부수로 적은 사실 — 「로컬 명령은
`ruff check --fix . && ruff format .`, CI 는 `ruff check .` 와 `ruff format --check .`; `--isolated`
한 플래그면 pyproject 의 E501 선택과 100자 폭을 읽지 않아 해당 오류가 사라진다」 — 는 Claude §7⑷ 이
L-㉕ 에서 인용한 것과 같은 사실이며 **양쪽이 독립적으로 같은 자리를 짚었다**.

## 9. 대조하지 못한 범위 · 「종합 중 발견 — 미교차」

### 9.1 codex 리뷰 부재·실패로 대조하지 못한 범위

**해당 없음** — 이 회차는 codex 독립 리뷰를 실제로 받았고(2회, 둘 다 exit 0, 잘림 없음, 재시도 0),
**「codex 리뷰 없음 — 교차 대조 미수행」은 이 파일에 적용되지 않는다.**

### 9.2 두 산출물 중 한쪽만 다룬 축 (대조 불가)

| 축·항목 | 상태 |
|---|---|
| AEAD round-trip·변조 거부·키 회전·Argon2·JWT clock skew | **양쪽 미검토** — Claude 는 「이 배치가 그 경로를 건드리지 않았다 → 범위 밖」으로 명시. codex 프롬프트에도 없었다. `privacy-gate` 의 새 감사 산출물도 이 회차에 없다 |
| parity 리포트·도메인별 mismatch·coverage | **양쪽 미검토** — 이 배치에 parity 도메인 변경 0 (Claude 실측) |
| CORS 노출 헤더·`Location`·RFC 5987 `Content-Disposition` | **Claude 미검토(범위 밖 — 변경 0)** · codex 무언급 |
| 정규식·유니코드·한글·POI·프롬프트 문자열 | **Claude: 변경 0 실측**(`core` diff 0, `parity/` diff 0) · codex 무언급 |
| `./gradlew build --rerun-tasks` 실제 실행 관측 | **양쪽 미실행** — Claude 는 「이 회차 미실행, 근거는 CI `kotlin` 잡 success 하나」, codex 는 「읽기 전용 환경이라 Gradle 을 재실행하지 않고 HEAD 직후 생성된 XML 을 점검했다」. **β-02 의 종단 재현이 양쪽 다 없다** |
| Cβ-2·Cβ-3·Cβ-5 의 종단 재현 | Claude 미실행(코드 수정 금지) — 실측/추정 경계는 각 항목에 표시됨 |

### 9.3 입력 산출물의 구조적 흠 (대조 불가로 이어진 것)

**1차 Claude 산출물의 `Cβ-8`·`Cβ-15` 는 판정 요약표(§1)와 교차 참조(§8·§9·§11)에만 있고 본문 구획이
없다.** 실측: `grep -n "^### Cβ-"` 결과에 두 ID 가 나타나지 않는다. 그래서 근거 파일·라인·처방을
codex 쪽과 대조할 수 없었다.

- `Cβ-8`(β-05)은 codex C2-5 가 **같은 대상**을 파일·줄로 짚었으므로 주제 수준에서 합의로 처리했다.
  **근거는 codex 쪽 것만 실린다.**
- `Cβ-15`(β-17)는 codex 대응이 없어 「Claude 단독 · 근거 본문 없음」으로 남는다.

### 9.4 「종합 중 발견 — 미교차」 → 다음 게이트로 올릴 별건

**본문 판정에 섞지 않았다.** 아래는 두 산출물의 **대조에서만** 드러난 것이고, 그 자체는 교차 검증을
받지 않았다. 다음 리뷰 회차의 범위로 리더에게 제안한다.

1. **처방끼리 충돌한다 — β-18 ⓐ 대 β-19.** Claude 의 Cβ-16 처분안 ⓐ 는 `llm-lane` 을 **명시적으로
   비차단으로 표시**하는 것이고, 그 관용적 구현은 `continue-on-error` 다. codex C2-3 은 CI 배선 검사가
   **`continue-on-error`·`|| true`·`if: false` 를 거부**해야 한다고 처방한다. 두 잡이 달라(llm-lane 대
   kotlin 게이트 스텝) 즉시 모순은 아니지만, **「비차단 표시」와 「종료 코드 은폐 금지」의 경계를 먼저
   정해야** 어느 처방도 다른 쪽을 깨지 않는다. 대상 레인: 하네스 + 리더.
2. **X3 을 가르는 최소 확인 하나.** codex 는 `tests/test_kotlin_gate_reach.py` **906-907 과 922-923 이
   서로 반대 주장을 적었다**고 지적했고, Claude 는 그 자리를 대조하지 않았다. **이 종합은 그 파일을 열어
   확인하지 않았다**(새 지적 금지). 「922-923 의 주장이 참인가」 한 번의 확인으로 X3 이 갈린다.
3. **β-19 의 두 회차 줄 번호가 다르다**(`1123-1130` 대 `1129-1177`) — §5.2 ②의 귀결. 수정 레인이
   어느 HEAD 를 보는지 먼저 정해야 한다.
4. **독립 관측의 수를 세는 방식.** §5.1 에서 「셋 중 둘」이 독립 관측 셋이 아니라는 문제가 실물로 나왔다.
   교차 대조표에 **관측의 독립성 등급**(다른 모델 / 같은 모델 다른 회차 / 같은 레인 산출물 재인용)을
   적을 자리가 지금 없다. 하네스(`codex-review` 스킬 §5 · 이 에이전트 정의) 개선 후보.

## 11. 이 게이트가 닫히려면 무엇이 남았는가

### 11.1 차단 — 이것이 열려 있으면 G-β 를 닫을 수 없다

1. **β-19 · β-20 · β-23 (codex 단독, 전부 「한 줄 또는 편집 0 · 자동 탐지 없음」).**
   세 항목이 겨누는 것은 **G-β 종료 판정의 근거로 인용될 게이트 자신**이다 — CI 배선 검사, 실행 개수
   하한, 리포트·이력 분모. 규칙대로 **Kotlin 코드가 멀쩡해도 ② 장치는 차단**이다. 다만 이 세 항목의
   4단계 환산은 **이 종합에서 처음 붙인 값(★)이라 교차 검증을 받지 않았다** — 리더가 X6 을 먼저 결정하면
   세 항목의 심각도가 자동으로 정해진다.
2. **β-02 (합의, 심각도 갈림).** 「게이트가 실제로 돌았다」가 **캐시 복원과 구별되지 않는다**.
   양쪽 다 종단 재현을 하지 못했고(§9.2), Claude 는 차단 상향 후보로, codex 는 medium 으로 봤다.
   **판정 필요**이지만, 이 항목이 열린 채로는 β-19·β-20 을 고쳐도 「고친 게이트가 이번에 돌았다」를
   증명할 수 없다 — **처리 순서상 먼저다.**
3. **β-01 의 장치 절반.** 인스턴스는 `94440d8` 로 닫혔으나 **재발 방지 장치는 0** 이고, 이 세션에서
   같은 형태가 **세 번째**다(L-㉕ #4 · Claude Cβ-1 · codex C2-7). 두 처방(라벨 분해 + SHA 결속)이
   서로 다른 층을 막으므로 **하나만으로는 닫히지 않는다.**
4. **X1 · X2 · X3 의 판정.** 세 충돌이 모두 「이 배치가 만든 강제자가 무엇을 증명하는가」에 걸려 있고,
   그 답 없이는 §8 의 C4·Contract·Security 칸을 채울 수 없다. **X3 은 확인 한 번으로 갈린다**(§9.4 ②).
5. **X6 (잔여 처분 기준의 문면).** 다른 판정들의 **선행 조건**이다. 이것을 정하지 않으면 β-08·β-19·
   β-20·β-23 의 심각도가 리뷰마다 흔들리고, 같은 논쟁이 다음 게이트에서 그대로 재발한다.

### 11.3 이 게이트에서 **양쪽이 함께 통과로 본 것** (다음 회차가 재검토하지 않도록)

두 리뷰가 **각각 독립적으로** 문제를 찾지 못한 자리다. 「검토함 — 지적 없음」이며 「미검토」가 아니다.

- **평문 로그·개인정보 유출(C7)** — codex 호출 1 이 「C7 평문·로그 유출은 찾지 못했다」고 명시,
  Claude 는 `toString()` 재정의·`handleTypeMismatch` 의 제출값 미포함·`HealthDiagnosis` 의 예외
  비로깅·스캐너 exit 0 을 실측으로 확인.
- **마스킹 선행** — 이 배치에 LLM 경로 변경 0. 양쪽 이견 없음.
- **즉시 파기가 표시(soft delete)가 아니라 파기인가** — codex 가 「현재 구현은 **실제 DELETE 와 FK
  CASCADE 를 사용한다**」고 긍정 관찰, Claude 가 스키마 FK 전수 + 전/후 쌍 + 문장 수 1 로 확인.
  **제품 파기 결함은 양쪽 다 없다고 본다**(X4 는 강제자의 증명 범위 다툼일 뿐).
- **`GET` 페이지 경계** — codex 호출 1 이 「GET 페이지 경계 불일치는 찾지 못했다」고 명시,
  Claude 가 `x-input-limits` ↔ 인라인 `parameters` ↔ 코드 상수 삼중 대조를 확인.
- **`{"detail": …}` 오류 형식 / `ProblemDetail` 누출 / snake_case / 소유권 404(403 아님) / 사적 헤더 2종의
  부착** — Claude 실측, codex 무지적.
- **모듈 경계 · 트랜잭션 경계 · Flyway · LLM SDK 누출** — Claude 실측 충족, codex 무지적.

## 12. 리더에게

- **정본은 이 파일이다.** 1차 산출물 둘은 근거로 남기고 덮지 않았다.
- **양쪽 다 「이 상태로 종료」에 반대한다** — codex 두 회차 `needs-attention`/「NO-SHIP」, Claude 차단 1 +
  판정 필요 3 + 수정 필요 5.
- **먼저 결정해야 하는 것은 X6 하나다.** 잔여 처분 기준의 문면이 정해지면 차단 4건 중 3건의 심각도가
  같이 정해지고, 다음 게이트에서 같은 논쟁이 반복되지 않는다.
- **가장 값나가는 산출은 「합의」가 아니라 「차이」다.** 이 회차의 차이는 한쪽으로 몰리지 않았다 —
  codex 단독 9건(하네스 신뢰 뿌리에 집중), Claude 단독 9건(보안 불변식 강제자·계약 공백·CI 신호 정합에
  집중), 충돌 7건. **두 레인의 맹점이 서로 달랐다는 것이 이번 교차 대조의 실증이다.**
- **판정하지 않은 것 셋**: codex 내부 분열(§5.1)의 승자, 독립성 한계(§5.3)가 어느 지적의 무게를 바꾸는가,
  충돌 7건(§4)의 승자. 전부 리더·사용자 몫이다.
