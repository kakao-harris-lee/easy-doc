  `components/responses/InternalError` 의 **example** 이고, 같은 노드의 규범 서술은
  *"`StorageError`(코드 버그) → **저장소가 만든 고정 문자열**"* 이다. OpenAPI `examples` 의
  규범력이 `description` 보다 약하다고 읽으면 「이탈」이 아니라 **「예시가 낡았다」**가 된다.
- **어느 쪽이든 남는 사실 둘**: ⑴ **계약 예시가 코드가 만들지 않는 문자열을 보여 준다**,

  무관하게 잔여다.
- **이 종합은 심각도를 정하지 않는다** — codex 의 `medium` 을 낮추지도 올리지도 않고 **판정 필요**로
  올린다(척도 적용이 갈리는 항목은 낮게 잡지 않는다).

### 4.4 ⑤-b 재현 실패 — 부분 합의 (항목 14)

## 9. 대조하지 못한 범위 · 「종합 중 발견 — 미교차」

### 9.1 codex 리뷰 부재·실패로 대조하지 못한 범위 — **해당 없음**

codex 산출물은 존재하고(236줄 · exit 0 · verdict `needs-attention`) **원문 그대로** 대조했다.
**「codex 리뷰 없음 — 교차 대조 미수행」은 이 회차에 해당하지 않는다.** 다만 두 단서를 적는다:

1. **codex 파일은 래퍼가 아니라 리더가 썼다.** `codex-reviewer` 래퍼가 호출은 성공시켰으나 산출물을
   쓰기 전에 「폴링하고 종료」를 14회차 반복(누적 ~1.8M 서브에이전트 토큰 · 산출물 0건)하고 수거
   책임을 반납했다. 리더가 바이트 그대로 옮겼고 판정·순위·병합·재서술은 하지 않았다고 명시했다.
   **원문성은 그 진술에 의존하며 이 종합이 독립 검증하지 못했다.**
2. **codex 는 Gradle 층을 실행하지 않았다.** 명령 로그에 `find … build/test-results/…`(기존 XML
   판독)와 `pytest tests/test_kotlin_gate_reach.py` 는 있으나 `./gradlew` 실행은 없다. 즉 codex 의
   계약 축 판정은 **기존 XML + 소스 판독**이다.

### 9.2 이 종합이 대조하지 못한 축

- **parity 위험 축 · Kotlin/Spring 관용성 축** — 리더가 축을 셋으로 지정했으므로 1차가 미검토이고,
  codex focus 도 같은 셋이었다. **양쪽 모두 미검토**이므로 이 종합도 판정하지 않는다. 구체적으로:
  `MaskedItemCodec` 저장 형식의 요구사항 충족 · 모듈 경계 · 트랜잭션 경계 · detekt 처분의 적정성.
- **음성 대조(변이)** — 1차 0건(코드 수정 금지 · 공유 트리 · 미커밋 5건). **예외 하나: K-1 은 리더가
  실측했다**(§5). 나머지 차단 다섯(G-1·G-2·S-1·S-2·S-5)은 **소스 읽기와 grep 근거이며 「고치기 전
  초록」의 실행 관측이 없다.** 각 항목의 기제는 1차 본문에 적혀 있어 리더가 하나씩 실행으로 가를 수 있다.
- **Gradle 전체 빌드 재실행** — 양쪽 다 안 했다. CR 표의 「전건 통과」는 커밋 메시지의 JUnit XML
  진술 근거다.
- **R-7**(`api` 테스트가 `infrastructure` main 을 본다) — 1차가 축 밖으로 두었고 codex 도 지적하지
  않았다. **미판정으로 남는다.**

### 9.3 종합 중 발견 — **미교차** (본문 판정에 섞지 않았다)

아래 셋은 **두 산출물 어느 쪽에도 없는 관찰**이므로 판정에서 분리한다. **다음 리뷰 회차의 범위로
리더에게 제안하며, 이 게이트의 판정 근거로 쓰지 않는다.**

1. **⟨미교차⟩ 계약 `:2123` 의 storage 문자열이 어느 코드도 만들지 않는 문자열일 가능성.**
   실측: `grep -n "저장된 문서를 읽을 수 없습니다\|저장된 변환 결과를 읽을 수 없습니다"
   contracts/easy-doc-v1.yaml` → **적중 1건(`:2123`)** 이고 그것은 `저장된 변환 결과…` 다. 코드 쪽
   상수는 `저장된 문서를…` 하나뿐(`DomainExceptions.kt:46`). 즉 **계약 예시의 문자열을 만드는 코드가
   저장소에 없을 가능성**이 있다. codex 는 「런타임이 계약과 다르다」까지만 적었고 「계약 예시가
   고아일 수 있다」는 적지 않았다. **양쪽 다 이 방향은 보지 않았다.**
2. **⟨미교차⟩ codex 지적 3건 중 다른 레인 15커밋에 귀속되는 것이 0건이라는 사실**(§1.2). 이것은
   두 산출물의 지적이 아니라 이 종합이 레인 분리를 수행해 얻은 결과다. **범위 결함의 피해 평가에만
   쓰고 심각도를 붙이지 않았다.**
3. **⟨미교차⟩ `MAX_TIMING_RATIO` 검사 본체의 도입 커밋이 기준선보다 앞이라는 사실**
   (실측 `git log -S 'MAX_TIMING_RATIO' … → 951b1fd`). codex 는 이 검사를 이 범위의 것으로 다뤘고
   (프롬프트가 *"새로 추가된 … 상한 래칫"* 과 묶어 물었다), Claude 는 사본 위치만 적고 도입 시점을
   적지 않았다. **심판 범위 판정에 쓰이는 사실**이므로 §4.2 에서 층 분리 근거로만 썼다.
