1. **이 파일은 태어난 순간부터 diff 로 읽힌 적이 없다.** 게이트 25 와 게이트 26, **연속 두 게이트 · 여섯 번의 레인 통과**에서 `git diff` 는 이 파일에 대해 `Bin …` 한 줄만 냈다.

### 2.2 codex B-1 재현 — `testsuite@name` 오식별

codex 가 *"실제 리포트로 요구 모드를 실행하자 `PromptInjectionGuardTest` 미실행 판정으로 실패했다"* 고 적은 자리다. 1차 §2.5 T-1 의 음성 대조(가드 전건 `@Disabled` → 초록)와 **결과가 갈리는 것처럼 보였으므로** 직접 돌렸다.

**→ codex B-1 은 사실이고, codex 가 준 처방(`testcase@classname` 집계)이 이 결함을 실제로 닫는다.** 두 값을 모두 실행으로 확인했다.

**codex 가 든 두 번째 축(리포트 덮어쓰기)도 `ci.yml` 배선으로 확인했다** — `kotlin` 잡의 스텝 순서는 ⑴ `./gradlew build` → ⑵ `:core:test --tests …ProvenanceCreationSitesTest` → ⑶ `:core:test --tests …MaskedTextGatewayTest` → ⑷ `KOTLIN_GATE_REACH_REQUIRE_REPORT=1 pytest`. **순서는 codex 가 적은 그대로다.** 다만 「필터 실행이 `core` 리포트 디렉터리를 덮어쓴다」는 **codex 의 추론이고 이 회차가 실행으로 확인하지 않았다** — 사실과 추론을 갈라 적는다.

**1차 T-1 과 codex B-1 은 상충이 아니다.** 같은 함수(`tests/test_kotlin_gate_reach.py:243-251`)의 **서로 다른 두 결함**이다 — T-1 은 *계수*(`tests` 가 skipped 를 포함해 꺼진 가드를 실행으로 셈), B-1 은 *식별*(`testsuite@name` 을 FQCN 으로 취급). 방향도 반대다: T-1 은 **거짓 초록**, B-1 은 **거짓 빨강**. 합치면 **이 장치의 판정은 지금 어느 방향으로도 신뢰할 수 없다.**

### 2.3 codex A-1 근거 확인 — 면제 스위치의 도달

```kotlin
// CryptoConfiguration.kt (관측)
if (properties.verifyOnStartup) { verify(properties, cipher) }
else { logger.warn("저장 암호화 기동 자기점검을 건너뛴다. 테스트 실행이 아니면 설정 오류다.") }
```

`verifyOnStartup` 은 `@ConfigurationProperties` 의 **평범한 필드**다 — Spring 의 모든 프로퍼티 소스(JVM `-D`, 명령행 인자, 환경변수, `SPRING_APPLICATION_JSON`, 외부 config)에서 바인딩된다. **codex A-1 의 전제는 사실이다.**

함께 둔 탐지기의 실제 도달을 실측했다.

| 축 | 값 |
|---|---|
| 탐지 토큰 (`SWITCH_TOKENS`, `CryptoStartupVerificationTest.kt:249`) | `verify-on-startup` · `verifyOnStartup` · **`VERIFY_ON_STARTUP`** — 환경변수 철자까지 든다 |
| 훑는 범위 (`:211-229`) | `backend-kotlin/**/src/main/resources/**.yml` **walk** + `docker-compose.yml` · `.env.example` · `backend-kotlin/Dockerfile` **정확 경로 3개** |
| 닿지 않는 자리 | JVM `-D` · 명령행 · 컨테이너 런타임 환경변수 · `JAVA_TOOL_OPTIONS` · `SPRING_APPLICATION_JSON` · 저장소 밖 배포 매니페스트(k8s·helm) — **전부 파일이 아니거나 저장소 밖** |

**→ 세 레인의 사실은 서로 모순되지 않는다.** privacy-gate 가 던진 네 물음(기본값이 켜짐인가 / 제품 **설정 파일**에 새는가 / 그 탐지기가 작동하는가 / 뒤집는 방향으로 실패하는가)은 **전부 참이고 음성 대조 M6 까지 붙어 있다.** codex 는 **다섯째 물음**을 던졌다 — *"운영자가 저장소 파일을 하나도 건드리지 않고 배포 시점에 끌 수 있는가."* 답은 **끌 수 있다**이고, 그 물음은 어느 레인도 묻지 않았다. 판정은 §5.2.

### 5.1 **Critical ②(차단②) — 1건 확정 권고.** 마감 **`documents` 단위 착수 전**

**항목:** `AesGcmContentCipherTest.kt`(I-7 전건 회귀 21케이스, X3·X4 의 유일한 증거)에 대해 **탐지 장치 세 층이 동시에 무력하다.**

**1차 판정은 「차단② 승격 후보 — 판정 필요」였다. 2차에서 Critical② 로 올린다 — 근거는 전부 신규 교차 입력 3건이고, 1차의 재독이 아니다.**

| 층 | 무력화의 내용 | 누가 봤나 |
|---|---|---|
| ⑴ **가드 클래스 대조** | 이 파일은 `GUARD_CLASS_FAMILIES` 밖이라 **선언조차 되지 않았다.** 지워도·꺼도 신고되지 않는다. families 를 줄이면 declared 와 discovered 가 **함께** 조용해진다 | Claude T-2·R-10 · codex B-6·B-7 (**2관점**) |

**신규 교차 입력 3건 (승격 근거):**

1. **codex B-1 + 이 회차 재현** — 1차는 ⑵ 를 「skip 을 통과시킨다」(거짓 초록 하나)로만 봤다. 실제로는 **양방향으로 고장나 있고**, 그 장치가 지금 HEAD 에서 **실패한다**. 「믿을 수 없는 장치」와 「관대한 장치」는 다르다.
2. **리더 실측(도입 커밋 `fcf584b`)** — 1차는 ⑶ 을 「게이트 25 도 못 봤다」로 적었으나 근거는 자체 추적이었다. 리더 실측으로 **연속 두 게이트 · 세 레인 × 두 회차**가 확정됐다. **일회성 누락이 아니라 상설 상태**다.
3. **codex D-1 의 범위 관측** — *"자동 검사는 돌아가도 테스트 자체가 올바른지는 diff 리뷰가 확인할 수 없다."* 즉 ⑶ 의 무력화는 스캐너·ktlint·detekt·test 로 **대체되지 않는다** — 그것들은 「이 테스트가 도는가」를 재지 **「이 테스트가 무엇을 재는가」를 재지 않는다.**

**§5 ② 정의 대조.** *"그 사건을 탐지·차단하는 게이트가 무력화된 상태(검증 없이 통과하는 경로, 위조 가능한 증거 파일, 검사 대상 0건인데 성공으로 끝나는 스크립트)."* — ⑴ 은 「검사 대상에 들지 않는 경로」, ⑵ 는 「검사 대상 0건인데 성공으로 끝나는 스크립트」의 정확한 사례(가드 전건 `@Disabled` → 초록), ⑶ 은 「사람이 검토했다고 기록되지만 실제로 볼 수 없었던 증거」다. **세 항목 모두 정의에 직접 걸린다.** 그리고 이 장치들이 지키는 사건 종류는 §5 Phase 7 ① — **AEAD round-trip 실패·변조 통과**다.

**Critical① 이 아닌 이유 (명시한다).** ①사건은 0이고(§5.0), **회귀의 내용 자체는 미검증이 아니다** — privacy-gate 가 이 파일을 **읽고 변조해** 음성 대조 7건(M1·M2·M3″·M4·M5·M6·M7)을 만들었고 전건 의도한 단언에서 RED 를 확인했다. 즉 **오늘 이 파일의 내용은 세 번째 레인이 실행으로 보증했다.** 무력한 것은 **내일 이 파일이 조용히 바뀌는 것을 막는 장치**다.

**착수 차단 여부는 판정하지 않는다.** 마감을 `documents` 단위 착수 전으로 적는 이유는 그 시점이 ⑴ 이 지키는 사건이 **처음 성립 가능해지는 시점**(첫 행이 이 암호로 쓰이는 때)이기 때문이다. §5 판단 규칙 5 에 따라 **Critical 이 남아 있으므로 Phase 4 종료를 보고하지 않는다.**

**닫는 데 필요한 최소 조치(세 레인 처방의 교집합, 참고용):**
- ⑴ families 이름 열거 → 「`src/test` 의 모든 최상위 테스트 클래스」를 분모로 삼고 **가드가 아닌 것을 근거와 함께 빼는** 탐지형으로 전환 (Claude R-10 · codex B-7 처방이 같은 방향)
- ⑵ `int(tests) - int(skipped) > 0` (Claude T-1) **+** `testcase@classname` 집계 (codex B-1 — **§2.2 에서 silent 0 으로 실측 확인**)
- ⑶ 원시 NUL → `\u0000` 이스케이프 (세 레인 만장일치, §7)

### 5.2 codex A-1 — F-2/X7 해제를 되돌리는가? → **되돌리지 않는다. 다만 해제 근거 네 개 중 하나를 무너뜨린다**

**판정: Major (수정 필요). 마감 `documents` 단위 착수 전.**

**되돌리지 않는 이유.** F-2/X7 이 주장하는 성질은 *"쓰기 키가 없거나 값이 틀리면 기동이 거부된다"* 이다. privacy-gate 가 이 성질을 **저장소 테스트를 거치지 않는 독립 탐침**으로 직접 확인했고(P1·P1b·P1c·P3c, `keys=[]`·세대 불일치·도메인 밖 전건 기동 거부), 기본값이 `verifyOnStartup == true` 임을 회귀가 단언한다. **codex A-1 은 이 성질이 거짓이라고 주장하지 않는다** — *"외부 설정으로 끌 수 있다"* 고 주장한다. 성질은 살아 있고, **그 성질을 켜 두는 것을 강제하는 장치**가 문제다.

**그러나 해제 근거 하나가 무너진다.** privacy-gate §2.2 는 네 물음으로 해제했다. 그중 **둘째 물음(「스위치가 제품 설정에 새는가」)의 답인 탐지기는 파일 스코프이고 저장소 스코프다**(§2.3 실측). JVM `-D`·명령행·컨테이너 환경변수·`SPRING_APPLICATION_JSON`·저장소 밖 매니페스트는 **닿지 않는다.** 그러므로 정확한 진술은 *"제품 **설정 파일**에 새지 않는다"* 이지 *"제품에서 끌 수 없다"* 가 아니다.

**세 레인이 하나로 모이면 이렇게 읽힌다** (셋 다 사실이고 서로 모순되지 않는다):

- **codex A-1** — 면제 스위치는 배포 시점에 저장소를 건드리지 않고 끌 수 있다
- **Claude S-2** — 그 스위치가 **모든 테스트 태스크에 전역**으로 걸려 있어, 키를 넣은 `@SpringBootTest` 를 써도 자기점검을 밟을 수 없다
- **Claude S-3** — 그 스위치를 지키는 훑기가 「열거하지 않는다」고 선언하고 셋을 열거한다
- **privacy-gate R-1**(실측) — 저장소의 **어떤 Spring 컨텍스트도 `verify()` 를 실행하지 않는다**(건너뜀 11 · 0세대 12)
- **Claude T-7 + privacy-gate F-6/X9 부분 해제** — 「조립된 빈을 실제 키로 쓰는 통합 경로」는 여전히 0

**합치면: 면제가 존재하고 · 그 면제의 감시자는 파일만 보며 · 면제되지 않은 경로를 밟는 컨텍스트는 저장소 어디에도 없다.** 세 레인이 각기 다른 축에서 같은 그림의 조각을 하나씩 가져왔다.

**Critical② 승격 논거(기각하지 않고 병기한다).** 이 스위치가 지키는 사건 종류는 privacy-gate 가 「가장 위험」으로 든 F-3 시나리오 — *"형식이 맞고 값이 틀린 키가 조용히 적재되고, 그 사이 쓴 행은 진짜 키로 열 수 없다"* 이며 이는 **복구 불가능한 데이터 손실**이다. 그것을 막는 장치가 배포 시점 프로퍼티 하나로 꺼지고 그 사실을 아무것도 탐지하지 않는다면 ②의 정의에 닿는다는 독법이 성립한다. **Major 로 둔 근거는 셋이다** — ⑴ 기본값이 켜짐이라 **가만두면 안전하다**(fail-closed 방향) ⑵ 끄는 데 운영자의 **고의적 배포 시점 행위**가 필요하다 ⑶ ①사건은 문서 저장 경로가 생겨야 성립하고 오늘 0이다. **판정이 갈릴 수 있는 자리이므로 승격 여부를 리더에게 올린다.**

### 5.3 codex B-3 — `xfail(strict)` 2종은 실제로 은폐형인가? → **은폐형이 맞다. 1차 W-3 의 등급은 근거가 부족했다**

**판정: 판정 필요 (Major 후보). 마감 문서 소유권 경로 진입 전.** 그리고 **이 판정이 privacy-gate 의 처방 하나를 무효화할 수 있으므로 리더 결정이 필요하다.**

**`CLAUDE.md` 규칙 4 ⑵ 의 분류 기준을 적용한다** — *"장치를 먼저 분류한다(탐지 / 은폐 / 강제·표현 / 범위 선언). … 은폐형(무시 패턴·억제·면제 조항)은 ⑴이 참이어도 넓히지 않는다 — 탐지형으로 갈아탄다. 범위 선언형은 빈 선언에서 통과하면 안 된다."*

분류를 가르는 물음은 하나다 — **그 구멍이 실제 제품 코드로 실현될 때 이 장치는 무엇을 하는가.**

| | 두 레인이 **합의한 사실** |
|---|---|
| 선언을 **삭제**했을 때 | 제품 게이트 결과가 **변하지 않는다** (codex 명시 / Claude W-3 §3 「결속 단언이 없다」가 같은 것을 약하게 말함) |
| 그 형태의 **실제 코드**가 들어왔을 때 | 스캐너는 계속 무적중이고 스위트는 **XFAIL 로 초록** (codex 명시 / Claude W-3 §1 이 「조용한 0 → 선언된 0」이라 적어 **가시성만** 얻었음을 인정) |
| `strict=True` 가 실제로 강제하는 것 | 합성 사례가 탐지되기 **시작하면** XPASS 로 실패 — 즉 **해소를 알리는 장치**이지 **미해소를 막는 장치가 아니다** (양쪽 동일) |

**즉 두 레인은 기제에 완전히 합의했고, 갈린 것은 「테스트 파일에 한 줄 남기는 것」을 탐지로 셀 것인가 하나다.** 규칙 4 의 판정 도구인 **음성 대조**를 적용하면 답이 나온다 — *"그 장치를 떼면 정확히 무엇이 깨지는가. 떼어도 아무것도 깨지지 않으면 검증된 장치가 아니다."* **떼어도 아무것도 깨지지 않는다는 데 두 레인이 합의했다.** 그러므로 **탐지형이 아니다.** 남는 후보는 범위 선언형인데, 규칙은 그 유형에 「빈 선언에서 통과 금지」를 요구한다 — 여기는 그 역, **비어 있지 않은 선언이 구멍이 열린 채로 통과**한다. 어느 쪽으로 읽어도 **규칙 4 가 요구하는 형태를 갖추지 못했고, 알려진 실패를 성공 종료로 바꾼다는 codex 의 규정이 맞다.**

**1차 W-3 의 등급 변경(별도 항목으로 표시).** 1차는 **권고**로 두면서 「살아 있다」의 근거로 *"실제 스캐너 패턴으로 재고, 대리 경로가 아니다"* 를 들었다. 그 문장은 **참이지만 다른 물음의 답**이다 — 「합성 사례를 정확히 재는가」와 「실제 구멍을 막거나 알리는가」는 다른 축이고, 규칙 4 가 묻는 것은 후자다. **codex B-3 이라는 신규 교차 입력으로 등급 근거가 갱신됐으므로 「판정 필요」로 올린다. 1차의 권고 등급은 표에서 지우지 않았다.**

**세 레인 처방의 정면 상충 — 리더 판단 요청.**

| 레인 | 이 장치에 대한 처방 |
|---|---|
| **privacy-gate** (§10.1 S-1 해제 조건 **ⓑ**) | 새로 발견한 줄바꿈 미탐을 *"`OWNERSHIP_403_DECLARED_MISSES` 에 **xfail(strict) 로 선언**하고 그 근거를 적는다"* — **이 장치를 더 쓰라** |
| **codex** (B-3) | *"strict xfail 을 **제거**한다"* — 이 장치를 쓰지 말라 |
| **Claude** (1차 W-3) | 유지하되 D2 에 현실적 예시 1건 추가 + 마감 못박기 — 중간 |

**교집합이 존재한다.** privacy-gate 는 ⓐ **또는** ⓑ 를 제시했고, **ⓐ(`OWNERSHIP-403` 이 논리 줄을 보게 해 인접성 요구를 무력화한다)는 세 레인 모두가 받아들일 수 있는 유일한 선택지다** — 탐지형이고, codex B-2 가 지목한 미탐 종류와도 같은 방향이며, Claude W-2 의 「자리 열거」 지적과도 겹치지 않는다. **ⓑ 를 고르면 codex B-3 이 은폐형이라 판정한 장치를 확장하게 된다.** 리더가 ⓐ/ⓑ 를 고를 때 이 사실을 아는 것이 이 문서의 목적이다. — **어느 쪽도 삭제하지 않았다.**

## 7. 원시 제어문자 처방의 교차 검토

### 7.1 세 처방을 나란히 놓는다

| 레인 | 처방 | 규칙 4 분류 |
|---|---|---|
| **privacy-gate**(R-6, 문서에 기재) | 그 한 글자를 `\u0000` 이스케이프로 적는다 (1글자, 동작 동일) | **점 수정** |
| **privacy-gate**(리더 프롬프트 경유 — **입력 문서에 없다**, §9 참조) | `git ls-files` **전수 탐지형 장치** — 면제 목록 없음 · 빈 스캔 실패 · git 자신의 텍스트/바이너리 분류에 위임 | **탐지형** |
| **codex**(D-1) | 원시 바이트를 `"\u0000없는값"` 이스케이프나 평범한 비어 있지 않은 표식으로 바꾸고 textual diff 를 다시 리뷰한다. **`.gitattributes` 강제는 명시적으로 기각** — *"NUL 을 남겨 다른 바이너리 판정기를 계속 속이므로 적절한 해결이 아니다"* | **점 수정** + 표현형 기각 |
| **Claude**(1차 K-1) | *"고치는 비용은 문자 하나(`"\u0000"`) **또는** `.gitattributes` 한 줄이다"* | **점 수정** 또는 **표현형** |

### 7.2 양립하는가 → **양립한다. 다만 Claude 1차의 둘째 선택지 하나가 기각된다**

**⑴ 점 수정은 세 레인 만장일치다.** privacy-gate R-6 · codex D-1 · Claude K-1 의 첫 선택지가 **글자 하나까지 같다**. 이견 0.

**⑵ `.gitattributes` — codex 의 기각이 옳고, Claude 1차의 둘째 선택지를 철회한다.** 규칙 4 의 분류로 보면 `.gitattributes text` 는 **표현형(강제·표현)** 장치다 — **git 의 렌더링만** 바꾸고 디스크의 바이트는 그대로 둔다. 그러면 `grep`·`git grep`·민짜 `diff`·`file`·다른 도구의 바이너리 스니핑은 **계속 속는다**. 1차 §2.4 K-1 이 스스로 그 사실을 적었다 — *"두 판을 파일로 떠서 민짜 `diff` 를 걸어도 `Binary files … differ` 하나만 나온다"*. **자기가 관측한 사실이 자기 처방의 둘째 선택지를 이미 반박하고 있었고, codex 가 그것을 짚었다.** 심각도 변화가 아닌 **처방의 사실 정정**이므로 여기 기록한다.

**⑶ 점 수정과 탐지형 장치는 서로를 대체하지 않는다 — 둘 다 필요하다.** 점 수정은 **오늘의 한 파일**을 고치고, 탐지형 장치는 **내일의 다음 파일**을 막는다. 규칙 4 의 판정 기준은 *"겪은 횟수가 아니라 결함의 구조"* 이고 *"빈자리가 구조적으로 재발하면(열거할 수 없는 자리를 **종류로** 댈 수 있으면) 그 종류만큼 넓히되, **은폐형은 넓히지 않는다 — 탐지형으로 갈아탄다**"* 이다. 여기서:

- **재발이 구조적인가 → 그렇다.** 이 회차가 `git ls-files` 전수로 실측한 값 — **추적 파일 중 원시 제어문자(TAB·LF·CR 제외)를 든 것 15개, 그중 8개는 jar·zip·docx·hwpx 바이너리 픽스처, 나머지 7개는 비바이너리다**:

  | 파일 | 제어문자 |
  |---|---|
  | `backend-kotlin/infrastructure/.../AesGcmContentCipherTest.kt` | `0x00` |
  | `backend-kotlin/application/.../WorkspaceNameRules.kt` | `0x01` |
  | `docs/migration/_workspace/02_kotlin-implementer_export-domain.md` | `0x01` |
  | `docs/migration/_workspace/reviews/12_export-luhn-suppression_cross.md` | `0x1f`, `0x7f` |
  | `docs/migration/_workspace/reviews/13_regression-and-pins_migration-reviewer.md` | `0x7f` |
  | `parity/fixtures/export/export.json` | `0x7f` |
  | `parity/fixtures/text/text.json` | `0x7f` |

  **`.kt` · `.md` · `.json` 세 종류에 걸쳐 있고, 그중 둘은 리뷰 산출물 자신이다.** 그리고 **여덟 번째 사례는 privacy-gate 의 이번 산출물 자신**이었다 — R-6 을 쓰면서 그 문단에 원시 NUL 을 붙여 넣었고 자기 정정으로 고쳤다(그 파일 라인 558). 리더가 든 「8건」은 이 여덟 번째를 포함한 수로 읽힌다.

  **그리고 아홉 번째가 이 문서다** — §12.1 참조. **이 절을 쓰는 행위가 이 절이 기술하는 결함을 다시 일으켰고, 그것도 privacy-gate 가 같은 실수를 했다고 적은 문단 바로 옆에서 일어났다.** 세 번째 재발이며, 셋 다 **「NUL 에 관해 쓰는 도중」**에 발생했다. **이보다 강한 구조적 재발의 증거는 만들기 어렵다** — 이 결함은 부주의가 아니라 **기제**다. 「NUL 을 언급하려면 NUL 을 타이핑하게 되고, 아무 도구도 그것을 막지 않는다.」 규칙 4 의 *"열거할 수 없는 자리를 **종류로** 댈 수 있으면 그 종류만큼 넓힌다"* 의 조건이 여기서 충족된다 — 종류는 **「원시 제어문자를 든 추적 파일 전부」**이고, 개별 자리를 열거하는 방식으로는 셋 다 못 잡았을 것이다.
- **NUL 만의 수는 세 레인이 일치한다.** codex: *"NUL 을 담은 추적 파일은 9개이고 나머지 8개는 jar·zip·docx·hwpx"* — **이 회차 실측과 정확히 일치**(0x00 보유 9개 = 소스 1 + 바이너리 8). Claude 1차: *"저장소 전체에서 NUL 을 든 텍스트 소스는 이 파일 하나뿐"* — **참**.
- **탐지형인가 은폐형인가 → 탐지형이다.** privacy-gate 가 선언한 세 성질(면제 목록 없음 · 빈 스캔 실패 · 분류를 자기가 정하지 않고 위임)은 규칙 4 가 **범위 선언형**에 요구하는 「빈 선언에서 통과 금지」와 **은폐형 금지**를 둘 다 만족한다. 면제 목록이 없다는 것이 결정적이다 — 면제 목록이 붙는 순간 은폐형으로 미끄러진다.

**결론: 두 처방은 양립하며, 규칙 4 분류로는 privacy-gate 의 탐지형 장치가 정답 유형이고, codex 의 점 수정이 그 장치가 서기 전 오늘의 사례를 닫는다. `.gitattributes` 만 떨어진다.**

**한 가지 주의는 §10 으로 분리했다** — 「git 자신의 분류에 위임」이라는 판정 기준의 폭에 관한 것이고, 이 회차의 어느 산출물과도 대조되지 않았기 때문이다.

## 10. 종합 중 발견 — **미교차** (다음 게이트의 범위로 올린다)

**이 회차의 어느 산출물과도 대조되지 않았다. 정본의 지적 목록에 넣지 않는다.**

1. **「git 자신의 텍스트/바이너리 분류에 위임」은 이번 결함을 잡지 못했을 기준이다.** privacy-gate 자신이 그 파일 라인 558 에 적어 두었다 — *"첫 8000바이트 밖이라 git 이 아직 바이너리로 잡지 않았을 뿐, **위치 운으로 살아 있던 상태**"*. git 은 파일 앞 8000바이트에서만 NUL 을 훑고, `0x01`·`0x1f`·`0x7f` 로는 바이너리 판정을 내리지 않는다. §7.2 가 센 **비바이너리 7파일 중 6개는 git 이 텍스트로 분류한다.** 즉 「git 이 바이너리라 부른 것」을 기준으로 삼는 장치는 **오늘 실재하는 7건 중 1건만** 잡는다. 판정 기준을 「원시 제어문자 보유」로 두는 것과 「git 이 바이너리로 부름」으로 두는 것은 **도달 범위가 크게 다르다.** — privacy-gate 의 장치 문면을 받지 못한 상태에서 낸 관측이므로 **미교차**로 분리한다. 다음 게이트에서 그 문면과 대조해야 한다.
2. **`ci.yml` 의 `kotlin` 잡이 지금 빨간지 확인되지 않았다.** §2.2 에서 요구 모드가 로컬 HEAD 에서 실패했고, `ci.yml` 스텝 순서는 codex 가 적은 그대로다. 그렇다면 이 스텝은 **CI 에서도 실패하고 있어야 한다.** 실패하고 있는데 아무도 몰랐다면 그 자체가 별건이고, 실패하지 않는다면 로컬과 CI 의 리포트 상태가 다르다는 뜻이라 **「리포트 XML 을 실행의 증거로 삼는 것」의 신뢰도 문제**가 된다. **어느 쪽인지 이 회차는 확인하지 못했다.**
3. **하네스 자기 보고의 음성 대조 H(요구 모드 ON + 리포트 완비 → exit 0, 27 passed)와 §2.2 의 실측(1 failed / 26 passed)이 갈린다.** 총 27개로 같으므로 **같은 스위트이고 리포트 상태만 달랐다.** 어떤 리포트 상태에서 H 가 통과했는지는 확인하지 못했다 — 그것이 밝혀지면 「리포트 기반 실행 증거」가 언제 참이고 언제 거짓인지가 정해진다.

### 12.1 자기 정정 — **이 문서가 §7 의 결함을 다시 저질렀다**

**숨기지 않고 적는다.** 이 문서의 초판을 쓰면서 §5.1·§7.1·§9.1 다섯 자리에 **원시 NUL 바이트(0x00)를 그대로 타이핑했다** — 「이스케이프로 바꾸라」는 처방을 인용하려다 이스케이프 대신 실제 제어문자를 넣었다. 작성 직후 스스로 검사해 발견하고 `\u0000` 표기로 바꿨다.

| 항목 | 값 |
|---|---|
| 발견 방법 | 산출물 작성 직후 자기 검사 — `python3` 로 전 바이트를 훑어 `c<32 and c not in (9,10,13)` 계수 |
| 초판 상태 | 75,556바이트 · **NUL 5개**(오프셋 35097 · 51635 · 52009 · 52394 · 67578) |
| **정정 도중 재발** | **이 §12.1 표를 쓰면서 또 2개를 넣었다**(같은 자리 — 「이스케이프로 바꿨다」를 적으려다). 재검사로 잡아 다시 고쳤다. **한 문서 안에서 두 번, 둘 다 정정을 기술하는 문장에서** 일어났다 |
| 현재 상태 | **원시 제어문자 0개** — 전 바이트 재검사로 확인(78,744바이트) |
| git 이 바이너리로 잡았는가 | **아니다** — 다섯 자리 전부 첫 8000바이트 **밖**이라 git 의 스니핑을 지나간다. **privacy-gate 와 정확히 같은 「위치 운」이다** |
| 정정 방식 | 원시 바이트 → `\u0000` 문자열 표기. **`cp` 를 쓰지 않았다**(규칙 5) — 같은 파일 안에서 바이트 치환 후 재검사 |

**이 사실이 §7.2 의 논거를 바꾼다.** 세 번의 재발이 모두 **「NUL 에 관해 쓰는 도중」** 일어났다 — `fcf584b` 의 테스트 작성, privacy-gate 의 R-6 작성, 이 문서의 §7 작성. **그리고 셋 다 자기 검사로만 발견됐고, 저장소의 어떤 자동 장치도 셋 중 하나도 잡지 못했다.** 그러므로:

- **점 수정만으로는 부족하다는 것이 실증됐다.** 오늘의 한 파일을 고쳐도 다음 사람이 그 파일을 **설명하는 순간** 재발한다.
- **privacy-gate 가 처방한 전수 탐지형 장치가 옳은 유형이다**(§7.2 결론 유지·강화).
- **다만 §10-① 의 주의가 더 무거워진다** — 이 다섯 개는 **git 이 텍스트로 분류한다**(8000바이트 밖). 「git 이 바이너리라 부른 것」을 기준으로 삼는 장치였다면 **이 문서를 잡지 못했을 것이다.** 판정 기준은 **「원시 제어문자 보유」** 여야 한다.

**이 항목은 새 지적이 아니다** — 이미 세 레인이 낸 지적(행 3)의 **아홉 번째 실증 사례**이자 이 회차 자신의 사고 기록이다. 리더가 §7 의 처방을 고를 때 이 사례를 재료로 쓸 수 있다.
