### 3.2 **N-01 — 네 번째 갈래: 안전한 호출이 위험한 호출의 방패가 된다 (한 계층 위에서)** 〔차단 ②장치〕

**근거 위치**: `.claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py:828`·`:865` (`rule.pattern.search(line)` — 논리 줄당 **첫 적중 하나만**) × `:231-257` (`log_body_is_real_candidate` 가 **그 한 적중의 인자 구간만** 판정)

**기제.** `refine` 훅은 "인자 구간 안의 본문 이름을 **전부** 본다"고 선언하고(`:241-243` docstring), 실제로 그렇게 한다 — **한 호출 안에서는.** 그런데 규칙 적용부는 논리 줄에서 `search()` 로 **첫 적중 하나**만 꺼내 refine 에 넘긴다. 한 논리 줄에 로그 호출이 둘 이상이고 **앞의 것이 안전하면**, refine 은 "찾았고 전부 안전"으로 빠져 **논리 줄 전체가 SUPPRESSED** 된다. 뒤의 위험한 호출은 아예 읽히지 않는다.

**직접 실행한 e2e 실측** (탐침 1파일, `scanner.scan()` 정식 경로):

```kotlin
fun a(draft: Draft) {
    if (ok) logger.info("id={}", draft.document.id) else logger.warn("b={}", draft.value)
}                                                                    // → SUPPRESSED

fun b(draft: Draft) {
    logger.info("n={}", draft.stats.count).also { logger.error("body={}", draft.value) }
}                                                                    // → SUPPRESSED

fun d(draft: Draft) {
    logger.error("body={}", draft.value)                             // → HIT (대조군)
}
```

```
hits:       [(20, 'logger.error("body={}", draft.value)')]
suppressed: {'LOG-BODY': {'값의 모양이 불변식 대상이 아님': 2}}
```

**순서 의존이다.** 같은 두 호출의 순서만 바꾸면(`위험` 먼저) **HIT** 이 된다. 즉 이 게이트의 판정이 코드 작성 순서에 달려 있다.

**왜 이것이 M-01·M-09·stop-gate 와 같은 종류인가.** 네 번 다 같은 문장으로 서술된다 — *"판정이 첫/가장 가까운 하나만 보고, 거기서 '안전'을 찾으면 나머지를 검사하지 않는다."* `_advance` KDoc(`:694`)이 이 형태에 **이름까지 붙여 두었다**: *"안전한 접근이 위험한 접근의 방패가 되는 형태다."* 그 이름이 붙은 자리는 **인자 구간 안**이었고, 같은 형태가 **호출 사이**에 그대로 남아 있다.

**은폐형이라는 점이 무게를 더한다.** `refine` 은 CLAUDE.md 규칙 4의 분류로 **은폐형**(억제·면제) 장치이고, 지금까지 네 번 전부 새는 방향으로 틀렸다(M-01 종단 / M-09 절단 / stop-gate 주석 / N-01 첫 적중). 규칙 4는 은폐형에 대해 *"⑴이 참이어도 넓히지 않는다 — 탐지형으로 갈아탄다"* 고 적었다.

**리포트에 흔적이 남지 않는다는 점도 같다.** 진짜 유출이 이 경로로 빠지면 리포트에는 `값의 모양이 불변식 대상이 아님 N건` 이라는 **숫자만** 늘고 위치는 찍히지 않는다.

**처방 제안(구현은 `kotlin-implementer` 몫)**: 논리 줄에서 `search()` 가 아니라 **`finditer()` 로 모든 적중을 꺼내 각각 refine 하고, 하나라도 안전하지 않으면 후보로 남긴다.** 그리고 그 성질을 `test_한_줄에_안전한_접근과_본문_접근이_섞이면_후보로_남는다`(`:170`)의 **호출 단위 확장**으로 고정한다 — 그 테스트는 지금 *한 호출 안의* 두 인자만 재고 있고, N-01 은 정확히 그 전제를 한 계층 위로 올린 자리다.

**마감**: **지금.** 이 게이트는 `ci.yml:104` 에서 이미 BLOCK 으로 돌고 있다.

### 3.3 M-02 의 상시 음성 대조가 없다 (§3.1 표의 빈칸)

`ci.yml:218-221` 이 클래스마다 `./gradlew --tests` 를 따로 돌리도록 갈랐다. 처방은 옳고, **"목록을 손으로 적는 것 자체는 이 스텝이 막지 못한다"** 는 한계도 주석에 적혀 있다(좋다).

## 6. 특별 점검 ④ — fixture 동결 방향과 `known_gap` 정의 어긋남

### 6.1 `masking-keeps-rrn-tab` 명명·전환 — 적정

`absent` → `present` 전환에서 **입력을 바꾸지 않고 방향만 뒤집었고**, id 를 `keeps-` 접두로 옮겼다. 이 fixture의 명명 규약상 `keeps-` 는 "가리면 안 된다"이므로, 방향이 뒤집힌 케이스가 옛 이름을 달고 있으면 목록을 훑는 사람이 방향을 잘못 읽는다 — **id 변경이 옳다.** 옛 id 는 원장에서 「낡은 항목」으로 지목됐고 갱신으로 닫혔음을 확인했다(`reference-ledger/masking.json` 에 `masking-rrn-tab` **없음**, `masking-keeps-rrn-tab` **있음**).

`reference_divergence: "expected"` 선언도 붙어 있다(Python `[ \t]` 가 TAB 을 여백으로 인정하므로 갈린다). 참고 갈림 29 → 32 로 증가한 것이 게이트 실행에서 재현된다(**갈림 32건**).

### 6.2 M-08 중복 검출 — 검출은 옳으나 **음성 대조가 상시가 아니다** 〔→ N-04〕

`compare_parity.py:875-891` 의 중복 입력 검사는 정확한 처방이다. 특히 *"손편집은 정본 대조가 이미 막으므로 이 검사가 받는 것은 **생성기에 중복이 들어오는 경로**"* 라는 범위 선언이 정확하다 — 새 장치가 기존 장치와 겹치는 부분을 스스로 가려냈다.

그런데 **`compare_parity.py` 에는 상시 회귀가 하나도 없다.** 저장소 전수 검색 결과 `tests/` 아래에서 이 스크립트를 부르는 파일이 **0개**다. M-08 의 음성 대조(생성기에 중복 주입 → exit 1 → 복원 → exit 3)는 1회성 실측이고, 이 게이트가 **Phase 2 종료 판정의 근거를 내는 바로 그 스크립트**다. M-13(Z-6)이 스캐너에 대해 닫은 형태(`tests/test_privacy_scanner.py` 신설 + CI 경로 명시)가 comparator 에는 그대로 열려 있다.

### 6.3 Z-7 분할(상시 7종 vs 한계 선언) — 적정

`tests/test_parity_ci_gate.py` 는 이 배치에서 가장 잘 만들어진 산출물 중 하나다.

### 6.4 `known_gap` 2건 — **리뷰 관점의 판단 근거** 〔→ N-03〕

`parity-verifier` 가 스스로 신고했다: *"판정을 **요청받고 명시적으로 판정하지 않기로 한**" 상태를 `known_gap`(= "아직 어느 게이트에도 판정을 요청하지 않은 자리")으로 표기하고 있다.* 신고 자체가 옳고, 숨기지 않은 것이 이 레인의 규율을 보여준다.

리더가 요청한 판단 — **"판정 보류" 표기 신설 vs `known_gap` 정의 확장** — 에 대한 내 근거는 셋이다.

**⑴ 정의를 넓히면 `known_gap` 이 무엇을 세는 수인지가 사라진다.**
§2.4 의 진입 조건은 `known_gap` 이 **대기열로 전용되는 것을 막는 유일한 장치**다. 넓히는 순간 "아무도 안 물어봤다"와 "물어봤고 게이트가 판정을 미뤘다"가 한 칸에 들어가고, `known_gap: 2` 라는 수는 **누구에게 무엇이 빚으로 남았는지**를 더는 말하지 않는다. 지금은 그 수를 보면 "미해결 판정 2건"임을 알 수 있는데, 넓히면 알 수 없다.

**⑵ `known_gap` 은 은폐형이고, CLAUDE.md 규칙 4가 이 자리를 직접 규정한다.**
> **은폐형**(무시 패턴·억제·면제 조항)은 ⑴이 참이어도 **넓히지 않는다 — 탐지형으로 갈아탄다.**

`known_gap` 은 "어느 방향도 단언하지 않는다"는 **면제 조항**이다. 정의 확장은 정확히 "은폐형을 넓히는" 조치이므로, 규칙이 이미 답을 정해 두었다. **정의를 넓히지 않는다.**

**⑶ 그러나 표기만 신설하는 것으로는 아무것도 바뀌지 않는다 — `known_gap` 은 지금 어느 게이트도 읽지 않는다.**
이것이 이 절의 핵심 발견이다. 전수 검색 결과 `known_gap` 은 **생성기(`dump_parity_fixtures.py`)가 쓰기만 하고 `compare_parity.py` 는 한 번도 읽지 않는다**(등장 **0회**). 즉:

- 별도 구획으로 리포트되지 않는다 — **`SKILL.md:322` 가 명령한 *"선언이 붙은 케이스는 별도 목록으로 올린다"* 가 구현돼 있지 않다.**
- 개수 상한이 없다. 0 → 2 로 늘었고 2 → 20 이 되어도 아무것도 빨개지지 않는다.
- **커버리지 수에 그대로 들어간다.** 게이트 리포트의 `성질 판정 108건` = masking 83 + repair-adoption 25 이고, 그 83 에 방향을 하나도 재지 않는 이 2건이 포함된다.

마지막 항목이 결정적이다 — **이것은 M-08 이 차단으로 판정한 것과 같은 기제다.** M-08 의 논거는 *"성질은 늘지 않는데 케이스 수는 늘고, 그 수가 리포트에서 커버리지의 대리 지표로 쓰인다"* 였다. `known_gap` 케이스는 성질을 **하나도** 늘리지 않으면서 같은 수를 늘린다. 같은 배치가 한쪽에는 exit 1 게이트를 세우고 다른 쪽에는 아무것도 세우지 않았다.

**따라서 처방 권고**: `pending_verdict` 를 신설하되 **표기가 아니라 탐지로 만든다.**

| 요소 | 내용 |
|---|---|
| 필수 필드 | `owner`(수신자) · `deadline`(Phase) · `referred_by`(판정서 절 번호) — 셋 다 없으면 **exit 1** |
| 리포트 | `known_gap`·`pending_verdict` 케이스를 **별도 구획**으로 찍는다 (`SKILL.md:322` 이행) |
| 커버리지 | `성질 판정 N건` 에서 **분리 집계**한다 (`판정 108건 중 무단언 2건` 형태) |
| 상한 | 선언 하한 파일 방식(`.github/parity-declared-floor.txt` 와 같은 비대칭 검사)으로 개수를 못박는다 — **이미 저장소에 있는 패턴이다** |

이렇게 하면 은폐형이 탐지형으로 갈아타고, `known_gap` 은 원래의 좁은 뜻을 유지한다.

> **부기 — 연도 배열 자체의 방향은 판정하지 않는다.** `2021 2022 2023 2024` 가 카드번호로 가려지는 것이 옳은지는 `privacy-gate` 가 명시적으로 판정을 미룬 자리이고, 그것을 리뷰 레인이 대신 정하면 판정 권한을 가로채는 것이다. 나는 **표기 체계의 처분**만 판단했다. 다만 `privacy-gate` 가 *"가리는 쪽이 정책 정합"* 이라고 적은 근거(검수 화면에 `original` 이 나란히 보인다)는 계약 `MaskedItemResponse.original` 필수 필드로 확인되므로 **근거 자체는 성립한다** — 교차 검증이 없을 뿐이다.

**N-02 상세 (실측)**

```
False  log.warn(x)          ← GlobalExceptionHandler 가 쓰는 이름
True   logger.warn(x)
True   logge.warn(x)        ← 이 이름은 잡는다(의도된 적 없다)
False  _log.warn(x)
False  LOG.warn(x)
False  logging.warning(x)
```

의도는 `_?log(?:ger)?\.` 였을 것이다. `logger?` 로 적히면서 **"log 또는 logger"가 아니라 "logge 또는 logger"** 가 됐다. 지금 `log.error(...)` 두 줄은 예외 클래스 이름만 찍으므로 **사건은 0건**이다. 그러나 이 파일은 **전역 예외 핸들러** — 본문·요청 값이 로그로 새기 가장 쉬운 자리이고, 거기서 탐지기가 전혀 발화하지 않는다. 불변식 4의 판정 근거가 "탐지 도달"인 이상(§5 판정표), 이 구멍은 그 판정의 전제를 무너뜨린다.

## 12. 리더에게 (1차 결론)

1. **게이트 09 의 차단 3건은 실측으로 닫혔다.** M-01 의 처방(열거 → 사슬 파싱)은 방향이 옳고, 상시 음성 대조가 붙어 있다.
2. **그러나 같은 탐지기에서 네 번째·다섯 번째 갈래가 나왔다.** N-01 은 내가 적대 입력으로 뚫었고 e2e 로 재현했다. N-02 는 정규식 한 글자(`logger?` ← `log(?:ger)?`)이며 **저장소가 지금 쓰는 로거 이름**을 못 본다. 둘 다 사건 0건, 장치의 빈자리다.
3. **`refine` 훅은 네 번 연속 새는 방향으로 틀렸다.** M-01·M-09·stop-gate·N-01. CLAUDE.md 규칙 4가 은폐형에 대해 정한 처방(*"넓히지 않는다 — 탐지형으로 갈아탄다"*)을 이 훅 자체에 적용할지 판단이 필요하다 — 나는 점 수정(`finditer`)을 권고하되, **다섯 번째가 나오면 훅을 걷어내는 선**을 지금 정해 둘 것을 제안한다.
4. **`known_gap` 처분에 대한 답**(§6.4): **정의를 넓히지 마라.** 규칙 4가 은폐형 확대를 금지한다. 「판정 보류」를 신설하되 **표기가 아니라 탐지로** 만들어야 한다 — 지금 `known_gap` 은 **어느 게이트도 읽지 않는다.**
5. **§4-septies 집행은 정합이다.** 해제조건 4건 전건, 그리고 "동작 무변경·근거만 교체" 주장이 diff 로 검증된다. 경계축 짝을 생성기 구조로 묶은 것은 이 배치의 가장 좋은 자리다.
6. **원장은 실물과 맞는다.** 실행 재현 9항 전건 일치. 남은 어긋남은 342행 선두 수치 정지 1건(N-11)이다.
