#### C-2 — 처방 ④가 리뷰 경계를 옮겼는데 리뷰 스크립트의 기본 `--scope` 는 그 경계에서 틀린 대상을 고른다 · **차단(② 장치)** · 마감: 첫 묶음 회차(= 다음 비-4축 변경)

`codex-review/scripts/codex-review.sh:74` — `--scope auto`(기본): "작업 트리가 더러우면 working-tree, 깨끗하면 기본 브랜치 대비 branch."

- **종전 경계(커밋 직전)**: 대상 = 아직 커밋 안 된 그 변경. `auto` → working-tree. **기본값이 맞다.**
- **개정 경계(Phase·회차 단위 묶음)**: 대상 = **이미 커밋된** 여러 변경. 작업 트리가 더러우면 `auto` 는 working-tree 를 고르고 **커밋된 묶음을 건너뛴다.** 대상이 0건이 아니므로 `EXIT_EMPTY_TARGET`(7) 도 안 걸리고, exit 0 · 비지 않은 출력이 남아 **그 회차의 통과 근거로 기록된다.**

스크립트 자신이 이 실패를 실측으로 적어 두었다 — `codex-review.sh:23-25`:

> "빈 diff를 주면 codex는 실패하지 않고 … verdict=approve로 끝낸다(실측: `adversarial --base HEAD` → exit 0, 1,164바이트). --base를 잘못 주거나(--base HEAD), **커밋한 뒤 --scope working-tree로 돌리거나**, 브랜치를 착각하면 **리뷰 대상 0줄인 채 게이트 통과가 기록된다.**"

두 SKILL 어디에도 묶음 리뷰에서 `--base <묶음 시작 커밋>` 을 요구하는 문장이 없고, 기본 scope 도 바뀌지 않았다. 처방 ④는 **기본값이 맞는 경계에서 기본값이 틀린 경계로** 리뷰를 옮기면서 그 기본값을 손대지 않았다. 이것이 「시점만 바꿨다」가 실제로 「여부가 바뀐다」로 넘어가는 기계적 경로다.

#### C-3 — 「모든 변경은 정확히 한 번 리뷰를 받는다」에 장부가 없다 · **차단(② 장치)** · 마감: 첫 묶음 회차

`묶어|보류|이연|deferred` 로 3파일을 훑으면 나오는 것은 "묶어 한 번에 리뷰한다" 세 줄뿐이고(`CLAUDE.md:25`, `kotlin-migration:157`, `codex-review:41`), **무엇을 이연했는지 적으라는 요구가 0개**다.

장부가 없으면 사후에 「이연됨」과 「끝내 리뷰 안 됨」이 **구분되지 않는다.** 이것이 리더 질문 ②의 답이다 — 면제 목록이 한 줄도 안 늘었다는 것은 은폐형 확대가 **아님의 필요조건일 뿐 충분조건이 아니다.** 은폐는 목록에서만 일어나지 않고 **장부 부재**로도 일어난다. 그리고 어느 축에 닿았는지 판정하는 주체가 리뷰 대상 본인(리더)이라는 점은, 장부가 있으면 사후 검증 가능한 문제이고 **장부가 없으면 검증 불가능한 문제**가 된다. 그래서 "판정 주체가 본인인 것이 문제인가"의 답은 조건부다 — **C-3가 열려 있는 동안은 문제다.**

**NC-2·NC-3 의 의미.** 신설 `test_원장_파일이_전부_실재한다` 는 **존재만** 단언한다. 그 docstring이 스스로 적은 피해 — "그 파일에 있던 표가 판정 밖으로 나가고, 표 개수 축은 그것을 알아채지 못한다"(`tests/test_harness_scope_reach.py:1163-1170`) — 는 NC-2·NC-3 에서 **똑같이 일어나는데 잡히지 않는다.** 범위 선언형 장치가 **빈 선언에서 통과한 것**이므로 SKILL.md 규칙 4 ⑶ 위반이다. 아울러 「아카이브는 append-only」 규약의 강제자도 0으로 확인됐다(NC-3 이 전량 교체를 통과).

이 결함은 §3-b 가 정정한 것과 **같은 종류의 한 걸음 옆**이다: 초판은 "개수 축이 소실을 잡는다"가 거짓임을 지적받고 삭제·개명을 막았고, **비움·전량교체는 그대로 열려 있다.**

#### M-3 — 「정확 일치는 한 개도 조용히 못 준다」는 게이트 색이 아니라 diff 가시성이다 · **판정 필요**

실측: `TEST_CLASS_COUNT`=111 = `len(TEST_CLASSES)`=111 · `MIN_TEST_CLASSES`=105 · `len(FLOOR_TEST_CLASSES)`=29 = `MIN_FLOOR_CLASSES`=29. `MIN_TEST_CLASSES`·`MIN_FLOOR_CLASSES` 는 `RATCHET_SCALAR_PINS` 에 등재돼 방향이 강제된다(확인).

`TEST_CLASS_COUNT` 복원 판정 자체는 옳다(§3-b). 다만 `tests/test_kotlin_gate_reach.py:361` 의 표현 — "이 상수는 「한 개도 조용히 못 준다」" — 은 게이트 색을 말하는 것으로 읽히는데, **3자리 동시 편집**(목록 1줄 + 상수 1 감소 + `.kt` 삭제)은 정확 일치·라쳇(110≥105)·소스트리(양쪽 일치)·리포트(재빌드하면 양쪽 일치)를 **전부 통과한다.** 리더 V3가 그 절반(상수 없는 상태)을 이미 측정했고, 상수 복원은 **같은 파일 안에** 두 번째 편집 자리를 만드는 것이라 exit code 를 바꾸지 않는다. 복원으로 얻은 것은 「기계 차단」이 아니라 「diff 가시성 + 필수 리뷰 라우팅」이다.

**리더 질문 ①의 답:** 그 창을 실제로 막는 것은 셋이고 어느 것도 기계 차단이 아니다 — ⑴ 바닥 목록(이름 고정 29개), ⑵ 정확 일치가 강제하는 2자리 diff, ⑶ **축③(그 파일 편집 = 필수 리뷰)**. ⑶이 유일한 실질 방어인데 그것이 C-2·C-3가 약화시킨 바로 그 리뷰다.

**창이 자라는 것이 장부에 정직한가:** 절반만. 규칙 8 「잃는 것과 그 크기」와 `test_kotlin_gate_reach.py:355-362` 가 창의 존재와 확대를 **서술**하고, 현재 크기 6을 **당시 값으로 주석에 박아** 뒀다. 그런데 `len(TEST_CLASSES) - MIN_TEST_CLASSES` 를 **매 실행에서 재거나 보고하는 장치가 0개**다. 규칙 3을 창 자신에 적용하면 도달 0이다 — 창은 Phase 길이에 비례해 자라고, 자란 크기를 아무도 재지 않는다.
