**행 수와 원 지적 수의 관계 — 오해를 막기 위해 명시한다.**

- **codex 는 finding 을 2건 냈다**(C-1·C-2). 그 2건이 표에서 5행에 걸쳐 있다: C-1 → X-1(본절) + X-2(Recommendation 후반), C-2 → X-4(본절) + X-3(부수절) + X-5(결론). **codex 가 5건을 지적한 것이 아니다.**
- **Claude 는 명명 항목 30건**을 냈다. 그중 `R-3·R-4·R-5·R-6·R-8` 5건은 도달 범위 점검의 **결과 칸**이고 각각 다른 N/R 항목을 가리키는 포인터라 독립 행으로 세지 않았다(Claude 자신의 §8 요약도 이 5건을 따로 세지 않는다). 30 − 5 = **25행**이 Claude 유래이고, 그중 3행(X-1·X-2·X-3)이 codex 와 만나 합의가 됐다. 25 − 3 = **22 = Claude 단독** ✔
- X-5는 **양쪽 산출물에서 유도된 새 행**이다 — Claude §3.C 의 「#4 해소」 판정과 codex C-2 의 결론이 정면으로 갈리는 자리라, 어느 한쪽 항목에 흡수시키면 충돌이 표에서 사라진다.

### 3.2 codex 의 「전제 확인 필요」 판정 — **전제는 참이다**

**전제 ⓐ 「CI 의 8/8 경로는 `--only-domain` 없이 비교기를 호출한다」 → 참 (V-1).**

**Claude 의 음성 대조 3종이 이 전제를 실측했는가 → 했다.** NC-1 은 「표시 파일 삭제 + `--only-domain` 없음」을 **CI 의 실제 8/8 경로로 지정해** 돌렸고 결과가 **exit 0 · 경고 한 줄 없음**이다. **전제 ⓑ 「표시 파일 헤더의 자기 무장 서술과 어긋난다」 → 어긋난다 (V-3).**

## 4. 리더 지정 판정 ② — C-2 와 Claude C 잔여의 병합 여부

**결론: X-3(빈 유도)는 병합, X-4(상수 stem)는 분리, N-03(C1 드리프트)은 분리.** 기제로 가른 근거는 아래와 같다.

### 4.1 판정 기제 — `check_contains_derived` 가 무엇을 보는가 (V-4)

```python
# compare_parity.py:747-749
missing = [
    item for item in required if not any(call.text(str(item)) in one for one in reported)
]
```

이 판정에는 성질이 **둘밖에 없다**: ⑴ `required` 의 각 원소가 ⑵ 산출물 문자열 안에 **부분 문자열로 존재하는가**. 여기서 곧바로 두 개의 빈자리가 나온다.

- **빈자리 A — `required` 가 비면 `missing` 도 비어 조용히 통과한다.** (`:750 if missing:` 이 거짓 → `:757 return []`)
- **빈자리 B — 케이스 사이의 구별을 요구하지 않는다.** 케이스별로 독립 판정하므로, 모든 케이스의 `required` 를 합집합으로 품은 **하나의 상수 문자열**이 전 케이스를 통과한다.

### 4.2 병합·분리 판정

| 항목 | 어느 빈자리인가 | 판정 |
|---|---|---|
| Claude **R-7** (빈 유도 무탐지) | **A** | **codex C-2 부수절과 병합 → X-3** |
| codex **C-2 부수절** (`all-forbidden` 표지 빔 · `control` 은 `입니다` 하나) | **A** | 같은 자리를 같은 기제로 짚었다. 표현만 다르다 |
| codex **C-2 본절** (46자 union stem 이 21건 전건 통과) | **B** | **분리 → X-4.** Claude 는 이 갈래를 재지 않았다 |
| Claude **N-03** (`FILENAME_FORBIDDEN` C1 드리프트) | **어느 쪽도 아님** | **분리 유지** |

**X-3 병합 근거**: 두 서술이 같은 fixture 케이스(`all-forbidden`·`control-chars`)를 같은 이유로 지목한다. Claude 는 「단언 608 중 3건이 빈 요구」라는 수치까지 붙였고, codex 는 「`control` 표본은 한 글자 조각이 버려져 일반적인 `입니다` 만 요구한다」로 **1자 조각 탈락(`len ≥ 2`)이라는 하위 기제**까지 같이 짚었다. Claude 의 §3.C 표 ③행이 정확히 같은 내용이다. **독립 합의로 본다.**

**X-4 분리 근거 — 방향이 반대다.** Claude 의 NC-4 는 파일명 22개를 **표지를 품지 않는 대체 이름**으로 치환해 게이트가 **발화하는지**(18건 발화) 봤다. codex 는 파일명 21개를 **모든 표지를 품는 상수**로 치환해 게이트가 **침묵하는지**(실패 0건) 봤다. 두 실측은 서로를 반증하지 않는다 — **같은 장치의 서로 다른 두 성질**을 잰 것이다. 그리고 **A 를 고쳐도 B 는 남는다**: 빈 표지를 금지해도 union stem 은 모든 표지를 품고 있으므로 여전히 통과한다. 역도 성립한다. 따라서 **하나의 수정 항목으로 묶되 수용 기준을 둘 다 걸어야 하고, 표에서는 별개 행으로 남긴다**(한 행으로 뭉치면 A 만 닫고 「C-2 처리 완료」가 성립해 버린다).

**N-03 분리 근거 — 결함의 종류가 다르다.** X-3·X-4 는 **거짓 통과(false pass)** 이고, N-03 은 **거짓 실패(false fail)** 다. 그리고 기제가 판정부가 아니라 **유도부의 입력 필터**에 있다 (V-5).

```python
# compare_parity.py:914-919 — 주석은 "요구사항이 지목한 집합이고 구현에서 읽지 않는다"
FILENAME_FORBIDDEN = set('\x00…\x0d"\\/:*?<>|') | {chr(c) for c in range(0x0E, 0x20)} | {"\x7f"}
#   → C0 + DEL + 구두점.  C1(U+0080–U+009F) 없음
```
```kotlin
// Export.kt:59-60
private val FORBIDDEN_IN_FILENAME = Regex("""[\u0000-\u001F\u007F-\u009F"\\/:*?<>|]""")
//   → C0 + DEL + C1 + 구두점
```

비교기는 C1 에서 표지를 가르지 않으므로 **C1 을 품은 표지**를 요구하고, Kotlin 은 C1 을 지우므로 그 표지가 산출물에 없다 → 거짓 실패. 이것은 「부분 문자열 존재만 본다」의 결과가 아니라 **같은 요구사항을 두 곳에 각각 선언해 두고 한쪽만 고친** 드리프트다. 비교기 주석이 「구현에서 읽지 않는다」로 X-4형 순환을 피한 것은 옳지만, 그 대가로 **두 선언이 갈릴 때 아무도 대조하지 않는다.** 수정 방법도 다르다(판정 규칙 강화가 아니라 두 집합의 정합), 따라서 분리한다. 마감은 Claude 1차대로 N-02 와 동시다 — N-02 를 집행하는 순간 발화하기 때문이다.

**보태서**: codex 는 focus 축③(d)에서 **이 두 집합의 차이를 명시적으로 질문받았다**(「`FILENAME_FORBIDDEN`(파이썬 쪽)과 `FORBIDDEN_IN_FILENAME`(Export.kt 쪽, U+0080–U+009F C1 을 새로 포함)이 서로 다른 집합인 것이…」). 지적은 나오지 않았다. **사실만 기록한다.**

### 5.2 codex 쪽 — 「증명하지 못한다」 (C-2 원문)

> - [medium] 파일명 하한이 모든 제목을 무시하는 하나의 공통 파일명을 통과시킨다 (`.claude/skills/python-kotlin-parity/scripts/compare_parity.py:741-749`)
>   판정은 제목 표지가 파일명 어디엔가 부분 문자열로 존재하는지만 본다. 현재 7개 제목에서 나온 모든 표지를 합친 동일한 46자 stem 을 21개 docx/txt/hwpx 결과에 주입한 변이에서 `run_assertions()` 가 전건 실패 0건을 반환했다. 즉 구현이 입력 제목을 전혀 읽지 않아도 고정 문자열에 표본 조각만 우연히 포함하면 초록이다. 또한 `all-forbidden` 은 표지가 비고, control 표본은 한 글자 조각이 버려져 일반적인 `입니다` 만 요구한다. **이는 사용자가 올린 제목의 정보 유실을 막는다는 선언을 증명하지 못한다.**
>   Recommendation: export 전용 검사를 분리해 입력과 출력 stem 의 연관성을 판정하라. 정제 후 비어 있지 않은 제목은 빈 표지를 금지하고, 서로 다른 제목을 같은 stem 으로 반환하는 변이와 런타임 생성 고유 표지를 무시하는 변이가 실패하도록 metamorphic 테스트를 추가하라.

근거의 성격: **선언(「사용자가 올린 제목의 정보 유실을 막는다」)이 요구하는 성질은 입력→출력 연관성인데, 장치가 재는 것은 부분 문자열 존재뿐이다.** 즉 「장치가 선언한 목적을 달성했음이 증명되지 않는다」는 의미의 미해소.

### 5.3 두 판정이 왜 갈리는가 — 사실은 갈리지 않는다

**두 실측 모두 참이고 서로 모순되지 않는다.** NC-4(대체 이름 치환 → 18건 발화)와 codex 변이(union stem 주입 → 0건 실패)는 같은 장치에 서로 다른 입력을 넣은 것이고, 두 결과가 동시에 성립한다. 갈리는 것은 **「해소」의 기준**이다.

| | 해소의 기준 | 그 기준에서의 결론 |
|---|---|---|
| Claude | **제기된 결함의 재현 여부** — 게이트 12 #4 는 「대체 이름 치환 시 불충족 0건」으로 정의됐고, 그 입력이 이제 막힌다 | 해소 |
| codex | **선언한 목적의 달성 여부** — 「제목 정보 유실 차단」을 증명하려면 입력 무시 구현이 걸려야 하는데 걸리지 않는다 | 미해소 |

이 저장소의 규칙(`CLAUDE.md` 「선언한 범위와 실제 도달을 대조한다」)은 **선언 대 도달**을 판정 기준으로 삼는다. 그 문면만 보면 codex 기준이 규칙에 더 가깝다. 그러나 「제기된 결함이 닫혔는가」와 「그 축의 검증이 충분한가」는 원래 다른 질문이고, 게이트 12 의 저지 조건 C 는 전자로 쓰였다. **이 문서는 어느 쪽으로도 판정하지 않는다.**

## 6. 리더 지정 판정 ③ — codex 축 ① 무지적 vs Claude A 판정의 비대칭

**결론: 비대칭의 원인은 항목마다 다르다. 「codex 시야 밖」이 맞는 것은 N-06 하나뿐이고, 나머지는 「focus 에 명시됐는데 지적이 나오지 않은」 것이다. 둘을 섞어 기록하면 안 된다.**

### 6.1 축 ① 하위 항목별 대조

codex focus 축①은 (a)~(e) 다섯 갈래를 명시했다. Claude 는 그중 넷에 대응하는 판단을 냈고, codex 는 **다섯 모두에 finding 을 내지 않았다.**

| focus 축①의 질문 | Claude 의 대응 판단 | codex |
|---|---|---|
| (a) 재탐색이 회수 못 하는 겹침 배치 | **N-05 — 구조상 닫힘**(원문·뷰 양 경로, 빈 매치 방어) | 무지적 |
| (b) lookbehind/lookahead 상호작용 | **N-12 에서 RRN 축을 구조적으로 분석**(재진입 가능 위치가 구분자 뒤뿐) | 무지적 |
| (c) 뷰 좌표 환원 | **N-07 — 좌표 결함은 없으나 경계 케이스 없음**(권고) | 무지적 |
| (d) 새 테스트가 실제로 무는가 | **N-08 — 이름이 재는 것보다 넓다**(입력 1건·방향만) | 무지적 |
| (e) 선형 성능 주장의 반례 | **N-09 — 반례 없음. 독립 측정으로 선형 확인** | 무지적 |

codex 산출물 §4.3 이 이 사실을 그대로 남겼다: *「트레이스를 보면 codex 는 `Masking.kt` 를 3회, `MaskingTest.kt` 를 3회 열람했고 입력 상한(4000)을 검색했으므로 범위 밖이라 못 본 것은 아니다. 다만 「검토한 결과 문제 없음」이라는 명시적 진술도 원문에 없다.」*

**따라서 (a)~(e)에 대해 codex 상태는 「안 함」이지 「검토함 — 지적 없음」이 아니다.** 원문에 그 진술이 없으므로 있다고 읽지 않는다. **codex 의 침묵을 「축 ① 무결」의 근거로 쓸 수 없다** — Claude 의 N-05·N-09 는 독립 검증이 붙은 해소 판정이므로 그 자체로 유효하지만, **「두 모델이 모두 문제없다고 봤다」로 승격되지는 않는다.**

### 6.2 fixture 공백(N-06)이 codex 시야 밖이었는가 — **focus 문면에는 없었다**

리더가 codex 에 준 focus 전문(codex 산출물 §2)을 다시 읽고 확인한 사실만 적는다.

- 축① 이 지목한 파일: `backend-kotlin/…/privacy/Masking.kt`, `backend-kotlin/…/privacy/MaskingTest.kt` — **둘 다 Kotlin 소스다.**
- 축② 가 지목한 파일: `.github/parity-full-gate.txt`, `compare_parity.py::full_gate_floor_problems`, `ParityDeclarationSyncTest.kt`.
- 축③ 이 지목한 파일: `compare_parity.py::check_contains_derived`·`_derive_title_markers`, `dump_parity_fixtures.py::build_export`.
- **`parity/fixtures/masking/masking.json` 은 focus 어느 축에도 등장하지 않는다.** 「masking fixture 에 이 회귀를 재는 케이스가 있는가」를 묻는 문장도 없다.

즉 **N-06 은 focus 문면이 지시한 검토 대상 밖이다** — 이것은 문서 대조로 확인되는 사실이다. 반면 **「그래서 codex 가 못 봤다」는 추정이므로 적지 않는다** (codex 는 지시받지 않은 것도 볼 수 있고, 실제로 축② 를 조사하며 `parity/fixtures` 를 열람한 트레이스가 있다 — §3.3 의 `rg -n '"id": "export-filename|"title"…' pari…`).

**N-06 이 Claude 에서 나온 경로**는 축의 교차다: 축②의 질문(「장치가 동작하는 것처럼 보이면서 아무것도 재지 않는 상태」)을 **masking 도메인에 던진 것**이 N-06 이다. focus 는 그 질문을 세 파일에 한정했고, Claude 는 도달 범위 점검(R-5)을 통해 도메인 쪽으로 옮겨 물었다.

### 6.3 비대칭의 처분

| 유형 | 해당 항목 | 기록 방식 |
|---|---|---|
| **focus 에 명시됐는데 지적 없음** | N-07(축①c) · N-08(축①d) · N-09(축①e) · N-18(축③c) · N-03(축③d) · R-9([부가확인]) | 표의 codex 열에 「안 함 (focus 축…에 명시됐으나 무지적)」으로 명시. **codex 의 무지적을 무결의 근거로 읽지 않는다** |
| **focus 문면 밖** | **N-06** · N-12 · N-13 · N-14 · N-20 · R-10 · §5(원장) | 표의 codex 열에 「안 함」. 사유 추정 없음 |

> **다음 회차 focus 에 대한 사실 기록(권고 아님, 판단은 리더)**: 위 표의 두 번째 행 7건이 전부 **Phase 2 종료 판정 전 마감** 또는 그에 준하는 항목인데, **codex 는 그중 어느 것도 지시받지 않았다.** 게이트 14 focus 를 짤 때 이 목록이 대조 대상이다.
