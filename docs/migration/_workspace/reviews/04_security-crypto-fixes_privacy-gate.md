### 0.1 먼저 정정한다 — 직전 산출물의 값 오류

직전 감사 `reviews/04_security_privacy-gate.md` §1 표의 **「고아 서로게이트 → U+FFFD 대체」는 틀린 값**이다.
실제 치환 문자는 **`?`(U+003F)**이고, **인코딩 시점**에 `String.getBytes(UTF_8)`(`CharsetEncoder` REPLACE)가
넣는다. U+FFFD 는 **디코딩** 시점 문자라 이 경로에서 나오지 않는다.
근거는 cross §4-② 의 JDK 21.0.4 직접 측정(`"x\uD800y"` → `78 3f 79` → `"x?y"`, `equals=false`)이고,
이번 배치의 `PlainBodyTest.UTF-8 왕복이 짝 없는 서로게이트를 잃는다` 가 **매 실행 재현**한다
(`assertThat(roundTripped).isEqualTo("x?y")`).

**원인 진단(「JVM 표준 동작이라 어떤 구현도 같다」)은 옳았고 기록된 값만 틀렸다.** 이 문서는 그 값을
다시 쓰지 않는다. 정정 대상 문서의 편집은 하지 않았다 — 심판 산출물을 사후 편집하지 않는다는 것이
게이트 25 판정 ① 이 세운 규율이고, 그 규율은 **자기 산출물에도 적용**된다. 여기에 정정을 남기고
`00_progress.md` §5-① 의 포인터가 이 문단을 가리키게 한다.

## 1. F-3 / X6 — 키 검사값(KCV) → **해제 (준수)**

### 1.1 「값이 틀린 32B 키」를 실제로 잡는가 → **잡는다**

독립 탐침(저장소 테스트를 거치지 않고 `CryptoConfiguration().contentCipher(...)` 를 직접 호출).

| 탐침 | 구성 | 결과 |
|---|---|---|
| **P1** | v1 자리에 **다른 32B 키**(K2), 설정 kcv 는 K1 의 것 | **기동 거부** — `ConfigurationException`, 「키 v1 의 kcv 가 설정값과 다르다 … 이 자리에 다른 키가 들어와 있다」 |
| P1b | 올바른 키 + 올바른 kcv | 조립 성공 |
| P1c | kcv 를 대문자 + 앞뒤 공백으로 | 조립 성공(정규화가 실제로 동작) |
| P3c | **쓰기 세대가 아닌 읽기 전용 세대**에 틀린 키 | **기동 거부** — 회전 중 옛 세대 자리를 잘못 채운 갈래도 닫힌다 |

직전 회차 F-3 이 「가장 위험」으로 든 시나리오(*"형식이 맞고 값이 틀린 키가 조용히 적재되고,
그 사이 쓴 행은 진짜 키로 열 수 없다"*)는 **기동 거부로 바뀌었다.** 한 건도 쓰기 전에 드러난다.

**KCV 자체의 성질** — 200,000개 무작위 32B 키에 대해 **충돌 0건 · 서로 다른 값 200,000개**,
같은 키 재료에 대해 결정적. 12자리 hex(48비트)에서 이 표본 크기의 기대 충돌은 ~3.5×10⁻⁵ 이므로
관측과 일치한다.

**음성 대조 M5** — `KeyCheckValue.matches` 를 무력화(`configured.isNotBlank() || computed.isBlank()`)하면
`CryptoStartupVerificationTest.F-3 오타 키 …` **단독으로 빨개진다**(`CryptoStartupVerificationTest.kt:85`).
컴파일 실패가 아니라 **의도한 단언의 실패**임을 확인했다.

### 1.2 KCV 값 자체가 키에 대해 무엇을 누설하는가 → **판정: 누설이 실무 위험을 만들지 않는다(준수)**

과제가 지목한 자리다. 실패 메시지가 실제로 무엇을 담는지 전문으로 캡처했다.

```
[kcv 불일치] … - 키 v1 의 kcv 가 설정값과 다르다(설정 <12hex> / 실제 <12hex>) — …
[kcv 없음]   … - 키 v1 에 kcv 가 없다. 이 키의 검사값은 <12hex> 다 — …
[쓰기 키 부재] … - 쓰기 세대 v1 의 키가 적재되지 않았다 (설정된 세대: []) — …
[깨진 재료]   … - 키 v1 의 값이 base64 32바이트가 아니다 — 이 세대는 실리지 않는다
```

**누설되는 것의 정확한 정의**: `KCV(K) = AES-256-GCM(K, nonce=0¹², aad="easydoc-kcv-v1", pt="")` 태그의
앞 6바이트. 즉 키에 대한 **결정적 48비트 함수값**이고, 구조적으로는 `E_K(J0) ⊕ GHASH_{E_K(0)}(aad)`의
절단이다 — **키 비트를 직접 담지 않는다.**

| 축 | 판정 | 근거 |
|---|---|---|
| 키 재료가 메시지·로그에 반향되는가 | **0건** | 6개 탐침(base64 전문 · base64 뒤 16자 · hex 전문 · hex 앞 16자, 두 키에 대해)을 **예외 메시지 4종 + 기동 로그 전량 캡처**에 대해 검사 — 전건 `present=false` |
| 키 공간 축소 | **없음** | 48비트 분할은 2²⁵⁶ 를 2²⁰⁸ 로 만들 뿐이다. 키는 `openssl rand -base64 32`(`.env.example`)라 저엔트로피 유도가 없다 |
| **오프라인 키 검증 oracle** | **성립하나 무해** | KCV 를 쥔 자는 암호문 없이 후보 키를 검증할 수 있다. 그러나 ⑴ 후보를 만들 방법이 없고 ⑵ 암호문을 쥔 자는 이미 같은 검증을 할 수 있다 |
| **키 동일성 연결(linkage)** | **성립 — 이것이 이 값의 기능이다** | 두 환경의 로그에 같은 KCV 가 있으면 같은 키다. 회전이 실제로 일어났는지도 드러난다. **이것이 F-3 을 닫는 수단 자체**이므로 대가로 받아들인다 |
| HTTP 응답으로 나가는가 | **나가지 않는다** | 이 메시지는 **빈 생성 시점**에만 만들어진다(`CryptoConfiguration.verify`). `@Bean` 이 eager singleton 이고 `@Lazy` 가 없으므로 컨텍스트가 뜨지 못하고, 따라서 `GlobalExceptionHandler` 의 `ConfigurationException → 503` 경로에 닿을 수 없다. 런타임에 나올 수 있는 유일한 crypto `ConfigurationException` 은 `MISSING_WRITE_KEY_MESSAGE`(「문서 암호화 키가 설정되어 있지 않습니다」)이고 여기엔 KCV 가 없다 |

**결론: 준수.** 다만 두 가지를 기록으로 남긴다 → **R-3**(운영 절차가 KCV 를 로그 경유로 배포한다).

| **음성 대조 M4** — `V4` 의 `ALTER TABLE … ADD CONSTRAINT` 두 줄을 제거 | 그 케이스 **단독으로 빨개진다**. 컴파일 오류가 아니라 단언 실패 |
| 도메인 정본의 단일화 | `EncryptedContent.KEY_VERSION_RANGE = 1..32767` 을 `CryptoConfiguration` 과 봉투가 함께 쓴다 — 값이 두 곳에 적히지 않는다 |
| 3중 방어 | 조립(기동 거부) → 봉투(`require`) → 스키마(`CHECK`). 앱을 거치지 않는 쓰기까지 마지막 방어선이 막는다 |

직전 회차가 실측한 「`key_version = -1` 이 **저장까지 성공**」은 닫혔다.

## 5. R-1 / X4 — AAD 2축 격리 → **해제 (준수)**. 직전 회차의 「아무도 재지 않았다」가 닫혔다

이 자리가 이번 배치의 **가장 중요한 해제**다. 직전 교차 종합 §5-② 가
*"109/109 는 「오늘의 거부」를, MUT-A·B 17/17 GREEN 은 「그 거부가 AAD 결속 때문이 아님」을 증명한다"* 로

이번 배치가 붙인 두 케이스가 그 자리를 정확히 겨눈다.

| 케이스 | 어떻게 다른 설명을 제거하는가 |
|---|---|
| `AAD 가 키 세대를 결속한다` | **두 세대에 같은 키 재료**를 넣는다. v1↔v2 의 키가 같으므로 「키가 달라서 실패」라는 설명이 사라지고, 세대 라벨만 v1→v2 로 바꿨을 때 남는 설명은 AAD 뿐이다. 대조군(같은 키니까 v2 봉투는 v2 로 열린다)이 그 전제를 함께 단언한다 |
| `AAD 가 방식과 키 세대를 싣는다` | 방식 축은 제품 경로로 잴 수 없다 — `decrypt` 의 이른 관문이 AAD 에 닿기 전에 끊는다. 그래서 **JCA 로 직접** 봉투를 열고 AAD 조각만 바꾼다 |

**음성 대조로 판정했다** — 두 축을 각각 AAD 에서 빼고 저장소 회귀를 돌렸다.

| 변조 | 결과 |
|---|---|
| **M1** — AAD 에서 `keyVersion` 제거 | **RED.** `I-7-5 AAD 가 **키 세대**를 결속한다 … (X4)` 가 `AesGcmContentCipherTest.kt:258` 에서 `AssertionError`. 함께 `AAD 문자열에 방식·키 세대가 실제로 실린다`·`표준 AES-256-GCM 으로 열린다` 도 빨개짐 |
| **M2** — AAD 에서 `scheme` 제거 | **RED.** `AAD 문자열에 방식·키 세대가 실제로 실린다 (X4)` + `표준 AES-256-GCM 으로 열린다` |

둘 다 **컴파일은 통과했고 의도한 단언에서 실패**했다. 직전 회차에 「MUT-B 17/17 GREEN」이던 자리가

## 6. X1 — 짝 없는 서로게이트 거부 → **준수**, 경계 하나를 기록

### 6.1 거부가 저장 경로 전체를 덮는가 → **Kotlin 호출자에 대해서는 덮는다**

`PlainBody` 는 `ContentCipher.encrypt` 의 **유일한 평문 입력 타입**이고, 저장 경로는
`PlainBody → encrypt → EncryptedContent` 하나다. 독립 탐침으로 정의역을 전수 확인했다.

| 입력 | 결과 |
|---|---|
| `x\uD800y` · `\uDC00` · `a\uDBFF` · `\uD800\uD800` · `ok\uD83D` · `\uDE00tail` | **전건 거부**(`InvalidInputException`) |
| 빈 값 · 한글 · 짝 맞는 이모지 · 공백 · BOM(U+FEFF) + 방향 제어(U+202E) | **전건 통과** — 거부가 BMP 밖 문자 전체로 번지지 않았다 |

**음성 대조 M7** — 거부 조건을 무력화하면 `PlainBodyTest` 의 두 케이스가 빨개진다.

**복호화 경로에 새 실패 갈래를 만들지 않는다** — `decrypt` 의 `PlainBody(String(opened, UTF_8))` 는
UTF-8 디코딩 산출물이라 짝 없는 서로게이트를 담을 수 없다. 즉 oracle 축을 건드리지 않는다.
조치 레인의 §2.1 서술과 일치하며, 코드로 확인했다.

### 6.2 사용자에게 어떤 응답으로 나가는가 → **422, 원문 조각 0**

- `InvalidInputException` → `GlobalExceptionHandler.mappingFor` → **422 `UNPROCESSABLE_ENTITY`**.
- 메시지는 고정 상수 `"문서 본문에 텍스트로 저장할 수 없는 문자가 있습니다"` **하나뿐**이고
  입력값도 위치(인덱스)도 담지 않는다. 회귀 `거부 문구가 입력을 담지 않는다` 가
  합성 개인정보(`"민원인 홍길동\uD800"`)를 넣고 `doesNotContain("홍길동")` 으로 단언한다.
- **위치 정보도 없다**는 점이 중요하다. 인덱스를 실으면 그 자체가 본문 구조에 대한 정보다.

### 6.3 우회 생성자·복사 경로 → **JVM 층에는 있다. 기록 R-5**

`@JvmInline value class` 의 알려진 성질을 리플렉션으로 확인했다.

```
PlainBody.constructor-impl(String)  public static -> String     ← init 실행(검사 있음)
PlainBody.box-impl(String)          public static final -> PlainBody  ← init 미실행
ContentCipher.encrypt-61yj8Sw(java.lang.String, UUID, EncryptedField)   ← 평문 자리가 String 으로 지워진다
ContentCipher.decrypt-bKW2k-Q(EncryptedContent, UUID, EncryptedField) : java.lang.String
```

실측: `box-impl("x\uD800y")` 는 **예외 없이** `PlainBody(3자)` 를 만들고 `getValue()` 가 원본과 같다.
즉 **가드는 Kotlin 컴파일러의 벽이지 JVM 의 벽이 아니다.** 역직렬화(Jackson 등)·Java 호출·리플렉션은
검사를 지나지 않는다.

**오늘 도달 0** — `PlainBody` 참조는 `crypto` 포트·어댑터·테스트뿐이고(§7), 제품 전 구간이 Kotlin이다.
**복사 경로는 없다** — `value class` 는 `data class` 가 아니므로 `copy()` 가 생성되지 않는다.
그래서 결함이 아니라 **경계의 정확한 기술**로 남긴다. `PlainBodyTest` 의 *"`PlainBody` 로 만들 수 있는
값이 곧 저장 왕복이 보장되는 값"* 은 **Kotlin 소스에서 만들 수 있는 값**으로 읽어야 참이다.

| `r.sendError(HttpURLConnection.HTTP_FORBIDDEN)` (한 줄) | miss | **BLOCK** ← 의도한 넓힘(H7) |
| `val label = "HTTP_403_FORBIDDEN"` | BLOCK(오탐) | **miss** ← 의도한 해소(H6) |
| **`.status(`⏎`    HttpStatus.FORBIDDEN,`⏎`)`** | **BLOCK** | **miss** ← **회귀** |
| **`return`⏎`    HttpStatus.FORBIDDEN`** | **BLOCK** | **miss** ← **회귀** |

**원인**: `_403_STATUS_SITE` 의 두 갈래가 모두 **인접성**을 요구한다 — ⓐ 는 호출 토큰 바로 뒤의 `(`,
ⓑ 는 `return`/`throw`/`->`/`=` 바로 뒤. 줄바꿈이 그 인접성을 끊는다. 논리 줄 결합기가
`.status( HttpStatus.FORBIDDEN )` 을 올바로 만들어 내는 것까지 확인했으므로 **결합기 문제가 아니라
규칙이 논리 줄을 보지 않는 문제**다.

**왜 중요한가**: 이 저장소는 `ktlintCheck` 를 CI 에서 강제하고, 제품 코드가 이미 이 형태로 쓰여 있다
(`AesGcmContentCipher.kt` 의 `logger.warn(`⏎`  "...",`⏎`  version,`⏎`)` 등 후행 쉼표 다중 줄 인자).
**즉 이 저장소의 표준 서식으로 쓴 소유권 403 이 BLOCK 규칙을 조용히 지나간다.**
마감이 「Phase 4 문서 소유권 경로 진입 전」인 항목이라 임박했다.

**그리고 이 잔여가 선언돼 있지 않다.** `OWNERSHIP_403_DECLARED_MISSES` 는 D1(계산값) · D2(응답 자리
밖 호출 인자) **둘뿐**이고, 줄바꿈 축이 없다. 커밋이 세운 장치의 취지(*"조용한 0 이 아니라 선언된 0"*)가
바로 이 자리에서 성립하지 않는다. 전수 리포트가 옛 판과 바이트 동일했던 것은 **현재 트리에 줄바꿈된
403 호출이 없기 때문**이라 회귀가 그것을 볼 수 없었다.

> **해제 조건 S-1**: 다음 중 하나. ⓐ `OWNERSHIP-403` 이 **논리 줄**을 보게 해 인접성 요구를 줄바꿈에
> 대해 무력화한다(결합기는 이미 올바른 문자열을 만든다). ⓑ 또는 줄바꿈 축을
> `OWNERSHIP_403_DECLARED_MISSES` 에 **xfail(strict) 로 선언**하고 그 근거를 적는다.
> 어느 쪽이든 위 표의 두 형태를 **형태 목록에 회귀로 고정**하고, 옛 판 대비 **양방향 대조**
> (새로 잡는 것 / 새로 놓치는 것)를 근거로 남긴다 — 이번 대조는 「새로 잡는 것」만 쟀다.
> 검증은 `privacy-gate` 가 같은 탐침(옛 판·새 판 동시 적재)으로 재측정한다.

### 10.2 **수정 필요 S-2 (낮음, 레인 = `kotlin-implementer`)** — 값이 **빈** 세대는 kcv 가 적혀 있어도 조용히 빠진다

`CryptoConfiguration.checkValueProblems` 가 `.filterNot { it.value.isBlank() }` 로 시작한다.
실측(독립 탐침 P3·P3b):

```
keys = [ v1(정상 키 + 정상 kcv),  v2(값 = 빈 문자열, kcv = 실제 v2 키의 검사값) ]
write-key-version = 1
→ 기동 성공. loadedKeyVersions = [1].  경고 0.  v2 는 조용히 사라진다.
```

**이것은 F-3 이 닫은 것과 같은 종류의 침묵이 읽기 방향으로 남은 것**이다. 회전 절차는
「새 세대를 더하고 쓰기 세대를 올린다, **옛 세대는 목록에 남긴다**」인데, 옛 세대의 환경변수가
비밀 저장소에서 빠지거나 오타로 비면 **앱은 정상 기동하고 옛 행 전량이 읽히지 않게 된다.**
증상은 첫 조회 때 `DecryptionFailedException` 이고, 그 사이 아무 신호가 없다.

**`kcv` 가 적혀 있다는 것은 「이 세대는 실재해야 한다」는 운영자의 명시적 선언**인데 그 선언이 무시된다.

빈 값을 관대히 넘기던 원래 근거(`application.yml` 의 `${EASYDOC_ENCRYPTION_KEY_V1:}` 자리표시자 때문에
개발 기동마다 빈 값이 들어온다)는 **이 배치로 이미 소멸했다** — 쓰기 세대가 비면 지금은 기동이
실패하므로, 자리표시자만으로 뜨는 개발 기동은 더 이상 존재하지 않는다. 즉 이 관대함이 지금 사는
유일한 자리가 **위 사고 시나리오**다.

> **해제 조건 S-2**: `kcv` 가 비어 있지 않은데 값이 빈 세대를 **기동 실패**로 올린다(또는 최소한
> 세대 번호만 실은 WARN). 회귀로 고정하고 **음성 대조**(그 판정을 되돌리면 빨개지는지)를 함께 남긴다.
> 값도 kcv 도 둘 다 빈 세대를 어떻게 볼지는 함께 정해 근거를 적는다 — 「선언만 있고 아무 내용이 없는
> 세대」를 허용할지의 문제다. 검증은 `privacy-gate` 가 같은 탐침(P3)으로 재측정한다.
