## 3. 충돌·갈림 항목 — 양쪽 근거 전문 병기 (리더 판단 요청)

> 표의 한 칸에 요약하면 근거가 잘려 판단이 불가능해진다. **어느 쪽도 삭제하지 않았다.**

### 3-1. X-1 — 삭제된 계정의 유효 토큰 (4관점 합의, 심각도 4갈래)

**사실은 네 관점이 같다.** 유효 토큰 + `users` 행 부재 상태에서:

| 경로 | 응답 | 관측한 관점 |
|---|---|---|
| `GET /auth/me` | **401** | privacy-gate |
| `GET /workspaces` | **200** `{"items":[]}` | privacy-gate |
| `POST /workspaces` | **500** (사용자 FK 위반) | codex(정적) · privacy-gate(실측) · 구현 산출물 미결 ⑥ |
| `PATCH` · `DELETE` | **404** | codex(정적) · privacy-gate(실측) |

**심각도가 갈린 네 근거.**

- **codex #1 — high, "NO-SHIP" 사유의 하나.**
  > *"계약 easy-doc-v1.yaml:299-302,1484-1492의 계정 삭제도 동일한 401이라는 요구와 정면으로 충돌한다.
  > SQL·스택은 고정 오류 본문 때문에 노출되지 않지만 **폐기된 자격증명이 승인되고 삭제 여부가 상태
  > 코드로 구분된다.**"*
  > 처방: *"모든 보호 요청에서 JWT 검증 직후 사용자 존재를 확인하고, 삭제 계정은 컨트롤러 진입 전에
  > 무효 토큰과 동일한 401·본문·헤더로 종료하라."*
- **contract-keeper ⑻ — 계약 미충족(차단 아님).**
  > *"`x-auth.failure_uniformity`(`:299-302`)가 **계정 삭제를 401 사유로 명시 열거한다** — 이메일 부재·
  > 비밀번호 불일치·토큰 만료·위조와 **같은 줄에서**. 그리고 이 열거는 `/auth/me` 절이 아니라 최상위
  > `x-auth` 아래 있다. … 「계정 삭제」를 별도 항목으로 세운 것은 **토큰이 아직 유효한 요청 시점**을
  > 가리킬 때만 뜻이 있다."*
  > 차단하지 않는 근거 셋: ⑴ 이 배치가 만든 결함이 아니라 **auth 단위부터 있던 미도달**, ⑵ 계정 열거
  > 위험 없음(그 사용자의 유효 토큰을 이미 가진 자만 도달), ⑶ 고치는 **방향이 구현 판단**이다.
  > 리더 통보: **"Phase 4 전에 인증 경계에서 닫기를 권고 — 그대로 두면 문서 API 에서 같은 형태가 반복된다."**
- **privacy-gate R-3 — 기록(차단 아님), 조건부.**
  > *"⑴ 교차 사용자 노출이 아니다 … ⑵ 500 본문이 고정 문구라 정보 유출이 0 이다. ⑶ **계약에 계정 삭제
  > 엔드포인트가 없다** — 현재 이 상태는 DB 직접 조작으로만 만들어지므로 도달 경로가 제품에 없다."*
  > **조건**: *"계정 삭제 기능이 들어오는 순간 이것은 「탈퇴한 계정이 토큰 수명(60분)까지 API 를 일부
  > 쓴다」는 실제 인가 결함이 된다. **계정 삭제 기능 커밋과 같은 단위에서 해소**할 것을 조건으로 건다."*
  > privacy-gate 는 **계약 해석을 「양쪽 병기」로 남겼다** — 위반 쪽/위반 아님 쪽 둘 다 적었다.
- **Claude J-4 — 판정 필요.** *"계약이 그 오퍼레이션에 `InternalError` 를 선언하므로 **계약 위반은 아니다**
  … **오늘 도달 0** — 계정 삭제 엔드포인트가 존재하지 않는다."* 마감: 계정 삭제 경로가 생기는 단위.

**제3의 근거 — 계약 문면 직접 대조(이 회차가 확인, 어느 쪽도 지우지 않는다).**

`contracts/easy-doc-v1.yaml:299-302`(`x-auth.failure_uniformity`):

```
failure_uniformity: |
  이메일 부재·비밀번호 불일치·토큰 만료·위조·계정 삭제를 **모두 같은 401과 같은
  메시지**로 처리한다. 구분하면 계정 열거 공격의 단서가 된다.
```

`:1484-1492`(`components/responses/Unauthorized.description`):

```
인증 실패. **헤더 누락·토큰 위조·만료·용도 불일치·계정 삭제를 모두 같은 401,
같은 메시지로 처리한다**
```

**세 가지 사실.**
1. **codex 의 인용은 두 자리 모두 문면 그대로다** — 전제 오류가 없다(§4.4 가 남긴 확인 요청 #1 종결).
2. **`:299-302` 는 `x-` 확장 절이다.** contract-keeper 가 escalate ④·O-8 에서 다투는 「`components/responses/*.description`
   의 원인 열거가 규범인가 서술인가」 논쟁에 **이 건은 걸리지 않는다** — `:1484-1492` 를 빼고 `:299-302`
   하나만으로도 요구가 선다. Claude J-4 가 근거로 든 「`InternalError` 선언」은 **응답 목록 쪽**이고,
   `x-auth` 의 조건 열거와 **다른 자리**다. 두 근거가 같은 층에서 부딪히지 않는다.
3. **Claude J-4 의 「계약 위반은 아니다」는 `x-auth` 를 보지 않은 상태의 판단이다.** contract-keeper 가 같은
   자리를 계약 소유자 권한으로 정정했다(§10 통보: *"등재를 「침묵」에서 **「계약 미충족(미도달)」**으로 바꿔라"*).
   **계약 준수 축의 채점 기준은 contract-keeper 다** — 이 항목에서 Claude 의 계약 해석은 유지하지 않는다.

**→ 리더 판단 요청.** ⑴ 심각도를 codex 의 high(= 배포 전 차단)로 볼 것인가, contract-keeper·privacy-gate 의
「계약 미충족 · 조건부 기록」으로 볼 것인가. ⑵ 마감이 **Phase 4 착수 전**(contract-keeper)인가
**계정 삭제 기능 단위**(privacy-gate)인가 — **두 마감이 다르다.** ⑶ 처방의 형태(인터셉터에서 매 요청 사용자
존재 확인 vs 쓰기 경로 FK 위반을 401 로 이관)는 **구현 판단**이라고 세 관점이 일치한다.

### 3-2. X-2 — 정책 값 복제 (사실 합의 · 결론 충돌)

**사실은 갈리지 않는다.** 이 회차가 파일을 열어 확인했다 — `WorkspaceNameRules.kt`:

```kotlin
/** 정규화 후 이름 길이 상한. 계약 `x-request-field-constraints.fields[4].limit`. */
private const val MAX_WORKSPACE_NAME_LENGTH = 50
...
/** 상한 초과 문구. 같은 자리의 **두 번째** 값이자 `examples.too_long` 이다. */
private const val NAME_TOO_LONG_MESSAGE = "작업 공간 이름은 50자 이하여야 합니다"
```

값 `50` 이 **두 번**(상수 + 문구 안), `detail` 문구 두 종이 애플리케이션 코드에 있다.
Claude F-1 과 codex #2 는 **같은 사실을 봤다.** 갈리는 것은 그 사실의 뜻이다.

- **codex #2 — high.**
  > *"N-11 변이는 불일치를 **탐지할 뿐** 구현이 계약을 소비하게 만들지 않으므로, **계약 파일 하나가
  > 정본이라는 필수 조건을 만족하지 않는다.**"*
  > 처방: *"YAML 에서 빌드 시 타입 안전한 정책 산출물을 생성하거나 infrastructure 에서 파싱·검증한 값을
  > application/api 에 주입하라. 구현과 테스트의 상한·문구·헤더·경로 변수 리터럴을 제거하고 **계약 변경
  > 하나만으로 런타임 값이 바뀌는지**를 검증하라."*
- **Claude F-1 — 수정 필요(문면만).**
  > *"변이가 빨강이 된 것은 **테스트의 기대값이** 코드가 아니라 계약에서 오기 때문이지, 코드에 복제가
  > 없어서가 아니다(프로덕션 코드가 런타임에 YAML 을 읽지 않는 이상 복제는 불가피하고, 그 복제를 **계약과
  > 묶어 두는 것**이 테스트의 일이다). **기제 자체는 옳다** — 계약을 60으로 바꾸면 테스트가 빨개져 구현을
  > 따라오게 만든다."* 고칠 것은 산출물의 판정 **문구**다.
- **contract-keeper ⑴ — 하드코딩 0.** 대상이 **테스트 코드**다: *"코드에 남은 문자열 두 자리… 상태 코드 상수 /
  예시 **이름**. **이름이지 값이 아니다.**"* 구현 코드의 상수는 이 판정의 대상이 아니었다.

**제3의 근거 — 「값을 옮겨 적지 않는다」 규약의 선언 범위(이 회차 확인).**

`03_contract-keeper_workspaces-test-spec.md` §0:

```
**상한의 숫자, `detail` 문구, 헤더 값 문자열, … 이 문서에 적지 않는다.**
**이 규약의 도달 범위 — 이 문서 전체다.** 표·산문·각주를 가리지 않는다.
```

§1 범위 표: `단언해야 할 **나간 바이트** | 그것을 어떻게 내는가`(오른쪽 = 범위 **밖**).

**즉 명세의 규약은 자기 문서와 테스트 기대값을 대상으로 선언됐고, 프로덕션 구현 코드까지 선언한 적이
없다.** 반면 codex 에게 준 focus text 의 채점 조건 4번은 *"상한… 은 계약에서 읽어야 하고 **코드·테스트에
복제돼 있으면 안 된다**"* 로 **구현 코드를 포함해** 적혔다. **codex 는 주어진 기준을 정확히 적용했다** —
codex 의 잘못이 아니라 **기준의 범위가 두 문서에서 다르다.**

**→ 리더 판단 요청.** 「계약이 정본」의 강제 범위가 **테스트 기대값까지**인가, **런타임 값까지**인가.
- 테스트까지로 정하면: X-2 는 Claude F-1(문면 정정)로 닫히고, **X-2a·X-2b 는 남는다**(테스트 기대값이
  계약을 안 거치는 자리 = A-5, 헤더 값은 테스트가 아니라 구현이므로 제외).
- 런타임까지로 정하면: codex 처방(빌드 시 생성/주입)이 서고 **blast radius 가 auth·workspaces 전역**이다 —
  이 판정은 Phase 4 문서 API 의 상한 6종에 곧바로 걸리므로 **Phase 3 종료 전에 정해야 비용이 가장 싸다.**

### 3-3. X-3 — 시간 채널 문턱 2.0 (충돌) + 음성 대조 부재 (codex 단독) — **두 축이다**

리더 지시대로 **문턱의 적정성**과 **실측값**이 별개 축임을 명시한다. 두 관점은 같은 것을 말하고 있지 않다.

**축 ⓐ — 실측값(구현이 지금 시간을 흘리는가).** 세 관점이 같은 방향이다.

| 관점 | 측정 | 비 |
|---|---|---|
| 구현 산출물 | (자기 보고) | 1.031 |
| **Claude(독립)** | 없음 2.400ms / 타인 2.247ms | **1.068** |
| **privacy-gate(독립, HTTP 경계 원시 소켓, 41×2, 워밍업 10, 고정 시드)** | PATCH 1.645/1.581 · DELETE 1.342/1.351 | **1.041 / 1.007** |

**세 측정이 전부 문턱(2.0) 한참 아래이고 서로 다른 하네스에서 나왔다.** 소유 조건이 SQL `WHERE` 에 있어
두 갈래가 **같은 질의 한 번**을 돈다는 구조적 근거와 정합한다(X-29 합의). **codex 는 이 축을 재지 못했다** —
Gradle 미실행(§5). codex 자신도 *"현재 SQL 소유 조건 자체는 안전해 보이지만"* 이라고 적었다.

**축 ⓑ — 문턱의 적정성(게이트가 무엇을 잡는가).** 여기서 갈린다.

- **codex #3 — high.**
  > *"테스트는 경로당 21표본의 중앙값 비율이 2.0 미만이면 통과한다. 공격자는 **반복 평균으로 훨씬 작은
  > 지속 격차도 증폭**할 수 있는데, 이 게이트는 **10~90% 차이를 모두 승인**한다. … **시간까지 은닉한다는
  > 선언을 이 테스트가 보장하지 못한다.**"*

### 3-4. X-4 — 파서 fail-open (충돌이 아니다 — 대상이 다르다)

  진짜 위반이 새 빨강과 구분되지 않는다.**

**「이미 오탐 판정」 문구가 CI 도달을 가린 경위 — 세 게이트의 기록을 그대로 잇는다.**

| 게이트 | 실행 명령 | 기록된 종료 코드 | 기록된 문장 |
|---|---|---|---|
| **20** | `… --changed --base 05862fa **--no-fail**` | `REAL_EXIT=0` | *"`--no-fail` 없이는 exit 1 이 됐겠지만 **실질 BLOCK 은 0** 이다"* |
| **21** | `… --changed --base bf08edd` | **`REAL_EXIT=1`** | *"BLOCK 1건은 게이트 20 에서 **이미 오탐**으로 판정한 그 자리다… **판정 유지: 오탐.**"* |
| **22** | `… --changed --base d04ad98` | **`REAL_EXIT=1`** | *"BLOCK 7건 **전부 오탐**이다"* |

`.github/workflows/ci.yml:98-104` 는 **정확히 그 반대를 선언한다**:

```
# `--no-fail` 을 붙이지 않는다: 붙이면 BLOCK 후보가 있어도 초록이라 게이트가 장식이 된다.
- name: 데이터 보호 불변식 스캔 (BLOCK 후보 0건 유지)
  run: uv run python .claude/skills/migration-safety-gate/scripts/scan_privacy_invariants.py
```

**경위는 이렇다.** ⑴ 게이트 20 이 `--no-fail` 로 재서 종료 코드를 0 으로 만들고 「실질 0」이라 적었다 —
**CI 가 도는 명령과 다른 명령으로 쟀다**(대리 경로 측정). ⑵ 게이트 21·22 는 `--no-fail` 없이 재서
**exit 1 을 정확히 기록**했지만, 판정을 「오탐」으로 닫고 **그 종료 코드가 CI 스텝에서 무엇을 하는지 묻지
않았다.** ⑶ 스텝 이름이 「BLOCK **후보** 0건 유지」인데 판정은 「**실질** BLOCK 0」이었다 — **게이트가 세는
것은 후보이고 감사가 센 것은 실질이라, 같은 단어의 다른 뜻이 세 회차를 통과했다.** ⑷ CI 실행 자체를 본
관점이 세 게이트 동안 **0** 이었다(원장 「Phase 3 auth 단위」 §6 사실 ⑨: *"CI 원격 캐시 거동은 이번에도
0관점"*). **이 회차가 그 0관점을 끊었고, 끊자마자 red 가 나왔다.**

**codex 가 이 축을 보지 않은 것은 사실이다** — codex 실행 셸 명령 123건에 `gh` 호출이 없고, codex 산출물
어디에도 CI 실행 관측이 없다. **짐작을 붙이지 않는다.**

**처방은 이 문서의 몫이 아니다.** `privacy-gate` 별도 레인이 진행 중이다. **다만 방향 하나는 이미 정해져 있다** —
`CLAUDE.md` 규칙 4: **은폐형(무시 패턴·억제·면제 조항)은 ⑴이 참이어도 넓히지 않는다 — 탐지형으로 갈아탄다.**
`OWNERSHIP-403` 은 「403 을 **기대하지 않는다**」는 단언까지 잡는 **구조적** 오탐이므로 무시 목록이 아니라
규칙 자신의 정밀도(문맥 인식)로 닫는 것이 이 하네스의 규약이다.

**→ 리더 판단 요청.** X-9 는 **차단 ②장치**이고 마감은 **즉시**다. 「아직 이 단위가 push 되지 않았으니
당장은 아니다」로 낮추지 않는다 — **이미 실사용 중인 게이트가 지금 red 다.** 착수 차단 여부의 판정은 리더 몫이다.

### 7-2. 그럼에도 열려 있는 것 — 착수 판단에 직접 걸리는 세 가지

1. **X-9 (차단 ②장치, 즉시).** 데이터 보호 불변식의 **기계 탐지선이 red 이고**, 그 red 가
   **스캐너 자신의 회귀 · parity 게이트 회귀 · 하네스 도달 검사 · Python 전체 스위트**를 함께 껐다.
   `codex-review` §5 판단 규칙 5: **Critical 이 하나라도 남으면 Phase 종료를 보고하지 않는다.**
   처방은 다른 레인에서 진행 중이며, **다음 단위의 코드가 이 상태 위에 쌓이면 그 코드도 스캔을 받지 못한다.**
2. **X-2 범위 판정(리더).** Phase 4 문서 API 는 상한이 **6종**(`max_convertible_chars`·`max_review_chars`·
   `max_upload_bytes`·`max_extracted_chars`·`zip_uncompressed_budget_bytes` 등)이다. 「계약이 정본」의
   강제 범위를 **Phase 4 착수 후**에 런타임까지로 정하면 그 6종을 **다시 짜야 한다.** 지금 정하면 한 자리다.
3. **X-1 마감 갈림(리더).** contract-keeper 「Phase 4 전」 vs privacy-gate 「계정 삭제 단위」.
   **Phase 4 는 사용자 FK 를 가진 쓰기 경로를 여섯 자리 더 만든다**(contract-keeper §8-4). 마감을
   뒤로 미루면 같은 형태가 여섯 개로 늘어난 뒤에 고치게 된다.

### 7-3. 착수 판단을 **가르지 않는** 사실 (오독 방지)

- **이 단위는 아직 push 되지 않았다**(원격 HEAD `6fe4357`). **X-9 의 red 는 이 단위 때문이 아니다** —
  base `d04ad98` 에서도 BLOCK 1건·exit 1 이었다. 이 단위는 그 수를 1 → 8 로 **늘렸을 뿐** red 를 만들지 않았다.
- **codex 지적 8건 전부가 정적이다.** 「실행으로 반박됐다」고 적을 수 있는 것은 **X-3ⓐ 하나뿐**이고,
  나머지 일곱은 실행이 닿는 대상이 아니거나(장치 설계) 아직 아무도 재지 않았다.

  내리지 않으며, 판정은 리더의 몫이다(`codex-review` 범위 밖 조항).

### 8-2. 종합 중 발견 — **미교차** (정본 판정 대상 아님 · 다음 회차 범위로 제안)

> 아래는 **어느 리뷰에도 없던 것**이라 교차 검증을 거치지 않았다. `..._cross.md` 본문 교차표에 넣지 않고

  (`ErrorProbeController.kt:205`, `sendError`·`ServletException` 경로에서만 주입), `ContainerRejectedRequest`
  6종의 원시 요청에는 그 표식이 **없다.** 따라서 그 여섯 케이스에서 「입력 비반사」 단언은 **검사 대상 0건인
  채 통과**한다. 나머지 셋(상태 코드 · `application/json` · 최상위 키 `detail` 하나)은 실질 검사가 맞다.
  **X-5 의 「6종 전건 측정」 서술을 다듬을 때 함께 볼 자리다** — 「6종을 쟀다」가 「네 성질을 다 쟀다」로
  읽히면 안 된다. 축: 도달 범위(계약 준수).

- **`x-changelog` 면제 조항의 형태.** `4a25a7c` 는 *"`x-changelog` 의 옛 항목은 고치지 않았다"* 를
  **면제 조항으로 적었다.** 근거(사후 편집하면 판정 근거가 사라진다)는 타당하지만, `CLAUDE.md` 규칙 4의

  날짜 스탬프)로 제외하는 방식. 축: 도달 범위(계약 준수). **contract-keeper 회부 제안.**
