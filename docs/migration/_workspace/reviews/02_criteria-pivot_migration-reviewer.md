#### A-2. `test_schema.py` 병합은 옛 검사 B보다 강하지만 옛 검사 A를 대체하지 않는다 · **medium / 수정 필요** · 마감 Phase 2 종료

작성자 주장("합성 집합이 전 범주를 덮으면 골든셋 전체도 덮으므로 옛 검사보다 좁아지지 않는다", `tests/golden/test_schema.py:165-166`)을 그대로 받지 않고 직접 따졌다.

병합 전 두 검사:
- **A** `test_합성_문서에는_합성_개인정보가_들어_있다` — 합성 문서 **하나하나**가 마스킹 대상을 가질 것
- **B** `test_마스킹_범주_전체가_골든셋에_등장한다` — **전체 문서**의 범주 합집합 == `set(MaskCategory)`

병합 후 하나(`test_schema.py:157`):
- **C** — **합성 문서**의 범주 합집합 == `set(MaskCategory)`

**[독해] C ⟹ B는 참이다.** C가 세는 집합은 B가 세는 집합의 부분집합이므로, 부분집합이 전체 범주를 덮으면 상위집합도 덮는다. **[실행 E3]** 실측도 일치한다 — 합성만의 커버리지와 전체 커버리지가 둘 다 `{주민등록번호, 카드번호}`이고, 실수집 36건은 **0건** 기여한다. 즉 이 축에서는 주장대로 **strictly stronger**다. 확인했다.

**그러나 C는 A를 함의하지 않고, A의 보장은 어디로도 가지 않았다.** A는 "합성 문서마다 PII가 있다"이고 C는 "합성 집합 전체가 전 범주를 덮는다"이다. 문서 2건이 C를 만족시킨다.

**[실행 E3·E4] 그 결과를 측정했다:**

| | 마스킹 항목 수(56문서) | PII 보유 합성문서 | PII 보유 실수집문서 |
|---|---|---|---|
| 축소 전(5종) | **31** | 20/20 | 0/36 |
| 축소 후(2종) | **2** | **2/20** (`003`, `011`) | 0/36 |

골든셋 계층이 마스킹 파이프라인을 실제로 태우는 횟수가 **31 → 2**로 떨어졌다. 모듈 docstring이 이 검사군의 존재 이유로 든 "마스킹 파이프라인 회귀를 잡으려면 개인정보가 든 문서가 필요하다"(`test_schema.py:158`)가 문서 2건에 걸려 있다.

**남아 있는 하한은 있다** — C가 범주별 최소 1건을 강제하므로 `003`이나 `011`에서 PII가 빠지면 잡힌다. **[독해]** 그 점에서 보장이 0이 된 것은 아니다.

**지적의 핵심은 다음 한 줄이다.** 커밋 메시지의 "**더 강한 대체 없이 사라진 테스트는 없다**"는 A에 대해 성립하지 않는다. A는 대체 없이 사라졌고, 대체된 C는 B보다만 강하다. 완료 보고에 쓰인 문장이라 그대로 두면 다음 회차가 "검증됐다"로 인용한다.

**요청**: (a) A의 보장이 2종 체제에서 더는 의미가 없다는 판단이면 그 판단을 테스트 파일이 아니라 인벤토리(A-1)에 `폐기` 사유로 남길 것, (b) 골든 계층의 마스킹 노출 하한(현재 2건)을 의도한 수치로 기록할 것.

#### A-3. 양성 케이스의 **정확 출력** 단언이 사라졌다 — 경계 과잉 잠식을 잡을 수단이 없다 · **medium / 수정 필요** · 마감 Phase 2 (Kotlin masking 포팅)

삭제된 `test_이메일에_붙은_조사와_마침표는_보존된다`는 유일하게 **치환이 일어난 상태의 출력 전문**을 단언했다:

```python
assert result.masked_text == "[[이메일1]]으로 회신 바랍니다."
```

**[실행]** 현재 `tests/privacy/test_masking.py`에서 `masked_text ==` 단언은 5곳뿐이고 **전부 음성 케이스**(`== text`, 아무것도 안 가려진 경우)다. RRN·CARD가 실제로 치환된 뒤 주변 본문·조사·구두점이 정확히 보존되는지를 문자열 전체로 확인하는 단언은 **하나도 없다**.

**[독해] `restores_input`은 이것을 대체하지 못한다.** 역치환은 `original`을 도로 꽂으므로, 마스킹이 조사까지 삼켰더라도 복원 결과는 입력과 같아진다. 과잉 잠식은 이 성질을 통과한다. 이는 비교기 `check_restores_input`(`compare_parity.py:439-479`)에도 그대로 해당한다.

**왜 parity에서 문제인가.** Kotlin이 내야 하는 것은 `masked_text` **문자열 그 자체**다. RRN 패턴에는 `[ \t]*`가 두 군데 있어(`masking.py:57`) 구분자 주변 공백을 흡수하는데, 새로 추가된 `test_구분자_주변_공백_표기도_마스킹된다`는 `rrn not in masked_text`와 범주만 보고 출력 전문은 보지 않는다. 공백을 한 칸 더 먹거나 덜 먹는 Kotlin 구현이 Python 단위 테스트·parity 단언 양쪽을 통과한다.

**요청**: `kotlin-implementer`에게 — RRN·CARD 각 1건에 대해 `masked_text == "…[[주민등록번호1]]으로…"` 형태의 정확 출력 단언을 추가. 아울러 `parity-verifier`에게 — masking fixture에 `equals_field`(path=`masked_text`) 단언 최소 2건 추가 검토(현재 masking 도메인은 `absent`/`present`/`restores_input`/`placeholder_scheme` 4종뿐, **[실행 E6]**).

### 축 B — parity 위험

#### B-1. `--record-reference` 한 플래그가 갈림 전건을 통과로 바꾸고, **정상 실행과 같은 종료 코드를 낸다** · **high / 차단 ②** · 마감 **Phase 2 parity 게이트 첫 실사용**

**[실행 E9]** 요구 성질은 전부 지키되 Python 참고값과 갈리는 산출물을 만들어 3회 실행했다:

| 실행 | 종료 코드 | 「기록되지 않은 참고 갈림」 보고 |
|---|---|---|
| 플래그 없음 | **1** | **23건** |
| `--record-reference` 추가 | **3** | 0 (같은 실행이 원장에 23건 기록) |
| 다시 플래그 없이 | **3** | 0 |

즉 **갈림 23건을 방금 침묵시킨 실행과 애초에 갈림이 0건이던 실행이 같은 종료 코드 3을 낸다.**

**[독해] 이것은 이 파일이 스스로 세운 원칙을 어긴다.** `compare_parity.py:104-105`가 부분 검증에 0 대신 3을 준 이유로 든 논거가 정확히 이것이다:

> **왜 0이 아닌가.** 종료 코드는 자동화가 읽는 유일한 계약이다. stdout에 찍히는 "게이트를 닫는 근거가 아니다"는 사람이 읽을 때만 유효하고, CI·에이전트는 exit code로 판정한다.

`--record-reference`가 찍는 `[원장 기록] … 갈림 23건`(`compare_parity.py:1502`)은 바로 그 "사람이 읽을 때만 유효한 stdout"이다. 같은 논거를 자기 자신에게 적용하지 않았다.

**현재 노출도는 낮다.** **[실행 E12]** CI는 이 플래그를 주지 않는다(ci.yml:293-294, 311-312). `02_parity-rebase.md:251`도 "CI에 `--record-reference`를 주지 않는다는 점 확인"을 리더/CI 소유자 항목으로 올려 두었다.

**그럼에도 차단 ②로 올리는 이유**: 이 하네스는 **에이전트가 명령을 조립해 돌린다**. 그리고 에이전트용 문서가 그 조립을 직접 지시한다 —

#### B-2. spec 구조 검사가 **검사 이름**만 보고 **내용**은 보지 않는다 — 잠재 무력화 3경로 · **medium / 수정 필요** · 마감 Phase 2 종료

`spec_shape_problems`(`compare_parity.py:796-833`)는 도메인마다 `under`·`over` 방향이 둘 다 있는지를 **`CHECKS[name].directions`로만** 판정한다. 다음 셋이 구조 검사를 통과한다:

1. **빈 needle 단언** — `{"check": "absent", "args": {}}`는 `call.arg("needles", [])`가 빈 목록이라 무조건 `[]`를 반환하는데(`compare_parity.py:421`), `directions`에는 `under`를 채워 넣는다. **아무것도 재지 않으면서 방향 가드를 만족시킨다.**
2. **`reference` 없는 케이스** — `compare_parity.py:1245`가 `"reference" not in case`면 조용히 `continue`한다. 참고 갈림 원장에 오르지 않고 아무 보고도 없다. `reference` 존재를 요구하는 구조 검사가 없다.
3. **`reference_divergence: "expected"` 선언** — 갈렸을 때 `continue`로 원장 기록 자체를 건너뛴다(`compare_parity.py:1255-1264`). 즉 **원장은 갈림의 완전한 목록이 아니다.** 모듈 docstring의 "갈린 자리를 기록하며, 기록되지 않은 갈림은 코드 1"(`compare_parity.py:11-18`)에는 이 예외가 적혀 있지 않다.
4. **방향 가드의 입도** — 가드가 **도메인 단위**라 케이스 A가 `absent`만, 케이스 B가 `present`만 가져도 도메인은 통과한다. 케이스별 양방향은 생성기 쪽 관행에 달려 있다.

**[실행 E6] 현재 masking fixture에는 이 셋이 하나도 없다** — 빈 needle 0건, `reference` 결손 0건, `reference_divergence` 0건. **지금 뚫린 구멍이 아니라 뚫릴 수 있는 문이다.**

**[독해] 공통 뿌리**: 이 커밋으로 "생성기 diff를 사람이 읽어야만 지켜지는 것"의 목록이 크게 늘었다 — `mode`, `spec_status`, `assert` 목록, `reference` 존재, `reference_divergence` 선언, `required_cases`. 비교기 docstring이 이를 "보장하지 못한다 (b) 정본 생성기 자체의 위조"로 정직하게 공시하고는 있으나(`compare_parity.py:65-66`), 공시 범위가 커지면 공시의 실효가 떨어진다.

**요청**: `spec_shape_problems`에 내용 검사 추가 — ① `absent`/`present`/`contains_all`의 인자가 비면 결함, ② spec 케이스에 `reference` 필수, ③ `reference_divergence`가 붙은 케이스도 원장에 `status: declared`로 남기기.

**왜 high인가.** 이것은 설명문이 아니라 **합격 기준을 적은 검증 절차**다. 절차대로 돌린 사람은 단언 81개를 보고 "23건 중 무언가 빠졌다"고 판단해 fixture를 손보거나, 갈림 3건이 없는 것을 이상 징후로 오인한다. `02_parity-rebase.md:140`에도 같은 `reference_divergence` 서술이 남아 있다.

**커밋 메시지는 89↔81 불일치를 알고 있었다**("명세 문서의 '단언 89개'는 실제 81과 어긋난다 … 문서 쪽이 낡았다"). 알면서 커밋 메시지에만 적고 **문서는 고치지 않았다.** 커밋 메시지는 그 문서를 여는 사람이 읽지 않는 자리다.

#### E-2. 변경 대상 밖 코드에 남은 낡은 서술 2건 · **medium / 수정 필요** · 마감 Phase 2 종료
