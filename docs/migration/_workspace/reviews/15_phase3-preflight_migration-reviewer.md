### 축 2 — parity 위험

#### P-A · 스냅샷 생성기가 **케이스 삭제를 탐지하지 못한다** — **차단(② 장치)** · 마감 **`app/**` 삭제 전**

X-9 의 산출물 `dump_python_snapshots.py` 는 기존 스냅샷을 **케이스 원장으로 읽고 출력만 다시 계산**한다(`.claude/skills/migration-safety-gate/scripts/dump_python_snapshots.py:197-211`). 그래서 케이스를 덜어 낸 스냅샷을 넣으면 그 축소분을 그대로 재생산하고 **diff 0 을 보고한다.**

**실측** (파일을 건드리지 않고 순수 함수만 호출):

```
원본 케이스 수: system_prompts 6 · user_prompts 5 · repair_prompts 5 · postprocess 29  (합 45)
축소 케이스 수: 각 1                                                                    (합  4)
>>> 축소된 스냅샷을 입력으로 재생성했을 때 diff 0 인가: True
>>> 즉 --check 는 케이스 삭제를 탐지하지 못한다
```

스타일 쪽도 같은 자리가 하나 있다. 파생 키 `GLOSS_COLLISION_PATTERN_GLOSSES`(**123 항목**)는 `if derived in previous:` 조건부로만 다시 만들어지므로(`:132-141`), 그 한 키를 지운 스냅샷은 재생성 diff 0 이다 — 실측 확인. 나머지 12개 상수는 `STYLE_CONSTANTS` 고정 튜플(`:60-75`)이 끊어 준다.

**왜 차단 ② 인가.**

1. 스냅샷은 이 하네스가 스스로 **"Kotlin 포팅 판정의 정본"** 이라 부르는 증거 파일이다(스크립트 docstring `:6-8`). 그 증거가 **축소로 위조 가능**하고 검사기가 "[일치] — 키 20개"를 찍는다. 최상위 키 수는 20 그대로라 개수 축에도 안 걸린다.
2. 스크립트 자신의 docstring `:29-30` 이 정확히 이 실패를 이름 붙였다 — *"조용히 빠뜨리고 나머지만 쓰면 그 순간 스냅샷이 줄어들고, 줄어든 스냅샷은 Kotlin 검사를 통과시킨다."* **상수 이름 축은 `SnapshotError` 로 끊었는데 케이스 축은 끊지 않았다.** 큐레이션 값 45건이 그 축에 산다.
3. **옳은 패턴이 같은 배치 안에 이미 있다.** `compare_parity.py:1680-1699` 의 `provenance_problems` 는 정본을 다시 만들어 `missing`·`extra`·**순서**까지 전부 잡고, `42f9e20` 이 그것을 회귀로 고정했다(`test_축소된_fixture는_정본_대조에서_막힌다`, `tests/test_parity_ci_gate.py:402`). 같은 세션이 한쪽에는 회귀를 붙이고 다른 쪽에는 붙이지 않았다.
4. 마감이 **되돌릴 수 없다**. `app/**` 가 지워지면 축소된 스냅샷을 복원할 방법이 없다. 원 지적(`07_core-rebuild_cross.md:305`)이 "유일하게 되돌릴 수 없는 마감"이라 부른 이유가 그것이다.
5. 이 생성기를 근거로 **L344·L345 가 `예` 로 승격됐다**(`e90cfe4`).

**닫는 방법**: `STYLE_CONSTANTS` 와 같은 층에 **케이스 하한**(그룹별 최소 건수 또는 케이스 id 집합)을 상수로 두고, 입력 스냅샷이 그보다 적으면 `SnapshotError`. 파생 키도 `if derived in previous` 를 무조건 재생성으로 바꾼다.

> **리더 판단 요청** — X-9 의 **원 지적은 "재현 경로가 없다"** 였고 그것은 닫혔다(재생성 diff 0 을 내가 독립 실행으로 확인). 위 지적은 산출물이 **새로 연 구멍**이다. 원 지적 기준으로 보면 해소, 산출물 기준으로 보면 차단이다. 나는 차단 ② 로 올린다 — 증거 파일의 위조 가능성은 그 증거를 근거로 한 모든 승격을 무르게 하기 때문이고, 스킬은 "판단할 수 없으면 낮게 잡지 말라"고 정한다.

#### P-B · 생성기의 **도달이 0** 이다 — 원 마감이 요구한 절반이 빠졌다 — **수정 필요** · 마감 **`app/**` 삭제 전**

`--check` 를 부르는 곳이 CI·테스트·스킬 문서 어디에도 없다. 실측 grep 결과는 **자기 docstring 2줄**(`:39-40`)뿐이다. `실행 경로` 어휘로는 `미배선` 이다.

**이것은 새 요구가 아니라 원 지적이 명시한 마감의 절반이다.** X-9 의 종료 조건 원문은 *"X-9 스냅샷 생성기 커밋 **+ CI 재생성 diff**"* 였다(`07_core-rebuild_cross.md:305`). `ef7b4a8` 은 앞 절반(생성기 커밋)을 냈고 뒤 절반(CI 배선)은 내지 않았다. 커밋 메시지·preflight 문서·`e90cfe4` 의 승격 주석은 모두 "재생성 diff 0 확인"만 적어 **한 번 손으로 돌린 것**을 근거로 삼는데, 원 마감이 `CI` 라고 적은 이유가 정확히 그것이다 — 손으로 한 번 돌린 확인은 다음 변경에 도달하지 않는다.

지금 diff 0 인 것은 내가 손으로 돌려 재확인했다. 그러나 `app/easyread/style_rules.py` 는 이 전환 기간에도 계속 손대는 파일이고(가장 최근 `49ea2eb`), 앞으로 바뀌면 **아무 데서도 빨개지지 않는다.** 스냅샷은 조용히 옛 Python 문면을 "Python 정본"이라 주장하는 상수 더미가 된다.

> 이 사실은 **L344·L345 승격의 근거를 직접 건드린다.** 승격 사유가 "X-9 해소"인데, X-9 의 마감은 두 조각이었고 한 조각이 남아 있다(§4.3).

#### P-C · `app/**` 삭제 후의 **경계가 선언되지 않았다** — **판정 필요** · 마감 **`app/**` 삭제 결정 시점**

### 축 4 — Kotlin/Spring 관용성

#### K-A · 모듈 경계 강제의 **도달이 선언보다 좁다** — 원 지적이 **부분 해소인데 완전 해소로 기록됐다** — **수정 필요** · 마감 **Phase 3**

닫힌 것은 확실하다. `api`·`worker` 가 `:infrastructure` 를 `runtimeOnly` 아닌 configuration 으로 선언하면 실패하고, compileClasspath 부재도 함께 본다. `check` 에 걸려 `./gradlew build` 가 지나며(`build.gradle.kts:338-340`), 음성 대조도 붙었고(preflight §2), 내가 직접 두 태스크를 돌려 통과를 확인했다. **원장 `:284` 가 이름 붙인 "한 글자 변경에 깨지는 테스트 0건" 은 해소다.**

문제는 그 다음이다. `boundaryAllowedConfigurations` 는 **두 모듈 이름의 하드코딩 열거**다.

```kotlin
// backend-kotlin/build.gradle.kts:264-268
val boundaryAllowedConfigurations: Map<String, Set<String>> =
    mapOf(
        "api"    to setOf("runtimeOnly", "testImplementation", "testRuntimeOnly"),
        "worker" to setOf("runtimeOnly", "testImplementation", "testRuntimeOnly"),
    )
```

셋이 빠져 있다.

1. **`application` → `:infrastructure` 가 무검사다.** `application/build.gradle.kts:3-5` 는 *"infrastructure 를 의존하지 않는다"* 를 불변식으로 **선언**하는데 강제자가 없다. 그리고 `implementation` 은 소비자 compileClasspath 로 전이되지 않으므로 `api`·`worker` 의 ⓑ 검사에도 걸리지 않는다. 유스케이스 층이 어댑터를 직접 import 하는 것은 §3.2 위반으로서 `api` 가 하는 것보다 **더 나쁘다**.
2. **새 모듈이 자동으로 들어오지 않는다.** `settings.gradle.kts` 에 모듈을 늘려도 이 지도에 이름을 적기 전까지 판정 대상 밖이다. 열거가 근거를 만드는 구조라, CLAUDE.md 규칙 4 가 `mypy` 에서 고친 것과 **같은 형태**다(개별 경로 열거 → 루트 명시). 여기서도 `subprojects` 에서 유도해야 구조로 닫힌다.
3. **`core` 순수성은 그대로다.** 커밋 주석 자신이 `build.gradle.kts:242-244` 에서 열거한 결함 ⑴(`compileOnly` 우회) ⑵(목록 밖 타입)는 **닫히지 않았다.** `CoreModuleBoundaryTest.kt` 는 이 배치에서 수정되지 않았고(git log 확인), 자기 KDoc `:17-20` 이 한계를 그대로 인정한 채다. codex #5 원문이 권고한 `annotationProcessor`/`kapt`/generated source set/plugin-added configuration/바이트코드 스캔도 전부 미착수다.

즉 커밋 메시지·주석·preflight 문서가 "**모듈 의존 방향 강제**"라 부르는 것의 실제 도달은 **5모듈 중 2 × `:infrastructure` 한 대상**이다. 주석 `:241` 은 "두 가지가 통째로 빠져 있었다"고 쓰고 **셋을 열거한 뒤 ⑶만 닫는다** — 문서 스스로 개수가 어긋난다.

**닫는 방법**: 지도를 `subprojects` 에서 유도하고(기본 금지 + 예외만 명시), `application` 을 판정 대상에 넣는다. ⑴⑵ 는 별도 항목으로 원장에 **남기고** — 지금처럼 닫힌 것으로 기록하지 않는다.

#### K-B · advisory lock 에 대기 상한도 진단 로그도 없다 — **수정 필요** · 마감 **Phase 3 첫 기동/배포**

```kotlin
// FlywayBaselineGuard.kt:97-100
connection.prepareStatement("SELECT pg_advisory_lock(?)").use { statement { ... } }
```

`pg_advisory_lock` 은 **무한 대기**한다. `finally` 해제는 올바르고(`:103-108`), 예외 경로·연결 반환도 맞다. 그런데 주석 `:90-91` 이 *"풀지 못한 연결이 풀에 남으면 다음 기동이 영원히 대기한다"* 라고 **그 상태를 예상해 놓고**, 그 상태에 빠졌을 때의 진단 수단이 하나도 없다.

배포 중 기동이 **아무 로그 없이 정지**하는 것은 이 클래스가 막으려는 "안 뜨는 편이 복구가 쉽다"(`:27-28`)와도 어긋난다 — 안 뜨는데 이유를 모른다. 최소한 획득 전후 로그 한 줄과 `SET LOCAL lock_timeout`(또는 `pg_try_advisory_lock` + 상한 재시도)이 필요하다.

잠금을 쥔 연결을 열어 둔 채 `flyway.migrate()` 를 부르므로 풀에서 연결 1개가 마이그레이션 내내 점유된다. `api`/`worker` 의 Hikari 설정에 `maximum-pool-size` 가 없어 기본 10 이므로 실질 위험은 낮다(`api/src/main/resources/application.yml:16-18`). 운영에서 풀을 1~2로 줄이면 교착하므로 그 사실을 설정 주석에 남기는 편이 좋다.

#### K-D · `EXPECTED_ALEMBIC_HEAD = "0006"` 의 지시 대상이 삭제 대상 안에 있다 — **권고** · 마감 **`app/**` 삭제 시**

#### K-E · 빈 `alembic_version` 테이블을 통과시킨다 — **권고**

`FlywayBaselineGuard.kt:175` — `if (actual.isEmpty() || actual == listOf(EXPECTED_ALEMBIC_HEAD)) return`. 테이블 **부재**(순수 Kotlin DB — 정상)와 테이블은 있는데 **행이 0**(누군가 truncate 했거나 alembic init 만 된 상태)은 성격이 다르다. 지문이 0006 모양과 정확히 일치하는데 리비전 행이 없는 것은 모순 상태이고, 이 검사가 잡으려는 축("값만 바꾸는 리비전")과 같은 위험을 갖는다. 테스트도 `DROP TABLE` 경로(`:126-135`)만 덮고 **빈 테이블 경로는 없다.**

#### K-F · 동시 기동 시나리오의 서술이 설정과 어긋난다 — **권고**

`FlywayBaselineGuard.kt:54-55` 와 `FlywayBaselineGuardTest.kt:27-28`·`:154` 가 *"api·worker·migrate 프로필이 함께 뜨면 **셋이** 같은 판정을 동시에 한다"* 라고 적고 `CONCURRENT_STARTS = 3` 을 그 근거로 든다. 그러나 **worker 는 Flyway 를 돌리지 않는다** — `worker/src/main/resources/application.yml:26-28`: *"worker 는 스키마를 적용하지 않는다. 마이그레이션 주체는 migrate profile 하나뿐이다."*

### 축 5 — 테스트 적정성

#### T-A · `동시 기동이 직렬화된다` 에 **음성 대조가 없고**, 단언의 모양이 약하다 — **수정 필요** · 마감 **Phase 3 착수 전**

> 심각도 단서: 아래 «측정 방법» 을 돌린 결과 잠금을 떼도 초록이면 **차단 ② 로 상향**된다. 측정 전까지는 수정 필요로 둔다.

**⑴ 음성 대조가 없다.** preflight §4 검사표(`:109-116`)는 모듈 경계 음성 대조만 적었고, `ef7b4a8` 커밋 메시지에도 이 테스트에 대한 음성 대조가 없다. `withAdvisoryLock` 을 제거했을 때 이 테스트가 빨개진다는 확인이 **어디에도 없다.**

**⑵ 단언이 "예외가 안 났음"이다.**

```kotlin
// FlywayBaselineGuardTest.kt:170-172
assertThat(failures).describedAs("동시 기동 중 하나라도 실패하면 잠금이 늦거나 없다").isEmpty()
```

잠금이 없어도 이 단언이 성립하는 경로가 있다. 세 스레드가 이력 없음을 동시에 보고 각자 `baseline()` 을 불러도, 같은 버전(1)의 중복 baseline 은 Flyway 가 예외 없이 넘길 수 있고 그 경우 뒤따르는 `appliedVersions == ["1","2"]` 와 `첫 type == BASELINE` 도 그대로 성립한다. 즉 **잠금을 떼도 초록일 수 있다.** 스킬 기준 그대로다 — *"떼어도 아무것도 깨지지 않으면 검증된 장치가 아니다."*

**⑶ TOCTOU 축 자체를 재현하는 테스트가 0건이다.** codex #4 의 원 지적은 두 갈래였다(지문 확인 후 baseline 전 스키마 변경 = TOCTOU / 동시 기동). 신규 5건은 리비전 불일치 · 지문 무반응 · alembic 부재 · 읽기 전용 · 동시 기동이고, **첫 갈래를 재현하는 것은 하나도 없다.** 잠금 안에서 DDL 을 끼워 넣으려는 탐침이 막히는지 잰 자리가 없다.

이 지적의 무게는 원 지적 문서가 정해 준다 — `01_skeleton_cross.md:460` 이 *"**F-2·F-5 는 코드 판정 근거이며 실증 근거가 아니다**"* 라고 못박았다. 이 배치의 값어치는 정확히 "실증을 붙였다"인데, 실증 5건 중 이 축을 재는 1건이 **탐지력 미확인**이고 다른 축(TOCTOU)은 0건이다.

**측정 방법**(내가 하지 않았다 — 리뷰어는 코드를 수정하지 않는다): `kotlin-implementer` 가 `withAdvisoryLock(connection) { ... }` 을 `run { ... }` 으로 바꾸고 이 테스트를 **반복 실행**한다.
- 안정적으로 빨개지면 → 이 지적은 ⑶만 남고 심각도 **권고**로 내려간다.
- 초록이거나 간헐적이면 → **차단 ②** 다(검증하지 않는데 검증한다고 집계되는 테스트). 그 경우 단언을 "baseline 행이 정확히 1건" · "동시 스레드 중 하나만 `flyway.baseline()` 에 도달" 같은 **직접 축**으로 바꾸고, TOCTOU 는 잠금 안에서 DDL 을 시도하는 별도 탐침으로 세운다.

**L344·L345 승격의 근거는 절반이다.** 승격 사유는 "X-9 해소(`ef7b4a8` — 스냅샷 생성기, 재생성 diff 0)"인데, X-9 의 마감 원문은 *"스냅샷 생성기 커밋 **+ CI 재생성 diff**"* 두 조각이었다(`07_core-rebuild_cross.md:305`). 낸 것은 앞 조각이고, 뒤 조각(CI 배선)은 도달 0 이다(P-B). 재생성 diff 0 자체는 내가 독립 실행으로 확인했으므로 **데이터는 옳다** — 부족한 것은 그것을 앞으로도 지킬 장치다. C-3·C-4 쪽은 `f73b8bd` 로 비교기가 강화됐다(범위 밖이라 미검증 — §5).

그리고 승격 후 판정표 `:408` 이 따라오지 않아 **한 문서가 같은 두 행을 예와 아니오로 동시에 적고 있다**(T-C). 공교롭게 `:408` 이 아직 적고 있는 사유가 "X-9(스냅샷 생성기 미커밋 — 남은 것은 재현 경로)"인데, **P-A·P-B 를 보면 그 행이 완전히 틀린 것도 아니다.**

> **리더 판단 요청** — 승격을 유지하려면 P-B(CI 배선)를 닫거나, X-9 의 마감을 "생성기 커밋까지"로 **명시적으로 축소 재정의**해야 한다. 지금은 마감을 줄인다는 결정 없이 절반으로 닫힌 상태다.

## 5. 미실행·확인 불가 항목

정직하게 적는다. 아래는 **판정하지 않았다.**

1. **Flyway 잠금의 음성 대조** — 실행하지 않았다. 리뷰어는 코드를 수정하지 않으며, CLAUDE.md 규칙 5 가 음성 대조 후 복원 사고를 두 번 기록했고 그중 하나가 이번 세션 preflight §2 에 있다. 측정 절차는 T-A 에 적었고 `kotlin-implementer` 소관이다.
2. **`f73b8bd`(C-3·C-4 해소)** — 리뷰 범위(`5797d87..614afed`) 밖이라 검증하지 않았다. L345 승격의 근거 절반이 여기 있으므로, 아직 교차 리뷰를 안 받았다면 별도 회차가 필요하다.
3. **CI 러너에서의 실제 도달** — 이 배치가 CI 를 손대지 않았으므로 `ci.yml` 잡 구성만 읽었고 러너 실행은 확인하지 않았다. `moduleBoundaryCheck` 가 `check` → `build` 를 타므로 `ci:kotlin` 의 `./gradlew build` 에 실린다는 것은 **배선 확인**이지 관측이 아니다.
4. **`x-request-field-constraints` 의 OpenAPI 스펙 유효성** — changelog 가 validator 통과를 적었으나 내가 재실행하지 않았다.
5. **보안 불변식 I-1~I-12 전반** — 이 배치가 닿는 3자리만 봤다(축 3). 전체 감사는 `privacy-gate` 소관이고, 판정이 갈리면 그쪽을 따른다.
6. **범용 품질 축**(성능·유지보수성 일반) — 이 에이전트의 범위 밖이다. 필요하면 글로벌 `multi-review` 를 별도로 돌리도록 리더에게 권고한다.
