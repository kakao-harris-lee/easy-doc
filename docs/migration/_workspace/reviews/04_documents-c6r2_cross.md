## 3. 충돌·판정 필요 항목 — 양쪽 근거를 병기한다

어느 쪽도 삭제하지 않는다. 판정 권한은 리더에게 있다.

### 3.1 판정 ① — codex High #1 은 Claude C-1·C-2 와 **같은 결함인가, 같은 장치의 다른 결함인가**

**판정: 같은 장치(K-1 인구조사)의 서로 다른 세 결함이다. 그중 codex #1 ∩ Claude C-2 는 「같은 자리·다른 기제」이고, codex #1 과 Claude C-1 은 별개 결함이다. 그리고 codex #1 은 Claude 가 안전으로 판정한 자리를 결함으로 판정했으므로 부분 충돌을 포함한다.**

세 결함을 분리한다. 셋 다 같은 단언 부재(`isNotEmpty()` 가 유일한 하한)에서 나오지만 **깎는 경로가 다르고, 처방도 다르다.**

| 결함 | 분모를 깎는 경로 | 지적 레인 | 처방 |
|---|---|---|---|
| **상류 절단** (codex #1) | 계약 `applies_to` 에서 구현 대상 5건 삭제 → auth 3건만 돌고 초록 | codex 단독 | 10개 대상의 **정체성 집합**(메서드+경로)을 독립적으로 고정하고 계약 집합과 **양방향** 일치 단언 + 삭제·치환 변이 |
| **하류 팽창** (Claude C-2) | 유보 목록 `NOT_YET_IMPLEMENTED` 를 늘림 → 10곳 중 9곳을 유보로 옮겨도 초록 | Claude 단독 | `MAX_DEFERRED_FLOOR_TARGETS = 2`(여유 0) · `MIN_FLOOR_CENSUS_TARGETS = 8`(여유 0) + 라쳇 핀 — S-2·S-5 와 **같은 형태** |
| **유보 영구화** (Claude C-1) | 유보를 끊는 술어가 상태코드 404/405 라 구현돼도 안 빨개진다 | Claude 단독 | 술어를 엔진에 직접 묻는 것으로 교체 — `ServedOperations.methodsOn(handlerMapping, environment, path)` (기구현) |

**세 처방은 서로를 대체하지 않는다.** 상류 절단 처방(정체성 집합 고정)만 넣으면 유보 목록을 늘리는 경로는 살아 있고, 유보 팽창 처방만 넣으면 계약을 깎는 경로가 살아 있다. Claude 가 C-1·C-2 에 대해 적은 「두 장치 중 하나만 있어도 막히는데 둘 다 없다」는 **하류 두 결함 사이의 관계**이고, codex 의 상류 결함은 그 곱셈의 **세 번째 항**이다.

**충돌 부분** — Claude 는 「분모를 계약에서 읽는 것」을 반복해 **안전 근거로** 제시했다:

- 1차 §3.1: *"분모가 구현이 아니라 계약이다 ✓"* (`ConversionReadContractTest.kt:155-190` 에 대해)
- 1차 §4.2 「검사의 기준이 검사 대상 자신에게서 나오지 않는가」: **검토함 — 지적 없음**. 근거로 든 목록에 `privateResponseHeaderTargets()` 가 **명시적으로 들어 있다.**

codex 는 정확히 그 상류를 결함으로 판정했다 — *"인구조사의 분모가 **변경 가능한** 계약 `applies_to` 자체이고"*. 즉 **계약을 상류로 두는 설계가 「검사 대상 자신에게서 나오지 않는다」를 만족하느냐**에서 두 레인이 갈렸다.

- **Claude 측 근거**: 계약은 구현과 독립한 외부 규범이므로 구현을 복사한 기대값이 아니다. 계약을 파싱하는 것은 이 회차 전반의 **좋은 패턴**이었고(`ContractCheckOrder` 는 검사 순서를 산문에서 파싱하며 `MIN_CHECK_ORDER_STAGES = 5` 로 파서가 조항을 놓치면 끊는다), 그 패턴을 결함으로 보면 계약 기반 단언 전부가 흔들린다.
- **codex 측 근거**: 계약도 **같은 변경 단위에서 편집 가능한 파일**이다. 보안 불변식의 하한선을 그 파일 하나에만 결속하면 「계약 5행 삭제」로 하한선 절반이 자동 신호 없이 사라진다. 하한선은 규범이므로 **둘 이상의 독립한 자리**에 있어야 한다.
- **결정적 비대칭**: Claude 가 안전 근거로 든 다른 사례들(`ContractCheckOrder`, `schemaRequired`)에는 **파서가 조항을 놓칠 때 끊는 하한**이 있다(`MIN_CHECK_ORDER_STAGES = 5`). K-1 에는 그 형태의 하한이 없고 `isNotEmpty()` 뿐이다. 즉 Claude 자신이 세운 기준을 K-1 에 적용하면 codex 결론이 나온다.

> **리더 실측 (재판정하지 않음)**: `PrivateHeaderFloorCensusTest` 의 `implementedTargets()` 단언은 `isNotEmpty()` 하나이고, 하한선 목록을 정체성으로 고정하는 곳은 `RequestFieldConstraintLayerTest` 의 auth 3건뿐이다. → **codex High #1 확인.**

**리더 판단 요청**: ⑴ codex #1 을 X-1b 로 확정하고 처방(정체성 집합 양방향 고정)을 C-1·C-2 조치와 **같은 편집 단위**에 넣을 것인가. ⑵ Claude §4.2 의 「검사의 기준」 판정을 「계약 상류에 하한이 붙어 있는 경우에만 안전」으로 좁힐 것인가 — 좁히면 이 회차의 다른 계약 기반 단언들도 같은 기준으로 재검토 대상이 된다(범위 판단 필요).

### 3.2 판정 ② — codex High #2 와 Claude M-4 의 **처방이 하나로 닫히는가**

**판정: 같은 자리·다른 기제이고, 처방은 하나로 닫힌다 — 단 합집합으로만. 어느 한쪽만 넣으면 다른 쪽 기제가 살아남는다.**

기제 3갈래(X-2a·b·c)와 처방 대조:

| 처방 항 | codex | Claude | 어느 기제를 막는가 |
|---|---|---|---|
| 산출물을 **정확히 3개**(codex-reviewer · migration-reviewer · cross) 요구 | ✓ | ✓ (M-4 처방 1) | X-2b (역할 구성) — **양쪽 합의** |
| 표의 **산출물 칸을 실제 경로로 파싱** | ✓ | **없음** | X-2a — codex 만 |
| 산출물이 그 행의 **`a..b` 문자열을 담는지** | (manifest 의 start/end SHA 로 대체) | ✓ (M-4 처방 3, `_cross.md` 한정) | X-2a 의 절반 (범위 결속) |
| `git cat-file -e <end>:<path>` 로 **end 커밋 시점 추적 확인** | **없음** (manifest 방식이 대안) | ✓ (M-4 처방 2) | X-2c — Claude 만 |
| canonical review ID + **diff digest** 를 산출물/manifest 에 기록 | ✓ | **없음** | X-2a 의 강한 판 (내용 결속) |

- **Claude 처방만 넣으면**: 산출물 칸이 여전히 미파싱이므로 표에 거짓 경로를 적는 것이 계속 통과한다. (다만 `{stem}_codex-reviewer.md`·`{stem}_cross.md` 실재를 요구하면 codex 가 재현한 「`없는-증거.md` 로 승인」 시나리오는 **부분적으로** 막힌다 — 어간 규칙이 실재 파일을 강제하므로.)
- **codex 처방만 넣으면**: 「정확히 3개」가 X-2b 를 흡수한다. 시점 결속은 manifest 의 SHA 기록으로 대체되지만, **manifest 자신을 누가 지키는가**가 새로 생긴다.
- **양쪽 다 인정하는 한계**: 「산출물 내용이 참인가」는 어느 처방으로도 재지 않는다. Claude 가 이것을 명시했고(*"셋 다 「내용이 참인가」는 여전히 재지 않는다 — 그 한계는 유지"*), codex 의 diff digest 는 「그 diff 를 보고 썼는가」까지만 잰다.

**닫히지 않은 전제 하나 (리더 확인 필요)**: Claude 가 이연 장부 `0fda906` 행을 인용해 이 강제자가 **동결(교체 계획 R-2 로 소멸 예정)** 이라고 적었다. **R-2 의 범위에 「역할 구성 검사」와 「산출물 칸 파싱」이 드는지 두 리뷰 모두 확인할 수 없었다.** 들지 않으면 교체 후에도 같은 세 빈자리가 남는다.

> **리더 실측 (재판정하지 않음)**: `_coverage_ranges()` 는 `cells[0]`(회차)·`cells[1]`(범위)만 읽고 **`cells[2]`(산출물 칸)를 아예 읽지 않는다.** → **codex High #2 확인.**

### 3.3 판정 ③ — codex High #3 과 Claude M-6 은 **같은 결함의 두 면인가**

**판정: 그렇다. 입구(codex)와 출구(Claude)이고, 양쪽 다 필요하다. 다만 두 처방의 발효 시점이 다르므로 순서 판정이 필요하다.**

- **codex = 입구**: `대기` 를 애초에 계상하지 말라. *"보호 브랜치/출하 모드에서는 `대기` 행이 하나라도 있으면 실패시키고, `이연` 만 임시 계상하라."*
- **Claude = 출구**: 계상된 `대기` 를 회수하라. *"`대기` 행의 SHA 가 어느 커버리지 범위에 들면 `닫힘` 칸이 `-` 가 아니어야 한다."*

**두 실측이 모순이 아니다 — 서로의 사각을 채운다.**

- Claude 실측: 장부 11 SHA × 커버리지 3 범위 **교집합 0** → 「리뷰됐는데 `닫힘` 이 `-` 인 행」은 오늘 없다.
- codex 실측: b4c2fda·6a9ca8b·6c970b6·4ac13ec 가 필수 축에 닿는다고 **원장 자신이 적으면서** 전부 `대기` 인데 테스트는 green.

즉 Claude 는 「범위에 든 `대기`」를 보았고(0건), codex 는 「범위에 들지 않은 채 계상된 `대기`」를 보았다(4건). **codex 가 짚은 것이 정확히 Claude 실측이 구조적으로 볼 수 없는 면이다.**

**순서 판정이 필요한 이유**: codex 처방을 지금 넣으면 오늘 11행 전부 `대기` 이므로 CI 가 **즉시 빨개진다.** 그런데 이 회차(`318bd36..b4646ee`)가 codex 가 든 4개 SHA 를 **포함**한다 — 이 회차 3단계(이 문서)가 닫히면 그 4행이 `닫힘` 을 받을 수 있다. Claude 도 같은 관찰을 했다(*"처방을 지금 넣으면 이 회차의 3단계가 그 처방의 첫 소비자가 된다"*).

**리더 판단 요청**: Claude 처방(출구)을 먼저 넣어 이 회차 4행을 닫고, codex 처방(입구, 출하 모드에서 `대기` 0 요구)을 Phase 4 종료 판정 시점에 발효시키는 2단 순서를 채택할 것인가. 아니면 동시에 넣고 남은 7행의 처분(닫기 / `이연` 재분류)을 먼저 정할 것인가. **어느 쪽이든 「빨개지니 처방을 미룬다」는 선택지로 세지 않는다** — 그것이 X-3 을 만든 기제다.

### 3.4 판정 ④ — codex Medium #4 와 Claude M-5 의 **두 처방이 양립하는가. 어느 쪽이 규칙 4 ⑵·⑶ 에 맞는가**

**판정: 양립한다. 합치는 것이 각각보다 낫다. 규칙 4 ⑵ 는 둘 다 통과하고, ⑶ 은 Claude 처방만 명시적으로 담고 있다. 남은 충돌은 「기존 어간 9종을 개명하는가」 하나이고 그 비용이 양쪽 산출물에 계산되지 않았다.**

**규칙 4 ⑵ (은폐형 금지 — 넓히지 말고 탐지형으로 갈아탄다)**

- **둘 다 통과.** 어느 처방도 면제 목록·무시 패턴을 늘리지 않는다.
- 그리고 **두 레인이 독립적으로 같은 안티패턴을 배제했다**(X-4b). Claude: *"표에 `documents-c3`·`documents-c6`… 를 열거해 넣는 것은 회차마다 표를 늘리는 은폐형이고 규칙 4 ⑵ 의 거부권에 걸린다."* codex: *"접미사를 scope 표에 매번 추가하는 방식은 도메인 정본을 회차 목록으로 변질시키므로 피하라."* **이 합의가 이 회차 교차 대조의 가장 강한 신호다** — 서로를 보지 않은 두 모델이 같은 처방 금지선을 그었다.

**규칙 4 ⑶ (범위 선언형은 빈 선언에서 통과하면 안 된다)**

- **Claude 처방이 명시적으로 담는다** — 처방 3: *"표를 파싱할 수 없으면 실패시킨다 — 표 형식이 바뀌어 0건을 읽으면 통과가 아니다."*

- **강제자의 소재**: Claude 는 강제자가 어디 사는지 지정한다(`tests/test_harness_scope_reach.py`, 분모 = `reviews/*.md` 디렉터리 **전수** → 새 파일이 자동으로 든다, fail-closed). codex 는 강제자의 **요구사항**만 말하고 소재를 말하지 않는다.

**합집합이 각각보다 나은 이유**

- codex 의 **구조 분리**(별도 `round` 필드·명시 구분자)를 채택하면 Claude 의 문법 검사가 **더 쉬워진다** — 구분자가 명시되면 파싱이 정규식 추측(`-[a-z0-9]+`)이 아니게 된다.
- Claude 의 **탐지자 + fail-closed**를 채택하면 codex 의 「정확히 일치」에 **집행자가 생긴다.** codex 처방만으로는 규약이 다시 문장으로만 남는다 — 그것이 오늘 X-4a(강제자 0)를 만든 상태다.

**남은 충돌 하나 — 기존 어간의 처분**

## 4. 게이트 자신의 결함 — **축② 가 한 레인만 받았다**

> 이 항목은 리더가 실측으로 지목해 이 문서에 담도록 지시한 것이다. 교차 대조표의 통상 행이 아니라 **게이트 자신의 결함**으로 분리한다.

**사실**

`codex-reviewer` 래퍼가 전달 프롬프트를 산출물에 전사하면서 리더의 축② 를 **뒤집었다.**

| 자리 | 문면 | 방향 |
|---|---|---|
| 리더가 준 축② | 계약 `required` 열셋을 `null`·`[]` 로 **유지하는가** | 올바름 |
| codex 산출물 「지켜야 하는 조건」(`:23`) | *"응답이 `null` 또는 `[]`인 경우에도 그 키가 직렬화되지 **않아야** 한다"* | **역전** |
| codex 산출물 「리뷰 축 4개」 §2 (`:56-59`) | *"계약 `required` 열셋을 null·[] 로 **유지**하는 보장"* | 올바름 |
| codex 판정문 본문 (`:80`) | *"제품 경로는 … 13개 required 키를 null·[]로 **직렬화**하지만"* | 올바름 |

**귀결**

- **거짓 지적은 나지 않았다.** codex 판정문 본문이 올바른 방향으로 읽었으므로 이 회차에 실질 피해는 없다.
- **그러나 그 축에 대한 codex 의 무지적은 「이상 없음」의 근거가 되지 못한다.** 전달 프롬프트의 한 절이 반대 방향을 지시했으므로, codex 가 그 축을 어느 방향으로 검사했는지 **산출물로 확정할 수 없다.** 판정문 한 줄이 올바른 방향을 담고 있다는 것은 「그 방향으로 검사했다」의 증거가 아니라 「최종 요약이 올바르다」의 증거일 뿐이다.
- **Claude 레인은 그 축을 판정했고 「문제 없음」이다** — 직렬화 경로가 하나(`ConversionController.kt:33` 의 `ConversionResponse.of(view)`), 13필드 전부 `@get:JsonProperty` 명시, `NON_NULL`·`JsonInclude`·`default-property-inclusion` 이 저장소 전체에 **0건**(실행 확인), 그리고 행위 단언 둘(CR-1 최상위 키 정확 일치 · CR-3b 완료 전 세 상태 전수 `body.keys == schemaRequired(CONVERSION_SCHEMA)`).
- **따라서 축② 는 두 레인이 아니라 한 레인만 받았다. 교집합으로 세지 않는다.** §2.4 표에 그렇게 기록했다.

**이 결함의 성격과 심각도**

- **장치 분류**: 강제·표현형(전달 프롬프트의 전사). **탐지 장치 0** — 전사의 정확성을 재는 것이 저장소에 없다.
- **왜 게이트 자신의 결함인가**: `CLAUDE.md` 가 `codex-reviewer` 를 *"호출·원문 보존만 하는 얇은 래퍼"* 로 규정하고 Haiku 를 배정한 근거가 *"래퍼가 자기 판정으로 원문을 대체하면 교차 대조가 Claude 대 Claude 가 된다"* 다. 이 사고는 그 실패의 **다른 형태**다 — 원문은 보존됐으나 **입력이 변형됐다.** 원문 보존만 규정하고 입력 전사를 규정하지 않은 것이 빈자리다.
- **심각도**: **차단 ② 장치.** 근거 — 이 축(계약 `required` 유지)은 §6 Contract 게이트의 직접 항목이고, 「두 레인이 봤다」가 이 회차 판정의 근거로 쓰이는 자리다. 무해했던 것은 우연이며(본문이 올바른 방향), **같은 사고가 방향이 중요한 축에서 나면 거짓 「이상 없음」이 정본에 실린다.**
- **마감**: **다음 codex 호출 전** — 하네스 단위.
- **수신 레인**: 하네스 레인 (`.claude/agents/codex-reviewer.md`).
- **처방이 저장소 안에 있는가**: **부분.** 원문 보존 규약은 이미 있다. 입력 전사의 정확성을 재는 장치는 **없다.** 최소 형태는 「전달 프롬프트를 요약·재서술하지 않고 리더가 준 문면 그대로 인용한다」를 래퍼 규약에 넣는 것이다 — 요약을 금지하면 역전이 구조적으로 불가능해진다. (탐지자를 만들 것인가는 리더 판정 — 이 회차의 다른 지적들과 달리 분모를 정의하기 어렵다.)

## 5. 관측 독립성 — 격리가 무엇을 벌었는가

**이 회차는 교집합이 실재한다. 직전 G-γ 회차는 교집합 0 이었다.**

### 5.1 같은 자리에 독립적으로 닿은 항목 — 4/4

codex 4개 지적 **전부**가 Claude 지적과 자리를 공유한다.

| codex | Claude | 자리 |
|---|---|---|
| High #1 | C-2 | `PrivateHeaderFloorCensusTest` 의 분모 하한 |
| High #2 | M-4 | `tests/test_review_coverage_reach.py:175-186` `_coverage_ranges()` |

그리고 **처방 금지선 하나가 독립 합의**다 — 「표에 회차를 열거하지 말라」(X-4b). 서로를 보지 않은 두 모델이 같은 안티패턴을 배제했다. 강제자 0 도 양쪽이 독립적으로 확인했다(X-4a).

### 5.2 한 레인만 닿은 항목 — 「보고도 안 지적했는가」 대 「보지 않았는가」

이 구분이 격리의 값을 재는 유일한 방법이므로 **산출물 근거로만** 가른다. 짐작은 적지 않는다.

**A. Claude 가 보고도 반대로 판정한 것 — 1건 (가장 값진 codex 소득)**

| 항목 | 근거 |
|---|---|
| 계약 `applies_to` 를 분모로 두는 것의 안전성 (codex #1 상류 절단) | Claude 1차 §4.2 「검사의 기준이 검사 대상 자신에게서 나오지 않는가」가 **검토함 — 지적 없음** 이고, 근거 목록에 `privateResponseHeaderTargets()` 를 **명시**했다. 즉 그 자리를 보았고, 안전으로 판정했다. codex 는 같은 자리를 결함으로 판정했다 → §3.1 충돌 |

**B. Claude 가 보고도 다르게 읽은 것 — 1건**

| 항목 | 근거 |
|---|---|
| 커버리지 표의 산출물 칸 미파싱 (codex #2) | Claude M-4 는 `:137-186` 을 읽고 판정 내용을 열거했다 — *"열 3개 · `범위` 칸이 백틱 `a..b` … · `회차` 칸이 백틱이고 `reviews/<회차>_*.md` 가 최소 2건 실재"*. **3열 구조를 알고 있었고 두 열의 검사를 서술했으나, 세 번째 열이 검사되지 않는다는 사실을 짚지 않았다.** 「열 3개」를 열 개수 검사로 읽고 내용 미파싱으로 잇지 않았다 |

**C. Claude 가 보았고 codex 는 산출물상 닿지 않은 것 — 1건**

| 항목 | 근거 |
|---|---|
| 장부 `닫힘` 열의 회수 장치 0 (Claude M-6) | codex 는 `:207-256` 을 읽고 `대기`·`이연` 파서를 분석했으나 `닫힘` 열을 언급하지 않았다. 입구만 보았다 |

**D. codex 가 보지 않은 것 — Claude 단독 11건 (X-6 ~ X-16)**

**기제는 전달 프롬프트의 축 설정이다.** codex 축 5개는 ① K-1 강제자 ② `required` 유지 ③ K-1 라쳇·바닥·단언 하한 ④ 어간 ⑤ 원장 판정 표다. Claude 단독 항목 중:

- **축 자체가 없었던 것**: X-8(`POST /documents` 검사 순서 — 계약 준수 축이 codex 에 없다) · X-12·X-13(제품 코드 관용성) · X-14·X-15(테스트 세부) · X-16(주석 예산).
- **축은 있었는데 지적이 나지 않은 것**: X-7·X-9·X-10 은 codex 축③(라쳇·바닥·단언 하한)의 사정거리 안이다. codex 는 그 축에서 지적을 내지 않았고, **「검토했으나 지적 없음」인지 「닿지 않았는지」가 산출물로 확정되지 않는다** — codex 산출물에 축별 무지적 기록 구획이 없다. §2.4 에 「부분 검토」로 적었다.
- **X-6(유보 해제 술어)은 codex 축① 의 사정거리 안이다.** codex 는 같은 클래스를 읽고 분모 상한을 지적했으나 유보 케이스의 술어(`NO_HANDLER_STATUSES`)에는 닿지 않았다.

### 5.3 이 회차가 격리로 실제로 번 것

1. **codex 가 Claude 의 안전 판정 하나를 뒤집었다**(§5.2 A). 이것이 격리의 본래 목적이고, 이 회차에서 실현됐다. Claude 단독 리뷰만 돌렸다면 X-1b 는 「검토함 — 지적 없음」으로 닫혔다.
2. **Claude 가 codex 시야 밖의 11건을 냈다**(§5.2 D). codex 단독 리뷰만 돌렸다면 차단 2건(X-6·X-7)과 계약 위반 1건(X-8)이 남았다.
3. **두 레인이 같은 처방 금지선을 독립적으로 그었다**(X-4b) — 합의가 이 회차에 값을 낸 유일한 자리다. 다른 세 자리의 합의는 「같은 장치를 보았다」이고, 실제 소득은 그 안의 **기제 차이**였다.
4. **잃은 것**: 축② 가 한 레인만 받았다(§4). 그리고 codex 산출물에 축별 무지적 기록이 없어 축③ 의 침묵을 해석할 수 없다.

## 8. 실패로 남은 것 · 미교차 · 확인 불가

### 8.1 codex 산출물의 「미실행·실패 항목」 두 줄 — 전사 및 판정

**⑴ `test_review_coverage_reach` 실행 1건 실패 (exit 1)**

> codex 원문: *"Python 환경에서 test_review_coverage_reach 자체 실행 시도 중 1건 실패 (exit 1) — 그러나 static 분석(rg, sed로 코드 읽기)은 모두 성공. 지적에 영향 없음."*

**판정: 이 실패는 codex High #2 의 「재현했다」 주장의 근거를 비운다.**

- codex High #2 본문은 실행 재현을 주장한다 — *"**실제로** 기존 `04_documents-c6_*` 파일을 둔 채 산출물 칸을 존재하지 않는 `없는-증거.md`, 범위를 `318bd36..b4646ee` 로 만든 합성 행이 `_coverage_ranges()` 에서 그대로 승인됐다."* 그런데 같은 산출물이 그 파일의 실행 실패를 기록한다. **두 기술이 같은 문서 안에서 긴장한다.**
- **지적 자체의 사실은 확정됐다** — 리더 실측(`cells[2]` 미판독)이 구조로 확인했다. **비는 것은 「승인됐다」의 실행 증거**이며, 정적 판정은 그대로 유효하다.
- **어느 축의 근거를 비우는가**: codex **축⑤(원장의 판정 표 자신이 입력 위조를 막는가)의 실행 근거.** 그리고 **Claude 레인도 이 파일을 실행하지 않았다** — Claude 가 실행한 것은 `tests/test_kotlin_gate_reach.py`(11 passed)다. 즉 **축⑤ 는 두 레인 모두 실행 근거가 0이고 구조 판정만 있다.** X-2·X-3 의 처방을 넣을 때 **음성 대조가 아직 한 번도 붙지 않았다**는 사실이 남는다.
- 관련 사실 (리더 실측): 원장 무결성 **확인** — `00_progress.md` 의 sha256 이 HEAD 와 동일하다. **codex 레인의 재현은 본 저장소를 변조하지 않았다.** 재현이 실제로 있었다면 임시 사본에서 이뤄졌다는 뜻이고, 그 사본은 산출물에 기록되지 않았다.

**⑵ `RequestFieldConstraintTest.kt` 파일 탐색 실패 (exit 1) — 실제 파일명은 `RequestFieldConstraintLayerTest.kt` 다**

> codex 원문: *"RequestFieldConstraintTest.kt 파일 탐색 실패 (exit 1) — 파일이 없거나 경로 변경. 그러나 Jackson 직렬화 경로는 다른 경로들로 검증됨."*

**판정: 이 실패는 축② 와 축① 양쪽의 근거를 비운다. 그리고 축② 는 §4 의 전사 역전과 겹쳐 이중으로 빈다.**

- **축②(`required` 유지)**: codex 가 *"다른 경로들로 검증됨"* 이라 적었으나 **그 다른 경로가 무엇인지 산출물에 없다.** 즉 축② 의 codex 측 근거는 ⓐ 전달 프롬프트가 역전됐고(§4) ⓑ 검증 경로가 미기재다. **축② 를 codex 가 판정했다고 볼 수 없다** — §2.4·§4 의 「한 레인만」 판정이 이 실패로 한 번 더 뒷받침된다.
- **축①(K-1)**: codex High #1 의 *"별도 테스트가 auth 3건만 고정하고 있어"* 라는 문장은 **그 파일을 열지 못한 채 쓴 것이다.** 리더 실측이 그 주장이 사실임을 확인했다 — 하지만 **산출물 자체에는 그 근거가 없다.** 즉 **결과적으로 옳았으나 검증되지 않은 주장이었고, 리더 실측이 사후에 근거를 공급했다.** 이 사실을 기록하는 이유: codex #1 의 확정은 codex 산출물이 아니라 **리더 실측에 의존한다.**

### 8.3 codex 리뷰 부재·실패로 대조하지 못한 범위

- **codex 리뷰는 존재한다.** 「codex 리뷰 없음 — 교차 대조 미수행」에 해당하지 않는다. 재요청도 필요하지 않았다.
- **대조하지 못한 범위**: ⑴ **축②** — 전달 프롬프트 역전 + 검증 경로 미기재로 codex 측 판정을 확정할 수 없다(§4, §8.1 ⑵). ⑵ **codex 축③ 의 침묵** — 라쳇·바닥·단언 하한을 축으로 받았으나 지적 0 이고, 산출물에 축별 무지적 기록 구획이 없어 「검토함 — 지적 없음」인지 「닿지 않았는지」를 가릴 수 없다. X-7·X-9·X-10 은 그 축의 사정거리 안이므로 **이 셋의 교차 대조는 미완이다.** ⑶ **parity 축 · Kotlin 관용성 축 · 마스킹·평문 로그·AEAD** — codex 축에 없어 전면 미검토.
- **이전 회차 충돌 항목의 리더 판단**: 1차 산출물이 격리 때문에 `04_documents-c6_cross.md` 를 읽지 않았고, **이 3단계 호출의 입력도 두 산출물뿐이라 그 파일을 읽지 않았다.** 즉 **직전 회차 충돌 항목이 리더 판단을 받았는지 이 문서는 확인하지 못했다.** 답이 오지 않았다는 이유로 조용히 닫지 않기 위해 사실로 남긴다 — **리더 확인 요청.**

### 8.4 「종합 중 발견 — 미교차」

교차 검증을 받지 않았으므로 차단 목록에 섞지 않는다. 다음 리뷰 회차의 범위로 제안한다.

1. **codex #2 처방의 manifest 방식이 규칙 7(게이트 깊이 3층, 4층 금지)과 긴장할 수 있다.** codex 는 「canonical review ID + start/end SHA + diff digest 를 별도 서명 manifest 에 기록해 표와 대조」를 제안한다. 이때 층은 ① 산출물 ② manifest ③ 표 ④ manifest 를 지키는 것 — **manifest 자신의 무결성을 누가 지키는가**가 4층째다. Claude 처방(`git cat-file` 로 산출물의 커밋 시점을 직접 보는 것)은 층을 늘리지 않는다. **처방 선택 시 규칙 7 을 함께 판정할 것을 제안한다.**
2. **codex #4 처방(기존 어간 개명)의 파손 비용이 양쪽 산출물에 계산되지 않았다.** 개명하면 커버리지 표·이연 장부의 기존 참조가 깨진다. 두 레인 모두 이 비용을 산정하지 않았다(§3.4).
3. **축별 무지적 기록 구획이 codex 산출물 형식에 없다.** 이 회차에 축③ 의 침묵을 해석할 수 없게 만든 원인이고, §4 의 축② 문제와 같은 뿌리(래퍼가 축 정보를 산출물에 어떻게 보존하는가)다. `codex-review` 스킬의 산출물 형식 개선 후보 — **§4 처방과 함께 검토할 것을 제안한다.**
