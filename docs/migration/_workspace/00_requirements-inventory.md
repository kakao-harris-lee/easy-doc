**상태:** 1차본 · **미승인**(리더·사용자 승인 대기)
**정본 출처(SSOT):** `docs/master-plan.md` 3장(정책 결정)·4장(우선순위). 파생 목록: 계획 §2.3.
**게이트 연결:** 계획 §1.1이 정의하고 계획 §6 `Requirements` 게이트("해당 Phase 범위 항목의 미충족 0")가 가리키는 정본 산출물이다.
**판정 기록 위치:** 항목별 충족(예/아니오) 판정은 이 파일이 아니라 각 Phase 게이트에서 `00_progress.md`에 남긴다. 이 파일은 **항목과 확인 방법을 확정**한다.

> **이 파일이 왜 생겼나 (리뷰 02_criteria-pivot A-1 / 교차 X-08).**
> 커밋 `49ea2eb`이 판정 기준을 "Python 출력 일치"(기계 확인)에서 "요구사항 충족"으로 바꾸면서, 새 기준의 계측기로 `요구사항 인벤토리`를 §6 게이트·Phase 0·2·4 종료 조건·완료 정의에 앉혔다. 그런데 그 이름의 산출물이 저장소에 없어 **"미충족 0"이 항목 0개일 때도 참**이 되는 구조였다(검사 대상 0건인데 성공). 이 1차본이 그 게이트에 **실제 항목**을 부여해 그 구멍을 닫는다.

## 읽는 법

- **유형**: `[불변]` 정책 불변식(동일성이 요구사항) · `[호환]` 롤백 창 값 동일성 요구 · `[기능]` 요구사항 기능(Python 동일성 불요) · `[보안]` 보안·비용 요구 · `[계약]` HTTP 계약.
  `[불변]`·`[호환]`은 CLAUDE.md·계획 변경 이력이 지정한 **기준 전환 예외**다 — 이 둘만은 Python과 값이 같아야 하는 것이 요구사항이다.
- **확인 방법**: 무엇을 실행/감사하면 판정되는가. 계측기가 아직 없으면 그 Phase를 `blocked-by`에 적는다. **확인 방법 자체를 못 적는 항목은 §9에 따로 모았다** — 확인 불가를 확인 가능한 척하지 않는 것이 이 인벤토리의 존재 이유다.
- **범위**: 전 항목 Lean MVP(master-plan §4.0) 안. Lean MVP 밖 항목은 §8에 기록만 하고 판정 대상에서 뺐다.
- **1차본의 한계(계획 §1.1)**: 전역 요구사항과 합격선만 여기서 확정한다. **도메인별 상세 항목(정확한 경계값·프롬프트 전문·스타일 규칙 상수)은 각 Phase 착수 시 그 범위만 추가한다.** 1차본을 도메인 완전 피복으로 읽지 말 것.

ID는 게이트·fixture·테스트가 참조하는 안정 키다. `관련 도메인`은 `dump_parity_fixtures.py --list`의 정본 도메인과 잇는다.

## 8. 범위 밖 (Lean MVP 제외 — 기록만, 판정 대상 아님)

master-plan §4.1 P0이지만 §4.0 Lean MVP 밖이라 이번 전환 범위가 아니다(CLAUDE.md 개발 단계). 빠뜨린 게 아니라 **의도적 제외**임을 남긴다.

- **크레딧 과금(P0-7)·결제/PG(P0-8)·RAG 사전 팝업(P0-5)·랜딩(P0-10)·운영자 어드민(P0-11)·공공도메인 인증·견적서(P0-1 확장)** — Lean MVP는 이메일 가입·핵심 변환·검수·기록만(§4.0). 현재 Python 런타임에도 없거나 최소 형태다. 전환 후 별건.
- **no-training 약관(§3.1)·위탁 문서화 마스킹 2종 기재(§3.2)** — 실행 게이트로 검증 불가한 **계약·법무** 항목. 코드에 남는 요구는 provider 구현체 주석의 no-training 명시(CLAUDE.md 보안규칙)뿐이며, 그 주석 존재 확인은 자동 게이트가 아니라 리뷰 육안이다.

## 9. 확인 방법 미확정 항목 (계측기 공백 — 다음에 만들 것)

**이 절이 이 인벤토리에서 가장 중요하다.** "미충족 0"이 의미를 가지려면 각 항목이 판정 가능해야 하는데, 아래는 판정 계측기가 없거나 불완전하다. 이걸 확인 가능한 척하면 리뷰가 지적한 바로 그 구멍(항목 0개에서 참)이 항목 수준에서 재발한다.

- **A. 품질 합격선 수치 (STY-03·STY-04)** — 도구(tests/golden·judge)는 **있으나** "필수 항목 충족률·규칙 위반 허용치·judge 절대 점수"의 **합격 수치가 저장소 어디에도 없다.** 계획 §4.6 게이트 2·5와 Phase 0 종료 조건이 "Phase 0에서 수치로 확정"이라 적었으나 미확정. **이 수치 없이는 STY-03·STY-04의 미충족 여부를 판정할 수 없다.** → 리더/Phase 0 재개 항목. `00_progress.md` Phase 0에 신설 행으로 올렸다.
- **B. INV-06 no-store 전역 부착 실측 (H-1)** — 확인 방법(원시 소켓 + `@SpringBootTest(RANDOM_PORT)`)은 정의됐으나, 필터 앞·바깥에서 컨테이너가 직접 만드는 응답 4종(malformed 400·핸들러 없는 404·413·415)에 헤더가 닿는지 **이 저장소에서 실측된 적이 없다.** MockMvc로는 측정 불가. → Phase 3, `00_progress.md` 미결 원장 H-1과 동일 건.
- **C. STY-05 HITL·UI 계열** — 자동 게이트가 없다. E2E/육안 확인만 가능. "확인 가능"으로 오분류하지 않도록 명시한다.
- **D. INV류 로그 스캔의 자동화 수준** — INV-04·INV-07의 "평문·개인정보 미로깅"은 현재 migration-safety-gate의 **감사(사람+스크립트)**로 판정한다. 상시 회귀(CI 로그 스캔 테스트)로 고정돼 있지 않다. 자동 회귀화는 별건 계측기.

## 부록 — `00_progress.md`·게이트와의 관계

1. 계획 §6 `Requirements` 게이트가 이 파일을 가리킨다. 게이트 통과 기준 "해당 Phase 범위 항목의 미충족 0"의 **범위 항목**은 위 표의 `Phase` 열로 선별한다(예: Phase 2 게이트 = INV-01·02, CNV-01·02·04, STY-01·02, DOC-05·06).
2. 항목별 예/아니오 판정과 근거는 각 Phase 착수·종료 시 `00_progress.md`에 기록한다. 이 파일은 **무엇을 판정하는가**를, `00_progress.md`는 **판정 결과**를 담는다.
3. §9의 미확정 계측기가 닫히기 전에는 해당 항목을 "충족"으로 세지 않는다 — 근거 없는 예는 아니오다(`00_progress.md` 스키마 규칙).
