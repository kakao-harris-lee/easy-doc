### 3.1 변환 오케스트레이션 상세 — CNV-01·CNV-02·CNV-04 (2026-08-13 추가 · parity-verifier)

> **왜 여기 있나.** 세 항목은 요구사항 한 줄씩만 있었고 **판정식**은 코드에만 있었다(`03_rebuild-extraction-list.md` §G). §G가 요구한 "인벤토리 상세"가 이 절이다. Python 삭제는 P2 선행조건("해당 도메인의 알려진 명세 누락 0")에 걸리므로, 여기 옮겨지지 않은 판단이 남아 있으면 변환 도메인의 Python은 지울 수 없다.
> **값의 정본은 fixture다** — `parity/fixtures/repair-adoption/repair-adoption.json`(25 케이스·단언 75개). 이 절은 그 fixture가 **무엇을 못박는지의 서술**이고, 둘이 어긋나면 fixture가 옳다. 명세 문서는 `02_parity-verifier_conversion-spec.md`.
> 인벤토리 「읽는 법」이 미뤄 둔 "각 Phase 착수 시 추가하는 도메인별 상세"의 Phase 2 변환 몫이다.

#### (가) 호출 상한의 정확한 의미 — CNV-01

1. **세는 단위는 "완성 요청 1건"**이다. 변환 1건이 쓸 수 있는 완성 요청은 **최대 2건** — ① 변환 1건, ② 기계 검출된 규칙 위반이 있을 때만 표적 보정 1건.
2. **루프가 아니다.** 보정 결과에 위반이 남아 있어도 다시 보정하지 않고, 보정 결과를 **기각한 경우에도** 다시 부르지 않는다. 상한은 "보통 2회"가 아니라 **구조적으로 2회**여야 한다 — 검사→호출을 반복하는 구조는 상한이 아니라 기대값일 뿐이다.
3. **위반이 없으면 1건이다.** "항상 2건"은 상한을 지키면서 요구를 어긴다 — 크레딧 원가 산정(master-plan 5장)이 두 배로 어긋난다.
4. **전송 계층 재전송은 이 수에 들어가지 않는다.** provider 어댑터가 타임아웃·5xx로 같은 완성 요청을 여러 번 전송하는 것은 전송 시도이지 완성 요청이 아니다. 두 수를 **따로 계측**한다 — 합치면 상한이 재시도 설정에 따라 흔들리고, 모델에게 실제로 몇 번 물었는지도 잃는다.
5. **응답 없이 끝난 호출도 센다.** 비용·지연은 이미 발생했고, 요점은 "다시 부르지 않는다"이다.

#### (나) 보정을 시도하는 조건 — CNV-01·CNV-04

- 1차 변환 결과가 **기계 검출 규칙 검사를 통과하지 못했을 때만** 보정한다. 부를지 말지를 사람이나 모델이 정하지 않는다.
- 보정 요청에는 **검출된 위반만** 싣는다(전면 재작성 요청이 아니다). 통과한 문장까지 흔들면 보정이 품질을 떨어뜨리는 쪽으로 작동한다.

#### (다) 보정 채택/기각 판정식 — CNV-04

> **채택 = (자리표시자를 하나도 잃지 않았다) AND (규칙 위반 건수가 늘지 않았다)**

- **자리표시자 축**: 1차 결과에 있던 자리표시자가 보정 결과에 하나라도 없으면 기각한다. *하나만* 잃어도 기각이고, 판정은 **존재 여부**이지 위치·순서가 아니다. 1차 결과에 애초에 없던 자리표시자는 "잃은 것"이 아니다.
- **건수 축**: 늘면 기각, **같으면 채택**(경계값). 같은 건수는 고친 자리와 새로 생긴 자리가 맞바꿈된 경우인데, 지적받은 쪽을 고친 결과를 남긴다.
- **기각의 결과는 1차 결과 채택**이다. 변환은 성공이고 "보정본을 썼는가" 표시는 거짓이다.
- **사용량(토큰) 보고는 채택 여부와 무관하게 두 호출의 합**이다. 부른 순간 비용은 발생했고, 빼면 원가가 실제보다 적게 잡힌다.
- **이 판정식이 보는 축은 둘뿐이다.** 본문·팩트 손실은 보지 않는다 — 미해결 요구 공백이며 `02_parity-verifier_conversion-spec.md` §6 갈림 후보 ①(리더 판정 대기).

#### (라) 4대 예외의 검출 조건과 결과 상태 — CNV-02

같은 사건이라도 **어느 호출에서 났는가**에 따라 결과가 정반대다.

| 예외 | 검출 조건 | 1차 호출에서 | 보정 호출에서 |
|---|---|---|---|
| 응답 절단 | provider가 "출력 상한에서 잘렸다"는 **사실**만 보고하고 정책(실패냐 재시도냐)은 변환 쪽이 정한다 | 변환 **실패** — 결과를 사용자에게 주지 않는다 | 보정을 버리고 **1차 결과 채택**, 변환은 성공 |
| 빈 결과 | 후처리 뒤 본문이 남지 않았다(빈 응답이거나 껍데기만 왔다) | 변환 **실패** | 1차 결과 채택 |
| 호출 실패 | provider 계층 실패(전송·서버 오류 등) | 변환 **실패** | 1차 결과 채택 |
| 자리표시자 유실(보정) | 위 (다) 자리표시자 축 | — | 보정 기각 → 1차 결과 채택 |
| 보정 악화 | 위 (다) 건수 축 | — | 보정 기각 → 1차 결과 채택 |

**비대칭의 이유**: 1차 결과가 없으면 사용자에게 줄 것이 아예 없다. 보정은 이미 쓸 만한 결과를 더 낫게 만들려는 **시도**일 뿐이라, 보정 실패가 변환 전체를 실패시키면 사용자는 받을 수 있었던 결과마저 잃는다. 두 위치를 같은 코드로 뭉뚱그리면 반드시 한쪽이 틀린다.

**실패의 노출**: 실패는 정의된 실패 코드로 기록되고 결과 본문은 비어 있다. 코드에 **문서 본문·모델 응답·파일명을 담지 않는다**(INV-04). 종류는 최소 셋을 구분한다 — 절단 / 빈 결과 / 호출 실패. 구분이 필요한 이유는 사용자가 취할 조치와 운영 집계가 다르기 때문이다(절단은 문서를 나눠 올리면 풀리고 호출 실패는 다시 시도하면 풀린다). ⚠ **그 코드 문자열의 정본이 아직 없다 — §9-E.**

#### (마) 자리표시자 유실 보고 — CNV-02 · INV-03 인접

- 최종 결과 본문에 남아 있지 않은 자리표시자 **라벨 전부, 그리고 그것만** 보고한다.
- **예외로 막지 않는다.** 개인정보가 새는 방향이 아니라 표시가 사라지는 방향(연락처 등 정보 누락)이므로 사람이 원문과 대조하도록 검수 화면 경고로 넘긴다. 여기서 실패로 처리하면 쓸 만한 결과를 통째로 버린다.
- **기준 본문은 채택된 최종 결과**다. 1차 결과에 대고 산출하면 사용자가 받은 본문에 멀쩡히 있는 라벨을 유실로 신고하게 되고, 목록이 비어 있지 않으면 내보내기가 409로 막혀 정상 결과를 못 받는다.
- 목록에 들어가는 것은 **라벨뿐**이다(원문 값이 아니다). 그래서 목록 자체는 개인정보가 아니고 계약도 그렇게 적고 있다.

## 9. 확인 방법 미확정 항목 (계측기 공백 — 다음에 만들 것 / A는 **처분 완료** 기록)

**이 절이 이 인벤토리에서 가장 중요하다.** "미충족 0"이 의미를 가지려면 각 항목이 판정 가능해야 하는데, 아래는 판정 계측기가 없거나 불완전하다. 이걸 확인 가능한 척하면 리뷰가 지적한 바로 그 구멍(항목 0개에서 참)이 항목 수준에서 재발한다.

> **2026-08-12 3차 — A는 처분 완료로 바뀌었다.** 계측기 공백이 아니라 **닫힌 항목의 기록**으로 읽어라. 남은 것은 "계측기가 없다"가 아니라 "**계측기는 있는데 아직 돌리지 못했다**"(기준선 미기록)이다. B·C·D는 그대로 공백이다.

- **A. 품질 합격선 (STY-03·STY-04) — 처분 완료 (2026-08-12 3차).** 이 항목의 이전 판은 "합격 수치가 저장소 어디에도 없다"고 적었다. **그 기술은 부정확했고**(`PASS_RATE_THRESHOLD` 0.90·`JUDGE_COVERAGE_THRESHOLD` 0.90·`JUDGE_SCORE_THRESHOLD` 4.0·`DEFAULT_FIDELITY_FLOOR` 2는 코드에 있었다 — `02_quality-baseline.md` §2), 진짜 공백은 **축별 허용치·채점자 고정·코퍼스 고정·통과 시 기록** 넷이었다. 넷 모두 처분됐다.

  | 공백 | 처분 | 근거 |
  |---|---|---|
  | 코퍼스 고정 | **지문 2축으로 닫음** — `corpus_sha256`(문서 id 집합·본문·`required_facts`·합성 여부) / `criteria_sha256`(`style_rules` 규칙 상수 전량). 지문이 다르면 수치를 읽지 않고 **비교 불가로 차단**한다 | `tests/golden/baseline.py` |
  | 통과 시 기록 | **`report.py`로 닫음** — 통과하는 실행도 수치를 남긴다. 상대 하한선은 직전 측정치가 **있을 때만** 성립하므로 이것이 선행 조건이었다 | `tests/golden/report.py` |
  | 채점자 고정 | **소멸** — 결정 ③(judge 비차단)으로 게이트의 전제조건에서 빠졌다. 고정할 수 없는 것을 차단축으로 쓰지 않기로 했으므로 고정할 필요가 없어졌다 | 계획 §4.6 게이트5 |
  | 축별 허용치 | **팩트축은 절대 0**(`REQUIRED_FACT_LOSS_LIMIT = 0`), **스타일축은 허용치 대신 통과율이 상대화**(직전 기록 대비 하락 0). 규칙별 세부 허용치를 정하지 않고 축의 성격으로 갈랐다 | 계획 §4.6 게이트2 |

  **합격선은 절대 수치가 아니라 기제로 확정됐고, 계측기는 구현·검증·커밋됐다**(`c43cae5`). 리더 직접 실행 실측: `pytest` **916 passed / 68 skipped**, `pytest tests/golden` **63 passed**, mypy **122 files**, 지문·기록·하락 재현 **14건** 통과. **KPI 0.90은 목표선으로 살아 있다** — 실수집 52.8%는 "괜찮다"가 아니라 **코퍼스 난이도**로 판정된 값이고 목표를 낮춘 것이 아니다.

  **남은 진짜 공백은 하나다 — ⓐ `tests/golden/baseline.json` 미기록.** LLM 키가 없어 실측할 수 없었고 **수치를 지어내지 않았다.** 현재는 "기준선 없음 → 차단, 기록 필요"로 떨어지며 이것이 설계된 정상 상태다. 첫 기록: `GOLDEN_RECORD_BASELINE=1 GOLDEN_PROVIDER=anthropic uv run pytest tests/golden -m llm`.

  **함께 열려 있는 것(공백이 아니라 예고·미결):** ⓑ 절대 팩트 게이트가 **첫 실행에서 통과하지 못할 공산** — 마지막 저장 실행(2026-08-08)의 팩트 잔존율 90.1%·14문서 누락이고, 실손실과 `accept` 목록 공백(정당한 의역)의 비율은 **정적으로 판정할 수 없다.** 게이트를 낮출 사유가 아니라 프롬프트를 고칠 사유이며, 첫 `-m llm` 실행이 삼분류 근거를 만든다. ⓒ **날조(fidelity=1)에 결정적 차단이 없다** — 팩트축은 누락만 잡고 judge는 비차단이다. 역방향 축(출력의 숫자·금액·날짜가 원문에 존재하는가)이 큰 부류를 잡을 수 있으나 합의된 범위 밖의 새 차단 게이트라 **짓지 않았다. 리더 판정 대기.** ⓓ **독립 리뷰 미실시.**

  **적용 범위의 한계(오독 금지):** 게이트 **로직과 배선**은 매 CI 기본 스위트에서 돈다(재현 40건, LLM 호출 없음). **실제 변환문에 대한 적용은 `-m llm` 레인에서만** 가능하다 — 변환 없이는 검사할 대상이 없다. "매 커밋 차단"이 아니다.

  **연결:** 이 합격선을 **책임지고 닫는 단계는 Phase 5 종료 게이트**로 확정됐다(계획 §4.6 codex Q6, Phase 7 진입 전 필수). 계획 §6 검증 매트릭스 Quality 행이 같은 기준으로 교체됐다. → `00_progress.md` Phase 0 해당 행 갱신.
