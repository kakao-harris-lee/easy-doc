# 첫 골든셋 -m llm 실행 기록 (2026-08-12) — 기준선으로 채택하지 않음

실행: `GOLDEN_RECORD_BASELINE=1 GOLDEN_PROVIDER=anthropic uv run pytest tests/golden -m llm`
소요 35분 20초. 결과 **2 failed / 1 passed**.

## 측정치

| 구분 | 통과 | 비율 |
|---|---|---|
| 전체 | 31/56 | **55.4%** |
| 합성 | 16/20 | 80.0% |
| 실수집 | 15/36 | **41.7%** |

judge: 채점 55/56, 충실성 평균 4.65, 가독성 평균 4.98,
**충실성 ≤2 문서 2건 — 041 · 042**(날조·중요 정보 누락 의심). 089는 변환 실패.

## 왜 기준선으로 굳히지 않았나

**두 조건이 비어 있다.**

1. **직전 저장 실행(2026-08-08)의 36/56 = 64.3% 보다 9%p 낮다.** 같은 코퍼스인데
   떨어졌고 **원인을 가리지 않았다.** 낮은 값을 하한선으로 삼으면 그 하락이 정상이
   되고, 다음 실행은 저하된 값과 비교해 통과한다.
2. **무엇으로 쟀는지 모른다.** `context.model` 이 `null` 로 기록됐다 —
   `settings.llm_model` 이 미설정이라 실행이 자기가 쓴 모델을 기록하지 못했다.
   `.env` 의 `LLM_EFFORT` 차이일 수도 있고 실제 품질 하락일 수도 있는데 **구분할
   근거가 파일에 없다.**

그래서 `tests/golden/baseline.json` 을 저장소에서 내렸다. 저장소에 있는 순간
**활성화**되기 때문이다 — 파일이 있으면 다음 실행이 그것과 비교한다.

## 기준선을 다시 기록하는 조건

1. `LLM_MODEL` 을 고정해 실행이 자기 조건을 기록하게 한다.
   `write_baseline` 이 `provider`·`model` 이 비면 **쓰지 않고 실패**하도록 고쳤다.
2. 9%p 하락의 원인을 가린다 — effort/모델 차이인지 실제 하락인지.
3. 그 뒤 같은 조건으로 다시 기록하고 diff 를 리뷰에 올린다.

## 이 실행이 만든 것

- **팩트축 삼분류 근거** — 필수 정보 보존 게이트가 실패했고, 그 목록이 실손실 /
  `accept` 목록 공백(정당한 의역) / 판정 불가를 가르는 입력이다.
- **미결 ⓒ·ⓔ 의 첫 실물** — 041 · 042 가 날조·누락 의심으로 지목됐다. 두 미결이
  추상적 우려가 아니라 지목된 문서를 갖게 됐다.
