## 1. Phase 3 몫의 정의 — 무엇이 「연결」인가

### 1-1. 계획 문서가 정한 경계

계획 `docs/plans/2026-08-11-kotlin-react-migration.md` §5 는 두 Phase 에 React 를 나눠 적었다.

| Phase | 원문 항목 | 이 문서의 해석 |
|---|---|---|
| **3** | 「React 를 Kotlin API 에 연결한 **로그인·작업 공간** E2E」 | 대상 엔드포인트가 **이름으로 한정**돼 있다 — `/auth/*` 3종 + `/workspaces` 4오퍼레이션. 문서·변환·내보내기는 Phase 4 에 구현이 생기므로 원리상 대상이 아니다 |
| **6** | OpenAPI 생성 타입 교체 · 승인된 계약 개선 반영 · polling·미저장 경고 검증 · a11y(키보드·focus·aria-live·대비) · nginx `/api` 프록시와 개발 CORS 검증 · **compose 기반 가입→…→삭제 전체 E2E** | 화면 **전체**와 **타입 기반**이 바뀌는 단계 |

**갈라야 하는 이유가 하나 더 있다.** Phase 3 의 E2E 는 「타입을 갈아끼우기 **전**의 React 가
Kotlin API 와 말이 통하는가」를 잰다. Phase 6 의 타입 교체가 그 뒤에 오므로, Phase 3 E2E 가
초록이면 **교체가 깨뜨린 것과 원래 어긋나 있던 것**이 구분된다. 순서를 뒤집으면 Phase 6 에서
나는 빨강이 어느 쪽 원인인지 알 수 없다.

### 1-2. Phase 3 몫 — 최소 정의 (이것이 종료 조건이다)

**실 브라우저에서 구동되는 React 앱**이 **실 Kotlin API 프로세스**(실 PostgreSQL 연결)를 상대로
아래 흐름을 통과한다. 스텁·목·MSW 를 쓰지 않는다.

1. 가입 → 자동 로그인 → 홈 진입 (`AuthProvider.tsx:64-70` 의 signUp = signup + signIn)
2. 로그인 → `/auth/me` 확인 → 작업 공간 목록 도착 → 머리말 메뉴에 기본 작업 공간이 뜬다
3. 작업 공간 **생성** → 목록 재조회 → 새 공간이 선택된 상태가 된다 (`WorkspaceProvider.tsx:89-99`)
4. 작업 공간 **이름 변경** → 목록 갱신 (`WorkspaceProvider.tsx:101-108`)
5. 실패 갈래 두 종이 화면에 도달한다 — 로그인 자격증명 401 과 **세션 만료** 401 이 **다르게** 처리된다
   (`client.ts:125-133` 의 `token !== null` 분기)

**「통과」의 판정 기준은 화면 상태 + 네트워크 관측 둘 다**다. 화면만 보면 서버가 계약을 어겨도
화면이 우연히 맞는 경우를 놓치고, 네트워크만 보면 `client.ts`·Provider 가 응답을 잘못 소비하는
경우를 놓친다. 이 축이 갈리는 자리가 실제로 있다 — §3-3 의 401 두 갈래가 그렇다.

### 1-3. Phase 3 몫이 **아닌** 것 (Phase 6 또는 다른 레인)

| 항목 | 왜 지금이 아닌가 | 어디로 |
|---|---|---|
| `types.ts` → OpenAPI 생성 타입 교체 | 계획 §4.1-1 이 Phase 6 항목으로 지정 | Phase 6 (`06_contract-keeper_frontend-type-swap.md`) |
| a11y 점검(키보드·focus·aria-live·대비) | 계획 §5 Phase 6 항목. 서버 연결과 독립 | Phase 6 |
| nginx 동일 출처 `/api` 프록시 | Phase 6 항목. **Phase 3 은 교차 출처(CORS) 경로를 잰다** — 프록시를 먼저 붙이면 CORS 계약(`contracts/easy-doc-v1.yaml:196-207`)이 한 번도 실행되지 않은 채 Phase 6 에서 처음 드러난다 | Phase 6 |
| 업로드·변환 polling·검수·내보내기·기록·삭제 | 구현이 Phase 4·5 에 온다 | Phase 6 전체 E2E |
| **`DELETE /workspaces/{id}` 의 409 두 갈래·마지막 하나** | **React 에 호출부가 없다.** 계약이 그것을 **의도로** 명시하고 Phase 6 타입 교체 후에도 래퍼를 만들지 말라고 적었다(`contracts/easy-doc-v1.yaml:1377-1380`, `frontend/src/api/client.ts:204-210`). E2E 로 이 갈래를 재려면 **계약이 만들지 말라고 한 호출부를 만들어야 한다** | **계약 테스트 층이 정본** — `03_contract-keeper_workspaces-test-spec.md` WD-4·WD-5. E2E 대상 아님 |
| `PATCH`·`DELETE` 의 **타인 자원 404** | 같은 이유로 UI 에서 도달 불가 — 메뉴는 자기 목록만 렌더한다(`WorkspaceMenu.tsx:65-69`) | 계약 테스트 WR-3·WD-2 (X-B1 마감분) |
| 이메일 **형식** 규칙 케이스 | 계약이 규칙을 게시하지 않았고 ASCII 정책이 사용자 판단 대기다(§5 OQ-E2) | 판정 후 |

> **삭제 흐름을 E2E 에 넣자는 제안이 다시 올라올 것이다.** 그때 근거로 쓸 문장은 이것이다 —
> 계약이 「호출 래퍼를 추가하지 않는다」고 **적어 둔** 자리이므로, 넣으려면 계약 개정이
> 먼저다(§7.2 ② React 런타임 코드가 의존하는 동작의 변경).

## 2. 드리프트 대조 — 수기 `types.ts`·`client.ts` ↔ 계약

**기준은 계약 파일이다.** Kotlin 을 기동해 응답과 맞춰 보지 않았다 — 그것은 구현 대조이지
계약 대조가 아니고, 구현이 계약을 어긴 자리에서는 잘못된 결론을 낸다.
대상은 Phase 3 범위(`/auth/*`·`/workspaces/*`)로 한정한다.

### 2-1. 런타임 동작이 깨지는 드리프트 — **0건**

Phase 3 범위에서 **React 가 계약과 어긋난 요청을 보내거나 계약에 맞는 응답을 못 읽는 자리는
없다.** 경로·메서드·요청 본문 필드·응답 필드가 모두 계약과 일치한다. 확인한 대응:

| React | 계약 | 판정 |
|---|---|---|
| `api/auth.ts:7-13`·`:16-22`·`:25-27` (경로·메서드·`auth:false` 두 곳) | `:787`·`:827`(`security: []`) · `:862`(Bearer) | 일치 |
| `client.ts:194-196`·`:199-202`·`:211-214` (GET/POST `/workspaces`, **PATCH** `/workspaces/{id}`) | `:1255`·`:1276`·`:1328`(PUT 아님을 명시) | 일치 |
| `types.ts:26-29` `UserResponse` | `:1725-1731` | 일치 |
| `types.ts:117-132` `WorkspaceResponse`·`WorkspaceListItem`·`WorkspaceListResponse` | `:2001`·`:2010`·`:2022` | 일치 (`document_count` 가 목록에만 실리는 비대칭까지 같다) |
| `types.ts:135-137` `WorkspaceNameRequest` (POST·PATCH 공용) | `:1987`·`:1290`·`:1341` | 일치 |
| `client.ts:69-92` `readErrorMessage` 의 문자열/배열 union | `:1627` `ErrorResponse` · `:1534-1566` `ValidationFailed`(두 모양이 같은 422 에 나온다) | 일치 |

### 2-2. 타입만 어긋나는 드리프트 — 3건 (Phase 6 부채, 런타임 무영향)

| ID | 자리 | 계약 | 성격 | 처분 |
|---|---|---|---|---|
| **RD-1** | `types.ts:20-23` `CredentialsRequest` 하나로 가입·로그인을 겸한다 | 계약은 **두 스키마를 분리 유지**한다(`:1696`·`:1718`, 유지 판정은 스킬 §2.8 판정 10) | 이름이 하나 vs 둘. 모양이 같아 지금은 무해 | Phase 6 교체 시 생성 타입이 둘로 갈린다. **계약을 React 에 맞추지 않는다** — 분리 유지 판정이 정본 |

### 2-3. 계약이 침묵하는데 React 가 값을 들고 있는 자리 — 2건 (이쪽이 진짜 위험이다)

| ID | 자리 | 무엇 |
|---|---|---|
| **RD-4** | `frontend/src/auth/validation.ts:13` 의 이메일 정규식 | **계약에 이메일 형식 규칙이 없다.** `x-request-field-constraints.fields[0]`(`:386-391`)은 길이·측정 기준·문구만 정하고 형식을 정하지 않는다. 한편 Kotlin 은 형식을 **ASCII 로 좁혔다**(`backend-kotlin/application/src/main/kotlin/kr/easydoc/application/auth/CredentialRules.kt:44-60`). 두 규칙이 다른 파일에 따로 산다 — 계약이 중재하지 않는다. **런타임 코드**이므로 단독 변경 불가(§5 OQ-E2) |
| **RD-5** | `validation.ts:10`·`:16` 의 길이 상수 2개 | 계약 `fields[].limit`(`:386-411`)의 **손으로 옮긴 사본**이다. 이 상한들은 `x-service-constraint`/`x-request-field-constraints` 에만 있고 OpenAPI `maxLength`/`minLength` 로는 **의도적으로 표현되지 않으므로**(`:426-431` `x-openapi-expressibility`) **Phase 6 타입 생성이 이 사본을 없애 주지 못한다.** 영구 수기 자리로 남는다 |

RD-4·RD-5 는 **화면 동작을 지금 깨뜨리지 않는다.** `validation.ts:5-6` 이 스스로 「백엔드보다
엄격하지 않게 유지한다」를 규약으로 적었고 현재 사본은 실제로 더 느슨하다(비ASCII·짧은 TLD 를
통과시켜 서버가 422 로 거절한다). 즉 **React 때문에 막히는 사용자는 없다.**
위험은 반대 방향이다 — 서버 규칙이 **느슨해지는** 개정이 오면 React 사본이 남아 사용자를 막고,
그때 계약에는 그 규칙이 없으므로 **어느 쪽이 정본인지 판정할 근거 자체가 없다.**

## 3. E2E 실행 계획

### 3-1. 도구 — 현재 저장소에 브라우저 E2E 가 없다

**실측.** `frontend/package.json` 의 테스트 도구는 Vitest 4 + Testing Library + jsdom 이고
(`vite.config.ts:8` 이 `environment: 'jsdom'`), Playwright·Cypress 계열 의존성은 **0건**이다.
저장소 루트의 `.playwright-mcp/` 는 MCP 도구의 산출물 디렉터리이지 테스트 하네스가 아니다.

**판정: Playwright(`@playwright/test`) 를 Phase 3 에서 도입한다.** 대안과 비교한 근거:

| 후보 | 왜 아닌가 |
|---|---|
| 현행 Vitest + jsdom 에 실 `fetch` 를 물린다 | jsdom 은 **CORS 를 강제하지 않는다.** 그러면 계약 `x-cors`(`:196-207`)가 이 단계에서도 한 번도 실행되지 않고, 프리플라이트·허용 origin 이 Phase 6 nginx 프록시 뒤로 숨어 **영영 안 잰다.** 「React 를 연결했다」의 핵심 위험을 비껴간다 |
| Node 에서 `fetch` 로 API 만 호출 | React 를 통과하지 않는다. 그것은 계약 테스트를 약하게 다시 쓴 것이고, 이미 강한 계약 테스트가 Kotlin 쪽에 있다(`api/src/test/.../WorkspaceContractTest.kt` 등) |
| **Playwright** | 실 브라우저라 CORS·프리플라이트가 진짜로 돈다. 응답 **원시 헤더**를 읽을 수 있어 §3-2 E12 가 가능하다. `window.prompt` 를 dialog 핸들러로 다룰 수 있어 `WorkspaceMenu` 를 실제로 조작할 수 있다. **Phase 6 이 요구하는 a11y·다운로드 파일명·nginx 검증에 그대로 재사용된다** — 두 Phase 가 하네스 하나를 나눠 쓴다 |

**제약 — §4.1 을 넘지 않는다.** E2E 하네스는 **테스트 인프라**이고 계획 §4.1 이 열거한 React
제품 변경 6항목 중 어디에도 해당하지 않는다. 이 단위에서 `types.ts`·`client.ts`·`pages/`·
`components/` 를 고치면 범위 초과다. 하네스 추가로 그 파일들을 고쳐야 한다면 **설계가 틀린
것이므로** 고치기 전에 리더에게 올린다.

**E10 의 설계 주의 하나.** `Cache-Control` 은 CORS `expose_headers` 에 **없다**(`:201`) — 브라우저
JS 의 `response.headers.get()` 으로는 교차 출처에서 읽히지 않는다. 그래서 이 단언은 **페이지
스크립트가 아니라 Playwright 의 응답 관측**으로 해야 한다(원시 헤더를 본다). 이 구분을 놓치면
「계약을 지키는 서버」에 대해 테스트가 빨강이 나고, 그 빨강을 고치겠다고 `expose_headers` 를
넓히는 **계약 개악**으로 이어진다. 넓힐 근거는 없다 — 브라우저 JS 가 이 헤더를 읽을 이유가 없다.

### 3-3. 401 두 갈래를 **왜 E2E 로 재는가**

이 두 갈래는 상태 코드가 같고 응답 본문 형태도 같다. 갈리는 것은 **클라이언트가 토큰을 들고
갔는가**뿐이고, 그 판정은 서버가 아니라 `client.ts:128` 이 한다. 따라서:

- 계약 테스트(Kotlin)로는 **원리상 잴 수 없다** — 서버는 두 경우에 같은 것을 낸다
- 현행 React 단위 테스트는 `fetch` 를 스텁하므로 **서버가 실제로 무엇을 내는지와 무관하게** 통과한다

즉 이 계약 조항은 **지금까지 어느 층에서도 검증된 적이 없다.** E2E 가 처음 닿는 자리이고,
그래서 E2·E3 를 최소 정의(§1-2)에 넣었다.

### 3-4. 실행 경로

#### `local:` — compose 경로를 정본으로 한다

```
docker compose --profile kotlin up -d --build   # postgres → kotlin-migrate → kotlin-api
VITE_API_BASE_URL=http://localhost:8100 npm run dev   # frontend/, 5173
npx playwright test                                    # frontend/e2e/
```

두 가지가 이 경로를 정본으로 만든다.

1. **포트.** `backend-kotlin/api/src/main/resources/application.yml` 의 `server.port` 기본값은
   Python api 와 **같은 값**이라, Gradle 로 로컬 기동하면 충돌한다. compose 는
   `backend-kotlin/Dockerfile:60` 이 `SERVER_PORT` 를 덮어써 갈라 둔다.
2. **CORS.** Vite dev 서버 포트가 Kotlin 기본 허용 origin 과 같다. **`vite preview` 로 돌리면
   포트가 달라 프리플라이트가 막힌다** — E2E 를 preview 빌드 위에서 돌리려면 허용 origin 을
   환경변수로 넣어야 하고, 그것은 계약 `x-cors.allow_origins` 가 「설정값」이라고 적은 그대로다.
   **기본값을 계약에서 바꾸지 않는다.**

#### `ci:...` — **현재 배선으로는 돌 수 없다**

실측(`.github/workflows/ci.yml`):

| 잡 | Postgres | Java/Kotlin JAR | 브라우저 |
|---|---|---|---|
| `quality`(`:18`) | **있다**(서비스 컨테이너) | 없다 | 없다 |
| `frontend`(`:182`) | 없다 | 없다 | 없다 (6 steps: checkout·node·`npm ci`·check·test·build) |
| `kotlin`(`:209`) | Testcontainers(러너 Docker) | **있다** | 없다 |

즉 **Kotlin 서버 + Postgres + 브라우저가 한 잡에 모이는 자리가 없다.** 배선안 둘:

| 안 | 내용 | 평가 |
|---|---|---|
| **(a)** `frontend` 잡을 키운다 — Java 21 + `bootJar` + Postgres 서비스 추가 | 순수 프런트 게이트에 DB·JVM 을 넣으면 **프런트 회귀가 인프라 실패로 빨강**이 된다. 신호가 섞이고 잡 시간이 늘어난다 | **아니오** |
| **(b)** 새 잡을 신설한다 — compose `--profile kotlin` 기동 + Playwright | 기존 두 잡이 그대로 남는다. **Phase 6 의 compose 기반 전체 E2E 가 같은 잡을 재사용한다.** 러너에 Docker 가 있다는 것은 `kotlin` 잡(`:240` 이미지 pull)이 이미 증명했다 | **예** |

**(b) 는 `실행 경로` 열의 어휘를 새로 만든다.** 그 어휘 정본은 `kotlin-migration` 스킬의
「선언한 범위와 실제 도달을 대조한다」 절이고 표기 검사기(`tests/test_harness_scope_reach.py`)가
집행한다. **계약 소유자가 단독으로 정할 자리가 아니다** — §5 OQ-E1 로 올린다.
**그때까지 이 축의 원장 표기는 `안 돎` 이 맞다.** 로컬에서 초록인 것은 실행 경로가 아니다.

### 3-5. 실행 주체

| 일 | 주체 |
|---|---|
| Playwright 도입, `e2e/` 스펙 작성, 픽스처 계정 준비, CI 잡 배선 | **프런트 실행 에이전트** — 리더가 배정한다. `kotlin-implementer` 몫이 **아니다**(Kotlin 코드를 쓰는 에이전트이고, 이 작업은 Kotlin 코드를 한 줄도 만들지 않는다) |
| 케이스 ↔ 계약 조항 매핑의 정본 제공 (§3-2 표) | **contract-keeper** — 이 문서 |
| 완성분의 계약 대조 검증 + 음성 대조 독립 재현 | **contract-keeper** — 별 회차 |
| 실행 경로 어휘 신설 판정, 프런트 실행 에이전트 배정 | **리더** |
| 보안 축(만료 토큰 픽스처가 실제 비밀키를 쓰지 않는지 등) | **privacy-gate** |

**픽스처 계정 주의 하나 — 이건 계약 아닌 안전 문제라 먼저 적는다.** E3·E9 가 요구하는
「유효하지 않은 토큰」을 만들 때 **운영 비밀키로 만료 토큰을 서명하지 않는다.** 서명 없는
문자열이나 다른 키로 서명한 토큰이면 충분하고(둘 다 계약상 같은 401 이다 — `:1494-1497` 이
헤더 누락·위조·만료·용도 불일치·계정 삭제를 **같은 401** 로 못박았다), 그 편이 테스트에
비밀키를 들이지 않는다.

### 3-6. 음성 대조 — 무엇을 뒤집으면 무엇이 빨강인가

**정직하게 층을 가른다.** 「계약 파일 값을 바꾸면 E2E 가 빨강」은 **E2E 가 계약 파일에서 읽는
값에 대해서만** 성립한다. E2E 가 계약을 통째로 파싱하는 것은 과잉이고, 그 일은 이미 Kotlin
계약 테스트가 한다(파서 P-1~P-21). E2E 의 값어치는 다른 데 있다 — **브라우저·클라이언트를
통과해야만 드러나는 것**을 잰다. 그래서 음성 대조를 두 축으로 나눈다.

**축 1 — 계약 파일 변이(E2E 가 계약에서 읽는 값에 한정).** 읽는 값은 셋뿐이어야 한다:
전역 응답 헤더 두 값(`:529-`), CORS 허용 origin·메서드(`:196-201`), 422 이름 규칙의 `detail`
문구(`:1306-1313`). 이 셋을 계약 파일에서 바꾸면 각각 E10·E11·E7 이 빨강이어야 한다.
그 밖의 값은 **E2E 가 읽지 않는다** — 읽으면 계약 테스트의 약한 복제가 된다.

**축 2 — 구현 변이(이쪽이 E2E 고유의 값어치다).** 각 변이가 **정확히 어떤 케이스만** 깨뜨리는지
확인한다. 「전부 빨강」이면 케이스가 서로 결속돼 원인을 못 가린다는 뜻이다.

| 변이 | 어디 | 빨강이어야 하는 케이스 | 지금 이것을 잡는 다른 층 |
|---|---|---|---|
| 사적 헤더 강제 수단(필터/밸브) 제거 | Kotlin | **E10만** | 계약 테스트가 잡는다 — E2E 는 **브라우저까지 도달**을 더한다 |
| 허용 origin 에서 dev 서버를 뺀다 | Kotlin 설정 | **E11 + 그 뒤 전부** (프리플라이트가 막혀 요청이 안 나간다) | **없다.** 서버 테스트는 origin 을 안 본다 |
| 목록 정렬을 뒤집는다 | Kotlin | **E1**(기본 작업 공간이 첫 항목이 아니게 된다) | 계약 테스트가 잡을 수 있다 — E2E 는 **업로드 기본 대상이 바뀌는 결과**를 보인다 |
| 타인 자원에 403 을 낸다 | Kotlin | (E2E 대상 아님) | C 층 X-B1 |
| `client.ts:128` 의 `token !== null` 을 지운다 | **React** | **E2**(로그인 실패가 세션 만료로 오인돼 화면이 다르게 움직인다) | **없다 — 어느 층도 잡지 못한다** |
| `AuthProvider.tsx:31-34` 의 핸들러 등록을 지운다 | **React** | **E3**(토큰은 지워지나 화면이 안 움직인다) | 현행 단위 테스트가 부분적으로 잡는다 |
| 인증 검사를 입력 검증 뒤로 옮긴다 | Kotlin | **E9** | C 층 WC-12·WR-8 이 더 강하게 잡는다 |

마지막 두 줄이 이 E2E 를 정당화한다 — **React 쪽 변이 두 건은 현재 어떤 게이트도 잡지 못한다.**

### 3-7. 이 계획이 재지 **않는** 것 (범위 표시)

- Kotlin 구현이 계약을 지키는지의 **일반** 판정 — 계약 테스트 레인의 일이다. E2E 는 §3-2 표의
  자리만 본다
- 성능·부하·동시성
- 접근성 — Phase 6
- `/health` 진단 응답 — React 가 부르지 않는다(`:1433`)
- 문서·변환·내보내기 전 구간 — Phase 4·6

## 4. 착수 전 확인 항목 (프런트 실행 에이전트용)

1. `docker compose --profile kotlin up -d` 로 `kotlin-api` 가 healthy 가 되는지 — Phase 3 코드가
   들어온 뒤 이 경로가 실제로 도는 것을 확인한 기록이 없다
2. Playwright 도입이 `npm run check`(`tsc -b` + eslint + prettier)를 깨지 않는지 — `e2e/` 를
   `tsconfig.app.json` 범위에 넣을지 별도 tsconfig 로 가를지
3. `npm run test -- --run` 의 기존 통과 수가 **줄지 않는지** — E2E 는 `npm run test` 와 **별
   스크립트**여야 한다. 같은 명령에 묶으면 `frontend` CI 잡이 서버를 요구하게 되어 §3-4 (a) 를
   뒷문으로 채택하는 것이 된다
4. 각 테스트가 **자기 계정을 만들어 쓰는지** — 공유 계정을 쓰면 E4(소유자 범위)와 E6(이름 중복)이
   실행 순서에 의존한다

## 7. 이 문서가 만든 것 / 만들지 않은 것

**만든 것**: Phase 3 「연결」의 최소 정의(§1-2)와 Phase 6 과의 경계(§1-3), 계약 기준 드리프트
목록 6건(§2), 케이스 12건과 층 배정(§3-2), 실행 경로 판정과 CI 배선 후보(§3-4),
음성 대조 2축(§3-6), 미결 5건(§5).

**만들지 않은 것**: 계약 파일 수정, Kotlin 수정, 프런트 수정, 테스트 코드, 원장 갱신.
**E2E 를 실행하지 않았다** — 하네스가 없으므로 이 문서의 모든 「빨강이어야 한다」는
**설계이지 실측이 아니다.** 실측은 하네스가 선 뒤 별 회차에서 한다.
