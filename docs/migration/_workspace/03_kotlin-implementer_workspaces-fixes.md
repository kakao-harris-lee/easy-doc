## 1. X-1 — 삭제된 계정의 유효 토큰 (4관점 합의 · 리더 판정 「구현」)

### 1-1. 처방

`AuthService.authenticate` 가 JWT 서명만 검증하고 끝났다. 확인을 **인증 경계 한 곳**에 넣었다 —
인터셉터가 부르는 그 함수다. 컨트롤러마다 두면 새 엔드포인트가 빠뜨리는데, **그 형태가 정확히
이 결함이었다**(`readUser` 에만 있어서 `/auth/me` 만 닫혀 있었다).

- `UserRepository.exists(id)` 신설 → `SELECT 1 FROM users WHERE id = ?`.
  `findById` 로도 같은 판정이 되지만 그쪽은 **이메일을 함께 읽는다** — 보호된 요청마다 도는
  질의라 쓰지 않을 개인정보를 매 요청 힙에 올리지 않는다.
- **캐시하지 않는다**(리더 지시). 캐시하면 삭제가 캐시 수명만큼 늦게 반영돼 결함이 그대로 남는다.
- 문구는 두 갈래 중 **`invalid_token`**(`이메일 또는 비밀번호가 올바르지 않습니다`)이다. 헤더가
  아예 없는 경우가 아니라 **토큰이 있으나 유효하지 않은** 경우이므로 계약
  `components/responses/Unauthorized` 의 두 예시 중 이쪽이다.
- `AuthenticationInterceptor` KDoc 이 선언하던 「계정 삭제」가 이제 실제로 도달한다(X-23).

### 1-2. 실측 — privacy-gate R-3 의 네 갈래가 전부 401 로 모였다

`DeletedAccountTokenReachTest`(HTTP 경계, 실제 DB, `users` 행 SQL 삭제).

| 경로 | 고치기 전(R-3 실측) | 지금 |
|---|---|---|
| `GET /auth/me` | 401 | **401** |
| `GET /workspaces` | **200 `{"items":[]}`** | **401** |
| `POST /workspaces` | **500**(사용자 FK 위반) | **401** |
| `PATCH /workspaces/{id}` | **404** | **401** |
| `DELETE /workspaces/{id}` | **404** | **401** |

**단언은 「401 이 나온다」가 아니라 「다섯이 서로 구분되지 않는다」다** — 다섯이 각각 401 을 내면서
본문이나 헤더가 갈리면 채널은 살아 있다. 본문 바이트 distinct **1종**, 헤더 이름 집합 distinct
**1종**을 건다. 여기에 **위조 토큰의 401 과도 바이트로 갈리지 않음**을 별도 케이스로 잰다(갈리면
「이 토큰은 한때 유효했다」가 샌다).

반대쪽도 잰다 — 계정이 살아 있는 동안 다섯 경로가 401 이 **아님**을 먼저 확인한다. 없으면
「무엇을 보내도 401 인 구현」과 구분되지 않는다.

### 1-3. 시간 동형 — 유지됐다

매 요청 사용자 조회가 늘었으므로 소유권 404 타이밍 게이트를 다시 쟀다. 4회 실측 비
**1.023 · 1.031 · 1.039 · 1.103** — 새 문턱 1.5 아래이고 종전 관측(1.007~1.068)과 같은 대역이다.
두 갈래가 **똑같이** 질의 하나를 더 도므로 비에 들어가지 않는다.

### 1-4. 부수 발견 — 슬라이스 테스트가 유령 계정으로 16번 통과하고 있었다

`WorkspaceContractTest` 가 소유자를 `UUID.randomUUID()` 로 만들어 **계정이 없는 토큰**을 썼고,
X-1 이후 13건이 빨개졌다. 계정을 실제로 만들도록 고쳤다(커밋 3).
**이 변경이 필요했다는 사실 자체가 X-1 의 도달 증거다.**

## 2. X-3 — 시간 채널 (ⓑ 문턱 · ⓒ 음성 대조)

### 2-1. ⓑ 문턱 2.0 → 1.5 (리더 판정)

`MAX_TIMING_RATIO` 를 auth 로그인 게이트와 같은 값으로 맞췄다. 종전 2.0 의 근거는 문턱을 **넓히는
방향으로만** 쓰였고, 그러면 「10~90% 의 지속 격차」를 전부 승인한다(codex #3).

실측 여유: 4회 최대 **1.103** → 문턱까지 약 36%.

### 2-2. ⓒ 음성 대조 — **빨강이 나오지 않았다.** 그래서 축을 바꿨다

리더 지시는 *"SQL WHERE 소유 조건을 「읽고 나서 비교」로 바꾼 변이 → 문턱 초과 빨강"* 이었다.
일회용 worktree 에서 그 변이를 정확히 만들어 3회 돌렸다.

| 회차 | 없음(ms) | 타인(ms) | 비 | 판정 |
|---|---|---|---|---|
| 1 | 2.769 | 2.804 | **1.013** | 초록 |
| 2 | 2.381 | 2.594 | **1.090** | 초록 |
| 3 | 2.882 | 3.028 | **1.051** | 초록 |

**문턱 1.5 는 물론 종전 2.0 에도 닿지 않는다.** 변이는 404 를 그대로 유지하므로 나머지 21건도
전부 초록이었다. 원인은 구조에 있다 — 「읽은 뒤 비교」와 「WHERE 로 거른다」의 실제 차이는
**인덱스 적중과 불발** 하나뿐이고, 밀리초 단위 응답에서 그것은 측정 잡음에 묻힌다.

**즉 이 게이트는 자기가 잡겠다고 선언한 변이를 잡지 못한다.** 문턱을 좁혀서 될 일이 아니다
(1.09 를 잡으려면 문턱이 1.05 여야 하는데 정상 측정이 이미 1.10 을 찍는다).

**그래서 탐지형으로 갈아탔다**(`CLAUDE.md` 규칙 4의 방향, codex 처방의 후반부 —
*"SQL 또는 query trace 로 owner 조건과 동일 DB 왕복 구조를 강제하라"*).
그 변이가 **실제로 바꾸는 것은 문장의 수**다.

- `CountingDataSource`(테스트 픽스처) — `Connection` 의 문장 생성 호출을 센다.
- `JdbcWorkspaceRepositoryTest`「이름 변경이 소유 결과와 무관하게 같은 수의 SQL 문을 낸다」 —
  없는 자원·남의 자원·**내 자원** 셋이 전부 한 문장을 도는지 단언한다. 지금 구현은 소유 판정과
  갱신을 `UPDATE … WHERE id = ? AND user_id = ? RETURNING …` 한 문장으로 끝낸다.

| 대조 | 없음 | 타인 | 내것 | 결과 |
|---|---|---|---|---|
| 현행 구현 | 1 | 1 | 1 | **초록** |
| 「읽고 나서 비교」 변이 | 1 | 1 | **2** | **빨강** (이 케이스 하나만 — 과잉 결합 없음) |

「셋이 같다」만 걸지 않고 **개수 자체(1)를 못박은** 이유: 셋 다 두 문장이 되는 구현도 「같다」를
만족하는데, 그 형태는 소유 판정이 갱신과 분리됐다는 뜻이라 잡아야 한다.

**시간 축 테스트는 남겼다** — 구조가 옳아도 시간이 갈릴 수 있다. 다만 **그물의 눈이 배 단위라는
사실을 KDoc 에 적었다**. 「측정했으니 게이트도 산다」로 읽히면 ⓒ 가 다시 사라진다.

### 2-3. 남는 사실 (리더 확인용)

`WorkspaceEndpointReachTest` 의 소유권 타이밍 케이스는 **여전히 자기 목표 변이에 대한 음성 대조가
없다**. 구조 축이 그 자리를 덮었지만 **다른 축의 장치**다. 시간 축 자체에 붙는 음성 대조는
「행을 하나 더 읽는 정도가 아니라 배 단위로 느려지는 구현」을 만들어야 하는데, 그런 구현은
소유권 은닉과 무관한 인위적 지연이라 무엇을 확인하는지 불분명하다. **이 상태를 그대로 등재한다.**

## 3. codex medium 4건

### 3-1. X-4 — 파서 fail-open (`ContractSpec.kt`)

`requiredOf` 의 `allOf` 갈래와 `pathParameters` 의 항목을 `filterIsInstance<Map<*, *>>()` 로
걸러 **읽을 줄 모르는 갈래를 조용히 버렸다.** 버리지 않고 끊는다(`error()` + 어느 인덱스인지 표시).

음성 대조(일회용 worktree — 계약에 스칼라 갈래 2곳 주입):

| 대조 | 결과 |
|---|---|
| **종전 파서** + 손상된 계약 | **16건 전건 초록** — fail-open 실증 |
| **새 파서** + 같은 계약 | **5건 빨강**(P-16 · WL-2 · WR-6 · WR-7 · WD-6), 메시지에 주입한 스칼라가 그대로 |
| 새 파서 + 정상 계약 | 16건 전건 초록 — 거짓 양성 0 |

contract-keeper 가 확인한 「P-16 배선 `isNotEqualTo` 로 막음」과 **충돌하지 않는다** — 그쪽은
「배선 누락」, 이쪽은 「지원하지 않는 노드 형태」로 서로 다른 실패 모드다(cross §3-4 판정 그대로).

### 3-2. X-6 — 배압 회귀의 집단 미단언

본문 distinct 개수만 보던 단언은 **한 집단만 전부 500 이고 다른 집단은 전부 401 이어도 통과**한다 —
그리고 바로 그 상태 코드 분포가 계정 존재 열거 신호다. 과부하 부분집합의 키가 두 라벨을 **정확히**
포함하고 각 집단 표본이 0 이 아님을 **먼저** 단언한 뒤 본문 균일성을 본다.

### 3-3. X-7 — 동시 삭제 테스트의 단언

`runCatching { … }.isSuccess` 로 불리언만 남기면 둘째 요청이 **교착·타임아웃·StorageException**
으로 실패해도 같은 단언을 만족한다. 결과 객체를 보존해 **성공 정확히 1건 + 실패가
`ConflictException`** 임을 단언한다. 교착·500 은 이제 실패다.

구현 정확성은 3관점 합의로 이미 통과였고(privacy-gate p2 12/12), 이 조치는 **회귀 검출력**만
고친 것이다. 두 층을 섞지 않는다.

### 3-4. X-8 — 배압 500 · ERROR 로그 → **코드 변경 없음**

계약 결정이 escalate ④(A/B/C)로 리더·사용자 재심에 있다. 판정 전에 응답 코드를 옮기지 않는다.
`GlobalExceptionHandler` 백스톱 KDoc 에 **비율만 사실로 더했다** — 배압 한 건마다 ERROR 한 줄이고,
privacy-gate 4b 의 240 동시 실측에서 로그인 성공률이 6.7% 였으므로 **그 부하에서 로그의 대부분이
이 줄**이다. 「드물게 섞인다」가 아니라는 것이 escalate 의 근거다.

## 4. D-2 / WD-9 — 계약 신설 조항에 결속 (contract-keeper `0fe654c`)

**「작업 공간 하나 + 그 안에 문서」를 지나는 케이스가 0건이었다.** WD-4 는 공간을 하나 더 만들어
두고 WD-5 는 문서를 안 넣는다. 그런데 그 상태는 드문 자리가 아니라 **가입 후 문서를 올리고 두 번째
공간을 만들지 않은 모든 사용자**의 상태다.

- `ContractSpec.deletionRefusalPrecedenceExample()`(P-22) — 계약
  `paths./workspaces/{workspace_id}.delete.description` 의 「둘 다 해당하면 N」을 앵커로 집어
  예시 **이름**을 돌려준다. **조항이 없거나 매치가 둘 이상이면 실패한다**(X-22 가 관찰한

- `WorkspaceEndpointReachTest` WD-9 — 겹치는 상태에서 DELETE → 계약이 가리키는 갈래의 `detail`.
- `WorkspaceService.delete` KDoc 의 「계약이 정하지 않았다」를 정정했다. 구현이 먼저였고 조항이
  뒤따랐지만 **이제 정본은 계약이다.**

## 5. Claude 지적 — A-2 · A-3 · A-4 (+ F-2 · F-3)

### 5-1. A-3 — `toString()` 이 사용자가 적은 이름을 찍는다

계약 자신이 작업 공간 이름을 사적 응답 헤더 대상으로 분류했는데(`x-private-response-headers.applies_to`)
`Workspace`·요청/응답 DTO 가 전부 `data class` 라 기본 `toString()` 이 모든 필드를 찍었다.
`Secret` 이 막는 것과 **같은 기본 동작**이고, `Workspace` KDoc 이 소유자를 담지 않는 근거로
*"담아 두면 toString·직렬화 어디로든 새는 경로가 생긴다"* 를 들면서 `name` 자신에는 같은 규율을
적용하지 않은 비대칭이었다.

`toString()` 에서 이름을 `***` 로 가린다(`Workspace`·`WorkspaceResponse`·`WorkspaceListItemResponse`·
`WorkspaceNameRequest`. `WorkspaceListing`·`WorkspaceListResponse` 는 구성 요소를 타고 자동으로 따라온다).
**가리는 것은 `toString()` 뿐이고 직렬화 값은 그대로다** — 계약이 `name` 을 required 로 뒀다.
그 구분을 `WorkspaceDtoLeakTest` 가 양쪽으로 단언한다.

**오늘 도달은 0이다**(이 경로에 로거 0개). 지금 막는 이유: 비용이 한 줄인데 새는 순간은
**로깅이 처음 들어오는 커밋**이고, 그 커밋을 쓰는 사람은 이 클래스를 다시 보지 않는다.
회귀는 `core`(`WorkspaceNameLeakTest`)와 `api` 양쪽에 둔다 — 모듈 경계를 넘는 두 벌이라야
한쪽만 고치는 변경에서 걸린다.

### 5-2. A-2 — 「터질 수 있는 제약은 하나뿐」 전제를 지키는 장치

`pg_constraint` 를 직접 물어 `workspaces` 를 참조하는 FK 가 정확히
`fk_documents_workspace_id_workspaces` 하나임을 단언한다. **마이그레이션 파일을 문자열로 읽지
않는다** — 그러면 Flyway 가 적용한 것이 아니라 **적힌 것**을 재게 된다.

실패 메시지가 처방을 담는다: *"제약을 늘렸다면 `delete` 의 예외 분류를 함께 고친다."*
그러지 않으면 다른 위반이 「작업 공간에 문서가 남아 있습니다」 409 로 둔갑해, 사용자는 문서를 다
지워도 계속 거절당하고 원인을 알 수 없다.

### 5-3. A-4 — READ COMMITTED 전제 기록

`SpringTransactionRunner` KDoc 에 적었다. 동시 삭제 정합성이 READ COMMITTED 의 `FOR UPDATE`
재평가(EPQ)에 기댄다 — REPEATABLE READ 로 올리면 같은 시나리오가 409 가 아니라 직렬화 실패
(SQLSTATE 40001) → 500 이 된다. **이제 그 자리를 올리면 X-7 조치로 예외 종류를 못박은 동시 삭제
테스트가 빨개진다** — 문면과 장치가 같은 것을 가리킨다.

### 5-4. F-2 — N-18 목록 정정 (수치 16 채택)

`03_kotlin-implementer_workspaces.md` §3-1 을 12 → **16** 으로 고쳤다. 빠졌던 넷은 WR-6·WR-7·WD-6 과
「소유권 404 응답 시간 동형」이다. Claude 재현(13)과 contract-keeper 재현(16)이 어긋난 것이 아니라
**재현 방법의 좁기가 달랐다**는 사실을 정정문에 함께 적었다.

### 5-5. F-3 — 「검사 결과」 표에 **스캐너 실행 결과 exit code** 상시 포함

**이번 배치부터 §7 의 표에 넣는다.** 로컬 검사 집합에서 빠져 있으면 red 를 커밋 전에 볼 방법이
없고, 실제로 두 회차가 red 위에 커밋했다.

### 5-6. A-1 — 개수 상한 (판정 필요 · **사실만**)

- 계약 `x-input-limits` 에 작업 공간 **개수** 상한이 없다(전수 확인).
- `GET /workspaces` 에 페이지네이션이 없다(계약의 명시적 선택).
- `lockForDeletion` 은 매 DELETE 마다 그 사용자의 **행 전부**를 `FOR UPDATE` 로 잠근다.
- 셋이 겹치면 `POST /workspaces` 를 반복할수록 자기 DELETE 가 잠그는 행 수와 목록 응답 크기가
  함께 커진다. **타인에게 닿지 않으므로 ①사건이 아니고, 계약 침묵 자리라 위반도 아니다.**
- **코드 변경 없음.** 상한을 정하는 것은 계약 소유자(contract-keeper)와 리더의 판단이다.

## 6. R-2 — 교환비·세마포어 대기 (코드 변경 없음 · 사용자 판단 대기)

현재 값을 그대로 적는다(`AuthConfiguration.AuthProperties`).

| 항목 | 현재 값 |
|---|---|
| `maxConcurrentHashes`(permit 수 `P`) | **4** |
| `maxHashWaitMillis`(대기 상한 `W`) | **250** |
| Argon2 1회 비용 `H`(실측) | 약 **100ms** |
| 유도 — 줄에서 통과 가능한 요청 수 `W × P / H` | **약 10건** |
| 종전 5000ms 의 같은 수 | 200건 = **Tomcat 기본 스레드 수와 동일** |
| privacy-gate 4b 실측(240 동시) | `/health` max **296.7ms**(종전 1244ms) · 로그인 성공률 **6.7%** |

**절충의 성격**: 대기 상한을 줄여 다른 API 의 지연(1244 → 296.7ms)을 샀고, 그 값으로 로그인
성공률 6.7% 를 치렀다. 어느 쪽을 얼마나 살지는 **용량 결정**이라 리더·사용자 판단 사항이다
(X-25). **이 배치는 값을 건드리지 않았다.**
