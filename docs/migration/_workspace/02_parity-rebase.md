## 1. 무엇이 바뀌었나

사용자 결정(2026-08-12):

> "파이썬이 회귀 문제가 많아서 코틀린으로 이전하고 있는 것이 핵심이야. 파이썬이 완벽한 코드가 아니야. 출력의 결과를 파이썬과 동일하게 맞출 필요는 없어. 프로젝트의 요구사항을 반영/구현하고, 이후에 개선해 나가면 돼."

이 하네스는 정확히 반대 전제 위에 서 있었다. 스킬 description에 "이 하네스의 기준은 현재 Python 동작이지 더 나은 결과가 아니다"가 박혀 있었고, 본문 전체가 "Python 출력과 값이 같은가"를 증명하는 방법론이었다. 그 전제를 폐기했다.

전제가 실제로 해로웠다는 근거는 코드 이력에 있다. `app/easyread/style_rules.py`의 최근 커밋은 `fix: 치환 비문 검출 오탐 제거·회귀 코퍼스 교체`, `fix: 마스킹 보안 구멍 수정(외국인등록번호·무구분자 표기)`, `fix: 골든셋 팩트 허용 변형 보정`이다. 정규식·휴리스틱을 고칠 때마다 오탐과 누락이 번갈아 생겼고, 그 동작을 값으로 굳혀 옮기는 것은 **회귀를 옮기면서 "증명됐다"고 부르는 일**이었다.

새 기준의 정본은 `docs/master-plan.md`다(프로젝트 CLAUDE.md가 그렇게 정한다). 이미 검증 가능한 형태로 적혀 있던 것들을 그대로 쓴다 — §3.2 마스킹 선행, §3.3 변환 호출 최대 2회·골든셋 임계값(`PASS_RATE_THRESHOLD=0.9`, `JUDGE_SCORE_THRESHOLD=4.0`, `DEFAULT_FIDELITY_FLOOR=2`)·스타일 상수(`MAX_SENTENCE_CHARS=50`, `MAX_COMMAS_PER_SENTENCE=2`), §4.0 Lean MVP 범위, §6.2 회귀 방지 4원칙.

## 2. 새 검증 모델

### 2.1 도메인마다 판정 방식이 하나다 (`mode`)

| mode | 도메인 | 판정 근거 |
|---|---|---|
| `spec` | masking, text, style, style-tables, prompts, postprocess, repair-adoption, export | fixture의 `assert` 목록을 Kotlin 산출물에 **실행**한다. Python 출력은 보지 않는다 |
| `compat` | crypto, jwt, argon2 | **값 동일성이 곧 요구사항**이다. 옛 방식 그대로 |

`mode`는 정본 생성기가 정한다. fixture 파일에서 `spec`을 `compat`으로 바꿔 적어 성질 검사를 피하는 경로는 정본 대조가 막는다(실측: 종료 코드 1 + "fixture 위조 의심 — `mode` 가 정본과 다르다").

### 2.2 성질을 fixture로 표현하는 방식

케이스마다 `assert: [{check, args}]`를 싣고, 비교기가 `CHECKS` 레지스트리의 함수를 산출물에 돌린다. 검사 8종:

| 검사 | 방향 | 무엇을 보는가 |
|---|---|---|
| `absent` | under | 가려야 할 문자열이 지정 경로에 남지 않았다 |
| `present` | over | 남겨야 할 문자열이 지워지지 않았다 |
| `restores_input` | 구조 | 자리표시자 역치환이 입력을 **정확히** 복원한다 |
| `placeholder_scheme` | 구조 | `[[{범주}{번호}]]` 형식·범주 집합·범주별 1부터 등장 순서·`items` 짝 |
| `equals_field` | 양방향 | 요구사항이 못박은 값과 같다 |
| `at_most` | over | 수가 상한을 넘지 않는다 (변환 호출 2회 계약) |
| `contains_all` | under | 요구 항목을 전부 포함 — **누락만 막고 추가는 허용** |
| `equals_derived` | 양방향 | 입력에서 **규칙으로 유도한 값**과 같다 (`control_strip`, `repair_policy`) |

설계에서 중요한 둘:

- **`equals_derived`** — 요구사항이 규칙으로 완전히 적히는 자리에서는 비교기가 **자기 힘으로 기대값을 계산한다.** `control_strip`은 `app/text.py`를 import하지 않고 XML 1.0 비허용 문자 집합을 직접 정의해 유도하고, `repair_policy`는 "자리표시자 무손실 AND 위반 미증가"를 산출물이 보고한 건수 위에서 다시 계산한다. Python 구현이 틀려도 기대값이 따라 틀리지 않는 유일한 형태다.
- **`contains_all`** — "이후에 개선해 나가면 돼"의 표현형. 치환 사전 246개를 값으로 비교하면 Kotlin이 항목을 **추가**하는 순간 빨개진다. 포함 관계로 보면 누락은 막고 개선은 통과한다.

속성 기반(property-based) 무작위 생성은 채택하지 않았다. 이 저장소의 결함은 무작위 입력으로 드러나는 종류가 아니라 **경계 표기**(무구분자 주민번호, 전각 숫자, 탭 구분자)에서 나오고, 그 경계는 이미 사람이 알고 있다. 무작위 생성을 얹으면 fixture가 비결정적이 되어 정본 대조(위조 방지의 핵심)를 포기해야 한다. 대신 **결정적 케이스 + 성질 단언**의 혼합을 골랐다.

### 2.3 방향 가드 강제 (새 장치)

성질 검증의 고전적 실패는 한 방향으로만 재는 것이다. "가려졌는가"만 재면 **본문을 통째로 가린 구현이 만점**을 받는다.

- 도메인 단위: `under`와 `over` 검사가 둘 다 없으면 구조 결함 → 종료 코드 1.
- 케이스 단위: `absent`가 붙은 케이스에는 생성기가 **남은 본문 조각에 대한 `present`를 자동으로 덧붙인다.**

실측으로 필요성을 확인했다. 자동 가드 도입 **전**에는 전문 마스킹 스탠드인이 RRN·CARD 케이스 대부분을 통과했고(23건 중 6건만 실패), 도입 **후**에는 22건에서 걸렸다.

### 2.4 Python 출력의 자리 — 참고 갈림 원장

Python 실행 결과는 fixture에 `reference`로 실린다(spec 도메인에서는 `expected`라는 이름을 쓰지 않는다 — 이름이 곧 계약이라 "맞춰야 할 값"이라는 읽기가 되살아난다).

판정에서는 뺐지만 버리지 않았다. 값이 갈린다는 것은 **둘 중 하나가 틀렸다는 신호**라 정보 가치가 크다. 그래서 `parity/reference-ledger/{도메인}.json`에 기록한다.

- 갈렸는데 원장에 없다 → 종료 코드 1. 닫는 방법은 **구현을 되돌리는 것이 아니라** `--record-reference`로 원장을 갱신해 커밋하는 것이다.
- 원장과 관측이 어긋난다(갈림이 생겼거나 사라졌거나 내용이 바뀌었다) → 같은 취급.
- 성질이 **불충족**인 케이스는 원장을 건드리지 않는다. 이미 설명된 차이이고, 고장난 산출물을 원장에 굳히면 그것이 다음 기준이 된다.
- 원장에 본문을 넣지 않는다 — 케이스 id, agree/diverge, 첫 차이 경로, 양쪽 SHA-256뿐이다.

막지 않고 기록만 하는 이유: 차이를 차단 사유로 쓰면 "Python이 정답"으로 되돌아간다. 그냥 통과시키지 않는 이유: 조용한 갈림은 6개월 뒤 아무도 설명하지 못한다. **막지 않되 조용할 수는 없게** — `.github/parity-canonical-floor.txt`가 게이트 축소에 쓰는 것과 같은 방식이다.

### 2.5 회귀의 재정의

| 층 | 회귀 | 잡는 장치 | 등급 |
|---|---|---|---|
| ① 성질 | 어제 충족하던 케이스가 오늘 불충족 | 같은 게이트 + 정본 대조(케이스가 사라지는 경로를 막는다) | 차단 (1) |
| ② 참고 갈림 | 어제 Python과 같던 자리가 오늘 갈림 (성질은 여전히 충족) | 참고 갈림 원장 | 기록 요구 (1, 기록으로 닫힌다) |
| ③ 품질 | 통과율·judge 점수·충실성 하락 | `tests/golden` (범위 밖이지만 회귀 방지의 세 번째 다리) | 골든셋 게이트 |

①이 성립하는 전제는 "케이스가 계속 존재한다"이고 그것을 정본 대조가 지킨다. 값 동일성 시절에도 같았으므로 회귀 방지력은 **줄지 않았다** — 판정 축만 바뀌었다.

## 4. 마스킹 범위 축소 반영

사용자 결정: **주민등록번호·카드번호 2종만 유지.** 근거는 "공용 문서 번역이 주 용도라 개인정보 위험이 낮고, 포팅 비용을 줄여 개발 속도를 얻는다". 정책 문구의 정본은 `docs/master-plan.md` §3.2와 프로젝트 CLAUDE.md이며, 그 문서들은 다른 에이전트가 갱신 중이므로 이 작업에서는 결정 내용만 근거로 썼다. **문서가 확정되면 fixture의 `requirement` 문장과 대조해야 한다.**

fixture: 22 → **23 케이스**(성격이 완전히 달라졌다).

- **가려야 하는 것**(`absent` 8건): 하이픈·무구분자·공백·탭 표기 주민번호, 성별코드 5(외국인등록번호), 앞 6자리 아랍-인도 숫자 주민번호, 하이픈·공백·무구분자 카드번호, 아랍-인도·전각 카드번호.
- **남아야 하는 것**(`present`): 날짜(`2026-01-01`), 12·14자리 숫자열, 이름·주소 줄, 그리고 자동 파생되는 주변 본문 조각.
- **의도한 갈림 3건**: 전화번호·이메일·계좌번호. 현재 Python은 가리므로 참고값과 갈린다 → `reference_divergence: "expected"`. 갈림이 **사라지면**(Python이 따라 축소되면) 선언이 낡은 것이므로 그때 종료 코드 1로 알려 준다.
- **알려진 공백 2건**(`known_gap`): 전각 숫자로만 적은 주민번호(Python이 못 잡는다 — 성별코드 `[1-8]`이 ASCII 리터럴), 숫자 사이 NUL이 낀 표기(마스킹 앞에 `strip_control_chars`가 없다). 요구사항으로는 가리는 편이 맞지만 지금 단언하면 Kotlin에 Python보다 넓은 구현을 요구하게 되므로 **어느 방향도 단언하지 않는다.** 개선하면 원장에 찍힌다. 제어문자 건의 보안 판단은 `privacy-gate` 소관이다.

**계약 레인이 확정한 값과 대조 완료** (`contracts/easy-doc-v1.yaml`): `MaskedItemResponse.category`는 `enum: ["주민등록번호", "카드번호"]`이고 `placeholder`·`missing_placeholders[]`는 `^\[\[(주민등록번호|카드번호)[0-9]+\]\]$`다. fixture의 `placeholder_scheme` 단언이 쓰는 범주 집합·번호 규칙이 이것과 같다 — **값이 한국어 문자열**이라는 점(영문 코드가 아니라)이 자리표시자에 그대로 박히므로 표기가 아니라 복원 키다. 계약의 "전화번호·이메일이 든 문서라도 `masked_items`가 비어 있는 것이 정상"은 fixture의 scope-out 3건이 값으로 검사한다.

유니코드 숫자 실측(이번 세션 재확인, `PYTHONPATH=. uv run python`):

| 입력 | 현재 Python |
|---|---|
| 앞 6자리 아랍-인도 주민번호 | **마스킹됨** (`\d{6}`이 유니코드, `[1-8]`은 ASCII로 맞음) |
| 전부 아랍-인도 / 전부 전각 주민번호 | 매칭 없음 (성별코드에서 끊긴다) |
| 아랍-인도·전각 카드번호 | **마스킹됨** (CARD는 전부 `\d`) |
| RRN 구분자 자리 NBSP·NUL | 매칭 없음 (`[ \t]` 리터럴) |

## 4.1 OQ-1(전역 헤더) 판정이 이 모델에 들어오는 방식

리더 판정(2026-08-12): `Cache-Control: no-store` + `X-Content-Type-Options: nosniff`를 Kotlin은 필터로 **전 응답에 전역 부착**하고, **Python은 고치지 않는다**(현행 10곳 유지 — 은퇴 예정 런타임에 미들웨어를 새로 넣는 위험이 이득보다 크고, 오류 응답에 개인정보가 없다는 실측이 유효하다).

이것은 새 모델의 첫 실사용례다. 옛 전제였다면 "두 런타임의 헤더가 다르다"가 그 자체로 불일치였다. 지금은 **참고 구현의 인정된 이탈**이고, parity 대조에서 불일치로 올리지 않는다 — 판정을 근거로 인용한다. 값 동일성이 요구사항인 자리(compat)와 그렇지 않은 자리를 구분한 것이 문서상의 구분이 아니라 실제 판단을 바꾼다는 증거다.

**parity 쪽에 남는 일은 실패 양상의 이동을 좇는 것이다.** 물어야 할 것이 "누가 한 자리를 빠뜨렸는가"에서 **"필터가 그 응답까지 닿는가"**로 바뀐다. 필터 앞에서 컨테이너가 직접 만드는 응답(malformed HTTP 400, 핸들러 없는 404, 413, 415)이 필터 체인에 도달하는지는 이 저장소에서 **실측된 적이 없다** — Phase 3 실측 항목으로 잡는다. 열거된 10곳의 개별 contract test는 전역 규칙의 하한선이므로 지우지 않는다.

부기(리더 정정): 계약 소유자가 "넓혔다가 좁히려면 서블릿 API에 헤더 삭제 수단이 없어 되돌릴 수 없다"고 적었는데 이는 과장이다. 좁히는 것은 필터에 조건을 더하는 일이지 전송된 헤더를 회수하는 일이 아니며, 절체 전이라 캐시에 남은 응답도 없다. 판정이 틀린 전제 위에 기록되지 않도록 함께 남긴다.

## 5. crypto 계열을 구분해 다룬 근거

`crypto`·`jwt`·`argon2`는 품질이 아니라 **호환성**이다. 절체 후 롤백 창에서 Python이 Kotlin 산출물을 읽어야 하고 반대도 성립해야 한다. 기존 Fernet 문서를 복호화하지 못하거나 기존 Argon2 해시로 로그인하지 못하는 것은 "결과가 조금 다른" 문제가 아니라 데이터 유실·서비스 중단이며, 계획 §5 Phase 7의 즉시 중단 기준이다.

여기서는 "개선"이라는 말이 성립하지 않는다 — 토큰 형식을 더 낫게 만들면 그것은 개선이 아니라 비호환이다. 그래서 이 세 도메인은 `mode: "compat"`으로 **옛 방식을 그대로 유지**했다: 양방향 fixture, tamper·다른 키 거부, `verification.mode = "external"` 역방향 케이스와 비교기 직접 실행, 세 도메인 독립 유지.

## 7. 이 구조가 보장하는 것 / 보장하지 못하는 것

### 보장한다

1. fixture가 정본 생성기의 산출물이다 — 헤더·케이스·**단언**·참고값까지 대조한다.
2. spec 도메인의 단언이 양방향이다 — 한쪽으로만 재는 성질 검증을 구조적으로 막는다.
3. 성질을 적지 않은 도메인은 통과로 집계되지 않는다(pending → 코드 2).
4. compat 도메인의 역방향 판정이 실제 실행에서 나온다.
5. Python과 갈리는 자리가 조용히 지나가지 않는다 — 기록되지 않으면 빨개진다.

### 보장하지 못한다 (조용히 뚫리는 것보다 적어 두는 편이 낫다)

1. **단언이 요구사항을 다 덮는가.** 이것이 새 구조의 핵심 한계다. 값 동일성 시절에는 "전부"를 재는 대신 무엇을 재는지 몰랐고, 지금은 무엇을 재는지 알되 그것이 전부가 아니다. 덮이지 않은 자리는 참고 갈림 원장과 골든셋 게이트가 받는다 — **커버리지는 사람이 리뷰해야 한다.** `{phase}_parity-verifier_coverage.md`에 "성질로 덮이지 않은 자리"를 함께 적기로 했다.
2. **성질이 요구사항의 올바른 번역인가.** `requirement` 문장과 `assert` 사이의 간극은 코드가 검사하지 못한다. 리뷰 항목이다.
3. **산출물을 정말 Kotlin이 만들었는가.** 변함없다. CI 배선(`parityHarness` + `parityManifestCheck`)이 유일한 방어다.
4. **정본 생성기 자체의 위조.** 생성기를 고치면 성질도 따라 바뀐다. 생성기·비교기 변경은 리뷰 게이트를 거친다.
5. **품질.** "가려졌는가"는 말할 수 있어도 "읽기 쉬운가"는 골든셋의 몫이다.

새 구조의 위험은 옛 구조와 방향이 반대다. 옛 구조는 **너무 많이 재서** 개선을 막았고, 새 구조는 **덜 재서** 놓칠 수 있다. 그래서 원장과 방향 가드를 함께 둔 것이다.
