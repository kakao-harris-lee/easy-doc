# Codex 작업 오케스트레이션

Codex가 Easy-Doc 변경 요청을 설계, 구현, 검증, 리뷰, 수정 단계로 진행할 때 따르는 작업 규칙이다. 이 흐름은 Codex 세션과 저장소의 `AGENTS.md`를 사용하며, 제품 런타임이나 별도 자동 실행 프로그램을 추가하지 않는다.

## 상태 흐름

```text
요청 → 범위·완료 기준 확인 → 설계 → 구현 → 검증 → 리뷰
                                      ↑          │
                                      └─ 수정 ───┘
리뷰 통과 → 완료 보고
요구사항 모호·환경 장애·한도 도달 → 진행 중단 및 상태 보고
```

리뷰가 구현 결함을 찾으면 그 지적과 재현 근거를 구현 단계로 전달한다. 리뷰가 구조나 전제의 결함을 찾으면 설계 단계로 돌아간다. 환경 장애는 코드 결함으로 간주하지 않고, 실행하지 못한 검증과 필요한 조치를 보고한다.

## 작업 상태

총괄자는 각 단계에서 아래 정보를 대화 맥락과 결과 보고에 유지한다.

| 항목 | 기록 내용 |
|---|---|
| 목표 | 사용자 요청과 관찰 가능한 완료 조건 |
| 범위 | 읽고 수정할 디렉터리, 허용 경로, 변경하지 않을 경계 |
| 설계 | 수정 대상, 접근 방법, 외부 계약 영향 여부 |
| 실행 역할 | 설계·종합 담당 및 구현 담당 |
| 변경 기준 | 마지막으로 검증한 diff 또는 커밋 식별자 |
| 검증 | 실제 실행 명령, 통과·실패·미실행 상태와 간단한 근거 |
| 리뷰 | 심각도와 파일·동작 근거를 포함한 지적 및 판정 |
| 제한 | 시도 횟수, 사용자 지정 달러 상한, 남은 판단 |

코드가 바뀌면 검증 상태를 `미실행`으로 되돌린다. 이전 변경에 대한 테스트나 리뷰 통과는 최종 변경의 통과 근거로 재사용하지 않는다.

## 단계별 책임

1. **범위 확인:** 가장 먼저 요청된 프로젝트의 `AGENTS.md`와 직접 연결된 테스트만 살핀다. 목표, 허용 경로, 완료 기준, 관련 기존 검증 명령, 최대 재작업 횟수를 정한다. API 계약이 바뀌지 않으면 다른 프로젝트를 열지 않는다.
2. **설계:** Opus 5 역할이 접근 방법, 파일 범위, 검증 계획, 주요 위험을 간결하게 기록한다. 계획만 요청받았으면 여기서 멈추며 구현이나 하네스를 추가하지 않는다.
3. **구현:** Sonnet 5 또는 Codex 역할이 승인된 범위 안에서 변경한다. 독립되고 파일 충돌이 없는 일만 하위 에이전트에 위임할 수 있다. 각 위임에는 경로, 산출물, 검증 책임을 적고 재귀 위임은 금지한다.
4. **검증:** 변경과 직접 연결된 기존 검증을 실행한다. 제품 범위 규칙의 명령을 따른다: 백엔드는 `cd backend-kotlin && ./gradlew build`, 프런트엔드는 `cd frontend && npm run check && npm run test -- --run && npm run build`, Compose 변경은 `docker compose config`. 테스트를 실행하지 못하면 성공으로 추정하지 않는다.
5. **리뷰:** 총괄자는 최종 diff를 요청·완료 기준·실제 검증 결과와 대조한다. 독립 리뷰가 유용하고 위임 가능한 경우 별도 리뷰 에이전트를 쓸 수 있다. 리뷰어에게 범위와 diff를 제공하고 결함만 근거와 함께 보고하게 한다.
6. **수정 또는 종료:** 필수 기준을 모두 만족하면 변경·검증·리뷰 결과와 남은 제한을 보고한다. 결함은 정해 둔 횟수 안에서 수정하고 검증·리뷰를 다시 거친다. 횟수나 예산 상한 도달, 사용자 판단 필요, 안전한 범위 불명확 시 중단 상태와 다음에 필요한 입력을 보고한다.

## 비용과 실행 경계

- 실제 유료 LLM 호출은 명시적인 별도 승인 없이 하지 않는다.
- 비대화형 실행은 작업 시작 전에 구체적인 달러 상한이 명시된 경우에만 시작한다. Codex의 작업 반복 횟수만으로 달러 상한이 강제된다고 주장하지 않는다. 실행 환경에서 비용 상한을 강제·관찰할 방법이 확인되지 않으면 비대화형 실행을 시작하지 않는다.
- 실행 중 사용량을 확인할 수 없고 남은 상한이 불확실하면 추가 유료 호출 전에 멈춘다. 비밀키, 서버 `.env`, 덤프, 사용자 로컬 상태를 작업 산출물에 포함하지 않는다.
- 재시도 상한을 넘기기 위해 같은 실패를 무한 반복하거나 검증 실패를 숨기지 않는다.

## 완료 보고 형식

최종 메시지에는 변경한 파일, 사용자 기준으로 달성한 동작, 실행한 검증 결과, 리뷰에서 남은 지적, 미실행 항목이나 중단 사유를 간결하게 적는다. 통과하지 않은 검증은 통과했다고 표현하지 않는다.
