**상태(2026-09-21): R0·R1과 R2 행동 안내 사용자 흐름(ER-07) 구현·fake E2E 완료, R3 프롬프트 정책의 opt-in 기반(PR #135) 병합, 기본 OFF·미배포.** 다음 개발 우선순위는 **R3 검수 정의·재변환 첫 설명·품질 평가 → R4 표·수치 관계 → R5 검수 이력 → R6 선택 설명 → R7 그림·배치**다. 개발 순서·범위·결정 목록은 [개선 로드맵](plans/2026-09-18-easy-read-improvement-roadmap.md), 작업·구현·UX·검증 문서는 해당 문서의 지도에서 확인한다. ## 2026-09-12 사용량·결제 정책 정리

**2026-09-12 결정:** 유료 결제는 신용·체크카드만 허용한다. 계좌이체, 세금계산서 필요 여부 질문, 카드 취소 후 이체 재수납은 제공하지 않는다. 카드 결제 증빙은 카드매출전표로 처리한다. `/usage`의 세금계산서 요청 폼·목록·조회 호출은 제거했다. 기존 요청 데이터와 관리자 처리/API는 남아 있으며, 신규 요청 API 자체를 폐쇄한 것은 아니다. 상용 결제는 아직 열지 않았다. local/test에는 토스 테스트 카드로 Start를 결제해 한 달 50크레딧을 적용하는 흐름이 구현되어 있고, 실제 청구·세무 증빙은 발생하지 않는다.

사용량 화면은 월 구독 안내와 현재 이용 기간 사용량·현재 남은 이용량으로 단순화한다. 사용량은 결제 완료 또는 무료 이용량 부여로 시작된 정확한 주기 시각부터 집계하고, 미결제·결제 실패·만료 상태의 과거 사용량은 섞지 않는다. LLM 원가·토큰·거래 원장은 사용자 화면에서 제거하고 운영 조회로 다룬다. 상세 증빙 근거는 `docs/plans/2026-09-10-legal-tax-policy-final.md` §3.7을 따른다.

### 1.1 시장 근거 (정확한 표현 기준)

- **법적 근거**: 「발달장애인 권리보장 및 지원에 관한 법률」 제10조 — 국가·지자체는 발달장애인이 이해하기 쉬운 형태로 정보를 제공해야 함. 단, **처벌 조항이 없는 규정이므로 영업·문서에서 "의무화"로 단정하지 않는다.**
- **실질 구매 동인**: 지자체 쉬운 글(읽기 쉬운 자료) 조례 확산, 보건복지부 가이드라인, 기관 평가지표 반영, 장애인정책종합계획.
- **기존 대안**: 당사자 감수 기반 전문 제작 기관(서울시 읽기쉬운자료개발센터 '알다' 등) — 품질은 높으나 고비용·장기간. 본 서비스는 대체가 아닌 **일상 행정문서 영역의 보완재**로 포지셔닝.

## 2. B2G 진입 전략 (3단계)

### Phase 1 — MVP: 소액 수의계약 시장 진입

- 계약 한도(추정가격 기준): **1인 견적 2,000만 원 이하 / 2인 이상 견적 5,000만 원 이하**. 여성기업·장애인기업·사회적기업 특례 해당 시 1인 견적 5,000만 원까지 가능 → **창업 주체의 특례기업 요건 충족 여부를 사업자 설계 단계에서 검토**.
- 결제 방식: 월 구독 + **연간 라이선스(선결제) 병행 필수** — 연 단위 예산 수요를 고려하되 결제는 카드만 허용한다.
- 결제 증빙은 카드매출전표 조회로 제공한다.

### Phase 2 — CSAP 취득 및 디지털서비스몰 등재

- 디지털서비스몰 SaaS 등재의 **필수 전제조건은 CSAP**(클라우드 서비스 보안인증). 2023년 등급제 개편 이후 **하등급(간편평가)** 트랙으로 진입 장벽이 낮아졌으므로 매출 발생 시점부터 준비 착수 (취득 소요 약 6개월+).
- 등재 후에는 **금액 제한 없는 카탈로그 수의계약**이 가능 — 전국 확산의 핵심 경로.
- GS인증은 별도 트랙(제3자단가계약·직접구매 대상)으로, 필요 시점에 별도 판단.

### Phase 3 — 전국 확산 및 프리미엄 라인

- 시·도 단위 기관 계약, 부서 단위 계정 관리 고도화.
- **당사자 감수 파트너십**: 발달장애인 당사자 감수 기관과 제휴하여 "AI 초벌 + 담당자 검수 + 당사자 감수" 프리미엄 티어 제공. 대외 배포용 공식 자료 시장 진입의 신뢰 기반.

## 3. 핵심 정책 결정 (Policy Decisions)

> 이 섹션의 결정은 아키텍처와 계약 문서에 직접 반영된다. 변경 시 반드시 본 문서를 갱신한다.

### 3.1 LLM 전략 — 확정: 추상화 레이어 + 상용 API

- **Provider 추상화 레이어**를 두고 LLM을 교체 가능한 구조로 설계한다. 코드 어디에서도 특정 벤더 SDK를 직접 호출하지 않는다.
- MVP는 상용 API(Claude/GPT 등)로 시작. 벤더 선정은 골든셋 벤치마크로 확정한다. **1차 비교 실행 완료(2026-08-08, 56건)**: 양쪽 완주 36건 기준 claude-sonnet-5가 규칙 통과율(91.7% vs 75.0%)·팩트 잔존(97.4% vs 94.7%) 우위, gpt-4.1이 지연(5.7초 vs 33.5초)·원가(1/3~1/5) 우위. 1차의 Anthropic 측 provider 설정 문제(적응형 사고가 max_tokens 4,096 공유 → 장문 36% 실패)는 수정 후 **재실행 완료(2026-08-08, 56건)**: 실패 20→0, claude-sonnet-5 규칙 통과율 80.4% vs 58.9%(gpt-4.1), 팩트 잔존 90.1%. 남은 확정 변수는 원가(정상가 기준 약 2.9배)·지연(약 3.3배) 수용 여부와 no-training 약관 확인, 그리고 judge 충실성 관찰 1건(문서 020 사람 대조 진행 중).
- **알려진 제약 (해소됨)**: claude-sonnet-5는 `thinking` 미지정 시 적응형 사고가 기본 켜지며 사고 토큰이 `max_tokens`를 공유한다. provider 기본값에 반영 완료 — max_tokens 16,000 + `LLM_EFFORT` 설정(채택: low. 사전 실험에서 medium 이상은 규칙·팩트 이득 없이 비용만 증가). 근거: `docs/benchmarks/2026-08-08-2136-llm-benchmark.md`.
- **벤더 확정 기록** (확정 시 채운다):

| 항목 | 내용 |
|---|---|
| 확정 벤더 · 모델 ID | 상용 벤더 확정은 별도 판단. **로컬 검증 구성(2026-09-12): openai / gpt-6-astra / medium**. 코드의 provider 기본값은 anthropic이며 로컬 `.env`가 덮어쓴다. 현재 품질·원가 근거는 [프롬프트·사전 재검증 보고서](reports/2026-09-12-prompt-rag-revalidation.md)에 기록한다. |
| 확정일 | (미정) |
| 근거 리포트 | `docs/benchmarks/2026-08-08-1642-llm-benchmark.md` (1차 비교) + `docs/benchmarks/2026-08-08-2136-llm-benchmark.md` (설정 수정 후 재벤치마크 + effort 실험·결정) + `docs/quality/` 리포트들 |
| no-training 약관 확인일 | (미확인 — 확정 전 필수) |
- 필수 계약 조건: **입력 데이터 학습 미사용(zero data retention 또는 no-training 조항)**.
- 국외 이전 리스크 관리: 마스킹 후 전송(3.2 — **2026-08-12부터 주민등록번호·카드번호 2종 범위**) + 개인정보처리방침·위탁 문서에 국외 이전 고지. 마스킹이 걷어 주는 범위가 좁아진 만큼 국외 이전 고지와 no-training 조항의 비중이 상대적으로 커진다. B2G 본격화(Phase 2) 시 국내 리전/국산 LLM 옵션을 추상화 레이어에 추가.

### 3.2 데이터 처리 정책

- **제품 전제(2026-09-07, 사용자 결정)**: 이 제품이 변환하는 것은 복지·행정 등 **공공 목적으로 배포되는 문서**이고, 그 문서에는 개인정보가 들어오지 않는다. 그래서 **개인정보 마스킹은 하지 않는다.** 2026-08-12에 5종에서 2종(주민등록번호·카드번호)으로 줄였던 자동 마스킹은 2026-09-07에 코드·계약·화면에서 **제거**했다(`docs/plans/2026-09-07-remove-masking.md`). 남겨 두면 마스킹 관련 작업이 계속 후보로 올라와 혼선을 만든다는 것이 제거 이유다. 위탁 계약서·처리방침·국외 이전 고지를 준비한다는 옛 항목도 같은 이유로 파기했다 — 그 근거는 B2G 영업에서 기관 문서를 「개인정보 처리 위탁」으로 볼 것이라는 초기 가정이었고, 제품 전제와 어긋난다. 업로드 화면의 「개인정보 포함 문서 지양」 안내는 남긴다.
- **보존·삭제**: 업로드 원문·변환 결과는 암호화 저장, 기본 보존 30일 후 자동 삭제(기관 설정으로 조정 가능). 삭제 요청 시 즉시 파기. 검수 피드백의 자유 의견(`conversion_feedback.comment_encrypted`)도 같은 기본 30일을 따른다 — 판정 근거인 척도 숫자(배포 의향·품질 만족도·소요 시간·수정률 지표)는 문서 파기 사슬 밖에서 영구 보존하되(`docs/kotlin-redevelopment-backlog.md` §1.1), 의견에 섞여 들어오는 문서 본문 조각만 `easydoc.feedback.comment-retention-days`로 별도 삭제한다.
- **로그**: 애플리케이션 로그에 문서 본문·개인정보를 남기지 않는다. 감사 로그는 행위(누가·언제·어떤 문서 ID) 단위만 기록.

### 3.3 품질 신뢰 체계

- **이해 기준 — 사용자 재확인(2026-09-12):** 보편적인 초등학교 5~6학년 정도의 어휘와 문장으로 공공문서를 자연스럽게 풀어 쓴다. 문서에 등장하는 대상의 나이로 독해 수준을 바꾸지 않는다. 독자 개인마다 다른 이해도를 보장하거나 모든 단어·문장의 정답을 미리 정의하는 것을 제품 목표로 확대하지 않는다.
- **작성 기준:** 어려운 행정 표현은 일상적인 말로 바꾸고, 관련 문장은 문단 안에서 연결한다. 문장만 잘게 나누거나 뜻풀이를 기계적으로 끼워 넣지 않는다. 공식 이름은 유지하되 문맥 이해에 필요한 낯선 개념은 가까운 자리에서 간단히 설명한다. 모든 낱말에 풀이를 붙이지 않는다. 원문의 대상·조건·금액·날짜·행위 주체·필수/선택 관계는 유지한다.
- **진행 기준:** 실제 초등학생 모집·독해 실험, 문서별 정답집, 대규모 사전의 선행 구축은 개발·모델 선택의 필수 조건이 아니다. 기존 문서와 산출물로 전반적인 어휘·문장 수준, 자연스러움, 의미 보존을 비교하며 개선한다. 사전은 문맥에 맞는 표현을 돕는 보조 자료로 사용한다.
- **평가 해석:** 낯선 표현 하나나 설명 한 곳의 부족만으로 문서 전체·모델 전체를 자동 탈락시키지 않는다. 문서 전반이 여전히 어렵거나 핵심 조건을 이해하기 어렵게 쓰였는지와 국소적인 표현 개선점을 구분한다. 사실·자격 조건의 변경은 별도의 의미 오류로 엄격히 다룬다. 기존 judge 통과율과 과거 판정은 당시 기준의 기록이며, 이 정책으로 소급해 합격률을 고쳐 쓰지 않는다. 2026-09-12 구현·실측은 [재검증 보고서](reports/2026-09-12-prompt-rag-revalidation.md)에서 소스·전체 출력·판정·비용을 함께 확인한다.
- **평문 구조 지시:** 붙여넣기(TEXT)·TXT의 추정 목록은 화면 비교용으로 보존하되 전체 생성의 줄 수 제약에서 제외한다. DOCX·HWPX·PDF의 추출된 표 구조는 기존대로 보호한다. 2026-09-12 실제 worker 경로에서 확인한 생성 지시 충돌을 반영했다.
- **원문 위치 표식(2026-09-12):** 제목·항목·주의사항의 `○`, `-`, `*`, `※`, 번호는 같은 항목 앞에 보존한다. 문장은 쉽게 고치고 `※` 안내는 바로 다음 줄로 나눌 수 있다. 원문에 표식이 있으면 설명용 새 표식을 추가하지 않는다. 표식의 종류·개수·순서 변경은 보정 대상으로 검사한다. [표식 보존 수정·실측](reports/2026-09-12-document-markers.md).
- **선택 단어 조회(2026-09-12):** 임의 부분 문자열 검색을 제거하고 선택 전체의 표면형·조사 일치를 검사한다. 복합어 설명은 확인된 3개 관계만 허용하며, 무관한 설명 후보도 음성 사례에서 실패로 판정한다. [조회 정확도 수정 기록](reports/2026-09-12-dictionary-lookup-fix.md).

- **자동 보정(2026-09-12 개정):** 한 번의 통합 프롬프트와 문맥에 맞는 사전 참고 자료로 쉬운 글을 만든다. 길이·쉼표·낱말의 기계 지적은 진단으로 남기며 이것만으로 전체 재서술을 요청하지 않는다. 검출한 사실 누락·뜻풀이 충돌·이중 피동·원문 표식 변경이 있을 때만 보정 1회를 호출한다. 최대 2회 상한·실패 시 첫 초안 유지·새 사실 누락 시 보정 거부는 유지하며, 원문 표식을 훼손한 보정도 거부한다. 모델 변경 시 첫 초안의 전체 어휘·문장 수준과 의미 보존을 다시 확인해야 한다. 이는 사용자 재변환의 별도 호출 예산을 바꾸지 않는다.

- **골든셋**: 실제 복지 안내문과 기대 사실을 `data/golden/documents/`에 언어 독립 JSON으로 보존한다(56건, `required_facts` 253개). 프롬프트·모델 변경 시 Kotlin 스타일 규칙 검사 + opt-in LLM-as-judge를 CI에서 강제하는 것이 목표다. **2026-08-24 기준** `backend-kotlin` 품질 게이트가 스키마·원문 사실 잔존·변환 스냅샷 스타일/사실·커밋된 기준선(`golden-baseline.json`: 파일명·ID·정규화 JSON digest·통과 건수)을 `./gradlew build`에서 검사한다. LLM-as-judge는 `./gradlew testLlm`이며 비밀값이 없으면 skip하고, 있으면 골든 문서를 실제로 변환해 채점한다. `Prompts.kt`·`StyleRules.kt` 스냅샷 테스트는 프롬프트/규칙 데이터의 정적 회귀를 계속 담당한다.
- **쉬운 글 스타일 규칙**: 국립국어원·보건복지부·알다 가이드라인 기반 체크리스트(문장 길이, 한 문장 한 정보, 어려운 한자어 치환, 능동태 등)를 명문화하여 프롬프트와 평가 기준에 공통 사용.
- **HITL**: 모든 결과물은 담당자 검수 후 확정. "AI 초안"임을 UI에 명시.
- **변환 호출 계약**: 문서 변환 1건 = LLM 호출 **최대 2회** — 변환 1회 + 사실 누락·뜻풀이 충돌·이중 피동이 기계 검출된 경우에만 보정 1회(루프 없음, 보정 실패·악화 시 첫 초안 채택; 2026-09-12 개정). 크레딧 원가 산정(5장)은 이 상한을 전제로 한다. **알려진 품질 한계(2026-08-08 갱신)**: gpt-4o의 장문 자체 요약(압축) 문제는 기본 모델을 gpt-4.1로 교체해 해소했다(전건 정상 팽창·충실성 바닥 0건 — docs/quality/2026-08-07-model-comparison.md, 2026-08-08-golden-reeval-gpt41.md). 분할 변환 필요성은 소멸. 현재 남은 한계는 **장문에서 문장 길이 등 스타일 규칙 준수율 하락**(2,000자 초과 통과율 0.11)으로, 파일럿 안내의 2,000자 내외 권장은 이 사유로 유지한다. **⚠ 이 두 판정(필요성 소멸·2,000자 권장)은 gpt-4.1에서 잰 값이다.** 제품 provider는 그 뒤 anthropic·claude-sonnet-5로 바뀌었다. 2,000자 초과 통과율은 아래 부분 관측(2026-08-30)이 같은 구간을 현재 모델로 다시 쟀지만 각 조건 1회·15건의 눈금이라 판정을 갱신하지 못하고, 「필요성 소멸」 판정 자체는 현재 모델에서 재검된 적이 없다. 2026-08-27 파일럿 표본 10건은 전부 3,076자 이하여서 장문 구간을 건드리지 않았다. 재측정은 §9 「게이트 ⓪」이 소유한다 — **그 결과가 나오기 전까지 이 줄의 두 숫자를 근거로 쓰지 않는다.** **→ 2026-09-03: 이 권장은 §9 게이트 ⓪ 판정으로 폐기됐다 — 상한 20,000자(계약 2.7.0), 근거는 현재 모델 3차 측정.** **→ 개정(2026-09-05, 사용자 확정; 근거 `docs/plans/2026-09-04-p0-4-paragraph-mapping-reconversion.md` §4):** 자동 변환 1건 = LLM 호출 최대 2회(변경 없음). 사용자 재변환은 문서당 호출 예산(기본 20회, 구성값 `easydoc.reconversion.call-budget`) 안에서만 실행되며, 예산은 요청이 아니라 실제 호출 수로 예약·정산한다.
  - **현재 모델 부분 관측(2026-08-30)** — 위 0.11을 **대체하지 않는다.** claude-sonnet-5(effort=LOW)로 골든 코퍼스를 각 조건 1회 돌린 값이다: **2,000자 초과 15건 스타일 통과 11/15(73.3%, 사전 컨텍스트 주입 off) · 9/15(60.0%, on)**, 2,000자 이하 41건 36/41(87.8%) · 38/41(92.7%). **두 값의 13.3%p 차이는 15건 표본에서 95% CI ±33.4%p라 잡음과 구분되지 않는다** — 주입 여부에 따른 차이로 읽지 말고, 현재 모델의 이 구간 통과율이 대략 어디쯤인지의 눈금으로만 쓴다. gpt-4.1 시절 0.11과는 자릿수가 다르다. **이 측정의 범위는 골든 최대 글자수(3,993자)까지다** — 여기서 말하는 "2,000자 초과"는 실제로는 **2,000~3,993자**이고, 게이트 ⓪이 보는 4,000자 초과 구간은 골든셋에 표본이 없어(§9) 이 값으로는 닫지 못한다. 애초에 이 측정의 목적은 게이트 ⓪ 재측정이 아니라 사전 컨텍스트 주입 A/B였다(부수적으로 나온 값이다). 상세와 한계는 `dictionary/docs/consumer-overlap-policy.md` §5.1. **재측정 소유권은 §9 「게이트 ⓪」 그대로이며, 위 "두 숫자를 근거로 쓰지 않는다"도 그대로다.**
- **절단 방지**: LLM 응답이 토큰 한도에서 잘리면(truncated) 실패로 처리하고 사용자에게 내보내지 않는다. 한도를 넘는 긴 문서는 분할 변환으로 대응한다(P0-3 비동기 처리와 연계, 분할 단위·크레딧 환산 관계는 구현 시 확정). **분할 변환 구현 전까지는 문서당 4,000자(공백 포함) 상한을 업로드 시점에 안내·거절한다** — 상한값은 골든셋 LLM 평가로 출력 팽창비를 측정한 뒤 재조정한다. **→ 20,000자(2026-09-03)**
- **당사자 감수**(Phase 3): 프리미엄 티어로 제공.

### 4.0 Lean MVP 권고안 — 파일럿 검증용 최소 제품

v1 기획의 MVP는 물론, 아래 P0 전체(11개)도 "정식 출시" 기준이다. **첫 6주 안에 파일럿 기관에 보여줄 제품은 그보다 더 작아야 한다.** 이 사업의 최대 리스크는 기능 부족이 아니라 "변환 품질이 실무자 기준을 통과하는가"이므로, Lean MVP는 그 검증에만 집중한다.

**Lean MVP 포함 (5개):**

| 기능 | 범위 축소 방식 |
|---|---|
| 계정 | 이메일 가입만. 소셜 로그인은 별도 진행. 세금계산서 자동 발급은 카드 전용 정책으로 제외 **→ 정정(2026-09-04, 사용자): 공공 도메인 인증은 하지 않는다 — 4.1 P0-1 참고.** |
| 문서 입력 | 텍스트 붙여넣기 + docx/pdf/hwpx 텍스트 추출 |
| AI 변환 + 마스킹 | 핵심 파이프라인. 마스킹 선행은 정책상 처음부터 필수이되 **범주는 주민등록번호·카드번호 2종** (3.2) |
| 분할 화면 에디터 | 원본/결과 비교 + 직접 수정 + docx 다운로드. 문단 단위 재변환은 다음 단계 |
| 변환 기록 | 목록 + 재다운로드 수준 |

**Lean MVP에서 의도적으로 뺀 것과 근거:**

- **결제 자동화(PG 연동)**: 무료 파일럿에서는 유료 주문·입금을 받지 않는다. 유료 전환 시 카드 정기 결제와 매출전표 조회를 연동한다.
- **쉬운 말 사전 RAG(2026-09-12 확인)**: 빌드된 JSON 색인의 문자 트라이·낱말 경계로 문서와 관련된 항목을 찾고, 우선순위·개수·문자 예산으로 선별한다. 임베딩 검색은 현재 경로에 없다. 생성에는 표현 후보·뜻풀이·검수 완료 예문을 참고 자료로 주고, 다른 사업의 조건이 섞인 주의 메모는 제외한다. 조회 API는 별도 스위치이며 선택한 낱말의 후보와 주의 메모를 제공한다. 사전 수량이나 임의의 ‘80%’ 수치로 효과를 주장하지 않는다.
- **랜딩 페이지**: 파일럿은 영업으로 데려오므로 1페이지 소개면 충분.
- **운영자 어드민**: 초기 고객 1~2곳은 DB 직접 조회/스프레드시트로 운영.

**Lean MVP의 성공 기준 (이걸 통과해야 P0 완성에 투자):** 파일럿 실무자가 실제 문서 10건을 처리했을 때 ① 외주 대비 시간이 유의미하게 단축되고 ② "이 결과물을 다듬어 실제로 배포하겠다"고 답하는 것.

- **연간 라이선스**: 각 플랜의 12개월 선결제(할인 적용) — 공공 예산 집행 방식 대응, 수의계약 견적의 기본형. **크레딧은 매월 나눠 부여한다**(연초 몰아쓰기와 중도 해지 정산 문제를 피한다).
- ~~추가 충전: 50크레딧 단위 Add-on~~ → **폐기(2026-09-10, 사용자 결정).** **별도 구매·충전 기능을 제공하지 않는다.** 이용량이 모자라면 상위 플랜으로 올린다.
- 모든 요금은 소액 수의계약 한도(연간 기준) 안에서 설계한다.

**결제 수단 — 신용·체크카드만 허용한다(2026-09-12).** 기관·연간 계약도 계좌이체 예외 경로를 제공하지 않는다.

**크레딧은 「구독에 포함된 주기 이용량」이다(2026-09-10, 사용자 결정 — 2026-09-08 「만료 없음」과 2026-09-09 「묶음별 만료」를 모두 대체한다).** 크레딧은 낱개로 파는 선불 상품이 아니라 **각 결제주기에 포함된 문서변환 이용량**이고, **결제주기가 끝나면 초기화하며 이월하지 않는다.** 통신 요금제의 월 데이터 제공량과 같은 성격이다.

미사용 잔액이 무한히 쌓이면 그것이 곧 부채라는 문제의식은 그대로이고, 별도 판매를 없애면서 **묶음·만료일·차감 순서라는 복잡도가 통째로 사라졌다.** 법적으로도 가벼워진다 — 「신유형 상품권 표준약관」의 유효기간·환급 기준은 판매되는 상품권을 겨눈 것이라 구독 포함 제공량과는 멀다.

**결제 증빙은 카드매출전표로 제공한다.** 별도 세금계산서 요청·결제 전 질문·카드 취소 후 이체 재수납은 폐기한다. 기존 요청 기록의 관리자 처리와 보존은 유지한다.

### 6.2 회귀 방지 4원칙 (2026-08-24 Kotlin/frontend 기준으로 재작성)

1. **의존성 잠금 (Gradle)**: `dependencyLocking`으로 재현 가능한 빌드. 전이 의존성이 조용히 올라가는 것을 락파일로 막는다.
2. **엄격한 타입 (Kotlin 컴파일러 + `allWarningsAsErrors`)**: 모든 함수 시그니처와 API 입출력에 타입 필수. API 입출력은 Kotlin data class(요청/응답 DTO)로 표현한다.
3. **코드 규격화 (ktlint + detekt)**: 포맷·린트·정적 분석 단일화. *(스타일 통일 도구이며 논리 오류를 막는 도구는 아님 — 논리 오류는 테스트가 담당)*
4. **CI/CD (Compose + GitHub Actions)**: `compose.yml`은 PostgreSQL·migrate·API·worker·frontend 전체 런타임을, `compose.ci.yml`은 `backend-check`·`frontend-check` 검증 서비스를 추가한다. CI는 두 Compose 모델의 유효성과 독립 프로젝트 게이트, Playwright E2E를 확인한다. CD는 같은 Compose build 정의로 backend/frontend 이미지를 GHCR에 게시한다. 실제 환경 배포는 대상 인프라가 결정된 뒤 추가한다. **Kotlin 골든셋 평가기는 아직 backlog다.**

**검증 기준**: 판정 기준은 **요구사항·정책(3장)·공개 API 계약 충족**이다. API 계약도 개선할 수 있지만, 변경 기록과 Kotlin 소비자·React 소비자를 같은 변경 단위로 맞춰야 한다. 마스킹 선행처럼 정책 자체가 순서를 정한 불변식은 구현 선택으로 완화할 수 없다.

> **2026-08-24 재개발 전환 완료.** 요구사항·API 계약·React(UI/UX)를 기준으로 Kotlin 제품을 개발한다. 제거 결정은 `docs/plans/archive/transition/2026-08-24-python-removal-for-kotlin-redevelopment.md`에 보관하며 현재 실행 계획으로 사용하지 않는다.
>
> 저장 암호화는 표준 AEAD(호환을 위한 Fernet 제약 없음)로 구현한다. round-trip·변조 거부·키 회전은 여전히 요구사항이며, 판정 근거는 값 동일성이 아니라 성질 충족이다.
>
> **재개발이 해결하지 않는 것**: 골든셋 통과율과 장문 처리 품질은 **런타임 언어와 무관**한 프롬프트·긴 문서 처리 전략의 문제다. Kotlin 쪽 골든셋 평가 도구가 아직 없으므로(위 6.2 4번) 수치 재측정은 그 도구가 생긴 뒤의 과제다.

### 6.3 접근성

- 서비스 자체가 **KWCAG(한국형 웹 콘텐츠 접근성 지침)** 를 준수한다. 접근성 서비스가 접근성이 낮으면 신뢰와 공공 조달 양쪽에서 치명적.

**게이트 ⓪ — 긴 문서 처리(게이트 ①의 선행 조건, 2026-08-27 추가)**: 실무 문서 길이를 제품 경로로 처리할 수 있는지 판정하기 전에는 파일럿을 착수하지 않는다.

근거는 실측이다. 2026-08-27에 `docs/golden`의 실제 공개 문서 중 **가장 작은 hwpx 3건과 pdf 1건**을 제품 경로로 올렸더니 **네 건 모두 422**였다(`현재는 4,000자 이하 문서만 변환할 수 있습니다`). 형식·용량 문제가 아니라 전부 길이에서 걸렸고, 그래서 같은 날 실행한 표본 10건은 **전량 텍스트 붙여넣기**로 들어갔다(`source_format = text`). 실제 안내문·사업안내는 1만 자를 넘는 것이 드물지 않다(2026-08-27 사용자 판단).

이것이 게이트 ①을 막는 이유는 기능이 모자라서가 아니라 **측정이 성립하지 않기 때문**이다. 4.0의 성공 기준은 "외주 대비 시간이 유의미하게 단축되는가"인데, 실무자가 문서를 손으로 잘라 여러 번 올린 시간은 제품이 만든 시간이 아니다. 상한을 둔 채로 파일럿을 돌리면 통과해도 실패해도 그 숫자가 무엇을 뜻하는지 말할 수 없다. 4단계에서 완성한 원본 형식 보존 내보내기(DOCX·HWPX) 역시 파일 업로드가 상한에 걸리는 한 파일럿에서 한 번도 실행되지 않는다.

**이 게이트는 분할 변환 구현을 뜻하지 않는다.** §3.2는 2026-08-08에 「분할 변환 필요성은 소멸」로 판정했고 그 판정을 여기서 뒤집지 않는다. 다만 **그 판정의 근거 모델은 gpt-4.1이고 현재 제품은 anthropic·claude-sonnet-5다**(2026-08-27 실행 기준). 같은 절이 남긴 한계 — 2,000자 초과에서 스타일 규칙 통과율 0.11 — 도 그 모델에서 잰 값이다. 현재 모델 측정은 골든 최대 글자수(3,993자)까지의 부분 관측(§3.2, 2026-08-30)뿐이고, 이 게이트가 보는 4,000자 초과 구간은 표본이 없다. 그래서 게이트 ⓪의 내용은 구현이 아니라 **측정과 선택**이다:

1. **먼저 잴 수 있게 만든다.** §3.2는 측정 방법으로 골든셋 LLM 평가를 지목했고 `./gradlew testLlm`이 그 레인이지만, **오늘 그 레인으로는 이 게이트를 판정할 수 없다.** 막힌 곳이 둘이다.
   - **장문 표본이 없다.** 승인된 골든셋 56건 중 4,000자를 넘는 것이 **0건**이고 최댓값이 3,993자다 — 현재 상한에 맞춰 수집된 말뭉치라 상한 밖을 잴 재료가 애초에 없다. 1만 자 구간은 아예 비어 있다.
   - **레인이 제품과 다른 모델을 잰다.** `GoldenCorpusLlmEvaluationTest`는 `OPENAI_API_KEY`가 있으면 OpenAI를 먼저 고르고 `easydoc.llm` 설정(provider·model)을 읽지 않는다. 키가 둘 다 있는 환경에서 돌리면 제품이 쓰는 anthropic·claude-sonnet-5가 아니라 **또 다른 모델의 값**이 나온다 — §3.2의 옛 판정이 gpt-4.1 값이어서 못 쓰게 된 것과 같은 함정이다.

   - **출력 토큰 상한이 장문을 감당하지 못한다.** `DEFAULT_MAX_TOKENS`가 **16,000으로 코드에 박혀 있다**(`core/llm/LlmProvider.kt:7`). 2026-08-27 실측에서 1,500자 문서가 출력 3,902토큰, 2,113자 문서가 7,479토큰을 썼다(최대 2회 호출 합계라 상계치다). 그 비율이면 **1만 자는 16,000토큰 안에 들어오지 않는다** — 응답이 `max_tokens`에서 잘리고, 절단은 §3.2 규칙대로 변환 실패(`ConversionFailureKind.TRUNCATED`)가 된다. 상한만 올리면 장문이 전부 실패로 떨어지는 구조다. **→ 해소(2026-08-31):** 상한을 `easydoc.llm.max-output-tokens`(env `EASYDOC_LLM_MAX_OUTPUT_TOKENS`, 기본 16,000) 구성값으로 옮겼고, 평가 레인도 같은 해석을 따라 측정 조건 보고에 `max_tokens`를 싣는다. 이제 측정에서 상한을 구성으로 바꿔 가며 절단율을 잴 수 있다.

   그래서 게이트 ⓪의 첫 작업은 측정 실행이 아니라 **측정을 성립시키는 것**이다: ⑴ 장문 골든 표본을 승인 경로에 넣는다(후보는 `docs/golden-drafts/`에 남겨 둔 `022`·`023`·`047`·`050`이며, `golden-baseline.json` 갱신은 리뷰 승인 사항이다 — `docs/golden-collection-plan.md` 「초안 감사 기록」) ⑵ 레인이 제품 provider 설정을 따르게 한다 ⑶ 출력 토큰 상한을 코드 상수에서 구성값으로 옮긴다(CLAUDE.md 「상수와 구성 관리」 — 운영 중 바뀔 수 있는 값은 `@ConfigurationProperties`다). **진행 상태(2026-08-31): ⑵·⑶ 완료. ⑴은 초안 4건이 승인 가능 상태로 준비됐다**(022 평문 연락처 자리표시자화, 022·023 required_facts·category 초안 — 리뷰 대기). 승인 디렉터리 이동은 변환 스냅샷과 `golden-baseline.json` 갱신과 같은 변경 단위다. **1차 측정은 2026-08-31 사용자 승인下에 실행됐다**(장문 4건·각 1회·`max_tokens=64000`·dictContext=off) — 절단 0/8 호출·단일 호출 최대 출력 7,621토큰(현행 16,000의 절반 이하, **주입 off 조건에 한한 값**), 팽창비 중앙 0.90(수축 문서 존재 시사, 문서별 값 미기록이라 022 단독 값 미확정 — 이 계측 결함은 2026-09-01 보정됐으나 1차 측정은 보정 전 실행이라 022 단독 값은 여전히 미확정), 050 사실 누락 3(**→ 2026-09-01 facts 검수로 원인 최소 1건은 변환 결함이 아니라 facts 초안 오류로 확인·교체됐다 — 나머지는 변환문 없이 확정 불가**). 수치와 읽는 법은 `docs/kotlin-redevelopment-backlog.md` §1.2. **022 변환문 실물 확인이라는 절차 자체는 2026-09-01 2차 측정(dictContext=product)에서 이뤄졌지만, 그 확인만으로 판정이 서는 것은 아니다 — 판정은 상한값 재조정 쪽이 유력하나 확정은 보류 중이다(2026-09-01 정정, 아래 「판정 — 상한값 재조정 쪽이 유력하나 확정은 보류」 참고).** **레인의 사전 컨텍스트 주입이 제품 경로가 아니었던 결함은 2차 측정 전에 보정됐다(2026-09-01, 레인 `src/test`만·제품 코드 무변경) — 상세는 `docs/kotlin-redevelopment-backlog.md` §1.2.** 레인이 변환문을 보존하지 않던 문제도 같은 날 노브(`EASYDOC_LANE_TRANSCRIPT_DIR`, 레인 `src/test`만)로 해소됐다 — 판정 기준(022 변환문 실물 확인)은 그대로이며, 상세는 같은 절.

   그 셋이 끝난 뒤 측정한다. **측정 항목은 셋이다**: 출력 팽창비, ~~스타일 규칙 통과율~~ **위반 밀도(문장당 스타일 위반 수)**(**결정 2026-09-02, PR #12 Codex 승인 뒤 사용자 확정 — 이진 통과율을 대체한다.** 근거는 이미 `docs/kotlin-redevelopment-backlog.md` §1.3 「사전 컨텍스트 주입과 스타일 통과율」에 있다: 통과율은 문서 단위 all-or-nothing 누적이라 길이 축에서 편향되고, `DIFFICULT_WORD` 과잉 발화로 용어 구성 축에서도 편향된다. **「무너짐」 판정 임계값(같은 실행의 단문 구간 대비 얼마나 나빠지면 붕괴로 볼지)은 이 결정에서 정하지 않는다 — 측정 뒤에 정한다.**), 그리고 **절단 발생률**. 앞의 둘만 재면 "품질은 괜찮은데 절반이 실패하는" 상태를 통과로 읽게 된다.

   **측정 설계(결정 2026-09-02):** 승인된 장문 골든 표본 각각을 **3회씩** 반복 실행한다(1·2차 측정의 n=4 각 1회 눈금을 벗어나기 위함). 조건은 제품 구성 — **anthropic·claude-sonnet-5·dictContext=product**·`max_tokens=64000`. 유료 실행이므로 착수 전 별도 비용 승인이 필요하다(CLAUDE.md 모델·비용 정책).
2. **그 결과로 고른다.** 상한 상향만으로 1만 자가 처리되면 **상한값 재조정으로 끝낸다**(§3.2의 원래 처방). 장문에서 품질이 무너지면 그때 분할 변환을 착수한다 — 그 경우에만 「필요성 소멸」 판정이 되살아난다.
3. **`max_convertible_chars`와 `max_review_chars`는 같은 변경 단위다.** 어느 쪽을 고르든 둘을 함께 바꾼다.

선택지와 미결 판단은 `docs/kotlin-redevelopment-backlog.md` §1.2에 둔다.

**판정 — 상한값 재조정 쪽이 유력하나 확정은 보류(2026-09-01 정정):** 2차 측정(dictContext=product, 제품 조립 경로)까지 마쳤고 장문(최대 21,926자)에서도 단일 호출 출력이 제품 상한 16,000의 72%(11,468토큰)에 머물렀으며, 022 변환문 실물 확인으로 장문의 사실 보존도 표본 수준으로 확인됐다 — 「상한만 올리면 장문이 전부 절단 실패로 떨어진다」던 구조는 두 회차 모두 재현되지 않았고, 이 근거는 그대로 유효하다. 다만 2026-09-01에 「상한값 재조정으로 끝낸다 — 분할 변환은 착수하지 않는다」로 한 차례 확정했던 것은 같은 날 되돌린다: 이 절 1~2번이 정한 판정 기준은 출력 팽창비·**스타일 규칙 통과율**·절단 발생률 셋을 함께 재는 것이고 「품질이 무너지면 분할 변환」이 처방인데, **스타일 통과율이 2차에서 1/4(25%)로 무너졌다**(1차 3/4) — 그 붕괴를 반영하지 않은 채 판정이 내려졌다. 장문 표본도 사실상 022 한 건뿐이다(측정 대상 4건 중 023·047·050은 현행 4,000자 상한 바로 위이고, 그 유일한 장문 022가 이번 회차에 스타일 미통과였다). 그 구간의 표본이 1건뿐이라는 것은 새 상한값을 이 기록에서 정하지 않는 이유이기도 하다. 상세 근거·확정에 필요한 조건은 `docs/kotlin-redevelopment-backlog.md` §1.2. (같은 회차에서 스타일 통과율이 사전 주입 조건과 함께 떨어진 관측은 §1.3에도 기록했다 — 재현 전까지는 방향 관측일 뿐이나, 이번 판정 보류의 직접 근거이기도 하다.) **→ 3차 측정 실행(2026-09-03):** 승인 표본 7건 각 3회 반복까지 마쳤다 — 절단 0건·위반 밀도 낮음(중앙값 0.015)은 상한값 재조정에 근거를 보태지만, 유일한 장문 022는 인프라 실패로 반복이 사실상 1회에 그쳐 이 보류를 뒤집지 않는다. 수치와 분석은 `docs/kotlin-redevelopment-backlog.md` §1.2 「3차 측정 실행」. **→ 최종 판정(2026-09-03, 사용자 확정): 상한값 재조정.** 분할 변환은 착수하지 않는다. 근거는 세 회차 모두 절단 0건(3차 0/7 문서·0/38 호출, 21,926자 022 포함)과 낮은 위반 밀도(3차 중앙값 0.015), 022 변환문 실물 확인이다. 022 반복 표본이 사실상 1건이고 5,000~20,000자 밴드 표본이 둘뿐이라는 한계는 알고 받아들인 결정이며, 그 한계는 `docs/kotlin-redevelopment-backlog.md` §1.2 「말할 수 없는 것」에 기록으로 남긴다. 이 판정으로 이 절 2번의 처방(상한값 재조정)이 적용되고 3번(`max_convertible_chars`·`max_review_chars` 동시 변경)이 다음 작업이 된다 — **새 상한값 숫자는 아직 정하지 않았다**(backlog §1.2 6번). **→ 새 상한값 20,000자(2026-09-03 사용자 결정), 계약 2.7.0으로 구현.** 출력 토큰 구성 기본값(application.yml)도 64,000으로 맞춰 측정 조건과 제품 조건을 같게 했다. 022(21,926자)는 상한 위라 제품 경로로는 거절된다.

**함께 무너지는 전제 하나**: §3.2는 "파일럿 안내의 2,000자 내외 권장"을 유지한다고 적었다. 오늘 실측한 실제 문서 네 건은 모두 4,000자를 넘었다 — **실무 문서는 그 권장 안에 들어오지 않는다.** 2,000자 권장을 지키면 파일럿 표본이 실무와 달라지고, 실무 문서를 받으면 권장이 지켜지지 않는다. 이 게이트의 측정이 그 숫자도 함께 갱신한다. **→ 판정이 확정됐으므로(2026-09-03) 이 2,000자 권장의 갱신은 새 상한값을 정하는 작업(backlog §1.2 6번)에 묶는다.** **→ 갱신(2026-09-03, 게이트 ⓪ 판정에 따른 갱신): 2,000자 권장은 더 이상 유지하지 않는다.** 파일럿 안내는 상한 20,000자를 기준으로 한다.

**게이트 ①**: 파일럿 실무자 검증(4.0 성공 기준) 통과 → 단계 2 진행. **→ 2026-09-04: 단계 2 착수의 선행 조건에서 해제(병행). 게이트 ②(유료 계약)의 선행 조건으로는 유지.**

판정 근거의 출처는 검수 화면의 피드백 폼(`PUT /conversions/{id}/feedback` → `conversion_feedback` 표)과 그것을 집계하는 `scripts/pilot-report.sql`이며, 판정 절차·통과 기준·집계 시점은 `docs/pilot-runbook.md`의 「게이트 ① 판정」 절이 정한다. 그 표는 문서 30일 파기와 분리돼 있어(FK 없음) 원문이 파기된 뒤에도 판정 근거가 남는다. **통과 기준의 숫자는 2026-09-04 사용자 승인으로 확정됐다(제안값 그대로).**
