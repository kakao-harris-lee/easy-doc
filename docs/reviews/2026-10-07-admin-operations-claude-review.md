## 지적과 처리

| ID | 심각도 | 위치·재현 조건 | 처리 |
|---|---|---|---|
| B1 | 높음 | AdminBillingController/JdbcAdminOperationsQuery: 상태 조회 이후 revision을 읽는 사이 변경되면 오래된 상태에 새 revision이 붙음 | revision을 먼저 읽고 이후 상태를 합친다. revision/감사는 같은 읽기 snapshot으로 조회한다. 변경이 끼면 보수적인 409가 된다. |
| B2 | 높음(계획 해석) | 기존 관리 조치 요청은 revision 생략 가능 | 사용자 요청의 기존 API 호환 유지에 따라 선택 필드로 추가한다. 새 화면은 revision 조회 전 새 조치를 차단하고 반드시 전송한다. 새 알림 변경 API는 필수다. 구형 호출의 CAS 부재를 계획과 계약에 명시했다. |
| B3 | 중간~높음 | 메일 조치가 409 이후 같은 stale revision에 고정됨 | id로 최신 알림을 조회해 UUID 이력이 있으면 완료로 복구하고, 이력이 없고 revision이 바뀐 확정 거절만 해제한다. 조회 실패·통신 불명확은 요청을 유지한다. |
| B4 | 중간 | V46 trigger의 작업공간 행 UPDATE가 구독·카드 행과 잠금 순서를 뒤집음, lease 갱신마다 revision 변경 | 공유 행 UPDATE를 제거하고 의미 있는 변경에만 row-local sequence revision을 찍도록 수정했다. 실제 쓰기 경로도 작업공간 잠금을 따른다. |
| B5 | 중간 | 카드 등록 시각이 삭제 경과 시각으로 표시됨 | 삭제 대기 진입 시각을 별도 기록한다. 과거 시각 미상은 null이며 화면은 경과 시간 확인 불가를 표시한다. |
| B6 | 중간 | 응답 유실 후 pending 관리 조치가 재전송되지 않고 대기함 | 같은 UUID 재전송과 terminal 결과 확인을 지원하고 pending 요청을 보존한다. 활성 작업만 제한된 backoff로 조회한다. |
| B7 | 중간(증거 부족) | 새 컨트롤러의 raw Map 응답에 private 헤더가 없을 가능성 | 전역 응답 헤더 필터와 실제 HTTP no-store 테스트로 확인한다. 응답 타입만으로 누락을 단정할 수 없다. |
| B8 | 낮음~중간 | feedback.list의 내부 호출이 트랜잭션 proxy를 우회 | list 진입점에도 REPEATABLE_READ를 적용한다. |

추가 통합 수정: nullable 과거 시각·숫자 알림 ID·KST 기간 경계를 계약/타입/UI에 맞췄다.
처리 대상 id 직접 조회, stale 페이지 복원, 현재 수신 대상·안전한 실패 분류를 보강했다.
Playwright가 브라우저 HTTP 모듈을 가져오지 않도록 금융 wire 타입을 별도 파일로 분리했다.

2차의 낮은 심각도 보완도 반영했다. 알림 확정 404/422는 복구 요청을 정리하고 대상을 다시
조회한다. worker 만료 처리와 완료 처리는 알림 행 다음 시도 행의 동일한 잠금 순서를 따른다.
금융 요청 UUID가 서로 다른 조치에 중복되면 새 조회 API는 500 대신 409로 모호함을 알린다.

## 비차단 관찰과 적용 경계

3차 리뷰의 아래 항목은 차단 결함이 아닌 후속 개선 의견으로 남긴다. 이번 코드에 대한
검증·리뷰 후 추가 제품 코드 변경은 없으며, 운영 재배포와 라이브 개방은 하지 않았다.

- 서로 다른 행에 sequence revision을 찍는 쓰기가 작업공간 잠금 없이 병행되면 낮은 stamp의 늦은 commit을 greatest 값이 감지하지 못할 수 있다. 현재 금융 쓰기 경로의 작업공간 잠금을 확인했고 불확실 결제 처리도 같은 잠금을 사용하도록 보완했다. 새 쓰기 경로에서도 이 조건을 유지해야 한다.
- 현재 정상 경로에서 하지 않는 주문/카드 행의 직접 삭제는 최대 revision을 바꾸지 않을 수 있다. 삭제 기능을 추가할 때 별도 무효화가 필요하다.
- 관리자가 삭제되어 감사 actor가 NULL이 되면 과거 알림 UUID 재전송은409다. 관리자 삭제/기록 보존 정책은 이번 범위에서 제외한다.
- 알림 상세 목록은 행별 시도·확인 이력을 조회한다(최대100행). 결제 목록의 반복 원장 조회 제거와 별개의 성능 개선 후보다.
- 작업 종류 필터를 선택하면 종류별 작업 건수도 해당 필터 범위를 따른다. 전체 무필터 고객 수가 아니라 현재 조건의 작업 건수다.
