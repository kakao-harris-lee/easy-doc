# 개인정보처리시스템 접속기록 보관·점검

- 작성 2026-09-11. 사용자 지시: 「접속기록 보관 체계도 별도 조각으로 진행.」
- 근거: 개인정보처리방침 §8이 게시 전에 갖춰야 한다고 적어 둔 항목. 관련 고시(개인정보의 안전성 확보조치 기준)가 **접속기록 1년 이상 보관**과 **월 1회 이상 점검**을 요구한다.
- **게시 선행조건이다.** 방침에 「접속기록을 보관·점검한다」고 적으려면 체계가 먼저 있어야 한다 — 없는 준수를 문서로 주장하지 않는다.

## 1. 범위를 먼저 좁힌다 — 무엇이 「접속기록」인가

**이용자가 사이트를 둘러본 기록이 아니다.** 고시가 요구하는 것은 **개인정보취급자가 개인정보처리시스템에 접속해 개인정보를 처리한 기록**이다. 우리에게 그 취급자는 **운영자(대표자)** 한 사람이고, 접속 경로는 둘이다.

1. **관리자 API** — 계약에 `x-admin-only`로 표시된 **10개 엔드포인트**.
2. **CLI 실행 프로필** — `usage-report`(사용자·워크스페이스별 사용량 CSV), `credit-grant`, `admin-grant`.

웹 서버(nginx)의 접근 기록은 이 의무의 대상이 아니다. 지금 컨테이너 표준 출력으로만 남고 보관 기간이 없는데, **그것과 이 조각을 섞지 않는다.**

## 2. 지금 참인 것

**감사 로그 표가 없다**(2026-09-11 확인). 있는 것은 **쓰기 작업의 행위자 흔적 셋**뿐이다.

| 흔적 | 어디 |
|---|---|
| `credit_transactions.actor_user_id` | 운영자 수동 크레딧 조정 (V17) |
| `invoice_requests.handled_by` | 세금계산서 처리 (V17) |
| `announcements.created_by` | 공지 작성 (V17) |

**읽기는 하나도 기록되지 않는다.** 그런데 개인정보가 실제로 노출되는 곳은 대부분 읽기다.

| 읽기 엔드포인트 | 노출되는 개인정보 |
|---|---|
| `listAdminWorkspaces` · `readAdminWorkspace` | 워크스페이스 소유자 **전자우편주소** |
| `listAdminInvoiceRequests` | 사업자등록번호, **대표자 성명**, 연락처 — **제3자의 정보다** |
| `readAdminUsage` | 사용자·워크스페이스별 이용량 |
| `readAdminErrors` | 오류 기록 |

「누가 대표자 성명을 열어 봤는가」가 지금 남지 않는다. 이 조각이 닫는 것이 그것이다.

## 3. 결정

### 3.1 표 하나를 새로 만든다 — 덧붙이기만 한다

`personal_data_access_logs`. 고시가 요구하는 항목을 열로 둔다.

| 열 | 내용 |
|---|---|
| `actor_user_id` | 접속한 취급자 |
| `accessed_at` | 접속 일시 |
| `client_ip` | **접속지 정보** — §3.4 참고 |
| `operation` | 수행 업무. 계약의 `operationId`를 그대로 쓴다(예: `listAdminInvoiceRequests`) |
| `subject_scope` | 처리한 정보주체의 범위 — 단건이면 그 식별자, 목록이면 조회 조건과 건수 |
| `outcome` | 성공·거절 |

**애플리케이션에 수정·삭제 경로를 두지 않는다.** 고시의 위·변조 방지 요구에 대한 최소 대응이다. 삽입만 하는 포트를 두고, 갱신·삭제 메서드를 아예 만들지 않는다.

**`actor_user_id`에 CASCADE를 걸지 않는다.** 감사 기록이 계정 삭제로 사라지면 목적을 잃는다. **관리자는 탈퇴가 409로 거절되므로**(회원 탈퇴 스팩) 이 제약은 실제로 막히지 않는다 — 두 규칙이 서로를 지탱한다.

### 3.2 잡는 자리는 관리자 API 경계 하나다

**엔드포인트마다 호출을 흩지 않는다.** `x-admin-only` 경로를 지나는 요청을 한 자리에서 잡는다(인터셉터). 이유는 둘이다 — 새 관리자 엔드포인트가 생겼을 때 **기록을 빠뜨릴 수 없고**, 기록 책임이 유스케이스에 섞이지 않는다.

**CLI 프로필 셋도 같은 표에 남긴다.** HTTP를 지나지 않으므로 각 실행이 직접 한 건을 쓴다. `client_ip`는 없으므로 실행 주체를 대신 남긴다(§3.4).

**기록 쓰기가 실패하면 요청도 실패한다 — fail-closed다(2026-09-11 결정).** 인터셉터는 기록 삽입을 try/catch로 감싸지 않는다. 삽입이 실패하면 그 요청은 컨트롤러에 닿지 못하고 500으로 끝난다.

리뷰 두 곳이 같은 자리를 짚었다 — `code-reviewer`는 HIGH(정당한 관리자 요청이 감사 기록 쓰기 하나 때문에 500이 된다), `migration-reviewer`는 MEDIUM(스키마 도입이 관리자 API 전체에 가용성 결합을 만든다). 지적은 옳지만 **동작은 바꾸지 않는다.**

- **기록하지 못한 채 개인정보를 내주는 것이 더 나쁘다.** 삽입 실패를 삼키고 요청을 통과시키면 「누가 대표자 성명을 열어 봤는가」가 남지 않은 조회가 생긴다 — 이 조각이 닫으려던 바로 그 구멍이다(§2).
- **「쓰기만 죽는」 상황의 실익이 작다.** 관리자 엔드포인트 10개는 모두 같은 PostgreSQL을 읽는다. 그 DB에 쓰지 못하는 상황이면 읽기도 대개 함께 무너진다 — 새로 생기는 실패 구간은 보기보다 좁다.
- **거절 경로에서는 기록 실패가 403을 500으로 덮어쓴다.** 접근이 거부되는 것은 변하지 않으므로 개인정보가 새지 않는다. 인터셉터 KDoc이 약속하던 「응답 자체는 바뀌지 않는다」의 범위는 **관리자 확인의 성패**이지 기록 쓰기 실패까지가 아니다 — 그 문장을 그렇게 고쳤다.

이 동작은 테스트로 고정한다. 기록이 실패하면 조용히 통과하지 않는다는 것이 요점이므로, 그것을 재는 테스트가 없으면 결정이 아니라 우연이다.

### 3.3 보관은 1년 이상, 파기는 그 뒤에

- **1년 미만에 지우지 않는다.** 기존 일일 파기 배치(`RetentionPurgeScheduler`)가 이 표를 건드리지 않게 한다 — 실수로 포함되면 의무 위반이다.
- 보관기간을 넘긴 행의 파기는 **이 조각의 범위 밖**으로 둔다. 1년이 지나기 전에 정할 시간이 있고, 지금 필요한 것은 **쌓이기 시작하는 것**이다. 대신 보관기간을 구성값으로 두어 나중에 파기를 붙일 자리를 만든다.

### 3.4 접속지 정보(IP) — 여기서만 저장한다

**우리는 원칙적으로 IP를 저장하지 않는다**(가입 동의 계획 §2 결정 4: 「수집 최소화가 분쟁 대비 가치보다 앞선다」). **접속기록은 그 원칙의 예외다** — 고시가 접속지 정보를 요구한다.

그러므로 이렇게 못박는다.

- **접속기록 외의 어떤 표에도 IP를 저장하지 않는다.** 이 조각이 IP 저장의 선례가 되어 다른 곳으로 번지지 않게 한다.
- 저장 대상은 **취급자(운영자)의 IP뿐**이다. 일반 이용자의 IP는 대상이 아니다 — 일반 이용자는 개인정보취급자가 아니다.
- 개인정보처리방침 §9(자동 수집 장치)의 「이용자 방문 이력을 추적하지 않는다」와 충돌하지 않는다. 대상이 다르다.

### 3.5 월 1회 점검은 CLI 보고서로 받는다

기존 `usage-report` 프로필과 같은 방식으로 **점검용 보고서를 뽑는 실행 프로필**을 둔다. 화면을 새로 만들지 않는다 — 취급자가 한 명이고, 점검은 월 1회다.

보고서에 담을 것: 기간, 취급자별 접속 횟수, 업무별 횟수, **거절된 접속**, 그리고 점검자가 눈으로 볼 수 있는 원시 목록.

**점검을 수행했다는 사실 자체의 기록**은 이 조각에서 만들지 않는다 — 보고서 파일이 그 증거이고, 운영 절차로 관리한다.

## 4. 슬라이스 (M)

마이그레이션 **V22**, `core`/`application`의 삽입 포트와 기록 유스케이스, `api`의 관리자 경계 인터셉터, CLI 셋의 기록 추가, 점검 보고서 프로필, 기존 파기 배치가 이 표를 건드리지 않는지 확인.

**계약 변경 없다.** 접속기록을 API로 노출하지 않는다.

**`docs/plans/2026-09-10-signup-consent.md`가 예약한 V22를 이 조각이 쓴다** — 가입 동의는 약관·방침 확정을 기다리는 중이고 이 조각이 먼저 나간다. 그 계획의 마이그레이션 번호를 V23으로 옮긴다.

## 5. 수용 기준

1. 관리자 읽기 엔드포인트를 호출하면 `personal_data_access_logs`에 **한 건**이 남고, `operation`이 계약의 `operationId`와 같다(실 DB).
2. **거절된 접속(403)도 남는다** — 권한 없는 접근 시도가 기록되지 않으면 점검의 의미가 없다.
3. **관리자가 아닌 요청은 남지 않는다** — 일반 이용자의 정상 이용이 이 표를 오염시키지 않는다.
4. CLI 프로필 셋 각각이 실행마다 한 건을 남긴다.
5. 애플리케이션에 **갱신·삭제 경로가 없다**(포트에 그 메서드가 존재하지 않는다는 것으로 고정).
6. 일일 파기 배치를 돌려도 **이 표의 행이 줄지 않는다**.
7. 점검 보고서가 기간·취급자·업무·거절 건수를 낸다.
8. **IP가 이 표 외의 어디에도 저장되지 않는다**(다른 표에 IP 열이 생기지 않았음을 인구조사류 테스트로 고정할 수 있으면 한다).
9. 로그(파일 로그)에 개인정보가 새지 않는다 — 기존 누출 테스트 방식.

## 6. 범위 밖

보관기간 경과 후 파기, 관리자 화면의 접속기록 조회 탭, 점검 수행 기록의 전산화, nginx 접근 기록의 보관 정책, 일반 이용자 로그인 이력.
