**사용자 결정 + 리더 판정.** "Python code를 모두 버리고 UI/UX 코드와 문서를 기반으로 개발하는 형태가 더 효율적이다. 이제 막 개발한 프로젝트라 다시 개발해도 문제 없다." 이로써 이 문서는 **포팅 계획**이 아니라 **재개발 계획**이 된다. Python 런타임은 참고 구현도 아니고 **폐기 대상**이다. 개발 기준은 **요구사항 + `contracts/easy-doc-v1.yaml` + 이미 만들어진 React 프런트(UI/UX)**다.

**이전 판단이 틀렸던 게 아니라 전제가 바뀌었다.** 초판과 1차 개정은 "롤백 창이 존재한다"를 전제로 호환성 요구를 세웠다. 리더가 그 전제를 거둬들였다(아래). 무엇이 언제 왜 바뀌었는지를 남기려 이 항목을 둔다.

**리더가 이미 판정한 것 (재론 대상 아님):**

1. **롤백을 포기한다.** 절체는 일방향이다. 보존할 운영 DB가 없고(§9-2 확정) 파일럿 전이다.
2. **따라서 호환성 요구가 통째로 소멸한다.** Fernet 암호문·JWT·Argon2의 **바이트 동일성은 롤백 대상이 존재할 때만** 성립하던 요구다. 표준 AEAD를 처음부터 쓴다. Phase 0에서 승인했던 "Fernet 직접 구현 ~150줄"(§9 결정 3)은 **불필요해졌다.**
3. **parity의 `compat` 판정 모드(crypto·jwt·argon2)는 근거가 사라졌다.** 이 세 도메인은 "값이 같아야 한다"가 아니라 "동작이 요구를 만족한다"로 내려간다.
4. **Python 오프라인 도구(judge·goldenset·collection·benchmark)도 최종 폐기한다.** Kotlin 대체물이 같은 fixture로 검증될 때까지만 한시 존치한다. 영구 oracle로 두자던 §5 Phase 9의 논거는 약하다 — 아키텍처 규칙 4가 프롬프트 생성과 골든셋 평가에 **같은 스타일 정의를 공유**시키므로 채점자 독립성은 지금도 없다. 진짜 독립성은 fixture·명세에서 온다.

**Phase 번호는 바꾸지 않는다 — 성격만 바꾼다 (deep-reasoner 판단).** 저장소 곳곳이 Phase 번호로 상호 참조한다: `00_progress.md`의 종료 판정, `00_requirements-inventory.md`의 `Phase` 열과 게이트 범위 선별, `.claude/agents/*`·`.claude/skills/*`의 착수 조건, `reviews/*`의 회차, 파일명 접두(`00_`·`01_`·`02_`). 번호를 바꾸면 이 참조가 전부 끊긴다 — 2026-08-11 변경 이력이 기록한 "레인 간 규약 드리프트"(Critical 급)가 재발한다. 반면 Phase 0~6은 **작업 경계 자체가 재개발에서도 그대로다**(기준 확정 → 골격 → 도메인 로직 → 데이터·인증 API → 문서 API·저장 암호화 → LLM·worker → React 통합). 바뀌는 것은 **후반 3단계의 성격**과 **몇몇 하위 항목**뿐이라, 번호를 유지하고 그 절의 내용을 다시 쓰는 편이 참조를 지키면서 혼란도 적다. 계약 `info.version 1.0.0` 유지·progress "역사 기록 불변" 규약과 같은 원리(식별자는 안정, 내용은 개정).

### 2026-08-12 — 판정 기준을 "Python 동작 보존"에서 "요구사항 충족"으로 바꿈

> **위 2차 개정이 이 항목의 호환성 부분을 무효화했다.** 아래 "바뀌지 않은 것"의 Fernet·JWT·Argon2 값 동일성과 절체·롤백 절차는 **롤백 창을 전제**했는데, 그 전제가 2차에서 사라졌다. 아래는 1차 개정 시점의 기록으로 남긴다.

초판(2026-08-11)은 "동등 포팅 우선, 개선은 나중"을 뼈대로 썼다. Kotlin 구현의 합격 여부를 Python이 같은 입력에 내는 출력으로 판정하는 구조였다.

이 전제를 뒤집는다. Kotlin 전환을 시작한 이유 자체가 Python 구현의 회귀 문제이기 때문이다. Python은 완성된 정답이 아니라 요구사항이 한 번 구현된 결과이고, 그 구현에는 고쳐야 할 것이 남아 있다. 출력을 Python에 맞추는 일을 합격 조건으로 두면 고치려던 문제를 그대로 옮겨 심게 된다.

새 기준은 다음과 같다.

- **판정 기준은 프로젝트 요구사항이다.** Kotlin 구현은 요구사항을 충족하면 통과한다. Python과 출력이 다른 것 자체는 실패가 아니다.
- **Python은 참고 구현이자 요구사항 발굴원이다.** 판정 oracle이 아니다.
- **개선을 뒤로 미루지 않는다.** 요구사항을 더 잘 만족하는 구현이 있으면 전환 중에 채택한다. HTTP 계약도 개선 대상이며, 필요하면 React를 같은 변경 단위에서 함께 고친다.

같은 날 함께 결정된 것.

- 마스킹 대상은 **주민등록번호·카드번호 2종**으로 줄인다. 전화번호·이메일·계좌번호는 마스킹하지 않는다(§2.3).
- §9의 결정 1·2·3이 승인됐다 — 제품 런타임만 Kotlin화 / 보존해야 할 기존 DB 없음 / Fernet은 JVM 라이브러리 의존이 아니라 직접 구현.

**바뀌지 않은 것**은 아래와 같다. 이들은 "Python 동작 보존"이 아니라 **호환성·보안·구조** 요구에서 나온 항목이므로 기준 전환의 영향을 받지 않는다.

- Fernet·JWT·Argon2의 값 동일성(§4.3) — 롤백 창에서 두 런타임이 같은 저장 데이터를 읽어야 한다
- DB 스키마 인수와 additive 원칙(§4.2), PostgreSQL 작업 큐 설계(§4.4), Gradle 모듈 구조(§3.2), Phase 순서(§5), 절체·롤백 절차(§5 Phase 7)
- 마스킹 선행 불변식, 최대 2회 LLM 호출, 소유권 은닉 404, 평문 미저장·미로깅 같은 보안·비용 요구

**이 전환이 치르는 대가**는 §1.1에 적었다. 요약하면, 동등 비교라는 자동 판정 수단을 잃기 때문에 의도치 않게 빠뜨린 동작을 알아채기 어려워진다.

## 1. 결론

이 프로젝트의 프런트엔드는 이미 React + TypeScript + Vite다. 따라서 프런트엔드를 다시 만드는 작업은 하지 않는다. 기존 로그인, 업로드, 변환 검수, 기록, 작업 공간 화면과 테스트를 재사용하고, 계약 개선에 따라 필요한 부분만 함께 고치며 접근성을 보강한다.

전환의 주 작업은 다음 세 가지다.

1. Python/FastAPI API와 ARQ 워커를 Kotlin/Spring Boot API·워커로 **재개발**한다(호환·병행 없음).
2. ~~롤백 창 동안 두 런타임이 같은 데이터를 읽도록 값 단위로 호환한다~~ → **무효(2026-08-12 2차).** 롤백 없음 → 저장 암호화는 표준 AEAD 신규, 인증도 신규 기준(§4.3).
3. 문서 추출·내보내기와 쉬운 글 변환이 **요구사항 기준**(필수 정보 보존, 스타일 규칙, 팩트 유지, 입력·비용 상한)을 충족함을 증명한다. 그 기준은 Phase 0에서 수치로 고정한다.
4. **지우기 전에 코드에만 있던 판단을 뽑아낸다**(`03_rebuild-extraction-list.md`) — 재개발의 실제 작업량이자 Python 폐기의 선행 조건.

병행·절체(Strangler)는 하지 않는다. 되돌아갈 운영 Python이 없으므로, 검증이 끝나면 Kotlin 스택을 첫 배포한다(§5 Phase 7, 일방향).

### 1.1 새 기준이 치르는 대가

동등 포팅을 포기하면 잃는 것이 하나 있다. "Python과 출력이 다르다"는 신호는 **비용 없이 얻어지던 회귀 탐지기**였다. 이 신호를 합격 조건에서 빼면, 요구사항 문서에 적히지 않은 동작 — 지금까지 코드에만 존재하던 예외 처리, 경계값, 서식 세부 — 이 조용히 사라져도 어떤 테스트도 붉어지지 않는다. 런타임 8,169줄 중 어디가 요구사항이고 어디가 우연인지를 코드는 알려주지 않는다.

세 가지로 방어한다.

1. **요구사항 인벤토리** — 정본 산출물 `docs/migration/_workspace/00_requirements-inventory.md`(2026-08-12 전역 1차본 작성, 미승인). Python 코드·테스트·골든셋에서 "이 시스템이 보장하던 것"을 항목으로 뽑아 추적표에 올리고, 항목마다 Kotlin 쪽 검증 수단을 매단다. Phase 종료 조건은 "미충족 0"이지 "Python과 동일"이 아니다. 전역 요구사항과 합격선은 Phase 0에서 확정하고, 도메인별 상세 항목은 각 Phase 착수 시 그 범위만 작성한다.
2. **차분 비교의 강등**. 같은 입력을 두 구현에 넣어 출력을 비교하는 하네스는 초판대로 만든다. 다만 불일치는 실패가 아니라 **분류 대상**이다. 각 불일치를 `의도된 개선` / `요구사항과 무관` / `미확인` 중 하나로 분류하고, **미확인이 0이 되어야** 해당 Phase를 닫는다. 자동 판정을 사람 판단으로 바꾼 것이므로 비용은 사라지지 않고 이동한다(§7).
3. **Python suite 병행 유지**. 절체 시점까지 Python 테스트를 계속 실행해 비교 기준으로 쓴다(§6).

이 방어가 완전하지는 않다. 인벤토리에 오르지 못한 동작은 여전히 놓칠 수 있다. 이 잔여 위험은 제거 대상이 아니라 감수 대상이며, 마지막 그물은 관찰 기간(§5 Phase 7)에 기능 누락 신고 경로를 열어 두는 것뿐이다.

| API | Python 3.12, FastAPI, Pydantic | Kotlin으로 교체 |
| 데이터 접근 | SQLAlchemy async, PostgreSQL 16, Alembic | Spring JDBC, Flyway로 교체 |
| 비동기 작업 | ARQ + Redis | PostgreSQL 기반 내구성 작업 큐로 교체 권장 |
| LLM | OpenAI·Anthropic provider 추상화 | 추상화 구조를 Kotlin으로 포팅 |
| 문서 처리 | docx·pdf·hwpx 추출, docx·txt·hwpx 내보내기 | JVM 구현으로 포팅 |
| 개인정보 | 마스킹 5종 후 LLM 전송, Fernet 암호화 저장 | 마스킹 2종으로 축소, **표준 AEAD 신규 저장**(호환 게이트 없음 — §4.3 2차) |
| 배포 | API·worker·migrate 동일 Python 이미지, React nginx 이미지 | Kotlin API·worker 동일 빌드 산출물 + React nginx 유지 |

현재 제품 런타임 Python 코드는 약 8,169줄이고, React 소스는 약 4,063줄이다. 2026-08-11 로컬 기준으로 백엔드는 `810 passed, 68 skipped, 4 deselected`, React는 `60 passed`이며 TypeScript·ESLint·Prettier 검사와 production build도 통과했다. DB·외부 LLM 조건이 없는 로컬 결과이므로 실제 운영 E2E 증거와는 구분한다.

### 2.2 외부 계약 — v1 출발점과 개선 절차

현재 14개 HTTP 엔드포인트를 Kotlin 전환의 v1 계약 **출발점**으로 삼는다. 초판은 이 계약을 동결했으나, 계약도 개선 대상이다(2026-08-12 결정). 대신 무엇을 바꿀 수 있고 무엇을 바꿀 수 없는지를 가른다.

**바꾸지 않는다 — 보안·상호운용 요구**

- 인증: `Authorization: Bearer`, JWT HS256, `sub`·`exp`·`typ` 의미. 발급·검증 정확성은 §4.3(2차)·migration-safety-gate I-9로 판정한다(양방향 호환 요구는 소멸 — 롤백 없음)
- 개인정보 응답: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`
- 접근 통제: 다른 사용자의 자원은 403이 아니라 404로 응답
- 입력 제한: 본문 4,000자, 파일 10MB, 지원 형식 docx·pdf·hwpx. 비용 상한이자 파서 공격면 방어다

**근거와 승인을 남기면 바꿀 수 있다**

- 오류 본문 `{"detail": ...}` 형태와 오류 코드 체계
- JSON 필드명 규약(`snake_case`)
- 상태 코드 선택: 가입 201, 업로드 202, 삭제 204, 입력 오류 422, 충돌 409, 인증 오류 401, 의존 서비스 오류 5xx
- 변환 상태값 집합 `pending | processing | done | failed`
- 업로드 접수 `Location` 헤더, 다운로드 미디어 타입과 RFC 5987 `Content-Disposition`, CORS 허용·노출 헤더

개선 절차는 세 가지를 함께 만족해야 한다. ① 요구사항 근거를 계약 파일에 남긴다. ② `contracts/easy-doc-v1.yaml`, Kotlin 구현, React 타입·화면·테스트를 같은 변경 단위에서 갱신한다. ③ 승인 지점을 통과한다(§9 결정 6).

**롤백 창 제약은 없다 (2026-08-12 2차).** 되돌아갈 Python 런타임이 없으므로(§9 결정 2·§5 Phase 7) 옛 "롤백 창 양립성" 제약은 소멸했다. 계약 개선은 요구사항 판단만으로 정하고, 승인되면 계약 파일·Kotlin·React를 **같은 변경 단위에서 함께** 갱신한다(절체 전/후 구분 없음).

계약 파일 `contracts/easy-doc-v1.yaml`을 먼저 만들고 FastAPI OpenAPI 결과와 현재 React 타입을 대조한다. 대조의 목적은 현재 상태를 정확히 기록하는 것이지 그 상태를 영구 고정하는 것이 아니다. 이후 계약 파일이 Kotlin API와 React 타입 생성의 단일 기준이 된다. Spring 기본 오류 응답인 `ProblemDetail`을 노출할지 현재 `detail` 형태를 유지할지는 위 개선 절차로 정한다. 어느 쪽이든 전역 예외 매퍼 한 곳에서 형태를 강제한다.

### 2.3 충족해야 할 내부 요구사항

아래는 Python이 그렇게 했기 때문이 아니라 제품·보안·비용 요구이기 때문에 지켜야 하는 항목이다.

- 원문은 마스킹한 뒤에만 LLM으로 보낸다. 이 순서를 우회하는 경로는 타입 수준에서 막는다.
- 마스킹 대상은 **주민등록번호·카드번호 2종**이다(아래 참고).
- LLM 호출은 변환 1회 + 조건부 보정 1회, 최대 2회다.
- 응답 절단, 빈 결과, 자리표시자 유실, 보정 악화 — 이 네 상황을 **검출해 정의된 상태로 처리**해야 한다. 각 상황에서 변환 상태와 사용자에게 보이는 결과가 무엇인지를 요구사항으로 고정하고, 판정 임계값과 검사 방식은 Kotlin에서 다시 정할 수 있다.
- AI 초안과 검수 수정본을 별도 보존해 수정률 KPI 원천을 유지한다.
- 원문·결과·마스킹 대응표는 평문으로 DB나 로그에 남기지 않는다.
- 보존 만료 문서는 매일 자동 파기한다. 다중 인스턴스에서 중복 실행되지 않아야 하고, 일부 실패가 전체를 막지 않도록 나눠 커밋한다. 현재 운영값인 04:00 KST·500건 단위는 출발값이며 Kotlin에서 조정할 수 있다.
- 삭제는 문서와 변환을 함께 파기하며, 문서가 든 작업 공간과 마지막 작업 공간은 삭제하지 않는다.
- HWPX는 생성 후 자체 추출기로 다시 읽어 본문이 일치해야 한다. 한컴 오피스 실제 호환성은 별도 사람 검증으로 남는다.

**마스킹 2종 축소 (2026-08-12 결정)**. 현재 `app/privacy/masking.py`는 이메일·주민등록번호·카드번호·전화번호·계좌번호 5종을 우선순위 순서로 치환한다. 이 중 주민등록번호와 카드번호만 남긴다. 따라오는 결과는 다음과 같다.

- 전화번호·이메일·계좌번호는 마스킹되지 않고 **원문 그대로 LLM provider로 전송된다**. 축소의 대가이며, 축소해도 되는 근거는 정책 판단이지 기술 판단이 아니다. 정책 문구는 별도로 확정 중이므로 이 계획서는 결정 사실만 근거로 쓴다.
- 패턴 우선순위 문제가 대부분 사라진다. 현재 코드가 이메일을 최우선에 두는 이유는 지역부의 숫자열이 전화·계좌 패턴에 먼저 걸려 도메인만 평문으로 남는 유출을 막기 위한 것인데, 두 패턴이 없어지면 그 방어가 필요 없다. 주민등록번호와 카드번호가 겹치는 구간 처리는 그대로 필요하다.
- 자리표시자 집합이 `[[주민등록번호N]]`·`[[카드번호N]]`으로 줄어든다. 프롬프트의 자리표시자 보존 지시, 출력 검사, 복원 로직이 함께 좁아진다(§4.6).
- 5종 기준으로 만들어진 Python 골든셋·수집 도구(`app/easyread/collection.py`)의 마스킹 통계는 Kotlin 결과와 자연히 달라진다. 이 차이는 §1.1 분류에서 `의도된 개선`으로 기록한다.

정확한 라이브러리 버전은 구현 시작 시 호환성 spike를 통과한 조합을 Gradle lockfile과 version catalog에 고정한다. Spring Boot·Kotlin·Jackson·LLM SDK를 각자 임의 버전으로 섞지 않는다.

### 3.2 Gradle 구조

```text
backend-kotlin/
  settings.gradle.kts
  gradle/libs.versions.toml
  core/             # 마스킹, 스타일 규칙, 프롬프트, 후처리, 도메인 타입
  application/      # 인증, 문서, 작업 공간, 변환 유스케이스
  infrastructure/   # JDBC, 암호화, 문서 파서, LLM provider, 작업 큐
  api/              # Spring MVC, 인증 필터, 오류·응답 계약

```

`core`는 Spring과 DB 의존성 없이 테스트 가능하게 둔다. API와 worker는 `application`과 `infrastructure`를 공유하지만 서로의 실행 진입점에는 의존하지 않는다. 최종 컨테이너 이미지는 같은 JAR/레이어를 사용하고 실행 profile만 `api`, `worker`, `migrate`로 구분한다.

## 4. 주요 설계 결정

### 4.1 React UI는 유지하고 계약 경계만 교체

현재 화면과 라우트는 그대로 유지한다.

- `/login`, `/signup`, `/`, `/conversions/:id`, `/history`
- `AuthProvider`, `WorkspaceProvider`, polling, 미저장 변경 경고
- 로그인·업로드·검수·내보내기·기록·작업 공간 동작

변경 대상은 다음이다.

1. 수기 타입인 `frontend/src/api/types.ts`를 OpenAPI 생성 타입으로 대체한다.
2. `frontend/src/api/client.ts`의 토큰, 401 처리, 네트워크 오류, 파일 다운로드 래퍼는 그대로 쓴다. 계약 개선으로 오류 형태가 바뀌면 이 래퍼도 함께 고친다.
3. Kotlin 오류 응답을 한국어 사용자 메시지로 바꾸는 어댑터를 검증한다.
4. 승인된 계약 개선(§2.2)은 React 타입·화면·테스트를 같은 변경 단위에서 함께 고친다. (롤백 창이 없으므로 "Python 응답도 처리" 제약은 없다 — 2026-08-12 2차.)
5. polling 중 상태 변화를 `aria-live`로 알리고, 키보드 초점·레이블·대비를 KWCAG 기준으로 점검한다.
6. 시각 디자인 개편은 API 전환과 분리한다. React 메이저 버전 업그레이드도 Kotlin 절체 후 별도 작업으로 진행한다.

### 4.2 데이터베이스와 Flyway 인수

ORM 교체와 스키마 재설계를 동시에 하지 않는다(마이그레이션 위생). **롤백 근거는 사라졌다**(2026-08-12 2차 — 되돌아갈 Python이 없다). 스키마는 원하는 형태로 설계하되, Phase 1이 이미 `V1__python_schema_baseline.sql`로 현행 스키마 형태를 baseline했고(`00_progress.md`), 이후 변경은 additive(V2~)로 쌓는다. `encryption_scheme`/`key_version`은 **키 회전용**으로만 남긴다(롤백 호환용 아님).

**보존 대상 DB 없음 (§9 결정 2 승인)**. 기본 경로는 빈 DB에 `V1` baseline을 적용하는 것이다. 아래 1·2·4번은 파일럿 데이터가 있는 환경이 생길 때만 수행하는 조건부 절차로 남긴다.

1. (조건부) 실제 대상 DB의 schema-only dump와 `alembic_version`을 수집한다.
2. (조건부) Alembic `0001~0006`의 기대 스키마와 실제 스키마를 비교한다. README에 `0003` 제자리 수정 이력이 있으므로 파일만 믿지 않는다.
3. 빈 DB용 `V1__python_schema_baseline.sql`을 만든다. 대상 DB 유무와 무관하게 필요하다.
4. (조건부) 기존 DB는 schema checksum이 일치할 때만 Flyway baseline version 1을 기록한다.
5. Kotlin 전용 변경은 `V2`부터 추가한다.
6. 절체 시점부터 한 환경에서 Alembic과 Flyway를 함께 실행하지 않는다.
7. Python 제거 전까지 `alembic_version`은 보존하고 Kotlin이 수정하지 않는다.

모든 초기 변경은 additive로 한다. 기존 컬럼 삭제·이름 변경·타입 축소는 Python 제거와 관찰 기간 종료 후 별도 마이그레이션으로 미룬다.

### 4.3 저장 암호화·인증 — 표준 AEAD 신규 구현 (재개발: 호환성 요구 소멸)

> **2026-08-12 2차 개정.** 롤백을 포기했고(§9-2·§9 결정 2) 보존할 데이터가 없으므로 **암호문·JWT·Argon2의 값 동일성 요구가 통째로 사라졌다.** 이 절의 옛 제목("호환성 게이트")과 아래 옛 번호 목록(양방향 fixture·Fernet 직접 구현·`fernet-v1` 읽기/쓰기 유지·tamper 호환)은 **역사 참고로만 남긴다 — 따르지 말 것.** parity `crypto`·`jwt`·`argon2`의 `compat` 판정 모드도 근거가 없다.

재개발 방침은 다음과 같다.

1. **저장 암호화는 표준 AEAD로 처음부터 쓴다** — AES-GCM(또는 검토를 거친 동등 AEAD)을 JDK/검증된 라이브러리로. Fernet 직접 구현(옛 §9 결정 3, ~150줄)은 **불필요**하다. 판정 기준은 "Python Fernet 암호문과 같은 바이트"가 아니라 **"Kotlin 안에서 암호화→복호화 round-trip이 성립하고 변조(tamper)를 단일 예외로 거부한다"**(복호화 oracle 금지 정책은 유지). **nonce/IV는 매 암호화마다 새로 생성한다(재사용 금지)** — AEAD를 직접 쓰면 우리 책임이다. 판정은 parity 하네스가 아니라 **Kotlin 자체 테스트 + migration-safety-gate I-7**이다(암호문이 불투명해 비교기가 못 연다).
2. **양방향·교차 런타임 fixture는 만들지 않는다.** Python이 Kotlin 산출물을 읽을 요구가 없다. crypto fixture는 Kotlin 단독 round-trip·tamper·빈값·긴값·다른 키만 본다.
3. **Argon2·JWT도 신규 기준.** "기존 PHC를 그대로 검증"·"양방향 JWT"의 근거가 사라진다. 남는 요구는 순수 기능·보안: Argon2id로 안전히 해시·검증하고 파라미터 상향 시 로그인 성공 경로에서 재해시(best-effort), JWT는 HS256으로 `sub`/`exp`/`typ`를 담고 `exp` 경계를 clock skew 0으로 판정. **Phase 0 spike가 발견한 함정(필수조치 A·B — 재해시 전체 파라미터 동등성, JWT skew 60초 기본값)은 호환과 무관한 순수 정확성 문제이므로 그대로 유효**하다. 판정은 **migration-safety-gate I-8(Argon2)·I-9(JWT)** + 필수조치 A·B 회귀 fixture다.
4. `encryption_scheme`/`key_version` 컬럼은 **향후 키 회전용**으로만 둔다(롤백 호환용이 아님). 처음부터 새 scheme 값(예: `aes-gcm-v1`)으로 쓴다.

> **옛 §4.3 번호 목록(양방향 교차 런타임 fixture·Fernet 직접 구현·`fernet-v1` 읽기/쓰기 유지·양방향 JWT/Argon2)은 삭제했다 — 위 재개발 방침 1~4가 대체한다.** 삭제 근거는 변경 이력 §4.3 항목(롤백·호환성 요구 소멸)이다. Fernet 구현 요건(0x80·128비트 IV·PKCS7·HMAC 우선·상수시간·TTL 없음)은 표준 AEAD로 갈음돼 더는 요구가 아니다. 역사 근거가 필요하면 `00_progress.md` 결정 3 상세·crypto-spike 산출물에 남아 있다.

### 4.4 비동기 작업 큐

ARQ의 Redis 내부 직렬화 형식을 Kotlin에서 흉내 내지 않는다. 권장 최종 구조는 PostgreSQL `conversion_jobs` 테이블과 lease 기반 worker다.

예시 필드:

- `conversion_id` PK/FK
- `state`, `attempts`, `next_attempt_at`
- `lease_owner`, `lease_until`
- `created_at`, `updated_at`

이 절의 설계는 기준 전환과 무관하다. ARQ를 흉내 내지 않기로 한 것은 초판부터 이미 "Python 동작 보존"이 아니라 내구성 요구에서 나온 결정이었다.

문서·변환·작업 행을 같은 DB 트랜잭션에서 저장하면 “DB 커밋 성공, 큐 등록 실패” 간극이 사라진다. worker는 `FOR UPDATE SKIP LOCKED`로 작업을 가져가고 lease 만료 시 재처리한다. 완료된 변환을 다시 LLM으로 보내지 않도록 idempotency 검사를 둔다. 최대 2회 호출 요구(§2.3)를 지키기 위한 것이지 Python 구현을 재현하기 위한 것이 아니다.

- 도메인 실패, 잘린 결과, provider 설정 오류: `failed`로 확정하고 자동 재시도하지 않는다.
- DB·일시 네트워크 오류: 제한된 횟수와 backoff로 재시도한다.
- 로그: conversion id, 상태, 시도 횟수, failure code만 기록한다.
- 보존 파기: scheduler + PostgreSQL advisory lock으로 다중 worker 중복 실행을 막고 나눠 commit한다. 04:00 KST·500건은 현재 운영값이며 조정 가능하다(§2.3).

전환 후 Redis가 다른 기능에 쓰이지 않는 것을 다시 확인한 뒤 Redis 서비스와 볼륨을 제거한다. 관찰 기간 전에는 롤백을 위해 보존한다.

### 4.5 문서 추출·내보내기

| 형식 | Kotlin 후보 | 필수 검증 |
|---|---|---|
| DOCX 입력·출력 | Apache POI XWPF | 본문, 표, 머리글·바닥글, 텍스트박스, 문단 줄바꿈 |
| PDF 입력 | Apache PDFBox | 페이지 순서, 텍스트 없는 PDF 거절, 크기·페이지 제한 |
| HWPX 입력·출력 | ZIP + namespace-aware StAX/JAXP | DTD/외부 엔터티 차단, zip bomb 제한, 자체 round-trip |
| TXT 출력 | JVM UTF-8 | BOM 없음, 제어문자 제거 |

현재 Python docx 추출기는 비공개 XML 요소까지 직접 순회한다. 초판은 그 순회를 그대로 재현하는 것을 목표로 삼았고, 이 항목을 일정 변동의 최대 요인으로 지목했다. 기준 전환으로 목표가 바뀐다. **판정 기준은 "Python과 같은 문자열이 나오는가"가 아니라 "원문서의 필수 정보(본문·표·머리글/바닥글·텍스트박스)가 누락 없이 추출되는가"다.**

기존 `tests/ingest/fixtures`와 골든 문서를 양쪽 구현에 넣어 정규화된 텍스트를 비교하는 하네스는 그대로 만든다. 다만 불일치는 실패가 아니라 §1.1의 분류 대상이다. Python이 놓치던 요소를 Kotlin이 더 잘 뽑아내면 그것은 통과 사유이며 `의도된 개선`으로 기록한다.

바뀌지 않는 것이 둘 있다. 첫째, 포팅하지 못한 요소를 조용히 누락하지 않는다. 지원 한계로 문서화하거나 실패로 알린다. 둘째, 입력 10MB, 압축 해제 예산, 제어문자 제거, DTD·외부 엔터티 거절, 스캔 PDF 거절, HWPX mimetype·ZIP 엔트리 순서 조건은 보안·비용 요구이므로 그대로 테스트로 옮긴다.

### 4.6 LLM과 쉬운 글 품질

Kotlin `LlmProvider`는 provider SDK 응답을 다음 공통 타입으로만 노출한다.

- text
- provider/model
- input/output token
- finish reason 및 truncated 여부

초판은 프롬프트·어려운 말 사전·마스킹 규칙·스타일 검사·보정 채택 규칙을 byte-for-byte 또는 정규화 동등하게 포팅하고 품질 개선을 섞지 않기로 했다. 이 요구는 철회한다. 포팅 방식은 항목마다 다르다.

| 대상 | 방식 | 이유 |
|---|---|---|
| 246개 어려운 말 사전 | 데이터를 그대로 옮긴다 | 축적된 자산이다. 자산 이전이지 동등 포팅이 아니다. 항목 추가·수정은 전환과 분리해 별도로 한다 |
| 프롬프트 | 현재 문안에서 출발하되 필요하면 고친다 | 마스킹 2종 축소로 자리표시자 지시가 바뀐다. 현재 문안을 그대로 두면 존재하지 않는 자리표시자를 지시하게 된다 |
| 마스킹 규칙 | 2종 기준으로 다시 구현 | §2.3 |
| 스타일 검사·보정 채택 | 요구사항 기준으로 다시 구현 | 판정 임계값은 Kotlin에서 정한다. 단, 스타일 규칙을 한 곳에 정의하고 프롬프트 생성과 골든셋 평가가 같은 정의를 쓰는 원칙은 Kotlin `core`에서도 유지한다 |

각 항목이 무엇을 보장해야 하는지는 요구사항 인벤토리(§1.1)에 올린다. 사전에서 실제 등장 낱말만 프롬프트에 싣고 출력 검사는 사전 전체 기준으로 도는 현재 구조처럼, 코드에만 적혀 있던 설계 의도가 인벤토리에 오르지 못하면 그대로 사라진다.

전환 게이트는 다음 순서다.

1. fake provider 단위 테스트로 파이프라인 계약(호출 횟수, 절단·빈 결과·자리표시자 유실·보정 악화 처리)을 검증한다.
2. `tests/golden/documents`의 56개 골든 문서로 스키마·팩트·스타일 규칙 검사를 **절대 기준**으로 판정한다. 합격선(필수 항목 충족률, 규칙 위반 허용치)은 Phase 0에서 수치로 확정한다.
3. 고정 응답 fixture로 보정 트리거와 채택 규칙이 요구사항대로 동작하는지 확인한다.
4. 실제 provider 소량 실행으로 모델, 파라미터, max token, Anthropic effort가 의도한 설정인지 확인한다.
5. 전체 LLM judge 평가는 별도 비용 승인 후 실행하고 **Phase 0에서 합의한 절대 점수 기준**으로 판정한다.

5번의 단서는 **미결이다(2026-08-12 2차 개정으로 재개봉).** 원래 단서는 "Python의 현재 점수를 참고 하한선으로 쓰고, Kotlin이 그보다 낮으면 `미확인`으로 열어 원인 설명 전까지 Phase를 닫지 못한다"였다. §7 검증 매트릭스 2차 개정은 반대로 **"품질 게이트는 Python 수치를 하한선으로도 쓰지 않는다"**고 적었다. 둘은 양립하지 않으므로 **어느 쪽도 지금 지켜야 할 규칙이 아니다.**

판단이 갈리는 이유가 실측에 있다 — Python의 현재 골든셋 통과율은 **실수집 52.8% · 전체 64.3%**이고 KPI는 **0.90**이다(`02_quality-baseline.md`). 실패하는 구현의 점수를 하한선으로 쓰면 *"Kotlin 65%"*가 통과가 되고, 반대로 하한선을 아예 두지 않으면 **조용한 하락을 잡을 장치가 없다.** 둘 다 실제 위험이다.

**이 단서는 품질 합격선 결정과 함께 확정한다**(인벤토리 §9-A, STY-03·04). 그 전까지 이 절을 근거로 Phase를 닫거나 열지 않는다.

LLM SDK 자체의 자동 retry와 worker retry가 겹쳐 호출 수가 늘지 않도록 한 계층만 재시도 책임을 가진다. 문서당 최대 2회라는 제품 계약은 네트워크 재전송과 별도로 메트릭에 드러나야 한다.

**제안 (미확정 — codex 계획 심사 Q6, 리더·Phase 0 합격선 확정에 종속).** 골든셋 64.3%→90%·장문 절벽은 언어 무관이라 재개발이 자동으로 닫지 않는데, 현재 계획에서 이 품질 합격을 **책임지고 닫는 단계가 명시돼 있지 않다** — 합격선은 Phase 7 즉시 중단 기준에서야 다시 나타난다. 담당 단계 후보를 **제안만** 한다(확정 아님): Kotlin 프롬프트·스타일·LLM provider가 모두 서는 **Phase 5 종료 게이트에 "현재 코퍼스·고정 judge로 Phase 0 합격선 충족" 증명을 추가**하고, Phase 7 진입 전 이를 필수 통과로 둔다. 단 **합격선 수치 자체가 미결(인벤토리 §9-A)**이므로 Phase 0 수치 확정 없이는 이 게이트가 판정 불가다. 최종 배치와 수치는 리더가 정한다.

### Phase 7. 첫 배포·파일럿 관찰 (일방향) — 배포 1일 + 관찰 1~2주

> **2026-08-12 2차 개정.** 롤백을 포기했고 절체할 운영 Python이 없다(재개발). "절체"가 아니라 **첫 배포**다. 아래는 병행 절체 절차를 일방향 배포로 다시 쓴 것이다.

1. 빈 DB에 Flyway로 스키마 적용, 스키마 checksum 기록
2. Kotlin API·worker 기동
3. 전용 synthetic 계정으로 전체 smoke 실행
4. React 트래픽을 Kotlin `/api`에 연결하고 파일럿 업로드 개시
5. 실패율·p95 지연·pending 체류·LLM 호출 수(문서당 ≤2)·내보내기 실패를 관찰
6. **기능 누락 신고 경로를 연다.** 재개발에는 Python 차분 그물이 없으므로(§1.1 방어 2·3 소멸) 이 신고 경로가 **누락을 잡는 마지막 그물**이다 — 접수 내용을 요구사항 인벤토리에 되먹인다. 신고가 실제 누락으로 확인되면 그 동작이 `03_rebuild-extraction-list.md`에서 빠졌던 것이므로 목록도 함께 고친다

즉시 중단 기준(롤백이 아니라 **신규 업로드 중단 + 원인 수정 후 재개**):

- AEAD 복호화 round-trip 실패, 또는 변조(tamper)가 예외 없이 통과됨(복호화 oracle)
- 다른 사용자 데이터 노출 또는 404 소유권 규칙 위반
- 마스킹 전 본문이 LLM이나 로그로 전송됨. 마스킹 2종 축소 이후에도 주민등록번호·카드번호가 평문으로 나가면 이 기준에 해당한다
- 중복 LLM 호출, 작업 영구 유실, pending 무한 체류
- 문서 추출·내보내기에서 필수 정보 누락 또는 산출 파일이 열리지 않음. 초판의 "주요 fixture 불일치"를 새 기준으로 다시 쓴 것이다 — Python과 텍스트가 다르다는 사실 자체는 중단 사유가 아니고, 사용자가 받는 문서에서 정보가 빠지거나 파일이 깨지는 것이 중단 사유다
- 골든 품질이 Phase 0 합격선 미만이거나 최대 2회 호출 요구 위반

**롤백 대상이 없다.** 되돌아갈 Python 런타임을 운영하지 않는다. 위 기준에 걸리면 대응은 "신규 업로드를 멈추고 Kotlin에서 원인을 고쳐 다시 배포"(fix-forward)다. ARQ 재등록 도구·Python 이미지·Redis·기존 키 보존은 모두 불필요하다. 계약 개선의 "롤백 창 양립성"(옛 §2.2) 제약도 없다 — 계약은 요구사항 판단만으로 고친다.

**미해결 위험 — 리더 판단 대기 (codex 계획 심사 Q3).** "보존할 운영 DB 없음"(§9 결정 2)은 **첫 파일럿 업로드 순간까지만** 참이다. 업로드가 시작되면 계정·암호문·문서·작업 상태가 생기고, 일방향 전환이라 그 데이터를 복구할 경로가 없다. 키·스키마·배포 결함이 나면 이미 받은 파일럿 데이터를 영구히 못 읽거나 장기 정지할 수 있는데, 현재 계획은 fix-forward만 규정하고 생성 데이터의 백업·복구를 규정하지 않는다. 롤백을 포기한 결정 자체는 유효하나(§9 결정 2), **파일럿 데이터 복구 전략(예: 파일럿 개시 전·배포 전 DB 스냅샷·키 백업·PITR)을 둘지는 사용자 결정 사항**이다. deep-reasoner는 이를 정하지 않는다 — 파일럿 업로드를 열기 전에 리더가 판단한다.

### Phase 8. Python 폐기와 문서 동기화 — 1주 (선행 조건 있음)

> **2026-08-12 2차 개정.** 재개발에서 Python 제거는 "결과"가 아니라 **선행 조건이 붙은 단계**다. **착수 전제: `03_rebuild-extraction-list.md`의 폐기 게이트가 0으로 닫혀 있어야 한다** — 프롬프트 전문·스타일 상수·**치환 비문 실측 튜닝**·골든셋 채점 기준 등 코드에만 있던 판단이 전부 명세·fixture로 옮겨졌음이 확인돼야 한다. 재개발에는 Python 차분 그물이 없어, 이 게이트가 열린 채 지우면 누락이 **영구 손실**이 된다.

- `app/` 런타임 제거 — **Phase 9까지 존치하는 오프라인 도구(`app/easyread/{judge,goldenset,collection,bokjiro}.py`·`scripts/{benchmark,collect_*,pilot_report}.py`)는 제외**한다(아래·§5 Phase 9 — Phase 9가 그 파일로 Kotlin 대체물을 검증하므로 먼저 지우면 순환). ARQ, FastAPI, SQLAlchemy, Alembic 제거
- Python API/worker Dockerfile과 compose 서비스 제거
- Redis가 무사용임을 확인하고 서비스·환경변수·볼륨 정의 제거
- README, master-plan 6장, 운영 runbook, 장애 대응 명령을 Kotlin 기준으로 갱신
- Python용 비밀값·의존성·CI gate 정리

오프라인 도구(judge·goldenset·collection·bokjiro·benchmark·리포트)는 이 단계에서 함께 지우지 않고 **한시 존치**한다 — 아래 Phase 9에서 건별로 이식/폐기한다.

### Phase 9. 오프라인 도구 이식·폐기 — 추가 2~3주 (한시 존치 후 최종 폐기)

> **2026-08-12 2차 개정.** "선택"이 아니라 **한시 존치 후 폐기**다. 영구 oracle로 두자던 논거("독립적인 두 번째 관점")는 약하다 — 아키텍처 규칙 4가 프롬프트 생성과 골든셋 평가에 **같은 스타일 정의를 공유**시키므로 채점자 독립성은 지금도 없다. 진짜 독립성은 fixture·명세에서 온다.

- `scripts/benchmark.py`, `collect_*`, `pilot_report.py`
- `app/easyread/goldenset.py`, `judge.py`, `collection.py`, `bokjiro.py`
- 관련 fixture·CLI·리포트 형식

이들은 코드에만 있는 판단이라기보다 **분량이 큰 꼬리 작업**이다(collection.py 1,071줄 등, `03_rebuild-extraction-list.md` §K). 건별로 "Kotlin 이식 vs 폐기"를 정한다. 단 judge **루브릭**과 goldenset **판정식**은 도구와 별개로 명세화한다(같은 문서 §D) — 도구를 버려도 §4.6 합격선 판정은 남아야 하기 때문이다. Python 도구의 최종 제거 조건은 "Kotlin과 같은 값"이 아니라, **Kotlin 평가 도구가 같은 fixture로 §4.6 합격선을 단독 판정**할 수 있음이다.

## 7. 예상 일정과 인력

런타임 전환은 약 **10~13 person-weeks**, 오프라인 도구까지 제거하면 **12~16 person-weeks**로 본다. 초판(11~14 / 13~17)에서 하단과 상단을 각 1주씩 낮춘 값이다.

기준 전환으로 줄어드는 작업과 늘어나는 작업이 함께 있으므로, 근거를 나눠 적는다.

**줄어드는 쪽**

- 문서 추출(§4.5). Python docx 추출기의 비공개 XML 순회를 문자 단위로 재현하는 작업이 빠진다. 초판이 "변동 폭이 가장 큰 항목"으로 지목한 곳이므로 상단 추정이 내려간다. Phase 4에서 약 0.5주.
- 도메인 로직(§4.6). byte-for-byte 일치를 맞추는 반복이 사라진다. Phase 2에서 약 0.5주.
- 마스킹 5종 → 2종. 패턴 3개와 그 우선순위·경계값 테스트가 빠진다. 실재하는 절감이지만 규모는 1일 안쪽이다. 92줄짜리 모듈의 일부다.
- 보존 DB 없음(§9 결정 2). 실 DB dump 수집·Alembic 대조·checksum 기반 baseline 절차가 조건부로 밀린다. Phase 0에서 1~2일.
- ~~Fernet 직접 구현 승인(§9 결정 3). spike의 성격이 "가능한가"에서 "정확히 구현했는가"로 바뀌어 실패 시 재암호화 시나리오가 빠진다.~~ **2차 개정으로 무효** — 롤백 대상이 사라져 Fernet 직접 구현(~150줄) 자체가 불필요해졌다. 절감은 "변동 폭 축소"가 아니라 **항목 삭제**이며, 표준 AEAD 채택으로 Phase 0·4에서 그 몫이 통째로 빠진다.

**늘어나는 쪽**

- 요구사항 인벤토리 작성(§1.1). 동등 비교를 판정에서 뺀 대가로, "무엇을 만들어야 하는가"를 사람이 적어야 한다. Phase 0 전역분 1~2일 + 각 Phase 범위분.
- 차분 불일치 분류. 자동 판정(같다/다르다)이 사람 판단(의도된 개선인가)으로 바뀐다. Phase 2·4에서 각 2~3일.
- 계약 개선(§2.2). Kotlin·계약 파일·React를 같은 변경 단위에서 함께 고친다(롤백 창 양립성 확인은 소멸 — 2차). 개선을 몇 건 채택하는지에 비례하며, Phase 3·6에서 0~0.5주.
- 품질 합격선 수치 합의(§4.6). 절대 기준을 새로 정해야 한다. Phase 0에서 1일.

**순변화**는 크지 않다. 절감분 약 1.5주에 신규 작업 약 1~1.5주가 맞물린다. 총량이 아니라 위험 분포가 바뀐 것이 이번 전환의 실질적 이득이다 — 동등 포팅에 실패해 일정이 폭증하는 시나리오가 사라지고, 대신 누락을 늦게 발견하는 위험이 생겼다(§1.1).

- 1명 순차 수행: 런타임 절체 11~15주 + 관찰 1~2주
- 2명 병렬 수행: 백엔드/문서·품질과 React/계약·E2E를 나누면 7~10주 + 관찰 1~2주

2명 병렬 추정은 초판과 같다. 요구사항 인벤토리와 불일치 분류는 병렬화가 잘 되지 않는 종류의 작업이라 인원을 늘려도 같은 비율로 줄지 않는다.

일정 단축을 위해 품질·보안 gate를 생략하지 않는다. 시각 UI 개편, React 메이저 업그레이드, DB 재설계, 새로운 결제·RAG 기능은 이 일정에 포함하지 않는다. 기준 전환이 "개선을 허용한다"는 뜻이지 "범위를 넓힌다"는 뜻은 아니다. 요구사항을 충족하는 데 필요하지 않은 개선은 전환 후로 미룬다.

## 8. 완료 정의

### 런타임 전환 완료

- 운영·compose 경로에 Python API/worker가 없다.
- React가 Kotlin API만 호출한다.
- **요구사항 인벤토리의 모든 항목이 구현·검증되고 미충족이 0이다.** 의도적으로 다르게 만든 항목은 사유와 함께 기록되어 있다.
- **저장 암호화·인증이 Kotlin 안에서 기능으로 검증된다** — AEAD 암호화→복호화 round-trip이 성립하고 변조를 거부하며, Argon2 해시·검증·재해시(전체 파라미터 동등성)와 JWT 발급·검증(skew 0 경계)이 요구대로 동작한다. **호환성·양방향 요구는 없다**(2026-08-12 2차).
- 승인된 계약 개선분이 계약 파일·Kotlin·React·테스트에 같은 내용으로 반영되어 있다.
- 골든 품질이 Phase 0에서 확정한 합격선을 충족한다.
- 핵심 사용자 E2E와 계약·보안 gate가 통과한다.
- Kotlin worker의 유실·중복·재시도·파기 동작이 운영 지표로 확인된다.
- 첫 배포·파일럿 관찰 절차와 운영 문서가 완료된다(롤백 리허설은 없다).
- **`03_rebuild-extraction-list.md`의 폐기 게이트가 0으로 닫혀 있다** — 코드에만 있던 판단이 전부 명세·fixture로 옮겨진 뒤에만 Python을 지운다.

### 저장소 전체 전환 완료

- 위 조건에 더해 골든 평가, 벤치마크, 수집, 파일럿 리포트 CLI가 Kotlin으로 전환된다.
- `pyproject.toml`, `uv.lock`, Python CI와 Python 소스가 제거된다.
- Python을 참고 구현으로 사용한 마지막 차분 비교 결과와 그 분류표가 보관된다. Python을 지우면 §1.1의 방어 수단 하나가 함께 사라지므로, 제거 시점의 인벤토리 상태를 함께 남긴다.
