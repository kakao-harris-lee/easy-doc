# R2 행동 안내 진단과 개선 계획

작성일: 2026-09-26 · 상태: **ER-27 표시 수정·ER-28 fake 분석 기반의 검증·PR #162 리뷰·검토용 재시작 완료**

최신 구현·리뷰·재시작 상태는 [구현 기록](../reports/2026-09-26-r2-implementation.md)을 따른다. 이하 진단 및 인계 당시의 미착수 표기는 이력이며, ER-28 잔여와 ER-29~32는 아직 완료되지 않았다.

## 1. 결론과 이번 작업의 범위

현행의 **6개 고정 섹션으로 별도 안내문 후보 생성 → 적용 → 확인 저장**은 기존 R2 계획과 대체로 일치한다. 그러나 안내문 적합성 판단·행동 추출·추가 안내·전체 문서 보완을 구분하지 않은 계획이 사용자 의도에 맞지 않는다. 후보 미리보기에서 주의사항을 숨기는 구현 결함도 별도로 있다. 이름만 바꾸거나 프롬프트에 보존 지시를 더하는 것으로 완료하지 않는다.

새 기준은 **변환글의 안내문 적합성 판단 → 원문 근거가 있는 행동 추출 → 사용자가 단계별 추가 안내 또는 전체 문서 보완 선택 → 누락·변경 대조 → 명시적 적용**이다. 기존 ER-05~07의 작업·과금·CAS 구현 이력은 보존하되, 새 요구 충족은 ER-27~32로 추적한다. 이 문서와 충돌하는 기존 R2 생성·UX·완료 기준은 이 문서를 우선한다.

이번에는 요청된 변환 한 건의 저장 데이터, 직접 연결된 R2 코드·계약·기존 테스트·계획을 읽었다. 수정 경로는 `docs/`뿐이다. 완료 조건은 사례의 실제 누락과 표시 누락을 구분하고 원인을 근거로 설명하며, 후속 구현 단위·계약 영향·검증 기준을 연결하는 것이다. 문서 검토·수정은 최대 2회로 제한한다. 운영 데이터 변경, 후보 적용, 재생성, 유료 provider 호출, 배포는 실행하지 않았다.

## 2. 요청된 변환의 확인 결과

대상: `conversions/6c0a995c-1868-49bd-8d5f-233bafbb036c`.

- 2026-09-26 조회 시 변환은 `done`, 본문 revision은 1이다.
- 행동 안내 작업 1건이 성공했다. 생성 접수 시각은 2026-09-26 08:28:30 KST이고 후보의 기준 revision도 1이다.
- `action_guides` 저장본은 없다. 현재 문제의 대상은 **적용 전 후보**이며, 기존 변환글이 이 후보로 덮어써진 상태는 아니다.
- 운영 PostgreSQL에 읽기 전용 세션으로 해당 건만 조회해 원문·저장 본문·후보를 대조했다. 암호화 키나 평문 덤프를 파일에 저장하지 않았다. 저장소에는 필요한 관찰만 남긴다.
- 코드 기준은 `31dae7a7`이다. 운영 프런트 컨테이너의 `ConversionPage-RWw__xzt.js`에서도 후보 미리보기의 `items.map(...text).join(' / ')` 경로를 확인했다. 브라우저 조작·화면 캡처나 배포 백엔드 전체의 소스 동일성 검증은 수행하지 않았다.

문서는 찾아가는 영화관 사업의 배경·목적, 운영 주체, 사업기간, 대상, 사전 문의를 설명한다. 완결된 신청 절차서는 아니며, 근거가 있는 독자 행동은 **희망 상영일 최소 1주 전 문의**다.

기간은 원문의 과거 연도를 그대로 보존해야 한다. 이를 현재 신청 가능한 사업으로 단정하거나 날짜를 현재 연도로 바꾸지 않는다. 최신 운영 여부는 이번 진단으로 확인하지 않았다.

## 4. 수정할 사용자 흐름

### 4.1 안내문 적합성 판단과 행동 추출

판단 대상은 현재 저장된 변환글이며 사실의 기준은 원문이다. 사용자가 ‘행동 확인’을 요청하면 문서가 안내문인지, 어떤 내용을 근거로 판단했는지, 독자가 할 일이 실제로 있는지를 보여 준다. 안내문 여부와 실행할 행동의 존재 여부를 별개로 다룬다.

- 안내문이며 행동 있음: 행동 목록과 각 행동의 조건·기한·근거를 표시한다.
- 안내문이지만 구체 행동 없음: 설명 자료라는 이유와 함께 ‘원문에서 할 일을 찾지 못했습니다’로 표시한다. 신청 절차를 생성하지 않는다.
- 안내문 아님: 판단 이유를 표시하고 R2 생성 선택지는 열지 않는다. 기존 본문 작업은 계속 가능하다.
- 혼합 문서: 안내 부분의 범위와 근거를 먼저 보여 준다. 전체 보완을 선택하면 비안내 부분도 보존한다.
- 판단 불확실: 관련 부분을 검토할 수 있게 한다. 사용자가 판단을 정정해도 없는 행동·기한의 근거가 생긴 것으로 처리하지 않는다.

R2의 두 생성 모드는 안내문 또는 혼합 문서에서 근거 있는 행동이 확인된 경우에만 허용한다. 행동 없음·비안내·판단 불확실 상태에서는 생성 모드를 제공하지 않고 판단 결과와 기존 본문 작업을 유지한다. 행동 없는 글의 일반적인 문장 개선은 이 기능의 전체 보완으로 우회하지 않는다. 서버가 분석별 허용 모드(`allowed_modes` 제안)를 반환하며 화면이 자체 추정하지 않는다. 판단 정정 후에도 행동 근거 검증을 통과해야 모드를 연다.

행동에는 누가, 무엇을, 어떤 조건에서, 언제까지, 어디로/어떻게, 필요한 것, 행동 결과와 다음 행동의 관계를 담되 **원문에 있는 정보만 채운다**. 없는 정보·불확실한 연결을 명시하고 ‘미기재’와 ‘해당 없음’을 구분한다. 행동 순서가 명시돼 있지 않으면 순서를 확정하지 않는다.

### 4.2 두 가지 산출물

| 선택 | 목적 | 반드시 보존할 범위 | 적용 |
|---|---|---|---|
| 단계별 추가 안내 | 할 일을 쉽게 찾고 따라가도록 돕는 보조자료 | 추출된 행동과 연결된 대상·조건·기한·준비물·예외 전체. 배경 설명 등은 원문/본문 링크로 남길 수 있음 | 별도 자료로 저장. 전체 문서 대체 자료로 표시하지 않음 |
| 전체 문서 보완 | 기존 변환글 전체에 행동 안내·필요한 풀이를 보완 | 원문의 의미·사실·배경·목적·목록·수치·조건·주석과 현재 본문의 유효한 편집 내용. 반복 표현 병합은 가능하되 대응 기록 유지 | 별도 미리보기에서 변경 비교 후 사용자가 전체 반영을 요청할 때 본문 저장 |

추가 안내는 문서와 함께 제공하는 자료임을 명시하고, 행동에 영향을 주는 조건을 외부 링크나 접힌 영역에만 숨기지 않는다. 전체 보완은 6개 신청 섹션으로 다시 요약하지 않고 기존 문서의 흐름과 범위를 유지하며 필요한 행동 블록을 넣는다. 보조자료에서 생략한 배경과 전체 보완본에서 누락된 배경을 같은 기준으로 평가하지 않는다.

전체 보완 과정에서 현재 본문과 원문이 충돌하면 자동 삭제·원문 복원·승인으로 해결하지 않는다. 해당 변경과 근거를 제시하고 담당자 해결 전 적용을 제한한다. 원문에 없는 사용자의 추가 문장도 조용히 지우거나 원문 사실처럼 확정하지 않는다.

### 4.3 이 사례의 기대 동작

문서를 ‘사업 소개와 사전 문의 안내가 섞인 안내문’으로 제시하고, 확인되는 행동은 ‘상영을 원하면 희망 상영일 최소 1주 전에 문의하기’ 1개로 추출한다. 대상 4개와 사업기간은 관련 조건으로 함께 보이고 문의처·필요 서류는 원문 미기재로 남긴다.

독자의 이해를 돕기 위해 대상과 기간 확인을 앞에 배치할 수 있지만, 이는 **읽고 확인할 내용**이며 원문에 명시된 필수 신청 절차와 구분한다. 전화하기·서류 제출·방문·접수 완료 같은 후속 절차는 추측하지 않는다. 행동 하나뿐이어도 정상 결과다.

추가 안내에는 위 행동과 조건을 쉽게 제시한다. 전체 보완에는 기존 배경·목적 문단, 관객 규모와 지역 격차 설명, 운영 주체·협력 내용, 대상 4개·기간·문의 기한이 모두 남아야 한다. 섬 지역 등 이미 쉬워진 표현을 유지하고 의심 표기는 원문 대조가 필요한 항목으로 제시한다.

### 4.4 적용 전 대조

‘새 안내문 후보’ 대신 ‘단계별 추가 안내 미리보기’ 또는 ‘전체 문서 보완 미리보기’를 표시한다. 적용 전에도 모든 text·cautions·검토 상태를 보여 주고 원문 근거를 열 수 있게 한다. 단계는 별도 줄/카드로 표시하고 `/`로 한 줄에 합치지 않는다.

기존 본문과 달라진 부분, 보존된 부분, 확인이 필요한 부분을 구분한다. 전체 보완에서 누락·변경 미해결 사항이 있으면 ‘전체 내용 확인됨’으로 표시하거나 전체 반영하지 않는다. 자동 검사 0건은 의미 보존 완료가 아니며, 검토 완료는 담당자가 해당 버전을 확인했다는 뜻이다. 초안 보관은 허용한다.

## 5. 누락 방지와 구현 방향

### 5.1 생성 전에 원문 범위를 고정

후보가 인용한 부분만 검증 분모로 삼지 않는다. 먼저 원문 전체 단위에 안정된 식별자와 범주를 부여하고 현재 본문과의 대응을 확보한다. 기존 원문 단위·문단 매핑을 재사용하되, 없거나 모호하면 제한 상태로 남긴다. 분석/생성 모델이 어떤 문단을 빼도 서버의 원문 단위 목록은 줄어들지 않아야 한다.

원문 단위별로 보존 위치, 병합 위치, 보조자료 범위 밖인 이유, 검토 필요를 기록한다. 행동별 조건·예외·기한도 별도 대응을 둔다. 인용이 존재한다는 것과 인용의 뜻을 결과에 보존했다는 것을 분리한다. 특히 한 문단의 여러 조건 중 일부만 옮긴 사례를 포함해 검토한다. ‘대응 있음’만으로 의미 검사를 통과시키지 않는다.

추출 단계에서 행동을 배경으로 오분류해 빠뜨리는 경우도 검토 대상이다. ‘추출된 행동을 모두 출력함’만으로 행동 누락 없음으로 판정하지 않는다. 원문 전체→분석의 행동·조건 추출 검토와 분석→생성의 보존 검토를 분리하고, 실제 문의처·서류가 있는데 `not_in_source`로 분류한 사례도 회귀에 포함한다. 행동/조건 추출의 미해결 신호가 있으면 서버 허용 모드를 열지 않는다. 이 검사에도 의미 판정의 한계를 표시하고 기계적인 원문 단위 대응률을 정확도 보증으로 사용하지 않는다.

전체 보완본은 원문 단위 중 미대응 항목이 있거나 실제 누락·충돌 신호가 미해결이면 적용/확인 출력을 막는다. 구조 매핑이 모두 있어도 사실·조건·쉬운 표현의 사람 검토는 남는다. 추가 안내는 모든 추출 행동과 관련 조건이 대응해야 하고, 제외한 비행동 정보의 범위를 명시한다. 원문 문장 전체를 그대로 복제해야 한다는 요구는 아니다.

### 5.2 분석과 생성의 계약 제안

정확한 wire 이름·경로는 ER-28에서 고정한다. 아래는 현행 API가 아닌 후속 계약 설계다.

| 자원/입력 | 필요한 정보 |
|---|---|
| 분석 스냅샷 | 본문 revision, 원문 단위 기준, 분석 버전, 안내문 적합성·이유·근거·판단 불확실성, 행동 목록, 문서 전체 대응 목록 |
| 추출 행동 | 안정 ID, 행위자/대상, 할 일, 기한·조건·예외·준비물·문의 정보, 순서 관계, 근거, 미기재/미확인 상태 |
| 생성 요청 | 분석 ID/revision, `mode`(추가 안내/전체 보완), 현재 본문·대상 안내문 revision, request_id, 저장된 읽기 수준 |
| 생성 결과 | 산출물 종류·schema version·기준 버전, 내용 블록과 행동 연결, 원문/현재 본문 대응, 변경·누락 신호, 검토 상태 |
| 적용/출력 | 대상 자원, 기대 revision, 담당자 확인 버전, 산출물 종류를 구분한 파일명·표제 |

현행 `ActionGuideContent` v1은 전체 보완본을 담기 위한 계약으로 사용하지 않는다. v2 또는 별도 결과 타입을 명시하고 OpenAPI·Kotlin DTO/계약 테스트·React API 타입을 한 변경 단위로 맞춘다. 분석 판단의 정정도 revision을 올려 이전 생성 결과를 무효화한다. 본문 변경·삭제·만료·소유권 검증은 분석부터 출력까지 이어진다.

누락·충돌 신호에는 대상 단위/행동·근거·기준 revision과 해결 상태를 둔다. 담당자가 분석/결과를 수정하고 해당 버전의 근거 대조를 확인하면 재검증하며, 신호별 해결 이력을 저장한다. 전체 확인 체크 하나로 모든 신호를 지우지 않는다. 결과 수정 시 기존 확인을 해제하고 전체 반영은 분석·결과·검토 revision까지 대조한다. 반영 멱등 키와 동일 본문 반영의 revision 처리도 계약에 명시한다.

### 5.3 생성 품질·길이·비용

- 저장된 읽기 수준을 전달하고 현재 본문의 쉬운 표현을 기준으로 삼는다. 공식 명칭은 보존하되 풀이를 유지한다. 원문의 어려운 단어로 되돌아가는 것을 회귀로 다룬다.
- 전체 보완에 4,000자·6섹션 상한을 적용하지 않는다. 기존 문서 길이 정책과 출력 팽창을 검토해 모드별 상한을 정한다. ER-28에서 입력/출력 한도와 초과 응답을 계약화하기 전 전체 보완을 노출하지 않는다. 상한 초과·절단은 제한/실패로 처리하고 내용 축약으로 숨기지 않는다.
- 분석은 화면 진입만으로 유료 호출하지 않는다. 기존의 현재 버전 분석이 있으면 재사용하고, 추가 분석에 모델이 필요하면 요청 전 비용과 목적을 알린다. 분석→생성 두 단계가 사용자 모르게 두 번 과금되지 않도록 합계와 각 요청 비용을 먼저 확정한다.
- 새 흐름의 호출 수·고객 크레딧·문서당 시도 상한 적용 방식은 ER-28의 출시 전 결정 항목이다. 기존 한 요청 1호출·자동 재시도 0회와 멱등/예약·반환 보장은 유지한다. 확정 전에는 fake 경로만 검증한다.
- 과거 R2 평가 승인이나 잔여 예산을 새 유료 평가 승인으로 간주하지 않는다. 실제 호출은 표본·모델·호출 상한·실패 포함 달러 상한을 명시한 실행 패킷의 별도 승인 후에만 수행한다.

### 5.4 저장·적용·호환성

추가 안내와 전체 보완 결과는 종류별로 보관하고 서로 덮어쓰지 않는다. 기존 v1 후보/안내문은 보조자료의 과거 결과로 식별하며, 분석·전체 대응 검증을 받은 결과로 승격하지 않는다. 재생성·추가 과금·검토 완료의 자동 이전은 하지 않는다.

전체 보완본 반영은 기존 본문 저장 CAS와 한 트랜잭션으로 묶고 content_revision을 증가시킨다. R1 확인, 행동 안내, 그림 등 본문 의존 상태는 기존 무효화 정책을 따라 갱신한다. 이전 본문은 기존 보존 기간 내 이력으로 남긴다. dirty·다른 탭 변경·생성 중 본문 변경 시 자동 덮어쓰지 않으며 초안 확인/복구 경로를 제공한다. 반영 후 본문 확인 상태도 자동 완료로 승계하지 않는다.

구현 인계 검토에서 현행 `ConversionReviewService.save`가 사용하는 `JdbcConversionRepository.SAVE_REVIEW_SQL`은 `reviewed_at = now()`를 항상 기록함을 확인했다. 따라서 기존 검수 저장 메서드를 그대로 호출하지 않는다. CAS·암호화·소유권·보존·무효화 경계를 재사용하되 전체 보완 반영에는 **확인 완료를 부여하지 않는 저장 동작**을 둔다. 이전 미확인 본문도 이력/복구 대상으로 남겨야 한다. R5 이력 토글이 OFF여도 전체 반영 트랜잭션에는 이전 본문의 암호화 스냅샷 보존을 필수로 포함하고, 스냅샷 저장 실패 시 반영을 롤백한다. 기존 snapshot 구조를 우선 재사용하되 선택적 확인 무효화 이벤트만으로 이전 본문 보존을 충족했다고 간주하지 않는다. 스냅샷도 문서 소유권·보존 기간·삭제·키 회전 규칙을 따른다.

기존 자원 읽기와 내보내기 회귀를 보장하고 새 계약은 capability로 구분한다. 기능을 되돌릴 때는 새 요청을 막고 진행 작업 정산·기존 자료 읽기를 보존한다. 배포나 토글 변경은 이번 계획 작성 범위에 포함하지 않는다.

현재 v1은 읽기·출력에도 같은 기능 토글을 검사하므로, v2의 신규 분석/생성 허용과 저장된 자료 읽기/출력 허용을 분리해 구현한다. 새 요청 차단 시에도 기존 자료는 소유권·보존·현재 버전·확인 정책에 따라 읽고 내보낼 수 있어야 한다. 단일 토글을 끄는 것만으로 이 롤백 요구를 충족했다고 간주하지 않는다.

| AC-R2-j | 상한 초과를 자동 요약으로 통과시키지 않음. 읽기 수준/쉬운 표현 유지. 분석/생성 비용을 사전 표시하고 재방문/재전송/worker 복구에서 중복 호출·정산 없음 |
| AC-R2-k | v1 자료를 전체 보완으로 오표시하지 않음. 전체 반영 시 본문 CAS·이력·R1/행동/그림 무효화 일관성, 보존·소유권·출력 경계 유지 |
| AC-R2-l | 결과를 보기 전에 고정한 문서별 기대 행동·조건·전체 보존 목록으로 개발/독립 보류 표본 평가. 잘못 추가한 의무/절차, 적용 조건 누락/변경, 전체 보완의 의미 누락 0건을 출시 게이트로 삼고 담당자가 대조. 독자의 정보 찾기·행동 이해와 실무자 검수 부담도 별도 확인 |

기존 AC-R2-a~e의 멱등·과금·복구·CAS·확인 출력은 회귀 기준으로 계속 유지한다. 현재 사례는 **유료로 다시 생성하지 않고** 저장 결과에서 관찰한 문제 유형을 회귀 기준에 반영한다. 실제 사용자 문서 전체를 fixture로 커밋하지 않는다. 재사용 허용이 확인된 공개 자료 또는 같은 실패 유형을 담은 합성 fixture를 기존 테스트에 추가한다.

구현 시 Kotlin은 관련 테스트 후 `cd backend-kotlin && ./gradlew build`, React는 `cd frontend && npm run check && npm run test -- --run && npm run build`, 연결 흐름은 기존 `frontend/e2e/action-guide.spec.ts`의 fake E2E로 검증한다. Compose 변경이 있으면 `docker compose config`도 확인한다. 코드가 바뀌면 최종 diff 기준으로 필요한 검증과 리뷰를 다시 수행한다.

무거운 Gradle/Testcontainers 검증 전 `pgrep -af 'GradleWrapperMain|GradleWorkerMain' | grep -v pgrep`와 `free -g`를 확인한다. 다른 프로젝트/워크트리 빌드가 있으면 기다리고, available이 6GB 미만이면 실행하지 않는다. 호스트 전체 무거운 빌드는 하나만 실행한다. 비정상 종료 시 `journalctl -u earlyoom`을 먼저 확인한다.

## 8. 이번 진단의 검증·한계

저장 데이터의 현재 상태와 내용 대조, 배포 프런트 번들, 직접 연결된 소스·기존 테스트·계약을 확인했다. 수정한 문서 8개의 로컬 링크 97개는 모두 존재했고, ER-27~32와 AC-R2-f~l의 연결을 검토했다. `git diff --check`와 새 문서의 공백 오류 검사를 통과했다. 제품 코드를 수정하지 않았으므로 Gradle·npm·E2E·유료 모델 평가는 실행하지 않았다. 기존 테스트의 통과를 이번 실행 결과로 주장하지 않는다.

한 건의 저장 결과로 일반 발생률이나 모델 품질을 추정하지 않는다. 이 사례에서는 배경 내용 축약과 표시 생략·표현 퇴행을 확인했고, 대상 4개·기간·문의 기한의 payload 누락은 확인되지 않았다. 개선 계획의 완료와 제품 수정·실제 품질 검증·출시는 각각 별도 상태다.

## 9. 구현 에이전트 전달 지시서

2026-09-26 후속 요청에 따라 이 계획을 구현 담당 에이전트에게 전달한다. 이번 인계의 완료 조건은 담당자가 계획과 직접 관련 코드를 읽고, 소유 경로·착수 순서·필수 검증·미결정을 확인해 회신하는 것이다. 제품 구현 완료와 구분하며, 이 인계 과정에서는 코드 수정이나 빌드를 실행하지 않는다.

### 9.1 담당과 파일 소유권

| 담당 | 소유 작업 | 수정할 경로 | 선행 조건 |
|---|---|---|---|
| `r2_frontend` | ER-27, ER-30 및 ER-31의 화면 연동 | `frontend/src/components/ActionGuidePanel*`, 필요한 변환 화면, 연결된 기존 React/Playwright 테스트 | ER-27은 바로 착수 가능. ER-30과 전체 반영 화면은 B의 계약·서버 기반 완료 후 |
| `r2_backend_contract` | ER-28, ER-29, ER-31의 계약·서버 | `contracts/easy-doc-v1.yaml`, 관련 Kotlin actionguide/본문 저장·이력·테스트, `frontend/src/api/` | ER-28에서 계약·상한·비용 제안을 구체화하고 정책 미결정은 명시. 계약·DTO·React API 타입 동시 변경 |
| 총괄 | 계획 정합성, 코드 리뷰, 검증 순서, ER-32 평가 실행 패킷 | 이 계획 및 관련 상태 문서 | 각 에이전트 최종 diff·검증 결과 수신 후 종합 |

`frontend/src/api/`는 B만 수정한다. A는 계약 요구를 B에 전달하며 같은 파일을 동시에 수정하지 않는다. 문서 상태 변경은 총괄이 담당한다. 재귀 위임·새 검증 하네스·운영 데이터 조회/수정·배포·유료 호출은 각 에이전트 작업에 포함하지 않는다.

### 9.2 A: 프런트엔드 구현 지시

1. ER-27에서 `text`·`cautions`·섹션 검토 상태를 적용 전에 모두 보이고, 항목별 원문 근거를 열 수 있게 한다. `/` 병합을 없애고 한 행동도 읽기 쉬운 블록으로 표시한다.
2. 현행 v1 결과의 제목은 ‘행동 안내 보조자료 미리보기’처럼 실제 제공 범위를 나타낸다. 분석·행동 추출이 구현되기 전에 ‘단계별 분석 완료’나 ‘전체 문서 보완’으로 표시하지 않는다.
3. caution에만 조건이 있는 사례, 내용이 있는 needs_review, 근거 없는 검토 항목, not_in_source, 한 행동, dirty/stale/충돌 회귀를 기존 테스트에 반영한다.
4. 이후 ER-30에서는 B가 확정한 계약을 사용해 판단 이유→행동→산출물 선택→대조 흐름을 구현한다. 서버 미지원 동작을 클라이언트에서 추측해 흉내 내지 않는다.
5. 구현 시 필수 검증은 프런트 check·전체 test·build와 관련 fake E2E다. Docker 스택을 사용하는 E2E는 총괄과 실행 차례를 조율한다.

### 9.3 B: 계약·백엔드 구현 지시

1. ER-28에서 분석 스냅샷·행동·두 결과 타입·대응 목록·실패/불확실 상태·CAS를 구체화한다. 계약만 바꾸고 소비자를 남겨 두지 않는다.
2. 비안내/행동 없음/불확실/혼합 문서를 정상 상태로 표현한다. 순서 근거가 없는 행동에 강제 순서를 부여하지 않고 수혜 대상과 신청 주체를 구분한다.
3. ER-29에서 원문 전체 단위 목록은 서버가 고정한다. 인용 존재 검사와 전체 누락 검사를 분리하고, 한 문단 안에서 일부 조건만 빠지는 사례를 검증한다. 읽기 수준을 전달하고 기존 쉬운 표현을 보존한다.
4. ER-31에서 전체 반영은 본문 CAS·이력·파생 상태 무효화와 함께 처리한다. v1 자료를 v2 검증 완료로 승격하지 않는다.
5. 분석/생성 호출·크레딧·시도 상한·길이 상한은 제안과 확정 여부를 구분해 보고한다. 미결정은 fake 구현의 구성 경계로 남기고 유료 노출을 활성화하지 않는다.
6. 구현 시 필수 검증은 관련 기존 Kotlin 테스트와 전체 `./gradlew build`, 계약 소비자 변경에 따른 프런트 check·test·build다. 무거운 빌드 전 프로세스·가용 메모리를 확인하고 다른 빌드와 겹치지 않게 한다.

### 9.4 회신과 완료 판정

인계 회신에는 담당 작업·읽은 기준 문서·소유 경로·첫 구현 조각·막히는 결정·검증 명령을 적는다. 인계 수신은 구현 완료가 아니다. 구현을 수행한 후에는 변경 파일, 해결한 인수 기준, 실제 실행 명령/결과, 미실행·잔여 결함을 보고한다. 수정·검증은 작업별 최대 3회이며 코드 변경 후에는 최종 diff에 대한 검증·리뷰를 다시 수행한다.

### 9.5 수신 확인과 남은 결정

- `r2_frontend`: 계획·직접 관련 화면/테스트/계약 검토 후 담당과 경로를 수신 확인했다. ER-27 착수를 막는 설계 문제는 없다. 행동 없음 상태의 모드 허용 문제는 §4.1의 서버 허용 모드 기준으로 보완했다.
- `r2_backend_contract`: 계획·직접 관련 Kotlin/계약/테스트 검토 후 담당과 경로를 수신 확인했다. 미추출 행동·허위 미기재, 신호 해결 절차, 기존 저장의 자동 확인 처리, 선택적 이력, 단일 기능 토글의 문제를 §5에 반영했다.
- 두 담당 모두 인계 검토만 수행했다. 코드 수정·빌드·운영 접근·유료 호출은 하지 않았다. ER-27 이후 ER-28→29→30→31 순서로 착수할 수 있도록 의존성을 전달했다.
- ER-28에서 확정할 항목: 입력/출력/본문 반영 길이와 토큰 상한, 분석·생성별 고객 크레딧과 행동 없음/불확실 결과의 정산, 현행 provider 시작 3회 상한의 단계·모드별 적용 방식. 권장안은 현재 버전 분석 재사용, 각 요청 최대 1호출·자동 재시도 없음, 단계별 비용과 합계 사전 표시다. 구체적인 숫자·고객 요금 확정이나 유료 호출 승인으로 해석하지 않는다.

### 9.6 실제 구현 지시

2026-09-26 사용자의 후속 지시 ‘agent 에게 구현 지시’에 따라 두 담당에게 실제 코드 수정과 검증을 요청했다. §9의 이전 인계 검토 한정은 그때의 작업 기록이며, 이번 구현 지시를 제한하지 않는다.

- 프런트 담당: ER-27 구현과 기존 컴포넌트·E2E 회귀 보강, 프런트 check·전체 test·build를 수행한다. ER-30/31 화면은 선행 계약·서버 기반과 연동한다.
- Kotlin·계약 담당: ER-28 계약·소비자·fake 분석 기반부터 구현하고 ER-29/31로 연결한다. 정책 미결정으로 유료 경로를 임의로 노출하지 않으며 v1 회귀를 보존한다.
- 총괄: 중복 파일 수정과 무거운 빌드 동시 실행을 조율하고 최종 diff·테스트·리뷰 결과를 확인한다. 작업별 최대 3회 수정·검증, 재귀 위임 금지, 유료 호출·운영 변경·배포 제외 조건은 유지한다.

현재 상태는 구현 지시·착수이며 ER-27~32 전체 완료나 테스트 통과를 뜻하지 않는다.
