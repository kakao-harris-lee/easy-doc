작성일: 2026-09-18 · 상태(2026-09-21): R0·R1과 R2 사용자 흐름(ER-07) 구현·fake E2E·PR #133 원격 CI 완료, R3 opt-in 프롬프트 기반(PR #135) 원격 CI 완료. D03/D04와 R2 평가 누적 US$50 상한 승인. 최초 모델 평가 후 최대 3회 보완을 종료했다. 최종 개발 회차 후보 검증 11/12로 출시 기준은 미충족이며, [누적 56호출·비용 원장](../reports/2026-09-21-r2-bounded-quality.md)을 최신 근거로 사용한다. 소수 크레딧 구현·로컬 검증 완료(운영 미적용), 원격 상태는 [PR #137](https://github.com/kakao-harris-lee/easy-doc/pull/137)에서 확인한다. AC-R3·파일럿·배포는 미완료.

ER-05는 fake runner와 PostgreSQL 통합 테스트로 작업·과금·중복 호출 방지를 확인했다. ER-06은 구조·원문 인용·일부 사실 규칙, 암호화 저장·키 회전, stale 교체·검수 상태·TXT 출력 경계를 확인했다. ER-07은 실제 브라우저·API·DB·fake worker를 거쳐 생성 전 확인, 재방문, 후보 적용, 편집·원문 대조, 저장·TXT, 충돌·stale 경계를 확인했다. [PR #133 최종 CI](https://github.com/kakao-harris-lee/easy-doc/actions/runs/35512616602)는 5개 작업이 성공했다. 당시 CI는 fake 경로 검증이다. 이후 실제 provider 20회 평가는 2026-09-21에 수행했으며 아래 §6의 결과와 구분한다.

2026-09-21 후속: R2 오탐 보완과 이전 20개 결과의 오프라인 재생은 PR #138에서 완료했다. 신규 생성과 의미 보존은 [최대 3회 평가·비용 원장](../reports/2026-09-21-r2-bounded-quality.md)으로 별도 판정한다. R3는 검수 정의·재변환 문맥 구현과 전체 백엔드 검증을 마쳤으며, 실제 모델 품질·검수 데이터 승인 전까지 기본 BASELINE을 유지한다.

## 4. 구현 시 실행할 명령

Kotlin 변경은 관련 회귀 테스트를 먼저 수행하고 다음 필수 검증으로 마무리한다.

```sh
cd backend-kotlin
./gradlew moduleBoundaryCheck --console=plain
./gradlew build --console=plain
```

React 변경은 해당 프로젝트에서 수행한다.

```sh
cd frontend
npm run check
npm run test -- --run
npm run build
```

통합 구성 변경 시 저장소 루트에서 `docker compose config`를 실행한다. 비밀값이 치환된 출력은 그대로 공유하지 않는다. 관련 브라우저 흐름은 기존 `frontend/e2e/run-local.sh` 또는 구성된 CI Playwright 레인을 사용하며 LLM/mail은 fake로 고정한다. 기존 변환·사전·크레딧 집행 흐름에 새 사례를 연결한다. 문서만 바꾼 PR에는 위 제품 테스트를 불필요하게 실행하지 않고 링크·범위·명세 일관성을 확인한다.

## 5. 품질 평가 계획

### 5.1 표본과 평가 순서

초기 10건은 조건 중심 4, 절차 중심 3, 표 중심 3으로 선정한다. 6건은 개선용, 4건은 보류 평가용으로 고정한다. 보류 문서를 보고 프롬프트를 고쳤다면 그 문서는 더 이상 독립 보류 표본이 아니므로 대체 문서를 확보한다.

각 문서에서 결과를 보기 전에 5개 이상 질문과 근거 구절을 작성한다. 중요한 조건이 5개보다 많으면 전부 포함한다. 원문 자체로 답할 수 없는 질문은 평가 정답에서 제외하고 ‘원문 정보 없음’ 처리 능력을 별도로 본다.

비교는 기준선 → 후보 하나 → 조합 순서로 한다. 같은 모델·effort·사전·원문을 유지하고 바꾼 축을 기록한다. 변동성을 보기 위한 생성 반복은 예산 승인 후 조건당 2회로 제안한다. 호출 비용이 승인되지 않았다면 기존 결과와 수동 예시로 UX만 검토하며 자동 생성 품질 결과로 기록하지 않는다.

### 5.2 출시 판정

- **필수 품질 기준:** 고정 표본에서 관찰된 자격·예외·금액·행동·기한의 중대한 의미 변경이 없어야 한다. 발견 시 해당 후보를 수정하고 영향 사례 및 독립 보류 문서를 재확인한다.
- **필수 제품 기준:** 해당 AC와 AC-SEC/AC-OFF 통과, 동시성·예약 정산·삭제 테스트 성공, CI 성공, 기본 경로 회귀 없음.
- **탐색 목표:** 실무자 검수 시간 중앙값 20% 단축, 정보 찾기 성공률 유지 또는 향상. 이는 성공 가설이며 실측 결과나 출시를 보장하는 수치가 아니다. 실패하면 기능의 범위를 다시 검토한다.
- **성능 초기 목표:** R1 분석 p95 2초 이하, R2 생성 p95 90초 이내. R1은 20,000자 상한의 fixture와 명시한 테스트 환경에서 측정한다. R2는 승인된 실제 provider 표본으로만 지연을 주장한다. 목표 미달이면 상한·비동기·표시 범위를 조정한다.
- 표현 한두 곳이 덜 쉬운 문제와 의미 오류를 구분한다. 모든 용어가 사전에 없다는 이유로 개발을 멈추지 않는다.

0건 관찰은 전체 오류율 0%가 아니다. R1 확인 건수는 독자 이해도도, 실제 오류 검출률도 아니다. judge 합격률을 사람의 정답률로 표시하지 않는다.

### 5.3 사람 평가

실무자 3~5명의 탐색 파일럿으로 시작한다. 읽기·수정 시간을 별도로 기록하고, 같은 문서 반복의 학습 효과를 줄이도록 원문/후보와 순서를 분산한다. 활동 중 시간만 측정하고 탭 비활성 시간을 제외한다. 생산 환경의 개인별 감시 지표로 사용하지 않는다.

목표 독자의 정보 찾기·모의 신청 준비 평가는 별도 모집·동의·접근 가능한 설명 후 진행한다. 질문을 잘못 이해했는지, 문서 자체를 이해하지 못했는지도 구분한다. 집단별 결과와 표본 수를 함께 보고한다. 이 평가는 대외 효과 주장에 필요하며 일반 표현 개선 전체의 출시 선행조건은 아니다.

### 6.2 승인된 실제 모델 평가 패킷

실행 패킷에는 개발용 6건·독립 보류용 4건의 문서 ID와 질문/근거, 비교할 기준선과 후보, 모델·effort·사전 버전, 문서별 입력/출력 토큰 상한, 조건별 반복 수, 실패·재시도까지 포함한 최대 호출 수와 보수적 달러 상한을 붙인다. R2 전용 `EASYDOC_R2_LANE_MAX_USD`에는 누적 US$50에서 이미 사용·예약한 비용을 뺀 잔여 예산 이하를 설정하고 실행 직전 provider·키·프로필과 상한을 확인한다. 일반 변환 레인의 `EASYDOC_LANE_MAX_USD`와 혼동하지 않으며 `testLlm` 전체를 실행하지 않는다. 실행 후 호출 수·토큰·지연·실패·원장·예상 비용을 기록하고, 보류 문서의 자격·예외·금액·행동·기한 변경을 검수한다. 승인 금액은 확정됐으며 호출 수·모델 등 실행 조건은 준비 결과로 채운다.

### 6.3 제한 파일럿 착수 패킷

[2026-09-21 실행 패킷](2026-09-21-r2-pilot-packet.md)에 과제 배치·동의·기록·중단 양식을 준비했다. 참여자·일정과 실측은 미확정이며, [오탐 보완·배포 확인](../reports/2026-09-21-r2-release-verification.md)을 별도 추적한다.

제품 담당자는 대상 기관·담당자 3~5명·사용 문서 범위·무상/크레딧 조건·일정을 기록하고, 개인정보와 업로드 문서의 사용 동의·접근 권한·삭제 기한을 확인한다. 평가 담당자는 사전 질문과 중대한 의미 오류 중단 기준을 고정하고, UX 담당자는 시간·수정률·정보 찾기 기록 양식과 접근성 관찰 항목을 준비한다. 운영 담당자는 토글·버전·복구 담당과 첫 24시간 관측 시간을 지정한다. 기관 모집·동의·실제 문서 검수·실사용자 평가는 아직 실행하지 않았다.

## 7. 배포 절차

1. 각 마일스톤에서 local 검사·리뷰·remote CI를 구분해 완료 기록을 남긴다.
2. 일반 확장 migration은 구버전 기본 경로와의 호환성을 확인한 뒤 적용한다. **소수 크레딧 전환은 예외**로, 구버전 정수 reader와 혼용하지 않도록 접수 중단·진행 중 요청 정리·DB와 API/worker 전환을 [별도 절차](2026-09-21-fractional-credits.md)에 따라 조율한다.
3. API와 worker를 신규 버전으로 배포하되 토글은 OFF로 둔다. API/worker가 읽는 공통 설정과 버전을 확인한다.
4. 신규 API 소비자가 반영된 frontend를 배포한다. 토글 OFF·레거시 저장 경로를 먼저 점검한다.
5. 내부 환경에서 `EASYDOC_ACTION_GUIDE_ENABLED=true`와 worker의 `EASYDOC_ACTION_GUIDE_WORKER_ENABLED=true`를 명시적으로 설정하고, fake provider로 기본/실패/만료/충돌 경로를 확인한다. 이 환경의 실제 토글·프로필·작업 상태를 기록한다.
6. 승인된 실제 생성 평가가 필요한 R2/R3는 별도 예산 안에서 실행하고 §5.2의 의미 오류 판정을 기록한다. 가이드 문구·지원 범위·필요 크레딧을 함께 확인한다.
7. D03/D04 승인과 품질 판정 뒤 기능을 켠 제한 파일럿 인스턴스 또는 환경에서 실제 경로를 확인한다. 현행 서비스에 워크스페이스별 토글 체계가 있다고 가정하지 않는다.
8. 운영 담당자가 실행 이미지/커밋·schema·토글·실제 요청·원장/예약 정산을 확인하고 출시 판정을 기록한다. 기록에는 환경, 담당자, 확인 시각, 정상·실패 요청 ID, 반환/소비 수치, 복구 경로를 포함한다.

이 문서는 배포 실행이나 유료 호출의 포괄 승인이 아니다. 개발 착수 요청이 오면 승인된 범위의 구현·검증을 진행한다.

## 8. 관측·중단 기준

배포 후 첫 24시간은 오류율·충돌률·예약 잔액·작업 상태·추가 비용·본문 없는 파기 건수를 확인하고, 첫 주에는 검수 사용성 의견을 정리한다. 담당자와 확인 시점은 마일스톤 완료 기록에 넣는다. 이 문서로 자동 모니터를 생성하지 않는다.

즉시 기능 중단 사유는 타인 데이터 노출, 중복 고객 과금, 저장된 수정본 유실, 삭제/만료 후 파생 본문 노출, 알려진 중대한 의미 오류의 반복이다. 단순 문체 선호·경고 오탐은 심각도와 빈도로 조정한다.

## 9. 롤백과 복구

- R1 UI/분석 장애: 신규 검수 토글 OFF, 기존 편집·출력 유지. **본문 버전 증가·파생 결과 무효화는 유지**한다.
- R2 장애: 신규 접수 OFF → 이미 시작한 작업 종료/실패 정산 → 미시작 예약 반환 → 활성 job과 원장 대조. 브라우저 재시도만으로 복구하지 않는다.
- R3 품질 회귀: 프롬프트/사전 설정을 이전 검증 버전으로 돌리고 새 생성만 영향받게 한다. 사용자 수정본은 덮지 않는다.
- R4~R7 장애: 해당 표시·출력 기능만 OFF. 기존 본문과 원본 파일 경로 유지.
- migration rollback은 DROP이 아닌 기능 중단·호환 코드 또는 forward fix를 우선한다. 버전 기반을 모르는 구버전으로 되돌릴 경우 모든 파생 자원을 stale 처리하고 신규 helper API를 꺼야 한다. 버전 미갱신 구버전이 쓰는 동안 helper를 다시 켜지 않는다.
- 복구 후 고정 회귀 사례·예약 정산·만료 파기를 다시 확인하고 제한된 환경에서 재활성화한다. 데이터 수정이 필요하면 대상·백업·영향·승인 범위를 별도로 기록한다.
