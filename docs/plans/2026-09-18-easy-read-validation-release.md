## 2. 인수 기준

| ID | Given / When / Then |
|---|---|
| AC-R0 | 공개 문서 10건 → 결과를 보기 전 질문·중요 사실 기록 → 출처·사용 허용 범위·기준선·개발용/보류용 구분이 있음 |
| AC-BASE | revision N을 읽은 두 화면 → A가 다른 본문 저장, B가 N으로 저장 → A만 성공, B는 409이며 입력 보존. 레거시 저장도 파생 결과 무효화 |
| AC-R1-a | 원문 날짜/서류 누락 → 규칙 분석 → 실제 원문 위치가 있는 누락 의심. 동치 숫자·표현은 기존 비교 기준 유지 |
| AC-R1-b | 숫자는 같고 제출/작성 또는 AND/OR가 다름 → 분석 → 자동 의미 통과 표시 없음, 관계 체크리스트 접근 가능 |
| AC-R1-c | 확인한 본문을 수정 후 저장 → 최신 조회 → 이전 확인은 최신 확인으로 표시되지 않음. 정규화 후 같은 본문 저장은 불필요한 초기화 없음 |
| AC-R1-d | 지도 없음·200단위 초과·신호 상한 초과 → 검수 화면 → 전체 비교 가능, 제한 안내, 기존 본문 저장/출력 가능 |
| AC-R2-a | 같은 요청 키의 POST를 반복 → 접수·실행 → 작업 1개, provider 최대 1회, 크레딧 소비 최대 1회 |
| AC-R2-b | worker 호출 직후 중단 → lease 복구 → 자동 중복 호출 없음, 불명확 실패와 예약 정산·원장 기록이 일관됨 |
| AC-R2-c | 원문에 제출처 없음/예외 있음 → 후보 생성 → not_in_source/예외 연결. 허위 인용·잘못된 index·과대 JSON·절단 결과는 채택하지 않음 |
| AC-R2-d | 생성 중 본문 수정·삭제·만료 → 결과 도착 → 오래된/삭제된 본문에 결과 저장 없음, 규정대로 예약 반환. 기존 유효 안내문 보존 |
| AC-R2-e | 미확인/수정 중/이전 버전 안내문 → 출력 → 차단 사유와 다음 행동 안내. 현재 버전 확인 저장 후 TXT 성공 |
| AC-R3 | 공식 이름·중의어·핵심 개념 문서 → 변환/문단 재변환/보정 → 명칭·조건 유지, 필요한 첫 설명, 추가 호출 없음 |
| AC-R4-a | 단순 DOCX/HWPX 표 → 추출 → 행/열/제목/단위/각주와 원문 줄 연결. 병합/중첩/PDF/과거 문서는 unsupported 또는 unavailable |
| AC-R4-b | 표 관계 표시/본문 편집 → 비교·내려받기 → 다른 사람의 금액·월/연·이하/미만을 섞지 않음, 기존 원본 형식 출력 회귀 없음 |
| AC-R5-a | 확인/취소/본문 변경 → 이력 조회 → 서버 시각·actor·버전·행위가 일치. 조작된 actor 무시, 페이지 중복/누락 경계 확인 |
| AC-R5-b | 과거 확인·스냅샷 삭제·문서 만료 → UI/기록 출력 → 현재 확인으로 혼동 없음, 없는 본문 명시, 만료는 404 |
| AC-R6 | 설명을 접거나 본문 수정 → 화면 → 필수 조건은 본문에 남음, stale 설명 비활성, 키보드로 조작 가능 |
| AC-R7-a | 그림 카탈로그 등록 → 이용 권리·출처·대체텍스트 검토 → 검수되지 않은 항목은 선택 불가 |
| AC-R7-b | 그림을 적용 → 웹/파일 결과 확인 → 의미 불일치 없음, 이미지 미포함 출력은 사용자에게 명시 |
| AC-SEC | 타인·삭제·만료·회원 탈퇴 → 모든 신규 read/write/export/job → 원문·인용·후보 유출 없음, 개인정보 본문 로그 없음 |
| AC-OFF | 신규 기능 OFF → 변환/편집/재변환/저장/내려받기 → 기존 흐름 유지, 신규 버튼 미노출 |

AC-R1-b는 시스템이 의미 오류를 모두 잡는다는 기준이 아니다. 한계를 알리면서 담당자가 확인할 수 있는지가 R1의 인수 범위다.

## 4. 구현 시 실행할 명령

Kotlin 변경은 관련 회귀 테스트를 먼저 수행하고 다음 필수 검증으로 마무리한다.

```sh
cd backend-kotlin
./gradlew moduleBoundaryCheck --console=plain
./gradlew build --console=plain
```

React 변경은 해당 프로젝트에서 수행한다.

```sh
cd frontend
npm run check
npm run test -- --run
npm run build
```

통합 구성 변경 시 저장소 루트에서 `docker compose config`를 실행한다. 비밀값이 치환된 출력은 그대로 공유하지 않는다. 관련 브라우저 흐름은 기존 `frontend/e2e/run-local.sh` 또는 구성된 CI Playwright 레인을 사용하며 LLM/mail은 fake로 고정한다. 기존 변환·사전·크레딧 집행 흐름에 새 사례를 연결한다. 문서만 바꾼 PR에는 위 제품 테스트를 불필요하게 실행하지 않고 링크·범위·명세 일관성을 확인한다.

## 5. 품질 평가 계획

### 5.1 표본과 평가 순서

초기 10건은 조건 중심 4, 절차 중심 3, 표 중심 3으로 선정한다. 6건은 개선용, 4건은 보류 평가용으로 고정한다. 보류 문서를 보고 프롬프트를 고쳤다면 그 문서는 더 이상 독립 보류 표본이 아니므로 대체 문서를 확보한다.

각 문서에서 결과를 보기 전에 5개 이상 질문과 근거 구절을 작성한다. 중요한 조건이 5개보다 많으면 전부 포함한다. 원문 자체로 답할 수 없는 질문은 평가 정답에서 제외하고 ‘원문 정보 없음’ 처리 능력을 별도로 본다.

비교는 기준선 → 후보 하나 → 조합 순서로 한다. 같은 모델·effort·사전·원문을 유지하고 바꾼 축을 기록한다. 변동성을 보기 위한 생성 반복은 예산 승인 후 조건당 2회로 제안한다. 호출 비용이 승인되지 않았다면 기존 결과와 수동 예시로 UX만 검토하며 자동 생성 품질 결과로 기록하지 않는다.

### 5.2 출시 판정

- **필수 품질 기준:** 고정 표본에서 관찰된 자격·예외·금액·행동·기한의 중대한 의미 변경이 없어야 한다. 발견 시 해당 후보를 수정하고 영향 사례 및 독립 보류 문서를 재확인한다.
- **필수 제품 기준:** 해당 AC와 AC-SEC/AC-OFF 통과, 동시성·예약 정산·삭제 테스트 성공, CI 성공, 기본 경로 회귀 없음.
- **탐색 목표:** 실무자 검수 시간 중앙값 20% 단축, 정보 찾기 성공률 유지 또는 향상. 이는 성공 가설이며 실측 결과나 출시를 보장하는 수치가 아니다. 실패하면 기능의 범위를 다시 검토한다.
- **성능 초기 목표:** R1 분석 p95 2초 이하, R2 생성 p95 90초 이내. R1은 20,000자 상한의 fixture와 명시한 테스트 환경에서 측정한다. R2는 승인된 실제 provider 표본으로만 지연을 주장한다. 목표 미달이면 상한·비동기·표시 범위를 조정한다.
- 표현 한두 곳이 덜 쉬운 문제와 의미 오류를 구분한다. 모든 용어가 사전에 없다는 이유로 개발을 멈추지 않는다.

0건 관찰은 전체 오류율 0%가 아니다. R1 확인 건수는 독자 이해도도, 실제 오류 검출률도 아니다. judge 합격률을 사람의 정답률로 표시하지 않는다.

### 5.3 사람 평가

실무자 3~5명의 탐색 파일럿으로 시작한다. 읽기·수정 시간을 별도로 기록하고, 같은 문서 반복의 학습 효과를 줄이도록 원문/후보와 순서를 분산한다. 활동 중 시간만 측정하고 탭 비활성 시간을 제외한다. 생산 환경의 개인별 감시 지표로 사용하지 않는다.

목표 독자의 정보 찾기·모의 신청 준비 평가는 별도 모집·동의·접근 가능한 설명 후 진행한다. 질문을 잘못 이해했는지, 문서 자체를 이해하지 못했는지도 구분한다. 집단별 결과와 표본 수를 함께 보고한다. 이 평가는 대외 효과 주장에 필요하며 일반 표현 개선 전체의 출시 선행조건은 아니다.

## 7. 배포 절차

1. 각 마일스톤에서 local 검사·리뷰·remote CI를 구분해 완료 기록을 남긴다.
2. 확장 migration을 먼저 적용한다. 새 컬럼·테이블이 있어도 구버전 기본 경로가 동작하는지 확인한다.
3. API와 worker를 신규 버전으로 배포하되 토글은 OFF로 둔다. API/worker가 읽는 공통 설정과 버전을 확인한다.
4. 신규 API 소비자가 반영된 frontend를 배포한다. 토글 OFF·레거시 저장 경로를 먼저 점검한다.
5. 내부 환경에서 토글 ON, fake로 기본/실패/만료/충돌 경로를 확인한다.
6. 기능을 켠 제한 파일럿 인스턴스 또는 환경에서 실제 경로를 확인한다. 현행 서비스에 워크스페이스별 토글 체계가 있다고 가정하지 않는다.
7. 승인된 실제 생성 평가가 필요한 R2/R3는 별도 예산 안에서 실행한다. 가이드 문구·지원 범위·필요 크레딧을 함께 확인한다.
8. 운영 담당자가 실행 이미지/커밋·schema·토글·실제 요청·원장/예약 정산을 확인하고 출시 판정을 기록한다.

이 문서는 배포 실행이나 유료 호출의 포괄 승인이 아니다. 개발 착수 요청이 오면 승인된 범위의 구현·검증을 진행한다.

## 8. 관측·중단 기준

배포 후 첫 24시간은 오류율·충돌률·예약 잔액·작업 상태·추가 비용·본문 없는 파기 건수를 확인하고, 첫 주에는 검수 사용성 의견을 정리한다. 담당자와 확인 시점은 마일스톤 완료 기록에 넣는다. 이 문서로 자동 모니터를 생성하지 않는다.

즉시 기능 중단 사유는 타인 데이터 노출, 중복 고객 과금, 저장된 수정본 유실, 삭제/만료 후 파생 본문 노출, 알려진 중대한 의미 오류의 반복이다. 단순 문체 선호·경고 오탐은 심각도와 빈도로 조정한다.

## 9. 롤백과 복구

- R1 UI/분석 장애: 신규 검수 토글 OFF, 기존 편집·출력 유지. **본문 버전 증가·파생 결과 무효화는 유지**한다.
- R2 장애: 신규 접수 OFF → 이미 시작한 작업 종료/실패 정산 → 미시작 예약 반환 → 활성 job과 원장 대조. 브라우저 재시도만으로 복구하지 않는다.
- R3 품질 회귀: 프롬프트/사전 설정을 이전 검증 버전으로 돌리고 새 생성만 영향받게 한다. 사용자 수정본은 덮지 않는다.
- R4~R7 장애: 해당 표시·출력 기능만 OFF. 기존 본문과 원본 파일 경로 유지.
- migration rollback은 DROP이 아닌 기능 중단·호환 코드 또는 forward fix를 우선한다. 버전 기반을 모르는 구버전으로 되돌릴 경우 모든 파생 자원을 stale 처리하고 신규 helper API를 꺼야 한다. 버전 미갱신 구버전이 쓰는 동안 helper를 다시 켜지 않는다.
- 복구 후 고정 회귀 사례·예약 정산·만료 파기를 다시 확인하고 제한된 환경에서 재활성화한다. 데이터 수정이 필요하면 대상·백업·영향·승인 범위를 별도로 기록한다.

## 10. 이번 문서 세트의 완료 범위

완료: 단계별 개발 절차, 구현 제안, UX, 인수·품질·출시 기준 작성.

미실행: 제품 구현·마이그레이션·실제 LLM 호출·실무자/독자 평가·CI·배포. 이후 ER 작업이 완료될 때 해당 근거를 붙여 상태를 갱신한다.
