## 1. 개념과 등장인물

| 이름 | 뜻 | 비고 |
|---|---|---|
| 사용자 | 로그인 계정 하나 | 이메일 1개 = 계정 1개 |
| 워크스페이스 | 문서·크레딧·청구가 붙는 단위 | 가입 시 기본 1개 자동 생성. 소유자 1명 |
| 크레딧 | **공백 포함 1,000자 = 1크레딧** | 문서 1건마다 올림 계산. 「페이지」라는 말은 쓰지 않는다 |
| 잔액 / 예약 / 가용 | 가진 것 / 변환 중에 잡아 둔 것 / 지금 쓸 수 있는 것 | 가용 = 잔액 − 예약 |
| 플랜 | 매월 정해진 크레딧을 받는 계약 | 무료·Starter·Pro·Enterprise |
| 추가 구매 | 플랜과 별개로 크레딧을 더 사는 것 | 50크레딧 단위 |
| 운영자 | 어드민 화면·CLI를 쓰는 우리 쪽 담당자 | `users.is_admin` |

**과금 단위가 워크스페이스인 이유**: 한 기관에서 부서별로 예산이 다르고, 세금계산서도 부서 단위로 끊는다. 계정이 아니라 워크스페이스에 잔액과 청구가 붙어야 그 현실과 맞는다.

## 2. 여정 한 장

| # | 단계 | 사용자가 하는 일 | 시스템이 하는 일 |
|---|---|---|---|
| A | 가입 | 이메일 또는 소셜로 가입, 이메일 인증 | 기본 워크스페이스 생성, 무료 크레딧 부여 |
| B | 무료 사용 | 문서를 변환해 본다 | 크레딧 차감, 잔액 표시 |
| C | 플랜 선택 | 요금 화면에서 플랜을 고른다 | 결제 수단에 따라 D 또는 F로 분기 |
| D | 카드 결제 | 카드 등록 → 즉시 결제 | 매월 자동 결제, 크레딧 자동 부여 |
| F | 계좌이체 | 견적서 받아 예산 집행 → 입금 | 입금 확인 후 크레딧 부여 |
| E | 추가 구매 | 잔액이 모자랄 때 50크레딧 단위로 산다 | 카드는 즉시, 이체는 입금 후 |
| G | 세금계산서 | 이체 건에 대해 요청 | 운영자가 홈택스로 발급하고 상태를 바꾼다 |

**두 갈래를 먼저 이해해야 한다.** 공공기관은 카드보다 **계좌이체 + 세금계산서**가 기본이다. 예산 집행 절차상 견적서와 세금계산서가 있어야 지출이 성립하기 때문이다. 카드 결제는 민간 고객과 소액 추가 구매를 위한 경로다. 두 경로는 크레딧이 들어오는 방식만 다르고 그 뒤는 같다.

## 3. A. 가입과 계정 준비

### 3.1 가입 경로

세 가지다. 어느 쪽이든 계정 하나로 수렴한다.

1. **이메일 + 비밀번호** — 가입 후 인증 메일의 코드를 입력한다.
2. **소셜 로그인** — 구글·카카오·네이버. 제공자가 확인해 준 이메일을 쓴다.
3. **초대**(팀 기능 이후) — 기관 담당자가 부서원을 초대한다.

같은 이메일로 소셜과 비밀번호를 함께 쓸 수 있다. 계정 설정에서 소셜을 연결하거나 끊고, 비밀번호를 새로 정할 수 있다. 마지막 로그인 수단은 끊을 수 없다.

### 3.2 이메일 인증이 필요한 이유

**인증을 마쳐야 문서 등록이 열린다.** 변환은 외부 LLM 호출이라 비용이 든다. 인증 없이 열어 두면 자동화된 가입으로 비용이 새고, 세금계산서 요청자의 신원도 확인되지 않는다.

인증 전에도 로그인·화면 둘러보기·요금 확인은 된다.

### 3.3 가입 직후 상태

- 기본 워크스페이스 1개가 만들어진다. 이름은 바꿀 수 있다.
- 무료 크레딧이 1회 부여된다(§4).
- 크레딧 계정이 만들어진다. 잔액·예약·거래 내역이 이때부터 쌓인다.

## 4. B. 무료 사용량

### 4.1 얼마를 주는가

**가입 시 50크레딧을 1회 부여한다.** 5만 자 분량이고, 보통 안내문 10~20건에 해당한다. Starter 한 달치와 같은 양이라, 유료 전환을 결정하기 전에 실제 업무 한 달을 시험해 볼 수 있다.

- 워크스페이스를 **추가로** 만들 때는 주지 않는다. 계정당 1회다.
- **유효기간이 없다.** 다 쓸 때까지 남는다.
- 거래 내역에 `무료 제공`으로 남는다.

### 4.2 무료 구간에서 안 되는 것

**없다.** 기능 제한을 두지 않는다. 무료와 유료의 차이는 크레딧 양뿐이다.

이유는 두 가지다. 첫째, 이 서비스의 판단 기준은 「변환 품질이 실무자 기준을 통과하는가」인데, 기능을 잠그면 그 판단을 못 한다. 둘째, 잠글 만한 부가 기능이 아직 없다.

### 4.3 다 쓰면

문서 등록 화면이 **등록 전에** 막고 안내한다. 이미 등록된 문서의 변환·검수·내려받기는 영향을 받지 않는다.

화면에는 세 가지를 함께 보여 준다: 이 문서에 필요한 크레딧, 지금 가용 크레딧, 그리고 충전 방법으로 가는 링크.

## 5. C. 플랜 구분

### 5.1 플랜표

| 플랜 | 월 크레딧 | 환산 분량 | 주 대상 | 기본 결제 |
|---|---|---|---|---|
| 무료 | 50 (가입 1회) | 5만 자 | 도입 검토 | — |
| Starter | 50 | 5만 자 | 담당자 1~2명, 부서 하나 | 카드 |
| Pro | 200 | 20만 자 | 과·팀 단위 상시 사용 | 카드 또는 이체 |
| Enterprise | 500 이상 | 50만 자 이상 | 기관 단위, 여러 부서 | 이체 |

- 팀원 수로 요금을 받지 않는다. 공공기관은 담당자가 자주 바뀌고 좌석 수 관리가 조달 절차를 복잡하게 만든다.
- Enterprise는 크레딧 양과 지원 범위를 협의로 정한다.

### 5.2 월 구독과 연간 라이선스

| | 월 구독 | 연간 라이선스 |
|---|---|---|
| 결제 | 매월 자동 | 12개월치 1회 선결제 |
| 할인 | 없음 | 있음 |
| 크레딧 부여 | 매월 초 | 매월 초(12회로 나눠서) |
| 주 사용처 | 민간·소규모 | 공공 예산 집행, 수의계약 |
| 해지 | 다음 결제일부터 | 계약 기간 종료 시 |

**연간 라이선스도 크레딧은 매월 나눠 준다.** 한 번에 다 주면 연초에 몰아 쓰고 남은 기간 원가가 튀며, 중도 해지 정산도 어려워진다.

모든 요금은 **소액 수의계약 한도(연간 기준) 안**에서 설계한다. 그 한도를 넘으면 입찰 절차가 필요해져 도입 자체가 막힌다.

### 5.3 플랜을 바꿀 때

- **상향**: 즉시 적용한다. 남은 기간을 일할 계산해 차액을 받고, 크레딧 차이를 즉시 부여한다.
- **하향**: 다음 결제일부터 적용한다. 이미 준 크레딧은 회수하지 않는다.
- **해지**: 다음 결제일부터 결제하지 않는다. 남은 크레딧은 유효기간이 없으므로 계속 쓸 수 있다.

## 6. D. 카드 결제

### 6.1 등록과 첫 결제

1. 요금 화면에서 플랜을 고른다.
2. 카드 정보를 입력한다. **카드번호는 우리 서버에 저장하지 않는다** — 결제대행사가 발급한 결제 키만 보관한다.
3. 첫 결제가 즉시 일어나고, 성공하면 그 자리에서 크레딧이 들어온다.
4. 영수증(신용카드 매출전표)이 메일로 간다.

### 6.2 매월 갱신

- 결제일은 최초 결제일과 같은 날이다. 말일 문제(31일 → 30일·28일)는 그 달의 마지막 날로 맞춘다.
- 결제 성공 → 크레딧 부여 → 영수증 메일. 이 셋은 한 묶음이다.
- 결제 3일 전에 예고 메일을 보낸다. 예산 담당자가 카드 한도를 확인할 시간을 준다.

### 6.3 결제가 실패하면

즉시 끊지 않는다. 공공기관에서는 카드 한도나 담당자 부재로 실패가 흔하고, 그때 서비스가 멈추면 업무가 멈춘다.

| 시점 | 처리 |
|---|---|
| 실패 당일 | 재시도 1회, 실패 알림 메일 |
| +3일 | 재시도 2회 |
| +7일 | 재시도 3회, 마지막 안내 |
| +14일 | 구독 정지. **남은 크레딧은 그대로 쓸 수 있다** |

정지된 구독은 카드를 바꾸면 즉시 되살아난다.

### 6.4 환불

- **크레딧을 쓰지 않은 결제**는 결제일로부터 7일 안에 전액 환불한다.
- **일부 사용했으면** 쓴 크레딧을 뺀 나머지를 환불한다.
- 환불하면 해당 크레딧을 회수한다. 회수로 잔액이 음수가 되면 그대로 둔다 — 다음 충전에서 상계된다.

### 6.5 카드 결제와 세금계산서

**카드로 결제한 건은 세금계산서를 발행하지 않는다.** 사업자등록번호가 기재된 신용카드 매출전표가 이미 매입세액공제의 근거이고, 같은 거래에 세금계산서를 겹쳐 발행하면 이중 발행이 된다.

세금계산서가 필요한 고객은 §8의 계좌이체 경로를 쓴다. 요금 화면과 결제 화면에 이 안내를 미리 띄워 결제 뒤에 요청이 오는 일을 줄인다.

> 이 규칙은 세무 담당의 확인을 받아 확정한다(§11 결정 3).

## 7. E. 사용량 추가 구매

### 7.1 언제 필요한가

플랜 크레딧을 다 썼는데 이번 달에 더 변환해야 할 때다. 연말 사업 정리처럼 특정 시기에 몰리는 업무가 있어 플랜만으로는 감당되지 않는다.

### 7.2 방법

**50크레딧 단위로 산다.** 필요한 만큼 여러 묶음을 한 번에 살 수 있다.

- **카드**: 즉시 결제, 즉시 부여. 잔액 부족 안내 화면에서 바로 이어진다.
- **계좌이체**: 청구서를 받아 입금하고, 확인 뒤 부여된다(§8).

### 7.3 성격

- 플랜과 별개로 쌓인다. 유효기간이 없다.
- **차감 순서를 두지 않는다** — 잔액은 한 덩어리다. 만료가 없으므로 순서를 나눌 이유가 없다.
- 추가 구매만으로도 서비스를 쓸 수 있다. 플랜 없이 필요할 때만 사는 고객도 받는다.

## 8. F. 계좌이체 경로

공공기관의 기본 경로다. 예산 집행 절차와 맞물려 있어 단계가 카드보다 많다.

| # | 단계 | 주체 | 산출물 |
|---|---|---|---|
| 1 | 견적 요청 | 고객 | — |
| 2 | 견적서 발행 | 운영자 | 견적서(PDF) |
| 3 | 내부 결재·계약 | 고객 | 계약서 또는 발주서 |
| 4 | 청구서 발행 | 운영자 | 청구서(PDF) |
| 5 | 입금 | 고객 | 이체 |
| 6 | 입금 확인 | 운영자 | — |
| 7 | 크레딧 부여 | 운영자 | 거래 내역 1건 |
| 8 | 세금계산서 | 고객 요청 → 운영자 발급 | 전자세금계산서(§9) |

**선결제가 원칙이다.** 크레딧은 입금 확인 뒤에 들어간다. 다만 연간 계약처럼 절차가 긴 경우, 계약서가 확인되면 입금 전에 먼저 크레딧을 넣고 청구를 이어갈 수 있다. 이 판단은 운영자가 하고 거래 내역에 사유를 남긴다.

## 9. G. 세금계산서 요청과 처리

### 9.1 요청할 수 있는 사람과 대상

워크스페이스 **소유자**가, **계좌이체로 결제한 기간**에 대해 요청한다. 카드 결제분은 §6.5에 따라 대상이 아니다.

### 9.2 요청 화면

사용량 화면의 「세금계산서 요청」에서 연다. 입력 항목은 이렇다.

| 항목 | 필수 | 검증 |
|---|---|---|
| 사업자등록번호 | 필수 | 하이픈을 넣어도 되고, 국세청 체크섬을 통과해야 한다 |
| 상호 | 필수 | |
| 대표자명 | 선택 | |
| 담당자 이메일 | 필수 | 세금계산서를 받을 주소 |
| 사업장 주소 | 선택 | |
| 기간 | 필수 | 시작 ≤ 종료, 366일 이내. 기본값은 지난달 |

같은 워크스페이스에 **같은 기간의 처리 대기 요청이 있으면 막는다.** 중복 발행은 정정 절차를 부르기 때문에 접수 단계에서 걸러야 한다.

### 9.3 상태

```
요청됨(requested) ──> 발급됨(issued)
                 └──> 반려됨(rejected, 사유 필수)
```

되돌리는 전이는 없다. 잘못 발급했으면 홈택스에서 정정 발행하고, 새 요청으로 다시 남긴다.

### 9.4 흐름

1. 사용자가 요청한다. 화면 목록에 「요청됨」으로 즉시 나타난다.
2. 메일 두 통이 나간다. 운영자에게 접수 알림, 요청자에게 접수 확인.
3. 운영자가 어드민 화면의 세금계산서 탭에서 확인한다. 해당 기간의 사용량·입금 내역을 같은 화면에서 본다.
4. 홈택스에서 전자세금계산서를 발행한다. **발행 자체는 수동이다.**
5. 어드민 화면에서 「발급됨」으로 바꾼다. 처리한 사람과 시각이 기록된다.
6. 요청자에게 상태 메일이 간다. 반려면 사유가 함께 간다.

### 9.5 반려하는 경우

- 해당 기간에 계좌이체 결제가 없다(카드 결제분이다).
- 사업자 정보가 계약 상대와 다르다.
- 이미 같은 기간에 발행했다.

세 경우 모두 사유를 적어 반려하고, 사용자가 무엇을 고쳐 다시 요청해야 하는지 알 수 있게 쓴다.

## 10. 사용량 확인과 알림

### 10.1 사용자가 보는 것

사용량 화면 하나에 모은다.

- **크레딧 카드**: 가용·잔액·예약 중.
- **이번 달 사용량**: 문서 수, 글자 수, 사용 크레딧.
- **거래 내역**: 부여·사용·환불·조정이 시간순으로. 각 건이 어느 문서였는지 링크된다.
- **세금계산서 요청 목록**: 기간·상호·상태·운영자 메모.

### 10.2 알림 메일

| 시점 | 내용 |
|---|---|
| 잔액 20% 이하 | 충전 안내 |
| 잔액 소진 | 등록이 막힌다는 안내와 충전 링크 |
| 결제 3일 전 | 예고 |
| 결제 성공·실패 | 영수증 또는 실패 안내 |
| 세금계산서 접수·발급·반려 | 상태 알림 |

**한 사건에 메일 한 통이다.** 같은 임계값을 여러 번 넘나들어도 다시 보내지 않는다.

## 11. 결정이 필요한 항목

목표 프로세스를 확정하려면 다음이 필요하다. **1번이 나머지를 좌우한다.**

1. **매월 부여 + 만료 없음의 누적 문제.** 2026-09-08에 「만료 없음」으로 정했다(크레딧 계획 §7). 파일럿에서는 옳지만, 매월 자동 부여하는 구독에서 만료가 없으면 안 쓰는 달의 크레딧이 무한히 쌓이고 그만큼 이연 매출과 원가 위험이 커진다. 선택지는 셋이다.
   - ⓐ 그대로 둔다. 단순하고, 공공기관의 계절성(연말 집중)과 맞는다. 대신 상한을 두지 않으면 노출이 열려 있다.
   - ⓑ 이월 상한을 둔다. 예를 들어 월 크레딧의 3배까지만 쌓인다.
   - ⓒ 플랜 크레딧만 매월 소멸시키고, 추가 구매분은 만료 없이 남긴다. 업계에서 가장 흔한 형태지만 잔액이 두 종류가 되어 화면과 차감 순서가 복잡해진다.
   - **권고: ⓑ.** 만료 없음의 단순함을 지키면서 노출을 닫는다.
2. **결제대행사 선정.** 정기 결제(빌링키), 공공기관 사업자 결제, 세금계산서 연동 여부, 수수료를 함께 본다.
3. **카드 결제분 세금계산서 미발행 원칙**(§6.5)을 세무 담당이 확인한다.
4. **환불 규정**(§6.4)의 기간과 비율을 약관에 확정한다.
5. **연간 라이선스 중도 해지** 시 정산 방식.
6. **견적서·청구서 서식**을 누가 만들고 어디에 보관하는가. 원클릭 발급은 이후로 내렸으므로 당분간 수동 서식이 필요하다.

## 13. 로드맵에 반영할 제안

`docs/master-plan.md` §4.1의 P0-7·P0-8과 §9 단계 구성에 다음을 반영할 것을 제안한다. **확정은 사용자 결정 사항이다.**

1. **P0-8(결제)을 셋으로 쪼갠다** — 플랜 모델, 카드 정기 결제, 청구·견적 서식. 지금은 한 줄이라 착수 단위가 되지 않는다.
2. **결제와 무관한 조각(§12.2의 8~11번)을 앞으로 당긴다.** 결제대행사 계약을 기다리는 동안 파일럿 운영이 실제로 겪는 불편(안내 부재, 알림 부재)을 먼저 없앤다.
3. **P1-3(추가 충전 Add-on)을 P0으로 올릴지 판단한다.** 플랜 없이 필요할 때만 사는 고객이 파일럿에서 관측되면 그쪽이 더 급하다.
4. **§11의 결정 1(크레딧 누적)을 마일스톤 전에 닫는다.** 뒤로 미루면 이미 부여한 잔액에 소급 적용해야 해서 비용이 커진다.
