## 2. 시작 전 확인

1. 현재 Git 변경·브랜치·AGENTS를 확인하고 관련 변경만 범위에 넣는다.
2. 로드맵의 현재 단계와 직전 완료 증거를 확인한다. R0/R1부터 순서대로 진행한다.
3. 외부 HTTP 변경이 있으면 영향받는 path/schema, Kotlin DTO·계약 테스트, React API 타입을 먼저 열거한다.
4. 후보 화면·입출력 예시와 예외 상태를 문서에 고정한다. 사용자에게 구현 결과처럼 보이는 상태 표시는 금지한다.
5. 요구사항·인수 기준·토글·데이터 변경·롤백 단위를 적는다. 미정 결정은 영향받는 작업만 보류한다.
6. 실제 모델 호출 전에는 사용자 승인과 레인의 달러 한도를 확인한다. 일반 변환은 `EASYDOC_LANE_MAX_USD`, R2는 `EASYDOC_R2_LANE_MAX_USD`를 사용한다. 2026-09-21 R2 평가의 누적 US$50 상한을 승인받았다. 실패·재시도·분할 실행도 같은 총예산에 포함하며 실행 패킷과 잔여 한도를 기록한다.

### 3.1 현재 완료 증거

- ER-00: 공개 문서 10건, 개발 6건/보류 4건, 기준 질문 60개와 원문 근거·해시를 고정했다.
- ER-01~ER-02: `content_revision` CAS, V28 평가 저장소, 규칙 기반 누락 신호와 관계 확인 5종, 암호화·소유권·보존·키 회전을 구현했다.
- ER-03: capability 기반 검수 패널, 원문 이동, 항목별 확인/해당 없음, dirty·stale·409 복구 UX를 구현했다.
- ER-04 당시 로컬 범위: Kotlin 전체 빌드, React check·689개 테스트·build, Compose 구성, fake LLM E13 브라우저 흐름을 통과했다. 이후 PR #133의 원격 회귀 CI도 통과했다. 제한 파일럿·배포는 남아 있다.
- ER-05: 행동 안내 작업 API와 2.39.0 계약, 요청 키·활성 작업 중복 방지, 크레딧 예약/정산, 전역 worker 슬롯 2개, lease/fence, 호출 시작 원장과 `outcome_unknown` 회수를 구현했다. stale·삭제·기능 OFF는 미시작 호출을 실행하지 않고 예약을 반환한다. Kotlin 전체 빌드, React check·695개 테스트·build, Compose 구성을 통과했으며 실제 provider 호출은 0회다.
- ER-06: 원문 근거를 검사하는 6섹션 후보, 암호화된 후보·안내문 저장, 현재 본문/안내문 CAS, 새 후보 적용 후 별도 확인 저장, 확인된 현재 버전의 TXT 출력을 구현했다. 2.40.0 계약과 React API 타입을 맞췄다. Kotlin 전체 빌드, React check·698개 테스트·build, Compose 구성을 통과했으며 실제 provider 호출은 0회다.
- ER-07: 기능 토글이 켜진 변환 조회 응답에 행동 안내 capability를 연결하고, 별도 탭의 생성 전 이용량 확인·작업 재방문·6섹션 편집·원문 대조 체크·초안/확인 저장·TXT·stale/충돌 복구를 구현했다. 엄격한 JSON 설정에서 필수 nullable 요청 필드를 검증하고 fake worker poller의 기동 누락을 고쳤다. 최종 PR #133 CI는 Kotlin 빌드, React check·54개 파일/715개 테스트·build, Compose·사전 검사, 기본 Playwright 27개 통과/1개 건너뜀과 집행 켜짐 E22·E23 2개 통과다. ER-07 브라우저 fake E2E 2개는 기본 묶음에 포함된다. 유료 provider 호출은 0회다.

R1 이전의 본문 버전 기반은 기능별 확인 상태가 현재 본문에만 적용되게 만드는 최소 작업이다. R5는 이 상태를 문서 보존 기간 안의 버전별 이력 화면으로 확장한다. ER-08은 원칙적으로 위 순서를 따르되 R2 외부 의사결정이 지연되면 제품 담당자가 R3 독립 진행을 기록할 수 있다.

## 4. PR 안의 구현 순서

1. 요구사항과 실패 예시를 읽고 기존 테스트에 회귀 사례를 추가한다. Kotlin 구현은 TDD 원칙을 따른다.
2. 순수 도메인·정규화·상태 전이와 application port를 구현한다.
3. 필요할 때만 Flyway와 infrastructure adapter를 추가한다. 기존 마이그레이션을 수정하지 않는다. 번호는 PR 착수 시 충돌 없이 배정한다.
4. API 계약·DTO·테스트·frontend API 타입을 한 변경 단위로 맞춘다. 제안 계약 문서만 먼저 운영에 적용하지 않는다.
5. 별도 UX PR보다 API를 먼저 병합한다면 서버 기능은 OFF이고 모든 실제 소비자가 새 타입을 처리해야 한다. 그 상태를 사용자 기능 완료로 표시하지 않는다.
6. React 화면·상태·접근성과 기존 E2E 흐름을 확장한다. wire type과 호출은 `src/api/`에 둔다.
7. 실패·충돌·재시도·삭제·토글 OFF를 검증하고 관련 공개 안내를 갱신한다.
8. 검증 근거와 미검증 범위를 PR에 기록한 뒤 리뷰·CI·출시 순서로 진행한다.

병렬 작업은 같은 API와 DB 정의가 고정되고 파일 소유 범위가 겹치지 않을 때만 나눈다. 본문 저장·검수 확인·요약 무효화의 트랜잭션 구현은 한 작업 단위로 유지한다.

## 5. 작업별 준비 완료 기준

- 실제 입력 예시와 기대 결과, 실패 예시가 각각 하나 이상 있다.
- 화면 문구·버튼·busy/empty/error/stale 상태와 저장 책임이 명확하다.
- API 필드·상태·오류·인증·멱등성·호환 경로가 정해졌다.
- 새 본문을 저장하는 위치, 암호화, 보존·삭제, 로그 제외가 정해졌다.
- 호출 수·토큰·시간·고객 과금의 상한이 정해졌다. 유료 호출이 없으면 0회로 적는다.
- 대응 인수 기준과 롤백 방법을 작성했다.

준비 완료와 실제 실행 승인은 다르다. 비용 승인이 없는 상태에서도 fake adapter와 화면·계약 구현은 가능하다.

## 6. PR 설명 양식

```text
작업: ER-xx / REQ-xx / AC-xx
문제: 어떤 입력·행동에서 무엇이 잘못되거나 오래 걸리는가
변경: 사용자가 보게 되는 최종 동작
범위: 계약 path/schema, 영향 소비자, 저장·보존 변경
검증: 명령/결과, fixture, E2E, 비용 승인과 실제 호출 유무
출시: 토글 기본값, 마이그레이션, 이전 버전 호환, 롤백
남은 한계: 검증하지 못한 독자·입력·배포 환경
```

실제 커밋·PR·CI 링크를 얻기 전에는 완료 표에 임의 링크를 넣지 않는다.

## 8. 범위 변경 처리

새 기능·입력 형식·추가 생성 호출이 필요하면 해당 단계의 요구사항과 비용·인수 기준을 함께 고친다. HTTP 변경은 계약·Kotlin·React 소비자를 분리해 미루지 않는다. 로드맵 순서를 바꾸면 이유와 의존성을 남긴다. 사전 정제는 현행 Kotlin 런타임 입력 자산 범위에서 다루고 새 Python 도구·비교 하네스는 만들지 않는다.
