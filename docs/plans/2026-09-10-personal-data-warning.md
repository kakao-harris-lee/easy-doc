# 개인정보 경고용 검출

- 작성 2026-09-10. 근거: `docs/plans/2026-09-10-legal-tax-policy-final.md` §3.5-7, master-plan P0-15.
- 사용자 결정: **「경고용 검출로만 진행.」** 막지 않고, 값을 바꾸지 않고, 검출값을 저장하지 않는다.

## 1. 무엇을 하려는 것인가

이 서비스의 전제는 「변환 대상은 공개 배포용 안내문이라 개인정보를 담지 않는다」이고, 실제로 담겨 들어오면 **입력한 이용자의 책임**이다. 그 전제와 고지는 그대로 둔다.

**이 조각은 그 고지를 화면에서 한 번 더 실효 있게 만드는 최소 보강이다.** 2026-09-07에 제거한 자동 마스킹을 되살리는 것이 아니다 — 값을 바꾸지 않는다.

## 2. 결정

### 2.1 두 가지만 검출한다 — 주민등록번호와 카드번호

**전화번호와 이메일은 검출하지 않는다.** 공공 안내문에는 담당 부서 연락처와 문의 메일이 **정상적으로** 들어 있다. 그것을 경고하면 거의 모든 문서에서 경고가 뜨고, **경고가 소음이 되어 정작 중요한 경우에 무시된다.** 경고의 가치는 드물게 뜨는 데 있다.

남는 둘은 공개 배포 문서에 **정상적으로 들어갈 이유가 없는** 것들이다. 2026-09-07에 제거한 마스킹이 겨눴던 것도 정확히 이 둘이었다 — 우연이 아니다.

| 종류 | 판정 | 오탐을 막는 장치 |
|---|---|---|
| 주민등록번호 | 13자리(하이픈 허용) + **검증식 통과** | 검증식이 없으면 사업자등록번호·전화번호·날짜 조합이 마구 걸린다 |
| 카드번호 | 13~19자리 + **Luhn 통과** | 같은 이유 |

**검증식을 통과한 것만 경고한다.** 자릿수만 보면 오탐이 쏟아지고 §2.1의 소음 문제가 그대로 재현된다.

### 2.2 등록 전에 멈춰 세우고, 확인하면 그대로 보낸다

**`POST /documents`에 `personal_data_acknowledged: boolean`(선택, 기본 false)을 더한다.**

- 검출되었는데 이 값이 참이 아니면 → **422**. 문서가 만들어지지 않고 변환도 큐에 들어가지 않는다.
- 이용자가 화면에서 「이대로 진행」을 누르면 같은 내용을 `true`로 다시 보낸다 → 정상 등록.

**왜 이 모양인가.** 등록한 뒤에 경고하면 이미 외부 LLM으로 나갔거나 곧 나간다 — 경고가 늦다. 반대로 아예 거절하면 **막는 것**이 되어 사용자 결정과 어긋난다. 「멈춰 세우고 확인받은 뒤 그대로 보낸다」가 정책 문구(「경고만 띄우고 이용자가 확인한 뒤 진행하게 한다」)와 정확히 같다.

파일 업로드도 같은 경로를 탄다 — 화면이 파일을 쥐고 있으므로 재전송이 가능하다.

### 2.3 검출된 값을 남기지 않는다

- 오류 본문은 이 저장소 규약대로 **`{detail}`뿐**이다. 「개인정보로 보이는 내용이 있습니다. 확인 후 다시 시도하세요.」
- **어떤 종류가 걸렸는지는 헤더로** 낸다: `X-Personal-Data-Kinds: rrn,card`(정렬된 소문자, 쉼표 구분). 계약의 `x-error-body-universality` 규약과 「추가 정보는 헤더」 선례(`X-Credit-Balance`)를 따른다. **CORS 노출 목록에 추가해야 한다** — 빠뜨리면 브라우저가 못 읽는다.
- **값도, 위치도, 건수도 남기지 않는다.** 로그에는 종류만 적는다(본문·개인정보 로깅 금지 규칙).
- **DB에 아무것도 쓰지 않는다.** 거절된 등록은 흔적이 없다.

### 2.4 검출은 순수 함수다

`core`에 둔다 — Spring도 DB도 없이 테스트된다. 입력은 정규화된 본문 문자열, 출력은 **종류의 집합**이다. 위치·값·건수를 돌려주지 않는다(돌려주면 어딘가에 남는다).

### 2.5 한계를 문서와 화면에 적는다

이름·주소·생년월일처럼 **패턴이 없는 개인정보는 잡히지 않는다.** 화면 문구가 「검사했으니 안전하다」로 읽히면 안 된다 — 「개인정보로 보이는 내용이 있습니다」까지만 말하고, 없을 때는 **아무 말도 하지 않는다**(무사고 통과를 보증처럼 보이게 하지 않는다).

**패턴이 있는데도 놓치는 경우가 셋 더 있다**(2차 리뷰 2026-09-10에서 확인. 셋 다 알고 남긴 것이지 빠뜨린 것이 아니다).

1. **PDF 추출이 숫자 중간에 줄바꿈을 넣으면 놓친다.** 정규식이 줄바꿈을 건너뛰지 않는다. 건너뛰게 만들면 **윗줄 끝 6자리와 아랫줄 첫 7자리를 하나의 주민등록번호로 잘못 묶는다** — 공공 안내문은 숫자 표가 많아 이 방향의 오탐이 더 비싸다. **놓치는 쪽을 택한다.**
2. **전각 숫자(０~９)는 잡히지 않는다.** `\d`가 반각만 본다.
3. **드문 길이·대역의 카드는 잡히지 않는다**(Diners 14자리 등). §2.1에서 15~16자리·첫 자리 3·4·5·6으로 좁힌 결정의 이면이다.

셋 다 **미탐**이고, 이 기능은 차단 장치가 아니라 경고 도구라 오탐을 줄이는 쪽을 먼저 둔 결과다. 실사용에서 1번이 실제로 문제가 되면 그때 다시 본다 — 그때도 표의 오탐을 어떻게 막을지가 먼저다.

## 3. 슬라이스 (한 조각, S)

- `core`: 검출기(주민등록번호 검증식·Luhn), 순수 함수.
- `application`: `DocumentService.store` 앞에서 검출, `personalDataAcknowledged`가 아니면 예외.
- `api`: `POST /documents` 요청 필드, 422 + `X-Personal-Data-Kinds` 헤더, CORS 노출 목록.
- 계약 **2.31.0**: 요청 필드, 422 응답, 헤더 선언(`ContractHeaderDeclarationTest`가 검사한다).
- 프런트: 422를 받으면 경고와 「이대로 진행」 버튼, 재전송. 붙여넣기·파일 업로드 두 경로 모두.
- 마이그레이션 없음.

## 4. 수용 기준

1. 검증식을 통과하는 주민등록번호가 든 본문을 확인 없이 등록하면 **422**이고 `X-Personal-Data-Kinds: rrn`이며 **`documents` 행이 0건**이다(실 DB).
2. Luhn을 통과하는 카드번호도 같다(`card`).
3. 둘 다 있으면 헤더가 `card,rrn`(정렬)이다.
4. **확인 플래그를 참으로 보내면 정상 등록**된다(202).
5. **전화번호·이메일만 있는 본문은 통과**한다 — 경고가 뜨지 않는다.
6. **검증식을 통과하지 못하는 13자리 숫자**(예: 사업자등록번호를 이어 붙인 문자열)는 통과한다.
7. 파일 업로드 경로도 1~4와 같게 동작한다.
8. 응답 본문에 `detail` 외 필드가 없고, **로그에 본문·검출값이 남지 않는다**(기존 로그 누출 테스트 방식 재사용).
9. 프런트: 422를 받으면 경고와 「이대로 진행」이 보이고, 누르면 재전송되어 성공한다.

## 5. 범위 밖

마스킹·치환, 이름·주소 검출, 검출 이력 저장, 관리자 통계, 파일 이름·메타데이터 검사, 재변환 경로(이미 등록된 본문).
