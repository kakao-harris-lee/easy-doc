## 1. 결제대행사 — 토스페이먼츠 확정, 착수는 1차 배포 이후

**2026-09-09 사용자 결정 ①: 결제대행사는 토스페이먼츠다.** 목표 프로세스 §12 결정 1이 닫혔다.

**2026-09-09 사용자 결정 ②: 실연동은 1차 배포 뒤에 시작한다.** 토스페이먼츠는 **운영 중인 서비스가 확인되어야** 신청·심사가 가능하다. 따라서 순서는 이렇다.

```
카드 결제를 스텁으로 개발 → https://easydoc.kr 1차 배포 → 서비스 검증
  → 토스페이먼츠 신청·심사 → 실연동 교체 → 실결제 개시
```

**서비스 검증이 먼저다.** 결제가 붙지 않아도 변환 품질과 운영이 서지 않으면 결제를 붙일 이유가 없다.

### 1.0 스텁으로 먼저 만든다

결제 흐름 전체(플랜 구매·정기 결제·실패·취소·환불·추가 구매)를 **모의 결제 어댑터**로 끝까지 돌아가게 만든다. 실연동은 어댑터 교체로 끝나야 한다.

- 이 저장소에 이미 같은 형태가 있다. `LlmProvider` 포트에 `fake` 어댑터를 두고 Compose·e2e가 유료 호출 없이 전 구간을 도는 구조다. **`PaymentGateway` 포트도 같은 방식으로 만든다** — 구성값 `easydoc.payment.provider=stub|toss`, 선택은 `@Configuration`에서만 한다.
- 스텁은 성공만 흉내 내지 않는다. **실패·부분취소·전액취소·중복 웹훅**을 재현할 수 있어야 실연동에서 처음 만나는 갈래가 없다.
- **기동 자기점검을 둔다.** 실결제를 여는 프로필에서 `provider=stub`이면 기동을 막는다(암호화 키·LLM provider 자기점검과 같은 자리).

> ⚠ **1차 배포에서 결제 화면을 일반 사용자에게 열지 않는다.** 스텁이 붙은 결제 화면을 그대로 노출하면 사용자가 결제했다고 오해한다. 요금 안내는 보여 주되 결제 버튼은 「준비 중」으로 두거나 화면 자체를 내린다. 파일럿 크레딧은 지금처럼 운영자가 수동으로 부여한다.

### 1.1 우리가 쓰는 기능

| 기능 | 쓰는 곳 |
|---|---|
| 일반 결제(카드) | 플랜 첫 결제, 50크레딧 추가 구매 |
| **빌링키 자동결제** | 월 구독 갱신(프로세스 §6.2) |
| **결제 취소** | 환불(§6.4), **카드→계좌이체 전환**(§10.5) |
| 결제 내역 조회 | 마이페이지 결제 내역, 어드민 대사 |

**결제 취소가 특히 중요하다.** 개인카드로 결제한 뒤 기관 명의 세금계산서가 필요한 경우, 카드 결제를 되돌려야 발행할 수 있다. 부분 취소 지원 여부와 취소 가능 기간을 계약 단계에서 확인한다.

### 1.2 계약 절차

신청 → 서류 제출 → 토스페이먼츠 심사 → **카드사 심사** → 결제·정산 개시 순이다. 신청 접수 후 3영업일 안에 계약부서 안내가 온다. **카드사 심사가 별도 단계라 리드 타임이 있으므로 지금 시작한다.**

**우리는 개인사업자다(§2.0).** 법인 기준 서류(법인등기부등본·주주명부·법인인감증명서)가 아니라 개인사업자 기준으로 준비한다 — 사업자등록증, 대표자 신분증, 정산 계좌 통장 사본, **통신판매업 신고증**(§2.0.3). 정확한 목록은 계약부서 안내를 따른다.

### 1.3 선행 조건

**통신판매업 신고가 필요하다**(§2.1). 전자결제 계약과 사이버몰 표시 의무가 모두 이 신고번호를 요구한다. 신고는 관할 시·군·구청에 한다.

### 1.4 기술 연동에서 미리 정할 것

- **결제 키는 서버에만 둔다.** 카드번호는 우리 저장소에 남기지 않는다(프로세스 §6.1).
- 웹훅으로 결제 성공·실패·취소를 받는다. **크레딧 부여는 웹훅 수신 시점이 아니라 결제 확정 확인 뒤**에 한 트랜잭션으로 처리한다. 재전송을 전제로 멱등하게 만든다(기존 재변환·정산 패턴과 같다).
- 테스트 키로 통합 테스트를 만들고, **실제 결제는 자동 테스트에서 호출하지 않는다**(프로젝트 규칙: 유료 외부 호출은 승인 대상).

| 대표자 | **이치훈** | |

**대표자 생년월일 등 사업자등록증의 개인 식별정보는 이 저장소에 적지 않는다.** 위 표는 전자상거래법이 공개를 요구하는 항목만 옮긴 것이다.

#### 2.0.1 일반과세자 — 세금계산서 프로세스가 성립한다

간이과세자였다면 세금계산서를 발행할 수 없어 목표 프로세스 §10 전체가 무너졌을 것이다. **일반과세자이므로 발행 주체 요건은 충족된다.** 다만 사업자등록증의 **「전자세금계산서 전용 전자우편주소」가 비어 있다** — 홈택스에서 등록하고, 발급 수단(공동인증서 등)을 갖춰야 실제 발행이 된다.

#### 2.0.2 사업장 주소 — 창업지원 공간으로 옮긴다(2026-09-09, 사용자 결정)

등록된 사업장 소재지는 아파트다. 전자상거래법은 **소비자가 불만을 제기할 수 있는 영업소 소재지**를 초기 화면에 표시하도록 요구하므로, 이대로면 자택 주소가 푸터에 공개된다. **주소를 숨기는 방법은 없다** — 법이 요구하는 것은 실제 영업소이고 허위 표시는 그 자체가 위반이다.

**사용자 결정(2026-09-09, 최종): 등록증의 현재 주소를 그대로 쓴다.** 창업지원 공간 입주를 검토했으나 승인까지 시간이 걸려 1차 배포를 막게 된다. **배포를 주소 때문에 미루지 않는다.**

- 푸터에 실을 주소는 **사업자등록증의 사업장 소재지 그대로**다(§2.0).
- **자택 주소가 공개된다는 점을 감수한 결정이다.** 이것은 법이 실제 영업소를 요구하기 때문이고, 다른 주소를 적는 것은 허위 표시다.
- **1차 배포의 선행 조건에서 주소가 빠진다.** 이미 등록된 주소를 쓰므로 사업자등록 정정도 필요 없다.

**나중에 옮길 때를 위해 지금 해 둘 일이 하나 있다.** 회사 정보(상호·대표자·주소·사업자등록번호·통신판매업 신고번호·연락처)를 **한 곳에서만 정의**한다. 푸터·약관·개인정보처리방침·세금계산서 서식에 같은 문자열을 흩뿌리면 이전할 때 빠뜨리는 곳이 생긴다. 이 저장소의 규칙대로 **타입 있는 구성값**(`@ConfigurationProperties`)으로 받고 화면은 그것을 읽는다. 그러면 입주가 확정될 때 **사업자등록 정정 → 구성값 한 곳 변경 → 재기동**으로 끝난다.

> 입주가 확정되면 그때 ⑴ 사업자등록 정정 ⑵ 구성값 변경 ⑶ 약관·방침의 주소 문구 갱신을 한 묶음으로 처리한다. **푸터 주소는 항상 사업자등록증의 사업장 소재지와 같아야 한다** — 다르면 공정거래위원회 사업자정보 조회에서 그대로 드러나고 표시 의무 위반이 된다.

#### 2.0.3 통신판매업 신고 — 토스 계약 뒤로 순서를 바꾼다(2026-09-09, 사용자 결정)

아직 신고 전이다. 신고는 관할 **제주시청**에 한다. **선지급식 통신판매는 신고 시 「구매안전서비스 이용 확인증」을 요구하는데, 그 확인증은 결제대행사가 발급한다.** 앞서 이것을 순환 의존으로 적었으나, **사용자 확인으로 풀렸다 — 토스페이먼츠를 먼저 처리하고 그 확인증으로 신고하면 된다.**

확정된 순서다.

```
1차 배포(무상) → 서비스 검증 → 토스페이먼츠 계약
  → 구매안전서비스 이용 확인증 발급 → 통신판매업 신고 → 결제 개시
```

**따라서 1차 배포 시점에는 통신판매업 신고번호가 없다.** 이것이 허용되는 근거는 **그 시점에 통신판매를 하지 않는다는 것**이다 — 결제 화면을 열지 않고(§1.0), 크레딧은 운영자가 수동 부여하며, 대가를 받지 않는다. **결제를 여는 순간부터는 신고가 있어야 한다.**

> 이 논리는 상식적이지만 **제주시청에 한 번 확인한다**(§7-6). 무상 서비스 단계에서 신고 없이 운영해도 되는지, 그리고 신고 전까지 푸터의 신고번호 자리를 비워 두어도 되는지 두 가지다. 푸터는 신고번호가 채워질 자리를 처음부터 만들어 두고, 결제 개시와 함께 값을 넣는다.

### 2.1 전자상거래법 표시 의무

사이버몰 운영자는 아래를 **초기 화면에 소비자가 알아보기 쉽게** 표시해야 한다. 관행대로 **푸터**에 둔다.

| 항목 | 비고 |
|---|---|
| 상호, 대표자 성명 | |
| 영업소 소재지 주소 | 소비자 불만을 처리할 수 있는 실제 주소 |
| 전화번호, 전자우편주소 | |
| 사업자등록번호 | |
| 통신판매업 신고번호와 신고기관 | §1.3 |
| 이용약관 | 링크 |
| 사업자정보 공개페이지 링크 | 공정거래위원회 통신판매사업자 조회 |

모바일처럼 한 화면에 다 담기 어려우면 순차 노출이 허용되고, 대표자 성명·사업자등록번호·이용약관은 **확인할 수 있는 방법**을 화면에 두면 된다.

### 2.2 개인정보 보호법 표시 의무

- **개인정보처리방침을 공개**하고, **다른 약관과 구분되도록 표시**한다. 푸터에서 이용약관과 나란히 두되 **굵게** 처리하는 것이 일반적이다.
- **개인정보 보호책임자**의 성명 또는 부서명과 연락처를 방침에 싣고 푸터에서 닿게 한다.

## 3. 크레딧 소멸 — 약관·법규 검토

프로세스 §8이 정한 소멸 설계(묶음별 유효기간, 만료 임박 순 차감, 자동 소멸)를 법적으로 받쳐 줄 것들이다.

### 3.1 쟁점 A — 선불전자지급수단이 되어서는 안 된다

전자금융거래법의 선불전자지급수단에 해당하면 **전자금융업 등록**과 선불충전금 관리 의무가 따라온다.

#### 조사 결과(2026-09-09) — 해당하지 않을 가능성이 매우 높다

법 정의의 요건 중 하나가 이것이다.

> **발행인(특수관계인 포함) 외의 「제3자」로부터** 재화 또는 용역을 구입하고 그 대가를 지급하는 데 사용될 것

**우리 크레딧은 우리 서비스의 문서 변환에만 쓰인다.** 발행인이 곧 용역 제공자이므로 **제3자 요건을 아예 충족하지 않는다.** 가맹점 개념이 없고 다른 사업자에게 대가를 지급하는 수단이 아니다.

**주의할 이력이 있다.** 예전에는 「2개 업종(한국표준산업분류 중분류) 이상」이라는 범용성 요건이 함께 있었고, 업종이 하나면 해당하지 않는다는 논리를 많이 썼다. **2024-09-15 시행 개정법이 이 업종 요건을 폐지했다** — 그래서 대부분의 모바일 상품권이 선불전자지급수단으로 들어왔다. **「업종이 하나라서 아니다」라는 옛 논거를 쓰면 안 된다.** 우리가 서는 근거는 업종 수가 아니라 **제3자 요건**이다.

**따라서 방향은 이렇다: 자사 전용을 유지하는 한 등록 대상이 아니다.** 반대로 말하면 **제휴사에서 크레딧을 쓰게 하는 순간 성격이 바뀐다** — 향후 제휴·재판매를 검토할 때 이 선을 먼저 본다.

아래 표는 그 성격을 유지하기 위한 설계 잠금이다.

**2026-09-09 사용자 결정: 전자금융업 등록은 하지 않는다. 따라서 크레딧을 「구매 계약」으로 설계한다.** 크레딧은 저장된 금전적 가치가 아니라, **가입한 계정이 쓸 서비스 이용량(변환 분량)을 미리 산 것**이다. 이 성격이 유지되도록 아래를 설계와 약관에 못 박는다.

| 못 박을 것 | 내용 |
|---|---|
| **계정 귀속** | 크레딧은 구매한 계정에 귀속된다. 다른 계정으로 옮길 수 없다 |
| **양도 금지** | 제3자 양도·판매·증여·담보 제공을 금지한다 |
| **환금 금지** | 현금·타 수단으로 교환하지 않는다. 환불은 §3.2의 구매 계약 해제 절차로만 |
| **자사 전용** | 우리 서비스의 문서 변환에만 쓰인다. 가맹점 개념이 없다 |
| **가치 표시 아님** | 크레딧은 **분량 단위**(1,000자)이지 금액이 아니다. 화면·약관에서 「충전」·「잔고」 대신 **「구매」·「남은 이용량」** 을 쓴다 |

마지막 항목이 특히 중요하다. **말이 성격을 만든다.** 「충전」·「환불 가능한 잔고」로 부르면 선불수단으로 읽히고, 「구매한 이용량」으로 부르면 서비스 구매 계약으로 읽힌다. 지금 화면과 러너북에 남아 있는 「충전」 표현을 **「구매」로 정리**한다(§8-6).

> ⚠ **P1-1 팀/부서 계정의 「크레딧 공유」와 충돌한다.** 여러 계정이 한 크레딧을 나눠 쓰면 계정 귀속이 흔들린다. 팀 기능을 열 때는 **크레딧이 워크스페이스 계약에 귀속되고 구성원은 그 계약의 이용자일 뿐**이라는 구성으로 다시 정리해야 한다. master-plan P1-1에 이 제약을 적어 둔다.

이 구조가 실제로 등록 의무를 피하는지는 **자문으로 확인한다**(§7-1). 다만 방향은 사용자 결정으로 닫혔다 — 등록이 필요한 설계는 채택하지 않는다.

### 3.2 쟁점 B — 「신유형 상품권 표준약관」의 잣대

공정거래위원회 표준약관은 소비자 대상 상품권을 겨눈 것이라 B2B 이용권에 그대로 적용되지는 않지만, 분쟁 시 유사한 잣대가 쓰일 수 있다. 그 기준은 이렇다.

| 표준약관 기준 | 우리 설계와의 거리 |
|---|---|
| 금액형 유효기간 **최소 1년**(+연장 3개월) | 추가 구매 12개월은 경계선에 걸친다. **연장 조항이 없다** |
| 유효기간 경과 후 **소멸시효 5년 내 90% 환급** | 우리 설계에는 없다. **가장 큰 간극** |
| 60% 이상(1만 원 이하 80%) 사용 시 잔액 환불 | 없다 |
| 구매일로부터 7일 내 전액 환불 | 프로세스 §6.4가 같은 취지로 이미 있다 |

**대응 방향(권고).** 크레딧을 두 종류로 나눠 약관에서 다르게 다룬다.

- **유상 크레딧**(추가 구매): 표준약관 잣대에 가깝게 간다. 유효기간 12개월, 만료 전 연장 요청 수용, 만료 후 일정 기간 환급 청구 가능.
- **구독 제공 크레딧**(플랜): 「구매한 상품권」이 아니라 **그 달의 이용권**이다. 주기 종료와 함께 소멸하는 것이 구독의 본질임을 약관과 요금 화면에 명시한다. 헬스장 월 회원권이 다음 달로 이월되지 않는 것과 같은 구조다.
- **무료 크레딧**: 대가가 없으므로 환급 대상이 아니다. 유효기간만 고지한다.

이 구분이 서지 않으면 **월 구독 크레딧의 매월 소멸이 통째로 위험해진다.** 소멸을 도입하는 이유가 부채를 닫는 것이므로, 이 구분을 약관에서 명확히 하는 것이 이 작업의 핵심이다.

### 3.3 쟁점 C — 소멸 전 고지

표준약관은 유효기간 도래 전 통지를 요구한다. 프로세스 §8.5는 7일 전 1회를 정했다. **30일 전과 7일 전 2회로 강화할 것을 권고한다** — 예산 담당자가 소진 계획을 세우려면 7일은 짧다.

### 3.4 약관에 반드시 들어갈 문장

1. 크레딧의 정의와 환산 기준(공백 포함 1,000자 = 1크레딧).
2. 종류별 유효기간과 **소멸 시점**.
3. **차감 순서**(만료 임박 순).
4. 소멸 예고 방법과 시점.
5. 환불·환급의 범위와 절차.
6. 양도 불가, 현금 교환 불가, 자사 서비스 전용.
7. 유효기간·요금 변경 시 사전 고지 방법과 기간.

## 4. 개인정보 취급·파기 이행

### 4.1 파기

개인정보처리자는 보유기간 경과·처리 목적 달성 등으로 개인정보가 불필요해지면 **지체 없이** 파기해야 하고, 정당한 사유가 없으면 **그날부터 5일 이내**다. 다른 법령에 보존 의무가 있으면 예외다.

우리가 이미 가진 것과 없는 것은 이렇다.

| 대상 | 현재 | 필요한 것 |
|---|---|---|
| 문서 원문·변환 결과 | 30일 보존 후 파기 배치가 **있다**(매일 03:00) | 방침에 보존기간과 파기 시점을 명시 |
| 회원 계정·이메일 | 탈퇴 기능·파기 절차 **없음** | 탈퇴, 탈퇴 시 파기, 법령 보존분 분리 |
| 결제 정보 | 없음(토스 도입 후 생김) | 법령 보존기간 뒤 파기 |
| 세금계산서 요청의 사업자 정보 | 저장 **있음** | 보존기간 결정과 파기 |
| 로그·접속기록 | 있음 | 보존기간 명시 |

**법령상 보존해야 하는 것**은 파기 대상에서 빼되 **분리 보관**하고 방침에 근거와 기간을 적는다. 전자상거래법의 계약·청약철회 기록, 대금결제·재화공급 기록, 소비자 불만·분쟁처리 기록, 통신비밀보호법의 접속기록이 여기에 해당한다. **각 기간은 자문으로 확정한다**(§7-2).

파기 방법은 전자 파일은 복구할 수 없는 방법으로, 출력물은 분쇄하거나 소각한다.

### 4.2 처리위탁과 국외이전

방침에 **수탁자와 위탁 업무를 공개**해야 한다. 지금 구조에서 공개 대상은 이렇다.

| 수탁자 | 업무 | 국외 |
|---|---|---|
| LLM 사업자(Anthropic·OpenAI 등) | 문서 변환 처리 | **국외이전 해당** |
| 메일 발송 | 인증·알림 메일 | 사업자에 따라 다름 |
| 토스페이먼츠 | 결제 처리 | 국내 |
| 클라우드·호스팅 | 인프라 | 리전에 따라 다름 |

#### 조사 결과(2026-09-09) — 별도 동의 없이 「처리방침 공개」로 갈 수 있다

개인정보 보호법 제28조의8은 국외 이전을 원칙적으로 막고 예외를 열거하는데, 그중 하나가 이것이다.

> **정보주체와의 계약의 체결 및 이행을 위하여** 개인정보의 **처리위탁·보관**이 필요한 경우로서, 같은 조 제2항 각 호의 사항을 **개인정보 처리방침에 공개**하거나 전자우편 등으로 알린 경우

**문서 변환은 이용자와 맺은 계약의 이행 그 자체이고, 해외 LLM 호출은 그 이행을 위한 처리위탁이다.** 따라서 **별도 동의 체크박스를 받지 않아도 되고, 처리방침에 제대로 공개하면 된다.** 가입 흐름에 동의 단계를 하나 더 넣지 않아도 된다는 뜻이라 화면 설계가 단순해진다.

**공개해야 하는 항목**(제28조의8 제2항): 이전받는 자, 이전되는 국가, 이전 일시와 방법, 이전하는 개인정보 항목, 이전받는 자의 이용 목적과 보유·이용 기간, **이전을 거부하는 방법·절차와 그 효과**.

마지막 항목이 실무적으로 까다롭다. **이전을 거부하면 변환을 제공할 수 없다**는 사실을 함께 적어야 한다 — 거부 수단이 사실상 「서비스를 이용하지 않는 것」이기 때문이다. 그 문구를 자문에서 받는다.

master-plan §3.2가 이미 「마스킹 후 전송 + 개인정보처리방침·위탁 문서에 국외 이전 고지」를 정했고, 2026-09-07에 마스킹을 걷어내면서 **고지와 no-training 조항의 비중이 커졌다**고 같은 절에 적혀 있다. 그 판단을 방침 문구로 옮긴다.

### 4.3 개인정보처리방침에 담을 항목

처리 목적·항목·보유기간 / 제3자 제공 / **처리위탁** / **국외이전** / 파기 절차와 방법 / 정보주체의 권리와 행사 방법 / 개인정보 보호책임자 / 안전성 확보 조치 / 방침 변경 고지.

**안전성 확보 조치는 이미 상당 부분 갖췄다** — 본문 AEAD 암호화와 키 회전, 소유 술어 기반 접근 통제, 로그에 본문·개인정보·토큰을 남기지 않는 규칙이 코드와 테스트로 고정돼 있다. 방침에 그 사실을 적을 수 있다.

### 6.3 응대 원칙

- 개인정보·문서 본문을 메일 본문에 옮기지 않는다. 문서 id로 지칭한다.

- 같은 문의가 세 번 이상 오면 도움말 문서에 항목을 추가한다.

## 8.5 경쟁 서비스(온글) 대조 — 참고되는 것과 안 되는 것

2026-09-09 사용자 요청으로 온글(easy-read.co.kr)의 공개 문서를 확인했다. **결론부터: 개인정보처리방침의 «형식»은 참고가 되지만, 크레딧 성격·소멸과 국외이전은 참고가 되지 않는다.** 판매 방식이 달라서다.

### 8.5.1 참고할 수 있는 것 — 개인정보처리방침의 뼈대

온글 방침은 목적별로 수집 항목을 나누고, 보유기간·파기·위탁·보호책임자·정보주체 권리를 차례로 둔다. 우리도 같은 뼈대를 쓴다.

| 절 | 온글이 쓴 방식 |
|---|---|
| 수집 항목 | **목적별로 나눈다** — 「회원 가입 및 관리」(성명·이메일·비밀번호)와 「서비스 제공」(+전화번호·소속기관·부서)을 따로 적고, 도입 계획 같은 것은 선택 항목으로 뺐다 |
| 보유기간 | 「탈퇴 시까지」 / 「서비스 제공 완료 또는 탈퇴 시까지」 / 「고충 처리 완료 후 관련 법령상 보존기간까지」 |
| 파기 | 사유 발생 시 대상을 선정하고 **보호책임자 승인을 거쳐** 파기. 전자 파일은 재생 불가능한 방법, 종이는 분쇄·소각 |
| 위탁 | 수탁자·위탁 업무·**위탁하는 개인정보 항목**을 표로 |
| 보호책임자 | 성명·직책·연락처(전화·이메일·팩스)와 **담당 부서**를 따로 |
| 정보주체 권리 | 열람·정정·삭제·처리정지 넷과 행사 방법(서면·전화·전자우편·팩스) |

**보유기간 표기가 우리보다 성기다.** 「관련 법령상 보존기간까지」로 뭉뚱그렸는데, 우리는 온라인으로 결제를 받으므로 전자상거래법의 계약·결제·불만 처리 기록 보존기간을 **항목별 숫자로** 적어야 한다(§4.1, §7-2).

### 8.5.2 참고가 되지 않는 것 — 그리고 그 이유

| 항목 | 온글 | 우리 |
|---|---|---|
| **이용약관·환불 정책·결제 약관** | **공개된 것이 없다** | 필요하다 |
| **크레딧 성격·유효기간·소멸 조항** | **없다** | 이번 검토의 핵심 |
| 사업자등록번호·통신판매업 신고번호 | 푸터에 **없다** | **필수**(§2.1) |
| 국외이전 | **「없음」** | **해당한다**(해외 LLM) |
| 위탁 | 국내 1곳(그룹사) | 해외 LLM·PG·메일·호스팅 |

**이유는 판매 방식이다.** 온글은 연간 계약을 영업으로 판다 — 체험조차 구글 폼 신청이고 가격은 「별도 문의」다. 온라인으로 대금을 받지 않으니 사이버몰 표시 의무와 크레딧 약관이 애초에 필요 없다. 반대로 **우리는 카드로 온라인 판매를 하므로 그 의무가 전부 발생한다.**

**따라서 온글에 없다는 사실을 「우리도 없어도 된다」로 읽으면 안 된다.** 여기서 가져올 것은 방침의 뼈대(§8.5.1)뿐이고, §7의 자문 항목은 그대로 남는다. 특히 **국외이전은 우리만의 노출**이라 참고할 선례가 없다 — master-plan §3.2의 판단(마스킹 제거 후 고지·no-training 조항의 비중 증가)을 방침 문구로 직접 옮겨야 한다.
