## 미션 CC — 워크스페이스

**Lean 결정(팀 공유는 P1-1로 보류 — 개인 소유 워크스페이스만):**
- 모델 `Workspace(id, user_id FK, name ≤50자, created_at)` + `Document.workspace_id FK(nullable→기본 워크스페이스 백필 후 NOT NULL)`. 마이그레이션: 기존 사용자마다 "기본 작업 공간" 생성·기존 문서 귀속.
- API: `GET/POST /workspaces`, `PATCH /workspaces/{id}`(이름), `DELETE /workspaces/{id}`(내부 문서 있으면 409 — 실수 방지, 비우고 삭제 유도), 문서 생성 시 `workspace_id` 선택(미지정 시 기본), `GET /documents?workspace_id=` 필터.
- 소유자 격리: 워크스페이스도 user_id 조인 검증(타인 404).
- UI: 헤더에 워크스페이스 선택 드롭다운(+생성·이름 변경), 업로드는 현재 워크스페이스로, 변환 기록은 현재 워크스페이스 필터. 선택 상태는 localStorage.
- 용어: UI 표기 "작업 공간".

## 미션 DD — hwpx 내보내기

- 제어문자·플레이스홀더 복원·캐시 헤더 등 기존 export 규율 동일 적용.

## 미션 FF — 연구 스파이크: 키워드/형태소 분리로 필터링 정확도 개선 여지

**목적**: 미션 EE의 `find_difficult_words`는 단순 문자열 부분일치(낱말 시작 위치 휴리스틱)다. 형태소 분석(예: kiwipiepy 등 순수 파이썬 분석기)이나 키워드 추출을 앞단에 붙이면 활용형·복합어 변형까지 잡아 필터링 정확도(재현율)가 의미 있게 오르는지 **실측**한다.

- `docs/golden/`의 실제 공공기관 문서(hwpx/pdf, 마스킹 전 원문 추출본)를 표본으로, 현재 `find_difficult_words` 탐지 결과와 형태소 분석 기반 탐지 결과를 비교.
- 형태소 분석기는 pyproject.toml에 반영하지 않고 `uv run --with <라이브러리>`로 임시 실행해 조사만 한다 — 의존성 추가는 효과 확인 후 별도 결정.
- 정량 지표: 형태소 분석이 추가로 잡아내는 참 위반(현재 방식이 놓치는 실제 어려운 낱말 등장) 건수·비율, 오탐 증가 여부, 처리 지연.
- **결론 분기**: 개선 효과가 뚜렷하고 지연·의존성 비용이 합리적이면 → 구체적 구현 계획(어느 함수를 어떻게 바꾸는지, 의존성 추가 사유)을 문서로 도출해 보고. 효과가 미미하거나 비용 대비 이득이 없으면 → 조사 결과만 기록하고 구현 안 함(YAGNI 유지).
- 이 미션은 조사이며, 결론과 무관하게 프로덕션 코드 변경은 하지 않는다(구현은 결과 보고 후 별도 승인).

**조사 결과 (2026-08-08, kiwipiepy로 실측) — 결론: 구현 불필요(YAGNI 유지)**

- 방법: `docs/golden/` 실제 문서(hwpx·pdf) 중 정상 추출된 11건을 표본으로, 베이스라인(`find_difficult_words()`)과 kiwipiepy 형태소 정확매칭을 비교. `uv run --with kiwipiepy`로 임시 실행, pyproject.toml·프로덕션 코드 무변경(git status로 확인).
- **재현율 개선은 미미**: kiwi 추가 검출은 전체 46건/1,197건(3.8%)이나, 이 중 29건이 PDF 추출 결함으로 공백이 소실된 이상치 문서 1건에 쏠렸다. 이상치를 빼면 개선폭은 **1.5%**(17/1,133) — "형태소 분석이 활용형·복합어를 더 잘 잡는다"가 아니라 "추출 결함에 더 강하다"는 별개 이슈였다.
- **오탐·치환위험 확인**: 표본 검토에서 "통상"이 "산업**통상**자원부"(부처명) 안에서, "전입"이 "위장**전입**"(고정 법률 용어) 안에서 검출되는 등 17건 중 3~4건(약 20%)이 오탐/치환 위험군 — `style_rules.py`의 기존 설계 원칙("복합어 끝 낱말은 놓치더라도 과잉 검출보다 낫다")이 실측으로도 재확인됨.
- **재구성 비용**: 사전 키 상당수가 조사/어미/접두어 결합형(`사전에`·`의하여`·`구비서류`·`부득이한` 등)이라 형태소 분리 시 여러 토큰으로 쪼개져 정확매칭이 오히려 실패 — 문서당 20개 이상을 새로 놓친다. 246개 키 전체를 재구성하려면 큰 재작업이 필요.
- **비용**: 문서당 처리시간 베이스라인 6.4ms → kiwi 평균 2,218ms(최대 7.2초, 약 350배). 의존성 +126MiB(kiwipiepy-model+numpy, 순수 wheel — 네이티브 빌드는 불필요).
- **결론**: 재현율 개선(이상치 제외 1.5%)이 오탐·치환위험(~20%)·지연(350배)·의존성(126MiB) 비용을 상회하지 못한다. 미션 EE의 필터링은 현행 `find_difficult_words()` 그대로 유지. 향후 사전 규모가 커지거나(다듬은 말 18,329건 등) 활용형 매칭이 핵심 요구가 될 때 재검토.

## 미션 GG — 치환 비문 제거: "어색하면 다시 쓰기"의 구조화 (2026-08-09 승인)

**배경**: `docs/quality/2026-08-09-doc020-fidelity-review.md`에서 사전 치환이 만든 비문이 3샘플에 반복 확인됐다 — "바우처 카드를 **내어 줌 받아** 사용", "**뽑음 결과**"(제목), "**사용 정해진 날짜가** 지나면". 제품 판단(사용자): 쉬운 글이 어색한 글이면 지불 이유가 없다 → 어색해지면 재서술이 **강제되는 구조**가 필요.

**원인 진단** (③은 구현 중 실측 검증):

1. 사전 값의 상당수가 명사형 뜻풀이("내어 줌"·"뽑음"·"받음")라 동사·복합어 자리에 끼우면 필연적으로 비문이 된다.

## 부록 — 쉬운 말 사전 RAG(P0-5) 사전조사 (이번 스프린트 미션 아님, 문서만 기록·구현 미착수)

master-plan §9(로드맵)상 "쉬운 말 사전 RAG"는 단계2 스프린트4 항목으로 잡혀 있으나(§249), 위 AA~DD로 실제 착수 대상이 대체되어 이월됨. 향후 착수 시 참고할 설계·데이터 소스 조사 결과만 기록.

### 파이프라인 구조 검토

"난이도분석→RAG검색→재작성→검수"의 4단계 멀티 에이전트 구조가 제안되었으나, 현행 변환 호출 계약(§94, "1건 = LLM 호출 최대 2회, 루프 없음")과 충돌해 **고정 4단계로는 채택하지 않음**. 단, 요지는 "모든 문장에 4단계를 다 태우자"가 아니라 "난이도에 따라 필요한 절차만 적응적으로 수행해 토큰을 아끼자"였고, 이는 현행 계약과 충돌하지 않는다 — 난이도분석·사전조회는 LLM 에이전트가 아니라 **비-LLM 전처리 단계**로 흡수하면 되고, LLM 호출은 재작성(1회)+조건부 보정(1회)만 유지하면 된다. RAG 자체는 P0-5로 로드맵에 이미 있고, 지금은 정적 치환 사전(`app/easyread/style_rules.py`의 `DIFFICULT_WORD_REPLACEMENTS`)이 그 자리를 대체 중 — §121 "정적 치환 목록으로 품질 80% 확보, 벡터 검색은 그 다음" 결정과 일치. RAG 도입 시에도 검수는 별도 Agent가 아니라 기존 규칙기반 `check_style()` + 조건부 표적 보정 1회 구조를 유지하는 방향.

### 적응형 사전 주입 — 미션 EE/FF로 승격

RAG 이전에 먼저 할 수 있는 토큰 절감안(정적 리스트 전량 주입 → 입력 기반 필터링)은 조사 단계를 넘어 이번 스프린트 **미션 EE**(구현)·**미션 FF**(형태소 분석 개선 여지 조사)로 승격했다. 실측치·설계 근거·안전성 트레이드오프는 미션 EE 절 참조. 아래 두 항목만 여전히 이 부록(참고용, 이번 스프린트 범위 밖)에 남긴다:

- **RAG가 실제로 필요해지는 지점**(미션 EE/FF로도 해결되지 않는 부분): ① 사전 규모가 국립국어원 "다듬은 말"(18,329건) 수준으로 커져 활용형·유사어까지 의미 기반으로 잡아야 할 때, ② P0-5의 "용어 클릭 시 팝업 추천" UI처럼 사용자가 지정한 단어 하나를 실시간 조회해야 할 때(프롬프트 주입과 무관한 별도 조회) — 둘 다 지금 Lean MVP 스코프 밖.
- **참고(상충 레버)**: `app/llm/anthropic_provider.py`에 prompt caching(`cache_control`) 미적용 확인 — 시스템 프롬프트를 캐싱하면 "고정 전량 주입" 방식의 비용도 낮출 수 있으나, 입력 기반 필터링을 적용하면 시스템 프롬프트가 문서마다 달라져 캐시 히트율이 떨어지는 상충 관계가 생긴다. 두 레버를 동시에 쓸 거라면 "항상 포함 고정 블록(캐시 가능)"과 "문서별 가변 서브셋(캐시 불가)"을 분리하는 하이브리드 설계가 필요 — 이번 스프린트 범위 밖.
