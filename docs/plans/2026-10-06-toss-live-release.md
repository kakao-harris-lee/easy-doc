# Start 정기결제 실서비스 출시 점검

이 문서는 2026-10-06 구현 변경의 운영 적용 절차다. 코드를 적용했다는 사실과 실제 라이브 거래 검증은 구분한다. 후속 사용자 요청으로 구매·자동 청구를 차단한 운영 배포를 진행한다. 실제 라이브 청구와 일반 구매 개방에는 대상·금액·환불 범위의 별도 승인이 필요하다.

## 운영 설정

API와 worker는 같은 `EASYDOC_PAYMENT_PROVIDER` (`stub`, `toss_test`, `toss_live`) 및 해당 환경의 개별 연동 키 쌍을 사용한다. 라이브는 `live_ck_`/`live_sk_`, 테스트는 `test_ck_`/`test_sk_`만 허용한다. 키 접두사 검사는 동일 MID 계약 여부를 확인하지 않으므로 개발자센터에서 별도로 확인한다. 환경이 다른 기존 세션과 주문에 현재 환경의 키를 사용하지 않는다. 기존 테스트 기록을 라이브로 수정하지 않는다. 한 프로세스는 설정된 한 환경만 처리한다. 다른 환경의 보존 기록은 해당 환경의 자격증명을 가진 별도 유지보수 인스턴스에서 조회·환불·삭제해야 하며, 동시에 두 환경의 신규 청구를 열지 않는다. 기존 암호화 카드의 웹훅 매칭 지문은 해당 세션을 다음 저장할 때 생성되므로, 전환 전에 미정리 테스트 카드가 없는지 확인한다.

- `EASYDOC_PAYMENT_PURCHASE_ENABLED=false`: 일반 신규 구매 차단.
- `EASYDOC_PAYMENT_AUTO_CHARGE_ENABLED=false`: 새 갱신 청구 차단. 승인 조회·환불·카드 삭제와 이미 승인된 이용 기간은 유지한다.
- `EASYDOC_PAYMENT_ALLOWED_WORKSPACES`: 제한 공개 대상 UUID 목록. 일반 구매 차단 중 이 목록에 해당하는 작업공간은 구매 가능하므로 실제 승인 전에는 비워 둔다.
- 서비스 설정을 `stub`로 바꿔 청구를 차단하지 않는다. 라이브 호환 설정에서 위 두 청구 설정을 사용한다.
- 테스트용 E2E에서는 격리 DB와 `toss_test` 키를 사용하고 구매/자동 청구 설정을 명시적으로 켠다.

## 적용 순서

1. 현재 이미지·DB 마이그레이션 버전·API/worker 환경 일치 여부를 기록한다. 비밀키 값을 보고서에 쓰지 않는다.
2. 기존 `ops/postgres-backup.sh`로 백업하고, 별도 DB에 복원하여 마이그레이션을 리허설한다. 운영 DB에서 테스트/리허설을 하지 않는다.
3. 구매·자동 청구 차단, 허용 목록 비움 상태로 라이브 호환 API와 worker를 함께 배포한다. V45 적용 전 기존 worker를 중지한다. 이전 worker는 알림 환경 필터가 없으므로 마이그레이션 중 실행하지 않는다.
4. 웹훅 `PAYMENT_STATUS_CHANGED`, `BILLING_DELETED` 등록과 실제 공개 경로 도달을 확인한다. 웹훅 내용을 결제 승인 사실로 신뢰하지 않는다. `CANCEL_STATUS_CHANGED`는 이 국내 카드 흐름에 사용하지 않는다.
5. 사업자 표시, 유료 약관 시행일과 동의 문구, 거래 기록 보존·탈퇴 운영 경로, SMTP 발송과 고객지원 연락처를 최종 검토한다.
6. 대상 작업공간·금액·환불 범위를 별도 승인받은 후에만 제한 목록을 채우고 최초 실결제를 실행한다. 승인/취소 시각, 50크레딧 지급·회수, 원장 합계, 카드 교체, 해지, 환불 복구를 대조한다.
7. 승인 후 일반 구매와 자동 갱신을 단계적으로 열고 첫 정상 갱신까지 감시한다.

## 장애 대응

- 처리 중인 주문에서 새 구매를 반복하지 않는다. 관리자 결제 관리의 결과 재조회는 기존 주문 조회만 실행한다.
- 1시간 이상 미확정 주문을 확인하고, 14일 이상은 수동 확인 상태로 관리한다. 토스 조회·상점 거래 내역과 원장 확인 없이 새 강제 청구를 하지 않는다.
- 환불 결과 미확정 시 확보 크레딧은 유지한다. 완료/실패가 확정된 뒤 worker가 확정 회수/확보 해제를 한다.
- 카드 삭제 실패는 삭제 재처리로 복구한다. 카드 발급이 14일 이상 미확정이면 관리자 확인 상태로 두며, 상점에서 발급 상태를 확인한 뒤 갱신 중단 조치로 알려진 키를 삭제하고 새 등록을 진행한다. 원격 발급 응답을 잃어 키 자체를 모르는 경우에는 토스 상점 지원을 통해 미사용 키 정리를 확인한다. 이미 승인된 이용 기간을 소급 취소하지 않는다.
- 알림 작업은 `billing_notifications`에 중복 방지 키로 저장된다. SMTP는 멱등 발송을 지원하지 않으므로 발송 결과가 불명확하거나 프로세스가 발송 중 중단되면 `manual_review`로 남긴다. 자동 재발송하지 않는다. `failed`/`manual_review` 발송은 운영자가 메일 공급자 결과를 확인해야 한다.
- V45부터 알림의 결제 환경을 저장하고 현재 worker 환경과 일치하는 건만 발송한다. 테스트 메일에는 테스트 표시를 넣는다. 기존 기록의 환경을 확정할 수 없으면 미발송 상태를 수동 확인으로 격리한다. 관리자 알림 조회·전달 확인·재발송 화면은 아직 없으므로 해당 운영 기능은 후속 구현 대상이다.
- 라이브 거래 이후 테스트 전용 이미지로 롤백하지 않는다. 두 청구 설정을 끄고 라이브 데이터와 마이그레이션에 호환되는 수정 릴리스를 배포한다.

## 출시 전 남은 외부 확인

실제 상점 MID·키 쌍·계약, 공개 웹훅 전달, 백업 복원 및 운영 마이그레이션 리허설, 실제 SMTP 전달, 실제 청구/환불, 최종 유료 약관 시행·사업자 표시, 법정 보존과 개인정보 삭제 운영 확인은 로컬 테스트로 대신할 수 없다. 현재 라이브 결제 기록이 있는 계정의 삭제는 보존 자료가 연쇄 삭제되지 않도록 차단한다. 별도의 보존·비식별화 절차가 승인되기 전에는 고객 탈퇴 완료를 약속하지 않는다.
