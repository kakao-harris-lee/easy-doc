# 읽기 수준 선택·집중 검토 UX 추가 계획

작성일: 2026-09-24 · 상태: **ER-21~25 로컬 구현·무과금 검증 완료, ER-26·운영 출시 미완료**.

연결: [로드맵](2026-09-18-easy-read-improvement-roadmap.md) · [실행 계획](2026-09-18-easy-read-delivery-plan.md) · [구현 명세](2026-09-18-easy-read-implementation-spec.md) · [UX](2026-09-18-easy-read-ux-spec.md) · [검증·출시](2026-09-18-easy-read-validation-release.md).

## 1. 목표와 범위

두 개선을 독립적으로 추가한다.

1. 현행 초등학교 5~6학년 수준 변환을 기본으로 유지하면서, 더 짧고 직접적인 설명이 필요한 사용자가 초등학교 3~4학년 수준을 목표로 하는 `더 쉽게` 단계를 요청 전에 선택할 수 있게 한다.
2. 별도 하단 패널에서 모든 관계 체크리스트를 확인하게 하는 검토 흐름을 없애고, 실제로 확인이 필요한 신호만 변환 결과의 해당 문단에 표시한다.

`초등 3~4학년 수준`과 `초등 5~6학년 수준`은 작성 목표를 설명하는 이름이다. 특정 독자의 실제 이해를 보증하거나 교육 평가·인증을 뜻하지 않는다. 두 단계 모두 날짜·금액·대상·예외·AND/OR·공식 명칭을 보존하는 현행 기준을 공유한다.

2026-09-24에 계획을 추가한 뒤 ER-21~25의 Kotlin/React/계약/DB 변경을 로컬 구현했다. 운영 기능 활성화와 실제 유료 LLM 호출은 하지 않았다.

## 2. 읽기 수준 선택

### 2.1 사용자 선택

요청 wire 값은 다음 두 개로 고정한다.

| 값 | 화면 이름 | 동작 |
|---|---|---|
| `grade_5_6` | 기본 · 초등 5~6학년 수준 | 현행 프롬프트와 결과를 기본값으로 보존 |
| `grade_3_4` | 더 쉽게 · 초등 3~4학년 수준 | 쉬운 낱말, 한 문장 한 핵심, 명시적 주체, 필요한 짧은 설명과 제한적인 핵심 반복 허용 |

`reading_level`을 생략한 기존 JSON·multipart 요청과 기존 DB 행은 `grade_5_6`으로 해석한다. 선택은 변환 접수 전에 하며 변환 행에 영속화한다. 최초 변환, 조건부 보정, 문단 재변환은 모두 저장된 수준을 사용한다. 완료된 본문의 수준을 화면 토글로 바꾸지 않으며 다른 수준이 필요하면 새 변환을 요청한다.

`더 쉽게`는 문장을 무조건 잘게 자르거나 같은 뜻을 반복하는 모드가 아니다. 설명 때문에 결과가 길어질 수 있지만, 원문에 없는 조건·혜택·절차를 추가해서는 안 된다. 현행 기본 결과와 프롬프트 스냅샷은 별도 회귀 기준으로 고정한다.

### 2.2 비용과 길이 안내

고객 크레딧과 provider 실제 원가를 구분한다.

- **고객 크레딧 구현 결정(D11):** 현행 산식으로 구한 0.1크레딧 단위 수를 `baseUnits`라 할 때 `grade_3_4`는 `ceil(baseUnits × 1.2)` 단위를 예약·소비한다. 따라서 기본보다 최소 1.2배이며 0.1크레딧 올림 때문에 짧은 문서는 그보다 커질 수 있다.
- **provider 원가:** 입력·출력 토큰과 보정 여부에 따라 달라지므로 정확히 1.2배라고 약속하지 않는다. `reading_level`별 토큰·비용 스냅샷을 내부 원장에 남기고 별도로 평가한다.

선택 카드에는 변환 전에 `설명이 더 길어질 수 있어요`와 비용 차이를 함께 표시한다. 붙여넣기는 현재 글자 수로 계산한 정확한 필요 크레딧을 보여 준다. 파일은 추출 전 글자 수를 모르므로 `파일에서 추출한 글자 수 기준`이라는 산식과 배수를 먼저 보여 주고, 접수 응답에는 서버가 예약한 정확한 크레딧을 반환한다. 접수 뒤 실제 토큰 사용량을 이유로 추가 청구하지 않는다.

D11 산식은 계약·서버·프런트에 같은 공식으로 반영했다. 운영 노출 전에는 약관·가이드 문구와 토글 조합을 함께 확인한다.

### 2.3 길이·저장 경계

설명이 길어진 결과가 현행 20,000자 검수본 저장 상한을 넘으면 생성에는 성공했지만 저장하지 못하는 결함이 생길 수 있다. ER-21에서 수준별 입력 상한, 생성 출력 상한, 검수 저장 상한을 한 단위로 결정한다.

- 결과를 조용히 자르거나 `grade_5_6`으로 자동 대체하지 않는다.
- 접수 전에 안전한 입력 상한을 넘은 것을 알 수 있으면 변환을 시작하지 않고 이유를 안내한다.
- provider 호출 뒤 상한 위반이면 실패·크레딧 반환 규칙을 명시하고 부분 결과를 정상 결과로 저장하지 않는다.
- 1:N 문단 증가, 200단위 비교 상한, 내보내기와 직접 편집 저장을 함께 회귀 검증한다.

정확한 상한은 기존 공개 문서의 수준별 출력 팽창비를 측정한 뒤 정한다. 이 측정에 실제 provider를 쓰면 별도 승인과 달러 상한이 필요하다.

## 3. 검토가 필요한 문단만 표시

### 3.1 신호 정책

현행 검수 분석은 누락 신호와 별도로 관계 체크리스트 5종을 항상 만든다. 새 흐름에서는 고정 5종 생성을 폐지하고, 실제 규칙이 발견한 고신뢰 신호만 `needs_review` 항목으로 반환한다.

자동 검사 결과가 0건이면 화면에 검토 마크를 표시하지 않는다. 이를 `정확함`, `검수 완료`, `모든 의미 보존`으로 표현하지 않고 필요하면 `자동 검사에서 추가 표시를 찾지 못했습니다` 정도로 제한한다.

### 3.2 결과 문단 통합

계약에 이미 있는 `ReviewItem.easy_unit_indexes`를 이용해 미확인 항목을 결과 문단에 연결한다.

- 대응표가 있고 200단위 이하인 일반 경로는 문단별 결과를 기본 화면으로 사용한다. 별도 `문단별 상세 비교` 토글과 모든 문단의 `대응 확인/추정` 배지는 제거한다.
- 신호가 연결된 문단만 경고 테두리와 `검토 필요 N개` 마크를 표시한다. 여러 항목은 한 문단 안에서 묶고 `원문과 비교`와 `이 문단 확인했어요`를 우선 행동으로 둔다.
- 문단 확인은 현재 assessment·content/review revision과 item ID 집합을 받는 트랜잭션 batch/CAS로 처리한다. 일부만 저장된 상태를 만들지 않는다. 항목별 `해당 없음`과 사유 입력은 보조 펼침 영역으로 낮춘다.
- 확인한 마크는 결과에서 사라진다. 잘못 누른 경우 접힌 `확인 완료` 또는 검수 이력에서 다시 열 수 있다.
- 편집 중에는 문단 색인이 낡으므로 마크를 숨기거나 비활성화하고 `저장하면 검토할 부분을 다시 찾습니다`를 표시한다. 저장 후 새 `content_revision`을 자동 분석한다.

누락된 사실은 결과에 대응 문단이 없어 `easy_unit_indexes`가 비어 있을 수 있다. 이런 항목을 숨기거나 가까운 문단에 추측으로 붙이지 않고 결과 상단에 `결과에서 위치를 찾지 못한 검토 항목 N개`로 모은다. 대응표 없음, 200단위 초과, 분석 제한 상태는 기존 전체 textarea와 같은 상단 요약으로 fallback한다.

기존 item 확인·재열기·해당 없음 이력과 소유권·만료·암호화·CAS 규칙은 유지한다. 새 흐름이 안정화될 때까지 별도 토글로 이전 패널로 롤백할 수 있게 하고, 제한 파일럿 뒤 이전 패널을 단계적으로 제거한다.

## 4. 계약·저장·관측 변경 후보

구현 PR에서 `contracts/easy-doc-v1.yaml`, Kotlin 계약 테스트/DTO, `frontend/src/api/`를 같은 변경 단위로 맞춘다.

- `DocumentTextRequest`와 `DocumentFileRequest`에 optional `reading_level`을 추가한다. multipart 문자열도 JSON과 같은 enum·422 규칙을 쓴다.
- `DocumentCreatedResponse`와 `ConversionResponse`에 선택 수준을 반환하고, 접수 응답에는 서버가 실제 예약한 `reserved_credits`를 포함한다.
- `conversions.reading_level`은 `NOT NULL DEFAULT 'grade_5_6'`와 CHECK를 갖는다. worker 작업 입력·조회·재변환에 전달한다.
- 삭제 뒤에도 비용 원장이 남는 현행 경계에 맞춰 `llm_calls`에는 수준 스냅샷을 둔다. 고객 크레딧과 provider 비용을 같은 값으로 해석하지 않는다.
- 공통 사실 보존 프롬프트와 수준별 표현 정책을 분리한다. 변환·보정·judge·프롬프트 스냅샷·골든 fixture가 같은 수준을 사용한다.
- 검수 분석기는 고정 관계 항목 대신 근거가 있는 신호만 만든다. 기존 item 단건 API는 호환을 위해 유지하고 문단 단위 확인을 위한 batch/CAS를 additive로 추가한다.

기능 토글은 `extra-easy`와 `focused-review`를 분리하고 기본 OFF로 둔다. 하나의 출시 지연이 다른 개선을 막지 않는다. 토글 OFF에서는 현행 `grade_5_6` 변환과 기존 검수 패널이 그대로 동작한다.

## 6. 인수 기준

| ID | 시나리오 | 통과 조건 |
|---|---|---|
| AC-R8-a | 수준 생략·기본 선택·더 쉽게 선택 후 변환/재조회/문단 재변환 | 생략과 기본은 현행 결과 정책, 더 쉽게는 저장 수준을 모든 호출이 사용하며 새로고침 뒤에도 유지. 서로 다른 수준이 한 변환에 섞이지 않음 |
| AC-R8-b | 두 선택 카드와 붙여넣기/파일 비용·장문 경계 | 요청 전에 비용 차이와 장문 가능성을 확인. 서버 예약액·402·반환이 D11과 일치하고 사후 변동 청구·절단·자동 기본 fallback 없음 |
| AC-R8-c | 같은 개발/보류 표본을 두 수준으로 생성·대조 | `grade_3_4`가 정의한 표현 기준을 충족하고 사실·조건 오류가 늘지 않음. 출력 팽창·토큰·보정·지연·비용을 수준별 기록하며 실제 독해 보증으로 과장하지 않음 |
| AC-R1-e | 신호 0건, 한 문단 1건/여러 건, 확인·재열기 | 0건이면 마크 없음. 필요한 문단만 한 마크로 묶이고 원문 대조 후 한 번에 확인, 확인 즉시 마크 제거, 이력에서 복구 가능 |
| AC-R1-f | 편집 중·저장 후·stale·충돌·위치 없음·지도 없음·201단위 | 낡은 마크 오적용 없음. 새 revision 재분석, CAS 충돌 복구, 위치 없는 실제 신호의 상단 요약, 전체 편집 fallback에서 내용·확인 상태 손실 없음 |

자동 검사의 정밀도는 개발 표본과 독립 보류 표본에서 `표시된 항목 중 실제 확인 가치가 있는 비율`을 우선 본다. 항목 수 감소만으로 품질 개선을 주장하지 않으며 놓친 중요 조건은 별도 실패로 기록한다.

2026-09-25 재개 리뷰에서는 서로 다른 문단의 반대 표현을 비교하는 오탐을 수정했다. 관계 비교는 양쪽이 한 문단이거나 기존 사실 앵커가 단일 원문 문단과 연결한 경우로 제한한다. 추정 대응과 여러 원문을 병합한 문단은 관계 반전의 근거로 쓰지 않으며, 관계 표현이 있어도 대응 근거가 부족하면 `mapping_unavailable`로 분석 제한을 알린다. 제한 응답은 화면에서 전체 글 검토로 전환하고, 분석 요청 실패는 재시도할 수 있다. 확인 충돌 뒤 다른 본문 버전의 분석이 이미 `ready`여도 최신 본문을 불러오는 절차를 유지한다. 이 규칙의 실제 정밀도·재현율 평가는 계속 ER-26에 남는다.

## 7. 검증·비용·중단 경계

구현 변경마다 최종 diff 기준으로 다음 기존 검증을 사용한다.

- Backend: `cd backend-kotlin && ./gradlew build`
- Frontend: `cd frontend && npm run check && npm run test -- --run && npm run build`
- Integration: `docker compose config`
- 관련 기존 Playwright: 수준 선택·개인정보 재전송·문단 검토·충돌·긴 문서 fallback
