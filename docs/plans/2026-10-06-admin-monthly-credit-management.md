# 관리자 월별 결제·크레딧 관리

**상태(2026-10-06): 구현·최종 필수 검증·운영 DB V40 적용·서비스 배포·공개 관리자 화면 검증 완료.**

## 목적과 지표

관리 단위는 작업공간이다. 이메일은 검색 기준이며 결제·크레딧 계정을 사용자별로 합치지 않는다.
달력 월 조회와 기존 구독 결제주기는 별개이며, 주기 종료 초기화·이월 없음 정책은 유지한다.

| 화면 지표 | 의미 |
| --- | --- |
| 현재 사용 가능 | 보유 − 처리 중 확보 |
| 현재 보유 | 아직 소비되지 않은 잔액. 확보된 몫 포함 |
| 처리 중 확보 | 진행 중 작업이 임시로 확보한 크레딧 |
| 선택 월 사용 | 해당 월 `consume` 거래의 실제 잔액 차감 합계 |
| 변환 문서 수 | 완료 변환·보정·재변환 호출의 고유 문서 수 |
| AI 처리 원가 | 공급자 USD 추정 원가. 고객 결제 원화와 구분 |

100크레딧 중 10을 확보하면 보유 100·확보 10·사용 가능 90이다. 성공 시 보유 90·확보 0이 되고 사용 10을 기록한다. 실패 시 확보만 해제해 보유 100·사용 가능 100으로 돌아온다. 예약·해제를 사용량에 더하지 않는다.

## 구현과 인터페이스

- 목록은 조회 월, 현재 사용 가능, 선택 월 사용·결제·환불을 구분한다. 기존 `month_*` 응답은 현재 월 의미를 유지하며 `selected_month`를 추가한다. 목록의 `timezone`·`current_month`는 서버 기준 월 선택에 사용한다.
- `GET /admin/workspaces/{workspace_id}/monthly-summary?month=YYYY-MM`: 현재 계정·주기·수정 버전, 월 결산, 사용량, 실제·테스트 결제 합계, 대사 경고.
- `GET .../monthly-history?year=YYYY`: 해당 연도 월별 비교. 현재 연도 미래 월은 제외.
- `GET .../credit-transactions?month=YYYY-MM&kind=...&page=1&size=20`: 월·종류별 원장. 지급·소멸 및 변경 전후 주기 메타데이터 포함.
- `GET .../payments?month=YYYY-MM&page=1&size=20`: 결제·환불 이벤트와 실패·처리 중 결제/환불 시도. 시도는 합계 제외. 발생일 미상 이벤트는 모든 월 페이지에 표시하되 월 합계 제외.
- 페이지는 기본 20·최대 100건, 시각과 ID로 안정적으로 정렬한다. 월 생략은 서버 현재 월이며 미래 월은 422다. 모든 새 경로는 관리자 인증·감사·no-store 응답 대상이다.
- 크레딧 조정은 필수 메모, 요청 UUID, 확인한 잔액·확보·revision을 받는다. 재전송은 중복 반영하지 않고 동시 변경은 409로 다시 확인한다. 회수는 확보분을 침범하지 못하며 과거 원장은 수정하지 않는다.

정확한 타입·필수 필드는 `contracts/easy-doc-v1.yaml`을 기준으로 한다. API는 문서 본문·프롬프트·암호화 결제 payload를 반환하지 않는다.

## 원장·월 경계·과거 자료

- 기존 `UsageProperties` 시간대(기본 `Asia/Seoul`)의 월초 이상·다음 월초 미만으로 집계한다. 소비는 확정 시각의 월에 기록한다.
- 월말 = 월초 + 지급 − 사용 − 소멸 + 조정 + 분해 불가 주기 순증감. 현재 월은 현재까지 결산이다. 현재 계정과 과거 월말을 별도로 표시한다.
- 모든 소비 사유를 포함하고 공급자 비용 미상 건수를 공개한다. 소비 원장 없는 과거 LLM 기반 추정은 별도 값이며 실제 소비나 잔액 식에 합산하지 않는다.
- V40은 계정 revision, 주기 변경 전후 스냅샷 및 지급·소멸·조정 세부, 결제 이벤트 원장, 조정 중복 방지 원장을 추가한다. 잔액 계산의 기준은 기존 계정과 크레딧 원장으로 유지한다.
- 계정 행의 모든 변경마다 revision을 증가시킨다. 조정은 사용자(소유자·관리자 ID 순서) → 작업공간 → 크레딧 계정 순서로 잠가 삭제와의 잠금 순서를 맞춘다. 동일 요청 재전송을 먼저 확인한 뒤 확인 버전을 검사하므로, 잔액이 원래 값으로 돌아온 경우에도 오래된 조정을 거절한다.
- 계정 변경 스냅샷은 작업공간별 최근 1건만 보관하고 같은 DB 트랜잭션 ID에서만 주기 원장에 사용한다. 독립 잔액이나 별도 청구 원장이 아니다. 스냅샷 FK는 이미 잠근 크레딧 계정을 참조해, 정산 중 작업공간 잠금을 추가로 잡지 않도록 한다.
- 신규 주기 원장 세부 순합은 기존 balance_delta와 일치해야 한다. 과거 주기는 확실한 분해 근거가 없으면 순변동과 경고만 표시한다.
- 음수 잔액을 주기 교체로 해소한 금액은 신규 지급·소멸 대신 조정으로 분리한다. 지급과 소멸이 같아 순변동이 0이어도 두 수량을 보존한다.
- 과거 결제의 created_at은 주문 생성 시각이므로 확정 월로 추정하지 않는다. 마이그레이션 결제·누적 환불은 발생일 미상으로 이관한다. 신규 이벤트는 확정 기록 시각을 사용한다.
- 결제 이벤트는 확정 결제 1건과 누적 환불액의 증가분을 추가 기록한다. 중복 키는 작업공간·원 결제·이벤트 종류/누적 환불액을 포함해 다른 작업공간의 같은 주문 UUID와 충돌하지 않는다. `stub`·`toss_test`는 테스트 금액으로 분리한다.
- 결제 연결은 실제 업무 식별자로만 연결한다. 날짜·금액 유사성으로 연결하지 않는다. 신규 확정 결제의 크레딧 연결 누락은 경고하며 무료 지급은 누락으로 간주하지 않는다.
- 보고서는 읽기 전용 repeatable-read 트랜잭션으로 계정·원장 대사 중 동시 작업의 중간 상태를 섞지 않는다. 기존 음수 잔액과 불일치를 숨기지 않는다.

## 검증과 배포

기존 명령 `./gradlew build`, `npm run check && npm run test -- --run && npm run build`, `docker compose config`를 최종 diff 기준으로 실행한다. 무거운 빌드는 Gradle 동시 작업 없음·가용 메모리 6GB 이상 확인 후 호스트에서 하나씩 실행한다. 실제 유료 LLM 또는 결제 공급자 호출을 검증에 사용하지 않는다.

회귀 검증은 한국 시간 월 경계·윤년·연말, 월간 예약 이월과 실제 소비, 그림 제안 소비, 과거 주기 순변동, 원장 불일치, 50건 초과 거래 페이지, 과거 결제의 이번 달 부분 환불, 테스트 결제·미상 시각·실패·진행 중 시도, 관리자 HTTP 401/403 및 422 검증, 조정 재시도·경쟁 상태·확보분 회수를 포함한다.

배포 시 스키마·기록 수집을 먼저 적용한 다음 API·화면을 전환한다. 2026-10-06 사용자 배포 승인에 따라 아래 운영 적용 기록까지 완료했다. 정확히 복원하지 못하는 과거 내역은 화면 경고와 미상 금액으로 유지한다.

### 적용 순서와 운영 확인

1. 최종 변경에 대한 필수 빌드·테스트·계약 검증과 리뷰를 완료한다. 운영 적용 전에 기존 백업·복구 절차로 복구 가능 상태를 준비한다.
2. V40을 먼저 적용한다. 기존 계정·거래 값은 변경하지 않고, 과거 확정 결제와 누적 환불은 시각 미상 이벤트로 이관한다. 이후 결제 상태 기록은 트리거가 신규 이벤트로 수집한다.
3. 백엔드·worker를 새 이미지로 교체해 주기 지급과 결제의 명시적 연결을 시작한다. 이전 이미지가 남은 전환 구간의 결제는 이벤트가 있어도 크레딧 연결이 비어 있을 수 있으므로 대사 경고를 확인한다.
4. 같은 릴리스의 프런트엔드를 전환한다. 조정 API에 필수 확인값이 추가되므로 관리자 화면을 새로 열어야 한다. 전환 중 오래된 화면에서 보내는 조정은 필수 필드 검증으로 거절되며, 안전 확인을 우회하는 자동 호환 경로는 두지 않는다.
5. 관리자 권한으로 현재 월·과거 월·연간 비교, 20건 초과 결제 및 50건 초과 원장 페이지, 실제/테스트 금액 구분, 메모와 사전 확인이 있는 조정을 확인한다. 원장과 계정 대사·신규 결제 연결·시각 미상 경고를 관찰한다.

과거 월 선택은 조회 조건이다. 조정은 항상 현재 시각의 새 거래이며 과거 월 거래를 덮어쓰지 않는다. 이번 작업은 구독 재시도 정책·상용 결제 활성화·유료 모델 검증의 완료 근거가 아니다.
