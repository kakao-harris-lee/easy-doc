# 100자 단위 소수 크레딧

2026-09-21 사용자 결정: 100자만 변환해도 1크레딧을 차감하던 산식을 100자당 0.1크레딧으로 바꾼다. 1크레딧의 분량은 여전히 공백 포함 원문 1,000자다.

## 산식과 적용 범위

필요 크레딧은 `ceil(char_count / 100) / 10`이다. 0자는 0, 1~100자는 0.1, 101자는 0.2, 1,000자는 1, 1,001자는 1.1이다. 원문 문자 수를 세는 기존 규칙은 그대로 쓰며 최초 변환·문단 재변환·행동 안내에 동일하게 적용한다.

예약 시점에 양을 확정한다. 소비·실패 반환은 그 예약량으로 처리하며 완료 시점의 산식으로 다시 계산하지 않는다. D03의 유효 후보 제공 후 소비, 제공 전 실패·stale·만료 반환 정책과 D04의 provider 시작 작업 3회 상한은 유지한다. 호출 시작 후 실패는 크레딧을 돌려줘도 시도 횟수에 포함한다.

## 수치 보존과 계약

잔액·예약·거래 증감·주기 제공량·작업별 예약량을 정확한 십진수로 처리한다. 부동소수로 정산하지 않는다. DB 기존 값 5는 5.0으로 표현될 뿐 0.5나 50으로 환산하지 않는다. 과거 원장·플랜의 제공량·결제 금액은 재계산하지 않는다. V15 이전 사용량의 역사적 추정 산식도 유지한다.

API 크레딧 수치는 JSON number와 0.1 배수 계약을 쓴다. 잔액·증감은 기존처럼 음수를 허용하고, 예약·필요량은 음수가 될 수 없다. 크레딧 HTTP 헤더는 십진수 문자열이며 클라이언트는 정수 파서로 소수를 버리지 않는다. 호출 횟수·문자 수·원화 가격은 정수로 유지한다.

## 검증

- 0/1/99/100/101/999/1,000/1,001자와 입력 상한에서 정확한 양을 산출한다.
- 잔액 0.1에서 0.1 예약·소비, 잔액 0에서 402, 실패 시 정확히 0.1 반환을 확인한다.
- 0.1을 여러 번 정산해도 잔액·예약과 원장 합계가 정확히 일치한다.
- 변경 전 잔액·원장·예약이 있는 DB를 마이그레이션해 수치가 그대로 유지되고 기존 작업이 저장된 예약량으로 완료/반환되는지 확인한다.
- 주기 갱신·관리자 조정·사용량 합계·행동 안내와 브라우저의 소수 잔액/필요량/402 안내를 확인한다.

## 로컬 완료 기록 — 2026-09-21

- Kotlin `./gradlew build --no-daemon` 통과: core 719, application 573, infrastructure 1,046, API 717, worker 63, 합계 3,118개 테스트 성공.
- React check·727개 테스트·build 통과. 계약은 `2.41.0`으로 갱신했다.
- 실제 Kotlin API·PostgreSQL·fake worker의 로컬 Playwright 5개 통과: E21 소수 예약·조회, ER-07 두 흐름, E22 0.1·0.9 차감과 추가 0.1 요청의 402, E23 기존 50크레딧 플랜 전량 소비.
- `docker compose config --quiet`와 whitespace 검사 통과. 프런트·계약 및 백엔드·마이그레이션 독립 리뷰에서 프로덕션 결함은 발견되지 않았다. 리뷰에서 발견한 테스트 허점은 FK 오류 대신 SQLSTATE `23514`와 해당 0.1 단위 제약 이름을 확인하도록 보완했다.
- V30의 기존 행동 안내 예약 2가 V31 뒤에도 2로 남고, 삭제 시 정확히 -2 반환되는 회귀를 검증했다.

원격 CI·병합·운영 배포는 별도 증거로 확인한다. R2 모델 평가 20회·예상 US$2.880730 결과는 [평가 보고서](../reports/2026-09-21-r2-model-evaluation.md)에 있으며 후보 검증 거절 9건으로 출시 기준을 충족하지 못했다.

## 배포 절차

이 문서는 배포 실행 기록이 아니다. 기존 API·worker는 정수 reader를 사용하므로 소수 값이 생긴 DB에서 구버전과 신버전을 혼용하지 않는다. 접수를 잠시 중단하고 실행 중 요청·worker를 정리한 뒤, DB migration과 API·worker 전환을 조율한다. 예약이 남은 작업은 새 코드가 저장된 양으로 정산할 수 있어야 한다. 프런트는 소수 계약을 읽는 버전으로 맞춘다.

전환 후 100자 문서의 예약·소비·실패 반환과 계정/원장 합계를 확인한다. 소수 거래가 생긴 뒤 정수 컬럼이나 구버전 애플리케이션으로 단순 롤백하지 않는다. 배포 전 백업과 복구 계획, 실제 커밋·schema·토글 상태를 별도 기록한다.
