# 쉬운글 품질 개선 로드맵

작성일: 2026-09-18 · 상태: R0·R1 로컬 구현 및 fake E2E 완료 / 기본 OFF·미배포.

이 문서와 연결 명세는 이번 조사에서 제안한 개선의 설계 기준이다. R0·R1은 Kotlin/React와 `contracts/easy-doc-v1.yaml`에 함께 반영했으며 기능 토글 기본값은 OFF다. R2 이후의 API·DB·화면은 해당 구현 변경에서 계약과 소비자를 함께 변경할 때 적용한다.

## 2. 목표와 유지할 원칙

목표는 공공·복지 안내문의 조건을 정확하게 전달하고, 독자가 할 일을 찾게 하며, 실무자의 검수 시간을 줄이는 것이다.

- 일반적인 초등학교 5~6학년 수준의 어휘·문장을 기본 목표로 유지한다. 성인 독자를 어린이처럼 대하지 않는다.
- 중요한 날짜·공식 명칭·대상·예외·AND/OR 관계를 가독성 때문에 바꾸지 않는다.
- AI 초안과 담당자 수정본을 구분한다. 자동 검사와 담당자 확인을 동일한 인증으로 표시하지 않는다.
- 초기 기능은 기존 검수 화면 안에서 제공한다. 새 편집기·별도 서비스·네이티브 플러그인은 만들지 않는다.
- 원문과 파생 결과의 소유권·암호화·보존 만료 정책을 함께 적용한다. 공유 링크와 다중 승인자는 이번 범위 밖이다.
- 유료 실험은 별도 승인과 달러 상한이 있을 때만 실행한다. 문서 작성으로 승인된 것으로 해석하지 않는다.
- 사람의 독해 시험은 효과 주장의 근거를 얻는 절차다. 모든 표현 개선을 막는 선행조건은 아니다.

## 3. 현재 코드에서 확인한 기반

| 확인 대상 | 현재 관찰 | 설계에 주는 제약 |
|---|---|---|
| `ConvertDocumentUseCase` | 최초 생성 + 필요한 경우 보정 1회 | 기존 변환에 새 평가 호출을 상시 추가하지 않음 |
| `FactPreservation.kt` | 값·날짜·서류명 등의 누락 진단 | 의미 관계 전체의 통과 판정으로 확장 해석하지 않음 |
| `ConversionReviewService` | 초안 보존, 수정본 정규화·암호화 저장 | 저장 버전과 파생 결과 무효화 추가 필요 |
| 재변환 요청의 `easy_text_fingerprint` | 서버는 되울리며 클라이언트가 변경 여부 확인 | 서버 동시성 제어 토큰으로 재사용 불가 |
| `segment_map`, `ReviewEditor` | 대응 지도가 있으며 화면의 문단 비교 상한은 200단위 | 지도 없는 문서·긴 문서에서도 일반 검수 제공 |
| `SourceUnitKind` | body/table_cell/list_item, 행·열 좌표 없음 | 표 관계 기능 전에 추출 구조 확장이 필요 |

확인 범위는 저장소의 관련 코드·계약이다. 운영 배포 상태를 검증했다는 뜻은 아니다. 파일별 연결점은 구현 명세 §2에 있다.

## 4. 단계별 로드맵

순서는 R0 → R1 → R2 → R3 → R4 → R5 → R6 → R7이다. R1의 최소 확인 기록·본문 버전은 뒤 단계가 의존하는 기반이므로 R5의 이력 확장보다 먼저 만든다. 일정은 고정하지 않고 아래 규모를 PR 분할 기준으로 사용한다.

| 단계 | 사용자 결과 | 필수 범위 | 완료·다음 단계 기준 | 규모 예상 |
|---|---|---|---|---|
| R0 기준선·예시 | 어떤 문제를 줄일지 공유 | 공개 문서 10건, 오류 유형, 기준 질문, 화면 예시 | 기존 결과와 기대 차이·출처 기록. 모델 호출 없이 시작 가능 | 작음 |
| R1 조건·예외 검수 지원 | 확인할 부분을 원문과 대조하고 확인 상태 저장 | 본문 버전, 누락 후보, 관계 확인 체크리스트, 만료·충돌 처리 | AC-R1 통과, 자동 검사 0건을 의미 보존 완료로 표시하지 않음 | 중간 |
| R2 행동 중심 안내 | 신청·제출 절차를 별도 초안으로 정리 | 명시적 생성, 근거 연결, 편집, 기한·예외 표시, 별도 TXT 출력 | AC-R2 통과, 원문에 없는 안내 추가 없음, 비용 정책 반영 | 큼 |
| R3 문맥 설명 강화 | 공식 명칭을 유지한 이해 가능한 설명 | 기존 생성 지침·사전 참고 개선, 첫 등장 설명, 공식 이름 보존 | AC-R3 통과, 의미 오류 증가 없음, 별도 호출 미추가 | 중간 |
| R4 표·수치 관계 | 적용 대상·단위·각주를 함께 이해 | DOCX/HWPX 단순 표 구조 추출, 출처·관계 표시, 미지원 처리 | AC-R4 통과, 복합 표·PDF에 검증되지 않은 좌표를 붙이지 않음 | 큼 |
| R5 검수 이력 확장 | 누가 어떤 본문을 확인했는지 재확인 | 버전별 확인 이벤트·이전 상태 조회·기록 내려받기 | AC-R5 통과, 이전 확인이 최신 본문으로 승계되지 않음 | 중간 |
| R6 설명량 선택 | 본문을 유지하면서 필요한 설명을 더 보기 | R3의 근거 있는 용어 설명 접기·펼치기 | AC-R6 통과, 필수 조건이 접힌 설명에만 존재하지 않음 | 작음~중간 |
| R7 그림·배치 | 절차·장소를 시각적으로 이해 | 권리 확인된 소수 그림, 텍스트 대안, 미리보기 | AC-R7 통과, 그림 의미·출력 지원 검증 | 탐색 후 재산정 |

‘규모’는 구현·검수의 상대적 추정이다. R0 완료 시 구현자가 PR별 예상 작업일과 가용 인력을 실행 계획에 기록한다. R4·R7은 입력·출력 실험의 영향이 커 정확한 일정은 해당 단계 착수 전 산정한다.

## 5. 출시 묶음

| 묶음 | 포함 | 독립적인 가치 | 출시 범위 |
|---|---|---|---|
| M1 검수 지원 | R0+R1 | 현재 본문에 대해 무엇을 확인했는지 구분 | 내부 확인 → 제한 파일럿 → 일반 노출 |
| M2 이해·행동 | R2+R3 | 행동 안내와 공식 용어 설명 | R2·R3는 각각 토글·평가하여 개별 출시 가능 |
| M3 기관 실무 | R4+R5 | 표 관계 확인과 검수 기록 | 지원 표 유형과 보존 기간을 명시 |
| M4 읽기 경험 | R6+R7 | 선택 설명과 시각적 안내 | R6 먼저, R7은 별도 평가 후 |

각 단계는 앞 단계의 기본 저장·보안·인수 기준에 의존한다. 사람 모집이나 R7 디자인 작업이 지연돼도 이미 검증된 R1/R3 개선을 묶어서 기다리지 않는다. R3를 별도 출시할 때도 실험 데이터와 프롬프트 버전을 분리한다.

현재 M1은 로컬 구현 게이트까지 통과했다. Kotlin 전체 빌드, React check·689개 테스트·build, Compose 구성, fake LLM 기반 E13 브라우저 흐름을 확인했다. 제한 파일럿·원격 CI·배포·실사용자 평가는 남아 있으므로 일반 노출 완료로 표시하지 않는다.

## 7. 추적과 완료 정의

작업 ID는 실행 계획의 `ER-*`, 요구사항은 구현 명세의 `REQ-*`, 인수 기준은 검증 계획의 `AC-*`를 사용한다. PR마다 세 ID와 검증 증거를 연결한다.

완료는 구현·계약/소비자 일치·필수 검사·UX 예외 경로·토글 OFF 회귀·운영 확인·공개 가이드까지 충족한 상태다. 문서 작성, fake 성공, 유료 품질 평가, 원격 CI, 배포 완료는 각각 따로 기록한다.
