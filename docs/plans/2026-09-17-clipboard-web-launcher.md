# 클립보드 웹 연동과 Windows 트레이 창

- 작성일: 2026-09-17
- 상태: 계획. 웹 기능과 Windows 앱은 아직 구현하지 않았다.
- 워크트리 표시 이름: `easy-doc-clipboard-web`
- 목표: Word, 아래한글, 메일 등에서 복사한 일반 텍스트를 작은 웹 창에서 검토하고 다시 붙여넣는다.

## 1. 선택한 구조

Windows는 트레이, 전역 단축키, 작은 WebView2 창의 표시·숨김만 담당한다. 입력, 로그인, 변환, 검토 정보, 비교, 수정, 결과 복사, 이력과 이용량은 기존 React 웹과 Kotlin 서버를 재사용한다.

| 후보 | 개발 범위 | 판단 |
|---|---|---|
| 기본 브라우저 열기 | 트레이와 단축키만 필요 | 가장 저렴하지만 탭 전환과 반복 호출 시 탭 증가가 생김 |
| 트레이 위 작은 웹 창 | 위 기능에 WebView2와 창 위치·수명 관리 추가 | 기본안. 편집기 옆에서 작업하고 같은 창의 상태를 유지 |
| 네이티브 편집창과 클립보드 자동 전송 | 별도 UI, 인증 연결, 전송과 적용 제어 필요 | 첫 버전에서 제외 |

작은 웹 창의 추가 비용은 수용하되 별도 네이티브 편집 화면이나 로컬 서버는 만들지 않는다. 기본 브라우저로도 같은 웹 경로를 사용할 수 있지만 서로 로그인·편집 상태가 자동 공유된다고 가정하지 않는다.

## 2. 사용자 흐름

1. 원래 편집기에서 문장 또는 문단을 선택하고 `Ctrl+C`로 복사한다.
2. 트레이 클릭 또는 전역 단축키로 작은 웹 창을 연다.
3. 최초에는 웹 계정으로 로그인하고, 입력란에 `Ctrl+V`로 붙여넣는다.
4. 사용자가 변환을 요청한다. 기존 개인정보 확인, 이용량, 처리 상태와 오류 흐름을 적용한다.
5. 같은 창에서 원문과 결과를 비교하고 수정한다.
6. 결과 복사를 누르고 창을 숨긴 뒤 원래 편집기에 `Ctrl+V`로 붙여넣는다.

첫 버전은 웹 창에서 사용자가 한 번 붙여넣는 동작을 허용한다. 앱 호출만으로 본문을 자동 수집하거나 변환하지 않는다. 복사 대상은 현재 클립보드 내용이므로 다른 내용을 복사했다면 입력 전에 원래 문장을 다시 복사한다.

## 3. 작은 웹 창 UX

- 트레이 클릭은 같은 창을 표시하거나 숨긴다. 단축키는 창을 표시하고 활성화한다. 새 창을 계속 만들지 않는다.
- 최초 표시 크기는 약 460 x 640 DIP를 기준으로 한다. 실제 모니터 작업 영역과 배율에 맞춰 줄이고, 창 크기 조절을 허용한다.
- 트레이 위치를 얻을 수 있으면 아이콘 위쪽의 작업 영역 안에 배치한다. 숨겨진 아이콘 등으로 위치 확인이 어려우면 해당 모니터 작업 영역 우측 하단에 배치한다.
- 첫 버전은 표준 창 테두리와 제목 표시줄을 쓴다. 긴 문서는 창을 확대해 같은 웹 화면에서 비교한다.
- 좁은 창에서는 입력 화면과 결과 화면을 순차적으로 보여주고, 결과의 원문/변환문은 기존 반응형 탭 패턴을 재사용한다. 큰 랜딩 화면이나 파일 업로드 선택을 먼저 보여주지 않는다.
- 최초 빈 입력 화면에만 자동 초점을 둔다. 다시 열 때는 작성 중인 입력, 결과, 스크롤과 선택 상태를 유지한다.
- 닫기 버튼은 창을 숨기며 앱 종료는 트레이 메뉴에서 한다. `Esc`는 웹의 메뉴·대화상자가 먼저 처리하고, 처리되지 않았을 때 창을 숨기는 동작을 검증한다.
- 포커스 이탈만으로 자동 숨김은 하지 않는다. 글을 선택하거나 로그인·권한 창을 다루다가 작업창이 사라지는 문제를 피하고 창 제어를 단순하게 유지한다.
- 숨길 때 WebView를 종료하거나 새로고침하지 않는다. 앱 자체 종료 시 입력 손실 가능성을 알리고, 프로세스 재시작 뒤 미저장 본문 복구까지 보장하지 않는다.
- 복사 성공 표시 후 사용자가 창을 숨긴다. 자동 붙여넣기, 원래 편집창 강제 활성화, 복사 후 자동 숨김용 네이티브 메시지 연결은 제외한다.

## 4. 기존 웹 재사용과 변경

현재 확인한 지점:

- `frontend/src/pages/UploadPage.tsx`: 텍스트 모드, 입력 검증, 제출과 개인정보 확인.
- `frontend/src/api/client.ts`: `createDocumentFromText`가 `POST /documents`로 본문을 보내고 접수 결과를 받음.
- `frontend/src/pages/ConversionPage.tsx`, `frontend/src/components/ReviewEditor.tsx`: 처리 상태, 원문 조회, 비교·수정 및 현재 수정 중 본문(`draft`).
- `contracts/easy-doc-v1.yaml`: 문서 생성은 저장과 변환 요청을 수반하고 기존 크레딧 정책을 적용함.

추가 작업:

1. 제안 경로 `/quick`을 만든다. 기존 인증과 텍스트 입력을 재사용하는 간결한 진입 화면으로 두며, 비교·편집기를 새로 복제하지 않는다.
2. 작은 화면에서는 계정과 필수 명령을 남긴 간결한 레이아웃을 사용한다. 빠른 입력에서 결과 화면으로 이동해도 이 레이아웃을 유지한다.
3. 로그인 후 `/quick`으로 복귀하고 입력란에 붙여넣을 수 있게 한다. 로그인 중 URL이나 임시 파일로 문장을 전달하지 않는다.
4. 결과 복사 명령은 클릭 시점의 최신 `draft`를 `navigator.clipboard.writeText`로 복사한다. 서버에 저장된 과거 결과를 복사하거나 복사를 저장 완료로 취급하지 않는다.
5. Clipboard API 호출이 성공한 뒤 복사 성공을 표시한다. 거부 시 결과를 선택하고 수동 복사할 수 있어야 한다.

일반 `Ctrl+V` 입력을 기본으로 하고 자동 읽기나 클립보드 감시는 넣지 않는다. Clipboard API는 HTTPS와 사용자 동작·권한 조건이 있으므로 WebView2에서도 실제 붙여넣기·복사를 확인한다.

변환 요청은 기존 저장·이력·보존·개인정보 확인·과금 정책을 따른다. 일회성 무저장 검사나 무료 검사로 안내하지 않는다. 별도 검사 API, 실시간 밑줄 검사, 새로운 교정 이유 생성은 추가하지 않고 기존 응답에서 제공하는 검토 정보만 표시한다.

## 5. Windows 최소 범위

- 기술 제안: C#/.NET WinForms의 `NotifyIcon`과 WebView2, Win32 `RegisterHotKey`. 새 코드의 책임은 OS 창과 실행 보조에 한정한다.
- 현재 저장소의 제품 런타임 지침은 Kotlin/React다. 후속 구현에서는 사용자가 요청한 Windows 보조 앱의 좁은 경계를 별도 `desktop-windows/AGENTS.md` 등에 명시하고 제품 로직을 옮기지 않는다. 이번에는 프로젝트나 런타임 지침을 변경하지 않는다.
- 트레이 메뉴는 열기와 종료만 둔다. 단축키 후보는 `Ctrl+Alt+E`; 점유된 경우 실패를 알리고 트레이 열기를 제공한다.
- 프로세스와 웹 창은 하나씩 유지한다. 숨김 후 재호출은 기존 WebView를 다시 보여준다.
- 로그인 유지에는 사용자별 WebView2 데이터 폴더를 사용한다. 브라우저의 쿠키·웹 저장소가 남을 수 있으며, 이를 무저장 앱으로 설명하지 않는다. 네이티브에서 별도 비밀번호·토큰 저장 기능을 만들지 않는다.
- 일반 Edge/Chrome과 로그인 세션을 공유하지 않는다. 시범 범위는 기존 이메일 로그인으로 검증한다. 소셜 로그인은 공급자의 내장 브라우저 허용 여부가 확인된 경로만 제공하며, 미지원 시 기존 브라우저에서 웹 흐름 전체를 사용할 수 있게 한다. 브라우저와 앱 사이 인증 토큰 전달은 구현하지 않는다.
- 고정된 제품 HTTPS 주소를 로드한다. 인증 등 필요한 이동 경로를 확인하고 외부 링크·새 창 요청을 처리한다. 임의 웹페이지에 네이티브 권한을 주는 범용 JS 브리지는 만들지 않는다.
- 네이티브 클립보드 접근, 본문 전송, API 호출, 로컬 HTTP 서버, 자동 키 입력, 편집기별 제어는 제외한다.
- Evergreen WebView2 Runtime 존재 여부를 확인한다. 없는 PC에는 설치 안내를 제공한다. .NET 런타임 포함 배포의 용량과 실행 가능 여부는 실제 Windows에서 확인한다.
- 시범 배포는 사용자 권한 실행과 수동 업데이트로 제한한다. 자동 업데이트, 시작 프로그램 등록 UI, 복잡한 설치 마법사는 제외한다. 공개 배포의 코드 서명과 기관 설치 조건은 별도 산정한다.

## 6. 구현 순서와 완료 기준

현재 개발 환경은 Mac이다. React 웹 화면과 Windows 앱 소스는 Mac에서 작성하고, 작은 창 크기의 웹 UX도 Mac 브라우저에서 검증한다. .NET의 `EnableWindowsTargeting`으로 Windows 대상 빌드가 가능하지만, 배포용 빌드는 Windows CI에서 수행한다. 트레이·단축키·WebView2 및 Word·아래한글과의 실제 왕복 동작은 Windows PC 또는 VM에서 확인한다. CI 빌드 성공을 실제 Windows UX 검증으로 대신하지 않는다.

Mac에서 웹 개발을 먼저 진행할 수 있으며, 아래 WebView2 확인은 Windows 셸 본격 구현 전의 검증 단계다.

1. 기존 웹을 실제 WebView2에서 열어 이메일 로그인, `Ctrl+V`, 결과 복사와 세션 유지를 짧게 확인한다. 여기서 새 인증 연동이 필요하면 시범 범위를 기본 브라우저 방식으로 축소한다.
2. 웹의 빠른 입력, 좁은 화면 레이아웃과 최신 수정문 복사를 구현한다. 서버 계약 변경은 계획하지 않는다.
3. 트레이·단축키·창 위치·표시/숨김을 붙이고 Windows 패키지로 확인한다.
4. 실제 Windows에서 Word와 아래한글 각각 한 문단을 복사하고, 웹 창에서 수정·복사한 뒤 원래 편집기에 반영한다.

웹 검증은 `npm run check`, `npm run test -- --run`, `npm run build`다. 로그인 후 복귀, 좁은 창의 입력·결과, 최신 수정문 복사, 복사 실패 시 본문 유지에 집중한다. 기존 API 테스트 대역을 사용하고 실제 유료 LLM 호출은 별도 승인 없이 실행하지 않는다.

Windows는 기존 빌드 도구와 실제 PC에서 검증한다. 숨김·재표시 후 본문 유지, 한글·줄바꿈, 단축키 충돌, Runtime 부재, 네트워크 오류, 로그인 만료, 100/150/200% 배율과 다중 모니터, 앱 종료 후 단축키 해제를 확인한다. 새 검증 하네스는 만들지 않는다. 실제 Windows 확인 전에는 Windows 검증 완료로 기록하지 않는다.

첫 버전 완료 조건은 두 편집기에서 위 왕복 흐름이 동작하며 기존 계정·변환·이용량·문서 저장 기능을 재사용하는 것이다. 일반 텍스트가 대상이며 표 구조, 글꼴, 부분 강조와 자동 번호의 보존은 보장하지 않는다.

## 7. 공식 근거

- [MDN Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API): 브라우저 클립보드 권한과 사용자 동작 조건.
- [Microsoft NotifyIcon](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/controls/notifyicon-component-overview-windows-forms): 트레이 아이콘과 메뉴.
- [Microsoft RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey): 전역 단축키.
- [WebView2 데이터 폴더](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder): 쿠키·권한·저장소 관리.
- [WebView2 Runtime 배포](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution): Runtime 설치 확인과 배포.
- [.NET Windows 대상 빌드](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#enablewindowstargeting): 비 Windows 환경의 개발 지원과 Windows 배포 빌드 권장.
