# R7 문맥 기반 그림 제안·생성 수정 계획

작성일: 2026-09-24 · 상태: **사용자 의도 반영·계획 수정 완료, 구현 착수 결정 기록(§6), ER-17 착수**.

## 1. 확인한 불일치와 적용 범위

2026-09-18 명세는 R7을 최대 10종의 승인된 그림 카탈로그로 한정하고 이미지 생성 호출을 제외했다. ER-15/16 구현 기록과 현행 `contracts/easy-doc-v1.yaml`도 공개 SVG 카탈로그 조회 및 본문 줄별 수동 배치 저장을 정의한다. 따라서 기존 구현은 당시 축소된 명세를 따랐지만, 2026-09-24 사용자가 확인한 의도와 다르다.

**R7의 목표는 원문과 쉬운 글의 문맥을 이해하고, 그림으로 설명하면 이해가 쉬워지는 부분을 제안한 뒤, 사용자가 요청한 경우에만 해당 문맥을 설명하는 새 이미지를 생성하는 것이다.** 특정 낱말에 고정 아이콘을 붙이는 것은 이 목표의 완료 근거가 아니다.

이번 변경은 `docs/`의 계획·진행률 정정이다. 현행 계약과 제품 동작은 그대로이며 실제 이미지 생성·유료 호출·배포를 실행하지 않는다. 과거 ER-15/16 구현·테스트 기록은 보존하고, R7 전체는 미완료로 재분류한다. 기존 카탈로그는 선택 보조 자료로 남길 수 있지만 새 흐름의 필수 관문으로 두지 않는다.

## 2. 제안할 문맥과 제안하지 않을 문맥

분석은 개별 줄이나 키워드만이 아니라 문서 목적, 주변 문장, 관련 원문 조건·예외를 함께 읽는다. 하나의 그림이 여러 문단의 관계를 설명할 수 있다. 제안에는 대상 문맥, 원문 근거, 그림이 도움이 되는 이유, 그릴 내용과 보존할 조건이 있어야 한다.

| 입력 문맥 예시 | 기대 제안 | 피해야 할 결과 |
|---|---|---|
| 원문이 서류 준비 → 주민센터 제출 → 결과 통보 순서를 명시 | 각 행동과 순서를 보여 주는 3장면 절차 그림 | 서류·건물 아이콘을 줄마다 붙이기, 원문에 없는 방문·처리 기간 추가 |
| 원문이 두 대상의 신청 경로와 예외를 구분 | 두 경로와 예외를 구별하는 비교 그림 | 두 대상의 조건을 합치거나 예외를 생략 |
| 원문이 준비물의 구성·사용 관계를 설명 | 무엇이 어디에 쓰이는지 함께 보여 주는 설명 그림 | 장식용 사물 그림만 나열 |
| 연락처·날짜만 나열하거나 그림이 추가 이해를 주지 않음 | 제안 없음 | 모든 문단에 그림을 억지로 제안 |

날짜·금액·자격·AND/OR·예외의 근거가 불명확하거나 시각화하면 오해가 커지는 경우에는 제안하지 않는다. 원문 근거 위치를 검증할 수 없으면 생성 가능한 제안으로 노출하지 않는다. 이 검사는 모든 의미 오류의 자동 검출을 보장하지 않으며, 실제 품질 평가는 별도로 수행한다.

## 3. 사용자 흐름과 상태

1. 저장된 변환 결과에 대해 문맥에 맞는 **텍스트 제안**을 보여 준다. ‘이 신청 순서를 그림으로 보면 이해하기 쉬워요’처럼 이유와 관련 문맥, 그림 구성 요약을 함께 표시한다. 이미지는 이 단계에서 생성하지 않는다.
2. 사용자는 제안을 무시·닫거나, 구성 설명을 검토하고 ‘이 내용으로 그림 만들기’를 누른다. 이용량이 발생하면 요청 전에 차감량을 표시한다. 구성 수정은 원문 의미를 바꾸지 않는 범위에서 허용하고 수정안을 다시 검증한다.
3. 생성 중·완료·실패 상태를 표시한다. 탭을 닫았다가 돌아와도 같은 작업을 조회하며, 중복 클릭·새로고침으로 추가 생성·차감하지 않는다. 실패 뒤 재시도는 사용자의 새 요청으로만 한다.
4. 생성된 그림, 대체텍스트, 설명 문구를 원문 문맥 옆에서 미리 본다. 사용자가 관계·조건이 맞는지 확인하고 ‘문서에 추가’를 누를 때만 웹 문서에 적용한다. 생성 완료만으로 본문을 바꾸거나 그림을 자동 삽입하지 않는다.
5. 그림은 해당 문맥 옆의 별도 설명 요소로 저장하고 제거할 수 있다. 필수 정보는 텍스트에도 남긴다. 여러 문단을 설명하는 그림을 임의의 한 줄과 같은 의미로 취급하지 않는다.

| 상태 | 사용자에게 보이는 결과 |
|---|---|
| 제안 없음 | ‘이 문서에서 추가 그림이 도움이 될 부분을 찾지 못했습니다.’ 기능 자체의 실패로 표시하지 않음 |
| 제안 분석 실패 | 재확인 안내, 기존 글 편집·저장·내려받기는 계속 가능 |
| 본문 수정 중 | 저장 후 최신 문맥을 확인하도록 안내, 이전 제안의 생성·적용 비활성 |
| 이전 버전 | 이전 그림은 현재 미리보기에서 제외, 제안 재분석 및 그림 재확인 필요 |
| 생성 실패·결과 불명확 | 실패 상태·이용량 처리 표시, 자동 재호출 없음 |
| 생성 완료·미적용 | 미리보기와 적용/버리기, 본문은 유지 |

초기 출력 범위는 웹 미리보기와 생성 이미지 개별 내려받기다. 내려받기는 문서 소유자에게만 허용하며 문서 보존 기간을 따른다. DOCX/HWPX/TXT에는 새 그림이 포함되지 않음을 생성 전과 문서 내려받기 옆에서 알린다. DOCX/HWPX 삽입은 별도 서식 검증 후 확장하며 R7 기본 완료 조건으로 오인하지 않는다.

## 4. 구현 경계와 데이터 설계

아래는 후속 구현의 제안 계약이다. 실제 path·schema·migration은 구현 PR에서 확정하고 Kotlin DTO/계약 테스트와 `frontend/src/api/`를 함께 변경한다.

- **제안 분석:** 원문·저장된 쉬운 글·`content_revision`과 문맥 범위를 입력으로 받는다. 제안은 `suggestion_id`, 원문 앵커, 쉬운 글 문맥 범위, 설명 목적, 제안 이유, 그림 구성, 보존할 사실·조건, 대체텍스트 초안, 분석 버전을 가진다. 낱말→아이콘 매핑만으로 후보를 만들지 않는다.
- **분석 시점:** 신규 변환은 기존 텍스트 생성 호출의 구조화 결과에 제안을 함께 담는 방안을 먼저 검증한다. 기본 변환의 추가 호출은 만들지 않는다. 이미 저장된 문서·편집된 본문은 명시적인 ‘그림 제안 확인’으로 별도 분석한다. 별도 분석이 유료라면 실행 전에 이용량을 알리며 자동 유료 재분석하지 않는다. 제안 0건과 분석 실패는 구분한다. 기존 변환의 출력·지연 예산 안에 안전하게 통합할 수 없으면 별도 요청 분석으로 통일하고 설계를 갱신한다. **2026-09-24 결정: 별도 요청 분석으로 통일했다(§6).**
- **이미지 생성 작업:** 검증된 제안 ID/버전, 구성 revision, `expected_content_revision`, `request_id`로 접수한다. 소유권·보존 만료·토글·현재 버전과 이용량을 서버에서 검사한다. 서버가 검증한 구성으로 프롬프트를 만들며 클라이언트가 보낸 임의 원문 근거를 신뢰하지 않는다.
- **중복·실패:** 같은 요청 키와 입력은 같은 작업, 다른 입력은 충돌이다. 한 사용자 생성 요청당 이미지 1장, provider 시작 최대 1회, 자동 재시도 0회를 기본안으로 한다. 호출 뒤 중단·타임아웃은 결과 불명확으로 기록하고 자동 재호출하지 않는다. 재생성은 별도 요청·이용량 안내를 거친다.
- **작업과 적용 분리:** 작업 상태 조회, 이미지 조회/내려받기, 명시적 적용/제거를 구분한다. 생성 결과는 현재 문맥과 대조·확인할 후보이며 원문 정확성 인증이 아니다. 적용 시 본문과 그림 상태 revision을 함께 검사한다. 생성 중 본문 변경·삭제·만료 시 결과를 현재 문서에 붙이지 않는다.
- **저장·접근:** 제안·프롬프트·이미지·대체텍스트는 사용자 문서 파생 자료다. 기존 공개 카탈로그 이미지 API로 제공하지 않는다. 인증된 소유자만 조회하고 암호화·키 회전·문서 만료·삭제·탈퇴 파기를 함께 구현한다. 객체 저장소를 쓰면 비공개 저장과 파기 재시도까지 검증한다. 원문·프롬프트·이미지를 로그에 남기지 않는다.
- **표현 검수:** 성인 독자를 어린이처럼 묘사하지 않고 장식보다 행동·관계를 설명한다. 생성 이미지 안의 글자에 중요한 조건을 맡기지 않는다. 필요한 정확한 명칭·수치·설명은 검증 가능한 텍스트와 대체텍스트로도 제공한다.
- **기능 전환:** 기존 카탈로그 토글을 켜는 것만으로 유료 생성이 활성화되지 않게 한다. 문맥 제안·이미지 생성 capability를 구분하고 기본 OFF로 추가한다. 구형 클라이언트·기존 배치 데이터는 보존하고 신규 흐름을 꺼도 본문 편집·저장·기존 출력은 동작한다.

## 5. 작업 순서와 완료 기준

| 작업 | 산출물·수정 경계 | 검증 |
|---|---|---|
| ER-17 문맥 제안 | 대표 문맥·무제안 사례, 구조화 제안과 근거/버전 검사, 계약·Kotlin·React API 및 제안 카드 | AC-R7-c/d, 기존 호출 수·본문 변환 회귀 |
| ER-18 요청형 생성 | 이미지 provider 포트/fake, 작업·멱등성·이용량 정산·비공개 자산·삭제, 계약/소비자 동기화 | AC-R7-e/f/h/i, 실제 유료 호출 없이 작업 경계 검증 |
| ER-19 검토·적용 UX | 생성 요청·상태 복구·미리보기·대체텍스트 확인·선택 적용/제거·개별 내려받기 | AC-R7-f/g/h, 기존 Playwright에 사용자 흐름 추가 |
| ER-20 품질·출시 | 승인된 실제 이미지 평가, 원문 의미 대조·이해 도움·비용/지연 측정, 운영/공개 안내 | AC-R7-c~i 및 별도 승인·달러 상한, R7/M4 판정 |

ER-17 → ER-18 → ER-19 → ER-20 순서다. ER-17은 기존 R1 본문 버전 기반을 재사용하며 ER-15의 고정 카탈로그에 의존하지 않는다. ER-18의 작업 접수·정산 패턴은 기존 작업 큐를 검토해 재사용하되 R2와 이미지의 요금을 동일하다고 가정하지 않는다.

변경별 기존 검증을 사용한다: `cd backend-kotlin && ./gradlew build`, `cd frontend && npm run check && npm run test -- --run && npm run build`, `docker compose config`, 관련 기존 Playwright. 새 검증 하네스는 만들지 않는다. 최종 diff 기준으로 검증·리뷰하고 구현 회차별 재작업 상한은 착수 시 정한다. 이번 문서 수정은 링크·요구사항 추적·상충 문구·`git diff --check`를 검증하고 리뷰 후 수정은 최대 2회로 제한한다.

## 6. 확정한 의도와 남은 결정

사용자가 확정한 것은 **문맥 기반 제안과 사용자 요청 후 이미지 생성**이다. 제공사·모델, 이미지 규격, 단가·고객 차감량, 문서당 횟수·동시성·시간·저장 상한, 별도 제안 분석 비용, 이용 권리·provider 보존 조건은 구현·출시 전 확정할 항목이다. 기존 카탈로그의 최대 10종/10배치를 이미지 생성 상한으로 자동 승계하지 않는다.

고객 과금의 제안 기본안은 생성 전 예약, 유효한 후보 제공 시 소비, 제공 전 실패·stale·만료 시 반환이다. 제공 후 사용자가 적용하지 않은 경우의 처리까지 명시해 확정하며, 실제 provider 비용은 실패·결과 불명확도 별도로 기록한다. D03/D04의 기존 텍스트 산식·횟수는 이미지 요금 승인으로 해석하지 않는다.

**2026-09-24 구현 착수 결정(사용자 선택):**

| 항목 | 결정 |
|---|---|
| 분석 시점 | **별도 요청 분석으로 통일.** 신규·기존 문서 모두 명시적 ‘그림 제안 확인’으로 한 번 분석한다. 기본 변환 프롬프트·출력은 바꾸지 않는다. 변환 호출 통합은 ER-20 평가 뒤 재검토 |
| 고객 이용량 | 예약→소비→반환 흐름은 구현하되 차감량은 구성값. 실제 provider 모드에서 미설정이면 접수 거부, fake 모드에서만 0 허용. 산식은 D10에서 확정 |
