# Easy-Read AI v0.app UI/UX 재구성 기획

- 작성일: 2026-08-24
- 상태: 디자인·정책 초안 (구현 승인 아님)
- 대상: React/TypeScript 사용자 화면, 운영자 관리자 화면, 요금 안내 화면
- 제외: Kotlin/React 구현, API 계약 변경, PG 연결, 실제 LLM 호출

## 1. 목표

Easy-Read AI의 핵심 경험을 다음 한 문장으로 정리한다.

> 담당자가 원문을 넣고 변환 조건을 고르면, 사용량을 미리 확인한 뒤 AI 초안을 받아 검수하고 내려받는다.

이번 재구성은 현재 Lean MVP의 업로드·변환·검수·기록 기능을 버리지 않고, 정식 출시를 위해 필요한 구독·사용량·조직·운영 화면이 들어갈 자리를 설계하는 작업이다.

## 2. 조사 결과와 설계 원칙

### 2.1 현재 제품 기준

- 현재 사용자 화면은 로그인/가입, 텍스트·파일 입력, 변환 진행, 원문/결과 검수, 변환 기록, 작업 공간 선택으로 구성돼 있다.
- 결제·사용량 차감·운영자 어드민은 아직 구현되지 않았다.
- 결과는 반드시 `AI가 만든 초안`으로 표시하고 사람이 검수해야 한다.
- 지원 입력은 텍스트와 docx/pdf/hwpx이며, 현재 문서당 상한은 공백 포함 4,000자다.
- 외부 HTTP 변경은 계약, Kotlin DTO/테스트, `frontend/src/api/`를 한 변경 단위로 다뤄야 한다. 이 문서는 필요한 화면과 데이터만 정의하고 계약을 직접 바꾸지 않는다.

### 2.2 v0.app 사용 방식

v0 공식 가이드는 복잡한 다중 역할 제품을 먼저 기획하고, 한 번에 전체 기능을 생성하기보다 컴포넌트와 화면을 나눠 점진적으로 만드는 방식을 권장한다. 따라서 공통 디자인 시스템을 먼저 만들고 사용자·관리자·요금 화면을 별도 프롬프트로 확장한다.

참고 자료:

- [v0 Text Prompting](https://api2.v0.dev/docs/text-prompting)
- [v0 PRD design](https://v0.dev/docs/prd-design)
- [v0 Design systems](https://v0.dev/docs/design-systems)
- [v0 Full-stack apps](https://v0.dev/docs/full-stack-apps)

### 2.3 제품 디자인 원칙

1. **쉬운 말 우선**: 내부 용어인 system prompt, inference, provider는 일반 사용자에게 노출하지 않는다. `변환 설정`, `쉬운 글 만들기`, `사용량`으로 표현한다.
2. **결제 전 예측 가능성**: 실행 전에 예상 차감량과 변환 후 잔여량을 보여 준다.
3. **AI보다 검수 강조**: 결과 화면의 핵심 행동은 생성이 아니라 비교·수정·저장·내려받기다.
4. **공공 업무에 맞는 신뢰감**: 과도한 그라데이션, 네온, 챗봇형 장식 대신 차분한 문서 업무 도구로 표현한다.
5. **접근성 기본값**: 키보드 조작, 명확한 초점, 색 이외의 상태 표현, 4.5:1 이상의 본문 대비, 충분한 글자 크기와 줄 간격을 요구한다. 기준은 [KWCAG 2.2](https://wa.or.kr/board/view.asp?BoardID=0004&page=1&sn=22592)다.
6. **민감정보 최소 노출**: 관리자 목록과 분석 화면에 원문·변환문을 표시하지 않고 문서 ID, 상태, 글자 수, 토큰, 오류 코드만 보여 준다.

## 3. 사용자와 역할

### 3.1 기관 사용자

- 복지관·학교·주민센터·구청에서 안내문을 작성하거나 배포하는 실무자
- AI 사용 경험이 많지 않을 수 있으며, 빠른 결과보다 올바른 검수와 재사용 가능한 파일을 중시한다.
- 주요 과업: 변환, 검수, 다운로드, 기록 검색, 잔여 토큰 확인, 결제/견적 확인

### 3.2 기관 관리자

- 기관의 계약·구독·부서 계정·공용 토큰을 관리하는 담당자
- 주요 과업: 구성원 초대, 사용량 확인, 결제 문서 다운로드, 플랜 변경 문의
- Enterprise의 부서 계정 공유가 구현되기 전에는 메뉴를 숨기거나 `도입 예정`으로 명확히 표시한다.

### 3.3 서비스 운영자

- Easy-Read AI 내부 운영·CS 담당자
- 주요 과업: 고객/구독 상태 확인, 사용량·원가 관찰, 실패 작업 대응, 토큰 수동 조정, 공지와 감사 기록 확인
- 원문 열람 권한은 기본 제공하지 않는다.

## 5. 핵심 사용자 흐름

### 5.1 새 변환

1. 사용자가 `텍스트 붙여넣기` 또는 `파일 올리기`를 고른다.
2. 대상 독자와 변환 수준을 고른다. 초기값은 `일반 쉬운 글`이며 고급 옵션은 접어 둔다.
3. 서버가 조합할 프롬프트의 의미를 `짧은 문장`, `어려운 말 풀이`, `중요 정보 유지` 같은 체크 항목으로 보여 준다. system prompt 원문을 편집하게 하지는 않는다.
4. 글자 수를 기준으로 예상 서비스 토큰을 계산해 `예상 3토큰 · 변환 후 약 197토큰`처럼 표시한다.
5. 사용자가 `쉬운 글로 바꾸기`를 누르면 입력 검증 후 작업을 접수한다.
6. 대기/처리 상태를 단계형으로 표시하고, 오래 걸릴 때 기록 화면에서 다시 확인할 수 있음을 안내한다.
7. 완료되면 원문과 쉬운 글을 나란히 보여 주고 `AI 초안` 고지를 첫 번째로 읽히게 한다.
8. 사용자는 수정·저장 후 docx/hwpx/txt로 내려받는다. 요금제에서 지원하지 않는 형식은 이유와 업그레이드 경로를 함께 보여 준다.

### 5.2 잔액 부족

- 입력을 버리지 않는다.
- `필요 3토큰 / 보유 1토큰`을 명확히 표시한다.
- 기관 구성원은 기관 관리자에게 요청, 기관 관리자는 플랜 변경 또는 추가 구매 문의로 연결한다.
- 결제 화면으로 이동해도 입력 초안은 세션에 보존한다.

### 5.3 운영자 토큰 조정

1. 고객 상세에서 현재 잔액과 최근 조정을 확인한다.
2. 증가/차감 수량과 필수 사유를 입력한다.
3. 확인 대화상자에서 기관, 변경 전후 잔액, 사유를 다시 보여 준다.
4. 저장 후 감사 로그 ID와 성공 알림을 표시한다.

## 6. 과금 정책

### 6.1 용어와 환산

요청된 `토큰 기반 월 결제`를 사용자에게 이해 가능한 서비스 단위로 정의한다.

- **변환 토큰**: 공백 포함 1,000자당 1토큰. 소수점은 올림한다.
- **LLM 토큰**: 공급자가 과금하는 입력/출력 토큰. 운영자 원가 화면에만 표시한다.
- **페이지 상당량**: 가격 비교를 돕는 표시 단위. 1페이지를 공백 포함 2,000자로 가정하므로 1페이지 상당량 = 2변환 토큰이다.
- 실제 차감은 파일의 물리적 페이지 수가 아니라 추출된 글자 수로 계산한다. 표와 각주에 이 사실을 상시 표시한다.

이 정의는 기존 마스터 기획의 `크레딧`을 `변환 토큰`으로 이름만 바꾸는 제안이다. 채택 시 `docs/master-plan.md`, 계약, 백엔드, 프런트 표기를 별도 변경 단위로 맞춰야 한다.

### 6.2 제안 요금표

| 플랜 | 타겟 고객 | 월 기본 제공량 | 월 구독 단가 | 연 결제 | 주요 기능 |
|---|---|---:|---:|---:|---|
| Basic | 소규모 복지관, 학교 | 100페이지 상당 / 200변환 토큰 | 99,000원 | 950,400원 (월 환산 79,200원) | 텍스트 변환, 쉬운 말 사전 추천 |
| Pro | 주민센터, 구청 실무 부서 | 500페이지 상당 / 1,000변환 토큰 | 290,000원 | 2,784,000원 (월 환산 232,000원) | Basic + HWPX 내려받기 |
| Enterprise | 시·도 단위 통합 부서 | 무제한 또는 계약별 합의 | 월 1,000,000원 이상 | 맞춤 견적 | Pro + 부서 계정 공유, CSAP 대응 옵션 |

- 연 결제 금액은 월 정가 × 12 × 80%로 계산했다.
- 위 표는 목표 상품 구성이다. 현재 기준으로 쉬운 말 사전, 결제/차감, 부서 계정 공유, 운영자 어드민은 미구현이므로 실제 공개 전 기능별 출시 상태를 다시 확인한다.
- 요청안의 `HWP 포맷 유지 다운로드`는 현재 계약의 `HWPX 내보내기`와 같지 않다. 구버전 `.hwp`와 원본 레이아웃 보존까지 제공하려면 별도 계약·구현·호환성 검증이 필요하다. 검증 전 공개 문구는 `HWPX 내려받기`로 제한하고 `포맷 유지`를 약속하지 않는다.
- Enterprise의 `무제한`은 비용 통제를 위해 계약서에 공정 사용 기준, 동시 작업 수, 비정상 사용 대응, 협의 사용량을 명시한다. 공개 화면에는 `무제한*`으로 표시하고 같은 화면에 조건을 둔다.
- `CSAP 보안`은 인증을 취득하기 전까지 제공 완료 기능처럼 쓰지 않는다. `CSAP 대응 옵션`, `인증 로드맵 문의`처럼 사실에 맞게 표시한다. SaaS CSAP는 인증받은 IaaS/PaaS 환경 등 별도 요건이 있으므로 [KISA CSAP 안내서](https://isms.kisa.or.kr/main/csap/notice/?boardId=bbs_0000000000000004&mode=list)를 기준으로 검토한다.
- VAT 포함/별도, 초과 사용 차단 시점, 미사용 토큰 이월, 중도 변경·환불, 결제 실패 유예 기간은 출시 전 결정해야 한다. 확정 전 v0 화면에는 `정책 확정 필요` 배지를 사용한다.

### 6.3 요금 페이지 필수 내용

- 월 결제/연 결제 토글과 `20% 할인` 표시
- 플랜별 대상, 제공량, 가격, 기능, CTA
- 미출시 기능에는 `도입 예정` 또는 `문의` 상태를 표시하고 실제 제공 기능과 섞지 않기
- `1변환 토큰 = 공백 포함 1,000자`, `페이지는 2,000자 기준 상당량` 설명
- 사용량 계산 예시: 2,450자 문서 → 3토큰
- 지원 형식과 출력 형식 비교
- 미사용량·초과분·해지·환불·갱신 정책
- 카드 자동결제와 계좌이체/세금계산서 경로 구분
- Enterprise 견적 문의 폼
- 서비스 사업자 정보와 거래조건 고지 영역

정기결제는 최초 인증 뒤 빌링키로 반복 승인되는 구조이므로 갱신일, 결제 금액, 해지 경로를 숨기지 않는다. 구현 참고는 [토스페이먼츠 자동결제 가이드](https://docs.tosspayments.com/guides/v2/billing), 거래조건 고지는 [전자상거래법 제13조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1027062829)를 확인한다.

## 7. 화면 상세

### 7.1 사용자 대시보드

- 첫 화면의 가장 큰 CTA는 `새 문서 변환`이다.
- 상단에 `잔여 184 / 200토큰`, 사용률 막대, 갱신일을 함께 표시한다.
- 최근 문서 5건은 제목, 상태, 작업 공간, 수정 시각, 사용 토큰만 보여 준다.
- 실패가 있을 때만 복구 안내 카드를 노출한다. 매출 그래프처럼 실무자 과업과 무관한 위젯은 넣지 않는다.

### 7.2 변환 화면

- 데스크톱: 왼쪽 입력 60%, 오른쪽 설정·예상 사용량 40%의 2열 구조
- 모바일: 입력 → 설정 → 예상 사용량 → 실행 순서의 1열 구조
- 입력 모드는 탭이 아니라 라디오/분할 버튼으로 명확히 선택한다.
- 개인정보 주의, 지원 형식, 4,000자 상한을 제출 버튼 근처에 둔다.
- 고급 설정은 기본 접힘이며, 사용자가 이해할 수 있는 결과 중심 표현을 쓴다.

### 7.3 검수 화면

- 상단 고정 영역: 상태, AI 초안 고지, 저장 여부, 사용 토큰
- 본문: 원문/결과 동기 비교, 결과 직접 편집
- 하단 또는 우측: 어려운 말 추천, 가린 개인정보, 다운로드
- 저장되지 않은 변경, 누락된 자리표시자, 다운로드 제한을 색만으로 구분하지 않는다.

### 7.4 운영자 대시보드

- 1행 KPI: 활성 기관, 유료 구독, 이번 달 변환 토큰, 변환 성공률
- 2행: 14일 성공/실패 추이, 서비스 토큰 대비 LLM 원가 추이
- 3행: 실패 작업, 결제 실패, 낮은 잔액 기관 등 조치가 필요한 목록
- 그래프의 모든 값은 표 또는 텍스트 요약으로도 접근 가능해야 한다.

## 8. 공통 상태 설계

모든 주요 화면은 다음 상태를 시안에 포함한다.

- 로딩: skeleton과 상태 문구
- 비어 있음: 이유 + 다음 행동 하나
- 오류: 사용자 문구 + 재시도/문의 경로
- 권한 없음: 필요한 역할과 돌아갈 위치
- 잔액 부족: 필요량/보유량 + 입력 보존
- 처리 지연: 기록에서 확인 가능하다는 안내
- 삭제/토큰 조정: 대상과 되돌릴 수 없음 또는 감사 기록을 확인하는 대화상자

## 9. 디자인 시스템 제안

- 톤: 공공 서비스의 신뢰감 + 쉬운 읽기, 밝은 배경 중심
- 기본색: 짙은 청록 또는 남색, 성공 초록, 경고 황갈색, 오류 진홍색
- 글꼴: Pretendard 우선, 시스템 한글 글꼴 폴백
- 본문: 최소 16px, 핵심 작업 화면은 17px 이상, 줄간격 1.6 이상
- 모서리: 8~12px, 그림자는 최소화하고 경계선과 여백으로 구조 표현
- 아이콘: 아이콘 단독 사용 금지, 항상 텍스트 레이블 또는 접근 가능한 이름 제공
- 표: 모바일에서 핵심 열 카드 변환 또는 가로 스크롤 안내
- 차트: 장식용 3D·도넛 남용 금지, 단위와 기간을 제목에 포함

## 10. API·데이터 후속 범위

시안 확정 뒤 별도 계약 설계가 필요한 데이터는 다음과 같다.

- 사용자/기관 역할과 운영자 권한
- 구독 플랜, 결제 주기, 갱신일, 상태
- 변환 토큰 잔액, 월 제공량, 예약/확정 차감, 조정 원장
- 견적·청구·세금 문서 메타데이터
- 팀 구성원과 초대
- 운영자 집계 지표, 변환 실패 검색, 감사 로그

토큰 차감은 `예상 → 예약 → 변환 성공 시 확정 / 실패 시 해제` 상태를 가져야 한다. 네트워크 재시도나 worker 재처리로 중복 차감되지 않도록 멱등 키를 사용해야 한다. 이 문서에서는 엔드포인트를 확정하지 않는다.

## 11. v0 산출물 수용 기준

- 사용자 앱과 운영자 어드민의 내비게이션이 분리돼 있다.
- 핵심 변환 흐름이 데스크톱과 모바일 모두에서 완성돼 있다.
- 요금표에 월/연 금액, 20% 할인, 토큰/페이지 환산과 Enterprise 각주가 있다.
- 로딩·빈 상태·오류·잔액 부족·권한 없음 시안이 있다.
- 키보드 초점, 레이블, 상태 텍스트, 대비가 명시돼 있다.
- 원문·변환문이 관리자 화면에 노출되지 않는다.
- 실제 API·LLM·PG를 호출하지 않고 목 데이터만 사용한다.
- Next.js 전용 서버 기능에 의존하지 않고 현재 React 18 + TypeScript + Vite로 옮길 수 있는 구조다.
