# 서비스 정체성 안내 재정비 — 로그인 전 화면·이용 가이드·첫 변환 화면

작성일: 2026-09-27 · 상태: 사용자 승인(2026-09-27), 구현 진행 중

## 1. 배경

며칠간의 파일럿 피드백에서 사용자들이 서비스의 정체성을 각자 원하는 대로 해석했다. 두 가지 오해가 반복된다.

1. **무엇을 위한 도구인지 모른다.** 관공서 담당자가 일반 주민, 특히 발달장애인 등 정보를 이해하기 어려운 사람이 읽을 수 있도록 안내문을 쉬운 글로 바꾸는 도구라는 사실이 화면에 없다. 변경 전 랜딩은 「어려운 안내문을 읽히는 문서로 바꾸세요」 한 줄과 예시 한 쌍이 전부였다(`frontend/src/pages/LandingPage.tsx`). 독자(누구를 위한 글인가)와 입력(어떤 문서를 넣는가)이 어디에도 없었다.
2. **「대충 넣어도 완벽한 것이 나온다」는 착각.** 일반 LLM 챗봇 경험을 그대로 가져온다. 「AI 초안」 고지는 있지만 랜딩에서는 회색 작은 글씨였고, 로그인·가입 화면의 고지는 모바일에서 숨겨졌다(`components/AuthIntro.tsx`).

담당자는 긴 설명을 읽지 않는다. 문장 수를 늘리지 않고 **첫 화면에서 5초 안에 「누구를 위해 · 무엇을 넣어 · 무엇이 나오는가」**가 읽히도록 배치를 바꾸는 것이 목표다.

사용자 결정(2026-09-27):
- 경쟁 제품·챗봇 이름을 쓰지 않고 **정의만** 명확히 적는다. 「~가 아닙니다」식 대비 문장도 쓰지 않는다.
- 로그인 후 **첫 변환(입력) 화면에도 같은 정의 한 줄**을 둔다. 새 확인 단계·상태 저장은 만들지 않는다.
- 독자는 master-plan §1 정의대로 **「발달장애인 등 정보를 이해하기 어려운 주민」**으로 부른다.

## 3. 정체성 문장(정본) — 모든 화면이 이 문장을 변형 없이 쓴다

**정의 한 문장**
> 행정·복지·법률 안내문을 발달장애인 등 정보를 이해하기 어려운 주민이 읽을 수 있는 쉬운 글 초안으로 바꿉니다. 마무리는 담당자가 합니다.

**세 가지 사실(목록용, 각 한 줄)**
- 누구를 위해 — 발달장애인·고령자 등 어려운 글을 읽기 힘든 주민
- 무엇을 넣나 — 주민에게 배포하는 안내문·신청 안내·공지문
- 무엇이 나오나 — 담당자가 확인하고 고쳐서 마무리하는 **초안**

**고지 한 문장(경고 블록용)**
> 결과는 초안입니다. 날짜·금액·대상·조건을 원문과 비교해 담당자가 확인한 뒤 배포하세요.

**문구 규칙**
- 한 문장 한 정보, 25자 내외. 화면당 새 문단을 만들지 않는다. 목록·칩·표만 추가한다.
- 「~합니다」체. 주어는 「담당자」 또는 「이 서비스」. 「AI가 ~해 드립니다」 금지.
- 금지어: 완벽·자동 완성·한 번에·혁신·스마트·누구나 쉽게(도구 사용 난이도 의미로). 경쟁 제품명 금지.
- 「초안」이 모든 대상 화면의 첫 스크롤에 1회 이상 보인다.
- 구현된 기능만 적는다(DESIGN.md §2, `docs/user-guide.md`). 당사자 감수·법률 자문·사실 확인 기능은 없으므로 「합니다」로 쓰지 않는다.

## 4. 화면별 변경

### 4.1 랜딩 `frontend/src/pages/LandingPage.tsx` — 주 변경

구조(hero → 변환 예시 1쌍)를 유지하고 정보만 보강한다. 카드는 최대 3개(DESIGN.md §5.2).

1. eyebrow → `공공기관 담당자용 · 쉬운 글 초안 도구`
2. h1 → 두 줄 유지(강조 span 구조 유지). 예: `주민 안내문을` / `누구나 읽을 수 있는 쉬운 글`로.
3. 부제 → §3 정의 한 문장.
4. CTA 2개 유지.
5. 고지 → 검수 화면 HITL 고지와 같은 경고 블록(`ShieldAlert` + `bg-warning-surface`, `role="note"`)으로 §3 고지 문장. hero 컬럼 안, CTA 바로 아래.
6. 새 섹션 「이 서비스가 하는 일」 — hero와 예시 사이. 한 카드 안에 2열(모바일 1열): `이런 문서에 맞습니다`(복지 서비스 신청 안내 · 주민 공지문 · 지원금·제도 안내) / `이런 문서는 넣지 마세요`(개인정보가 든 민원 서류 · 원문 없이 새로 쓸 글 · 법령 조문 전체). 카드 하단 한 줄 `원문에 없는 내용은 만들지 않습니다.`

## 6. 실행 순서

1. `feature/service-identity-guide` 브랜치.
2. Sonnet 실행 에이전트에 조각 A(랜딩)·B(AuthIntro)·C(가이드+Upload)·D(로고+DESIGN.md)를 파일이 겹치지 않으므로 병렬 위임. 지침에 §3 정본 문장과 문구 규칙을 그대로 싣는다.
3. 검증: `cd frontend && npm run check && npm run test -- --run && npm run build`.
4. 리뷰 패스(sonnet code-reviewer, 저작 에이전트와 분리) → push → PR → `/code-review:code-review` → 리뷰 대응. 머지·파일럿 반영(`docker_startup.sh restart`)은 사용자 승인 후.

## 7. 반영 후 확인(5초 테스트, 코드 없음)

파일럿 담당자 2~3명에게 새 랜딩을 5초 보여 준 뒤 세 질문: ① 이 서비스는 무엇을 하나요 ② 누구를 위한 글인가요 ③ 결과를 그대로 배포해도 되나요. 세 답이 §3과 맞으면 통과. 결과는 이 문서 하단에 날짜와 함께 기록한다. 참여자 이름은 저장소에 적지 않는다.
