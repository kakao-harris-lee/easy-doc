# 가입 시 약관·개인정보 수집·이용 동의

- 작성 2026-09-10. 사용자 지시: 「가입시 약관·개인정보 수집 동의 절차는 계획 작성 하고 로드맵에 포함해.」
- 근거: `docs/plans/2026-09-10-legal-tax-policy-final.md` §6. **파일럿의 선행조건이다** — 회원가입을 받는 이상 약관·방침을 «표시»하는 것만으로는 부족하고 **동의를 받아야 한다.**

## 1. 지금 참인 것

1. **동의 절차가 아예 없다.** 2026-09-10 코드 확인 결과 가입 화면(`frontend/src/pages/SignupPage.tsx`)에도, 계약(`contracts/easy-doc-v1.yaml`)의 `POST /auth/signup` 요청에도 동의 항목이 없다.
2. 가입 경로는 셋이다 — 이메일/비밀번호(`AuthService.signup`), 소셜 3종(`SocialLoginService.callback`), 그리고 추후 초대. **소셜은 콜백에서 계정이 만들어지므로 동의를 받을 화면이 그 앞에 없다.**
3. 이용약관·개인정보처리방침 문서는 **아직 없다**(법률 자문 뒤 확정). 푸터도 아직 없다(P0-13).
4. 계약 2.29.0, 마이그레이션 V20. 이 묶음은 **2.32.0 · V22**(주기 이용량 묶음이 2.30.0 · V21을, 개인정보 경고용 검출이 2.31.0을 쓴다 — 검출 쪽은 마이그레이션이 없다).

## 2. 결정

1. **필수 동의 둘, 선택 동의 하나.**
   - **[필수] 이용약관 동의**
   - **[필수] 개인정보 수집·이용 동의**
   - **[선택] 마케팅 정보 수신 동의** — 지금은 보낼 것이 없지만, 나중에 추가하면 **그때 다시 받아야 한다.** 처음부터 자리를 두는 편이 싸다. 기본값은 **꺼짐**이고, 켜지 않아도 가입이 된다.
2. **필수 항목을 하나로 묶지 않는다.** 「전체 동의」 체크박스는 편의로 둘 수 있으나, 각 항목이 **개별 체크박스**로 따로 존재해야 한다. 묶어서 한 번에 받으면 동의의 개별성이 깨진다.
3. **동의 없이는 가입되지 않는다.** 서버가 검증한다 — 화면만 막으면 API 직접 호출로 우회된다. 필수 동의가 빠지면 **422**다.
4. **무엇에 동의했는지 기록한다.** 표 `signup_consents(user_id, kind, agreed, document_version, agreed_at, ip_hash?)`. 나중에 「동의를 받았는가」를 입증해야 하는 자리이므로 **약관·방침의 버전**을 함께 남긴다.
   - 문서 버전은 파일 내용의 해시가 아니라 **명시적인 버전 문자열**(예: `terms-2026-10-01`)로 둔다. 사람이 읽고 대조할 수 있어야 한다.
   - IP는 남기지 않는 쪽을 기본으로 한다 — 분쟁 대비 가치보다 수집 최소화가 앞선다. 필요하다는 판단이 서면 그때 해시로 추가한다(자문 항목).
5. **소셜 가입은 콜백 앞에 동의 화면을 둔다.** 제공자에게 다녀온 뒤 **계정을 만들기 전에** 동의를 받는다. 이미 계정이 있는 사람(로그인)은 이 화면을 보지 않는다.
   - 구현상 이것이 이 조각에서 가장 까다로운 자리다. 콜백에서 「신규 가입인가」를 판정한 뒤 계정 생성을 미루고 동의 화면으로 보내야 한다.
6. **약관이 바뀌면 다시 받는다.** 재동의 흐름은 이번 범위 밖이지만, `document_version`을 남기는 것이 그 준비다. 기존 이용자에게 소급 적용하지 않는다.
7. **동의 화면에서 전문을 볼 수 있어야 한다.** 각 항목 옆에 「전문 보기」 링크를 두고 새 창이나 펼침으로 보여 준다. 링크만 있고 내용이 없는 상태로 가입을 열지 않는다 — **약관·방침 문서가 확정된 뒤에 이 조각을 배포한다.**
8. **탈퇴하면 동의 기록도 지운다.** `user_id` CASCADE. 법정 보존 대상이 되는지는 자문 항목이며, 그 답에 따라 분리 보존으로 바꾼다.

## 3. 슬라이스 (한 조각, M)

V22, `POST /auth/signup` 요청에 동의 필드 추가와 서버 검증(422), 소셜 콜백의 신규 가입 동의 단계, `SignupConsentRepository`와 기록, 계약 2.32.0, 가입 화면의 체크박스·전문 보기·오류 표시, 접근성(라벨 연결·오류 `role="alert"`), 인구조사·가드 테스트 갱신.

**선행 조건: 이용약관·개인정보처리방침 문서의 확정과 게시**(법률 자문 뒤). 문서 없이 체크박스만 먼저 넣지 않는다.

## 4. 수용 기준

1. 필수 동의를 모두 체크해야 가입 버튼이 열린다(화면).
2. **필수 동의 없이 API를 직접 부르면 422**이고 계정이 만들어지지 않는다(실 DB로 행 수 확인).
3. 선택 동의는 켜지 않아도 가입된다.
4. 가입 뒤 `signup_consents`에 항목별 행이 남고 **문서 버전이 함께** 기록된다.
5. **소셜 가입도 동의 없이는 계정이 만들어지지 않는다.** 이미 계정이 있는 사람은 동의 화면을 보지 않고 바로 로그인된다.
6. 탈퇴하면 그 사용자의 동의 기록이 0건이다.
7. 접근성: 각 체크박스에 라벨이 연결되고, 미동의 오류가 `role="alert"`로 읽힌다.
8. e2e: 동의 없이 가입 시도 → 막힘 → 동의 후 가입 성공.

## 5. 범위 밖

약관 변경 시 재동의 흐름, 만 14세 미만 확인(법정대리인 동의), 동의 철회 화면, 마케팅 발송 자체, 약관·방침 문안(법률 자문).

## 6. 자문에 함께 물을 것

`docs/plans/2026-09-10-legal-counsel-questions.md`에 실어 보낸다.

1. 필수·선택 동의 항목 구성이 맞는가. **개인정보 수집·이용 동의를 항목별로 더 쪼개야 하는가**(예: 필수 항목과 선택 항목의 분리 고지).
2. **동의 기록에 IP를 남겨야 하는가.** 남긴다면 원본인가 해시인가, 보유기간은.
3. 동의 기록이 **법정 보존 대상**인가. 탈퇴 시 즉시 파기해도 되는가.
4. **만 14세 미만** — 사용자 결정(2026-09-10)은 「막을 이유 없음」이다. 그런데 법은 만 14세 미만 아동의 개인정보를 처리할 때 **법정대리인 동의**를 요구하므로, 연령을 전혀 확인하지 않으면 그 절차를 갖춰야 하는 쪽으로 간다. **권고는 동의란에 「만 14세 이상입니다」 확인 한 줄을 두는 것이다** — 기관 담당자에게는 장벽이 아니면서 법정대리인 동의 절차를 없앤다. 확인받을 것: 이 한 줄로 충분한가, 아니면 실제 생년월일 확인까지 필요한가.
5. 소셜 가입에서 제공자로부터 받은 정보에 대한 동의를 **별도로** 받아야 하는가.
