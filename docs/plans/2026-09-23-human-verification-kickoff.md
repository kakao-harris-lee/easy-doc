# 쉬운글 개선 사람 검증 착수 계획

작성일: 2026-09-23 · 상태: **착수 준비**. R0~R7의 제품 코드는 모두 main에 병합됐고 신규 기능 토글은 전부 기본 OFF다. 남은 것은 대부분 코드가 아니라 사람과 운영이 확인해야 하는 항목이다(예외는 V4의 사전 exporter 변경). 이 문서는 그 항목을 트랙으로 나누고, 각 트랙의 선행 조건·필요한 결정·완료 기준·기록 위치를 고정한다. 실행 기록이 아니며, 배포·유료 호출·참여자 모집의 승인도 아니다.

### V1 운영 배포 전환 V27→V34

목적: 운영 스택을 현재 main으로 올리되 신규 기능은 전부 OFF로 유지한다. 이것이 V5와 「토글 ON 제한 파일럿」의 공통 선행 조건이다.

선행 조건과 절차는 [소수 크레딧 전환 §배포 절차](2026-09-21-fractional-credits.md)와 [검증·출시 계획 §7](2026-09-18-easy-read-validation-release.md)을 그대로 따른다. 요약하면 (1) 새 백업과 SHA-256 확인, (2) 접수 중단과 진행 중 작업·worker 정리, (3) 구버전 API·worker 동시 중단, (4) 이미지 빌드·V28~V34 적용·신버전 기동 — 예약이 남은 작업은 새 코드가 저장된 양으로 정산돼야 한다, (5) 소수 계약을 읽는 프런트 배포, (6) 100자 문서로 예약 0.1·소비·실패 반환과 계정/원장 합계 확인, (7) 환경·실행 커밋·schema·토글·확인 시각·담당·정상/실패 요청 ID·복구 경로를 기록. 정수 reader 구버전과 소수 값 DB를 혼용하지 않으며, 소수 거래가 생긴 뒤 구버전으로 단순 롤백하지 않는다.

주의: 이 호스트가 곧 운영 서버다. `docker compose up -d --build`는 곧 운영 변경이므로 사용자가 시각과 담당을 정한 뒤에만 실행한다. 기존 사용자 6명·작업 11건의 크레딧 잔액 숫자는 전환 후에도 보존돼야 한다.

완료 기준: 실행 커밋 = main, Flyway V34, 신규 토글 전부 OFF 확인, health 200, 100자 예약·소비·반환 3경로 확인, 첫 24시간 관측 담당·시각 기록. 기록 위치: `docs/reports/2026-MM-DD-pilot-cutover-v34.md`.

**2026-09-23 실행(K1 사용자 결정):** 15:23 KST에 전환을 실행했고 [기록](../reports/2026-09-23-pilot-cutover-v34.md)에 남겼다. Flyway V34, health 200, 토글 전부 OFF, 잔액·거래 보존을 확인했다. 16:09 KST 사용자 승인 유료 호출 1건으로 100자 예약 0.1·소비 경로를 확인했고(원장 grant → reserve → consume, 잔액 1.0 → 0.9), 24시간 관측은 담당 사용자·첫 판독 16:10 KST로 시작했다. **실패 반환 경로(운영 미유도)와 관측 종료 판독(2026-09-24 15:23 KST 이후)이 남아 있어 V1을 아직 완료로 표시하지 않는다.**

### V2 R2 실무자 탐색 파일럿

[R2 파일럿 패킷](2026-09-21-r2-pilot-packet.md)이 과제 배치(P01~P05 × 070/088/074/097, A/B 조건)·동의 문구·기록 양식·중단 기준을 이미 고정했다. 보존된 후보([평가 산출물](../reports/2026-09-21-r2-model-evaluation-artifacts/README.md))를 쓰므로 새 모델 호출이 없고, 운영 배포와도 독립이다. 진행자 사전 메모(088 비급여 범위 누락 — [개선 회차](../reports/2026-09-21-r2-bounded-quality.md)의 후보에서는 세 회차 모두 보존됐지만, 파일럿이 쓰는 보존 후보에는 그대로 남아 있음)는 패킷대로 참여자 응답 뒤에만 설명한다.

착수 전 채워야 하는 패킷 항목: 기관·실무자 3~5명(이름·연락처는 저장소 밖), 진행 일시·진행자·판정자, 참여 조건·크레딧 부담 없음 확인, 동의 방식, 기록 보관·삭제 기한과 담당, 중단·복구 담당.

완료 기준: 문서·조건별 표본 수, 정보 찾기 통과/평가 가능 질문 수, 활동 시간 중앙값, 수정 필요 항목 비율, 중대한 의미 오류 목록을 보고한다. 탐색 목표는 중앙값 20% 단축과 정보 찾기 성공률 유지다. 통과·미달 모두 R2 일반 출시 판정이 아니라 판정의 근거 하나다. 기록 위치: `docs/reports/2026-MM-DD-r2-practitioner-pilot.md`.

### V3 R3 실제 품질 평가(유료)

기존 Kotlin 품질 레인의 `EASYDOC_LANE_VARIANT=r3`를 쓰고 `EASYDOC_LANE_MAX_USD`로 상한을 건다. 새 실행 프로그램을 만들지 않는다. 검수 정의가 0건이므로 이번 평가는 **프롬프트 변형(공식 명칭 보존·첫 등장 설명)의 효과만** 잰다. 검수된 정의를 근거로 한 설명 품질은 V4 이후에만 측정할 수 있다. 두 측정을 같은 판정으로 합치지 않는다.

착수 전 고정할 것: 표본 — 보류 4건은 R2 평가에서 이미 열람했으므로 독립 표본이 아니다. 개발 6건은 반복 확인용으로만 쓰고, AC-R3 판정에는 [검증·출시 계획 §5.1](2026-09-18-easy-read-validation-release.md)대로 같은 유형의 새 공개 문서로 **대체 보류 표본**을 확보한다. 조건은 `BASELINE`과 `r3` 두 팔이며 조건당 2회다(한 팔만 돌리면 「BASELINE 대비」 판정이 성립하지 않는다). 그 밖에 모델·effort·입출력 상한, 최대 호출 수, 보수적 달러 상한, 판정 질문(R0 Q1~Q6과 공식 명칭 유지 항목)을 고정하고, 실행 전에 검증·출시 계획 §6의 승인 기록 행을 먼저 채운다. 실행 직전 provider·키·프로필·상한을 확인한다.

완료 기준: AC-R3 — 명칭·조건 유지, 필요한 첫 설명, 추가 호출 없음, BASELINE 대비 의미 오류 증가 없음. 통과해도 기본값은 BASELINE으로 두고, 켜는 결정은 별도로 한다. 기록 위치: `docs/reports/2026-MM-DD-r3-model-evaluation.md`와 검증·출시 계획 §6의 승인 기록 행.

### V4 사전 검수 정의 공급

R3·R6이 운영에서 의미를 가지려면 사전 색인에 명시적 `v=reviewed`가 있어야 한다. 현재 exporter(`dictionary/` 빌드 도구)는 이 키를 내지 않으며, Kotlin 쪽은 기존 `active`·review 상태·검수 메모를 자동 승격하지 않는다(R3 구현 보고서 「리뷰 리스크」).

작업 순서: (1) 사람이 검수할 정의 범위를 정한다 — 정의문이 있는 423건 전부인지, 공식 명칭(`keep`) 우선인지, (2) 검수 결과를 `dictionary/data/reviews/`의 기존 검수 SQL 방식으로 남긴다, (3) exporter가 검수된 정의에만 `v: "reviewed"`를 쓰도록 바꾸고 결정성·재현성 테스트를 통과시킨다, (4) 배포 색인을 재생성해 Kotlin 기동 검증과 `REVIEWED` 필터 테스트를 통과시킨다, (5) e2e 프로필의 fake 정의원 대신 실제 색인으로 R6 패널이 채워지는지 확인한다.

완료 기준: 운영 색인의 reviewed 정의 수 > 0이고 그 수·검수자·일자가 기록됨. 검수되지 않은 정의는 여전히 전달되지 않음. 기록 위치: `dictionary/README.md` 검수 결정 절과 `docs/reports/2026-MM-DD-dictionary-reviewed-definitions.md`.

### V5 게이트 ① 실제 문서 파일럿

성공 기준의 정본은 [master-plan §4.0](../master-plan.md)이고, 판정 절차·통과 기준·집계는 [파일럿 실행서 「게이트 ① 판정」](../pilot-runbook.md#게이트--판정)을 따른다. 사전 조건은 기관 1~2곳, 실제 업무 문서 10건(기관 합산, 가급적 실무자 2인 이상), 실제 provider와 유료 호출 승인, 기존 방식 소요 인터뷰, 개인정보 문서 지양 안내, 그리고 게이트 ⓪(긴 문서 처리)의 선행 판정이다. 게이트 ⓪은 2026-09-03에 상한 20,000자로 판정이 확정돼 이미 충족됐다. 통과 기준은 2026-09-04 확정값(배포 의향 8/10 이상, 만족도 평균 3.5 이상, 소요 시간 중앙값은 사람이 판정)이다.

V1이 끝나기 전에는 시작하지 않는다. 현재 운영 이미지는 R2 이전 코드라 소수 크레딧·4단어 제한·검수 지원이 없는 제품을 평가하게 되고, 그 결과를 현재 main의 판정으로 쓸 수 없다. 신규 기능 토글은 V5에서도 OFF가 기본이며, R1(검수 지원)만 켤지는 V1 뒤 별도로 정한다.

기록 위치: 실행서의 「기존 방식 소요」 표와 집계 절, master-plan §9의 게이트 ① 줄, `docs/reports/2026-MM-DD-gate-1-verdict.md`.

### V6 목표 독자 평가

검증·출시 계획 §5.3의 두 번째 단락 그대로다. 별도 모집·동의·접근 가능한 설명 뒤에 정보 찾기와 모의 신청 준비를 평가하고, 질문 오해와 문서 자체 이해 실패를 구분하며 집단별 결과와 표본 수를 함께 보고한다. 대외 효과 주장에 필요하지만 일반 표현 개선의 출시 선행 조건은 아니다. 이 문서에서는 트랙으로만 등록하고 착수 시점을 정하지 않는다.

## 3. 순서와 의존

```
지금 가능:   V2 (참여자만 확정)   V4 (검수자·범위 확정)   V3 (예산 확정, 프롬프트 효과만)
V1 배포 전환 ──▶ V5 게이트 ①
V4 검수 정의 ──▶ V3 재평가(검수 정의 효과) ──▶ R3/R6 운영 ON 결정
V6 은 독립, 시점 미정
```

V2·V3·V4는 서로 파일과 자원을 공유하지 않으므로 병행할 수 있다. V1은 이 호스트의 운영 변경이라 다른 트랙과 같은 시간대에 겹치지 않게 한다.

## 5. 이 문서가 아닌 것

- 배포·유료 호출·참여자 접촉의 승인이 아니다. 각 트랙은 §4의 해당 결정이 기록된 뒤에만 시작한다.
- 자동 검증 통과(§1.1)를 사람 검증 완료로 표현하지 않는다. 로드맵 §7의 완료 정의 중 이 날 자동 검증이 채운 것은 「구현·계약/소비자 일치·필수 검사·토글 OFF 회귀」이고, 「UX 예외 경로」는 각 ER 보고서의 fake E2E 기록에 의존하며 이 날 재실행하지 않았다. 「운영 확인·공개 가이드」는 V1·V5가 채우고, 검증·출시 계획 §5.3의 실무자·독자 평가는 V2·V6이 채운다.
- 새 검증 하네스·자동 모니터·실행 프로그램을 만들지 않는다. 기존 Gradle 품질 레인, Playwright, 실행서의 집계 절차를 그대로 쓴다.
