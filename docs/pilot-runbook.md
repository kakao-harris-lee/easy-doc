# 파일럿 세션 런북

파일럿 기관 실무자와 함께 앉아 **실제 문서 10건**을 처리하고, 그 결과로 Lean MVP의
성공 기준(master-plan 4.0)을 판정하기 위한 진행 가이드다.

판정하려는 것은 기능 목록이 아니라 두 가지 질문의 답이다.

1. 외주로 처리하던 시간이 **유의미하게 줄어드는가**
2. 실무자가 "이 결과물을 다듬어 **실제로 배포하겠다**"고 답하는가

이 두 답이 나오지 않으면 P0 기능을 더 만들어도 소용이 없다는 것이 4.0의 전제다.
따라서 세션의 목표는 제품을 잘 보이게 하는 것이 아니라, **판정에 필요한 사실을
정확히 모으는 것**이다. 잘 안 되는 문서가 나오면 그것이 가장 값진 데이터다.

> 화법 주의(master-plan 1.2): 안내·설명에 "의무화" 표현을 쓰지 않는다. 근거 조항과
> 평가지표 반영 추세까지만 말한다.

## 1. 사전 준비 (진행자, 세션 하루 전)

### 1-1. 스택 기동

```bash
docker compose up -d --build
```

확인 순서 — 하나라도 어긋나면 세션 중에 드러난다.

| 확인 | 방법 | 기대 |
|---|---|---|
| API 생존 | `curl -s localhost:8000/health` | `{"status":"ok"}` |
| 화면 | 브라우저로 `http://localhost:8080` | 로그인 화면 |
| 마이그레이션 | `docker compose logs migrate` | 정상 종료(코드 0) |
| 워커 | `docker compose logs worker` | `redis_version=... starting worker` |

**워커가 떠 있지 않으면 업로드는 접수되지만 변환이 `대기 중`에서 멈춘다.** 세션 중
가장 흔한 사고이므로 시작 직전에 한 번 더 본다.

### 1-2. 키 확인

`.env`에 아래가 채워져 있어야 한다. 값은 저장소에 넣지 않는다.

- `OPENAI_API_KEY` (또는 `ANTHROPIC_API_KEY`) — 없으면 변환이
  `failure_code: ProviderUnavailable`로 실패한다.
- `LLM_PROVIDER` / `LLM_MODEL` — 현재 기본은 openai `gpt-4.1`
  (근거: `docs/quality/2026-08-08-golden-reeval-gpt41.md`).
- `FERNET_KEY` — 없으면 문서 저장 자체가 안 되고, 세션 후 KPI 리포트도 만들 수 없다.
- `JWT_SECRET` — 없으면 로그인이 503이다.

키를 바꿨으면 `docker compose up -d` 로 컨테이너를 다시 만든다(`.env`는 기동 시점에만 읽는다).

### 1-3. 계정 생성

실무자 **본인 계정**을 세션 자리에서 직접 만들게 한다 — 진행자 계정을 빌려 쓰면
소유자별 목록·삭제 동작을 그대로 보여줄 수 없고, 세션 후 데이터 정리 주체도 흐려진다.

화면 우상단 "가입" → 이메일 + 비밀번호(8자 이상). 기관 메일 주소를 쓸 필요는 없다.

### 1-4. 리허설 1건

세션 시작 전에 진행자가 **공개 안내문 한 건**으로 업로드 → 변환 → 검수 → 내려받기를
한 바퀴 돈다. 첫 변환은 provider 연결이 처음 열려 조금 느리다.

## 2. 세션 시나리오 (실무자, 약 90분)

### 2-1. 문서 고르기 (10분)

실무자가 **실제로 쉬운 글로 바꿔야 했던 문서 10건**을 고른다. 우리가 고르지 않는다 —
잘 될 것 같은 문서를 골라 주면 판정이 무의미해진다.

권장 조건과 그 사유:

| 권장 | 사유 |
|---|---|
| **붙여넣기**로 입력 | 검수 화면의 원본 패널은 파일에서 **추출한 텍스트**다. 표·단 나눔·머리글이 평평해져 원본 문서와 눈으로 대조하기 어렵다. 붙여넣기는 실무자가 넣은 그대로가 원본 패널에 남는다 |
| 문서당 **2,000자 내외** | 2,600자를 넘으면 모델이 스스로 요약해 내용이 빠지는 경향이 실측됐다(장문 입력에서 출력이 원문의 0.56배로 압축 — `docs/quality/2026-08-07-fidelity-diagnosis.md`). 긴 문서는 안내문 단위로 잘라 넣는다 |
| 종류를 섞기 | 신청 안내·자격 요건·일정 공고 등을 섞어야 어떤 유형에서 무너지는지 보인다 |

상한은 **4,000자**다. 넘기면 업로드 단계에서 거절된다(문단 분할 변환은 다음 단계).

### 2-2. 한 건씩 처리 (60분)

문서마다 같은 순서를 밟고, **문서 한 건이 끝날 때마다** 기록표(3-1) 한 줄을 채운다.

1. 본문 붙여넣기 → 올리기
2. 변환이 끝나면 검수 화면에서 왼쪽(원본) / 오른쪽(쉬운 글) 대조
3. 가려진 개인정보 목록을 확인 — 과하게 가려진 항목이 있는지 본다
   (누락보다 과잉이 안전하다는 정책이라 기관 대표번호도 가려진다 — master-plan 3.2)
4. 실무자가 **직접 고친다.** 진행자가 대신 고치지 않는다 — 수정률이 KPI다
5. 저장 → docx로 내려받기
6. 기록표 한 줄 작성

진행자가 세션 중에 하지 말아야 할 것:

- 결과를 변호하지 않는다. "원래 이런 문서는 어렵습니다" 같은 말은 데이터를 지운다
- 실무자 대신 문장을 고치지 않는다
- 잘 나온 문서를 다시 보여주며 인상을 덮지 않는다

### 2-3. 마무리 대화 (20분)

기록표를 함께 보며 3-3의 질문지를 진행한다.

## 3. 측정 항목

### 3-1. 문서당 기록표 (손으로 적는다)

| # | 문서 유형 | 글자 수 | 붙여넣기/파일 | 시작 시각 | 배포 가능 판단이 선 시각 | 손댄 정도(체감) | 메모 |
|---|---|---|---|---|---|---|---|
| 1 | | | | | | 안 고침 / 조금 / 많이 / 다시 씀 | |
| … | | | | | | | |

- **시작 시각**은 붙여넣기를 누른 순간, **끝 시각**은 실무자가 "이 정도면 배포하겠다"고
  판단한 순간이다. 저장 버튼이 아니라 판단 시점을 적는다.
- "손댄 정도(체감)"는 실무자의 주관이다. 아래 스크립트가 재는 수치와 어긋나는 경우가
  오히려 중요한 신호라, **둘 다 적는다**.
- 실패한 건도 지우지 않는다. 사유(변환 실패·품질 미달·중단)를 메모에 남긴다.

### 3-2. 수정률·소요 시간 (스크립트가 잰다)

세션이 끝난 뒤 한 번 돌린다. 자세한 실행법은 4-1.

`scripts/pilot_report.py`가 DB에서 문서별로 다음을 뽑는다.

- 글자 수 / 변환 소요 시간 / 검수 여부 / 업로드→검수까지 걸린 시간
- **수정률** — AI 초안 대비 문자 단위 편집 비율(0% = 초안을 그대로 사용)
- 실패율과 실패 사유 코드

리포트에는 **문서 ID 앞자리와 수치만** 담긴다. 수정률 계산에는 본문 복호화가
필요하지만, 복호화한 글은 비율을 재는 순간에만 존재하고 리포트에는 남지 않는다.

### 3-3. 주관 평가 질문지 (마무리 대화에서)

**성공 기준 2문항 (master-plan 4.0 — 이 두 답이 판정이다):**

1. 같은 문서 10건을 기존 방식(외주·직접 작성)으로 처리하면 얼마나 걸렸습니까?
   오늘 걸린 시간과 비교하면 어떻습니까?
2. 오늘 만든 결과물 중 **실제로 배포하겠다**고 답할 수 있는 것은 몇 건입니까?
   (각각에 대해: 그대로 / 조금 더 다듬어서 / 못 쓰겠다)

**보조 질문:**

3. 가장 잘 나온 문서와 가장 안 나온 문서는 무엇이 달랐습니까?
4. 고칠 때 가장 자주 손댄 지점은 어디였습니까? (문장 길이 / 용어 / 빠진 정보 / 말투)
5. 가려진 개인정보 표시가 과했거나 부족한 곳이 있었습니까?
6. 이 도구를 다음 주 업무에 쓴다면 무엇이 먼저 있어야 합니까?
7. 기관 안에서 이 결과물을 검토·승인하는 절차는 어떻게 됩니까?

답변은 요약하지 말고 **말한 그대로** 적는다. 5·6번 답이 다음 미션의 우선순위가 된다.

## 4. 알려진 한계 — 세션 시작 전에 먼저 알린다

숨기면 실무자가 제품의 결함을 자기 잘못으로 오해하고, 그 순간 피드백의 질이 떨어진다.
아래를 미리 말해 두고, 해당하는 상황이 나오면 "말씀드린 그 지점"이라고 확인한다.

| 한계 | 세션에 미치는 영향 |
|---|---|
| **긴 문서의 스타일·충실성** | 2,600자를 넘으면 모델이 스스로 요약해 내용이 빠지는 경향이 있다. 골든셋 규칙 통과율이 아직 목표(90%)에 못 미치고, 위반의 상당수가 **문장 길이 초과**다 |
| **구버전 `.hwp` 미지원** | `.hwpx`(2010 이후)만 읽는다. `.hwp`는 한글에서 `.hwpx`로 저장하거나 본문을 붙여넣어야 한다 |
| **스캔 PDF 미지원** | 텍스트가 없는 이미지 PDF는 추출되지 않는다(OCR 없음) |
| **이메일 알림 없음** | 변환 완료를 화면에서 확인해야 한다. 긴 문서는 수 초~수십 초 걸린다 |
| **파일 업로드 시 원본 대조가 어렵다** | 원본 패널에는 추출된 평문 텍스트가 뜬다. 표·레이아웃은 남지 않는다 (붙여넣기를 권하는 이유) |
| **문단 단위 재변환 없음** | 마음에 안 드는 문단만 다시 돌릴 수 없다. 전체 텍스트를 직접 고친다 |
| **내려받기는 docx·txt** | pdf·hwp 내보내기는 다음 단계다 |
| **크레딧 차감 자동화 없음** | 파일럿 기간 사용량은 수기로 집계한다 |

## 5. 세션 후 정리

### 5-1. KPI 리포트 만들기

```bash
# 표준출력으로 확인
uv run python scripts/pilot_report.py

# 파일로 남기기 (기관·날짜를 파일명에 적는다)
uv run python scripts/pilot_report.py --since 2026-08-08 \
  --output docs/pilot/2026-08-08-○○기관.md
```

`--since`는 세션 당일 날짜를 준다 — 리허설·이전 세션 문서가 섞이지 않는다.
`FERNET_KEY`·`DATABASE_URL`이 있는 환경에서 돌려야 한다(호스트에서 돌린다면 `.env`가
가리키는 DB가 데모 스택의 것인지 확인).

리포트의 수치와 3-1 기록표의 체감을 나란히 놓고 본다. **둘이 어긋나면 그 문서를 따로
본다** — 수치상 조금 고쳤는데 체감이 "많이"라면, 짧지만 결정적인 수정(빠진 정보 보충)이
있었다는 뜻이다.

### 5-2. 데이터 삭제 안내

실무자에게 아래를 그대로 안내한다.

- 올린 문서와 변환 결과는 **암호화되어 저장**되며, 기본 **30일 뒤 자동으로 삭제**된다.
- 그 전에 지우고 싶으면 **변환 기록 화면의 각 줄에 있는 "삭제" 버튼**을 쓴다. 누르면
  문서와 변환 결과가 즉시 파기되고 되돌릴 수 없다.
- 세션 문서에 실제 민원인 정보가 들어갔다면, **세션이 끝난 자리에서 바로 지우는 것**을
  권한다. KPI 리포트는 지우기 **전에** 만들어야 한다(5-1이 먼저다).

기관 요청으로 전체를 앞당겨 파기해야 하면 운영자가 만료 삭제 잡을 손으로 돌린다.

```bash
docker compose exec worker python -m app.workers.purge
```

이 잡은 **보존 기간이 지난 문서만** 지운다. 아직 만료되지 않은 문서를 지우려면 화면의
삭제 버튼을 쓴다.

### 5-3. 판정 기록

세션당 아래를 한 장으로 남긴다. 이것이 영업 자료와 다음 미션 우선순위의 원천이다.

- 성공 기준 2문항의 답 (시간 단축 여부 / 배포 가능 건수)
- 문서별 기록표 + KPI 리포트
- 5·6번 답에서 나온 요청 목록
- 진행자가 관찰한 것 중 실무자가 말하지 않은 것 (막힌 지점·망설인 지점)
